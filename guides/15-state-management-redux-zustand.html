Global State: Redux, Zustand & Knowing When You Need Them

Where React state goes when it outgrows a single component — and the far more interesting question of whether it actually has.

I want to start this guide with a confession: for the first year I used Redux, I had no idea what problem it solved. I knew how to use it. I could write an action creator, a reducer, a connect call. But if you'd asked me "why does this exist?", I'd have said something vague about "managing state at scale" and hoped you'd move on.

That's exactly the answer that loses you an interview. Not because it's wrong, but because it's a phrase you memorised instead of a thing you understood.

So we're not going to start with Redux. We're going to start with a Tuesday afternoon and a component that needs a user's avatar.

Part 1 · The problemThe pain: prop drilling

Here's a real, small app. A user logs in. Deep inside the UI — inside the dashboard, inside the sidebar, inside the header of the sidebar — there's a little avatar badge that shows their profile picture.

The user object lives in App, because that's where we fetched it. The avatar badge lives eight levels down. So the user has to travel.

The journey of one prop
function App() {
  const [user, setUser] = useState(null);
  return <Dashboard user={user} />;
}

function Dashboard({ user }) {        // doesn't use it
  return <Layout user={user} />;
}
function Layout({ user }) {           // doesn't use it
  return <Sidebar user={user} />;
}
function Sidebar({ user }) {          // doesn't use it
  return <SidebarHeader user={user} />;
}
function SidebarHeader({ user }) {    // doesn't use it either!
  return <AvatarBadge user={user} />;
}

function AvatarBadge({ user }) {
  return <img src={user.avatarUrl} alt={user.name} />;  // 👈 finally
}

Four components in the middle take a prop they never read. They're couriers. They exist, as far as user is concerned, only to hand the parcel to the next person in the corridor.

This is prop drilling, and now that you've seen it, notice what's actually annoying about it. It isn't the typing. It's this:

  • To add one field to AvatarBadge, you edit five files.
  • Every intermediate component now has a prop in its type signature that lies about what it does. Sidebar claims to care about users. It doesn't.
  • If you want to reuse Sidebar somewhere without a user, you can't — the courier chain is baked in.

Wait — isn't prop drilling supposed to be A Bad Thing?

Honestly? Much less than the internet suggests. Passing a prop down two or three levels is completely normal React and needs no fix at all. Props are the most obvious, most debuggable data flow there is: you can trace exactly where a value came from by reading upward. Global state trades that away for convenience.

Prop drilling becomes a real problem when the chain is long and the value changes often and it's needed in many unrelated places. Two levels deep for a stable value is not a problem. Reaching for a state library to avoid it is genuinely worse than the disease.

So we've got a real irritation, but before we go shopping for a library, let's try the thing that costs nothing.

Part 2 · The cheap fixThe first fix is composition, not a library

Here's the move most people skip, and it's the one that senior engineers reach for first.

The reason Sidebar needs the user prop is that Sidebar is the one constructing AvatarBadge. But what if it didn't? What if Sidebar just left a hole in itself, and whoever renders it fills the hole in?

✅ Composition: pass the element, not the data
function App() {
  const [user, setUser] = useState(null);

  return (
    <Dashboard>
      <Layout>
        <Sidebar header={<AvatarBadge user={user} />} />  // 👈 built here
      </Layout>
    </Dashboard>
  );
}

function Sidebar({ header }) {
  return <aside>{header}<nav>...</nav></aside>;   // knows nothing about users
}

The user prop now travels zero levels. AvatarBadge is created right next to the state it needs, and then the finished element is handed down as children (or a named prop like header). The middle components hold an opaque box. They don't know or care what's in it.

The analogy I like: prop drilling is passing a letter hand-to-hand down a line of people, and every person has to be told they'll be handling a letter. Composition is writing the letter and sealing it in an envelope first. The people in the line still carry it, but now they just carry "an envelope" — the contents are none of their business, and nobody's job description changes when you change the letter.

Where the analogy breaks: React re-renders complicate this slightly. The element you pass as children was created by the parent, so it re-renders when the parent does, not when the middle components do — which is actually a nice performance side effect, but it's a different story from a physical envelope.

In an interview

If someone asks "how do you avoid prop drilling?" and your first word is "Context" — you've answered the recall question. If your first word is "composition, usually", you've answered the judgement question. Say both. The second one is the signal.

Composition doesn't fix everything, though. Sometimes the consumer isn't one element you can hoist — it's forty components scattered through the tree, all needing the theme, or the current locale, or the logged-in user. You can't hoist forty holes. This is where Context earns its keep.

Part 3 · ContextWhat Context solves — and what it very much doesn't

Context is React's built-in answer to prop drilling. You create a channel, a Provider broadcasts a value on that channel, and any component underneath tunes in — no matter how deep — without anyone in between knowing.

✅ Context: teleport a value down the tree
const UserContext = createContext(null);

function App() {
  const [user, setUser] = useState(null);
  return (
    <UserContext.Provider value={user}>
      <Dashboard />                     // no user prop anywhere below
    </UserContext.Provider>
  );
}

function AvatarBadge() {
  const user = useContext(UserContext);  // 👈 reaches up, 8 levels, instantly
  return <img src={user.avatarUrl} alt={user.name} />;
}

Beautiful. The couriers are gone.

Now here's the sentence that I want you to be able to say in an interview without hesitating, because it's the single crispest thing you can say about Context:

Context is a transport mechanism, not a state manager. It solves getting a value from here to there. It doesn't solve anything about how that value is stored, updated, or subscribed to.

People conflate the two constantly because Context is usually paired with useState — but the useState is doing the state management, and Context is doing the delivery. They're separate jobs. Let's be concrete about what "doesn't manage state" actually costs you.

1. Every consumer re-renders on any change

This is the big one. Imagine you get lazy — as everyone does — and make one AppContext holding everything:

❌ The context that re-renders your whole app
<AppContext.Provider value={{ user, theme, cart, notifications, setCart }}>
  <WholeApp />
</AppContext.Provider>

Two things are wrong here, and they compound.

First, that object literal { user, theme, ... } is a brand new object on every single render of the provider. Context compares values with Object.is. A new object is never Object.is-equal to the old one, so every consumer is notified — even if nothing inside actually changed.

Second — and this is the part people don't expect — even if you memoize that object perfectly, Context has no concept of "part of the value". If cart changes, the context value changed, so every component calling useContext(AppContext) re-renders, including the fifty components that only read theme and don't care about carts at all.

2. No selectors, so no partial subscriptions

Following directly from the above: there's no useContext(AppContext, value => value.theme). React has never shipped a selector API for Context (it's been proposed for years). Your only workaround is to split into many small contexts — one per slice — which works, but you're now hand-rolling the thing a state library gives you for free, and the nesting gets silly at ten providers deep.

3. No devtools

With Redux DevTools you get a scrolling log of every action, the state before and after each one, a diff view, and a slider that lets you scrub backwards through your app's history. With Context you get... console.log. When a bug is "the cart emptied itself and I don't know who did it", that difference is enormous.

4. No middleware

There's no place to hook into "every state change" globally. Want to log every update, persist a slice to localStorage, fire analytics on certain events, or retry a failed action? With Context you sprinkle that logic through components by hand. There's no interception point.

5. No state-shape discipline

Context imposes zero conventions. Anyone can put anything in there, update it from anywhere, in any shape. On a team of two that's freedom. On a team of twenty, six months in, it's a context value with 31 keys that nobody can safely change.

A common misconception

"Context causes performance problems."

Context itself is fine — it's a lookup, it's fast. What causes performance problems is putting frequently-changing state in a context that many components consume, because there's no way to subscribe to part of it. That's a design problem, not a Context bug. A theme context that changes twice a day is perfect. A mouse-position context that changes 60 times a second is a bonfire.

Right. We know what's missing. Now let's build the thing that provides it — and I mean literally build it, because Redux's core is smaller than you think.

Part 4 · Redux coreRedux from scratch: store, actions, reducers, dispatch

Forget every Redux tutorial you've seen. Redux's actual core is about twenty lines of vanilla JavaScript with no React in it at all. Let's write it.

We want one object holding all our state, a way to read it, a way to change it, and a way to be told when it changed.

Redux, more or less, in 18 lines
function createStore(reducer, initialState) {
  let state = initialState;
  let listeners = [];

  return {
    getState: () => state,

    dispatch(action) {
      state = reducer(state, action);   // 👈 the only line that writes state
      listeners.forEach((fn) => fn());
    },

    subscribe(listener) {
      listeners.push(listener);
      return () => { listeners = listeners.filter((l) => l !== listener); };
    },
  };
}

That's it. That's the whole idea. Everything else — Redux Toolkit, thunks, sagas, react-redux — is scaffolding around those three methods. If you can rebuild this on a whiteboard, you understand Redux better than most people who've shipped it.

Let's name the four nouns properly, because interviewers will use these words and expect you to use them back.

The store — one object tree

Not one store per feature. One store for the entire app, holding one plain-object state tree. It looks something like:

The whole app's state, in one object
{
  auth:  { user: { id: 'u7', name: 'Priya' }, token: 'abc' },
  cart:  { items: [{ sku: 'sku-42', qty: 2 }], coupon: null },
  ui:    { sidebarOpen: false, activeModal: null },
}

The single-store rule sounds restrictive and it is, deliberately. Because there's exactly one tree, you can serialise the entire app's state to a string, email it to a colleague, and they can load it and see precisely what you saw. That's not a party trick — it's the basis of bug reports that actually reproduce.

Actions — plain objects describing what happened

An action is not a command. This is the most commonly missed nuance. An action is a past-tense description of an event, in the form of a plain, serialisable object with a type field.

Actions are events, not instructions
// ✅ describes what happened
{ type: 'cart/itemAdded', payload: { sku: 'sku-42', qty: 1 } }
{ type: 'auth/loggedOut' }

// 🤔 works, but thinks like a command — the UI is dictating the update
{ type: 'SET_CART_ITEMS', payload: [ ...allTheItemsRecomputedInTheComponent ] }

Why does the distinction matter? Because if actions are events, many reducers can respond to one action. cart/itemAdded can update the cart, bump an analytics counter, and close the "empty cart" banner — three slices reacting to one fact about the world. If actions are commands ("set this value to that"), each one talks to exactly one place and you've just built a clumsier useState.

The analogy: an action is a receipt, not an order. It records that something occurred. Anyone can read the receipt afterwards and decide what it means for them. This analogy leaks a bit — real receipts don't cause anything to happen, whereas dispatching an action does trigger the update — but the "record of a fact, readable by many parties" part is exactly right.

Reducers — pure (state, action) => newState

A reducer takes the current state and an action, and returns the next state. It never modifies the state it was given. It computes a new value.

A reducer for the cart slice
const initial = { items: [], coupon: null };

function cartReducer(state = initial, action) {
  switch (action.type) {
    case 'cart/itemAdded':
      return { ...state, items: [...state.items, action.payload] };

    case 'cart/couponApplied':
      return { ...state, coupon: action.payload };

    default:
      return state;      // 👈 unknown action? hand back exactly what you got
  }
}

Two details that trip people up:

The default: return state is mandatory. Every reducer sees every action — there's no routing. If your cart reducer doesn't recognise auth/loggedIn, it must return the state unchanged, or it'd wipe the cart every time anyone logs in.

The spread is not decoration. { ...state, items: [...] } creates a new top-level object with a new items array, while coupon keeps its exact same reference. This is called structural sharing, and it's what makes change detection cheap: to ask "did the coupon change?", you compare two references with ===. No deep equality scan. Remember this term — it comes back when we do Immer.

Dispatch and subscribe — the cycle

Now we can draw the thing that Redux is really about: a strictly one-way loop that nothing is allowed to shortcut.

Walk it once with real events. You click "Add to cart". The click handler calls dispatch({ type: 'cart/itemAdded', payload: item }). The store hands the current state and that action to the root reducer. The reducer returns a new state object. The store swaps its internal state for the new one and calls every listener. react-redux is one of those listeners; it checks whether the slice your component reads actually changed, and if so, re-renders it. The UI now shows an extra item.

And critically: there is no other path. No component can write to the store. No reducer can be called except by a dispatch. In a big app, that means the answer to "how did this value get like that?" is always findable — it's in a reducer, responding to an action, which you can see in the devtools log.

Under the hood — how React connects to this

react-redux's useSelector is built on React 18's useSyncExternalStore hook, whose whole job is "safely subscribe a component to a store that lives outside React". It calls store.subscribe(), and on each notification runs your selector function and compares the result to last time (with === by default). Same result? No re-render. Different? Re-render.

That comparison is the entire reason selectors exist, and it's why the "why does my component re-render on every dispatch?" question has the answer it does. We'll get there in Part 10.

Part 5 · The whyWhy reducers must be pure

Redux insists that reducers be pure functions: same inputs always produce the same output, no mutation of the arguments, and no side effects (no API calls, no Math.random(), no Date.now(), no writing to localStorage).

That sounds like dogma until you see what it buys.

Time-travel debugging

If staten is purely a function of staten-1 and actionn, then the store can keep the list of actions and recompute any past state at will. Redux DevTools' time-travel slider isn't magic; it's just replaying the reducer from the start. The moment a reducer calls an API or reads the clock, replaying it produces a different answer, and time travel breaks.

Replayability and bug reports

A user hits a bug. You capture the action log. You replay it locally and land in the exact same broken state. That's only possible because reducers are deterministic and actions are plain serialisable objects — which, incidentally, is why "don't put a Promise, a function, or a class instance in an action payload" is a real rule and not fussiness.

Change detection

If a reducer mutated state.items.push(x) instead of returning a new array, the reference wouldn't change. === would say "nothing happened". Your component would not re-render, and you'd get the classic "the data is right in the devtools but the UI is stale" bug. Immutability isn't philosophical here — it's the mechanism that makes re-rendering work.

Testability

A pure reducer is the easiest thing in the world to test: call it with a state and an action, assert on the returned object. No mocks, no DOM, no network stubbing.

Wait — so where do API calls go?

Excellent, that's the exact question, and the honest answer is: outside the reducer. Side effects live in middleware (thunks, sagas) or in your components' event handlers. Part 9 is entirely about this. Hold the thought.

The honest bit: this is a lot of ceremony

Let's not pretend. To add one boolean to classic Redux you'd historically write: an action type constant, an action creator, a case in a reducer, a mapStateToProps, a mapDispatchToProps, and a connect call — across three or four files. For a boolean.

That ceremony is the reason the ecosystem moved. Not because unidirectional data flow was wrong — it was right, and it won so completely that it's now just how React works. But the packaging was exhausting, and everything that came after (Redux Toolkit, Zustand, Jotai) is an attempt to keep the good idea and drop the paperwork.

In an interview

Being able to say "the constraints exist to buy replayability and cheap change detection, and yes, classic Redux made you pay for that in boilerplate — which is exactly what RTK fixed" tells the interviewer you've held an opinion, not just an API surface. That's the depth signal.

Part 6 · JudgementWhen Context is enough vs when you need a real store

This is the question that actually gets asked, and the one where candidates flail because they answer with preferences instead of criteria. So here are criteria.

First, a split that reframes the whole problem:

Server state is not client state

Most of what people historically put in Redux wasn't really state — it was a cache of someone else's data. The list of products, the user profile, the order history: those live in a database on a server. Your app holds a copy that goes stale, needs refetching, needs loading and error flags, needs deduping when three components ask at once.

That's server state, and it has its own tool category — React Query / TanStack Query, SWR, RTK Query — which handles caching, staleness, background refetch and deduplication for you. That's covered in its own guide; I'm not going to duplicate it here. The only thing you need from it for this guide is the punchline:

Once you move server state to a query library, the amount of genuinely global client state left in a typical app is astonishingly small. Theme. Auth session. Sidebar open. A multi-step form in progress. A cart, maybe.

Which is why so many teams pulled Redux out around 2021–2023: it wasn't that Redux got worse, it's that 80% of what was in it belonged somewhere else.

The five questions

For whatever client state is left, ask these:

QuestionContext + useReducerRedux Toolkit / Zustand
How often does it change?Rarely — theme, locale, auth. Every consumer re-rendering is harmless.Often — a live cart, a canvas editor, form state, anything per-keystroke or per-frame.
How many independent slices?One or two. You can give each its own provider without silly nesting.Five or more unrelated slices. Provider pyramids get ugly fast.
Do you need partial subscriptions?No — consumers roughly all care about the same thing.Yes — a big state object where components read tiny disjoint pieces.
Devtools / middleware?Don't need an action log, persistence layer, or global interception.You want time travel, an audit log, undo/redo, persistence, analytics on every action.
Team size & conventionSmall team, everyone reads the whole codebase.Large team over years. You want enforced patterns so twelve people can't invent twelve state styles.

Notice that the last row has nothing to do with technical capability. It's a social argument, and it's a completely legitimate one — probably Redux's strongest remaining case. Redux Toolkit's opinionated shape ("slices, in features/, with these naming conventions") means a new hire can find things. Zustand will happily let each team member invent their own architecture.

My actual recommendation, stated plainly

  • Server data → React Query / RTK Query. Not Redux, not Context.
  • A couple of rarely-changing globals (theme, auth, locale) → Context, one provider per concern. No library.
  • Genuinely shared, frequently-changing client state in a small-to-mid app → Zustand. Tiny, no provider, selectors built in.
  • Large app, big team, complex flows, needs devtools and conventions → Redux Toolkit. It's still excellent at this and nothing has really replaced it.
  • Lots of fine-grained, interdependent derived values (an editor, a spreadsheet, a design tool) → an atomic library like Jotai. More on that in Part 12.

A common misconception

"You should put all your state in the global store."

No. Most state should stay local. If a value is only read by one component and its children, useState is the correct answer and moving it to a store makes the code worse — harder to trace, harder to delete, harder to reuse the component. Global state is a cost you pay to solve sharing. No sharing, no payment.

Part 7 · Tier 2Redux Toolkit vs classic Redux

Let's see the boilerplate problem with our own eyes, then watch it vanish.

❌ Classic Redux — one feature, spread thin
// constants.js
export const ITEM_ADDED = 'cart/ITEM_ADDED';

// actions.js
export const itemAdded = (item) => ({ type: ITEM_ADDED, payload: item });

// reducer.js
export function cartReducer(state = { items: [] }, action) {
  switch (action.type) {
    case ITEM_ADDED:
      return { ...state, items: [...state.items, action.payload] };
    default:
      return state;
  }
}

// store.js — plus applyMiddleware, composeEnhancers, devtools wiring...

Now the same thing in Redux Toolkit:

✅ Redux Toolkit — one file, done
import { createSlice, configureStore } from '@reduxjs/toolkit';

const cartSlice = createSlice({
  name: 'cart',
  initialState: { items: [], coupon: null },
  reducers: {
    itemAdded(state, action) {
      state.items.push(action.payload);   // 👈 wait, mutation?!
    },
    couponApplied(state, action) {
      state.coupon = action.payload;
    },
  },
});

export const { itemAdded, couponApplied } = cartSlice.actions;
export const store = configureStore({ reducer: { cart: cartSlice.reducer } });

Three things just happened, and they're worth naming individually because interviewers ask about them individually.

createSlice generates the actions from the reducers

You wrote a function called itemAdded. RTK produced an action creator cartSlice.actions.itemAdded that returns { type: 'cart/itemAdded', payload: ... } — the type string is auto-derived from name + the key. No constants file, no hand-written action creators, no chance of a typo'd string silently doing nothing. One place to change, and the whole triple stays in sync.

configureStore gives you sane defaults

Classic Redux's createStore gave you nothing: you wired up devtools by hand with a window.__REDUX_DEVTOOLS_EXTENSION_COMPOSE__ incantation, and added thunk yourself. configureStore ships with Redux DevTools connected, redux-thunk included, and — my favourite — dev-only middleware that throws if you accidentally mutate state outside a reducer or put a non-serialisable value in an action. It turns two of the classic silent Redux bugs into loud errors.

Immer: how "mutation" is safe

This is the one people ask about, so let's do it properly. That state.items.push(...) line looks like it breaks every rule in Part 5. It doesn't, and here's why.

The state object handed to your reducer is not your real state. It's a draft: a JavaScript Proxy wrapping the real state. A Proxy is a language feature that lets you intercept property reads and writes on an object. So when you run state.items.push(item), Immer's proxy notices "somebody is writing to items", and instead of touching the original, it lazily makes a shallow copy of just that branch and records the change there.

When your reducer returns, Immer walks what it recorded and produces a brand new state object where:

  • every branch you touched is a fresh copy with your changes applied, and
  • every branch you didn't touch is the exact same object reference as before — structural sharing, the same idea from Part 4.

"So does RTK actually mutate my state?"

No — and this is a real interview question, so here's the crisp answer. You mutate a draft proxy, not the state. Immer records those writes and produces a new immutable state via structural sharing; the previous state object is untouched, so time travel and === checks still work exactly as before.

Two practical caveats worth knowing: (1) don't both mutate the draft and return a new value from the same reducer — pick one, Immer throws otherwise; (2) Immer only proxies plain objects, arrays, Maps and Sets. A class instance or a Date in your state won't be drafted the way you expect, which is another reason to keep state plain and serialisable.

createAsyncThunk for async flows

Almost every async operation has the same three-phase shape: it started, it worked, it failed. createAsyncThunk generates all three action types for you.

✅ Async, with the three phases handled
export const fetchOrders = createAsyncThunk(
  'orders/fetch',
  async (userId) => {
    const res = await fetch(`/api/users/${userId}/orders`);
    return res.json();                // becomes action.payload on success
  }
);

const ordersSlice = createSlice({
  name: 'orders',
  initialState: { list: [], status: 'idle', error: null },
  reducers: {},
  extraReducers: (builder) => {       // 👈 responds to actions it didn't define
    builder
      .addCase(fetchOrders.pending,   (s) => { s.status = 'loading'; })
      .addCase(fetchOrders.fulfilled, (s, a) => { s.status = 'done'; s.list = a.payload; })
      .addCase(fetchOrders.rejected,  (s, a) => { s.status = 'error'; s.error = a.error.message; });
  },
});

extraReducers is where a slice reacts to actions defined elsewhere — the "many reducers can respond to one action" idea from Part 4, made concrete.

In an interview: "would you use Redux or Redux Toolkit?"

RTK is Redux. It's the official, recommended way to write Redux and has been for years — the Redux docs actively tell you not to hand-write the classic patterns. Saying "I'd set up a classic Redux store with action constants and connect" reads as "I learned this in 2017 and stopped reading". Not fatal, but it's a mild flag, and it's free to avoid: say RTK, and mention you know what it's abstracting over.

Part 8 · Tier 2Zustand: the store as a hook

Zustand ("state" in German, and yes it's a pun on Redux being Russian-ish sounding — the same author also made Jotai, "state" in Japanese) takes a different bet: keep the external store and the selector subscriptions, throw away the actions, the reducers, and the provider.

✅ A whole Zustand store
import { create } from 'zustand';

export const useCartStore = create((set) => ({
  items: [],
  coupon: null,
  addItem: (item) => set((s) => ({ items: [...s.items, item] })),
  clear:   () => set({ items: [], coupon: null }),
}));

State and the functions that change it live in the same object. And to use it:

✅ Reading with a selector
function CartCount() {
  const count = useCartStore((s) => s.items.length);  // 👈 subscribes to just this
  return <span>{count}</span>;
}

function AddButton({ item }) {
  const addItem = useCartStore((s) => s.addItem);     // stable, never re-renders
  return <button onClick={() => addItem(item)}>Add</button>;
}

Look at what's absent:

  • No <Provider>. The store is a module-level object; the hook reaches out to it directly. Nothing wraps your app.
  • No action types, no reducer, no dispatch. You just call addItem(item).
  • No re-render when coupon changes, in CartCount. The selector returned the same number, so useSyncExternalStore's comparison says "nothing to do". This is the Context problem solved by construction.

The "no provider" point has one nuance worth knowing, because it's a good follow-up answer: a module-level store is a singleton. That's fine in a browser app, but in SSR it means one store shared across all users' requests — so for Next.js you create the store per-request and pass it through a Context provider after all. Knowing that caveat is a nice depth signal.

The tradeoff, stated fairly

Redux ToolkitZustand
Bundle~12–14 kB gzipped (+ react-redux)~1 kB gzipped
BoilerplateLow (post-RTK), but real: slices, dispatch, action typesAlmost none
SubscriptionsSelector-based via useSelectorSelector-based, built in
DevtoolsFirst class, time travel, action logVia a middleware; usable, less rich
Enforced structureStrong — one obvious way to do thingsWeak — the store is just an object you wrote
AsynccreateAsyncThunk, middleware ecosystemJust async functions in the store

The critical honest point: Zustand's freedom is a real liability at scale. Redux's action log gives you an audit trail — a flat, named list of everything that has ever happened. Zustand's set calls are scattered across arbitrary functions; there's no equivalent narrative. On a team of three, you don't miss it. On a team of thirty, that narrative is how you debug production.

Part 9 · Tier 2Middleware: where the side effects go

Back to the tension we parked. Reducers must be pure. But real apps must call APIs, write to localStorage, fire analytics, set timers. So where does that code live?

Redux's answer is middleware: a chain of functions that every dispatched action passes through before it reaches the reducer. Think of it as airport security between the check-in desk (dispatch) and the plane (reducer). Every passenger walks through. Each station can inspect them, log them, delay them, redirect them, or refuse to let them through entirely.

The shape looks bizarre the first time you see it:

The middleware signature: three nested arrows
const logger = (store) => (next) => (action) => {
  console.log('dispatching:', action.type);
  const result = next(action);          // 👈 pass it to the next middleware
  console.log('new state:', store.getState());
  return result;
};

Read the layers outside-in — each one is applied at a different moment:

  1. (store) => runs once, at store creation. It hands you getState and dispatch.
  2. (next) => runs once per middleware, when the chain is assembled. next is "the rest of the chain" — the next middleware, or the reducer if you're last.
  3. (action) => runs on every dispatch. This is where your actual work happens.

The genius of next is that you decide the flow. Call next(action) to let it through. Don't call it, and the action dies right there. Call it with a different object, and you've transformed it. Call it later, and you've delayed it.

Thunk: "what if an action could be a function?"

Here is redux-thunk, in full. It really is this small:

The entire thunk middleware
const thunk = (store) => (next) => (action) =>
  typeof action === 'function'
    ? action(store.dispatch, store.getState)   // 👈 it's a function: run it
    : next(action);                            // plain object: business as usual

That's the whole idea. Normally you can only dispatch plain objects. With thunk installed, you can dispatch a function, and the middleware intercepts it and calls it, handing over dispatch and getState. Inside that function you can do anything — it's not a reducer, purity doesn't apply.

✅ An async flow as a thunk
const submitOrder = (cart) => async (dispatch, getState) => {
  dispatch({ type: 'checkout/started' });
  try {
    const order = await api.submitOrder(cart);
    dispatch({ type: 'checkout/succeeded', payload: order });
  } catch (err) {
    dispatch({ type: 'checkout/failed', error: err.message });
  }
};

dispatch(submitOrder(cart));   // dispatching a function 😅

Note the shape: the reducers stay pure. They only ever see the three plain objects. All the messy async lives in the thunk, outside the store's contract. That's the trick — side effects didn't disappear, they got moved to a place where they're allowed.

Saga: effects as data

redux-saga takes a stranger and more powerful approach using generator functions — functions declared with function* that can pause at each yield and resume later.

The key idea: a saga doesn't do the API call. It yields a plain object describing the call — call(api.submitOrder, cart) returns something like { type: 'CALL', fn: api.submitOrder, args: [cart] } — and the saga middleware performs it and feeds the result back in.

The same flow as a saga
function* checkoutSaga() {
  yield takeLatest('checkout/submitted', function* (action) {  // 👈 auto-cancels prior runs
    try {
      const order = yield call(api.submitOrder, action.payload);
      yield put({ type: 'checkout/succeeded', payload: order });
    } catch (err) {
      yield put({ type: 'checkout/failed', error: err.message });
    }
  });
}

Two payoffs, and then the judgement call — which is the only part you need at speaking speed.

Testability. Since call(...) only returns a description, you test a saga by stepping the generator and asserting on the yielded objects. No network mocking at all — you're asserting "it intended to call this, with these args."

Orchestration and cancellation. Saga has real vocabulary for this: takeLatest (cancel the previous run when a new one starts — correct for search-as-you-type), race (for timeouts), all, debounce. "Cancel the previous request, unless a logout happens, in which case abandon everything" is a mess of flags with thunks and a few lines with sagas.

And is that complexity justified? Usually not, and less than it used to be — which is the answer to give. Sagas earn their keep for long-lived cancellable orchestration: websockets, polling with backoff, wizards abandoned mid-flight. For "fetch data and put it in the store" it's a bazooka, and the generator learning curve is a real tax on a team. If the flow is server-state fetching, the modern answer is neither — it's React Query / RTK Query.

Other middleware you'll mention

Logging, persistence (redux-persist writing a slice to localStorage and rehydrating on boot), analytics (mapping action types to tracking events so components stay clean), and crash reporting (wrap next(action) in try/catch, attach the last N actions to the report).

That last one is the real argument for middleware generally: it's the only place you can say "on every state change, do X" once instead of in a hundred components.

Part 10 · Tier 3Selector memoization and reselect

Here's a bug that has bitten literally everyone. This component re-renders on every single dispatch in the entire app, even ones with nothing to do with todos. Can you see why?

❌ Re-renders on every dispatch, anywhere
function TodoList() {
  const visible = useSelector((state) =>
    state.todos.items.filter((t) => !t.done)     // 👈 look closely
  );
  return <ul>{visible.map(renderTodo)}</ul>;
}

Take a second before reading on. The logic is right — it really does return the incomplete todos.

The problem is .filter(). It always returns a brand new array, even when every element inside is identical.

Recall from the "Under the hood" box in Part 4 what useSelector does: on every store notification, it re-runs your selector and compares the result to last time with ===. Two different array objects with identical contents are not ===. So the comparison says "changed!", every time, for every action in the app. Someone toggles the sidebar; your todo list re-renders.

The fix is memoization: remember the last inputs and the last output, and if the inputs are unchanged, hand back the same output object rather than computing a new one. That's what createSelector from reselect (bundled inside Redux Toolkit) does.

✅ Memoized derived state
import { createSelector } from '@reduxjs/toolkit';

const selectVisibleTodos = createSelector(
  [(state) => state.todos.items, (state) => state.todos.filter],  // input selectors
  (items, filter) => items.filter((t) => t.status === filter)      // only runs if inputs changed
);

function TodoList() {
  const visible = useSelector(selectVisibleTodos);   // 👈 same array reference now
  return <ul>{visible.map(renderTodo)}</ul>;
}

Mechanically: the input selectors are cheap and just pluck references out of state. createSelector compares those plucked values with ===. If they're all identical to last time, it skips the expensive filter entirely and returns the cached array — the same object reference. useSelector's === check now passes, and your component doesn't re-render. When items genuinely changes, the filter runs and produces a new array, and you re-render exactly once, correctly.

The mental model: a memoized selector is a receptionist with a good memory. "Same question as last time? Here's the answer I already have. Something changed? Fine, I'll go find out again." The analogy's weak spot is that the default reselect cache size is one — ask a different question, and it forgets the previous answer.

Wait — a cache of one? Doesn't that break with lists?

Yes, and this is the classic gotcha. If ten <TodoItem id={n} /> components all use the same selectTodoById(state, id) selector with different ids, each call evicts the previous cache entry and memoization does nothing.

Two fixes: create a per-component selector instance with useMemo, or use RTK's newer createSelector options / weakMapMemoize to get a multi-entry cache. Naming this problem in an interview is a strong depth signal.

Two more things worth knowing, and both come up as follow-ups:

Selectors are also an abstraction boundary. If every component reads state.todos.items directly, restructuring your state means editing fifty files. If they all call selectTodos(state), you edit one. Colocate selectors with their slice and export them.

Returning a fresh object has the same bug. useSelector(s => ({ name: s.user.name, email: s.user.email })) creates a new object every time — same problem as .filter(). Either call useSelector twice (once per primitive — usually the simplest answer), or pass an equality function: useSelector(fn, shallowEqual).

Part 11 · Tier 3Normalizing state: your store is a database

Your API returns nested JSON, because that's convenient for the API. So you drop it straight into the store:

❌ Nested and duplicated
{
  posts: [
    { id: 'p1', title: 'Hello', author: { id: 'u7', name: 'Priya' } },
    { id: 'p2', title: 'Again', author: { id: 'u7', name: 'Priya' } },
    { id: 'p3', title: 'More',  author: { id: 'u7', name: 'Priya' } },
  ]
}

Priya is in there three times. Now she changes her display name to "Priya S." — and you have a genuinely nasty problem:

  • You must find and update every copy. Miss one and your UI shows two different names for one person.
  • To do it immutably, you have to map over the posts array, and inside that rebuild each matching post, and inside that rebuild its author. Deeply nested spread hell.
  • And because you rebuilt the whole posts array, every post component re-renders — including the ones that didn't change at all.

The fix is to store data the way a relational database does: each entity once, in a lookup table, referenced by ID.

✅ Normalized: byId + allIds
{
  posts: {
    byId: {
      p1: { id: 'p1', title: 'Hello', authorId: 'u7' },   // 👈 a reference, not a copy
      p2: { id: 'p2', title: 'Again', authorId: 'u7' },
    },
    allIds: ['p1', 'p2'],          // keeps order, and gives you a cheap list to map
  },
  users: {
    byId: { u7: { id: 'u7', name: 'Priya' } },
    allIds: ['u7'],
  },
}

Now the rename is one line: state.users.byId.u7.name = 'Priya S.'. One source of truth, so inconsistency is structurally impossible. The posts slice isn't touched at all, so post components that only render titles don't re-render.

Why the two fields? byId gives you O(1) lookup by ID — no array.find() scans. allIds preserves ordering and lets you render a list by mapping IDs. A list component maps over allIds and passes just an id to each child; each child selects its own record. That way, changing one post re-renders exactly one row.

Redux Toolkit gives you this shape prebuilt via createEntityAdapter:

✅ createEntityAdapter does the bookkeeping
const postsAdapter = createEntityAdapter({
  sortComparer: (a, b) => b.createdAt - a.createdAt,
});

const postsSlice = createSlice({
  name: 'posts',
  initialState: postsAdapter.getInitialState({ status: 'idle' }),  // { ids: [], entities: {} }
  reducers: {
    postAdded:   postsAdapter.addOne,       // prewritten CRUD reducers
    postUpdated: postsAdapter.upsertOne,
    postRemoved: postsAdapter.removeOne,
    postsLoaded: postsAdapter.setAll,
  },
});

export const { selectAll, selectById } = postsAdapter.getSelectors((s) => s.posts);

It maintains ids and entities (RTK's names for allIds/byId), keeps sorting correct on insert, and generates memoized selectors. You get add/update/remove/upsert/setAll for free.

"Should I normalize everything?"

No. Normalizing costs you readability — you trade "just read the object" for "join it back together in a selector". It's worth it when: the same entity appears in multiple places, entities get updated individually, or lists are long enough that re-rendering everything hurts.

It's not worth it for a settings object, or a one-off list you fetch, display, and throw away. And if the data is server state living in React Query, its cache is already keyed by query — normalization is usually someone else's problem at that point.

Part 12 · Tier 3Atomic state: Jotai, Recoil, Valtio

Everything so far has been top-down: one big state object, and components select slices out of it. There's a whole other family that works bottom-up.

The unit is an atom: a single, tiny, independent piece of state that you define on its own and use directly. There's no root store to register it with.

Jotai: atoms, and atoms derived from atoms
import { atom, useAtom } from 'jotai';

const cartAtom = atom([]);                                // a primitive atom
const cartCountAtom = atom((get) => get(cartAtom).length); // 👈 derived from it
const cartTotalAtom = atom((get) =>
  get(cartAtom).reduce((sum, i) => sum + i.price * i.qty, 0)
);

function CartBadge() {
  const [count] = useAtom(cartCountAtom);   // only re-renders when the count changes
  return <span>{count}</span>;
}

The interesting bit is derived atoms. cartCountAtom declares its dependency by calling get(cartAtom), so the library builds a dependency graph automatically. When cartAtom changes, it knows exactly which derived atoms are affected, recomputes only those, and re-renders only the components subscribed to them.

Compare to the Context problem from Part 3. In Context, "which components care about this change?" is unanswerable, so everyone re-renders. In Redux, you answer it with selectors and memoization — a fix layered on top. In an atomic library, the granularity is the design. There's no big object to over-subscribe to, because there's no big object. The re-render problem is avoided by construction rather than patched.

The mental model: Redux is one big whiteboard everyone reads, with selectors as the discipline of only looking at your corner. Atoms are a wall of sticky notes — you read only the ones you need, and some notes compute themselves from other notes. (The analogy breaks on actions: sticky notes have no equivalent of Redux's action log. That's the auditability tradeoff again.)

Name-recognition is enough here: Jotai is the one to name today (small, TypeScript-first, maintained); Recoil is its Facebook-built ancestor, effectively unmaintained, so know it historically and don't propose it; Valtio is the mutable-proxy flavour where you write state.count++ and readers re-render automatically.

What earns the point isn't the list — it's saying why the category exists: fine-grained, automatically tracked dependencies, which suits apps with lots of interdependent derived values (editors, canvases, dashboards, forms with cross-field logic).

Part 13 · The interview layerHow this actually gets asked

State management is a judgement topic. Interviewers rarely want to know if you can write a reducer — they want to know whether you'd reach for Redux on a five-page marketing site. Almost every question here is secretly "do you know when not to use this?"

The literal phrasings

  • "How do you manage state in a React app?"
  • "Walk me through how Redux works."
  • "When would you reach for a state management library?"
  • "What's the difference between Context and Redux?"
  • "Have you used Redux Toolkit? What does it give you over plain Redux?"
  • "How do you handle async operations in Redux?"
  • "Tell me about a time state management got messy. What did you do?"

The model answer to the big one

Q: "How do you decide between Context and a state management library?"

"First I'd split the state up. Anything that's really server data — lists, profiles, anything fetched — I'd put in React Query rather than a global store, because that's a caching problem, not a state problem. Then for what's left, if it's a couple of values that change rarely, like theme or the auth session, Context is genuinely enough — it's a transport mechanism and that's all I need. I'd move to Zustand or Redux Toolkit when I need things Context can't do: selector-based subscriptions so components don't all re-render on every change, devtools and an action log for debugging, or middleware for things like persistence. And on a big team there's a convention argument for RTK too — it gives everyone one obvious way to structure state."

Why it lands: it separates server state from client state unprompted (senior signal), it treats Context as legitimate rather than something to sneer at, and it names specific capabilities as the trigger for upgrading instead of vibes. You've shown you'd add a dependency for a reason.

Q: "Walk me through the Redux data flow."

"There's one store holding the whole app's state as a single plain object. When something happens in the UI, you dispatch an action — a plain object with a type, describing what happened, in the past tense. The store passes the current state and that action to a reducer, which is a pure function that returns a brand new state object rather than mutating the old one. The store saves that and notifies subscribers, and react-redux re-renders the components whose selected slice actually changed. It's strictly one direction — nothing writes to the store except a reducer responding to a dispatch. That's what makes it debuggable: any state change is traceable to a named action in the devtools log."

Why it lands: it's the full cycle in order, it uses the right nouns, and the last sentence explains the point of the constraint rather than just reciting it.

Follow-up questions — the highest value part

"Why not just use Context for everything?"

Because Context is a transport mechanism, not a state manager. It has no selector API, so every component consuming a context re-renders whenever any part of that context value changes — you can't subscribe to just the piece you read. It also gives you no devtools, no middleware hook for cross-cutting concerns like persistence or logging, and no conventions about state shape.

For a theme or a locale that changes twice a session, none of that matters and Context is the right call. For a value that changes frequently and is read by many unrelated components, the broadcast behaviour becomes a real performance problem, and the workaround — splitting into a dozen tiny contexts — is just hand-rolling a worse version of what a store gives you.

"Why must reducers be pure?"

Four reasons, and I'd give at least two. Purity means staten is a deterministic function of staten-1 and the action, so the devtools can replay the action log to reconstruct any past state — that's how time-travel debugging works, and how a captured bug report reproduces exactly. Immutability specifically is also the change-detection mechanism: components compare state by reference, so if a reducer mutated an array in place, the reference wouldn't change and the UI would silently go stale. And pure reducers are trivially testable — inputs in, assert on the output, no mocks.

"Does RTK's Immer actually mutate my state?"

No. The state object your reducer receives is a draft — a Proxy wrapping the real state. The proxy intercepts your writes and records them instead of applying them. When the reducer returns, Immer produces a new state object using structural sharing: branches you touched are copied with the changes applied, and branches you didn't touch keep their original object references. So the previous state is untouched, === comparisons still work, and time travel is unaffected.

Two caveats: don't both mutate the draft and return a new value from one reducer — Immer throws. And Immer only drafts plain objects, arrays, Maps and Sets, so class instances or Dates in state won't behave as expected.

"Why does my component re-render on every dispatch?"

Almost always because the selector returns a new reference each time. useSelector re-runs your selector on every store notification and compares the result with ===; something like useSelector(s => s.items.filter(...)) or useSelector(s => ({ a, b })) builds a fresh array or object every run, so the comparison always fails and it re-renders on every action in the app.

Fixes: select primitives (call useSelector twice rather than returning an object), use createSelector from reselect so the derived value is memoized and the reference is stable, or pass shallowEqual as the second argument to useSelector.

"When would you pick Zustand over Redux?"

Small-to-mid app, small team, and I want selector-based subscriptions without the ceremony. Zustand is about 1 kB, needs no provider, and the store is just an object of state plus the functions that update it — so I get the thing Context can't do (partial subscriptions) at almost no cost.

I'd go the other way — RTK — when I want the strong conventions, when the app has lots of interdependent slices and complex async flows, or when the devtools action log matters for debugging production. On a large team, having exactly one obvious way to write state is worth real boilerplate. And I'd note that Zustand's module-level store is a singleton, so under SSR you need to create it per-request.

"What problem does middleware solve?"

Reducers have to be pure, so there's nowhere in the core cycle for side effects — API calls, logging, persistence, analytics. Middleware is an interception layer that every dispatched action passes through before reaching the reducer, so it's the sanctioned home for that impure work. The signature is store => next => action => {}: you can inspect the action, pass it along with next(action), transform it, delay it, or swallow it entirely.

Thunk is the simplest example — nine lines that check whether the "action" is actually a function and call it with dispatch and getState if so, which is how async works in Redux. It's also the only place you can express "on every action, do X" once instead of in every component.

"Is Redux dead?"

No, but its scope shrank a lot, and that's a good thing. Historically most of what people put in Redux was cached server data, and query libraries like React Query and RTK Query handle that far better — caching, staleness, deduplication, background refetch. Once that moves out, the remaining global client state in most apps is small enough for Context or Zustand, so a lot of apps genuinely don't need Redux any more.

Where it's still the right answer: large apps with lots of interdependent client state, big teams that benefit from enforced conventions, and anything where the action log and time-travel debugging are genuinely valuable. And Redux Toolkit removed most of the boilerplate that gave Redux its reputation. So: not dead, just no longer the default.

"How do you handle async in Redux?"

Not in reducers — they have to stay pure. The standard answer is createAsyncThunk from Redux Toolkit: you give it a name and an async function, and it generates pending / fulfilled / rejected action types automatically. You handle those in extraReducers to set loading, data, and error state. Under the hood it's just redux-thunk, which lets you dispatch a function that receives dispatch and getState.

For complex orchestration — cancellation, racing, debouncing, websockets, multi-step flows that can be abandoned — redux-saga's generators are stronger, because it has real cancellation and effects like takeLatest and race. But if it's plain data fetching, the honest answer today is RTK Query or React Query rather than either.

"Why normalize state?"

Because nested API responses duplicate entities. If the same user is embedded in thirty posts and they change their name, you have to find and update thirty copies immutably — easy to get wrong, and you end up rebuilding the whole posts array so every post re-renders. Normalizing means storing each entity once in a byId lookup with an allIds array for order, and referencing by ID. Then an update is one line at one location, inconsistency is structurally impossible, lookups are O(1) instead of array scans, and only the components reading that specific entity re-render. RTK's createEntityAdapter builds that shape and its CRUD reducers and selectors for you.

"What are atoms, and how are they different?"

Atoms are bottom-up state — instead of one big store you select slices from, you define lots of tiny independent pieces and use them directly. Jotai is the main one today; Recoil was the original but is effectively unmaintained. The interesting part is derived atoms: an atom can be computed from other atoms, and the library tracks that dependency graph automatically, so a change recomputes only the affected derived atoms and re-renders only their subscribers. The over-rendering problem that Context has and that Redux solves with selectors and memoization simply doesn't arise, because there's no big object to over-subscribe to. It suits apps with lots of fine-grained interdependent values — editors, canvases, complex forms.

Depth vs recall — how to tell what's being tested

"What is an action?" is a recall question; answer it in one sentence and stop. Asking that clarifying question is itself most of the point.
