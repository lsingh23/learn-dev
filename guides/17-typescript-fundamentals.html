Section 1The one thing you have to believe first

Let's start with some code that looks completely reasonable and does not work. I want you to look at it and predict what happens.

❌ Doesn't compile
interface User {
  name: string;
  email: string;
}

function handle(value: unknown) {
  if (value instanceof User) {   // 👈 what happens here?
    console.log(value.name);
  }
}

Take a second with it. There's no typo. User is defined right there, two lines up. And yet:

// → 'User' only refers to a type, but is being used as a value here. ts(2693)

If that error has ever made you feel a bit stupid — good, welcome, that's the correct reaction and it's the reason this guide starts here. The error isn't about instanceof. It's about something much bigger, and once you internalise it, roughly half of TypeScript's weirdness stops being weird.

Here it is:

TypeScript is a compile-time-only layer. Every type you write is deleted before your code runs.

Not "mostly deleted". Not "compiled into runtime checks". Deleted. The TypeScript compiler reads your annotations, uses them to shout at you in your editor, and then throws them in the bin and emits plain JavaScript. Here's the whole pipeline:

So instanceof User fails because at runtime there is no User. There's no variable called User, no constructor, no object — nothing for instanceof to compare against. You wrote a note in the margin and then asked the browser to read your margin.

The analogy: scaffolding

TypeScript is scaffolding around a building. While you're constructing, it's everywhere — you walk on it, you lean things against it, it stops you falling off the third floor. Then, on the day the building opens, it all comes down. The finished building has no scaffolding in it. If you designed a room that only stays up because scaffolding is holding it, you have a serious problem, because that scaffolding is leaving.

Where the analogy breaks down: scaffolding is passive — it just sits there. TypeScript is more opinionated than that; it actively refuses to let you build things it considers unsound. But the "it's gone before anyone moves in" part is exact, and that's the part that matters.

The three consequences you'll actually hit

One: you can't check a type at runtime. Not with instanceof, not with typeof myUser === 'User', not with anything. You can only check things that survive erasure — the actual shape of the actual object (typeof x === 'string', 'email' in x, Array.isArray(x)). We'll build real runtime checks in the narrowing section.

Two: types do not validate data coming in from outside. This one bites people in production.

❌ Confidently wrong
const res = await fetch('/api/user');
const user: User = await res.json();   // 👈 this is a wish, not a check

console.log(user.name.toUpperCase());  // → 💥 if the API returned null

res.json() returns any. Writing : User does not inspect the payload. It just tells the compiler "trust me, it's a User", and the compiler — which has no way to see the network — believes you. If the backend renamed name to fullName last Tuesday, TypeScript will happily let you crash. At every boundary where data enters your program — fetch, localStorage, JSON.parse, URL params, form input, a third-party SDK — you need an actual runtime check (hand-written, or a schema library like Zod). Types on their own stop at the border.

Three: this is exactly why any is dangerous. Since types are your only safety net and they vanish at runtime, punching a hole in the net doesn't produce a loud failure — it produces silence, until production. More on that in section 3.

A common misconception

"TypeScript makes my app safer at runtime." It does not. It makes your development safer, which very often prevents runtime bugs from ever being written — but the shipped JavaScript is exactly as fragile as JavaScript always was. TypeScript catches the class of bug where you misused your own code. It catches none of the class where the world hands you something unexpected.

In an interview

"Does TypeScript make your code safer at runtime?" — This is a filter question. A surprising number of candidates say yes.

Model answer — say this out loud

"No, and that's important to be clear about. TypeScript is purely a compile-time layer — every type gets erased before the code runs, so the JavaScript that ships has no type checks in it at all. What it gives me is confidence that my code is internally consistent: I can't call a function with the wrong arguments, I can't read a property that doesn't exist. But anything crossing a boundary — an API response, localStorage, user input — is unvalidated as far as TypeScript is concerned. Annotating res.json() as User is just an assertion; it doesn't inspect anything. So at those boundaries I still do a real runtime check, usually with a schema validator like Zod, and derive the TypeScript type from the schema so the two can't drift apart."

Why it lands: you've shown you understand erasure, you've named the exact boundary problem, and you've offered the standard professional solution. That last sentence — deriving the type from the schema — is what separates "read the docs" from "shipped this".

Section 2interface vs type

Almost every TypeScript interview asks this, and almost every answer is a shrug: "they're basically the same, I use whichever." That answer isn't wrong, but it's a wasted opportunity, because the real differences are interesting and knowing them signals that you've read past the tutorial.

Let's start with the 95% case, where they genuinely are interchangeable:

Identical in effect
interface User {
  name: string;
  email: string;
}

type User = {
  name: string;
  email: string;
};

Same checking, same errors on misuse, same everything. So what actually differs?

Difference 1: type can describe things that aren't objects

An interface describes the shape of an object (or a function, or a class). That's its whole job. A type is an alias — a name you give to any type expression at all. That's a much wider job description:

type Status = 'idle' | 'loading' | 'error';     // union — interface can't
type ID = string;                                // primitive alias — can't
type Point = [number, number];                   // tuple — can't
type Handler = (event: MouseEvent) => void;      // function (interface can, awkwardly)
type Nullable<T> = T | null;                     // generic alias over a union — can't

None of the lines marked "can't" have an interface equivalent. There is no way to write "this type is the string 'idle' or the string 'loading'" using interface. So already: anything that isn't an object shape has to be a type. That's not a preference, it's a constraint.

Difference 2: declaration merging

This is the one that surprises people. Declare the same interface twice and TypeScript doesn't complain — it merges them:

interface Window {
  myAnalytics: (event: string) => void;
}

interface Window {
  featureFlags: string[];
}

// Window now has BOTH. And it also still has every property
// the DOM lib declared on the built-in Window interface.

Do the same with type and you get Duplicate identifier 'Window'.

Merging sounds like a footgun, and inside your own app it mostly is — two developers accidentally naming two different interfaces Config and silently getting one Frankenstein type is not fun. But it exists for a genuinely good reason: it's how you extend types you don't own. That Window example is real. It's how you tell TypeScript about a script tag that stuck something on window, how you add custom properties to Express's Request, how library authors let you augment their types. A type alias is sealed; an interface is open for extension by consumers.

Wait, what about…

"Doesn't that mean a library using interface is less safe?" — Slightly, in the sense that anyone can bolt things on. But it's a deliberate trade: openness is a feature for a library's public surface, because the alternative is that consumers with a legitimate need are stuck. Inside your own application code, where nobody needs to augment anything, the openness buys you nothing.

Difference 3: extends vs &

Both can combine object types, and they look equivalent:

interface Admin extends User {
  permissions: string[];
}

type Admin = User & { permissions: string[] };

They produce the same shape, but they behave differently when things go wrong. extends is a checked relationship: if you extend User and redeclare name as a number, TypeScript stops you immediately with a clear error, because you've claimed to be a valid User and you aren't. An intersection is not a check — it just mashes the two together, and a conflicting property quietly collapses to never (a type with no possible values), so nothing can ever satisfy it. You get no error at the definition, only a baffling one much later at the usage site.

❌ Silently broken
type Base = { id: string };
type Broken = Base & { id: number };
//  id is now (string & number) → never. No error here.

const x: Broken = { id: '1' };  // → Type 'string' is not assignable to type 'never'
                                //   ...good luck working out why

Interfaces also tend to produce nicer error messages and editor tooltips: hover an interface and you see User, hover a big intersection and you can get a wall of expanded structure. And there's a small performance angle — the compiler caches interface relationships, while intersections are recomputed. On a huge codebase that's measurable; on yours it probably isn't.

So which do you use?

Here's the guidance, and the reasoning behind it:

Use interface for object shapes. Use type for everything else.

It works because it's mechanical — no judgement call at the keyboard — and it lines up with what each tool is actually built for. Objects get the better errors, the extendability, the compiler caching. Unions, tuples, primitives, function signatures, and anything computed get type, because they have no choice.

The honest caveat: plenty of excellent codebases use type for everything and are completely fine. This is a style question with mild technical grounding, not a correctness question, and you should say so.

In an interview

"Do you use interface or type?" — They're testing whether you have reasons, not which one you picked. A candidate who says "type, because it's more flexible, and here's the one case where I'd reach for interface" scores exactly as well as the reverse.

Model answer

"My default rule is interface for object shapes and type for everything else. The main reason is that type is the only one that can express unions, tuples, primitives and mapped types, so those are forced. For objects, interfaces give slightly better error messages, and they support declaration merging, which matters when you need to augment something you don't own — like adding a property to Window or Express's Request. I also prefer extends over an intersection because a conflicting property is caught at the declaration, whereas an intersection silently collapses it to never and you find out much later. That said, it's a convention, not a correctness thing — I'd follow whatever the codebase already does."

Why it lands: the never-collapse detail is the tell. It's specific, it's true, and it's the kind of thing you only know from having been burned. The closing line about following the codebase shows you're not going to relitigate style in code review.

Section 3any, unknown, and never

Here's a small function. It takes something from outside — a parsed JSON blob, say — and pulls a name out of it.

❌ With any
function getName(data: any) {
  return data.user.profile.name.toUpperCase();
}

getName({ hello: 'world' });   // compiles fine ✅
                               // → 💥 Cannot read properties of undefined

TypeScript let all of that through without a murmur. Not one squiggle. And that's not a bug — it's any doing precisely what it's designed to do, which is switch type checking off for that value.

Think of any as a diplomatic passport. Whatever that value does, wherever it goes, nobody's allowed to search its bags. Call it as a function? Fine. Index into it with a random key? Fine. Pass it to something expecting a Date? Absolutely fine.

And here's the part that makes it genuinely dangerous rather than merely permissive: any is contagious. Anything you pull out of an any is also any. It spreads outward through your code, and because it spreads silently, a single any at an API boundary can quietly disable checking across an entire feature. Half the time when someone says "TypeScript didn't catch it", this is why.

unknown: the same door, but with a lock

unknown is the type-safe version of "I don't know what this is". Like any, it will accept any value. Unlike any, it won't let you do anything with that value until you've proven what it is.

✅ With unknown
function getName(data: unknown) {
  return data.user.name;   // → 'data' is of type 'unknown'. ts(18046)
}

The error arrives immediately, at the exact line where you made an unfounded assumption. To get past it you have to convince the compiler:

✅ Narrowed, then used
function getName(data: unknown): string {
  if (
    typeof data === 'object' && data !== null &&
    'name' in data && typeof data.name === 'string'
  ) {
    return data.name.toUpperCase();   // 👈 data.name is string here. Provably.
  }
  return 'Anonymous';
}

Yes, that's more code. That's the entire point — the extra code is the check that was missing, the one that would have prevented the crash. any didn't save you work, it deferred the work to a production incident.

The way I hold these in my head: any means "stop checking". unknown means "check later, but you will check." Two very different promises.

Under the hood

Type theory calls unknown the top type — the set of all possible values. Every type is assignable to it, and it's assignable from nothing except itself and any. never is the bottom type — the empty set, no values at all. It's assignable to everything (vacuously true: a function with no members satisfies every requirement) and nothing is assignable to it. any isn't in this hierarchy at all — it's an escape hatch that pretends to be both ends at once, which is exactly why it's unsound.

never, and the exhaustiveness trick

never is the type of a value that can't exist. A function that always throws returns never. An infinite loop returns never. A variable narrowed down until no possibilities remain is never.

That last one is the useful one, and it powers my single favourite TypeScript pattern. Watch:

type Shape =
  | { kind: 'circle'; radius: number }
  | { kind: 'square'; size: number };

function area(shape: Shape): number {
  switch (shape.kind) {
    case 'circle': return Math.PI * shape.radius ** 2;
    case 'square': return shape.size ** 2;
    default:
      const exhaustive: never = shape;   // 👈 the guard
      throw new Error(`Unhandled shape: ${exhaustive}`);
  }
}

In that default branch, TypeScript has eliminated circle and square, so shape is never — nothing is left. Assigning never to never is fine, so today this compiles.

Now a teammate adds { kind: 'triangle'; base: number; height: number } to Shape and forgets about this file. Suddenly shape in the default branch is the triangle variant, and you can't assign a triangle to never. The build fails, in the file they forgot, pointing at the exact case they missed.

That's the move: you've turned "someone might forget to update this" into a compile error. Do this in every reducer, every state machine, every place you switch on a union — and mention it in the interview, because it reads as senior in about eight words.

strict mode, and why noImplicitAny is the load-bearing flag

None of this matters if any is sneaking in without you writing it. Without noImplicitAny, an unannotated parameter is silently any:

function greet(user) {          // user is implicitly any — checking is OFF
  return user.nmae.trim();      // typo sails right through
}

Turn on "strict": true in tsconfig.json and you get that flag plus the other big one, strictNullChecks, which stops treating null and undefined as members of every type. Without it, string secretly includes null and TypeScript can't warn you about the most common runtime error in all of JavaScript. Strict mode is not "advanced TypeScript" — it's the difference between TypeScript working and TypeScript performing type safety at you.

In an interview

"What's the difference between any and unknown? Why is unknown better?"

Model answer

"Both accept any value, but any turns type checking off for that value — you can call it, index it, pass it anywhere, and TypeScript won't say a word. And it's contagious: anything you read off an any is also any, so one of them at an API boundary can silently disable checking across a whole feature. unknown is the type-safe top type. It holds anything, but you can't touch it until you've narrowed it — with typeof, an in check, a type predicate, whatever. So it's the right type for genuinely unknown input, like a caught error or a JSON payload, because it forces the validation to actually happen. I'd only reach for any to unblock an incremental migration, with a comment saying why."

Why it lands: "contagious" is the word that shows you've felt the pain rather than read the definition. Naming catch (e: unknown) is a nice bonus — since TS 4.4 with useUnknownInCatchVariables, caught errors are unknown, because you genuinely cannot know that someone threw an Error.

Trap: "any is fine as long as you're careful"

This gets candidates dinged because it misunderstands the failure mode. The danger isn't that you misuse the any value — it's that any propagates to code written by people who never saw the annotation, six months later, in a different file. Carefulness doesn't compose across a team. Say unknown plus a narrowing function instead.

Section 4Generics, from the problem up

Generics are where people bounce off TypeScript. The syntax looks like algebra and every tutorial starts with function identity<T>(arg: T): T, which explains the syntax and none of the point.

So let's not do that. Let's write a function that has a problem, and see what the problem is.

The problem

I want first — takes an array, returns the first element.

❌ Attempt 1: any
function first(arr: any[]): any {
  return arr[0];
}

const name = first(['Ada', 'Grace']);
name.toUpperCase();   // ✅ compiles
name.toFixed(2);      // ✅ also compiles 😬 → 💥 at runtime

The information was right there — I passed an array of strings — and the function threw it away. Everything after this call is unchecked.

❌ Attempt 2: one copy per type
function firstString(arr: string[]): string { return arr[0]; }
function firstNumber(arr: number[]): number { return arr[0]; }
function firstUser(arr: User[]): User { return arr[0]; }
// ...and one for every type that will ever exist. Forever.

Correct, and absurd. Note that these bodies are character-for-character identical. The logic doesn't care about the type at all. The only thing that varies is a type, and we're duplicating an entire function to vary it.

Which is a familiar shape, isn't it? When the only thing that varies is a value, you don't write forty functions — you add a parameter. Generics are that same idea, one level up: a parameter whose argument is a type.

✅ Attempt 3: a type parameter
function first<T>(arr: T[]): T {
  return arr[0];
}

Read <T> exactly like you'd read a function's parameter list. function first(arr) says "I need an array; the caller supplies it." function first<T>(...) says "I need a type; the caller supplies it." T is a placeholder that gets filled in at each call site, and : T[] and : T say "whatever they fill in, the input is an array of it and the output is one of it."

The angle brackets are just the syntax for "this parameter list holds types, not values". That's it. That's the whole idea.

You almost never write the type argument

Here's the bit that makes generics pleasant instead of noisy — TypeScript infers the type argument from the values you pass:

const names = ['Ada', 'Grace'];
const firstName = first(names);   // T inferred as string
firstName.toUpperCase();          // ✅
firstName.toFixed(2);             // ❌ Property 'toFixed' does not exist on type 'string'

const ages = [31, 45];
first(ages);                      // T inferred as number — same function

first<string>(names);             // explicit, if you ever need it

One function, full type information preserved through it, zero annotations at the call site. That's the payoff. You've probably been using generics for months without noticing — Array<string>, Promise<User>, Map<string, number>, useState<number> are all exactly this.

Wait, what about…

"Why T?" — Pure convention (T for Type, then U, V for extras; K for Key, V for Value). Nothing magic about the letter. In real code, please write <TItem> or <TResponse> when there's more than one — <T, U, V, K> is a puzzle nobody wants to solve.

Constraints: "any type, but it must at least…"

Naked T means literally any type, which means you can't do anything with it — same lock unknown puts on you, and for the same reason. This fails:

❌ Too permissive
function logLength<T>(item: T) {
  console.log(item.length);   // → Property 'length' does not exist on type 'T'
}

Correct of it. You said "any type", and number has no .length. So narrow the promise with extends:

✅ Constrained
function logLength<T extends { length: number }>(item: T) {
  console.log(item.length);   // ✅ guaranteed to exist
}

logLength('hello');        // ✅ strings have length
logLength([1, 2, 3]);      // ✅ arrays do too
logLength(42);             // ❌ number doesn't satisfy the constraint

extends here doesn't mean inheritance — read it as "must be at least". A useful pairing is K extends keyof T, which is how you write a type-safe property getter:

function getProp<T, K extends keyof T>(obj: T, key: K): T[K] {
  return obj[key];
}

const user = { name: 'Ada', age: 36 };
getProp(user, 'name');   // → string
getProp(user, 'age');    // → number  👈 different return type, same function
getProp(user, 'emial');  // ❌ typo caught: not assignable to 'name' | 'age'

Look at what that bought: the return type depends on the argument value. That's not something a non-generic signature can express at all.

Default type parameters

Just like default values for value parameters:

interface ApiResponse<TData = unknown> {
  data: TData;
  status: number;
}

const a: ApiResponse = { data: 'anything', status: 200 };        // TData = unknown
const b: ApiResponse<User[]> = { data: [], status: 200 };        // TData = User[]

Generics in React

The two places you'll write them for real. First, a custom hook that keeps the type of whatever it stores:

function useLocalStorage<T>(key: string, initial: T) {
  const [value, setValue] = useState<T>(() => {
    const raw = localStorage.getItem(key);
    return raw ? (JSON.parse(raw) as T) : initial;   // 👈 assertion — see §8
  });
  return [value, setValue] as const;
}

const [theme, setTheme] = useLocalStorage('theme', 'dark');  // T = string
const [count, setCount] = useLocalStorage('count', 0);       // T = number

Without the generic you'd return any and every consumer would lose its types. And second, a generic component — a list that doesn't care what it's listing:

type ListProps<T> = {
  items: T[];
  renderItem: (item: T) => React.ReactNode;
};

function List<T>({ items, renderItem }: ListProps<T>) {
  return <ul>{items.map((item, i) => <li key={i}>{renderItem(item)}</li>)}</ul>;
}

<List items={users} renderItem={(u) => u.name} />
//                                    👆 u is User. Inferred from `items`.
In an interview

"What problem do generics solve?" — and the follow-up that separates people: "why not just use any?"

Model answer

"Generics let a function or type work with many types while keeping the relationship between them. Take a first function that returns an array's first element — without generics I either type it as any[], which throws away the caller's type and disables checking downstream, or I write one copy per type, which is identical logic duplicated forever. A type parameter <T> is just a parameter whose argument is a type: the caller fills it in, usually by inference, and the signature (arr: T[]) => T records that the output type is tied to the input type. That's the key thing any can't do — any is a hole, a generic is a link. Then constraints like T extends { length: number } let me require a minimum shape while still staying open."

Why it lands: "any is a hole, a generic is a link" is a sentence an interviewer will remember. Leading with the concrete broken version instead of a definition shows you can teach, which is most of what senior interviews are actually measuring.

Section 5Structural typing (why that assignment worked)

Another one to predict. Two types, completely unrelated — neither extends the other, they're declared in different files, they have nothing to do with each other conceptually:

interface Point2D { x: number; y: number; }
interface Vector2D { x: number; y: number; }

function draw(point: Point2D) { /* … */ }

const velocity: Vector2D = { x: 3, y: 4 };
draw(velocity);   // 👈 does this compile?

It compiles. Happily. No complaint at all.

If you've come from Java or C#, that should feel wrong, because those languages are nominally typed: a type's identity is its name, and a Vector2D is not a Point2D because it isn't called that, full stop.

TypeScript is structurally typed. A type's identity is its shape. The question TypeScript asks is never "is this a Point2D?" — it's "does this have everything a Point2D needs?" velocity has an x: number and a y: number. It qualifies. Case closed.

The analogy I like: nominal typing is a guest list, structural typing is a dress code. A guest list checks your name against the paper. A dress code checks whether you're wearing a jacket and tie — it doesn't care who you are, and it doesn't care that you also happen to be wearing a hat. Where it breaks down: a real bouncer sees you all at once, whereas TypeScript checks the requirements one at a time and can also check that a function you're carrying has an acceptable signature. But "requirements met, name irrelevant" is exactly right.

This is not an accident or a compromise — it's the correct design for a language layered on top of JavaScript, where objects are built ad hoc from literals, spreads and JSON, and mostly never came from a class at all. Requiring a name would make TypeScript unusable on the language it's describing. It's also why you can pass an object literal to a function without declaring that you implement anything, and why mocks in tests just work.

Where it bites

Now the uncomfortable case. Two IDs in your app:

❌ Compiles, ships, breaks
type UserId = string;
type OrderId = string;

function cancelOrder(id: OrderId) { /* … */ }

const userId: UserId = 'usr_8321';
cancelOrder(userId);   // ✅ compiles. Both are string. Structurally identical.

Those aliases give you documentation and nothing else. To TypeScript they are both, exactly and only, string. Same for a Meters and a Feet that are both number — and that class of bug has famously destroyed actual spacecraft.

Branded types: forcing nominal behaviour

The trick is to make the shapes genuinely different by adding a property that exists only in the type system:

✅ Branded
type UserId  = string & { readonly __brand: 'UserId' };
type OrderId = string & { readonly __brand: 'OrderId' };

// The only way in — a checked constructor:
function toOrderId(raw: string): OrderId {
  if (!raw.startsWith('ord_')) throw new Error('Bad order id');
  return raw as OrderId;        // 👈 the single, deliberate assertion
}

cancelOrder(userId);              // ❌ now a compile error 🎉
cancelOrder(toOrderId('ord_12')); // ✅

At runtime these are still just strings — __brand does not exist, nothing is allocated, there's zero cost. The brand exists purely to make the two shapes incompatible to the checker. You concentrate all the unsafety into one small validated constructor, and everywhere else is safe by construction. Worth it for IDs, currency amounts, units, and anything pre-validated (a SanitizedHtml, an Email).

Excess property checking (the exception that confuses everyone)

If shape is all that matters, why does this fail?

❌ Object literal
interface Options { url: string; timeout?: number; }

fetchData({ url: '/api', timeuot: 500 });
// → Object literal may only specify known properties,
//   but 'timeuot' does not exist in type 'Options'. Did you mean 'timeout'?

Structurally that object does satisfy Options — it has a url: string, and extras should be harmless. And they are, when the object arrives via a variable:

const opts = { url: '/api', timeuot: 500 };
fetchData(opts);   // ✅ no error. Same object!

So why the difference? Because of intent. When you write an object literal directly at the call site, that object has no other purpose — there's no other consumer who might want timeuot. An extra property there is overwhelmingly likely to be a typo or a misremembered API, so TypeScript adds a special extra check for that one case. Once the object lives in a variable, it might legitimately be used elsewhere with more fields, so the check backs off.

It's a deliberate, pragmatic exception to structural typing, aimed squarely at optional-property typos. Knowing why it exists — and that assigning to a variable makes it disappear — is a genuinely good interview detail.

In an interview

"Why can I pass this object to a function expecting a completely unrelated type?"

Model answer

"Because TypeScript is structurally typed — compatibility is decided by shape, not by name. If an object has all the members the target type requires, it's assignable, even if the two types were declared independently and share no ancestry. That's the right call for a language sitting on top of JavaScript, where most objects come from literals or JSON and never had a nominal type to begin with. The downside is that two aliases like UserId and OrderId that are both string are completely interchangeable, so you can pass the wrong one. When that matters I use a branded type — intersect the primitive with a phantom property so the shapes differ — and funnel creation through one validating function. The brand is erased at runtime, so it's free."

Why it lands: naming the structural/nominal distinction shows you have vocabulary from outside TypeScript. Following it with branded types shows you know the escape hatch, not just the complaint.

Section 6Utility types: types are values you can transform

Here's a small thing that changes how you see TypeScript. You have a User:

interface User {
  id: string;
  name: string;
  email: string;
  password: string;
}

Now you need the shape of the half-filled form draft — every field optional while the user is still typing. And the shape you send to the client — everything except the password. And a lookup keyed by user ID.

The instinct is to write three more interfaces. Don't. Types are values you can compute with. Just as you'd never copy-paste an array and delete an element by hand, you shouldn't copy-paste a type. You derive it:

type UserDraft  = Partial<User>;              // every field optional
type PublicUser = Omit<User, 'password'>;     // everything but password
type UserMap    = Record<string, User>;       // { [id: string]: User }

That's the whole concept, and it's worth more than memorising the list: utility types are functions that take types and return types. Once you see them that way, the payoff is obvious — add a createdAt field to User and all three derived types update themselves. Copy-pasted interfaces drift; derived ones can't.

The ones you'll actually use

Partial<T> — every property optional. The classic use is a patch/update:

function updateUser(id: string, changes: Partial<User>) { /* … */ }
updateUser('u1', { email: 'new@example.com' });   // ✅ don't need the rest

Required<T> — the inverse; strips the ? off everything. Handy after you've filled in defaults, so the rest of the function doesn't have to keep checking for undefined:

function init(opts: Partial<Config>) {
  const full: Required<Config> = { ...defaults, ...opts };
  // 👆 from here on, every field is guaranteed present
}

Pick<T, K> and Omit<T, K> — subset by keeping, or by removing. Omit is what you want for a DTO leaving the server; Pick is what you want for a component that only needs two fields:

type UserCardProps = Pick<User, 'name' | 'email'>;
type PublicUser    = Omit<User, 'password'>;

Rule of thumb: use Pick when the list is short and Omit when the exclusion list is short. There's one real difference — Pick's keys must exist on T, but Omit tolerates keys that don't, so a rename can silently stop omitting. Mild reason to prefer Pick for anything security-sensitive.

Record<K, V> — a dictionary. The second most useful after Partial, and it's especially nice with a union key, because then it's exhaustive:

type Status = 'idle' | 'loading' | 'error';

const labels: Record<Status, string> = {
  idle: 'Ready',
  loading: 'Loading…',
  // ❌ Property 'error' is missing  👈 add a status, this breaks. On purpose.
};

Readonly<T> — all properties non-assignable. Compile-time only, and shallow (nested objects stay mutable), but great for props and config you don't want anyone mutating.

ReturnType<F> and Parameters<F> — reach into a function's signature. This is how you avoid re-declaring the shape of something a library already knows:

function createStore() {
  return { user: null as User | null, cart: [] as Item[] };
}

type Store = ReturnType<typeof createStore>;   // 👈 no second declaration to keep in sync
type Args  = Parameters<typeof updateUser>;    // → [string, Partial<User>]

That typeof is TypeScript's type-level typeof, not JavaScript's — in a type position it means "the type of this value". You'll use it constantly.

Awaited<T> — unwraps a Promise (recursively, so nested promises flatten). Nearly always paired with ReturnType to get what an async function actually resolves to:

async function fetchUser() { return { id: '1', name: 'Ada' }; }

type FetchedUser = Awaited<ReturnType<typeof fetchUser>>;   // → { id: string; name: string }
// without Awaited you'd get Promise<{ id: string; name: string }>

NonNullable<T> — removes null and undefined from a union. Useful after a filter:

type MaybeUser = User | null | undefined;
type DefinitelyUser = NonNullable<MaybeUser>;   // → User
Under the hood

None of these are compiler magic — they're ordinary TypeScript, written in the standard library using mapped and conditional types. Partial is literally type Partial<T> = { [K in keyof T]?: T[K] }. You can write your own. That's a separate guide, but it's reassuring to know there's no secret layer: it's types all the way down.

Section 7Union vs intersection & discriminated unions

This section contains the single most counterintuitive thing in TypeScript. Let's walk right into it:

type Dog = { name: string; bark: () => void };
type Cat = { name: string; meow: () => void };

type Pet = Dog | Cat;

function greet(pet: Pet) {
  pet.name;    // ✅ fine
  pet.bark();  // ❌ Property 'bark' does not exist on type 'Pet'
}

The union says "Dog or Cat", so you'd think you'd get access to both sets of properties. You get fewer. Meanwhile the intersection — "Dog and Cat", which sounds narrower — gives you more:

type Chimera = Dog & Cat;

function greet(pet: Chimera) {
  pet.bark();  // ✅
  pet.meow();  // ✅ both available
}

"Or" gives you less, "and" gives you more. That feels backwards, and it trips up nearly everyone — including me, for embarrassingly long. The fix is to stop thinking about properties and start thinking about sets of values.

The mental model: sets, not fields

A type is a set of all the values that satisfy it. Dog is the set of all objects that have a name and a bark.

Dog | Cat is the union of the two sets — a bigger circle. And here's the key move: the more values a type can hold, the less you can guarantee about all of them. Some members of that bigger set are cats, and cats can't bark. So the only properties you're allowed to touch are the ones present in every member: name.

Dog & Cat is the overlap — the smaller set of things that are somehow both. A smaller, stricter set means stronger guarantees, so you get everything from both.

Say it as a slogan: a union widens the values and narrows the capabilities; an intersection narrows the values and widens the capabilities. Or if you want it even shorter: unions are about the values, intersections are about the constraints. The words "or" and "and" apply to different things than you assumed, which is the whole reason it felt backwards.

Wait, what about…

"So how do I ever use bark?" — You narrow: prove to the compiler that this particular value is in the Dog part of the set, and inside that block you get Dog's properties back. That's the whole next section, and it's the thing unions are for. A union isn't a limitation to route around — it's a promise you have to check.

Discriminated unions: the best pattern in frontend TypeScript

If you take one practical technique from this guide, take this one.

Here's how most people model a data fetch:

❌ The bag of optionals
interface State {
  isLoading: boolean;
  data?: User;
  error?: Error;
}

Count the states that type permits. Three booleans-ish fields, eight combinations — and most of them are nonsense. isLoading: true with both data and error set. Not loading, no data, no error (what do you even render?). Data and an error at once. Every one of those is representable, so every one of them is something your component has to defend against, forever, with if (state.data) checks scattered through the JSX.

Now the same thing as a discriminated union — a union of object types that all share one common literal-typed field, the discriminant:

✅ Impossible states removed
type RequestState =
  | { status: 'idle' }
  | { status: 'loading' }
  | { status: 'success'; data: User }
  | { status: 'error'; error: Error };

Four states. Exactly four. There is no way to write a value of this type that has both data and error, or that's loading with data attached — the illegal combinations cannot be expressed. You haven't documented the rule, you've made breaking it a compile error.

And the payoff at the point of use is lovely, because TypeScript follows the discriminant:

function render(state: RequestState) {
  switch (state.status) {
    case 'idle':    return 'Click to load';
    case 'loading': return 'Loading…';
    case 'success': return state.data.name;    // 👈 data exists here. No check needed.
    case 'error':   return state.error.message; // 👈 and error exists here.
  }
}

No optional chaining, no defensive ifs, no "this can't be undefined but TypeScript doesn't know that". Inside case 'success', TypeScript has eliminated the other three members of the union, and data is simply there.

Add the never exhaustiveness check from section 3 in the default branch and you also get: every future variant someone adds will break this switch until they handle it. Combined, that's about as close to correct-by-construction as frontend code gets.

Discriminants must be literal types ('success', not string) — that's what lets the compiler tell the members apart. The field is conventionally type, kind, or status; the name doesn't matter, consistency does. And you've seen this before: Redux actions are a discriminated union on type. So are useReducer actions. So is basically every well-modelled event system.

In an interview

"How would you type the state of a request that can be loading, successful, or failed?" — This is a design question wearing a syntax question's clothes. They want to see whether you reach for the bag of optionals.

Model answer

"I'd use a discriminated union rather than an object with optional fields. Something like a status field that's the literal 'idle' | 'loading' | 'success' | 'error', where the success variant carries data and the error variant carries error. The reason is that the optional-fields version allows combinations that should be impossible — loading and errored at once, or success with no data — so every consumer ends up writing defensive checks for states that shouldn't exist. With a union those states are literally unrepresentable. And switching on the discriminant narrows the type, so inside the success branch data is guaranteed present with no null check. I'd also add a never assertion in the default branch so that if someone adds a variant later, the build fails until every switch handles it."

Why it lands: "make impossible states unrepresentable" is the phrase that signals you think about type design, not just type syntax. Bringing in the never guard unprompted is the cherry.

Section 8Narrowing and type guards

We've now got several situations where TypeScript knows a value might be one of a few things and won't let you touch it until you commit. Narrowing is how you commit.

The engine behind it is control-flow analysis. TypeScript doesn't assign one type to a variable for its whole life — it tracks the type at each point in the program, and each check you write splits the flow and refines what's possible on each branch:

function format(value: string | number | null) {
  // here: string | number | null

  if (value === null) return 'N/A';
  // here: string | number     👈 null is gone. Permanently, on this path.

  if (typeof value === 'number') {
    return value.toFixed(2);   // here: number
  }

  return value.trim();         // here: string — nothing else is left
}

Note that last line: no check, no assertion, and TypeScript is certain it's a string. It reasoned its way there by elimination. That's the whole game.

The narrowing tools, in order of how often you'll use them

typeof — for primitives. Works because typeof is real JavaScript that survives erasure. (Remember typeof null === 'object'; TypeScript knows this quirk and narrows accordingly, which can surprise you.)

Discriminant checks — if (state.status === 'success'). Covered above; by far the most valuable in app code.

Truthiness — if (user) { … }. Cheap and everywhere, but be careful: it removes 0, '', NaN and false too. If your value is number | undefined, if (count) throws away a legitimate zero. Prefer if (count !== undefined).

instanceof — for actual classes, which do exist at runtime. Great in a catch:

try { await save(); }
catch (err) {                 // err is unknown
  if (err instanceof Error) console.error(err.message);   // ✅ narrowed
  else console.error('Unknown failure', err);
}

in — for object unions with no discriminant. Checks for a property's presence:

function speak(pet: Dog | Cat) {
  if ('bark' in pet) pet.bark();   // 👈 narrowed to Dog
  else pet.meow();                 // narrowed to Cat
}

Equality narrowing — comparing two union-typed values narrows both to their common members, which is a neat trick people rarely notice:

function compare(a: string | number, b: string | boolean) {
  if (a === b) {
    // both narrowed to string — it's the only type they share
    a.toUpperCase();
  }
}

Type predicates: teaching the compiler your own check

Built-in narrowing runs out when your check lives in a helper function:

❌ Narrowing doesn't escape the function
function isUser(value: unknown) {
  return typeof value === 'object' && value !== null && 'email' in value;
}

if (isUser(data)) {
  data.email;   // ❌ 'data' is of type 'unknown'
}

Reasonable of it — all TypeScript sees is a function returning boolean. A true tells it nothing about data. So we upgrade the return type from boolean to a type predicate: value is User. Read it as "returning true means the argument is a User".

✅ With a predicate
function isUser(value: unknown): value is User {   // 👈 the whole change
  return (
    typeof value === 'object' && value !== null &&
    'email' in value && typeof (value as User).email === 'string'
  );
}

if (isUser(data)) {
  data.email.toLowerCase();   // ✅ data is User in here
}

One caveat, and it's a real one: TypeScript does not verify that your predicate is honest. You could write return true and it would believe you. A predicate is a promise you're making, and the compiler propagates it on trust. So keep the body small and obviously correct — a predicate is exactly where a subtle lie does the most damage.

A close cousin is the assertion function, which throws instead of returning a boolean, and narrows everything after the call:

function assertIsUser(value: unknown): asserts value is User {
  if (!isUser(value)) throw new Error('Not a user');
}

assertIsUser(data);
data.email;   // ✅ narrowed for the rest of the scope

(Assertion functions need an explicit type annotation on the variable holding them — TypeScript can't infer asserts through a const.)

as is a lie to the compiler

Which brings us to the tool everyone reaches for too early:

const user = data as User;   // "trust me"

A type assertion performs no check whatsoever. It generates no code. It doesn't convert anything. It is a note to the compiler saying "stop reasoning, I've got this" — and if you're wrong, you've disabled the one system that would have told you.

Every as is a place you've taken personal responsibility for a guarantee the compiler was providing for free. Sometimes that's the right call. The legitimate cases are narrow:

  • Inside a validated boundary — the one line in your branded-type constructor or your predicate, where you've just done the runtime check.
  • as const, which isn't really the same thing — it narrows to literal types instead of widening, and it's always safe.
  • Reaching into a DOM API that returns a supertype: document.getElementById('email') as HTMLInputElement. TypeScript can't know your HTML.
  • Test fixtures where you deliberately want a partial mock.

The illegitimate case — and it is most of them — is "the error was annoying and this made it go away". If as is how you resolve type errors, you've built a codebase with the syntax of TypeScript and the guarantees of JavaScript. Also worth knowing: as any as Something (the double assertion) exists to force casts TypeScript refuses outright, and its appearance in a diff should always start a conversation.

In an interview

"When is a type assertion acceptable?" — They're probing whether you treat as as a tool or as a painkiller.

Model answer

"I treat as as telling the compiler to stop checking — it does no runtime conversion and no validation, it just overrides the inference. So it's acceptable when I genuinely know something the compiler can't: right after a runtime check inside a type guard or a branded-type constructor, or with DOM queries where TypeScript can't see my HTML and returns HTMLElement. What I avoid is using it to silence an error I don't understand, because at that point the type is a claim nobody has verified. My default is a user-defined type predicate instead — same ergonomics at the call site, but the assertion is confined to one small function I've actually reviewed."

Why it lands: "does no runtime conversion" preempts the classic misconception that as casts like (int) in C. Offering predicates as the alternative shows you know what to do instead, which is what they're really asking.

Section 9?. and ??

Two small operators, one very common bug.

Optional chaining: ?.

The old defensive pyramid:

const city = user && user.address && user.address.city;

becomes:

const city = user?.address?.city;   // → the city, or undefined

The mechanic that matters: ?. short-circuits the entire chain. If user is null or undefined, evaluation stops right there and the whole expression is undefined — it does not go on to look at .address and explode. And note it's undefined even when the left side was null. That's deliberate: ?. normalises "nothing here" to a single value.

It works in three positions, and the second two are easy to forget:

user?.name             // property
users?.[0]             // index — note the dot before the bracket
user.save?.()          // call — only if save exists

That last one is lovely for optional callbacks: props.onClose?.() instead of if (props.onClose) props.onClose().

A common misconception

?. is not a general "don't crash" operator. It guards against null and undefined only. user?.address.city still throws if user exists but address is missing — you need a ?. at each link that might be nullish. It's also easy to over-apply: if user is typed as non-optional, writing user?.name is noise that quietly hides a bug where user genuinely shouldn't be missing.

Nullish coalescing: ?? — and the bug

Here's the one. Guess what this logs:

const settings = { volume: 0, username: '' };

const volume = settings.volume || 50;
const name   = settings.username || 'Anonymous';

console.log(volume, name);   // → ?
Reveal the answer

50 'Anonymous' — and both are wrong. The user explicitly muted their audio and it just got reset to 50%.

|| checks for falsiness, and JavaScript's falsy set includes 0, '', NaN and false alongside null and undefined. So "give me a default when there's no value" silently becomes "give me a default when the value is zero, or empty, or off". Any time a legitimate value happens to be falsy, || eats it.

?? checks only for nullish — null or undefined, nothing else:

✅ Fixed
const volume = settings.volume ?? 50;         // → 0    ✅ zero survives
const name   = settings.username ?? 'Anon';   // → ''   ✅ empty string survives

My rule: if the fallback is for a missing value, use ??. Use || only when you actually mean "or any falsy thing" — which, for numbers, strings and booleans, you almost never do. For a value that can only be an object or nullish, they're equivalent, but ?? still communicates intent better.

They pair naturally with ?., since ?. produces undefined and ?? catches exactly that:

const city = user?.address?.city ?? 'Unknown';

And there's the assignment form, ??=, which assigns only if the target is currently nullish:

config.retries ??= 3;    // sets it only if null/undefined — a 0 is respected
config.retries ||= 3;    // ❌ would overwrite a deliberate 0

One syntax gotcha: you can't mix ?? with || or && without parentheses — a || b ?? c is a syntax error. That's intentional, because the precedence would be ambiguous to a reader and the language would rather you say which you meant.

In an interview

"?? vs ||?" — a two-second question with a right and a wrong answer. The wrong answer is "they're basically the same".

Model answer

"|| falls back on any falsy value, ?? only on null or undefined. That matters whenever 0 or an empty string is a legitimate value — volume || 50 resets a deliberately muted volume back to 50, whereas volume ?? 50 keeps the zero. So I use ?? for defaults on anything numeric, string, or boolean, and reserve || for when I genuinely mean 'or anything falsy'. Same distinction with ??= versus ||=."

Section 10TypeScript + React

Everything so far, applied where you'll actually use it.

Typing props

A props type is just an object type. That's genuinely all it is:

interface ButtonProps {
  label: string;
  onClick: () => void;
  variant?: 'primary' | 'secondary';   // 👈 optional, and only two valid strings
  children?: React.ReactNode;
}

function Button({ label, onClick, variant = 'primary' }: ButtonProps) {
  return <button className={variant} onClick={onClick}>{label}</button>;
}

Two things worth noticing. That variant union means an interviewer's favourite typo — variant="primari" — is a compile error, which is one of the highest-value-per-character things you can do in a React codebase. And the return type is inferred as JSX.Element; you don't need to annotate it.

Why React.FC fell out of favour

You'll see this in older code:

const Button: React.FC<ButtonProps> = ({ label }) => { … };

It's not broken, and React 18's types fixed its worst sin, but the community moved off it and you should know why:

  • It used to add children implicitly. Every React.FC component accepted children whether or not it rendered them, so an <Avatar>oops</Avatar> typechecked and silently dropped the text. React 18 removed the implicit children — which meant a huge amount of code that relied on it broke on upgrade. So it's been both too loose and, later, a migration headache.
  • It's awkward with generics. A generic component is much cleaner as a plain function declaration; with React.FC you're fighting the annotation.
  • It buys you almost nothing. The return type was already inferred. You're adding an import and an indirection for a guarantee you had.
  • It types the variable, not the function, which makes some inference and overload scenarios worse.

The modern default is a plain function with a typed props parameter, and declaring children: React.ReactNode explicitly when the component actually takes children. Explicit beats implicit, and it's self-documenting at the call site.

On ReactNode: it's the widest "anything renderable" type — elements, strings, numbers, arrays, null, undefined, booleans. That's what you want for children 95% of the time. ReactElement is narrower (a JSX element specifically, not a string), and JSX.Element is what a component returns.

useState: when inference is enough, and when it isn't

Most of the time you write nothing, because the initial value tells TypeScript everything:

const [count, setCount] = useState(0);           // number
const [name, setName] = useState('');            // string
const [isOpen, setIsOpen] = useState(false);     // boolean

Inference falls short in exactly two situations. First, when the initial value is null or undefined but the eventual value isn't:

❌ Inferred too narrowly
const [user, setUser] = useState(null);   // inferred: null
setUser(fetchedUser);                      // ❌ User is not assignable to null
✅ Tell it the full type
const [user, setUser] = useState<User | null>(null);

Second, when the initial value is a widened version of what you mean — an empty array, or a string that should be a union:

const [items, setItems] = useState<CartItem[]>([]);       // else: never[]
const [status, setStatus] = useState<Status>('idle');     // else: string

That second one is important: without the annotation, 'idle' widens to string, and you've lost the exhaustiveness you were trying to buy. And of course the best version of all of this is one state variable holding a discriminated union rather than four booleans — section 7 applies directly here.

Typing events

React's synthetic events are generic over the element that fired them. Getting the element right is what gives you e.target.value:

function handleChange(e: React.ChangeEvent<HTMLInputElement>) {
  setName(e.target.value);   // ✅ string, because the element is an input
}

function handleClick(e: React.MouseEvent<HTMLButtonElement>) {
  e.preventDefault();
}

function handleSubmit(e: React.FormEvent<HTMLFormElement>) {
  e.preventDefault();
}

Handy shortcut: if you write the handler inline, you don't need any of this — the event is inferred from the JSX attribute.

<input onChange={(e) => setName(e.target.value)} />
//                 👆 already ChangeEvent<HTMLInputElement>. Free.

Which gives you a nice discovery trick: write it inline, hover to see the type your editor infers, then copy that into the extracted handler's signature.

Refs

Two flavours, and mixing them up is a classic:

// A DOM ref you hand to React — must be initialised to null, and is read-only
const inputRef = useRef<HTMLInputElement>(null);
inputRef.current?.focus();   // 👈 ?. because it's null before mount

// A mutable box for a value that isn't state
const timerRef = useRef<number | null>(null);
timerRef.current = window.setTimeout(…);   // ✅ writable

The rule: useRef<T>(null) gives you a RefObject whose current is read-only (React owns it), while useRef<T | null>(null) gives you a writable MutableRefObject. And current is nullish until after mount, so ?. is doing real work there — not being paranoid.

as const

Not really React-specific, but it shows up constantly in React code. By default TypeScript widens literals, because it assumes you'll reassign:

const config = { theme: 'dark', retries: 3 };
// inferred: { theme: string; retries: number }   👈 'dark' widened away

const config = { theme: 'dark', retries: 3 } as const;
// inferred: { readonly theme: 'dark'; readonly retries: 3 }

as const says "freeze this at its most specific — every property readonly, every literal exact". Three places it earns its keep:

// 1. Deriving a union from a runtime array — one source of truth
const STATUSES = ['idle', 'loading', 'error'] as const;
type Status = typeof STATUSES[number];   // → 'idle' | 'loading' | 'error'

// 2. Returning a tuple from a hook, so destructuring keeps positions typed
return [value, setValue] as const;   // → [T, Dispatch<SetStateAction<T>>]
                                     //   without it: (T | Dispatch<…>)[]

// 3. Keeping a literal narrow enough to satisfy a union prop
const variant = 'primary' as const;   // 'primary', not string

That first one is genuinely great: the array exists at runtime so you can .map() over it to render options, and the type is derived from it, so they can never disagree.

In an interview

"Why do people avoid React.FC now?"

Model answer

"Mainly because it used to implicitly add children to every component's props, so a component that doesn't render children would still accept them and silently drop whatever you passed. React 18's types removed that implicit children, which then broke a lot of code that had been depending on it — so it's been awkward in both directions. It also plays badly with generic components, and it doesn't really buy anything: the return type was already inferred from the JSX. So the standard now is a plain function with a typed props parameter, declaring children: React.ReactNode explicitly when the component actually takes children."

Why it lands: knowing the React 18 change dates you correctly — it says you've upgraded a real codebase, not just read a blog post from 2019.

Section 11Interview cheat sheet

Read this on the train. One crisp line each.

The foundation

  • Erasure — every type is deleted before the code runs; TypeScript is a compile-time layer only.
  • Runtime safety — no. TypeScript checks that your code is internally consistent; it validates nothing coming in from the network, storage, or users.
  • Boundaries — validate at runtime where data enters (Zod or a hand-written guard), and derive the type from the schema so they can't drift.

Declaring types

  • interface vs type — interface for object shapes, type for everything else. Only type can do unions, tuples, primitives, mapped types. Only interface can declaration-merge.
  • extends vs & — extends errors on a conflicting property; an intersection silently collapses it to never.

The special types

  • any — checking off, and contagious. unknown — holds anything, but you must narrow first. Default to unknown.
  • never — no possible values. Assign a narrowed variable to never in a default branch to force exhaustiveness at compile time.
  • strict: true — turns on noImplicitAny and strictNullChecks. Non-negotiable; without it half of this doesn't work.

Generics

  • What they solve — reuse without losing type information. any is a hole; a generic is a link between input and output types.
  • Syntax — <T> is a parameter list for types; the caller fills it in, usually via inference.
  • Constraints — <T extends { id: string }> means "any type, but at least this shape". K extends keyof T for type-safe property access.

Structural typing

  • Shape, not name — unrelated types with matching members are assignable. Right for a JS-shaped world.
  • The risk — UserId and OrderId as string aliases are interchangeable. Fix with branded types (string & { __brand: 'UserId' }), erased at runtime, free.
  • Excess property checking — extra-fields error applies only to object literals at the assignment site, to catch typos; assigning through a variable skips it.

Composing types

  • Utility types — types are values you can transform. Derive, never copy-paste: Partial, Required, Pick, Omit, Record, Readonly, ReturnType, Parameters, Awaited, NonNullable.
  • Union vs intersection — a union widens the set of values and narrows what's guaranteed; an intersection narrows the values and widens the capabilities.
  • Discriminated union — a shared literal field across variants. Model loading/error/success this way to make impossible states unrepresentable.

Narrowing

  • Tools — typeof, instanceof, in, truthiness, equality, discriminant checks. Control-flow analysis tracks the type per branch.
  • Type predicate — function isUser(v: unknown): v is User. TypeScript trusts it without verifying, so keep it small.
  • as — no runtime check, no conversion; it overrides the compiler. Fine right after a real validation or for DOM queries; not for silencing errors.

Operators & React

  • ?. — short-circuits the whole chain to undefined on null/undefined. Works for props, ?.[i], and ?.().
  • ?? vs || — ?? falls back only on nullish; || falls back on any falsy value, so it eats a legitimate 0 or ''.
  • Props — plain function with a typed props parameter. Avoid React.FC: implicit children historically, poor with generics, adds nothing.
  • useState — annotate when the initial value is null, [], or a literal that would widen (useState<Status>('idle')).
  • Events — React.ChangeEvent<HTMLInputElement>, React.MouseEvent<HTMLButtonElement>. Inline handlers infer for free.
  • Refs — useRef<HTMLInputElement>(null) for DOM (read-only current), useRef<T | null>(null) for a mutable box.
  • as const — freeze literals and readonly-ify. Use for hook tuples and deriving a union from a runtime array.

The one-liner if you only remember one thing

TypeScript is a conversation you have with a very literal colleague who reads all your code, forgets everything the moment you hit deploy, and is never wrong about the things you actually told it. Tell it the truth, narrow before you use, validate at the border — and it will catch a genuinely startling number of your mistakes before anyone else sees them.

Good luck out there. 🎯
