Here's a piece of React that has confused approximately every developer who has ever written React. Have a look and tell me what you think happens.

A perfectly ordinary component

function App() {
  const [count, setCount] = useState(0);

  return (
    <div>
      <button onClick={() => setCount(count + 1)}>Clicked {count} times</button>
      <Sidebar />   {/* 👈 no props at all */}
    </div>
  );
}

You click the button. count goes from 0 to 1. App re-renders — obviously, its state changed.

But what about Sidebar? It receives no props. Nothing about it changed. Nothing it depends on changed. Does React re-render it?

Take a second and actually commit to an answer, because your instinct here determines whether the rest of this guide makes sense.

Show me the answer

Yes. Sidebar re-renders. Every single time you click that button. So does everything inside Sidebar, and everything inside that, all the way down the tree.

If you believed React would skip it because "nothing changed" — good, that's the belief we're going to dismantle, and dismantling it is the entire foundation of this topic.

This one behaviour is the root of nearly every React performance question you'll ever be asked. So we're going to start there, slowly, and we're not going to touch React.memo until it's completely airtight.

Section 1What a "render" actually is

The word "render" is badly overloaded. People use it to mean "draw pixels on screen," which is what the word means everywhere else in computing. In React it means something much more boring, and the boringness is the point.

A render is React calling your component function. That's it. That's the whole thing.

Your component is a function. It takes props, it runs some hooks, and it returns a description of what the UI should look like. When React "renders" your component, it invokes that function and collects the returned description.

What your JSX actually is

// This JSX...
<button className="primary">Save</button>

// ...is just this object. It's a description, not a DOM node.
{
  type: 'button',
  props: { className: 'primary', children: 'Save' }
}

So a render produces a plain JavaScript object tree. Nothing has touched the screen yet. React then compares that new tree with the previous one, works out the minimal set of real DOM operations needed, and applies them. React calls these two phases the render phase and the commit phase. Afterwards the browser does its own thing — layout, paint — and you finally see pixels.

Here's the piece that trips people up: a re-render does not imply a DOM update. If Sidebar re-renders and produces an identical description to last time, React diffs it, finds nothing different, and touches the DOM zero times. The user sees nothing. Nothing flickers. The only cost was running the function and comparing some objects.

A common misconception

"Re-rendering means React rebuilds the DOM." No. Re-rendering means React re-runs your function and compares the result. Rebuilding the DOM only happens for the parts that genuinely differ. This is why re-renders are much less scary than beginners think — and why "stop this re-render!" is often the wrong instinct.

Section 2The three things that cause a re-render

This is the section to get right. Everything else in this guide is a consequence of it.

A component re-renders when one of exactly three things happens:

  1. Its own state changed. You called a setState from useState, or dispatched with useReducer, and the new value is actually different.
  2. Its parent re-rendered. Full stop. No conditions. If the parent re-renders, the child re-renders.
  3. A context it consumes got a new value. If the component calls useContext(SomethingContext) and the value the provider hands down changes identity, this component re-renders — even if its parent didn't.

Notice what's not on that list.

A common misconception (the big one)

"A component re-renders when its props change."

This is the single most widespread false belief about React, and it's false in both directions.

Props changing is not sufficient — props can't change on their own; the only way a prop gets a new value is if the parent re-rendered and passed something new. The parent re-render is the cause; the new prop is a side effect.

Props changing is not necessary — Sidebar in our opening example takes no props whatsoever, and it re-renders every single click.

Say it in an interview like this: "A component re-renders because its parent did, not because its props changed." That one sentence signals more understanding than a paragraph of hedging.

Let's make this concrete. Add some logging to the opening example:

Watch the cascade

function Sidebar() {
  console.log('Sidebar rendered');
  return <nav><NavLinks /></nav>;
}

function NavLinks() {
  console.log('NavLinks rendered');
  return <ul>{/* ... */}</ul>;
}

// Click the counter button once:
// → 'Sidebar rendered'
// → 'NavLinks rendered'
// Neither of them takes a single prop. 🤷

The mental model to carry around: a state update doesn't re-render "the component that owns the state" — it re-renders that component and its entire subtree. State updates fall downwards, like water. They can never flow up or sideways.

Wait — what about that fourth cause?

There's technically a fourth: subscribing to an external data source with useSyncExternalStore (which is what Redux, Zustand and friends use under the hood). That's a component subscribing to something outside React and asking to be re-rendered when it changes. We'll come back to it in the section on external stores — it's exactly the escape hatch Context lacks.

Also worth knowing: in development with StrictMode on, React deliberately calls your component function twice per render to help you catch impure components. So if your console logs look doubled, that's why, and it doesn't happen in production.

Section 3Why re-renders are usually cheap (and premature memoization isn't)

Reading section 2, the natural reaction is panic. "My whole app re-renders on every keystroke?! I need to wrap everything in React.memo immediately!"

Hold on. Let's think about what a re-render actually costs.

Running a component function means: executing some straight-line JavaScript, calling a handful of hooks (which are basically array lookups), and allocating a few small objects for the JSX. On a modern device that's typically in the microseconds. React can comfortably do thousands of these within a single 16ms frame.

Here's an analogy I like. Imagine a restaurant kitchen. When an order comes in, the head chef re-reads the whole ticket for the table — all six dishes — even though only one dish changed. Re-reading a ticket takes a second. Cooking the dish takes twenty minutes. Optimising the ticket-reading is not where your wins are.

In React, "re-reading the ticket" is the render phase. "Cooking" is the commit phase touching the DOM — and React already skips that automatically for anything that didn't change. (Where this analogy breaks down: if you have 5,000 tickets, re-reading them all does start to matter. Volume is what turns cheap into expensive.)

So when is a re-render expensive? Realistically:

  • Volume. A table with 2,000 rows, each re-rendering, each producing JSX. A thousand cheap things is one expensive thing.
  • Genuinely heavy work inside the render. Sorting a 50,000-item array, running a syntax highlighter, parsing markdown, doing date math over a big list — on every keystroke.
  • Frequency. Re-rendering half your app on a mousemove or a scroll handler firing 60 times a second.
  • Heavy trees. A chart library or rich text editor that does real work when it re-renders.

Notice that "a few dozen simple components re-rendered" isn't on that list, because it costs about a millisecond and nobody will ever perceive it.

In an interview

If you're asked "how do you optimise a React app?" and your first word is "useMemo," you've already given away that you optimise by reflex rather than by measurement. The strong opening is: "First I'd profile it, because most re-renders are cheap and I'd want to know which ones actually aren't."

And memoization is not free. Every React.memo boundary means React must compare the previous props to the new props on every render. Every useMemo means storing the previous value and the previous deps array in memory forever, and comparing the deps every render. If the work you're skipping is smaller than the work of checking whether you can skip it, you've made your app slower and harder to read.

The honest framing: memoization is a trade, not an upgrade. You spend memory and complexity to buy back CPU time. That's a good trade when the CPU time is real and a bad trade when it isn't.

Section 4Detour: values vs. references

We need this before React.memo, and if it's already second nature to you, skim it. But almost every "why isn't my memo working?" bug is really this concept in disguise, so it's worth being ruthless about.

JavaScript has two categories of things. Primitives — numbers, strings, booleans, null, undefined, symbols, bigints — are compared by their value. Objects — including arrays and functions — are compared by their identity: are these two names pointing at the same thing in memory?

The rule, in five lines

5 === 5                    // → true  (same value)
'hello' === 'hello'        // → true  (same value)

{ id: 1 } === { id: 1 }    // → false 👈 different objects, identical contents
[1, 2] === [1, 2]          // → false
(() => {}) === (() => {})  // → false

Think of an object as a house, and a variable as a slip of paper with the house's address written on it. === on objects doesn't walk inside and compare the furniture. It just compares the two addresses. Two identical show-homes on the same street are still two different addresses.

Now here's why this matters so much in React. Every render of a component re-executes its body from the top. Every object literal, array literal, and function defined in that body is created fresh, at a brand new address.

New addresses on every single render

function ProductPage({ product }) {
  const [zoom, setZoom] = useState(false);

  const style = { padding: 16 };            // 👈 new object, every render
  const tags = product.tags.filter(Boolean); // 👈 new array, every render
  const handleBuy = () => addToCart(product); // 👈 new function, every render

  return <ProductCard style={style} tags={tags} onBuy={handleBuy} />;
}

Those three values are logically the same every time. But they're three new addresses every time. React has no way to know they're "the same" — from its point of view, ProductCard received three different props.

Keep that picture. It's about to explain everything.

Section 5React.memo

We established that a child re-renders whenever its parent does, regardless of props. React.memo is how you opt out of that rule.

You wrap a component in it, and you get back a new component with a bouncer at the door. When the parent re-renders and React comes to render this child, the bouncer intercepts: "Hang on. Are the new props the same as last time? If yes, you're not coming in — I'll reuse last render's output."

The basic shape

const Sidebar = React.memo(function Sidebar({ links }) {
  console.log('Sidebar rendered');
  return <nav>{links.map(/* ... */)}</nav>;
});

Now, when App re-renders because of its counter, React checks Sidebar's props, sees that links is the same as before, and skips the render entirely — along with its whole subtree. NavLinks doesn't render either, because Sidebar never ran to produce it.

That last part is important and often missed: memo blocks the whole branch, not just one node. Placing a single memo high in the tree can skip hundreds of components. That's why where you put it matters far more than how many you place.

How does it compare props? Shallowly.

"Same props" means React walks the props object one level deep and runs Object.is on each value. Roughly:

The default comparison, in essence

function shallowEqual(prev, next) {
  const keys = Object.keys(prev);
  if (keys.length !== Object.keys(next).length) return false;
  return keys.every(key => Object.is(prev[key], next[key])); // 👈 one level only
}

One level. Not deep. It never recurses into a nested object. So if you pass user={{ name: 'Ada' }}, memo compares the outer object's address, and if that address is new, it does not care that the contents are identical.

A common misconception

"React.memo does a deep comparison of props." It does not, and it never has. It's a shallow, one-level, reference-based check. This is a favourite interview question precisely because getting it wrong explains the number one memo bug.

And this is deliberate: a deep comparison would have to walk arbitrarily large object graphs on every render, which could easily cost more than the render you're trying to skip. React chose the fast, predictable check.

So: why isn't my React.memo working?

This is the question. Here's the classic failure — and it looks completely innocent.

❌ Buggy — memo does absolutely nothing here

const Sidebar = React.memo(function Sidebar({ links, onSelect }) {
  return <nav>{/* ... */}</nav>;
});

function App() {
  const [count, setCount] = useState(0);

  return (
    <>
      <button onClick={() => setCount(count + 1)}>{count}</button>
      <Sidebar
        links={['Home', 'Settings']}       // 👈 new array, every render
        onSelect={(id) => navigate(id)}    // 👈 new function, every render
      />
    </>
  );
}

Every click, App re-renders. Every re-render creates a fresh array literal and a fresh arrow function — new addresses. Memo compares old vs. new, finds two mismatches, shrugs, and renders Sidebar anyway.

You have added a comparison cost to every render and bought literally nothing. This is worse than not memoizing, and it's silent — no warning, no error, just an optimisation that quietly isn't one.

The fix is to give those props stable identities, which is exactly what useMemo and useCallback are for:

✅ Fixed — stable references, so memo can actually do its job

function App() {
  const [count, setCount] = useState(0);

  const links = useMemo(() => ['Home', 'Settings'], []);      // same array forever
  const handleSelect = useCallback((id) => navigate(id), []); // same fn forever

  return (
    <>
      <button onClick={() => setCount(count + 1)}>{count}</button>
      <Sidebar links={links} onSelect={handleSelect} />
    </>
  );
}

Now the addresses are stable across renders, memo's shallow check passes, and Sidebar genuinely skips.

In an interview

Say this out loud and you sound like you've debugged it for real: "React.memo compares props shallowly by reference, so if the parent passes an inline object, array or arrow function, those are new references on every render and the comparison always fails. The memo runs, costs a little, and skips nothing. The fix is to stabilise the props with useMemo/useCallback — memo on the child and stable props from the parent are a matched pair; either one alone is useless."

The other three ways memo "doesn't work"

Reference-unstable props are the big one, but there are three more, and knowing them is what separates a memorised answer from an understood one.

1. The component has its own state, or consumes context. Memo only blocks re-renders coming from the parent. It has no power over cause #1 (own state) or cause #3 (context). A memoized component whose context value changes will re-render, every time, no matter how stable its props are. Remember that — it comes back in the Context section.

2. You're passing children. This one is sneaky:

❌ Buggy — memo defeated by children

<MemoizedPanel>
  <ExpensiveChart />   {/* 👈 this is a prop called `children` */}
</MemoizedPanel>

JSX nested inside a component becomes the children prop, and as we saw in section 1, JSX compiles down to an object literal. A new object literal, created fresh in the parent's render. So children is a new reference every time, and the shallow comparison fails. Memo skips nothing.

3. You wrapped it but the parent never re-renders anyway. Then the memo is pure overhead. Dead weight, extra indirection, and one more thing for the next developer to reason about.

The custom comparator

React.memo takes an optional second argument: your own comparison function.

Second argument: arePropsEqual

const UserRow = React.memo(
  function UserRow({ user, onSelect }) {
    return <li>{user.name}</li>;
  },
  (prevProps, nextProps) => {
    // return TRUE to SKIP the re-render (props are "equal")
    return prevProps.user.id === nextProps.user.id
        && prevProps.user.name === nextProps.user.name;
  }
);

Here we've said: I don't care that user is a new object each time, and I don't care about onSelect at all — if the id and name match, skip it.

Two things people get wrong:

The return value is inverted from what your gut expects. true means "equal, so don't re-render." If you're coming from class components, shouldComponentUpdate returned true to mean "yes, update." memo's comparator is the exact opposite. Getting this backwards produces a component that never updates, which is a genuinely horrible bug to chase.

It is a footgun. If you ignore a prop in your comparator — like onSelect above — you've promised React that stale prop can never matter. If someone later changes onSelect to close over state, your component silently calls the old one forever. Custom comparators are an escape hatch, not a default. And please don't reach for JSON.stringify or a deep-equal library in there: you'll pay a real cost on every render to avoid a cost that was probably smaller.

Under the hood

React.memo is not the same thing as PureComponent from the class era, though the idea is the same. PureComponent shallow-compared both props and state; memo only compares props, because function components don't have a state object to compare.

Also: memo isn't a guarantee. React reserves the right to re-render a memoized component anyway — for example when it frees memory for offscreen content. Treat it as a performance hint, never as correctness. If your code only works because a component didn't re-render, your code is broken.

Section 6useMemo

React.memo caches a component's output. useMemo caches a value.

The problem it solves comes straight out of section 4: your component body runs top to bottom on every render, so every calculation in it re-runs on every render. Usually fine. Occasionally not.

❌ Slow — re-sorts 20,000 rows on every keystroke

function ProductList({ products }) {
  const [query, setQuery] = useState('');
  const [isDarkMode, setIsDarkMode] = useState(false);

  // This runs on EVERY render — including when only isDarkMode changed 😬
  const sorted = [...products].sort((a, b) => a.price - b.price);

  return <Table rows={sorted} />;
}

Toggle dark mode and you re-sort twenty thousand products for absolutely no reason. useMemo lets you say "only redo this when the inputs change."

✅ Fixed — re-sorts only when products changes

const sorted = useMemo(
  () => [...products].sort((a, b) => a.price - b.price),
  [products]  // 👈 the dependency array
);

The mechanics: on the first render, React runs your function and stores both the result and the deps array. On every later render, it compares each dep to the stored one with Object.is. All the same? Hand back the stored value without running the function. Any different? Run it again, store the new result and new deps.

A useful picture: useMemo is a sticky note on your desk. "Last time someone asked me for the sorted product list, and the list was this exact list, the answer was this." Someone asks again with the same list — you read the note instead of redoing the work. They ask with a different list — you throw the note away and do the work again. (Where it breaks down: you only ever keep one note. It's a cache of size one, not a lookup table. Alternating between two different inputs means you recompute every single time.)

The second reason, which is the one people miss

Everyone learns useMemo as "for expensive calculations." That's reason one. Reason two is at least as important in real codebases and it has nothing to do with how expensive the computation is:

useMemo preserves reference identity.

Look back at section 5. The reason memo failed was that links={['Home', 'Settings']} was a new array every render. Building that array costs nanoseconds — it's not expensive at all. But its identity mattered, because something downstream compared it by reference.

✅ Memoizing something trivially cheap — and still correct

// Building this object is basically free. That's not why we're memoizing.
const chartConfig = useMemo(
  () => ({ currency, locale, showLegend: true }),
  [currency, locale]
);

return <MemoizedChart config={chartConfig} />;  // 👈 the memo boundary needs stability

Who compares by reference downstream? Three things, and they're the three places this matters:

  • A React.memo boundary's shallow prop check.
  • Another hook's dependency array — useEffect, useMemo, useCallback. An unstable object in a useEffect's deps means the effect re-runs every render, which is how you get infinite fetch loops.
  • A Context provider's value. (Section 12. This is the big one.)
Wait — is useMemo a guarantee?

No, and the React docs are explicit about it: useMemo is a performance optimisation, not a semantic one. React may discard the cached value — for instance to free memory for offscreen content — and recompute. So never put anything in useMemo that your app's correctness depends on running only once. No side effects, no writing to refs, no subscriptions. Those belong in useEffect. If you need a value created exactly once and never again, that's useRef or lazy useState initialisation, not useMemo.

Section 7useCallback

Now that useMemo is clear, useCallback takes about thirty seconds, because it is literally a special case of it.

Functions are objects. A function defined in a component body gets a new identity every render, and there's no way around that — the function keyword and arrow syntax both allocate. So how do you keep a handler stable? You could write useMemo(() => handleClick, [])... and that works! But the double-arrow is awkward enough that React ships a shorthand.

These two lines are exactly equivalent

const handleBuy = useCallback(() => addToCart(id), [id]);

const handleBuy = useMemo(() => () => addToCart(id), [id]);
//                        👆 the outer arrow RETURNS the function we want

That's the whole difference. useMemo calls your function and caches what it returns. useCallback caches the function you passed in itself, without calling it.

So the distinction to say in an interview: useMemo memoizes a result; useCallback memoizes a definition. If you catch yourself writing useMemo(() => () => ...), use useCallback.

A common misconception

"useCallback stops the function from being created." It doesn't! The arrow function is still created on every render — it has to be, it's an expression in the function body being evaluated. It's then handed to useCallback, which throws it away and returns the one from last time. The allocation still happens; only the identity you use is stable.

Which is another reason wrapping trivial handlers in useCallback is pointless: you didn't avoid creating a function, you added a deps comparison on top of creating a function.

Under the hood

Both hooks store their cache on the component's fiber — React's internal object for that particular component instance. That's why the cache dies when the component unmounts, and why two instances of the same component don't share a memo. It's also why hook order must be stable: React finds your memo by position in the hook list, not by name.

Section 8What memoization actually costs

We keep saying "it isn't free." Let's be specific, because "what's the cost of memoization?" is a real interview question and vague hand-waving about "overhead" doesn't land.

1. The comparison itself. Every render, React iterates the deps array or the props object and runs Object.is on each entry. Small, but it's strictly additional work on top of the work you were already doing. If the memoized computation is a + b, comparing the deps costs more than just doing the addition.

2. Memory. The cached value and the deps array stay alive for as long as the component is mounted. Memoize a big derived array in a list of 500 rows and you're now holding 500 extra arrays that the garbage collector can't touch. Memoization trades memory for CPU, and memory pressure has its own performance cost.

3. Correctness risk from the deps array. This is the expensive one, and it's a human cost. Every memo introduces a list you must keep in sync with reality. Miss a dep and you get a stale value — a callback closing over yesterday's state, a memo returning a result computed from props that have since changed. These bugs are subtle, intermittent, and hard to reproduce. (The ESLint rule react-hooks/exhaustive-deps catches most of these. Turn it on. Don't silence it with a comment unless you can articulate exactly why.)

4. Readability. Compare these:

The same logic, twice

// Before
const fullName = user.firstName + ' ' + user.lastName;

// After
const fullName = useMemo(
  () => user.firstName + ' ' + user.lastName,
  [user.firstName, user.lastName]
);

The second version is four times longer, has a dependency list to maintain, and saves you a string concatenation. Every future reader has to stop and ask "why is this memoized? is there something expensive here I'm not seeing?" You've added a permanent tax on comprehension for a benefit of zero.

5. It's often a placebo. The failure mode from section 5 — memo on the child but unstable props from the parent — costs you all four items above and buys nothing. Memoization is a chain, and a chain with any link broken transmits no force at all, but every link still weighs something.

In an interview: "should you wrap everything in useMemo?"
Say something like

"No — I'd default to not memoizing. Every memo adds a comparison, holds memory, and adds a dependency array that can go stale, and it makes the code harder to read. Most renders are cheap enough that you'd never measure the difference. I reach for it when profiling shows a real problem, or when I specifically need a stable reference — to keep a React.memo boundary working, or to stop an effect firing on every render. Going forward the React Compiler does a lot of this automatically, which is a good signal that hand-memoizing everything was never the right default."

Why it lands: it shows you know memoization is a trade with a real price, that you optimise from evidence rather than superstition, and that you're current with where React is heading. Candidates who answer "yes, it's always better to memoize" are showing they've never actually profiled anything.

Section 9The structural fixes you should try first

Here's the thing about memoization that took me embarrassingly long to internalise: most re-render problems are component-structure problems wearing a costume. Reach for the structure first. It's usually less code, it has no deps array, and it can't go stale.

There are two moves. Learn both — they show up constantly in interviews as the "what would you do instead?" follow-up.

Move 1: Push state down

If state lives high in the tree but is only used low in the tree, every update re-renders everything in between for nothing. So move the state to where it's used.

❌ Buggy-ish — every keystroke re-renders the huge list

function Page() {
  const [name, setName] = useState('');  // 👈 only the input cares about this

  return (
    <>
      <input value={name} onChange={e => setName(e.target.value)} />
      <ExpensiveProductList />   // re-renders on every keystroke 😖
    </>
  );
}

✅ Fixed — the state moved into its own little component

function NameField() {
  const [name, setName] = useState('');
  return <input value={name} onChange={e => setName(e.target.value)} />;
}

function Page() {
  return (
    <>
      <NameField />              // updates are now trapped in here
      <ExpensiveProductList />   // Page never re-renders, so this never does 🎉
    </>
  );
}

Remember: state updates flow downward. By moving the state down, you shrank the subtree beneath it. No memo, no deps array, and the component is arguably better designed now anyway.

Move 2: Lift content up, using children

Sometimes you can't move the state down — the state genuinely belongs at the top. A theme toggle, a modal open/closed, a drag position. In that case you move the expensive content up and pass it through as children.

This one is genuinely brain-bending the first time you see it, so let's take it slowly.

❌ Buggy-ish — state at the top drags everything with it

function App() {
  const [isOpen, setIsOpen] = useState(false);

  return (
    <div className={isOpen ? 'shifted' : ''}>
      <button onClick={() => setIsOpen(!isOpen)}>Toggle</button>
      <ExpensiveDashboard />   // re-renders on every toggle
    </div>
  );
}

✅ Fixed — the expensive thing is created by a component that doesn't re-render

function Shell({ children }) {          // 👈 the state now lives here
  const [isOpen, setIsOpen] = useState(false);

  return (
    <div className={isOpen ? 'shifted' : ''}>
      <button onClick={() => setIsOpen(!isOpen)}>Toggle</button>
      {children}                    // 👈 just a prop, not re-created here
    </div>
  );
}

function App() {
  return (
    <Shell>
      <ExpensiveDashboard />        // created by App, which never re-renders
    </Shell>
  );
}

Why does this work? Because <ExpensiveDashboard /> — that JSX object from section 1 — is created inside App's render, not Shell's. App has no state, so it renders once and never again. Its children element object is therefore created once, with a stable identity forever.

When Shell's state changes and Shell re-renders, it hits {children} and finds the exact same element object it had last time. React's reconciler sees an identical element reference and bails out of re-rendering that branch — without any React.memo at all. You got memoization for free, out of the shape of the tree.

Wait — React bails out on identical elements automatically?

Yes. If React encounters the exact same element object (same reference) in the same position as last render, it knows the output can't have changed, and it skips that subtree. This is a built-in reconciler optimisation that predates hooks, and almost nobody knows it exists. It's the entire engine behind the children trick.

This is also, incidentally, why <MemoizedPanel><Chart /></MemoizedPanel> from section 5 breaks: there, the <Chart /> element is being re-created by a parent that re-renders. Same mechanism, opposite outcome.

Move 3 (bonus): split the component

A 400-line component with nine pieces of state re-renders all 400 lines when any one of them changes. Splitting it into four components with their own state means an update only re-renders a quarter of the work. Component splitting isn't just a code-cleanliness thing — it's a performance boundary, because render scope follows component boundaries.

Section 10The React Compiler

Everything in the last five sections is manual bookkeeping. You, a human, working out which values need stable identities and maintaining dependency arrays by hand. That's exactly the kind of tedious, mechanical, error-prone job a compiler should be doing.

So the React team built one. The React Compiler is a build-time tool (a Babel plugin) that analyses your components, figures out what depends on what, and inserts the memoization automatically — around values, around functions, and around chunks of JSX.

What you write vs. what ships

// You write this — plain, readable, no hooks noise:
function Cart({ items }) {
  const total = items.reduce((sum, i) => sum + i.price, 0);
  const handleClear = () => clearCart();
  return <CartView total={total} onClear={handleClear} />;
}

// The compiler emits code that caches `total`, `handleClear` and the
// resulting JSX in a hidden per-render cache, keyed on what they depend on.

It only does this where it can prove your code follows the Rules of React — components must be pure functions of their props and state, no mutating props, hooks called unconditionally. Where it can't prove that, it bails out on that component and leaves it alone. Which means writing idiomatic React is what unlocks the optimisation.

In an interview: how to talk about the compiler today

Don't say "the compiler handles it, so memoization doesn't matter." That's the wrong lesson and interviewers hear it as a dodge. Say something closer to:

Say something like

"The React Compiler auto-memoizes at build time, so a lot of manual useMemo and useCallback becomes unnecessary. But I'd still want to understand what it's doing, for three reasons: most codebases I'd join aren't on it yet; it bails out on components that break the Rules of React, so you need to recognise when that's happened; and when you're profiling, you still have to reason about which components re-rendered and why. The compiler changes who writes the memo, not whether you need to understand re-renders."

Why it lands: it shows you're tracking where the ecosystem is going without using it as an excuse to skip the fundamentals. That combination — current and grounded — is exactly the senior signal.

Section 11Context, properly understood

Let's change topic — though you'll see in about two sections why it isn't really a change of topic at all.

Say the currently logged-in user needs to be available in a component seven levels deep. The obvious approach is to pass it down, hop by hop:

❌ Prop drilling

<App user={user}>
  <Layout user={user}>
    <Sidebar user={user}>
      <UserPanel user={user}>
        <Avatar user={user} />   // 👈 finally, someone who wanted it

Every component in the chain takes a prop it doesn't use, purely to hand it along. It's noisy, it makes those components harder to reuse, and adding one more field means editing five files.

The analogy that gets Context right: prop drilling is passing a parcel hand-to-hand down a line of people. Context is the building's mail chute. You drop the parcel in at the top and anyone on any floor can open their hatch and take it out. The people in between never touch it and never even know it went past. (Where it breaks down: a real mail chute delivers to one address. Context broadcasts to everyone who opens a hatch — which turns out to be the entire performance story.)

The three pieces

Create → Provide → Consume

// 1. Create the channel (module scope, outside any component)
const UserContext = createContext(null);

// 2. Provide a value to a subtree
function App() {
  const [user, setUser] = useState(null);
  return (
    <UserContext value={user}>   {/* React 19+; before that: <UserContext.Provider> */}
      <Layout />
    </UserContext>
  );
}

// 3. Consume it, at any depth
function Avatar() {
  const user = useContext(UserContext);  // 👈 no props needed
  return <img src={user.avatarUrl} alt={user.name} />;
}

useContext walks up the tree from the calling component looking for the nearest matching provider, and returns that provider's value. If it doesn't find one, you get the default you passed to createContext — which, by the way, is why passing null and then reading user.name gives you the classic "cannot read property of null" when someone forgets the provider. A common pattern is a custom hook that throws a clear error instead:

✅ A friendlier consumer

function useUser() {
  const context = useContext(UserContext);
  if (context === null) {
    throw new Error('useUser must be used inside a <UserProvider>');
  }
  return context;
}

The thing you must say in an interview

Context is not a state manager. Context is dependency injection.

This distinction is the whole ballgame, so let's make it precise. Context has no state of its own. It stores nothing, updates nothing, and has no notion of actions or reducers or selectors. It is a transport — a way to move a value from one place in the tree to another without threading it through the middle.

The state still lives in a useState or useReducer somewhere. Context just makes it reachable. Saying "I'll use Context for state management" is like saying "I'll use the postal service for storing my documents." The post moves things. It doesn't file them.

A common misconception

"Context re-renders consumers when the state changes." Nearly right, and the imprecision is where the bug lives. Context re-renders consumers when the value prop's identity changes, compared with Object.is. That's often the same thing as "the state changed"... and often catastrophically not, as we're about to see.

Section 12Why Context causes performance problems

Here's the rule, and it's short: when a provider's value changes identity, every component that consumes that context re-renders. All of them. Even ones that only read one field. Even ones wrapped in React.memo.

Read that last clause again, because it surprises people. React.memo blocks re-renders coming from the parent — that's cause #2 from section 2. A context update is cause #3, a completely separate channel. Memo has no authority over it. A memoized consumer will re-render on every context change, forever.

The classic value={{ ... }} bug

Now combine that rule with section 4, and you get the single most common Context performance bug in existence. It's in an enormous number of real codebases, probably including one you've worked in.

❌ Buggy — looks completely normal, re-renders your entire app

function UserProvider({ children }) {
  const [user, setUser] = useState(null);
  const [theme, setTheme] = useState('light');

  return (
    <UserContext value={{ user, setUser }}>  {/* 👈 new object EVERY render */}
      {children}
    </UserContext>
  );
}

Spot it? {{ user, setUser }} is an object literal in the component body. New address on every render of UserProvider.

So: someone toggles the theme. UserProvider re-renders. A brand new { user, setUser } object is created — same contents, different identity. React compares it with Object.is against the old one, sees they differ, and notifies every consumer of UserContext in the entire application to re-render. The user object didn't change at all. Not one byte. But every consumer re-renders anyway.

And this is precisely the case where memo can't save you. A memoized consumer still re-renders, because context bypasses memo entirely.

✅ Fixed — a stable value identity

function UserProvider({ children }) {
  const [user, setUser] = useState(null);
  const [theme, setTheme] = useState('light');

  const value = useMemo(() => ({ user, setUser }), [user]);
  // 👆 setUser from useState is already stable, so `user` is the only real dep

  return <UserContext value={value}>{children}</UserContext>;
}

Now toggling the theme re-renders UserProvider, useMemo sees user is unchanged, hands back the same object, Object.is passes, and no consumer re-renders. This is that "reason two" for useMemo from section 6, doing serious work: the object is trivially cheap to build, and memoizing it is still absolutely correct, because identity is what matters here.

Wait — is setUser really stable?

Yes. React guarantees the setter returned by useState keeps the same identity for the life of the component, and the same goes for dispatch from useReducer. That's a deliberate design decision, precisely so you can safely leave them out of dependency arrays. Custom functions you write yourself have no such guarantee — those need useCallback.

Mitigation 2: split state from dispatch

The useMemo fix solves "the provider re-rendered for an unrelated reason." It does not solve the deeper problem: when user genuinely does change, every consumer still re-renders — including the ones that only ever call setUser and never read user at all.

So split the context in two: one for the value, one for the updater.

✅ Two contexts, two audiences

const UserContext = createContext(null);
const UserDispatchContext = createContext(null);

function UserProvider({ children }) {
  const [user, dispatch] = useReducer(userReducer, null);

  return (
    <UserContext value={user}>
      <UserDispatchContext value={dispatch}>  {/* 👈 identity never changes */}
        {children}
      </UserDispatchContext>
    </UserContext>
  );
}

Now a component that only needs to dispatch — a logout button, a form's submit handler — subscribes only to UserDispatchContext. Since dispatch's identity never changes, that context value never changes, and those components never re-render from state updates at all. Only the components that actually read the user data re-render when the user data changes.

Notice we didn't even need useMemo here: passing user directly means the value is the state, so its identity only changes when the state does. Splitting removed the need for the memo entirely. Nice when that happens.

The same idea generalises: make each context as narrow as the thing that changes. One giant AppContext holding user, theme, locale, cart and notifications is a machine for re-rendering everything whenever anything happens. Four small contexts means a theme change only wakes up the theme readers.

Under the hood: why is there no selector?

You might wonder why React can't just let you write useContext(UserContext, u => u.name) and only re-render when name changes. There have been proposals for exactly this for years (the community package use-context-selector approximates it with some clever internals), but it isn't in React.

The reason is that context propagation is baked into how React walks the fiber tree during a render pass — when a provider's value changes, React marks the consumers it finds as needing work. Adding per-consumer selector comparison changes the shape of that traversal in ways that interact with concurrent rendering. So for now: no selectors. Which is exactly the capability external stores exist to provide.

Section 13Context vs. prop drilling vs. an external store

You now know enough to answer the real question, which is not "which is best" but "which problem am I actually having."

Prop drilling

The default, and it's underrated. Explicit, trivially debuggable, no indirection — you can read a component's signature and know precisely what it depends on. It's also the fastest, because React does nothing special.

It becomes a problem when the chain gets long and the middle components have no use for the data. Two or three levels of drilling is completely fine and I'd leave it. Six levels through components that don't care is a smell — but check first whether composition fixes it, because half the "I need Context" cases are really "I passed a component where I should have passed children."

Context

Right when: the value is needed in many places at many depths, and it changes infrequently.

The canonical examples are canonical for a reason — theme, current user / auth, locale and translations, feature flags, a design-system config. Each is read all over the app and changes maybe once a session. A full-app re-render when you switch to dark mode is completely acceptable; it happens once and the user is expecting a visual change anyway.

Wrong when:

  • High-frequency updates. Mouse position, scroll offset, a form field on every keystroke, a websocket price tick. Every update re-renders every consumer, and at 60 updates a second you've built a stutter machine.
  • One big blob of state with many independent slices. Without selectors, a change to any slice re-renders readers of all slices.
  • You need real state-management features — middleware, devtools time-travel, derived/computed values with caching, optimistic updates, persistence, undo. Context provides none of that, because it isn't a state manager.

An external store (Redux Toolkit, Zustand, Jotai, MobX…)

Here's the key architectural difference, and it's worth saying explicitly in an interview because it shows you understand why these libraries exist rather than just that they do.

The state lives outside the React tree. Components don't receive it through rendering — they subscribe to it, and crucially they subscribe with a selector: "wake me up only when cart.itemCount changes."

Subscribing to a slice (Zustand-flavoured)

function CartBadge() {
  // Re-renders ONLY when itemCount changes.
  // Other parts of the store can churn all day; this component won't notice.
  const itemCount = useCartStore(state => state.items.length); // 👈 selector
  return <span>{itemCount}</span>;
}

That selector is the thing Context structurally cannot do. Under the hood these libraries use useSyncExternalStore — the fourth re-render trigger from section 2 — which lets a component say "here's how to subscribe, and here's the specific snapshot I care about." React re-renders it only when that snapshot changes.

Which is why the honest answer to "can Context replace Redux?" is partly. Context + useReducer genuinely replaces Redux for small-to-medium app state with infrequent updates, and for a lot of apps that's plenty. What you don't get is selectors, middleware, devtools, or a good story for very frequent updates. If you're hand-rolling those on top of Context, you're building a worse Redux.

The decision framework

Learn this ladder. It's a genuinely good answer to a very common question, and the ordering is the point — you climb only when the current rung actually hurts.

Wait — what about server data?

Worth a sentence, because it's a strong extra point to make. A huge amount of what people put in Redux isn't really client state at all — it's a cached copy of data from the server. That has its own problems (caching, revalidation, loading and error states, deduping requests) that general state managers don't solve, which is why TanStack Query, SWR and RTK Query exist. Splitting "server cache" from "client UI state" often shrinks your global state to almost nothing. Saying this in an interview reads as genuine modern experience.

Section 14How to actually diagnose a perf problem

Everything so far has been "what to do." This section is "how to know what to do," and it's the part most candidates can't speak to — which makes it a great place to stand out.

The discipline, stated plainly: measure, change one thing, measure again. Optimising without profiling isn't engineering, it's ritual. And it's specifically dangerous in React because your intuitions about what's slow are usually wrong — the render you're worried about takes 0.3ms and the one that's killing you is a chart library you forgot re-mounts.

Step 1: is it actually a React problem?

Before opening React DevTools, check the browser's own Performance panel. Plenty of "React is slow" turns out to be a 4MB unoptimised image, a blocking third-party script, an N+1 waterfall of network requests, or a CSS animation on a property that triggers layout. React can't be blamed for any of those, and no amount of useMemo will help.

Step 2: "Highlight updates when components render"

This is the fastest possible triage and takes five seconds. In the React DevTools Components tab, open the settings gear → General → tick "Highlight updates when components render."

Now use your app. Every component that re-renders flashes with a coloured outline — and the colour tells you the frequency: blue/green for occasional, yellow then red for components re-rendering many times in quick succession.

What you're looking for: type one character into a search box and see half the screen flash. That's your problem, located in seconds. If a big region flashes on an interaction that shouldn't affect it, you've found where state is living too high in the tree.

Step 3: the Profiler

The Profiler tab is the real instrument. Hit record, perform the slow interaction, hit stop. You get:

The commit bar chart across the top — one bar per commit, height and colour showing how long it took. Tall yellow bars are your suspects. Click one to inspect it.

The flame chart for the selected commit. Bars are the component tree; width is how long that component and its descendants took to render. Grey bars mean "did not render in this commit" — and grey is what you want to see. A wide coloured bar with lots of coloured children beneath it is a subtree that re-rendered when it probably didn't need to.

Read it top-down: find the widest coloured bar, ask "why did this render at all?", then walk down to where the real time is being spent.

The ranked chart (the second toggle) sorts every component that rendered in that commit by its own render time, most expensive first. Great when the flame chart is too tall to scan.

Step 4: "Why did this render?"

This is the killer feature and it's off by default. In Profiler settings, tick "Record why each component rendered while profiling." Now clicking any component in a commit shows a reason:

  • "Props changed: (config, onSelect)" — and it names them. If a prop is listed that you know is logically identical every time, you've just found a reference-identity bug.
  • "Hooks changed" — its own state or a hook it depends on.
  • "Context changed" — a context it consumes got a new value. If this fires on interactions unrelated to that context, go straight to the value={{...}} bug.
  • "The parent component rendered" — the default cascade from section 2. Fix it structurally or with memo.

That list maps one-to-one onto section 2's causes, which is not a coincidence — it's the same model, surfaced as a tool.

Under the hood: a couple of practical notes

Profile a production-like build where you can. Development React is substantially slower (extra checks, warnings, StrictMode double-invocation), so dev numbers overstate everything. React ships a react-dom/profiling build for profiling production bundles.

You can also instrument programmatically with <Profiler id="Cart" onRender={callback}>, which fires with actual and baseline durations for a subtree — handy for logging real-user timings rather than your own fast laptop.

In an interview: "how would you find why a component re-renders too much?"
Say something like

"I'd start with the React DevTools Profiler rather than guessing. I'd turn on 'record why each component rendered', record the slow interaction, and find the expensive commits in the bar chart. Then in the flame chart I'd look for wide subtrees that shouldn't have rendered, and check the reason React gives — props changed, hooks changed, context changed, or parent rendered. Each of those points at a different fix: a props-changed on a value that's logically identical means an unstable reference, context-changed on an unrelated interaction usually means an unmemoized provider value, and parent-rendered usually means the state is sitting too high in the tree. I'd also flip on 'highlight updates' first, since that often shows the problem in about five seconds."

Why it lands: almost everyone can name React.memo; far fewer can describe a diagnostic process. This answer shows you've actually sat in front of the Profiler, and it demonstrates the loop — measure, identify cause, choose the fix that matches the cause — which is the transferable skill they're really probing for.

Section 15The follow-up questions, answered

These are the ones that come after the first answer, when the interviewer is checking whether you actually understand it or just memorised the headline. Try answering each before expanding it.

"Does React.memo do a deep comparison?"
Answer

No. It's a shallow comparison: it iterates the props object one level deep and runs Object.is on each value. It never recurses into nested objects or arrays. So user={{ name: 'Ada' }} fails the check every render even though the contents are identical, because the outer object is a new reference.

It's shallow on purpose — a deep comparison could walk an arbitrarily large object graph on every render and easily cost more than the render it's trying to skip. If you genuinely need different comparison semantics, you pass a custom comparator as the second argument, but that's an escape hatch and it's easy to introduce stale-prop bugs with it.

"Why isn't my React.memo working?"
Answer

Almost always because the parent is passing a new reference every render — an inline object, array literal, or arrow function. Memo's shallow check compares by reference, so those always look "changed" and the memo skips nothing while still costing you a comparison.

The fix is to stabilise the props with useMemo/useCallback. Memo on the child and stable props from the parent are a matched pair; either one alone does nothing.

Three other causes worth naming: the component has its own state that's updating (memo can't block that); it consumes a context whose value is changing (memo can't block that either — context bypasses it); or you're passing children, which is a freshly-created element object every render.

"useMemo vs useCallback?"
Answer

useMemo caches the result of calling a function. useCallback caches the function itself. They're literally the same mechanism — useCallback(fn, deps) is exactly useMemo(() => fn, deps); useCallback just exists so you don't have to write the double arrow.

Use useMemo for an expensive computation or to keep a derived object/array's identity stable. Use useCallback when you're passing a handler to a memoized child or into another hook's dependency array.

"Should you wrap everything in useMemo?"
Answer

No — the default should be not to memoize. Each one costs a comparison on every render, holds memory for the life of the component, adds a dependency array that can drift out of sync and cause stale bugs, and makes the code meaningfully harder to read. For a value like a + b, comparing the deps costs more than recomputing.

Memoize when profiling shows a real cost, or when you specifically need reference stability — to make a React.memo boundary work, to keep an effect from firing every render, or for a Context provider value. And note the React Compiler now automates much of this, which is a decent signal that manual memo-everything was never the right default.

"What's the cost of memoization?"
Answer

Four things. CPU: the dependency or prop comparison runs on every render, in addition to the work you were already doing. Memory: the cached value and deps array are retained for the component's lifetime — multiply that by every row in a long list. Correctness risk: the deps array is a manual invariant, and a missing dep gives you a stale closure or stale value, which are nasty intermittent bugs. Readability: it's more code, and it signals to future readers that something here is expensive, which may not be true.

And there's a fifth, sneakier one: a memo whose props aren't stable pays all of the above and delivers none of the benefit.

"How do you stop a component re-rendering?"
Answer

First I'd ask whether I should — most re-renders are cheap, and the render phase rarely touches the DOM. But assuming it's a measured problem, it depends on why it's rendering.

If it's because the parent re-rendered, the best fixes are structural: move the state down into a smaller component so the expensive subtree isn't beneath it, or pass the expensive part as children from a component that doesn't re-render — React bails out automatically when it sees the identical element reference. Those need no dependency arrays and can't go stale. If structure won't work, React.memo plus stable props.

If it's because of its own state, you can't block it and shouldn't want to — but you can shrink the component so less re-renders. If it's from context, memoize the provider value and split the context so it only consumes the slice it cares about; memo won't help there.

"Why does Context cause performance problems?"
Answer

Because it's a broadcast with no selectors. When the provider's value changes identity — compared with Object.is — every consumer of that context re-renders, even one that only reads a single field, and even one wrapped in React.memo, because context updates bypass memo entirely.

The classic bug is passing an inline object, value={{ user, setUser }}. That's a new reference on every render of the provider, so any unrelated state in the provider re-renders every consumer in the app even though the user data never changed. You fix that with useMemo on the value.

The deeper mitigation is splitting contexts — separate the state from the dispatch, and keep each context narrow — since dispatch from useReducer is identity-stable, so components that only dispatch never re-render at all. But you can't fully fix the fan-out: when the state genuinely changes, all readers re-render, and that's why high-frequency state doesn't belong in Context.

"Can Context replace Redux?"
Answer

For some apps, yes. Context plus useReducer gives you a store-like shape — state, dispatch, reducer — and for app state that's small and changes infrequently that's genuinely enough, with no dependency to add.

What you don't get is what Redux actually provides beyond storage: selectors, so components subscribe to a slice instead of everything; middleware; devtools and time-travel; and a structure that scales to many independent slices. Context has no selector mechanism, so every update wakes every consumer.

So my rule is: Context for low-frequency, app-wide values like theme, auth and locale; an external store like Redux Toolkit or Zustand when updates are frequent, the state has many independent slices, or I need selectors and devtools. And I'd add that a lot of what used to go in Redux is really server cache, which belongs in something like TanStack Query instead.

"Why not just use one big AppContext for everything?"
Answer

Because the granularity of a context is the granularity of your re-renders. One context holding user, theme, cart and notifications means a notification arriving re-renders every component that reads the theme. Splitting into narrow contexts means each update only wakes the components that care. It's also better for testing and reuse — a component that only needs the theme shouldn't need the whole app's state mocked to render.

"You memoized the provider value — does that solve Context's performance problem?"
Answer

It solves half of it. useMemo stops spurious re-renders — the case where the provider re-rendered for an unrelated reason and created a new value object with identical contents.

It doesn't help when the state genuinely changes, because then the value legitimately has a new identity and every consumer re-renders by design. Context has no way for a consumer to say "only wake me if this one field changed." That's a structural limit, and it's exactly the point where you split contexts, or move to a store with selectors.

"Isn't useCallback avoiding the cost of creating a function?"
Answer

No — the function is still created on every render; that expression evaluates regardless. useCallback receives it, throws it away, and returns the previously stored one. What you gain is a stable identity, not a skipped allocation. Creating a closure is cheap anyway; the reason to use useCallback is always identity, never allocation cost.

Traps that get candidates dinged

Don't saySay instead
"A component re-renders when its props change." "A component re-renders when its own state changes, its parent renders, or a context it consumes changes. Props changing is a symptom of the parent rendering, not an independent cause."
"Re-renders are bad / re-render means the DOM updates." "A re-render is React calling the function and diffing the result. The DOM is only touched where the output actually differs, so most re-renders are cheap."
"I memoize everything to be safe." "I profile first. Every memo has a real cost, and memoizing by reflex often adds cost without benefit."
"React.memo stops all re-renders." "It only blocks re-renders caused by the parent. Its own state and context updates go straight past it."
"Context is React's built-in state management." "Context is dependency injection — a transport for values. The state still lives in useState/useReducer; Context just avoids drilling it."
"useMemo guarantees the value is only computed once." "It's a performance hint. React may discard the cache, so never rely on it for correctness or side effects."

The morning-of version. One crisp line each.

What is a render?
React calling your component function to get a description of the UI. Committing that description to the DOM is a separate, later step.
What causes a re-render?
Own state changed · parent re-rendered · a consumed context value changed. (Plus an external store subscription firing.)
The misconception to kill
A component re-renders because its parent did, not because its props changed. Props can't change without the parent rendering.
Are re-renders expensive?
Usually no — microseconds, and no DOM work unless output actually differs. They get expensive through volume, heavy computation, or high frequency.
Value vs. reference
Objects, arrays and functions compare by identity, not contents. Every render creates new ones. This causes ~90% of memo bugs.
React.memo
Skips a component's render (and its whole subtree) if props are shallowly equal. Blocks parent-driven renders only — not own state, not context.
Shallow or deep?
Shallow. One level, Object.is per prop. Never recurses. Optional second-arg comparator returns true to skip — inverted vs. shouldComponentUpdate.
useMemo
Caches a computed value across renders, keyed on a deps array. Two reasons: expensive computation, and preserving reference identity for a memo boundary, a deps array, or a Context value.
useCallback
Caches a function's identity. Exactly useMemo(() => fn, deps). The function is still created each render; only the identity you use is stable.
Cost of memoizing
Comparison on every render, retained memory, a deps array that can go stale, worse readability — and zero benefit if the props aren't stable.
Better than memoizing
Move state down · pass expensive content as children (React bails out on identical element references) · split big components.
React Compiler
Auto-memoizes at build time where it can prove your components follow the Rules of React. Changes who writes the memo, not the need to understand re-renders.
What Context is
Dependency injection / transport, not a state manager. It moves a value down the tree without prop drilling. State still lives in a hook.
Context's performance problem
Every consumer re-renders when the provider value's identity changes — even readers of one field, even memoized ones. No selectors.
The classic bug + fix

Context vs. external store
Context: app-wide, low-frequency (theme, auth, locale, flags). Store: frequent updates, many slices, selectors, middleware, devtools.
The ladder

If you take one thing from all of this, make it the shape of the reasoning rather than the API surface. Interviewers asking about useMemo are almost never checking whether you know its signature — they're checking whether you understand that performance work is a trade, that you make trades from evidence, and that the cheapest fix is usually a better component structure rather than a smarter cache.

Know why a component re-rendered, know what it actually cost, and know the boring structural fix you'd try before the clever one. That's the answer they're listening for. 🎯
