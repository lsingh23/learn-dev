How React Actually Renders

Virtual DOM, reconciliation, keys, and Fiber — the machinery under the JSX you've been writing.

Here's a small React component. I want you to predict what it does.

Guess first 🤔
function LoginForm() {
  const [isSignUp, setIsSignUp] = useState(false);

  return (
    <form>
      {isSignUp
        ? <input placeholder="Choose a username" />
        : <input placeholder="Email address" />}
      <button onClick={() => setIsSignUp(!isSignUp)}>switch</button>
    </form>
  );
}

You type hello@example.com into the box. Then you click "switch". The placeholder changes to "Choose a username"… and your text is still there. You're now looking at a username field containing an email address.

Most people expect the old input to be destroyed and a brand new, empty one to appear. It isn't. React quietly reused the exact same <input> DOM node and just swapped one attribute.

That's not a bug, and it's not arbitrary. It falls directly out of how React decides what to touch in the DOM. By the end of this guide you'll be able to look at that snippet and say "yeah, obviously" — and you'll be able to explain why to an interviewer without hand-waving.

We're going to build this up from the very bottom: what the DOM is, why writing to it directly is painful, what a React element actually is (spoiler: a plain object), the two phases of a render, the diffing rules, keys, and finally Fiber. No forward references. If I use a word, I've taught it.

1. The problem: talking to the DOM by hand

Before React, before frameworks, there was just the DOM. Let's make sure that word is solid, because everything else stacks on top of it.

When the browser loads your HTML, it doesn't keep the HTML text around. It parses it into a tree of objects in memory — one object per tag, nested the way your tags were nested. That tree is the DOM (Document Object Model). Each object has properties (textContent, className, value) and methods (appendChild, remove). JavaScript can reach into that tree and change it, and the browser re-paints the screen to match.

So the DOM is the browser's live, mutable model of the page. It's the only thing that actually puts pixels on screen. React, Vue, Svelte, jQuery — all of them ultimately end up calling the same handful of DOM methods. There's no secret back door.

What hand-writing DOM code looks like

Say we want a cart button in the header that shows the item count.

Imperative — you give step-by-step instructions
const button = document.createElement('button');
button.className = 'cart-btn';
button.textContent = `Cart (${cartCount})`;
button.addEventListener('click', openCart);
document.querySelector('#header').appendChild(button);

// ...somewhere else, much later, when the cart changes:
button.textContent = `Cart (${cartCount})`; // 👈 don't forget this line
// and if the cart is empty we also want to hide it, so:
button.style.display = cartCount === 0 ? 'none' : 'block';

This is imperative code: a list of commands describing how to change the page, step by step. And notice the shape of the bug that's waiting for you. The description of what the button should look like is now written twice — once when creating it, once when updating it. Every time you add a new piece of state that affects this button, you have to remember to add a matching line in the update path. Miss one, and your UI is showing a stale number. This is where "the badge says 3 but the cart has 4 things in it" bugs come from, and in a real app there are hundreds of these little sync points.

Now the React version:

Declarative — you describe the result
{cartCount > 0 && (
  <button className="cart-btn" onClick={openCart}>
    Cart ({cartCount})
  </button>
)}

There's exactly one description of the button, and it's written in terms of the data. There's no "update path" to forget, because there is no update path — you just describe what the UI is for the current values, every time. That's declarative: you state what you want, and something else figures out how to get there.

"Fine, so just rebuild everything on every change"

Here's the tempting shortcut. If describing the whole UI from scratch is so pleasant, why not do exactly that — regenerate the entire HTML string and slam it into the page?

❌ The naive way to get declarative UI
function render() {
  app.innerHTML = `
    <h1>${title}</h1>
    <input value="${draft}" />
    <ul>${items.map(i => `<li>${i}</li>`).join('')}</ul>
  `;
}

This works! For about ten seconds. Then you notice:

  • The user was typing in that input. Blowing away innerHTML destroys the real input node and builds a new one, so focus is lost and the cursor jumps. Try typing in a field that gets rebuilt on every keystroke — it's unusable.
  • Scroll position resets. Text selection vanishes. CSS transitions restart. A playing <video> stops dead.
  • Every event listener you attached is gone with the nodes it was attached to.
  • And it's genuinely slow, because of the next bit.

Why DOM writes are expensive

Reading a property off a DOM node is cheap. Writing one can be very expensive — not because the write itself is slow, but because of what it triggers.

When you change something that affects geometry — text content, width, padding, adding a node — the browser has to recompute where everything on the page goes. That's layout (also called reflow): "given these boxes and these styles, what are the exact x/y/width/height of every element?" Then it has to paint those boxes into pixels, and composite the layers together.

Layout is the pricey one, because changing one element's size can push its siblings around, which can resize its parent, which can push that element's siblings around. One innocent write can force the browser to re-measure a large chunk of the page.

So we're stuck between two bad options. Hand-written imperative updates are minimal but miserable to maintain. Regenerating everything is lovely to write but destroys the page and thrashes layout.

What we want is to write the second one and get the performance and node-preservation of the first. That is the entire reason the virtual DOM exists. Hold onto that sentence — it's the answer to half the interview questions in this guide.

2. What a React element actually is

Time to demystify JSX, because people carry a lot of superstition about it.

JSX is not part of JavaScript. Browsers have no idea what <button className="x"> means in a .js file. A build tool (Babel, or the compiler inside Vite/Next) transforms it before it ever reaches the browser. And the transform is boring — it's a plain function call.

What you write
<button className="cart-btn" onClick={openCart}>
  Cart
</button>
What the compiler produces (classic transform)
React.createElement(
  'button',
  { className: 'cart-btn', onClick: openCart },
  'Cart'
);

Modern setups use the "automatic runtime" and emit jsx('button', {...}) imported from react/jsx-runtime instead, so you don't need import React at the top of every file. Same idea, slightly different plumbing.

Now the important part. What does createElement return? Not a DOM node. Not a class instance. Not anything magical. It returns a plain JavaScript object, roughly this:

A React element, logged
{
  $$typeof: Symbol(react.element),   // security marker, ignore it
  type: 'button',                   // 👈 a string = host element
  key: null,
  ref: null,
  props: {
    className: 'cart-btn',
    onClick: openCart,
    children: 'Cart'
  }
}

That's it. That's a React element. It is a description of what you want on screen, frozen into an object. It has no methods that draw anything. Creating one costs about as much as creating any small object — which is why React is happy to create thousands of them per second.

For your own components, type holds the function itself:

<CartButton count={3} />
{
  type: CartButton,   // 👈 the actual function reference, not a string
  key: null,
  props: { count: 3 }
}

And because children is just another prop, nesting produces nested objects. A whole screen's worth of JSX becomes one big tree of these little objects.

The mental model

A React element is a blueprint, not a building. It's the architect's drawing that says "a 2-metre door here, painted blue". You can print a thousand copies of a drawing cheaply. Actually knocking a wall down and hanging a door is the expensive part — that's the DOM.

Where the analogy breaks: a blueprint is drawn once and built once. React re-draws the entire blueprint on every render and hands it to a builder who compares it against what's already standing.

3. So what is the virtual DOM? (and is it faster?)

The virtual DOM is that tree of plain element objects. That's the whole thing. It's a lightweight, in-memory, JavaScript-object description of what the UI should look like right now.

And here is the loop:

  1. Something changes (state updates).
  2. React calls your components again, producing a new tree of element objects.
  3. React compares that new tree to the previous one it kept around.
  4. It works out the minimum set of real DOM operations that would turn the old UI into the new one.
  5. It performs only those operations.

You get to write "here is the entire UI for this data" — the pleasant declarative style — and React converts that into targeted surgery on the real DOM, which is what the hand-written imperative version was doing all along.

A common misconception

"The virtual DOM is faster than the real DOM."

This is the single most-parroted line in frontend interviews, and it doesn't survive one follow-up question. The virtual DOM is extra work — you're building a tree of objects and running a diff that hand-written code wouldn't need at all. A tuned vanilla-JS update will beat React every single time, because it skips all of that.

The comparison that actually makes sense is: virtual DOM vs. the naive declarative alternative (throw away the DOM and rebuild it from scratch). Against that, yes, hugely faster. Against a careful human doing surgical textContent updates? No.

The honest framing: the virtual DOM is a tool for making declarative UI practical while keeping DOM writes minimal. It buys maintainability at a small, predictable CPU cost, and it's fast enough. Say that in an interview and you'll stand out immediately.

Under the hood — optional

Some frameworks skip the virtual DOM entirely. Svelte compiles your template into imperative DOM instructions at build time; Solid uses fine-grained reactivity so a change to one signal updates exactly one text node with no diffing at all. They're proof that the virtual DOM isn't the only way to get declarative UI — it's one trade-off, chosen for flexibility (it works with plain JS control flow, arbitrary functions, and multiple renderers like React Native) rather than for raw speed.

4. Render vs commit — the most important distinction

If you take one thing from this guide, take this: "rendering" does not mean "touching the DOM."

The word is horribly overloaded. In everyday English, "rendering" means drawing something on a screen. In React, it means something much narrower and much less scary:

Render = React calls your component function and collects the element objects it returns.

That's it. Calling a function. Building objects. Zero pixels move. Nothing in the DOM changes. If your component re-renders 60 times and the output is identical every time, the browser does nothing at all — no layout, no paint.

Then, separately:

Commit = React applies the differences it found to the real DOM.

Why does splitting these matter so much? Two reasons, and both come up in interviews.

First, it defuses the panic about re-renders. "My component re-rendered!" is not automatically a problem. If the output is the same, the commit phase has nothing to do. A re-render that produces an identical tree costs you one function call and a shallow comparison — measured in microseconds. Reaching for React.memo everywhere to prevent re-renders is usually solving a problem you don't have, and the memo comparison itself isn't free.

Second, it's why the render phase must be pure. React reserves the right to call your component, throw the result away, and call it again. Or start rendering, get interrupted by something more urgent, and restart from scratch. If your component body mutates a variable outside itself, or writes to localStorage, or fires off a fetch, those side effects happen an unpredictable number of times. That's exactly why side effects belong in useEffect — effects run in or after the commit phase, which happens exactly once per committed update. It's also why StrictMode double-invokes your components in development: it's smoking out impure render logic on purpose.

Wait, what about…

"So does a re-render always update the DOM?" No — and this is a great interview answer because it proves you understand the two phases. A re-render always means "React called my component again." It only means "the DOM changed" if the new element tree differs from the old one in a way that requires a DOM operation. Re-render 100 times with identical output and React performs zero DOM writes.

5. Reconciliation: the diffing algorithm

Reconciliation is React's name for step 4 above — figuring out what changed between the old tree and the new one. Let's understand why it needs a trick.

Why a "proper" tree diff is impossible

The general computer-science problem here is: given two trees, find the minimum sequence of operations that transforms one into the other. The best known algorithms for that run in O(n³) — where n is the number of nodes.

Let's feel that number. A modest page has 1,000 DOM nodes. 1,000³ is one billion operations. To update a page. Once. At that cost you'd be lucky to get one frame per second. Completely unusable.

So React cheats. It gives up on finding the minimum set of changes and instead uses two assumptions that are almost always true about real UIs. Those assumptions collapse the problem to O(n) — a single pass over the tree. The trade is: React will occasionally do more DOM work than strictly necessary, in exchange for being fast enough to run on every keystroke.

Under the hood — where the O(n) comes from

The general algorithm is expensive because it considers moving any node to any other position anywhere in the tree. React's heuristics forbid that entirely: it only ever compares nodes at the same position in the tree, and within a list it only compares siblings to each other. That means each node is visited a constant number of times, so total work is proportional to the number of nodes. That's the whole trick.

Heuristic 1: different type → tear it all down

If an element at a given position changed type — <div> became <span>, or <ProfileCard> became <LoadingSkeleton> — React does not try to salvage anything. It unmounts the old node and its entire subtree, destroys all their state, and builds the new subtree from scratch.

Before → after
// old
<div><Counter /></div>

// new
<span><Counter /></span>

// → the div is removed, Counter unmounts (state lost!),
//   a fresh span + fresh Counter are created.

Harsh? A bit. But the reasoning is solid: if the tag changed, the developer almost certainly meant "this is a different thing now", and any attempt at clever partial reuse would cost more than it saves.

Heuristic 2: same type → update in place and recurse

If the type matches, React keeps the existing DOM node. It compares the old props to the new props and applies only the ones that differ, then walks down into the children and does the same thing again.

Before → after
// old
<div className="card" title="Cart">...</div>

// new
<div className="card featured" title="Cart">...</div>

// → same <div> node kept. React runs exactly one operation:
//   node.className = 'card featured'
//   title is untouched. Children are then diffed the same way.

For a component type, "update in place" means: keep the component's state and hooks, hand it the new props, call the function again, and diff whatever it returns.

6. "Same position in the tree" — and the login-form surprise

Both heuristics hinge on the phrase "at the same position", so let's pin it down precisely, because this is where people's mental models quietly break.

React identifies a component by where it sits in the rendered tree — its path from the root: "first child of the root's second child", and so on. Not by what it's called in your source code. Not by which line of JSX produced it. Not by its props.

So: if the same component type shows up at the same slot in the tree on two consecutive renders, React considers it the same component instance and preserves its state — even if that JSX came from a completely different branch of a ternary.

Which brings us back to the snippet from the top of this guide.

The surprise, revisited
{isSignUp
  ? <input placeholder="Choose a username" />
  : <input placeholder="Email address" />}

Two different lines of source. Two different-looking bits of JSX. But look at what actually reaches the reconciler. Before the toggle, the first child of <form> is an element with type: 'input'. After the toggle, the first child of <form> is… an element with type: 'input'.

Same position. Same type. Heuristic 2 fires: reuse the node, patch the props that differ. React sets placeholder and moves on. The DOM node was never replaced, so the text you typed — which lives on the real DOM node — is still sitting there.

React can't see your ternary. By the time reconciliation runs, the ternary has already been evaluated; all that's left is a tree of objects. The source code that produced them is invisible.

Once you see it that way, the behaviour goes from "weird React quirk" to "well, obviously." That's the click.

Pushing on the edge: the same thing, but worse

Here's the version that trips up people who think they've got it:

What happens to the count when you toggle?
{isFancy
  ? <div className="fancy"><Counter /></div>
  : <section><Counter /></section>}
Take a guess, then open this

The count resets to zero. The wrapper at that position changed from div to section — different type — so heuristic 1 fires and the entire subtree is destroyed, Counter included. Its state goes with it.

Change the second branch to a <div> with different styling instead of a <section>, and the count survives. Same visual intent, totally different state behaviour, and the only difference is one tag name. This is exactly why understanding the reconciler beats memorising rules.

The conditional-rendering state loss

The flip side bites just as often:

Where did my form data go?
{showAdvanced && <AdvancedSettings />}

User expands the panel, half-fills the form, collapses it to check something, expands it again — everything's blank and they're annoyed.

Why: when showAdvanced is false, that expression evaluates to false, which React renders as nothing. The position is empty. AdvancedSettings is unmounted — its state is deleted, its effects are cleaned up. Toggling back mounts a brand new instance with fresh useState initial values.

This is React working correctly. If you want the state to survive, you have two options: keep the component mounted and hide it with CSS, or lift the state up to a parent that stays mounted.

✅ Keep it mounted, hide it visually
<div hidden={!showAdvanced}>
  <AdvancedSettings />   // 👈 never unmounts, keeps its state
</div>

The trade-off is real: hidden-but-mounted components still render, still run effects, still hold memory. For a heavy component you may prefer unmounting and lifting the important state up. There's no free lunch — just a choice you now understand well enough to make deliberately.

Trap: defining a component inside another component

This one looks harmless and causes a truly baffling bug — an input that loses focus after every single keystroke.

function Page() {
  function Field() { return <input />; }  // 👈 the bug
  return <Field />;
}

Every time Page renders, Field is a brand new function object. React compares element types with ===, so old Field !== new Field — different type, heuristic 1, whole subtree destroyed and rebuilt. The input node is replaced on every render, so focus and cursor position are lost. Always define components at module top level.

7. Keys: identity for lists

Everything so far compared nodes by position. That works beautifully for fixed structure — your header is always the first child, your footer is always the last. But lists break the assumption completely, because in a list, position is exactly the thing that changes.

The problem, concretely

Say we render three todos:

Old tree → new tree
// old              // new (we prepended "Call mum")
<li>Buy milk</li>    <li>Call mum</li>
<li>Walk dog</li>    <li>Buy milk</li>
                     <li>Walk dog</li>

A human sees "one item was inserted at the top." React, comparing purely by position, sees something else entirely: child 0's text changed from "Buy milk" to "Call mum", child 1's text changed from "Walk dog" to "Buy milk", and a new child 2 appeared. Three DOM operations instead of one — and, far worse, any state living inside those rows has now shifted up by one.

React needs a way to know that the "Buy milk" row in the new tree is the same row as the "Buy milk" row in the old tree, even though it moved. It can't figure that out on its own; text content is a terrible identifier, and comparing everything to everything is the O(n³) problem we already rejected.

So React asks you. That's what key is.

The mental model

A key is a luggage tag. Bags on a carousel are constantly reordered, and nobody identifies their suitcase by "third one round the bend" — they read the tag. React does the same: within one list of siblings, it matches old children to new children by key, not by position. Then it knows the "Buy milk" row simply moved, so it can move that DOM node instead of rewriting it.

Where the analogy breaks: luggage tags are globally unique; React keys only need to be unique among siblings. Two different lists can both use key "1" with no problem at all.

What actually goes wrong with index keys

The lazy fix everyone reaches for first:

❌ Buggy
{todos.map((todo, index) => (
  <TodoRow key={index} todo={todo} />   // 👈 the warning goes away…
))}

The console warning disappears, so it feels solved. It isn't. key={index} is literally the position, so you've handed React the exact information it already had. You've told it "identify each row by where it sits", which is the thing that breaks.

Let's watch it fail. Each row has a note field the user can type into:

The setup
function TodoRow({ todo, onDelete }) {
  const [note, setNote] = useState('');   // 👈 state lives per row
  return (
    <li>
      {todo.title}
      <input value={note} onChange={e => setNote(e.target.value)} />
      <button onClick={() => onDelete(todo.id)}>delete</button>
    </li>
  );
}

The user types a note next to "Buy milk", then deletes "Buy milk". Here's the frame-by-frame with key={index}:

Walk through React's reasoning, because it's completely logical once you see it. New list has keys 0 and 1. Old list had 0, 1, 2. So React concludes: key 0 still exists → keep that component instance (including its note state), just pass the new todo prop, which now says "Walk dog". Key 1 still exists → same deal. Key 2 is gone → unmount the last row.

React did exactly what you told it. You told it the identity of a row is its position. The user's note was attached to "position 0", not to "Buy milk". So the note stayed at position 0 while a different todo moved in underneath it.

And notice the second cost: React re-rendered both remaining rows with new props and updated their text nodes, when the correct answer was "remove one node, touch nothing else."

✅ Fixed
{todos.map(todo => (
  <TodoRow key={todo.id} todo={todo} />   // 👈 tied to the data, not the slot
))}

Now the key travels with the todo. Delete "Buy milk" and key "t1" vanishes from the list, so React unmounts precisely that row and leaves the other two — and their state, and their DOM nodes — completely untouched.

When is index as a key actually fine?

It's not forbidden. It's fine when the index genuinely is a stable identity, which requires all three of these:

  • The list never reorders, and items are never inserted or removed anywhere except the end.
  • The list isn't filtered or sorted (filtering re-indexes everything).
  • The items have no state, no uncontrolled inputs, and no refs you care about.

A static list of nav links from a hard-coded array? Index is fine. Rendering skeleton placeholders while data loads? Index is fine. Anything user-editable, sortable, filterable, drag-and-droppable, or paginated? Use a real ID.

The pragmatic rule: if the data has an ID, use it. If it genuinely doesn't and the list is dynamic, generate a stable ID once when you create the item (crypto.randomUUID() at creation time) and store it alongside the data — not during render.

Why key={Math.random()} is a disaster

It silences the warning and it is the worst possible thing you can do. Keys are generated during render, so every render produces a completely new set of keys. React matches old keys to new keys, finds zero matches, and concludes that every single item was deleted and a completely different set of items was created.

Consequences: the entire list is destroyed and rebuilt from scratch on every render — maximum DOM work, the exact opposite of what keys are for. All component state in the list is wiped every render. Focus is lost, so a user typing in a list input can't type. Scroll position jumps. Every effect in every row unmounts and re-runs, so you may fire a network request per row per render.

Same applies to key={uuid()} or key={Date.now()} inline. A key must be stable across renders — that's the entire job description.

Wait, what about… duplicate keys?

"What happens if two siblings have the same key?" React logs a warning ("Encountered two children with the same key") and the behaviour becomes unreliable. When matching old children to new, React builds a map from key → child, so a duplicate key overwrites the earlier entry. In practice you get items being dropped, state and DOM nodes attaching to the wrong item, and updates that silently don't apply.

The classic real-world cause is using a non-unique field as a key — key={user.firstName} works right up until you have two people called Sam. Keys only need to be unique among siblings, but within that scope they must be genuinely unique.

Keys as a deliberate remount tool

Here's the flip: everything above describes keys preserving identity. You can also use them to deliberately destroy it.

Common problem — a profile editor where switching users leaves the previous user's draft in the form:

❌ Buggy: stale state when userId changes
<ProfileEditor userId={selectedUserId} />
// same type, same position → React reuses the instance,
// so the internal draft state from the previous user survives
✅ Fixed: a new key means a new component
<ProfileEditor key={selectedUserId} userId={selectedUserId} />
// key changed → React unmounts the old instance entirely
// and mounts a fresh one: state reset, effects re-run

Keys work on a single element, not just lists. Changing the key tells React "this is a different thing now," and it unmounts and remounts. This is the officially recommended way to reset a component's state when a prop changes — much cleaner than a useEffect that watches userId and manually resets five pieces of state.

And it directly answers a favourite interview question: "How do you force a component to reset its state?" Change its key. That's the answer. (The follow-up "why does that work?" is the one that separates people — because a changed key means React can't match it to the old instance, so it treats it as a brand new element at that position and mounts fresh.)

8. What actually causes a re-render

Quick check: which of these makes a component re-render?

  1. Its own state changed.
  2. Its parent re-rendered.
  3. A context it consumes changed value.
  4. Its props changed.
The answer is not what most people say

1, 2, and 3 cause re-renders. 4 does not. Props changing is not a trigger at all.

A common misconception

"A component re-renders when its props change."

Backwards. Think about the mechanics: how would new props even arrive? Props are the argument object passed in by the parent when it builds the element. For a child to receive new props, the parent must have re-rendered to create that element. So the parent re-rendering is the cause; the new props are a consequence.

And the giveaway that it's not about props: when a parent re-renders, React re-renders all its children — including ones whose props are byte-for-byte identical. React doesn't compare props by default. It just walks down the tree.

The correct sentence: "A component re-renders when its own state changes, when its parent re-renders, or when a context it subscribes to changes."

This is exactly what React.memo changes: it wraps a component so React does a shallow prop comparison first and skips the re-render if nothing changed. Note that this makes "props changed" a trigger only because you explicitly opted in — it's not the default.

And remember phase one of this guide: re-rendering all the children is usually cheap, because most of those renders produce identical trees and commit nothing. Don't wrap everything in memo reflexively.

Does changing state always cause a re-render?

No — and this is a lovely follow-up to be ready for.

When you call a setter, React compares the new value to the current one using Object.is (basically ===, with saner handling of NaN and -0). If they're the same, React can bail out and skip re-rendering that subtree.

Bailouts in action
const [count, setCount] = useState(0);
setCount(0);          // → same value, bails out. No re-render.

const [user, setUser] = useState({ name: 'Sam' });
setUser(user);         // → same reference, bails out.
setUser({ name: 'Sam' }); // 👈 NEW object → different reference → RE-RENDERS,
                       //   even though the contents are identical.

That last line is the one that catches people. Object.is compares object references, not contents. Two objects with identical fields are two different objects. This is the root cause of an enormous number of "why is this re-rendering forever?" bugs — usually a useEffect that sets state derived from an object that gets rebuilt on every render.

Two caveats worth knowing, because a sharp interviewer might probe them:

  • React may still render the component once before bailing out, since it sometimes needs to render to be sure nothing else changed. It just won't go deeper or commit anything. So a bailout is "no DOM work and no children re-rendered", not always literally "zero function calls".
  • Bailouts compare against the current state at the time the update is processed, so in a batch of updates the comparison happens per-update, not against the value you saw when you called the setter.

9. Fiber: why React rewrote its reconciler

Everything so far describes what React computes. Fiber is about how and when it computes it. It shipped in React 16 and it's the foundation everything modern sits on.

The problem with the old reconciler

Pre-16, reconciliation was a plain recursive function. Render the root, which calls render on its children, which calls render on their children, all the way down — one deep recursive descent using the JavaScript call stack. Hence the name: the stack reconciler.

Recursion is a lovely fit for trees, but it has one property that turned out to be fatal here: you cannot pause it. Once you're twelve frames deep in a recursive call, there's no way to say "hold this thought, I'll come back in a moment." The call stack is the browser's, not yours. The only way out is to finish.

Combine that with the fact that JavaScript runs on a single thread — the same thread that handles clicks, keystrokes, scrolling, and painting. If reconciling a big tree takes 300ms, then for 300ms the browser cannot paint a frame, cannot process a keypress, cannot respond to anything. The page is frozen.

The classic demo: a search box filtering a list of thousands of items. You type, and each keystroke triggers a render that takes longer than the gap between keystrokes. Characters appear late, in bursts. It feels broken — because the work is uninterruptible, so even though the user has clearly moved on and typed three more letters, React has to finish rendering the results for the stale query first.

The mental model

The stack reconciler is reading a book by putting your finger between pages as you follow footnotes. You go deeper and deeper, and you cannot put the book down — your fingers are the bookmark. If someone knocks at the door, they wait until you're done.

Fiber replaces that with a to-do list on paper, with a bookmark clipped to the current item. Each item says what to do and what to do next. You can stop after any item, deal with the door, and pick up exactly where you left off — or throw the list away and start a new one, if what's at the door matters more.

Where it breaks down: a real to-do list is linear, whereas fibers still describe a tree — the "what's next" pointer just encodes the tree walk explicitly instead of relying on the call stack.

What a fiber is

A fiber is a plain JavaScript object representing one unit of work — roughly one component instance. It holds the component's type, its props, its state and hooks, a pointer to the real DOM node it's associated with, and — crucially — pointers to its neighbours:

  • child — first child
  • sibling — next sibling
  • return — parent (where to go back to when this subtree is done)

Those three pointers turn the tree into a linked list you can walk manually. React holds one variable pointing at the next fiber to process, does a chunk of work, then checks the clock. Still have time in this frame? Process the next fiber. Out of time? Store the pointer, yield to the browser so it can paint and handle input, and continue on the next tick.

That single change — from "recursion on the call stack" to "a linked structure React walks itself" — is what unlocks everything else, because now the render phase can be:

  • Paused mid-tree and resumed later, so the browser gets to paint and stay responsive.
  • Prioritised — an update from a keystroke is urgent; re-rendering a big filtered list can wait. React can work on the urgent one first.
  • Abandoned — if a more important update arrives, React can throw away the half-finished work and start over. This is safe precisely because the render phase is pure and hasn't touched the DOM yet.
  • Reused — a subtree whose props and state didn't change can be cloned rather than re-rendered.

Two trees: current vs. work-in-progress

There's a related idea that makes "abandon the work" possible: React keeps two fiber trees.

The current tree describes what is on screen right now. When an update comes in, React builds a work-in-progress tree — reusing and cloning fibers from the current tree as it goes. Each fiber holds an alternate pointer to its counterpart in the other tree, so React can hop between them cheaply instead of allocating a fresh tree every time.

All the render-phase work happens on the work-in-progress tree. The current tree — the one matching the DOM — is never mutated during render. Then, at commit time, React applies the changes to the DOM and swaps the pointer: work-in-progress becomes current, in one atomic step.

The mental model

It's a theatre with two stages on a turntable. The audience watches one set while crew build the next one out of sight. When it's ready, the turntable spins — one clean transition, no half-built furniture visible. And if the director changes their mind halfway through building, they just clear the back stage; the audience never knew.

This is the same trick as double buffering in graphics: never let anyone see a partially-drawn frame.

What Fiber unlocked

Fiber by itself didn't make anything visibly different in React 16 — it was infrastructure. The payoff came later:

  • Concurrent rendering. React can prepare multiple versions of the UI at once and work on the highest-priority one, without blocking the browser.
  • Transitions (useTransition, startTransition). You mark an update as non-urgent — "re-filter this huge list" — and React keeps the input responsive, interrupting the slow work whenever a keystroke arrives. That's the search-box problem from earlier, fixed.
  • useDeferredValue. Show stale content while the expensive new content renders in the background.
  • Suspense. A component can say "I'm not ready" mid-render, and React can pause that subtree, show a fallback, and resume when data arrives — only possible if a render can be suspended and picked back up.
  • Automatic batching everywhere, and priority lanes so a click beats a background data refresh.
Trap: over-claiming about Fiber

Don't say "Fiber makes React asynchronous" or "Fiber renders on a separate thread." Neither is true. JavaScript is still single-threaded and the commit phase is still fully synchronous and uninterruptible — you never see a half-updated DOM. Fiber makes the render phase interruptible by breaking it into units and yielding between them. Say it that way and you sound like you've actually thought about it.

10. The interview layer

How this gets asked

Rendering is one of the most reliably-asked React topics, because it separates people who've used React from people who understand it. The phrasings you'll hear:

  • "What is the virtual DOM, and why does React use it?"
  • "Walk me through what happens when I call setState."
  • "Why do we need keys in lists? What happens if I leave them out?"
  • "I see key={index} in this PR. Any concerns?"
  • "What's reconciliation?"
  • "What's Fiber and why was it introduced?"
  • "How would you reset a component's state when a prop changes?"

The first three are recall questions with a depth trap hidden in the follow-up. The rest are depth questions from the start.

Model answer: "What is the virtual DOM?"

Say this out loud

"The virtual DOM is a tree of plain JavaScript objects describing what the UI should look like. JSX compiles to createElement calls that produce those objects — they're just descriptions, they don't touch the DOM at all. When state changes, React builds a fresh tree, diffs it against the previous one, and applies only the actual differences to the real DOM. The point isn't that it's faster than the DOM — it can't be, it's strictly extra work on top. The point is it lets me write declarative code, where I describe the UI for the current state, without paying the cost of tearing down and rebuilding the real DOM every time. It's fast enough, and it's much harder to write a stale-UI bug."

Why this lands: you name the mechanism, you actively correct the "faster than the DOM" myth before they can test you on it, and you frame it as a trade-off. That reads as someone who's reasoned about it rather than memorised a blog post.

Model answer: "Why do we need keys?"

Say this out loud

"React normally matches old and new elements by their position in the tree, which works fine for fixed layout but breaks for lists, because position is exactly what changes when you insert, remove, or reorder. A key gives each item a stable identity, so React can tell that an item moved rather than that its contents changed. Without keys — or with index keys — deleting the first item makes React think every subsequent item's content changed, so component state and DOM nodes end up attached to the wrong rows. Focus in an input, a half-typed value, a checked checkbox: all land on the wrong item. Using the item's ID fixes it because the key travels with the data instead of the slot."

Why this lands: you explain the mechanism (position-based matching) rather than reciting "keys help React identify items", and you name a concrete user-visible symptom. Symptoms prove you've actually hit the bug.

Follow-up questions, with answers

"Is the virtual DOM faster than the real DOM?"

No — that comparison doesn't really make sense. The virtual DOM is built on top of the real DOM; every update still ends in real DOM calls, plus the extra cost of building and diffing the object tree. Hand-tuned imperative DOM code will always beat it. What the virtual DOM beats is the naive way of getting declarative UI — regenerating the entire DOM on every change. It's a mechanism for making declarative code practical while keeping DOM writes minimal.

"Why is diffing O(n) and not O(n³)?"

The general minimum-edit tree diff is O(n³), which would be a billion operations for a 1,000-node page. React makes two assumptions to avoid it. One: elements of different types produce different trees, so if the type changed it destroys the whole subtree instead of trying to match anything inside. Two: within a list of siblings, keys tell it which items are the same across renders, so it doesn't have to compare every child to every other child. Both of those mean each node is visited a constant number of times, so it's a single linear pass. The cost is that React sometimes does more DOM work than the theoretical minimum — a fair trade for something that runs on every keystroke.

"Why not use the array index as a key?"

Because the index is the position, so you've given React back the information it already had. If anything is inserted, removed from the middle, sorted, or filtered, the indices shift: the item that was index 1 is now index 0. React matches by key, sees key 0 in both trees, and keeps that component instance while handing it a different item's data. So state, focus, and uncontrolled input values stay behind on the slot while different data moves in underneath. You also lose the performance benefit — React rewrites every row after the change point instead of moving one node.

"OK, when is index as a key actually fine?"

When the index really is a stable identity: the list never reorders, items are only ever appended at the end, it's never sorted or filtered, and the items hold no state, refs, or uncontrolled inputs. Static nav links, or loading skeletons, are fine. My default is still to use a real ID if the data has one — and if it doesn't and the list is dynamic, I generate an ID once when the item is created and store it with the data, rather than during render.

"What happens if two siblings have the same key?"

React warns in the console and behaviour becomes undefined in practice. It builds a key-to-child map when matching, so the duplicate overwrites the earlier entry — you get items disappearing, state attaching to the wrong item, and updates that silently don't apply. Keys only need to be unique among siblings, not globally, but within that list they must be genuinely unique. The usual cause is keying on a non-unique field, like a name.

"Does a re-render always update the DOM?"

No. A render and a commit are two separate phases. Rendering just means React called my component function and collected the elements it returned — no DOM involvement at all. Only if the new tree differs from the old does the commit phase touch the DOM. A component can re-render many times and produce zero DOM operations. That's why "it re-rendered" isn't automatically a performance problem, and why I don't reach for memo until I've measured something.

"Does changing state always cause a re-render?"

No. React compares the new state to the current value with Object.is and can bail out if they're the same. The catch is that Object.is compares references for objects and arrays, so setting a brand new object with identical contents does re-render. That's behind a lot of accidental infinite loops — an effect that sets state from an object rebuilt every render. Worth noting React may still render the component once before bailing out; what it skips is committing and re-rendering the children.

"Why did React build Fiber?"

The old stack reconciler was a recursive function, so once a render started it ran to completion — you can't pause the JavaScript call stack. On a single thread, that means a big render blocks clicks, keystrokes, and painting for as long as it takes. Fiber restructures the tree into linked-list nodes with child/sibling/parent pointers, so React walks the tree itself instead of relying on the call stack. Now it can do a bit of work, check whether it's out of time, yield to the browser, and resume from a stored pointer — or prioritise a more urgent update, or throw the half-finished work away entirely. That's safe because the render phase is pure and hasn't touched the DOM. It's what made concurrent rendering, transitions, and Suspense possible. To be clear though: it doesn't make React multi-threaded, and the commit phase is still synchronous and uninterruptible.

"How do you force a component to reset its state?"

Give it a key that changes — usually the ID of whatever it's showing, like <ProfileEditor key={userId} />. React matches elements by position and key, so a new key means it can't match the old instance: it unmounts the old one and mounts a fresh one, resetting all state and re-running effects. It's much cleaner than a useEffect that watches a prop and manually resets several pieces of state, and it's the approach the React docs recommend.

"Why can't React just compare props to decide what to re-render?"

It could, and that's what memo does — but doing it by default would often be slower. A shallow prop comparison isn't free, and most components take props like inline objects, arrays, and arrow functions that are freshly created on every parent render, so the comparison would fail anyway and you'd pay for it with nothing to show. React's default is "just re-render, it's cheap", and it lets you opt into memoization at the specific places where rendering is genuinely expensive.

"Why must the render phase be pure?"

Because React reserves the right to call a component more than once, or to render it and then throw the result away — that's exactly what interruptible rendering means. If my component body mutates something outside itself or fires a request, that happens an unpredictable number of times. Side effects belong in useEffect or event handlers, which run in or after the commit phase, exactly once per committed update. StrictMode double-invoking components in development is deliberately surfacing impure render logic.

One last thing. Almost every confusing React behaviour you'll hit — surprise state loss, surprise state retention, an input that won't hold focus, a list that forgets what you typed — comes back to a single question: does React think this is the same component instance as last time, or a different one?

It answers that with position and type, and with keys inside lists. That's it. That's the whole model. Once you're asking that question instead of guessing, React stops being magic and becomes something you can reason about — which, conveniently, is exactly what the interviewer is checking for. 🎯
