Testing Frontend: What to Test, and What Not To

Two tests, both useless

I want to start with two real-ish tests, because I think the whole subject clicks faster from failure than from definitions.

Here's the first one. It's testing a login form.

❌ Test A
test('email state updates', () => {
  const wrapper = shallow(<LoginForm />);
  wrapper.find('#input-email').simulate('change', {
    target: { value: 'ada@example.com' },
  });
  expect(wrapper.state('email')).toBe('ada@example.com'); // 👈 hmm
});

This test passes. It will keep passing. And here's the thing that should bother you: the login form could be completely broken — the submit button disabled forever, the password field invisible, the network call pointed at the wrong URL — and this test would still be sitting there, green, telling you everything is fine.

Now the second one.

❌ Test B
test('renders the login form', () => {
  const { container } = render(<LoginForm />);
  expect(container.firstChild).toMatchSnapshot(); // 400 lines of HTML
});

This one has the opposite problem. Someone changes a wrapper <div> to a <section> for accessibility reasons — an improvement, zero behaviour change — and this test goes red. The developer looks at a 400-line diff they cannot possibly review, shrugs, presses u to update the snapshot, and moves on. Which means the next time it catches a real bug, they'll do exactly the same thing.

Test A fails to fail when things break. Test B fails when nothing broke. Those are the only two ways a test can be bad, and pretty much everything in this guide is about staying out of both ditches.

What a test is actually for

Let me give you the sentence that the rest of this guide hangs off. If you remember one thing, remember this one:

A test exists to give you confidence that a change didn't break behaviour a user cares about.

Read it again slowly, because there are four load-bearing words in there.

“Confidence” — a test is not proof. It's evidence. You're buying belief, and belief has a price (writing the test, running it, maintaining it). Every testing decision is really a question of whether the confidence is worth the price.

“A change” — tests are for the future, not the present. You mostly already know your code works right now; you just clicked it. The test's job is to still be watching six months from now when someone who's never met you refactors it.

“Break” — which means a test that goes red when nothing broke is actively lying to you, and a test that stays green when something broke is also lying to you. Both are bugs in the test.

“Behaviour a user cares about” — not the shape of your state object. Not the name of your CSS class. Not whether you used useReducer or useState. What the user can see, click, read, and get.

Here's an analogy I like. Testing is a smoke alarm, not a building inspection. A building inspection proves the whole structure is correct according to code — expensive, exhaustive, done once. A smoke alarm just screams when something's on fire, and you keep it forever. Tests are smoke alarms. Which reframes two things immediately: an alarm that never goes off is worthless (Test A), and an alarm that goes off every time you make toast gets the battery pulled out (Test B). That second one is the more common failure in real codebases, and it's the one interviewers probe hardest.

The analogy isn't perfect — a smoke alarm doesn't help you locate the fire, whereas a good unit test tells you exactly which function is burning. Hold onto that difference; it comes back when we talk about test levels.

In an interview

When someone asks “how do you approach testing?”, the low-signal answer names tools: “I use Jest and React Testing Library, and Playwright for E2E.” Every candidate says that. The high-signal answer starts from purpose: “I try to write tests that fail when a user-visible behaviour breaks and don't fail otherwise — which mostly means testing through the UI the way a user would, and being pretty stingy about testing internals.” Now you're having a conversation instead of reciting a package.json.

The absolute basics skip if you've written a test

I promised to assume nothing, so: what is a test, mechanically?

A test is just a program that runs your program and complains if it sees something it doesn't like. That's it. There's no magic.

the entire concept
function formatPrice(cents) {
  return '$' + (cents / 100).toFixed(2);
}

// the "test":
if (formatPrice(1999) !== '$19.99') {
  throw new Error('formatPrice is broken');
}

A test runner (Jest, Vitest) is a tool that finds all the files ending in .test.js, runs them, catches the errors, and prints a nice report instead of blowing up. An assertion is the “complain if” part, dressed up: expect(formatPrice(1999)).toBe('$19.99'). It throws a descriptive error when the values don't match.

Two more words you need before we go further:

jsdom. Browser code needs a browser — document, window, elements. But spinning up Chrome for every test is slow. jsdom is a fake browser written in JavaScript: it implements the DOM API in memory, with no actual pixels, no layout engine, no rendering. Jest and Vitest run your component tests inside it. This is why a jsdom test can't tell you whether a button is visually covered by a modal — there's no visual. Remember that; it's the seed of the visual regression section later.

Testing Library (usually React Testing Library, RTL). A small library that renders your component into jsdom and then gives you functions to find things the way a user would — by the button's label, by the form field's name, by the visible text. Its whole design philosophy is a single sentence from its author, Kent C. Dodds:

The more your tests resemble the way your software is used, the more confidence they can give you.

That sentence is basically the exam. Almost every “right answer” in a frontend testing interview is a specific application of it.

Unit, integration, E2E — one feature, three tests

The vocabulary everyone uses, plus the tradeoff underneath it.

People throw these three words around as if they were categories in a filing cabinet. They're not. They're three points on a single sliding scale, and the scale is:

Every test you write replaces some real things with fake things. A unit test replaces nearly everything: no real network, no real router, no real child components sometimes. An E2E test replaces almost nothing: real browser, real clicks, real HTTP. The more you fake, the faster and more precise the test — and the further it drifts from the thing your users actually run.

Let's make it concrete with one feature: a login form. Same feature, three tests.

Unit: one thing, alone

A unit test takes one function (or one small component) and checks it in isolation.

unit
// validateCredentials.test.js
test('rejects an email with no @', () => {
  const result = validateCredentials({
    email: 'ada.example.com',
    password: 'hunter2hunter2',
  });
  expect(result.errors.email).toBe('Enter a valid email address');
});

This runs in about a millisecond. If it fails, you know exactly where the bug is — it's in validateCredentials, there's nowhere else it could be. That precision is the real product of a unit test.

But here's the catch, and it's a big one. Units passing individually says almost nothing about whether they work together. validateCredentials can be flawless while the form never calls it, or calls it with { username } instead of { email }, or renders result.error (singular) so the message never appears. Every one of those is a real, user-facing bug, and all your unit tests are green.

That's the classic image: two perfectly-tested drawer units and a wardrobe you can't open. Which is why...

Integration: several units, wired up for real

An integration test uses multiple real pieces together. On the frontend, that almost always means: render a chunk of the component tree, then interact with it like a person would.

✅ integration (the sweet spot)
test('shows an error when the email is malformed', async () => {
  const user = userEvent.setup();
  render(<LoginForm onSuccess={vi.fn()} />);

  await user.type(screen.getByLabelText(/email/i), 'ada.example.com');
  await user.type(screen.getByLabelText(/password/i), 'hunter2hunter2');
  await user.click(screen.getByRole('button', { name: /log in/i }));

  expect(await screen.findByText(/enter a valid email address/i)).toBeVisible();
});

Look at what this test just covered without mentioning any of it: the label is correctly associated with the input (or getByLabelText would have thrown), the button is a real button with an accessible name, the submit handler is wired, validation runs, the error is rendered, and it's rendered somewhere visible. One test, six potential bugs caught, and not one line of it names an internal implementation detail. If you rewrite LoginForm from class component to hooks to a form library, this test doesn't move.

This is why I'd claim — and I'd claim it out loud in an interview — that for frontend work, integration tests give the most confidence per unit of effort. They're one order of magnitude slower than unit tests (tens of milliseconds, not one), which is nothing, and they're two or three orders faster than E2E.

E2E: the real thing

End-to-end tests drive an actual browser. Real Chrome, real URL bar, real network, usually a real (or realistic) backend.

E2E (Playwright)
test('a user can log in and reach the dashboard', async ({ page }) => {
  await page.goto('/login');
  await page.getByLabel('Email').fill('ada@example.com');
  await page.getByLabel('Password').fill('hunter2hunter2');
  await page.getByRole('button', { name: 'Log in' }).click();

  await expect(page.getByRole('heading', { name: 'Your dashboard' })).toBeVisible();
});

This one covers things nothing else can: that the auth cookie is actually set with the right flags, that the redirect happens, that the router config is right, that the bundle even builds, that the backend accepts the payload shape you're sending. Real confidence.

And it costs. It takes seconds instead of milliseconds. It needs a running server and a seeded database. When it fails, the message is “expected heading to be visible, timed out after 5000ms” — which could be a frontend bug, a backend 500, a slow CI machine, a stale test user, or an expired seed script. And it will fail sometimes for none of those reasons, which we'll get to in the flakiness section.

Wait — where's the line between integration and E2E, really?

Genuinely blurry, and you should say so if asked. Is an RTL test that renders your whole <App /> with a memory router and a mocked network layer a “unit” test or an “integration” test? Kent C. Dodds — who wrote RTL — calls most RTL tests integration tests. Plenty of teams file every Jest test under “unit tests” because they run in the unit-test job in CI. Both are defensible.

The useful move in an interview isn't to pick the One True Definition; it's to show you know the definitions are fuzzy and that the fuzziness doesn't matter. What matters is: how much is real, and how much is faked? Say “I'd call it an integration test because it renders several real components together and only fakes the network — but I know teams that'd file it under unit, and I don't think the label changes what it's worth.” That answer sounds like someone who's argued about this on a real team.

So how do you decide?

Here's the heuristic I'd actually give:

Reach for a unit test when the logic is intricate and self-contained. Date-range math, a price/tax/discount calculator, a permissions resolver, a reducer with a dozen action types, a URL-parsing utility. These have many input combinations and no UI. Driving all fifteen edge cases through clicks would be miserable and slow; calling the function fifteen times is a joy.

Reach for an integration test when the risk is in the wiring. Which is most frontend code, honestly. Forms, lists with filters, modals, anything with loading and error states. The bugs here are “the pieces don't fit”, and only a test that assembles the pieces will find them.

Reach for E2E when a failure would be catastrophic and crosses system boundaries. Sign-up, login, checkout, payment. Keep the number small — a handful of critical user journeys, not a mirror of your integration suite.

The big one: implementation details vs behaviour

If you only get five minutes to prepare, spend them here.

Let's go back to Test A from the top of the guide, because I want to name precisely what's wrong with it.

❌ Brittle
expect(wrapper.state('email')).toBe('ada@example.com');

Ask yourself: does a user know or care that there's a piece of state called email? No. Users know that when they type into a box, letters appear in the box, and when they submit, the right thing happens. The existence of a state variable named email is a decision you made this afternoon and might unmake tomorrow.

That's the definition of an implementation detail: something your users can't observe, that you're free to change without changing what the app does.

And this is the diagnostic — the one sentence to have loaded and ready:

If I refactor without changing behaviour, does the test fail? Then the test was testing the wrong thing.

Rename email to emailValue: Test A breaks. Move from useState to useReducer: Test A breaks. Adopt React Hook Form: Test A breaks. The user experience is byte-for-byte identical in all three cases. Every one of those failures is a false alarm — a test screaming at you while you make toast.

The usual suspects

Here's what testing implementation details looks like in the wild. I've written every single one of these, so no judgement.

❌ Four flavours of brittle
// 1. Internal state
expect(wrapper.state('isOpen')).toBe(true);

// 2. Internal method calls
const spy = vi.spyOn(instance, 'handleSubmit');
expect(spy).toHaveBeenCalled();

// 3. CSS class names
expect(container.querySelector('.btn--loading')).not.toBeNull();

// 4. Exact DOM structure
expect(container.firstChild.children[1].tagName).toBe('SPAN');

And here is the same set of intentions, written in terms a user would recognise:

✅ The same four, made resilient
// 1. the menu is actually open — because you can see its items
expect(screen.getByRole('menu')).toBeVisible();

// 2. submitting did the thing the user wanted
expect(await screen.findByText(/order confirmed/i)).toBeVisible();

// 3. the button reports itself as busy — to users AND screen readers
expect(screen.getByRole('button', { name: /pay now/i })).toBeDisabled();
expect(screen.getByText(/processing/i)).toBeVisible();

// 4. the content is there; nobody cares which tag holds it
expect(screen.getByText('$24.99')).toBeVisible();

Notice something about the fixed versions: they read like a description of the feature. If you deleted the code and handed only these assertions to another developer, they could rebuild the behaviour. That's the tell. A good test doubles as a specification; a brittle test doubles as a diff of your last refactor.

A common misconception: “but the state IS the behaviour”

The objection goes: if isOpen is true, the menu is open — same thing, and checking the state is more direct.

It isn't the same thing, and the gap is exactly where bugs live. isOpen can be true while the menu is invisible because you forgot to pass the prop down, or because a CSS class hides it, or because it renders into a portal that isn't mounted, or because an error boundary swallowed it. State is your intention. The rendered output is the result. Tests should check results, because users experience results. Checking the intention is checking your own homework with your own answer key.

Why brittle tests are worse than no tests

This claim sounds like an exaggeration and it isn't, so let me argue it properly.

With no tests, you know you have no safety net. You're careful. You click through the feature manually. You're honest with yourself about the risk.

With brittle tests, three bad things happen in sequence.

First, they punish the good behaviour. A developer starts a clean refactor, and 40 tests go red. Not because they broke anything — because the tests were welded to the old internals. Now the refactor costs three times what it should, and the rational response is to not refactor. Your test suite is now actively preserving bad code.

Second, they train people to update tests without reading them. When red usually means “the test is out of date”, people stop treating red as information. They fix the test to match the new reality reflexively. And the day the test is right and the code is wrong, they'll do the same thing on autopilot. The alarm has been disconnected — not officially, just in everybody's head.

Third, they poison trust in the entire suite. This is the killer. A suite is judged as a whole. Once “the tests are flaky/annoying/always broken” becomes team folklore, nobody looks carefully at any failure, including the ones from your careful, well-written tests. You can't have a partially trusted smoke alarm.

In an interview
Say this out loud

“The main thing I watch for is whether a test is coupled to implementation details. My rule of thumb is: if I refactor the component without changing what the user sees, and the test fails, the test was wrong. So I try not to assert on state, internal function calls, or class names — I query by role and text and assert on what's actually rendered. Brittle tests are worse than no tests in my experience, because they get updated on autopilot and then people stop trusting failures at all.”

Why it lands: it gives a criterion, not a preference. Anyone can say “test behaviour not implementation” — it's a slogan. Giving the refactor test shows you can apply it to a case you've never seen, which is what the interviewer is really checking.

Testing Library's query priority, and why it exists

Okay, so you're sold on “query things the way a user would”. But a user finds a button by looking at it. How does a test do that?

Testing Library answers with a ranked list of ways to find elements. The ranking isn't arbitrary — it's ordered by how close the query is to how a human (or a screen reader) identifies the thing.

Why getByRole sits at the top. A “role” is what an element is in the accessibility tree — the parallel representation of your page that screen readers and other assistive tech consume. A <button> has role button. An <h2> has role heading with level 2. An <input type="text"> has role textbox. And crucially, you can query by role and accessible name: getByRole('button', { name: /log in/i }).

Here's the lovely consequence. If that query passes, you have simultaneously proven that (a) there's a button, (b) it's a real button rather than a clickable <div>, and (c) it has an accessible name that a screen-reader user would hear. You got an accessibility assertion for free, without writing one. If someone later swaps the button for a <div onClick>, your test fails — and it should, because that genuinely broke behaviour for keyboard and screen-reader users.

Under the hood: what's an “accessible name”?

It's the label the accessibility tree computes for an element, using a defined algorithm. Roughly, in order: an aria-labelledby reference, then aria-label, then the element's own text content, then things like alt on images or the associated <label> for form fields. So <button>Log in</button> and <button aria-label="Log in"><SvgArrow /></button> both have the accessible name “Log in”, and both match the same query. That's the right behaviour: to a screen-reader user they are the same button.

Why getByTestId sits at the bottom. A data-testid attribute is invisible to users, so it can't be wrong from their perspective — which means it can't detect anything from their perspective either. A test id survives you removing the label, breaking the accessible name, or replacing the button with a div. Everything still passes. It's not forbidden — it's genuinely the right tool for something with no accessible identity, like a chart container or a specific list row among identical ones. But every test id is a small admission that you couldn't find the thing the way a user would, and that's worth a second's thought each time.

Wait — what about getBy vs queryBy vs findBy?

They differ in two dimensions and it's worth nailing now, because the async section leans on it.

  • getBy* — synchronous. Throws a helpful error if not found. Use for things that should already be on screen.
  • queryBy* — synchronous. Returns null if not found. This is the only one you use to assert absence: expect(screen.queryByText('Error')).not.toBeInTheDocument(). Using getBy there would throw before you ever reach the assertion.
  • findBy* — asynchronous, returns a Promise. Retries for a bit (1 second by default) until the element shows up, then resolves. Use for things that appear after something async finishes.

And each has an *AllBy* sibling (getAllByRole) for when you expect several matches — the singular versions throw if they find more than one, which is a feature, not a bug.

Mocking: the useful kind and the poisonous kind

A mock is a fake version of something real, swapped in during the test. That's the whole idea. But why would you want fakes in a test that's supposed to be realistic? Four honest reasons.

1. It's slow. A real API call takes 200ms, and you have 800 tests.

2. It's nondeterministic. Anything that gives a different answer each run: Date.now(), Math.random(), a live API whose data changes, a timezone. A test that passes in London and fails in Tokyo isn't a test, it's a coin flip.

3. It's hard to steer. You need to check the “payment declined” UI. Are you going to make a real card actually get declined, on every CI run? You need control over the response.

4. You don't own it. Stripe's servers, an analytics SDK, a maps provider. Your test failing because a third party had a bad afternoon is noise, and hitting their API from CI is rude and possibly expensive.

Underneath all four: mock things at the edge of your system that you can't control or can't afford. Which is the seed of the rule that matters.

The rule: mock at the boundary, not inside your own code

Picture your app as a house. The boundaries are the doors and pipes: HTTP requests, localStorage, the system clock, window.location, third-party SDKs. Everything inside — your components, hooks, reducers, utilities — is furniture. Fake the pipes. Don't fake the furniture. Every piece of furniture you replace with a cardboard cut-out is a piece of your own app that stopped being tested.

Let's see the difference, because it's very concrete.

❌ Mocking inside your own code
vi.mock('../api/cart', () => ({
  fetchCart: vi.fn(() => Promise.resolve({ items: [], total: 0 })),
}));

You've now replaced your own api/cart module. Everything it does — building the URL, setting auth headers, parsing the response, mapping snake_case to camelCase, throwing on a 401 — is untested from here on. And notice the subtler trap: your fake returns { items, total }. If the real module returns { items, totalCents }, your test is green and your app is broken. You've encoded your belief about your own code into the test, and then tested against the belief.

✅ Mocking at the network boundary (MSW)
const server = setupServer(
  http.get('/api/cart', () => HttpResponse.json({
    items: [{ id: 'sku-1', name: 'Kettle', price_cents: 2499 }],
  }))
);

beforeAll(() => server.listen());
afterEach(() => server.resetHandlers()); // 👈 stops tests leaking into each other
afterAll(() => server.close());

MSW (Mock Service Worker) intercepts requests at the network layer — the level of “an HTTP request left the app”. So your real api/cart module runs: real URL construction, real headers, real response parsing, real error handling. The only fake thing is the server on the other end, which is precisely the part you don't own.

There's a second, underrated benefit: the same handlers work in the browser during development, in your integration tests, and in Storybook. One definition of “what the backend does”, shared. That's harder to let drift.

Wait — why not just stub global.fetch?

You can, and it's better than mocking your own module. But you end up hand-rolling a bad HTTP server: you have to fake ok, status, json(), headers, and if you forget one, your code hits undefined in a way it never would in production. You also can't easily assert on the request body, and it breaks the moment someone switches to axios or the app starts using XMLHttpRequest somewhere. MSW handles all of it because it works below the client library. If someone asks “why MSW?”, that's the answer: it's the lowest boundary you can fake, so the most of your real code runs.

The vocabulary: fakes, stubs, spies, mocks

People use these interchangeably in conversation, but knowing the distinctions is cheap signal.

TermWhat it isExample
StubReturns a canned answer. Doesn't care how it's called.getUser always returns { name: 'Ada' }
SpyWraps the real thing and records the calls. Behaviour unchanged.vi.spyOn(console, 'warn') to check a deprecation warning fired
MockA fake you assert against — you check it was called, with what, how often.expect(onCheckout).toHaveBeenCalledWith({ id: 'sku-1' })
FakeA real, working implementation — just a simpler one.An in-memory localStorage; SQLite instead of Postgres

The practical takeaway: fakes and stubs are usually safer than mocks, because asserting “this function was called with these arguments” is an assertion about your implementation. It's the brittleness problem wearing a different hat. Assert on outcomes where you can; assert on calls only when the call is the outcome — like “clicking Pay actually called the payment provider with the right amount”, where there's nothing else visible to check.

Fake timers, for anything with a delay

Some things are slow on purpose. A search box that waits 300ms after you stop typing (a debounce) has a real 300ms in it. Multiply by fifty tests and your suite crawls. Worse, real timers plus a busy CI machine equals flakiness.

So you fake the clock. The test runner replaces setTimeout, setInterval, and Date with controllable versions, and you move time yourself.

✅ Testing a debounced search input
test('only searches once after the user stops typing', async () => {
  vi.useFakeTimers();
  const user = userEvent.setup({ advanceTimers: vi.advanceTimersByTime }); // 👈 essential
  const onSearch = vi.fn();
  render(<SearchBox onSearch={onSearch} delay={300} />);

  await user.type(screen.getByRole('searchbox'), 'kettle');
  expect(onSearch).not.toHaveBeenCalled();   // → still quiet mid-typing

  act(() => vi.advanceTimersByTime(300));
  expect(onSearch).toHaveBeenCalledTimes(1);
  expect(onSearch).toHaveBeenCalledWith('kettle');  // → not 'k','ke','ket'...
});

Read what that test asserts, because it's a nice example of testing behaviour rather than mechanism. It never mentions setTimeout, or clearTimeout, or a ref holding a timer id. It says: while you're typing, nothing happens; 300ms after you stop, exactly one search runs with the full query. That's the actual promise a debounce makes. Swap the implementation for lodash's debounce, or a useDeferredValue, and the test still holds.

The advanceTimers option on userEvent.setup is the gotcha that eats an afternoon: userEvent internally uses timers to simulate realistic typing, so with fake timers installed and no wiring, await user.type(...) hangs forever.

The real danger: contract drift

Now the thing that makes over-mocking genuinely dangerous, rather than just a bit lazy.

Every mock is a claim about how something else behaves. Your MSW handler says /api/cart returns { items: [{ price_cents }] }. That was true when you wrote it. Then a backend engineer ships a change: price_cents becomes price, as a decimal string.

Your tests? All green. Every last one. Because they're testing your code against a description of the backend that no longer matches the backend. The app is broken in production and your suite is celebrating. This is contract drift, and it is the single biggest hole in a heavily-mocked frontend test suite.

You can't fix it with more mocking. You fix it with three things, and knowing this makes you sound like someone who's shipped: a few E2E tests that hit a real (staging) backend, so drift fails somewhere; generated types from the API schema, so drift becomes a TypeScript error at build time; or proper contract tests. The last two get their own section later.

In an interview: “when is mocking harmful?”
Say this out loud

“It's harmful when you mock inside your own code, because everything you replaced stops being tested and you end up asserting against your own assumptions. My rule is to mock at the boundary — the network, the clock, third-party SDKs — and let all my own code run for real. The bigger risk is contract drift: my mock says the API returns one shape, the deployed API returns another, and every test passes while production is broken. That's why I want either generated types from the schema or a couple of real E2E tests, so drift fails somewhere before a user finds it.”

Why it lands: most candidates can say “don't over-mock.” Naming contract drift and then naming the specific mitigations shows you've felt the pain, not just read the blog post.

Testing async UI without going insane

Almost every interesting component fetches something. And the moment it does, it stops having one state and starts having at least three.

Here's my strongest opinion in this section: if a component fetches, you owe it two tests — loading → success, and loading → error. Not one. The error path is the one nobody clicks through manually (how do you make the API fail on your laptop?), which means it's the one where error.message is actually error.response.data.message and nobody ever noticed.

The three ways to wait, and when to use which

You cannot assert on data that hasn't arrived yet. So the core skill is expressing “wait for the UI to settle” without hard-coding a delay.

✅ loading → success
test('shows the cart once it loads', async () => {
  render(<CartPage />);

  // 1. the loading state is real UI — assert on it
  expect(screen.getByRole('status', { name: /loading/i })).toBeVisible();

  // 2. findBy* retries until it appears (or times out)
  expect(await screen.findByText('Kettle')).toBeVisible();

  // 3. queryBy* for absence — the spinner should be gone
  expect(screen.queryByRole('status')).not.toBeInTheDocument();
});

Three tools, three jobs:

  • getBy* — “this is on screen now.” No waiting.
  • findBy* — “this will be on screen soon.” Retries until it appears. This is your default for anything post-async.
  • waitFor(cb) — “retry this whole callback until it stops throwing.” Use it when the thing you're waiting on isn't an element appearing — a mock having been called, an element disappearing, a value changing.

A useful bit of trivia that doubles as understanding: findByText(x) is literally waitFor(() => getByText(x)). It's sugar. Prefer it when it fits, because the failure message is much better — it prints the DOM and tells you what it couldn't find, whereas a bare waitFor often just says “timed out”.

❌ The classic flake generator
await new Promise((r) => setTimeout(r, 500)); // "should be enough"
expect(screen.getByText('Kettle')).toBeVisible();

Why is this so bad? Because you've picked a number, and the number is wrong in both directions at the same time. It's too long on your machine — you just added half a second to every test run, forever. And it's too short on the CI box that's running eight jobs in parallel on a shared vCPU, where that render takes 700ms. So the suite is both slower and flakier. Retry-until-true (findBy/waitFor) is faster in the happy case, because it resolves the instant the condition is met, and more reliable in the slow case, because it keeps waiting. There's no scenario where sleep() wins.

act() warnings: what they're actually telling you

Sooner or later you get this in your console:

Warning: An update to CartPage inside a test was not wrapped in act(...)

Most people's response is to sprinkle act() around until it goes away. Let me explain what it means instead, because it's genuinely useful information.

React batches work. When state changes, React doesn't re-render synchronously line-by-line — it schedules, then flushes. act() is React's way of saying “run this, then flush everything — all the re-renders, all the effects — before continuing.” It makes the async internals behave synchronously for the duration of the test, so your next assertion sees a settled UI.

So the warning means: something updated state after your test had already moved on. Usually a fetch resolving after the assertions ran — sometimes after the test finished entirely. And that's a real signal, not noise. It's telling you your test isn't waiting for the thing it should be waiting for. Two consequences: your assertions may be running against a half-settled UI, and state may be updating on an unmounted component, which points at a missing cleanup or cancellation in the component itself.

The fix is almost never to wrap things in act() manually. It's to await the right thing: use findBy*/waitFor so the test doesn't proceed until the update has happened. RTL already wraps render, userEvent, and its async utilities in act for you. If you're reaching for a manual act(), the two legitimate cases are advancing fake timers and calling a hook's returned function directly in a hook test.

Race conditions and cancellation

Here's a bug class that only shows up in async tests, and it's a great thing to bring up unprompted.

User types “ket”, a request fires. They type “kettle”, a second request fires. The first request happens to be slower, so it resolves after the second. Now the screen shows results for “ket” while the box says “kettle”. Classic. It's invisible on a fast connection and infuriating on a slow one.

✅ Testing that stale responses lose
test('ignores a slow response from an older query', async () => {
  server.use(
    http.get('/api/search', async ({ request }) => {
      const q = new URL(request.url).searchParams.get('q');
      if (q === 'ket') await delay(200);   // 👈 the old one is slower
      return HttpResponse.json({ results: [q] });
    })
  );

  await user.type(screen.getByRole('searchbox'), 'kettle');

  expect(await screen.findByText('kettle')).toBeVisible();
  await waitFor(() => expect(screen.queryByText('ket')).not.toBeInTheDocument());
});

Being able to control latency per request is the superpower here, and it's another reason MSW beats a hand-rolled fetch stub. The fix in the component is either an AbortController that cancels the previous request, or a “request id” guard that drops results from anything but the latest query — and this test verifies either one without caring which you chose.

Optimistic updates and rollback

An optimistic update is when you update the UI immediately, before the server confirms, because you're fairly confident it'll succeed — it makes the app feel instant. Click the heart, it fills in right away; the request goes off in the background.

The interesting half is what happens when you were wrong. The request fails, and the UI has to roll back — un-fill the heart, put the item back in the cart, show a message. That rollback path is under-tested almost everywhere, because triggering it by hand means deliberately breaking your own API.

✅ Optimistic update, then rollback
test('restores the item when removal fails', async () => {
  server.use(http.delete('/api/cart/sku-1', () =>
    new HttpResponse(null, { status: 500 })));

  render(<CartPage />);
  await user.click(await screen.findByRole('button', { name: /remove kettle/i }));

  // optimistic: gone immediately, before the server has answered
  expect(screen.queryByText('Kettle')).not.toBeInTheDocument();

  // rollback: it comes back, and the user is told why
  expect(await screen.findByText('Kettle')).toBeVisible();
  expect(await screen.findByRole('alert')).toHaveTextContent(/couldn't remove/i);
});

I love this test because the middle assertion is doing something subtle: it proves the update really was optimistic. If someone “simplifies” the code to wait for the server response, that line fails — correctly, because the snappy feel the feature existed for is gone. The test is guarding a UX property, not a code shape.

Snapshot tests and why everyone ignores them

A snapshot test serialises something to a string, saves it to a file the first time, and on every subsequent run compares against the saved copy. Different? Fail.

the whole idea
test('renders the product card', () => {
  const { container } = render(<ProductCard product={kettle} />);
  expect(container).toMatchSnapshot();
});

The appeal is obvious and, honestly, real: one line, and you've “covered” a component. Coverage number goes up. It takes ten seconds to write.

And then, on most teams, it quietly rots. Four reasons, and they compound.

They're unreviewable at size. A snapshot of a real component is 200–600 lines of serialised DOM. Nobody reads that in a pull request. So the file gets approved unread, which means it has stopped being a check on anything.

They generate noise on every cosmetic change. Change a class name, add a wrapper div, upgrade a design-system component, reorder two attributes — red. None of that is a behaviour change. This is the brittleness problem from earlier, at industrial scale.

“Just press u.” Because failures are usually noise, the reflex becomes jest -u, commit, move on. At that point the snapshot doesn't assert that the output is correct. It asserts that the output is whatever it currently is, which is a tautology. And the one time the diff contains a real bug — a price field that vanished — it goes through with everything else.

They assert on structure, not behaviour. This is the deepest one. A snapshot has no opinion. It can't tell you the button is disabled when it shouldn't be, or that the total is wrong — it only knows the string changed. It's brittle by construction, because it asserts on everything, and most of everything is implementation detail.

A common misconception: “a failing snapshot means something broke”

A failing snapshot means the serialised output changed. That's all. The reviewer has to decide whether the change was intended — and the value of the test is entirely in the quality of that human judgement. A 400-line diff makes good judgement impossible, so a big snapshot is a test whose only working part has been designed out. That's worth saying in an interview: the snapshot doesn't fail; the review fails.

Where they're actually great

I'm not anti-snapshot. I'm anti-huge snapshot. They shine when the output is small, meaningful, and hand-readable:

  • Serialised data and config. The output of a normaliser, a resolved theme object, a generated GraphQL query string, a webpack/vite config, a formatted CSV row. Structure is the behaviour here.
  • Error messages. A validation error object is exactly the kind of thing you want to see change explicitly in a diff.
  • Small focused fragments. Snapshot the rendered price line, not the whole page.

And the format upgrade that fixes most of the problem: inline snapshots.

✅ Inline snapshot — the diff lives where you'll read it
expect(summarise(cart)).toMatchInlineSnapshot(`
  {
    "itemCount": 3,
    "subtotal": "$74.97",
    "shipping": "Free",
  }
`);

The expected value sits in the test file, right next to the code. It shows up in the PR diff where a reviewer is already looking, it's small enough to read, and it's obviously wrong when it's wrong. That's a snapshot doing its job.

Flakiness, a first-class topic

A flaky test is one that passes and fails on the same code. Same commit, same everything — run it five times, get four greens and a red.

People treat flakiness as a nuisance. It isn't. It's a suite-level emergency, for a reason that's worth thinking through: a test suite's entire value comes from the meaning of red. Red must mean “stop, you broke something.” The moment red sometimes means “eh, run it again”, every red in the suite becomes ambiguous — including reds from tests that are perfectly sound. One tolerated flaky test degrades the signal from all of them. It's one drop of ink in the glass of water.

The main causes, roughly in order of how often I've seen them:

Timing. Arbitrary sleep()s, animations that need to finish, debounces, transitions, waiting on a fixed duration instead of a condition. Fix: wait for conditions (findBy/waitFor, Playwright's auto-waiting assertions), and disable animations in the test environment (prefers-reduced-motion, or a global CSS override that zeroes durations).

Shared state between tests. A module-level cache, a localStorage entry, a MSW handler overridden with server.use() and never reset, a mock whose call count carries over. The tell: the test passes alone and fails in the suite. Fix: reset everything in afterEach, and don't let modules hold mutable state across tests.

Test order dependence. Test B only passes because Test A logged a user in. Then someone adds a test, or the runner shuffles order, or parallelises — boom. The diagnostic is delightful: run the suite in random order. If it breaks, you have hidden dependencies. Every test should be able to run alone, first, and in any order.

Real network. Any test that touches a live service inherits that service's uptime, latency, and rate limits. Even a “fast” API occasionally takes 3 seconds.

Real time and locale. Tests that pass except at midnight, or on the last day of the month, or in a timezone west of UTC, or during a DST changeover. Freeze the clock and pin the timezone in CI.

In an interview: “how do you deal with a flaky test?”
Say this out loud

“First I stop it hurting people — quarantine it, so it's not blocking merges, with a ticket attached so it can't be forgotten. Then I try to reproduce it: run it in a loop, run it alone versus in the suite, shuffle the order. That usually tells me if it's timing or shared state. Most of the ones I've fixed came down to waiting on a duration instead of a condition, or state leaking between tests. What I try hard not to do is add a blanket retry, because that hides the flake instead of fixing it — and sometimes the flake is a real race condition in the product that users are also hitting.”

Why it lands: two things. Quarantine-with-a-ticket shows you understand the team dynamics, not just the debugging. And “sometimes the flake is a real bug” is the sentence senior engineers nod at — a race condition that makes a test flaky makes the app flaky too.

“Checkout broke. What would you test before merging?”

This exact prompt gets asked constantly, and it's a trap in a friendly way. The tempting answer is to reel off a list of test cases. But a list is guessable; what the interviewer wants to hear is a method — because a method works on a bug they describe that you've never seen.

Here's the one I'd walk through, in order.

1. Reproduce it in a failing test, before you fix anything

The first test you write should fail, for the same reason the bug exists. This is non-negotiable, and here's why: a test written after the fix has never been observed to fail. You have no evidence it can detect the bug at all. Maybe it passes for an unrelated reason. Writing it first turns red→green into proof that this test catches this bug.

This is a regression test — it exists to make sure this specific bug can never come back silently. It's the highest-value test in the whole exercise, because you know for a fact this failure mode is reachable. Somebody already reached it.

2. Choose the right level for it

Now, where does that test go? Ask where the bug actually lived.

  • Tax computed wrong for a specific region? That's logic — unit test the calculator, and hammer the edge cases while you're in there.
  • The button stayed enabled after submit, so people double-charged? That's wiring — integration test on the checkout form.
  • Redirect after payment lost the session, or the webhook never fired? That's crossing systems — E2E.

Pick the lowest level that can actually catch it. Lower is faster and more precise. But be honest: if the bug was in the seam between two units, no unit test will ever see it, and forcing it down a level gives you a green test and a broken checkout.

3. Then widen, deliberately

With the regression pinned, expand outward in rings:

The happy path. If checkout broke and there was no test for a successful checkout, that's the actual finding. Add it.

The specific failure mode, generalised. The bug was “tax wrong in Quebec.” Test a few other regions too — the bug was probably a pattern, not a single value.

Adjacent states. This is where you show range, and I'd name these explicitly:

  • Empty cart — can you even reach checkout? What does it say?
  • Payment declined — is the error message human, and is the cart still intact so they can retry?
  • Network timeout mid-submit — the scariest one, because the user has no idea whether they were charged. Does the UI say something honest?
  • Double-submit — impatient double-click, or the Enter key twice. Does it place two orders? (An idempotency key belongs here, and mentioning it is a nice signal.)
  • Stale price — item price changed while it sat in the cart.
  • Back button after payment — resubmits? Shows a stale summary?

4. Ask whether a test is even the right fix

This is the step that separates a good answer from a great one. Some bug classes shouldn't be caught by tests at all — they should be made unrepresentable.

If the bug was that someone passed cents where dollars were expected, no number of tests fixes the class of bug. A branded type does:

✅ Make the bug unrepresentable
type Cents = number & { readonly __brand: 'Cents' };
type Dollars = number & { readonly __brand: 'Dollars' };

function chargeCard(amount: Cents) { /* ... */ }

chargeCard(cart.totalDollars); // → compile error. No test needed, ever.

Same with state. If the bug was “the app showed both a spinner and an error at once”, the fix isn't a test asserting that can't happen — it's modelling status as 'idle' | 'loading' | 'success' | 'error' instead of three independent booleans, so the impossible state literally can't be constructed. Or: if the double-submit bug was possible because the handler was re-entrant, the design fix (disable on submit, plus a server-side idempotency key) is worth more than the test.

Tests catch bugs. Types and design prevent whole categories of them. Prefer prevention where you can get it, and use tests for everything that can't be made impossible.

5. Close the loop in CI

Finally — and interviewers love that you got here on your own — what stops this recurring?

  • The regression test runs on every PR, not nightly. A test that runs after merge doesn't prevent merges.
  • The critical-path E2E (add to cart → pay → confirmation) runs pre-merge, even though it's slow. Checkout is worth the two minutes.
  • A smoke test against production/staging after deploy, so if the backend contract shifts you hear it from a robot rather than from support.
  • If the root cause was a type or schema mismatch, wire schema-generated types into the build so drift is a compile error.
  • And the boring one that actually works: put the bug in the PR template as a checkbox for the next person touching checkout.

The pyramid, the trophy, the honeycomb, and coverage

You'll get asked about the test pyramid. It's worth knowing the original argument, and worth knowing why a lot of frontend people have moved off it.

The pyramid's argument (Mike Cohn, mid-2000s) is basically economic: tests at the top are slow, expensive to write, and fragile, so have very few of them; tests at the bottom are cheap and fast, so have loads. Broad base, narrow tip. As a statement about cost, it's still completely correct.

The pushback is that cost isn't the only axis — confidence is the other one, and the pyramid doesn't weigh it. Push it to its logical end on a frontend codebase and you get a suite that's 90% unit tests, hits 95% coverage, and still lets a broken login form through, because every unit passed and the wiring was never exercised. High coverage, low confidence. That's the signature failure of a pyramid-shaped frontend suite, and if you've worked somewhere with one you'll recognise it instantly.

The testing trophy (Kent C. Dodds) rebalances. Static analysis at the base — TypeScript and ESLint catch a surprising slice of real bugs (typos, wrong argument types, unhandled null, unused variables, missing hook dependencies) at zero runtime cost and zero maintenance. Then a modest layer of unit tests for gnarly logic. Then integration as the widest band, because that's where the confidence-per-effort peaks for UI code. Then a thin cap of E2E.

The honeycomb (from Spotify's backend world) makes a similar move for services: fat middle of integration tests, thin unit and end-to-end layers. Different domain, same insight.

Have an opinion

Interviewers ask about shapes to see whether you'll recite one or reason about one. So reason:

Say this out loud

“I think the pyramid's economics are right but its shape is wrong for frontend. Most of our bugs aren't wrong logic inside one function — they're wrong wiring between components, or a mismatch with the API. Unit tests structurally can't see either. So I weight toward integration tests, which for React means rendering a component tree and driving it like a user, with the network mocked at the boundary. Under that I lean hard on TypeScript, which removes a whole class of bugs I'd otherwise be writing tests for. And I keep a handful of E2E tests on the paths where a failure means lost revenue.”

Why it lands: you named the model, named its limitation, and justified your position with the kind of bug your domain actually produces. That last part is what makes it sound earned rather than memorised.

Coverage, and why 100% is a bad goal

Code coverage measures which lines/branches ran while the tests ran. That's genuinely all it measures. It does not check that anything was asserted.

❌ 100% coverage, zero value
test('renders', () => {
  render(<CheckoutPage />);
}); // no assertions. Coverage: through the roof. Bugs caught: none.

Coverage is a lower bound on ignorance, and it's only useful in one direction. If a file is at 0%, you know nothing about it — that's real information. If it's at 95%, you know the lines executed. You don't know whether anything was checked, and you certainly don't know whether the right behaviours were checked.

Why is 100% specifically a bad target? Because the last stretch — roughly 90% to 100% — is where the cost curve goes vertical and the value curve goes flat. That final 10% is defensive branches that can't happen, error handlers for impossible states, generated code, third-party glue. Getting to it means writing contorted tests that mock deep internals just to reach a line, and those are exactly the brittle tests we spent this whole guide trying to avoid. Chasing 100% actively produces bad tests. Worse, it converts coverage from a diagnostic into a target — and once it's a target, people write assertion-free tests to hit it, and now the number means nothing at all.

In an interview: “what's your target code coverage?”

The trap is naming a confident number (“90%!”). It signals you think coverage is the goal.

Say this out loud

“I don't manage to a global number, because coverage measures execution, not verification — you can hit 100% with tests that assert nothing. I do use it as a diagnostic: I look at what's uncovered and ask whether it's risky. Something like 70–80% falls out naturally on a well-tested codebase, and I'd want critical paths like checkout much higher than that. The thing I'd actually push for is a rule that coverage can't drop in a PR, plus a look at what's uncovered in the diff — that catches the untested new code without turning the number into a target people game.”

Why it lands: you refused the number, explained the metric's actual limitation, and then gave a workable policy. Refusing without offering an alternative reads as dodging.

Visual regression testing

Remember jsdom — the fake browser with no rendering? Here's the consequence.

Every test we've written so far can be completely green while the app is visually destroyed. Your submit button can be white text on a white background. Your modal can render behind the page overlay. A CSS change can collapse the layout to zero height. Your dark theme can be unreadable. getByRole('button') finds it every time, toBeVisible() passes (it only checks things like display: none, visibility, and hidden — not whether pixels actually reached the screen), and the test suite reports success.

Visual regression testing closes that gap by taking screenshots in a real browser and diffing them, pixel by pixel, against approved baselines. If pixels changed, a human reviews the diff and either approves it (intended redesign) or rejects it (regression).

So it catches the whole class of things assertions structurally can't see: CSS regressions from a specificity change three files away, layout breaks and text clipping, a theme token that's fine in light mode and invisible in dark, spacing drift after a design-system bump.

Now the honest part, which is what an interviewer is actually listening for. Two costs dominate:

Rendering differs across platforms. Your Mac and the Linux CI container antialias text differently and ship different fonts, so you get thousands of changed pixels on a screenshot where nothing changed. The fix is to always render in one pinned environment — a Docker image or the hosted service's browsers — and never to generate baselines from a laptop.

Dynamic content flags everything. Relative timestamps, random avatars, animations mid-flight. You have to freeze time, seed randomness and disable animations, and that's real work. Add review overhead — a design-system bump can produce 200 changed screenshots, and "approve all" is the snapshot-u problem in a nicer UI.

Names worth having: Chromatic (Storybook team — snapshots your existing stories, so the marginal cost is low if you already have Storybook), Percy, and Playwright's built-in toHaveScreenshot().

The defensible take to offer: visual regression pays for itself on design systems and shared components, where one CSS change fans out to a hundred usages. On feature pages that change every sprint, the noise outweighs the catches. Target it; don't blanket it.

Contract testing

Let's go back to contract drift, because it deserves a proper answer.

The situation: your frontend tests use mocks. Your backend has its own tests, with its own idea of what it returns. Both suites are green. Both teams are happy. And nothing, anywhere, has ever verified that the two agree. The first thing that checks is the deployed app, in front of a user.

Contract testing puts a test in that dashed line. The contract is the agreed shape of the exchange: this endpoint, given this request, returns a response with these fields and these types.

The formal approach: Pact recognise the name, that's enough

In one pass: your frontend writes tests describing what it expects from an endpoint, which produces a pact file — and your own mocks are built from that same file, so they can't drift from it. The pact gets published, and the backend runs its suite against every published pact, replaying those requests against the real service. If a backend change would break your frontend, the backend's build fails, before deploy, with no release coordination.

Consumer-driven is the key word: expectations come from actual consumers, so the provider only guarantees what someone depends on rather than its whole API surface.

The honest downside, and the reason it stays a name for most frontend engineers: Pact is real infrastructure — a broker, CI wiring in two repos, and a backend team who now have a build that can fail because of your file. Great for microservices with many consumers, heavy for one frontend and one backend.

The lightweight approach: generate from the schema

Which is why most frontend teams I'd advise reach for this instead. If the backend publishes an OpenAPI spec or a GraphQL schema, that document is a contract. Point a code generator at it and get TypeScript types out.

✅ Drift becomes a build failure
# in CI, before typecheck:
npx openapi-typescript https://api.example.com/openapi.json -o src/api/schema.d.ts

# then the backend renames price_cents → price:
# src/CartPage.tsx:42 — Property 'price_cents' does not exist on type 'CartItem'.
# → the build fails. Nobody had to write a test. ✅

Regenerate types in CI from the deployed schema, and any drift surfaces as a compile error in whichever build runs next. You get most of the protection for a fraction of the setup. The same trick applies to mocks: tools can generate MSW handlers from an OpenAPI spec, and GraphQL codegen gives you typed operations plus mock data — so your fake responses are structurally guaranteed to match the schema rather than matching your memory of it.

What this doesn't catch is semantic drift: the field is still called status and still typed string, but the backend started sending "PENDING_REVIEW" where it used to send "pending". Types can't see that. Which is the standing argument for keeping a few real E2E tests against staging — the last line of defence when the shape is right and the meaning changed.

The follow-up questions, answered

Click each one to expand. These are the ones that come after your first answer, where the real evaluation happens.

“What would you not test?”

This is one of my favourite questions to be asked, because saying “everything!” is a wrong answer and most people don't realise it. Testing has a cost, and a test that can't fail meaningfully is pure cost.

I wouldn't test: third-party libraries (React's useState works; don't test it), the framework (that a prop passed down arrives), trivial pass-throughs (a component that renders {children}), static markup with no logic or interaction, implementation details generally, exact styling values in jsdom (that's visual regression's job, and asserting margin-top: 8px is testing your stylesheet against itself), and anything the type system already guarantees — writing a test that a function rejects a string when the signature says number is testing TypeScript.

The framing that makes this crisp: “I don't write tests that can only fail if React is broken, or if I've changed code without changing behaviour.”

“How do you decide unit vs integration?”

I ask where the risk lives. If the risk is in logic — many input combinations, tricky rules, pure computation — that's a unit test, because driving twenty cases through the UI is slow and painful and the failure message would be vague. If the risk is in the wiring — does the click reach the handler, does the error render, is the label attached to the input — that's an integration test, because unit tests structurally cannot see seams.

My default for frontend is integration, because most frontend code is glue. I drop to unit when a piece of logic is complex enough to deserve its own exhaustive case list, which usually also means it deserves to be extracted into its own module.

“Why is testing state a bad idea?”

Two reasons, and the second is the interesting one.

First, state is an implementation detail: rename it, restructure it, move to a reducer or a form library, and the test breaks despite identical behaviour. That's a false alarm, and false alarms erode trust in the suite.

Second — and this is the part worth saying — state is your intention; the DOM is the result. The bug is almost always in the gap between them. isOpen: true with the menu invisible is a completely normal bug: the prop wasn't threaded through, a CSS rule hides it, a portal didn't mount, a parent short-circuits the render. Asserting on state checks that you set the variable you meant to set, which you already know. It skips the part that can actually be wrong.

“When is mocking harmful?”

When you mock inside your own code, because everything you replaced stops being tested — and the mock encodes your assumption about that code, so the test can pass while the real module returns a different shape.

It's also harmful when it makes the test unfalsifiable in practice: mock enough and you're testing the mocks. The specific danger to name is contract drift — mocks are frozen claims about a system that keeps moving, so a fully-mocked suite is green by construction. Mitigate with mocks at the boundary (MSW), schema-generated types, and a few real E2E tests.

One more: mocking a component's own children is usually a smell. It's the fastest way to get a test that passes while the composed page is broken.

“Why do snapshot tests get ignored?”

Because they fail constantly for reasons that don't matter, and the diffs are too big to review. Any cosmetic change — a class name, an added wrapper, a library upgrade — turns them red, and the diff is 300 lines of serialised DOM that nobody can meaningfully read in a PR. So the culture becomes “press u and move on”, and at that point the test no longer asserts correctness; it asserts that the output is whatever it currently is.

The root cause is that a snapshot asserts on everything, and most of everything is implementation detail — so it's brittle by construction. I use them where the output is small and meaningful: serialised data, config objects, error messages. And I prefer inline snapshots, because the expected value sits in the test file where a reviewer will actually see it.

“How do you test a component that fetches data?”

I mock at the network boundary with MSW, so my real fetching code, URL building, and response parsing all still run — the only fake thing is the server. Then I test at least two paths: loading → success and loading → error. The error path especially, because that's the one nobody exercises manually.

Mechanically: assert the loading state is visible, then await screen.findByText(...) for the loaded content — findBy* retries until it appears, so I never hard-code a delay. Then assert the spinner is gone with queryBy*, which returns null rather than throwing. If I get an act() warning, I treat it as a signal that I'm not awaiting something I should be, not as noise to silence.

If the component can be raced — a search box, a tab switcher — I'll add a test where an older request resolves after a newer one, to prove stale responses get discarded.

“What's your target code coverage?”

I don't set a global target, because coverage measures which lines executed, not whether anything was verified — a test with zero assertions still counts as coverage. Pushing for 100% makes it worse: the last 10% is unreachable branches and defensive handlers, and reaching them means mocking deep internals, which produces exactly the brittle tests I'm trying to avoid.

What I do use it for is finding blind spots: a 0% file is genuinely informative. In practice something like 70–80% falls out of a well-tested codebase, with critical paths much higher. As policy I'd rather enforce “coverage doesn't drop in a PR” and review coverage on the diff, which catches untested new code without turning the number into a target people game.

“How do you deal with a flaky test?”

Quarantine first so it stops blocking merges, with a ticket so it can't be quietly forgotten — a flaky test left in the suite teaches everyone to ignore red, which devalues every other test.

Then reproduce: run it in a loop, run it alone versus in the full suite, run the suite in random order. Alone-passes/suite-fails points at shared state; random-order-fails points at test order dependence. Most of what I've fixed has been waiting on a duration instead of a condition, unreset mocks or localStorage, or animations that hadn't finished.

What I avoid is a blanket retry policy. Retries hide the symptom, and sometimes the flake is a real race condition — which means users are hitting it too, just less reproducibly.

“How would you test a debounced search input?”

With fake timers, and asserting on the promise the debounce makes rather than on its mechanism. Install fake timers, wire userEvent.setup({ advanceTimers }) so typing doesn't hang, type a query, assert the search callback has not fired, advance the clock past the delay, then assert it fired exactly once with the complete query — not once per keystroke.

Notice what that never mentions: setTimeout, clearTimeout, or a ref holding a timer id. Swap in lodash debounce or a useDeferredValue and the test still passes, which is the point.

If they push further, the good follow-ons are: a trailing keystroke should reset the timer rather than queue a second call; unmounting mid-delay shouldn't fire or warn; and if the search is async, a slow older response must not overwrite a newer one.

“Should you test the implementation of a custom hook?”

Usually not directly. A hook is an implementation detail of the components that use it — nobody ships a hook to a user. My default is to test the component that consumes it, because that covers the hook and the wiring, and it survives me inlining or restructuring the hook later.

The exception is a hook that's a genuine public API: something in a shared package, or one with enough state-machine complexity (usePagination, useUndoRedo) that exercising all its transitions through a component would be absurd. Then I'd test it directly with renderHook — but still through its public surface: call the returned functions, assert on the returned values, never reach into internal refs or the state variable names.

And even then, I'd want at least one integration test of a real component using it, because a hook that's correct in isolation can still be wired up wrong.

“Why not just write E2E tests for everything? They're the most realistic.”

Because realism isn't the only thing you're buying. A full E2E suite is slow enough to stop being run on every PR, which is where tests earn their keep. It's flaky in ways that erode trust. And the failure messages are terrible — “timed out waiting for heading” could be a frontend bug, a backend 500, a bad seed, or a slow runner, so debugging costs are high.

There's also a coverage-shape problem: driving twenty validation edge cases through a real browser is agonising, and you'll quietly stop testing them. I want E2E for a handful of critical journeys where crossing system boundaries is the point, and integration tests for the breadth.

“How do you decide something is worth testing at all?”

I ask two questions: how likely is this to break, and how bad is it if it does? High likelihood usually means complex logic or code that changes often. High impact means revenue, data loss, security, or accessibility.

Anything high on both gets tested thoroughly and runs on every PR. High-impact-but-stable (checkout) still gets solid coverage, because the downside is severe even if the probability is low. Low-impact-and-stable — a marketing page's static markup — I'll leave alone, and I don't feel bad about it.

I'd also mention that “has broken before” is the strongest predictor there is. Bugs cluster. A regression test on a module with a history is worth three speculative tests somewhere quiet.

If you take away one movement from this guide, make it this: every question above is the same question wearing a different costume. Does this test fail when a user-visible behaviour breaks, and stay quiet otherwise? Brittleness, mocking, snapshots, coverage, flakiness, the pyramid — they're all just that question applied to a different corner of the problem.

Which is genuinely good news for an interview, because you don't have to memorise twenty positions. You have to hold one principle and be willing to reason out loud from it. That's what the person across the table is listening for. 🎯
