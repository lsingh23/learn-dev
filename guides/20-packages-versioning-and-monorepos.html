package.json, Lockfiles & Semantic Versioning

A mystery in three acts: the build works on your laptop, the exact same commit fails in CI, and git swears nobody touched a single line of code.

I want to start with a bug report. Not a code bug — a build bug, which is somehow worse, because there's nothing to step through in a debugger.

It's Tuesday. You open a pull request. It's a one-line CSS change. Your local build is green. You push. Twelve minutes later, CI comes back red:

$ npm run build

TypeError: Cannot read properties of undefined (reading 'match')
    at normalizePath (node_modules/some-postcss-plugin/index.js:41:22)

Build failed. Exit code 1.

You stare at it. You run npm run build locally again. Green. You check out your branch on a colleague's machine. Green. You re-run CI. Red. Same commit. Same command. Same Node version, even — you checked.

Someone on the team says the sentence that has been said in every engineering org since the beginning of time: "but it works on my machine." Someone else says the more interesting one: "but nobody changed any code."

And here's the thing — they're both right. Nobody changed any code in your repository. But your application isn't just your repository. Your application is your repository plus roughly 900 packages you didn't write, and one of those 900 packages published a new version at 3am, and your CI machine happily downloaded it while your laptop is still sitting on the old one.

Everything in this guide — every field in package.json, every caret, the entire existence of lockfiles, half of why pnpm exists — is a response to that one problem. Let's solve the mystery properly.

Act oneThe file that records intent, not reality

Let's look at the most boring file in your project.

package.json
{
  "name": "checkout-app",
  "version": "2.4.0",
  "dependencies": {
    "react": "^18.2.0",
    "date-fns": "^2.30.0"
  },
  "devDependencies": {
    "vite": "^5.0.0"
  }
}

Read that "react": "^18.2.0" out loud. Most people read it as "we use React 18.2.0." That is not what it says. It says something much looser, and the looseness is the whole story.

What it actually says is: "give me any version of React that is at least 18.2.0, but still starts with 18." It's not a version. It's a range — a shape of acceptable versions. Today that range resolves to 18.3.1. Next month it might resolve to 18.4.0. You didn't ask for that upgrade, but you did permit it, in writing, with that little ^.

So here's the first mental model I want you to hold, and everything else hangs off it:

The three layers

package.json is your shopping list. "Some milk, a loaf of bread." It describes what you want in general terms.

node_modules is your fridge. It contains actual, specific, physical items — this exact carton, this exact loaf.

package-lock.json is the receipt. It says precisely which carton you got: brand, size, batch number, which shop, and a barcode you can check against.

The list is not the fridge. Two people shopping from the same list on different days come home with different fridges. That's the bug at the top of this page.

What actually happens when you run npm install

Before we go further, let's be really concrete, because a lot of people have never watched this process in their head.

  1. npm reads your package.json and collects your direct dependencies — the ones you asked for by name.
  2. For each one, it asks the registry (by default registry.npmjs.org) "what versions of date-fns exist?" and picks the highest one that satisfies your range.
  3. It downloads that package and opens its package.json — which has its own dependencies, with its own ranges. So it repeats step 2 for those. And for theirs. And theirs.
  4. This continues until nothing new is left. The result is a dependency tree, usually several hundred to a few thousand packages deep, that gets written to disk as node_modules.

Those indirect packages — the ones you never named, that came along because something you named needed them — are called transitive dependencies. In a typical React app they outnumber your direct dependencies by something like 50 to 1.

That diagram contains the entire bug. package.json + node_modules looks like a complete story, but there's a third input in the middle that isn't in your repo, isn't in your git history, and quietly changes every single day.

So: what are those ranges, exactly? What does ^ really permit? Let's do that properly, because interviewers love this and most candidates are fuzzy on it.

Act twoSemantic versioning, and what a caret actually allows

Every version on npm is three numbers separated by dots: 2.30.0. This is semantic versioning, usually shortened to semver, and each number is a promise from the package author to you.

  • PATCH (2.30.4 → 2.30.5): a bug fix. Nothing you were doing should stop working.
  • MINOR (2.30.4 → 2.31.0): new features added, but everything that worked before still works. Additive.
  • MAJOR (2.30.4 → 3.0.0): something you relied on has changed or been removed. Your code may need edits.

A nice way to hold it: the version number is a traffic light for your upgrade risk. Green light for patch, amber for minor ("probably fine, but there's new surface area"), red for major ("stop and read").

The range operators

Now the part that actually shows up in your package.json. When you write a dependency, you're describing a set of acceptable versions.

You writeIt meansWill acceptWon't accept
^1.2.3 ≥ 1.2.3 and < 2.0.0
minor + patch may move		 1.2.4, 1.3.0, 1.99.0 2.0.0, 1.2.2
~1.2.3 ≥ 1.2.3 and < 1.3.0
patch only		 1.2.4, 1.2.99 1.3.0, 2.0.0
1.2.3 exactly 1.2.3 1.2.3 anything else
>=1.2.3 anything newer, forever 1.2.3, 2.0.0, 9.0.0 1.2.2
* or "" literally any version everything nothing 😬
1.2.x same as ~1.2.0 1.2.7 1.3.0

The caret is npm's default — when you run npm install date-fns, npm writes ^2.30.0 into your file, not 2.30.0. That default is a deliberate bet: "trust authors to follow semver, so you passively get bug fixes and security patches without doing anything." Whether that bet is a good one is a genuinely interesting question, and we'll come back to it.

The 0.x special case (a favourite follow-up)

Here's a question worth pausing on. Given "some-lib": "^0.2.3", and the library publishes 0.3.0 — do you get it?

Take a guess before reading on. The naive rule says "caret means the major number is locked, and the major here is 0, so 0.3.0 has the same major and should be allowed."

You don't get it. ^0.2.3 means >=0.2.3 <0.3.0. The caret behaves like a tilde down here.

Why? Because of what 0.x means. Semver says major version zero is for initial development — the API is explicitly unstable, and anything may change at any time. Authors on 0.x have no bigger number to bump when they break something, so in practice the minor position becomes the breaking-change position. 0.2.x → 0.3.0 is the 0.x equivalent of 1.x → 2.0.0.

So the caret quietly shifts one position to the left when the major is zero. Here's the full rule, which is genuinely worth memorising because it makes you sound like someone who has read the spec:

Under the hood — what the caret really does

The caret allows changes that do not modify the left-most non-zero position.

^1.2.3 → left-most non-zero is the major → >=1.2.3 <2.0.0
^0.2.3 → left-most non-zero is the minor → >=0.2.3 <0.3.0
^0.0.3 → left-most non-zero is the patch → >=0.0.3 <0.0.4 (an exact pin, effectively!)

That last one surprises people. On a 0.0.x package, the caret gives you no flexibility at all.

Pre-release tags

Sometimes you'll see a version with a hyphen: 3.0.0-beta.2, 18.3.0-canary.14, 5.0.0-rc.1. That suffix is a pre-release tag, and it does two things.

First, it sorts before the plain release. 3.0.0-beta.2 is less than 3.0.0. Think of the release as the finished cake and the pre-releases as the cake at various points during baking — they come before, not after.

Second — and this is the useful bit — ordinary ranges will never accidentally pick up a pre-release. If you have ^3.0.0 and the author publishes 3.1.0-beta.1, you don't get it. You'd only get a pre-release if your range explicitly opts in, e.g. ^3.1.0-beta.1, and even then only for that same 3.1.0 tuple. This is a safety feature: authors can publish experimental versions to the registry without every consumer's install suddenly changing.

Related, and often confused with pre-release versions: dist-tags. Every package has named pointers to versions. latest is the one you get by default; authors also publish things like next, beta, or canary. When you run npm install react@next, you're saying "whatever version the next label currently points at."

The uncomfortable truth about semver

Everything above describes a rule system. I now need to tell you that the rule system is not enforced by anything.

Semver is not a technical guarantee. There is no bot at npm that diffs your public API and refuses your publish if you removed a function in a minor. Semver is a promise made by a human being, often at 11pm, often about a codebase where "breaking" is genuinely ambiguous. Is tightening a TypeScript type breaking? Is fixing a bug that people were depending on breaking? Is making an error message clearer breaking, if someone was regex-matching it?

In practice, accidental breaking changes in minor and patch releases happen constantly. Not usually from malice — from a maintainer who genuinely believed the change was additive.

A common misconception

"Lockfiles exist because npm can't figure out which versions to install."

No — npm resolves ranges perfectly well. Lockfiles exist because semver is a social contract, not a mechanism. If every author on earth followed semver flawlessly, a caret range would be genuinely safe and lockfiles would be a nice-to-have for install speed. In the world we actually live in, the lockfile is the thing standing between you and someone else's honest mistake.

Which brings us, finally, to the fix.

Act threeThe lockfile: a photograph of the whole tree

When npm finishes resolving your ranges into a concrete tree, it writes down what it found. That file is package-lock.json (yarn calls it yarn.lock, pnpm calls it pnpm-lock.yaml — same idea, different syntax).

Here's one entry from a real lockfile, trimmed:

package-lock.json (one entry of ~900)
"node_modules/date-fns": {
  "version": "2.30.0",                                  // 👈 exact, no range
  "resolved": "https://registry.npmjs.org/date-fns/-/date-fns-2.30.0.tgz",
  "integrity": "sha512-fnULvOpxnC5/Vg3NCiWelDsLiUc9bRwAPs/+LfTLNvetFCtCTN+yQz15C/fs4AwX1R9K5GLtLfn8QW+dWisaAw==",
  "dependencies": { "@babel/runtime": "^7.21.0" },
  "engines": { "node": ">=0.11" }
}

Four things are recorded, and each one is doing real work:

  • version — the exact version. Not a range. A single point.
  • resolved — the exact URL the tarball came from. This matters if you use a private registry or a mirror; it pins where, not just what.
  • integrity — a cryptographic hash (SHA-512) of the tarball's contents. On install, npm downloads the file, hashes it, and compares. If a single byte differs, the install fails loudly.
  • The entry appears for every package in the tree — your direct deps and all ~900 transitive ones. That's the crucial part. Your package.json pins nothing about transitive deps; the lockfile pins all of them.

Wait — why does it store the URL and a hash?

Because they answer different questions. The URL answers "where do I get this?" The hash answers "did I get the thing I expected?"

Think of ordering a specific book. The URL is the shop's address. The integrity hash is you checking the ISBN on the cover when the parcel arrives. If the shop has quietly swapped in a different book — a compromised registry mirror, a man-in-the-middle, a maliciously re-published tarball — the ISBN check catches it, even though the address was right.

Solving the mystery

Let's go back to Tuesday's red build. Here's what actually happened.

Your project depends on a PostCSS plugin, but not directly — it's four levels down, pulled in by something pulled in by your build tool. Its version was declared somewhere as ^4.1.0.

  • Three weeks ago, you ran npm install on your laptop. The best match at that moment was 4.1.6. It went into your node_modules and has been sitting there ever since. You haven't reinstalled — why would you?
  • Last night at 3am, the plugin author published 4.2.0. New feature, no breaking changes intended. But it changed an internal path-normalisation helper to assume a config field is always present. In your setup, it isn't.
  • This morning, CI started from a clean machine with an empty node_modules. It ran npm install. The range ^4.1.0 now best-matches 4.2.0. CI installed a different tree than the one on your laptop.

Same commit. Same command. Different node_modules. Nobody changed any code, and yet the code being executed was different — because most of the code being executed was never in your repo.

That's the whole thing. Once you see it, "works on my machine" stops being a joke and becomes a precise, diagnosable statement: my machine has an older resolution of the tree than yours.

Wait — didn't the lockfile stop this?

Good instinct, and this is the sharp edge. The repo had a lockfile. The problem is that CI ran npm install, and npm install treats the lockfile as a strong suggestion rather than the law — it will happily update it when it thinks it should. There's a different command that treats it as law. Let's look at both.

The fixnpm install vs npm ci

These two commands look interchangeable. They are not, and knowing the difference cold is one of the cheapest interview wins available.

npm install — "make the tree satisfy package.json"

Its job is to get you to a working state, and it's allowed to change things to get there. It will:

  • use the lockfile as a starting point where it can,
  • but re-resolve anything the lockfile doesn't cover or that has drifted from package.json,
  • write back to package-lock.json, and possibly to package.json too (if you passed a package name),
  • install on top of whatever node_modules already exists, patching it up rather than starting clean.

It is a reconciling command. Useful for humans. Non-deterministic by design.

npm ci — "make the tree match the lockfile, exactly"

"ci" stands for clean install (it's also very convenient that it stands for continuous integration). It:

  • deletes node_modules entirely first, so there's no leftover state,
  • installs precisely what the lockfile says — it does no version resolution at all,
  • never writes to package-lock.json or package.json,
  • fails loudly if the lockfile and package.json disagree (e.g. someone hand-edited a version into package.json and forgot to reinstall),
  • refuses to run at all if there's no lockfile.
❌ In CI — reintroduces the drift you were trying to eliminate
- run: npm install
- run: npm test
✅ In CI — reproducible, and it catches lockfile drift for you
- run: npm ci
- run: npm test

That "fails loudly" behaviour is underrated. It turns a whole category of silent inconsistency into a build error, which is exactly where you want it. If a teammate bumps a version in package.json by hand and doesn't regenerate the lockfile, npm ci stops the PR. npm install would quietly paper over it and produce a build that nobody can reproduce.

It's also meaningfully faster, because it skips the entire resolution phase — no round-trips to the registry to ask what versions exist, no dependency-graph solving. It just reads a manifest and downloads.

Under the hood — the equivalents elsewhere

Every package manager has this pair. yarn install --immutable (Yarn Berry) or --frozen-lockfile (Yarn 1) fails if the install would change yarn.lock. pnpm install --frozen-lockfile does the same, and pnpm does this automatically when it detects a CI environment. Same principle everywhere: in CI, the lockfile is read-only input, never output.

Section 5Why lockfiles go in git — and when they don't

The lockfile only helps if everyone has the same one. That means it goes in version control, committed, reviewed, and pushed like any other file. Four reasons, in rough order of how often they come up:

1. Reproducible builds

You, your teammate, CI, and the production build server all produce byte-identical trees. When something breaks in production, you can check out that commit and get exactly the code that was running — not an approximation of it. Without this, "reproduce the bug locally" is a coin flip.

2. Auditability

Because it's in git, a dependency change becomes a reviewable diff. "This PR bumps 40 transitive packages" is now visible information rather than an invisible event. When a build breaks the day after a merge, git log -- package-lock.json tells you what moved. Dependency upgrades become deliberate, dated, attributable actions instead of weather.

3. Security

Those integrity hashes are pinned in the file. If someone compromises a registry mirror or a maintainer account and republishes a tarball with a crypto-miner in it, the hash won't match what's in your lockfile and the install fails. Without a lockfile, you'd just... install it.

4. Speed

Least glamorous, most felt. Skipping resolution makes installs noticeably faster, which compounds across every CI run of every day.

A common misconception

"We should gitignore the lockfile so everyone always gets the latest security patches."

This inverts the goal. You don't get security from drift — you get it from controlled, visible upgrades. Ignoring the lockfile doesn't mean you're always patched; it means nobody knows what's installed anywhere, patched or not. The correct tool for staying current is a bot (Dependabot, Renovate) that opens a PR bumping the lockfile, which CI then tests. That's the same outcome, but observable and revertible.

The nuance: applications vs libraries

This is the follow-up interviewers reach for when they want to see if you've thought about it, or just memorised "always commit the lockfile."

Applications commit their lockfile, and it is authoritative. An app is deployed, not consumed. It's the final node in the graph. Nothing installs your app as a dependency, so your resolution is the resolution. Lock it hard.

Libraries are different — and the key insight is that a published library's lockfile is never used by its consumers. When someone runs npm install your-library, npm reads your library's package.json ranges and folds them into their tree, resolved against their other dependencies. Your lockfile isn't even in the published tarball. It has zero authority downstream.

So should a library repo commit one at all? The honest answer is "yes, but understand what it's for": it pins your own CI and contributor environment, which is useful for reproducible test runs. What it does not do is describe how consumers will experience your package.

Which creates a real risk. If your library only ever tests against one frozen resolution, you'll never notice that your declared range ^2.0.0 is broken against 2.9.0 — because your lockfile keeps you on 2.1.3 forever. Mature libraries handle this with a second CI job that installs without the lockfile (or with dependencies deliberately updated to their range maximums), so they're testing the promise they actually made in package.json.

Wait — can a library force exact versions on consumers?

There's a mechanism called npm-shrinkwrap.json. It's the one lockfile that does get published in your tarball and does bind consumers. It's rare and mostly reserved for CLI tools that people install globally, where you're effectively shipping an application rather than a library. For a normal library it's considered antisocial: you're overriding your consumer's ability to dedupe and patch their own tree.

Lockfile merge conflicts

Two teammates each add a package on their own branch. Both regenerate the lockfile. Both touch thousands of lines. Git throws up its hands.

The instinct is to open the file and start picking sides. Don't. A lockfile isn't source — it's a generated artefact, and it's internally consistent in ways a human editor can't maintain. Hand-merging two halves of a resolved dependency graph produces a file that looks fine, installs something subtly wrong, and now nobody can reproduce anything.

The fix is always: throw the conflicted lockfile away and regenerate it.

✅ Resolving a lockfile conflict
# 1. Take the merge for package.json BY HAND — that one is real source.
#    Make sure both people's new deps survive.

# 2. Throw away the conflicted lockfile and rebuild it from the merged intent.
git checkout --theirs package-lock.json   # or --ours; it doesn't matter
npm install                                # regenerates a coherent tree

# 3. Sanity check, then commit the regenerated file.
git add package-lock.json
npm ci && npm test

Modern npm can even do most of this for you: npm install on a repo with a conflicted package-lock.json will detect the conflict markers and resolve them itself. Yarn Berry and pnpm handle it similarly. The rule to remember is the principle, not the incantation: regenerate, never hand-edit.

The other half of the answer — the part that makes an interviewer nod — is prevention. Add this to .gitattributes:

package-lock.json merge=binary linguist-generated=true

The first flag tells git not to attempt a textual merge (so you get a clean "pick one and regenerate" instead of a scrambled file). The second hides it from PR diffs by default, so reviewers aren't scrolling past 4,000 lines of noise to find the two lines that matter.

Section 6dependencies, devDependencies, peerDependencies

Your package.json can list dependencies in several buckets. People treat this as bookkeeping. It isn't — it changes what gets installed, what gets shipped, and whether your library breaks its consumers.

The practical rule

Ask one question: does the running application need this to execute?

  • dependencies — yes. React, your date library, your state manager. This code ends up in the bundle or runs on the server.
  • devDependencies — no. Vite, TypeScript, ESLint, Jest, Prettier. These build, check, or test your code. Once the build output exists, they're not needed.

Here's the counter-intuitive one that catches people: TypeScript belongs in devDependencies, even though your entire app is written in TypeScript. Why? Because what ships is the compiled JavaScript. The compiler is a tool you used at build time, like a hammer — the hammer doesn't come with the house.

Does the distinction actually matter?

Here's the honest answer, which is more interesting than the textbook one.

For a bundled frontend app: barely, and not for the reason people think. Your bundler decides what's in your bundle by following import statements from your entry point — it does not read the dependencies field. Sticking React in devDependencies won't remove it from your bundle. Being sloppy here costs you almost nothing at runtime.

For a published library: enormously. When someone installs your package, npm installs everything in your dependencies into their node_modules, and nothing from your devDependencies. Put your test framework in the wrong bucket and every consumer downloads Jest. This is where you see packages with a 4 MB install size for 12 KB of actual code.

For Docker images and servers: enormously. Production installs typically run npm ci --omit=dev to keep images small and reduce attack surface. If something the server needs at runtime is in devDependencies, it's simply not there.

The classic gotcha 🔥

A Dockerfile does this:

RUN npm ci --omit=dev
RUN npm run build

and the build dies with sh: vite: not found.

Of course it does — vite is a devDependency, and you just told npm not to install those. The subtlety is that this is correct configuration in the wrong order. You need dev deps to produce the artefact and don't need them to run it. The fix is a multi-stage build: install everything and build in stage one, then copy only the build output plus a production-only install into stage two. Same class of bug bites people on platforms that prune dev dependencies — as long as the prune happens after the build, you're fine; when a platform installs production-only from the start, you're not.

peerDependencies: "don't bring your own, use the host's"

This is the one people flannel through in interviews, so let's build it from the problem up.

You're writing react-fancy-modal. It's a React component library. It obviously needs React — you can't call useState without it. So React goes in dependencies, right?

Let's trace what happens if you do. An app installs your library. The app already has React 18 in its own dependencies. Now npm builds the tree, and if the versions don't match exactly, it can end up with two copies of React on disk — the app's copy at the top level, and your library's copy nested inside node_modules/react-fancy-modal/node_modules/react.

And two copies of React is not a disk-space problem. It's a correctness catastrophe.

Why two copies of React breaks everything

To see why, you need one fact about how hooks work. When you call useState, that function doesn't contain the state logic. It's a thin forwarder that looks up "the currently rendering component's dispatcher" from a mutable variable living inside the react module itself. The renderer (react-dom) sets that variable right before it renders your component, and clears it after.

Now: in Node/bundler module systems, each copy of a package on disk is a separate module instance with its own separate variables. So:

Your modal calls useState, which reaches into Copy B's dispatcher variable, which is null, because react-dom only ever set Copy A's. You get the infamous:

Error: Invalid hook call. Hooks can only be called inside
the body of a function component.

...which is a maddeningly misleading message, because you did call it inside a function component. The React team even lists "you might have more than one copy of React" as one of the three causes, and it's by far the most common one in library land.

The same class of breakage hits Context. createContext() returns a unique object. A Provider created by Copy A and a consumer created by Copy B are looking at two different objects, so the consumer never sees the value and silently falls back to the default. That one doesn't even throw — it just quietly renders the wrong thing, which is worse.

So what's the actual fix?

Declare React as a peer dependency:

✅ react-fancy-modal/package.json
{
  "peerDependencies": {
    "react": "^18.0.0 || ^19.0.0"       // 👈 "the host must provide this"
  },
  "devDependencies": {
    "react": "^18.2.0"                    // 👈 for OUR tests and dev server only
  }
}

A peer dependency says: "I need React to exist in the final application, and I need it to be version 18 or 19, but I am not going to install it — I'll use whichever one the host already has." One copy. One dispatcher. Hooks work.

The analogy

A regular dependency is a contractor who brings their own ladder. A peer dependency is an electrician who says "I'll do the wiring, but the building must already have mains power, and it must be 240V." They don't bring a generator — they'd electrocute someone by running a second, unsynchronised supply through the same walls.

Where it breaks down: the electrician can physically see whether the building has power before starting. Your library can't — it declares its requirement in package.json and trusts the package manager to enforce it. Which is exactly why the enforcement rules below matter so much.

You'll see peer dependencies everywhere once you look: plugin ecosystems (eslint-plugin-* peer-depend on eslint), anything that hooks into a framework's internals (@testing-library/react, styled-components, every React component library), and anything where shared identity matters — a single instance, a single context, a single registry.

--legacy-peer-deps, in one paragraph

You will hit this flag on a real job, so know what it actually does. Up to npm 6, peers weren't installed — you just got a warning that scrolled past. From npm 7 on, peers are auto-installed, and genuinely conflicting peer ranges make the install fail with ERESOLVE.

npm install --legacy-peer-deps

This does not "force the install". It tells npm to ignore peerDependencies entirely — back to npm 6 behaviour. So it's the right call for a stale range (a library declaring "react": "^17" that works fine on 18 because nobody republished it), and the wrong call for a real conflict, where it just stops telling you about the problem. The cleaner fix is overrides in package.json (resolutions in yarn): a committed, reviewable "use this version everywhere" instead of a flag in someone's shell history.

Two footnotes you'll never be asked about, but might see

Optional peers. peerDependenciesMeta: { typescript: { optional: true } } means "if you have it, it must be this version; if you don't, don't nag anyone."

bundledDependencies. Ships those packages' files inside your published tarball instead of fetching them at install time. Essentially vendoring, for air-gapped or unpublished deps. It's about packaging, not resolution.

Section 7npm vs yarn vs pnpm, and the phantom dependency

Three tools that all read package.json and produce node_modules. The differences look cosmetic until you understand what they each do with the shape of that folder — and that shape has consequences you can feel.

Flat hoisting, and the bug it creates

In npm 1 and 2, node_modules was a literal tree. If your app needed express, and express needed debug, you got node_modules/express/node_modules/debug. Simple and correct — but on Windows it blew past the 260-character path limit, and it duplicated the same package dozens of times.

So npm 3 introduced hoisting. Every package, direct or transitive, gets lifted to the top level of node_modules where possible. Only genuine version conflicts get nested.

The phantom dependency

A phantom dependency (sometimes "ghost dependency") is a package you can successfully import even though it appears nowhere in your package.json. It works purely because hoisting parked it at the top of node_modules, and Node's resolver has no idea who asked for it.

Here's the failure, and notice how nasty its shape is:

❌ src/utils/format.js — works today, breaks with no warning later
// I never ran `npm install lodash`. But it's in node_modules,
// because our test runner depends on it. So this works. For now.
import { debounce } from 'lodash';

export const saveDraft = debounce(sendToServer, 500);

Everything is green. Tests pass, CI passes, it ships. Then, six weeks later, the test runner releases a minor version that switched from lodash to lodash-es. Nobody at your company reads that changelog — why would you, it's a test runner. Your lockfile updates, lodash vanishes from the top of node_modules, and your production checkout page dies with Cannot find module 'lodash'.

The reason this is so poisonous: the change that broke you is invisible in the diff of the thing that broke. Nobody touched format.js. You had a real, load-bearing dependency on lodash and never wrote it down, so nothing in your tooling could protect it.

The fix, obviously, is to declare what you use. The problem is that nothing makes you, and in a codebase with a few hundred files, phantom imports accumulate silently. Which is precisely the gap pnpm was built to close.

pnpm: a content-addressable store and a strict layout

pnpm is two separate ideas that people blur together, and you only need a sentence on each.

One: store every file once per machine. npm copies package files into each project. Twelve projects on React 18.3.1 means twelve copies on disk. pnpm keeps one global store keyed by file content hash, and links your project at it with hard links — a second name for the exact same bytes, free to create. So installing something you already have anywhere on the machine means no download and no copy. That's the whole reason "pnpm is faster and smaller"; it isn't a cleverer algorithm, it's just doing far less I/O.

Two: a strict, non-flat node_modules. This is the one that kills phantom dependencies. The top level of node_modules contains only your direct dependencies — exactly what's in your package.json. Everything else lives in a hidden node_modules/.pnpm/, symlinked so each package can reach only what it declared.

This strictness is occasionally painful — some older packages genuinely rely on hoisting and break under pnpm. There are escape hatches (public-hoist-pattern, shamefully-hoist — the name is a good hint about how the maintainers feel). But it's the right default, and the failure mode is loud rather than silent.

Yarn, in brief

Yarn 1 (Classic) mattered enormously in 2016 — it brought lockfiles, deterministic installs and offline caching to an npm that had none of them. npm then copied all of it. Yarn 1 is now maintenance-only, and its layout is flat and hoisted, so it has npm's phantom-dependency problem too.

Yarn Berry (2+) asks a genuinely interesting question: why have a node_modules folder at all? It's a lookup table implemented as a filesystem, resolved by stat()-ing your way up thousands of directories. Plug'n'Play replaces it with one generated map file (.pnp.cjs) pointing at zipped, never-unpacked packages. Installs get near-instant, phantom deps become impossible, and the cache is small enough to commit — "zero installs."

The cost is compatibility: a decade of tooling assumes it can read files out of node_modules with plain fs calls. That friction is why PnP never took over, and why Berry also ships a conventional node-modules linker.

Under the hood — how do you enforce "pick one"?

The packageManager field: "packageManager": "pnpm@9.1.0". Node's Corepack reads it and makes sure the right manager at the right version is used, so a teammate running npm i in a pnpm repo gets stopped rather than generating a rogue package-lock.json. Pair it with engines: { "node": ">=20" } and you've eliminated another chunk of "works on my machine."

Section 8Monorepos, workspaces, and the task graph

A monorepo is one git repository containing several separately-versioned packages — a web app, an admin dashboard, a shared component library, a shared config package. Not one giant application; several distinct units that happen to share a repo and a toolchain.

The problem it solves

Start with the pain of not having one. Your design system lives in its own repo. You need to change a Button prop, which requires updating three apps that consume it. Today:

  1. PR to the design system. Review. Merge.
  2. Publish @acme/ui@3.1.0 to the registry. Wait for CI.
  3. PR to app one bumping the dependency. Discover a problem. Go back to step 1.
  4. Repeat for apps two and three, which are now on three different versions of the design system.

That's days of latency for a one-line change, four PRs that must be reviewed in isolation, and a window where your apps disagree about what a Button is. Monorepos fix this with:

  • Atomic cross-package changes. One PR changes the Button and all three call sites. It's reviewed as one coherent unit, and CI verifies the whole thing together. There's never a moment where the repo is half-migrated.
  • Shared tooling. One ESLint config, one TypeScript config, one CI setup, one Prettier version. Not eight slightly-drifted copies.
  • One version of the truth. Every package uses the same React, the same test runner. You never debug "app A is on React 17 and app B is on 18."
  • Discoverability. One clone, one search. You can find every usage of a component with a single grep.

And the problems it causes

I want to be fair here, because "monorepo good" is a shallow take and interviewers notice.

  • Build and CI times. The naive setup runs every test in the repo on every PR. Change a README, wait 40 minutes. This gets bad fast.
  • Tooling complexity. You now need a task runner, a caching strategy, a versioning/release tool. Your CI config stops being ten lines.
  • Coupling by default. Because importing across packages is trivial, people do — and you can end up with a distributed monolith where nothing can be extracted.
  • Repo weight. Clone times, editor indexing, and git operations all get slower.
  • Ownership blur. Who reviews a PR that touches five packages owned by three teams?

Workspaces: the base primitive

Every serious package manager supports workspaces, and this is the layer everything else builds on. You declare which folders are packages:

root package.json (npm / yarn)
{
  "name": "acme",
  "private": true,               // 👈 stops you publishing the root by accident
  "workspaces": ["apps/*", "packages/*"]
}

(pnpm uses a separate pnpm-workspace.yaml with the same idea.)

Two things change when you do this. First, the app can depend on the local package by name — "@acme/ui": "workspace:*" — and the package manager symlinks the local folder into node_modules instead of downloading from the registry. Edit the library, the app sees it immediately. No publish, no version bump, no npm link pain.

Second, dependencies are installed and deduplicated once at the root, and there's a single lockfile for the entire repo. So the whole guarantee we built up earlier now applies across every package simultaneously — one resolution, one reproducible tree, everywhere.

Workspaces give you linking and installing. What they don't give you is any intelligence about running tasks. That's the next layer.

Turborepo and Nx: the task graph

Here's the problem workspaces leave on the table. You type npm run build at the root. Which order do things build in? The web app imports @acme/ui, so @acme/ui must build first. Nothing in package.json expresses that ordering.

Turborepo and Nx let you declare it, then do something clever with it:

turbo.json
{
  "tasks": {
    "build": {
      "dependsOn": ["^build"],      // 👈 build my deps' `build` first
      "outputs": ["dist/**"]
    },
    "test": { "dependsOn": ["build"] }
  }
}

That ^ means "in my dependencies." So the tool builds a task graph — nodes are (package, task) pairs, edges are ordering constraints — and runs it with maximum parallelism. But ordering isn't the selling point; two things the graph enables are.

Caching

Before running a task, the tool hashes everything that could change its output — source files, resolved dependency versions, task config, declared env vars — and uses that as a cache key. Seen this hash before? Don't run the task; replay the stored output (restore dist/, reprint the log) in milliseconds.

Point that cache at shared storage — remote caching — and it stops being a local nicety. CI builds @acme/ui on your PR; your colleague who didn't touch it gets a cache hit and downloads the result instead of compiling; the production deploy hits it too. The interview framing: a given piece of work is done exactly once across the whole organisation. That's how a 20-minute CI run becomes 90 seconds.

Affected-only execution

The same graph answers the CI-time question: given the files this PR changed, which packages could possibly be impacted? Diff against the base branch, map changed files to packages, walk the graph upward to everything that depends on them, and run tasks for only that set.

This is what makes monorepo CI scale. A change in apps/docs shouldn't test the checkout flow, and with a task graph, it doesn't.

The difference between the two tools, briefly: Turborepo is deliberately minimal — it orchestrates and caches the scripts you already have, and you can adopt it in an afternoon. Nx is a fuller platform: same graph and caching, plus code generators, enforced module boundaries (lint rules that forbid certain packages importing others), and deep framework integrations. Turborepo for "I want fast CI"; Nx for "I want an opinionated platform for a large org."

Wait — what about versioning and publishing?

Separate concern, separate tool. Changesets is the common answer: contributors add a small markdown file describing their change and its semver bump, and a release job aggregates them into version bumps, changelogs, and publishes — including cascading bumps to dependent packages. Lerna used to own this space and still works; Changesets is the more current default for JS libraries.

When a monorepo is NOT worth it

Say this part unprompted and you'll stand out, because it shows you're evaluating rather than following fashion.

  • One app, one team. Then it's not a monorepo, it's a repo. Don't add a task runner to a single Next.js project.
  • Packages that genuinely don't share code. If the only thing your repos have in common is that the same company owns them, you're paying the tooling cost for none of the atomic-change benefit.
  • Genuinely independent release cadences with external consumers. An SDK shipped to third parties on its own schedule often wants its own repo, its own issue tracker, and its own release history.
  • No appetite for build-infrastructure ownership. A monorepo makes build tooling a permanent, staffed responsibility. If nobody will own it, CI times will rot and everyone will blame "the monorepo."
  • Hard access boundaries. If some code must be visible to only a subset of engineers, repo-level permissions are a much simpler answer than path-based access control.

Section 9npm audit and the supply chain

One more thread, and it ties the whole guide together — because supply-chain risk is the reason a lot of these defaults are what they are.

You have ~900 packages in your tree. You chose maybe 15 of them. The other 885 arrived because of transitive resolution, written by people you've never heard of, and their code runs with the same privileges as yours — in your build, on your CI machine (which has deploy credentials), and often in your users' browsers.

What npm audit actually does

It takes the list of exact versions from your lockfile (note the dependency on everything we built earlier — without a lockfile there's no precise list to check), sends it to a service backed by the GitHub Advisory Database, and gets back "these versions of these packages have known reported vulnerabilities." It then reports them by severity and, where a compatible fixed version exists, offers npm audit fix.

It's a genuinely useful hygiene tool. It's also widely misunderstood, and understanding its limits is the more interesting half.

The limits

  • No reachability analysis. It flags a package version, not a code path. A ReDoS vulnerability in an argument parser used only by a build script you run locally gets the same "high severity" badge as an auth bypass in your session library. This produces enormous noise, and noise trains teams to ignore the tool — which is the real damage.
  • Dev dependencies are counted. Much of a typical report is build tooling that never touches production. npm audit --omit=dev gives a far more honest picture of shipped risk.
  • It only knows what's been reported. A malicious package uploaded yesterday isn't in any database. Audit is a rear-view mirror; the highest-impact attacks are, by definition, not in it yet.
  • npm audit fix --force is dangerous. The plain version only applies fixes inside your declared ranges. Add --force and it will happily push through major upgrades to make the report green. You can trade a theoretical vulnerability for a real broken build. Run it, then read the diff.
  • Sometimes there is no fix. A transitive dep four levels down with no patched release. Your options are overrides in package.json to force a patched version, replacing the top-level dependency, or documenting an accepted risk. All three are legitimate; pretending the number is zero isn't.

How supply-chain risk shapes everything else

Three connections worth making, because they reframe decisions from earlier in the guide:

  • The lockfile is a security control, not just a reproducibility one. Integrity hashes mean a tampered tarball fails the install, and pinned transitive versions mean a package compromised at 3am reaches you as a PR someone reviews, not as a silent update.
  • Install scripts are the sharp end. Packages run arbitrary code on postinstall — on your laptop and on CI, which holds deploy credentials. That's how most real npm compromises actually executed. --ignore-scripts shuts it off (some native modules genuinely need them).
  • Fewer dependencies is a real strategy. Every package is a trust relationship with a stranger. "Do we need a library for this?" is a security question, not only a bundle-size one.

A trap to avoid saying

"We run npm audit in CI and fail the build on any vulnerability."

It sounds rigorous, and it's how teams end up with a permanently red pipeline that everyone routes around with --audit-level=none. A better answer: audit runs and reports; the build fails on high and critical in production dependencies; a bot proposes routine upgrades; and someone actually triages the rest on a schedule. Security controls that get bypassed are worse than none, because they also generate false confidence.

Section 10The interview layer

This topic gets asked in two very different registers, and it helps to know which one you're in.

Recall sounds like: "what's the difference between ^ and ~?" There's a right answer and you say it in one sentence.

Depth sounds like: "walk me through what happens when CI installs dependencies," or "a build broke and nobody changed code — how do you debug it?" These are open, and they're really asking: have you operated a real project, or have you only read about one? The tell is whether you naturally reach for the lockfile.

How this gets asked

  • "What's the difference between package.json and package-lock.json?"
  • "Should the lockfile be committed? Why?"
  • "What's the difference between npm install and npm ci?"
  • "Explain semantic versioning. What does ^1.2.3 allow?"
  • "What's a peer dependency? Why does a React component library use one?"
  • "Have you used pnpm? What's the advantage?"
  • "How would you structure a repo with a shared component library and three apps?"

The model answer

Say this out loud — "package.json vs the lockfile"

"package.json records my intent — usually a range like ^18.2.0, meaning any 18.x. The lockfile records the result of resolving all those ranges: the exact version of every package including all the transitive ones, plus where it came from and an integrity hash. That distinction matters because a range resolves against whatever the registry contains at that moment — so without a lockfile, two installs a week apart from identical source can produce different node_modules. That's the classic 'works on my machine but CI broke and nobody changed code' bug. We commit the lockfile so every machine gets the same tree, and CI runs npm ci, which installs the lockfile exactly and fails if it's drifted from package.json, rather than npm install, which will quietly re-resolve and rewrite it."

Why that lands: it never defines a term with the term. It names the mechanism (ranges resolve against a moving registry), attaches it to a failure everyone has lived through, and ends with an operational decision. That arc — mechanism, consequence, decision — is the shape of an answer from someone who has actually shipped software.

Follow-ups, with answers

Why commit the lockfile?

Reproducibility first: everyone and every CI run gets a byte-identical tree, so bugs reproduce and "works on my machine" becomes debuggable. Then auditability — dependency changes become a reviewable diff in git history, so upgrades are deliberate and attributable rather than ambient. Then security: the integrity hashes mean a tampered or republished tarball fails the install instead of being silently used. And it's faster, because there's no resolution step.

What's the actual difference between npm install and npm ci?

npm install reconciles: it makes the tree satisfy package.json, re-resolving where needed, installing on top of existing node_modules, and writing back to the lockfile. npm ci reproduces: it deletes node_modules, installs exactly what the lockfile says with no resolution at all, never writes to package.json or the lockfile, errors if there's no lockfile, and errors if the lockfile and package.json disagree. That last behaviour is the one I care about most in CI — it turns silent drift into a build failure.

What does the caret actually allow?

^1.2.3 means >=1.2.3 <2.0.0 — minor and patch can move, major can't. ~1.2.3 is tighter: >=1.2.3 <1.3.0, patch only. The caret is npm's default when you install something, on the bet that authors follow semver so you passively pick up bug fixes. The precise rule is that the caret allows changes that don't modify the left-most non-zero position, which is what makes the 0.x case behave differently.

Why doesn't ^0.2.0 update to 0.3.0?

Because under semver, major version zero means the API is explicitly unstable — there's no bigger number to bump when you break something, so authors use the minor position for breaking changes. npm honours that: ^0.2.0 resolves to >=0.2.0 <0.3.0, so the caret behaves like a tilde. And it goes one further — ^0.0.3 means >=0.0.3 <0.0.4, effectively an exact pin. The general rule is "don't modify the left-most non-zero position."

When would you pin an exact version?

When a package has burned us before with a bad minor or patch, or is core enough that an unattended upgrade is unacceptable. When we need to hold a specific version temporarily while a regression is investigated upstream. And for tools where the output must be byte-identical across machines — a formatter or a compiler — because a patch bump that reformats everything creates enormous diff noise. I'd add that with a committed lockfile, pinning in package.json is more about signalling intent to teammates and to upgrade bots than about the install itself, since the lockfile already fixes the version. For a published library I'd avoid exact pins, because they stop consumers deduping and force duplicate copies into their tree.

What's a peer dependency, and why does React use one?

It's a declaration that says "I need this package to be present in the final app, at this version range, but I'm not going to install it — I'll use the host's copy." A React component library peer-depends on React because React must be a single shared instance. If the library brought its own, you could end up with two copies of React in the tree, and that breaks in serious ways. Since npm 7, peers are auto-installed and conflicting peer ranges cause an ERESOLVE failure rather than a warning. I'd also put React in my own devDependencies so I can run tests and a dev server locally.

What breaks if there are two copies of React?

Hooks, most visibly. useState doesn't hold the logic itself — it reads a "current dispatcher" variable stored inside the react module. Each copy on disk is a separate module instance with its own copy of that variable, so react-dom wires up copy A while your component reads from copy B, which is null. You get "Invalid hook call," which is confusing because the component looks completely correct. Context breaks too, and more quietly: createContext returns a unique object, so a Provider from one copy and a consumer from the other never match, and the consumer silently falls back to the default value. You can confirm it with npm ls react — if more than one version shows up, that's your answer.

What's a phantom dependency?

A package you can import successfully even though it's not in your package.json. It happens because npm and yarn hoist transitive dependencies to the top level of node_modules, and Node's resolver can't tell the difference between "you asked for this" and "something else did." It works fine until the package that was actually pulling it in changes its own dependencies — then the import disappears and your app breaks, with nothing in your own diff to explain it. pnpm prevents it structurally: only your declared dependencies are at the top level, so an undeclared import fails immediately.

Why is pnpm faster and smaller?

Two things. It keeps one global content-addressable store, indexed by file hash, so a given file exists once per machine — and it hard-links from that store into your project rather than copying, which means installing something you already have anywhere involves no download and no copy. And its node_modules is a symlink structure rather than a flat copy, so building it is cheap. The strictness of that structure is arguably the bigger win: only declared dependencies are at the top level, so phantom dependencies become impossible. The main gotcha is that hard links can't cross filesystems, so if the store is on a different volume — a common Docker setup — it falls back to copying.

How do you resolve a lockfile merge conflict?

Never by hand — it's a generated artefact and hand-merging produces a tree that looks plausible and installs something wrong. I merge package.json manually, since that's real source and I need both people's new dependencies. Then I discard the conflicted lockfile — take either side — and run npm install to regenerate it from the merged intent, then npm ci && npm test to verify before committing. Modern npm can auto-resolve conflict markers for you. I'd also add package-lock.json merge=binary linguist-generated=true to .gitattributes so git doesn't try a text merge and PR diffs stay readable.

Should a library commit a lockfile?

It's worth committing for the library's own CI and contributors, so test runs are reproducible — but it's important to understand it has no authority over consumers. It isn't published in the tarball, and when someone installs the library, npm resolves the library's package.json ranges against their tree. There's a real risk in relying on it: if CI only ever tests one frozen resolution, you never find out that your declared ^2.0.0 range is broken against 2.9.0. So mature libraries add a CI job that installs without the lockfile, to test the promise they actually made. The exception is npm-shrinkwrap.json, which does publish and does bind consumers — reasonable for a global CLI tool, antisocial for a normal library.

Why not just delete node_modules and reinstall whenever something's weird?

It often works, which is exactly the problem — it resolves the symptom without telling you the cause, and the cause is usually one of a few specific things: your local tree is stale relative to the lockfile, or someone hand-edited package.json, or you have duplicate copies of a package with shared state. npm ci is the disciplined version of the same instinct: it's a guaranteed clean install and it fails loudly if the lockfile and package.json disagree, so you learn something. And npm ls <package> tells you if you've got duplicates before you nuke anything.

Why not just put everything in dependencies and stop thinking about it?

For a bundled frontend app you'd mostly get away with it, because the bundler decides what ships by following imports, not by reading the dependencies field. But it breaks in two places that matter. For a published library, everything in dependencies gets installed into every consumer's tree — that's how a 12 KB package ends up costing 4 MB. And for anything deployed as a server or a Docker image, production installs run --omit=dev, so the split is what keeps images small and reduces attack surface. It's also documentation: the split tells the next person what's load-bearing at runtime.

Back to Tuesday

Let's close the loop. Same red build, but now you know what you're looking at.

Your first move isn't to re-run CI — it's git diff on the lockfile, which shows nothing, because CI regenerated it in a container you can't see. So your second move is to notice that CI runs npm install. That's the bug. Not the PostCSS plugin, not the code, not the machine: the pipeline was allowed to resolve fresh versions, so the lockfile you carefully committed was never being honoured.

You change one line in the workflow, npm install → npm ci, and now CI installs precisely the tree your laptop has. Green. Then, separately and deliberately, you open a PR that bumps that plugin to 4.2.0 — and that PR goes red, on its own, in an isolated diff that says exactly what changed and why. Which is the whole point. The upgrade didn't stop being a problem; it stopped being a mystery.

That's really all any of this is. package.json says what you'd accept. The lockfile says what you actually got. npm ci insists that they agree. Everything else — peer dependencies, pnpm's strict layout, a monorepo's task graph — is the same instinct applied at a different altitude: make the invisible thing explicit, so that when it changes, somebody notices.
