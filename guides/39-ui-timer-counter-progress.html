Counter, timer, countdown, progress bar

Four prompts that all have the same shape: something changes because time passed. They're easy to half-build and easy to get wrong in exactly two places — cleanup and stale closures. Here's the build order, and the two bugs.

Counter: the one real lesson

A counter is a flag's simpler cousin — one number, two buttons. You can write it in forty seconds, and the interviewer knows that. They're asking it as a warm-up, or as a trapdoor.

Here's the trapdoor. What do you think this logs when you click once?

❌ Looks fine, isn't
const [count, setCount] = useState(0);

function handleClick() {
  setCount(count + 1);
  setCount(count + 1);   // 👈 surely this makes it 2?
}

It goes to 1. Both calls read the same count — the number 0, baked into this render's handleClick when the function was created. So both calls say "set it to 1", and React obliges, twice.

That's the whole idea, in one sentence: the handler closed over the value from the render it was created in. The fix is to stop reading the variable and ask React for the latest value instead:

✅ Functional updater
setCount(c => c + 1);
setCount(c => c + 1);   // → 2. React feeds each one the result of the last.

The rule, and say it out loud when you write it: if the next value depends on the previous one, use the function form. It costs three characters and it's never wrong.

The double-click case is contrived. The one that actually bites you is next, and it's the reason we're covering the counter at all: an increment inside a setInterval.

❌ Increments once, then stops forever
useEffect(() => {
  const id = setInterval(() => setCount(count + 1), 1000);
  return () => clearInterval(id);
}, []);   // 👈 empty deps: the callback sees count === 0 forever

The effect runs once. The interval callback it created captured count as 0, and nothing ever replaces that callback, so every second it dutifully sets the count to 1. Swap in setCount(c => c + 1) and it just works — no dependency array gymnastics, no re-creating the interval every second.

Stale closures confuse everyone

Genuinely. This trips up people who've shipped React for years, because the mental model "the variable updates" is so much more natural than "each render gets its own frozen copy of every variable." You don't need to internalise the whole thing today. You need the reflex: a value read inside a long-lived callback is probably stale — reach for the function form, or a ref.

Stopwatch: cleanup is what makes pause work

Now the real prompt: start, pause, reset, and a running display. State shape first, as a comment, before any JSX:

// state:
//   elapsed    → number, milliseconds accumulated
//   isRunning  → flag
// derived:
//   display    → format(elapsed)   ← never state
// laps (upgrade) → list of records: [{ id, at }]

Two pieces of state. That's it — and notice isRunning is one of our four shapes (a flag) and elapsed is just a number. The display is derived; storing a formatted string would be storing what you can compute.

✅ Simplest working version
const [elapsed, setElapsed] = useState(0);
const [isRunning, setIsRunning] = useState(false);

useEffect(() => {
  if (!isRunning) return;                      // not running? no interval.
  const id = setInterval(() => setElapsed(e => e + 100), 100);
  return () => clearInterval(id);              // 👈 this line is the pause button
}, [isRunning]);

Say that last part plainly in the interview, because it's the insight: I don't write a pause function. Pausing is just isRunning going false, which re-runs the effect, which runs the cleanup, which clears the interval. The three buttons are now one-liners:

<button onClick={() => setIsRunning(true)}>Start</button>
<button onClick={() => setIsRunning(false)}>Pause</button>
<button onClick={() => { setIsRunning(false); setElapsed(0); }}>Reset</button>

Laps are a free upgrade if you have time: a list of records, setLaps(l => [...l, { id: crypto.randomUUID(), at: elapsed }]), rendered as a list. Same functional-updater rule, same reason.

The drift problem (this is the senior signal)

The version above is wrong, and confidently pointing that out yourself is worth more than anything else in this guide.

setInterval(fn, 100) does not run every 100ms. It runs no sooner than every 100ms — the callback queues behind whatever else is on the main thread, so each tick is a little late, and you're adding a hardcoded 100 for a gap that was actually 104. The error accumulates. Leave it running for five minutes and it's visibly behind the wall clock. And in a background tab, browsers throttle timers to roughly once per second, so a stopwatch that counts +100 per tick runs at about a tenth speed.

The fix is a one-word change to your state shape: store a timestamp, not a count. Keep the moment you pressed start, and compute elapsed from the clock on every tick. The interval stops being the source of truth and becomes a dumb "re-render me now" trigger — which means its inaccuracy no longer matters at all.

✅ Timestamp-based, drift-free
const [elapsed, setElapsed] = useState(0);   // for display only
const startedAt = useRef(0);                 // when this run began
const accumulated = useRef(0);               // ms banked from earlier runs

useEffect(() => {
  if (!isRunning) return;
  startedAt.current = Date.now();
  const id = setInterval(() => {
    setElapsed(accumulated.current + (Date.now() - startedAt.current));
  }, 50);                                    // tick rate ≠ accuracy now
  return () => {
    clearInterval(id);
    accumulated.current += Date.now() - startedAt.current;  // bank it on pause
  };
}, [isRunning]);

Resume works because the cleanup banks the finished run into accumulated, and the next start measures a fresh Date.now() on top of it. Reset zeroes both refs and elapsed. The refs are deliberate: these values change without needing a re-render, and putting them in state would restart the effect every tick.

What they're scoring here

Almost nobody reaches for timestamps unprompted. If you build the naive version first and then say "this drifts, and it'll be worse in a background tab — let me base it on Date.now() instead," you have demonstrated that you know the browser is a real machine with a real event loop. That's the difference between mid and senior on this question.

Countdown: the same machine, inverted

A countdown is the stopwatch with the subtraction flipped and one extra job: stop at zero and tell someone. Same timestamp trick, same cleanup.

// props: durationMs, onComplete
// state: remaining → number (derived from a deadline timestamp)

useEffect(() => {
  if (!isRunning) return;
  const deadline = Date.now() + remainingRef.current;
  const id = setInterval(() => {
    const left = Math.max(0, deadline - Date.now());   // clamp, never negative
    setRemaining(left);
    if (left === 0) { clearInterval(id); setIsRunning(false); onComplete?.(); }
  }, 100);
  return () => clearInterval(id);
}, [isRunning]);

Two things to call out while you type them. Math.max(0, …) because a late tick can overshoot the deadline and you don't want -40ms on screen. And clearInterval(id) inside the callback as well as in the cleanup, so the completion fires exactly once even if the state update hasn't landed yet.

The unmount case

If the component unmounts mid-countdown — user navigates away, parent closes the modal — the effect's cleanup runs and clears the interval, so no callback survives to call setState on a dead component. That's the whole protection, and it's why "always return a cleanup" is non-negotiable rather than tidiness. If you've been told to guard with an isMounted flag: don't. Clean up the thing that would have fired instead.

Formatting is derived, always

Do not put minutes and seconds in state. That's two more things to keep in sync with the one thing that's true.

function format(ms) {
  const total = Math.floor(ms / 1000);
  const mm = String(Math.floor(total / 60)).padStart(2, '0');
  const ss = String(total % 60).padStart(2, '0');
  return `${mm}:${ss}`;
}

If they want centiseconds, add Math.floor((ms % 1000) / 10) padded the same way. Still derived, still one line.

Progress bar: no state at all

The nice surprise: a controlled progress bar holds zero state. It takes value and max, and everything else is arithmetic.

const pct = Math.min(100, Math.max(0, (value / max) * 100));   // clamp both ends

<div className="track" role="progressbar"
     aria-valuenow={value} aria-valuemin={0} aria-valuemax={max}>
  <div className="fill" style={{ transform: `scaleX(${pct / 100})` }} />
</div>

Clamp on both ends and mention why: a parent will eventually pass you 101, or a negative, or a max of 0. Divide-by-zero gives you NaN, which renders as a broken bar rather than an error, so it hides.

Why scaleX and not width? Animating width changes layout, so the browser re-runs layout and paint on every frame. transform is compositor-only — no layout, no paint, it runs on the GPU and stays smooth under load. Set transform-origin: left and add transition: transform 200ms. (The trade: a scaled fill would distort text or a border inside it, so keep the fill a plain block of colour.)

Also worth ten seconds of narration: <progress value max> is a real element that gives you all of this for free, including the indeterminate state when you omit value. It's hard to style consistently, which is why people hand-roll it — but saying "I'd use <progress> if the design allows" is exactly the kind of answer that reads as experienced.

Tying it together

The natural follow-up is "now wire it to the countdown," and it should take you fifteen seconds, because there's nothing to add:

<ProgressBar value={durationMs - remaining} max={durationMs} />

One source of truth (remaining), one derived percentage, no new state. That's the whole method paying off.

Follow-ups

"Why does your timer slow down in a background tab?"

Browsers throttle background timers to save battery — roughly one tick per second, sometimes less. If you count ticks, you lose time. If you compute from Date.now(), the display just updates less often while hidden and is instantly correct when you come back.

"Why setCount(c => c + 1) instead of setCount(count + 1)?"

Because count is the value from the render that created this callback. Inside an interval or two updates in one handler, that value is stale. The function form gets handed the latest value by React, so it's correct regardless of which render it came from.

"How would you make it accurate to the millisecond?"

Drop setInterval and drive the display with requestAnimationFrame — it fires once per repaint, which is the fastest the user can actually perceive, and it pauses in background tabs instead of fighting the throttle. Still read the time from a timestamp: performance.now() - startedAt, which is monotonic and immune to the system clock changing under you.

"Why does your pause work?"

Because isRunning is in the dependency array. Setting it false re-runs the effect, React runs the previous cleanup first, and the cleanup clears the interval. I never wrote a pause function — pause is a state change, and the cleanup does the work.

"How would you test this?"

Fake timers. vi.useFakeTimers() (or Jest's), then act(() => vi.advanceTimersByTime(3000)) and assert the display reads 00:03. If the implementation is timestamp-based, also mock the clock — vi.setSystemTime() — since advancing timers alone doesn't move Date.now(). Then assert the interval is cleared on unmount.

Cheat sheet

  • Next value depends on the previous? Use setX(x => …). Always, but especially inside intervals and timeouts.
  • A value read inside a long-lived callback is probably stale. Function form, or a ref.
  • Stopwatch state: elapsed (number) + isRunning (flag). Two pieces, nothing more.
  • Cleanup is the pause button. if (!isRunning) return plus return () => clearInterval(id), with isRunning in the deps.
  • Never count ticks — subtract timestamps. Date.now() - startedAt, plus accumulated ms for resume.
  • Keep the timestamps in refs, not state — they change without needing a render.
  • Clamp everything: Math.max(0, remaining), pct to 0–100, and guard max === 0.
  • mm:ss is derived. Math.floor(ms / 60000) + padStart(2, '0'). Never state.
  • Progress bar is pure props when controlled. scaleX over width — compositor-only, no layout thrash.
  • A11y: role="progressbar" with aria-valuenow/min/max, or just <progress>. Drop aria-valuenow when indeterminate.
  • Test with fake timers, and mock the system clock too if you're timestamp-based.
