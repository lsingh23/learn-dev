Async lists: useFetch and infinite scroll

"Build a job board that loads from an API." Under the costume, every async list is the same three-part problem: model the request states, avoid the race, then decide how the next page gets asked for. Get those three and the JSX is transcription.

The state shape, which is most of the interview

Guide 34 says step 2 is the whole interview. For an async list that's more true than usual, because the naive shape is so tempting. Here's what nearly everyone types first:

❌ Three booleans that must be kept in sync by hand
const [isLoading, setIsLoading] = useState(false);
const [isError,   setIsError]   = useState(false);
const [jobs,      setJobs]      = useState([]);   // hasData = jobs.length > 0

It works for about four minutes. So let me ask the question that kills it: how many combinations do those three flags have?

Eight. And six of them are nonsense. isLoading && isError — are we loading or did we fail? !isLoading && !isError && !hasData — is that "haven't started" or "finished with zero results"? Different screens, and your state can't tell them apart. So you carry an invisible rulebook about which combinations are real, enforced by remembering setIsError(false) at the top of every retry. Miss one and you get the classic bug: a stale error banner above freshly loaded results. And every render branch becomes a nested ternary that reads like a riddle.

✅ One status string
// state:
//   status → 'idle' | 'loading' | 'success' | 'error'
//   data   → Job[] | null   (only meaningful when status === 'success')
//   error  → Error | null   (only meaningful when status === 'error')
const [status, setStatus] = useState('idle');

Four states instead of eight, and all four are real. Loading-and-errored is now structurally impossible — that's making illegal states unrepresentable, and it's worth saying out loud in exactly those words. There's no syncing, because there's one variable. Transitions are one assignment each.

The related trap: useState([]) as the initial data

An empty array is a lie — it claims "the server said zero jobs" before you've asked. Start at null, and let status be the thing that says whether you've asked.

Now the render is a flat ladder. No nesting, no ternary chains, one branch per real state:

if (status === 'loading') return <JobsSkeleton />;
if (status === 'error')   return <ErrorState onRetry={refetch} message={error.message} />;
if (data.length === 0)    return <Empty text="No jobs match those filters." />;
return <ul>{data.map(j => <JobRow key={j.id} job={j} />)}</ul>;

Read it top to bottom. That readability is the argument — a switch on status works just as well, and either beats any boolean version.

The four states you must render

Loading, error, success — and the one candidates skip, empty. A successful response with zero items is not loading and it is not an error; it's a real screen that needs real words ("No jobs match those filters" plus a way to clear them). Interviewers watch for this specifically, because forgetting it is the tell that you only thought about the happy path. It costs you one line and buys you a disproportionate amount of credit.

Two polish notes worth narrating even if you don't build them:

Skeletons beat spinners for a list: a skeleton says "roughly this much content is coming" and reserves the space, so nothing jumps when data lands.

Don't flash a spinner for a 60ms response. A loader that appears and vanishes inside a couple of frames reads as a glitch. Two standard fixes: delay showing it by ~200ms so fast responses never show one at all, or once shown, keep it up for a 400ms minimum. Mentioning this in an interview is a strong senior signal.

useFetch: the race is the point

Target signature: const {data, error, status, refetch} = useFetch(url). One effect, keyed on url. The interesting part isn't the fetch — it's what happens when url changes while the first request is still in flight.

Type filter "react", then quickly "reactjs". Two requests are in flight; if the first is slow and lands second, you render results for "react" while the input says "reactjs". Silently wrong data, the worst kind. The request needs a way to know it's been superseded.

✅ Version 1: five lines, always correct
useEffect(() => {
  let ignore = false;                         // 👈 this render's request is "current"
  setStatus('loading');
  fetch(url)
    .then(res => { if (!res.ok) throw new Error(res.status); return res.json(); })
    .then(json => { if (!ignore) { setData(json); setStatus('success'); } })
    .catch(err => { if (!ignore) { setError(err);  setStatus('error');   } });
  return () => { ignore = true; };             // cleanup marks it stale
}, [url]);

When url changes, React runs the cleanup for the old effect before the new one, so the old closure's ignore flips to true and its .then becomes a no-op. Each effect run only writes state if it's still the current one. This also fixes "setState after unmount". Write this first: it's short and it always works.

res.ok is doing real work there. fetch only rejects on a network failure — DNS died, connection dropped. A 404 or a 500 is a successful HTTP round trip that happened to carry a sad status code, so the promise resolves happily and you'd render "no results" for what is actually a broken backend. Check res.ok yourself, every time.

✅ Version 2: AbortController, which also stops the network
useEffect(() => {
  const ctrl = new AbortController();
  setStatus('loading');
  fetch(url, { signal: ctrl.signal })
    .then(res => { if (!res.ok) throw new Error(res.status); return res.json(); })
    .then(json => { setData(json); setStatus('success'); })
    .catch(err => {
      if (err.name === 'AbortError') return;   // 👈 not a real error. swallow it.
      setError(err); setStatus('error');
    });
  return () => ctrl.abort();
}, [url]);

ignore discards the answer; abort cancels the question — it frees the connection and stops the browser burning one of its six-per-origin slots on a response nobody wants. The one thing you must not forget is the AbortError guard. Aborting rejects the promise, so without that line every keystroke paints an error banner. That's the bug interviewers wait for.

refetch is a tick counter in the dep array (setTick(t => t + 1)). Retry button done.

Say this, then build it anyway

"In production I'd use React Query or SWR here — caching, dedupe, retries and stale-while- revalidate are solved problems and hand-rolling them is how you get subtle bugs. But I'll write it by hand since that's what we're exercising." One sentence, and it reframes you from "doesn't know the ecosystem" to "chose the exercise." Then write the hook. Guide 16 covers server state properly.

Infinite scroll

Same status machine, three extra fields — and note that items is appended, never replaced:

// state:
//   items   → Job[]    accumulated across pages: [...prev, ...next]
//   page    → number   (or a cursor string from the last response)
//   hasMore → boolean  false once the server runs out
//   status  → 'idle' | 'loading' | 'success' | 'error'   (same machine as above)

The modern answer for "when do I load the next page" is an IntersectionObserver watching a sentinel element under the last row. When the sentinel scrolls into view, the browser tells you. No scroll handler, no throttle, no layout reads.

const io = useRef(null);
const sentinelRef = useCallback(node => {
  if (status === 'loading') return;            // 👈 bug 1 guard: don't double-fire
  io.current?.disconnect();                    // 👈 bug 3 guard: never leak observers
  if (!node) return;
  io.current = new IntersectionObserver(([entry]) => {
    if (entry.isIntersecting && hasMore) setPage(p => p + 1);
  }, { rootMargin: '200px' });                 // prefetch just before it's visible
  io.current.observe(node);
}, [status, hasMore]);

Render <div ref={sentinelRef} /> after the list, and let a useEffect keyed on page do the fetching. A ref callback rather than useRef + effect, because the sentinel unmounts and remounts as the list grows, and the callback re-runs exactly when the node changes.

Name the three bugs out loud — that's most of the marks:

  1. Firing twice for the same page. The sentinel can intersect again before the response lands. Guard on status === 'loading', or an isFetching ref if you need it synchronously.
  2. Never stopping. Without hasMore you happily request page 400 forever. Derive it: setHasMore(batch.length === PAGE_SIZE), or better, take the nextCursor the API gives you and stop when it's null.
  3. Leaking the observer. Disconnect before re-observing and on unmount, or you accumulate one live observer per render.
The old way, worth naming

Before IntersectionObserver you listened to scroll and checked scrollHeight - scrollTop <= clientHeight + threshold, throttled to ~100ms because scroll fires per frame and every check forces a synchronous layout. It works, it's jankier, it's more code. Name it anyway — "the old approach was a throttled scroll handler measuring scrollHeight" — and you've shown you know both.

Cursors beat page numbers

Offset pagination on live data duplicates and drops rows: if a job is inserted at the top between page 1 and page 2, everything shifts down by one and you refetch a row you already have. Cursor/keyset pagination ("give me the 20 after id X") is immune. One sentence, big signal.

Infinite scroll vs "Load more"

Infinite scroll is flashier, but a button is often the better product: keyboard and screen-reader users get an explicit, focusable control instead of content appearing behind them unannounced. And infinite scroll eats the footer — the user can never reach your contact link, which is why Google's results still paginate. The common hybrid: auto-load two or three pages, then switch to a button.

One more boundary to name and then leave alone: at a few thousand rows the problem stops being fetching and becomes rendering, because you now have 5,000 live DOM nodes. The fix is virtualisation — render only the visible window — and it's a genuinely different problem with a different solution.

Follow-ups, with answers

"Why one status string instead of three booleans?"

"Three booleans give eight combinations and only four are legal — loading and error can't both be true, and I can't distinguish 'not started' from 'finished, zero results'. A single status string makes the illegal combinations unrepresentable and turns the render into a flat ladder instead of nested ternaries."

"The user scrolls fast and fires three page loads. What happens?"

"Without a guard, three requests for the same page and duplicate rows. I guard the observer callback on status === 'loading', so only one page is in flight at a time — and I append with a de-dupe by id anyway, since a stale response can still slip through."

"Why AbortController instead of just ignoring the result?"

"The ignore flag fixes correctness — the stale response can't overwrite the new one. Abort fixes correctness and waste: it cancels the request so the connection is freed instead of holding one of the six per-origin slots. Cost is remembering to swallow AbortError, otherwise cancelling looks like failing."

"How do you avoid a spinner flash on a fast response?"

"Delay it. Don't render the loader for the first ~200ms — if the response beats that, the user never sees one. Or, once it's shown, hold it for a 400ms minimum so it doesn't blink."

"Where do you keep scroll position when the user opens a job and comes back?"

"This is the real cost of infinite scroll. You need the loaded items, the page/cursor, and the scroll offset to survive the navigation, so cache them outside the component — a route-level store, or sessionStorage keyed by route. Restore the list first, then set scrollTop, or there's no height to scroll to. React Query gives you this free, which is another reason I'd reach for one."

"Why doesn't fetch throw on a 500?"

"Because the fetch succeeded. The promise reflects the network transaction, not the semantics — a 500 is a response that arrived intact. It only rejects on things like DNS failure, a dropped connection or CORS. So I check res.ok and throw myself. Axios does that for you, which is one reason people prefer it."

Cheat sheet

  • One status string, not three booleans. Eight combinations, six illegal.
  • Initial data is null, not []. An empty array is a claim you haven't earned.
  • Render four states: loading · error (with retry) · empty · success. Empty is the one people forget.
  • Skeleton, not spinner, for lists — and delay it ~200ms so fast responses never flash.
  • Every effect that fetches needs a cleanup. let ignore = false first; AbortController as the upgrade.
  • Swallow AbortError or cancelling renders as failing.
  • fetch doesn't reject on 404/500. Check res.ok and throw.
  • Infinite scroll = append, don't replace, plus hasMore and a cursor.
  • IntersectionObserver on a sentinel, with rootMargin to prefetch; name the old throttled-scroll approach as the fallback.
  • Three bugs to say out loud: double-fire, never stops, observer never disconnected.
  • Mention React Query in one line, then hand-roll it anyway.
