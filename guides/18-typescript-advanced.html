Advanced TypeScript: Mapped Types, Conditional Types & Modelling State

The features that look like black magic right up until somebody shows you the mechanism. Then they look like ordinary code, and you can write them yourself.

You already know the basics. You can write a generic function, you understand that string | number is a union, and you know that an if (typeof x === "string") narrows things down. Good — that's genuinely all you need to start here.

But at some point you open a library's type definitions, or somebody's utils/types.ts, and you see this:

Somebody's real code
type Handlers<T> = {
  [K in keyof T as `on${Capitalize<string & K>}Change`]: (value: T[K]) => void
};

And you close the file. I did too, for about two years! It looks like line noise. It looks like the sort of thing you either "get" or don't.

Here's the good news, and it's the whole reason this guide exists: that snippet is built from exactly four small ideas, each of which is boring on its own. We're going to learn all four, one at a time, and then that line will read as plainly as a for loop. By the end you'll be able to build Partial, Readonly, Pick, ReturnType and Awaited from scratch — which, as a bonus, is one of the most common senior TypeScript interview questions there is.

1. Two things you need first

Everything in this guide is built on two tiny operators. If you already know them, skim — but don't skip, because I want us using the same words for things.

keyof gives you the keys, as a union

Given an object type, keyof hands you back a union of its property names as string literal types:

keyof
type User = {
  name: string;
  age: number;
  isAdmin: boolean;
};

type UserKey = keyof User;
// → "name" | "age" | "isAdmin"

Not string. Not an array. A union of three specific string literal types. That distinction matters constantly, so let me make it concrete: const k: UserKey = "nmae" is a compile error, because "nmae" isn't one of the three.

Indexed access gives you the type at a key

Once you have a key, you can look up what type lives there. The syntax is the same square brackets you'd use at runtime, except it's happening in type-land:

Indexed access
type Name = User["name"];   // → string
type Age  = User["age"];    // → number

type Anything = User[keyof User];
// → string | number | boolean   👈 pass a union, get a union back

That last line is the one people miss. If you index with a union of keys, you get a union of the value types. TypeScript is doing the lookup once per member of the union and gluing the results together with |. Hold onto that idea — "operations on unions happen once per member" is going to come back in a big way later.

That's it. That's the whole prerequisite. keyof T gives you keys; T[K] gives you the type at a key. Everything else is built out of these.

2. Mapped types

The problem, first

Say we've got that User type, and somewhere in the app we need a version of it where nothing can be reassigned — a frozen user we hand to a rendering function that has no business mutating it.

The obvious move is to just... write it out:

❌ The version that rots
type ReadonlyUser = {
  readonly name: string;
  readonly age: number;
  readonly isAdmin: boolean;
};

This works! Today. Then next Tuesday somebody adds email: string to User, doesn't know ReadonlyUser exists, and now you have two types that claim to describe the same thing and disagree. TypeScript will not warn you — as far as it's concerned these are two unrelated types that happen to look similar.

What we actually want to say is: "same shape as User, but every field is readonly." A rule, not a copy. A transformation.

The mechanism

Here's the syntax, and then I'll take it apart:

✅ A rule, not a copy
type ReadonlyUser = {
  readonly [K in keyof User]: User[K]
};

Read [K in keyof User] out loud as: "for each key K in keyof User..." It's a for...of loop, except it runs at compile time and it builds a type instead of a value.

On each pass through the loop, K is bound to one key. The thing after the colon is what that key's type should be — and since we want to keep the original type, we write User[K], which is the indexed access we just learned. Slap readonly on the front and every generated property gets it.

A mapped type is a photocopier with a filter on the glass. The original document goes in, each line comes out, but every line passes through the same little transformation on the way. Where the analogy breaks: a photocopier can't add or remove pages, and a mapped type absolutely can rename or drop keys — we'll get there in a minute.

Now make it generic, and you've written Readonly

Hardcoding User in there is silly. Swap it for a type parameter:

✅ You just wrote a built-in utility type
type MyReadonly<T> = {
  readonly [K in keyof T]: T[K]
};

type Frozen = MyReadonly<User>;
// → { readonly name: string; readonly age: number; readonly isAdmin: boolean }

That is, character for character, how Readonly<T> is defined in TypeScript's own lib.es5.d.ts. Not a compiler intrinsic. Not special-cased. Just a mapped type somebody wrote, sitting in a .d.ts file you could open right now.

I want to dwell on this because it's the mental unlock of the entire guide: the utility types are not magic. They're library code. You can read them, and you can write them.

Partial, in one line

Same shape, different modifier. Instead of readonly, we want ?, which goes after the key:

✅ Partial from scratch
type MyPartial<T> = {
  [K in keyof T]?: T[K]
};

type Draft = MyPartial<User>;
// → { name?: string; age?: number; isAdmin?: boolean }
🎤 In an interview: "How would you implement Partial yourself?"

This gets asked a lot, because it's a perfect one-line test of whether you understand mapped types or just memorised a list of utility names. Write the three lines above, then say the sentence that proves you get it:

Say this

"type Partial<T> = { [K in keyof T]?: T[K] }. It's a mapped type — keyof T gives me a union of the keys, K in loops over that union, and for each key I emit the same key with the same value type, plus a question mark to make it optional. That's genuinely the whole definition in lib.es5.d.ts; the built-in utility types aren't compiler magic, they're just mapped types."

Why it lands: the phrase "they're just mapped types" signals you've actually read the lib files rather than treated the type system as a black box. That's the difference between a mid and a senior answer.

Pick and Record — the loop doesn't have to be over keyof T

Here's the part people don't expect. The thing on the right of in just has to be a union of keys. It usually comes from keyof T, but it doesn't have to:

✅ Pick from scratch
type MyPick<T, K extends keyof T> = {
  [P in K]: T[P]
};

type Preview = MyPick<User, "name" | "age">;
// → { name: string; age: number }

We loop over K — the caller's chosen subset — and look each one up in T. The K extends keyof T constraint is what stops someone passing "emial" and getting a type full of never.

And Record is the same trick with the value type held constant:

✅ Record from scratch
type MyRecord<K extends string | number | symbol, V> = {
  [P in K]: V
};

type Flags = MyRecord<"dark" | "beta", boolean>;
// → { dark: boolean; beta: boolean }

Adding and removing modifiers with + and -

So we can add readonly and ?. Can we take them away? Yes — prefix the modifier with a minus sign:

✅ Required and Mutable
type MyRequired<T> = {
  [K in keyof T]-?: T[K]      // 👈 strip the optionality
};

type Mutable<T> = {
  -readonly [K in keyof T]: T[K]   // 👈 strip the readonly
};

type Complete = MyRequired<Draft>;
// → { name: string; age: number; isAdmin: boolean }

+readonly and +? also exist, and mean exactly the same thing as writing readonly and ? with no sign. They're there for symmetry and for when you want to be loud about intent. You'll almost never write them.

Mutable is a genuinely useful one that isn't built in, which is a nice thing to know — it's the escape hatch for when a library hands you a deeply readonly config and you need a working copy.

Wait — why did MyReadonly<User> keep the ? on optional fields?

Good catch, and this is a real rule with a real name. When a mapped type has the exact shape { [K in keyof T]: ... } — looping directly over keyof T where T is a bare type parameter — TypeScript calls it homomorphic, and treats it specially: existing readonly and ? modifiers are carried through, and if you hand it an array or tuple you get an array or tuple back rather than a weird object with numeric keys.

Compare with MyPick, which loops over K rather than keyof T... except Pick is also treated as homomorphic because K is constrained to keyof T. The rule is fiddlier than it looks. You don't need to recite it; you just need to know the word exists so that when Readonly<string[]> gives you readonly string[] instead of nonsense, you know why.

A realistic one: making a form's fields nullable

Enough toy examples. Here's the shape of a thing you'll actually write. A form's submitted values are fully populated, but a form's in-progress values have empty fields, and in our API layer "empty" means null:

✅ One rule, applied to every field
type Nullable<T> = {
  [K in keyof T]: T[K] | null
};

type SignupForm = { email: string; age: number; referrer: string };

type FormDraft = Nullable<SignupForm>;
// → { email: string | null; age: number | null; referrer: string | null }

Three fields today, eleven fields next quarter, and FormDraft stays correct without anyone touching it. That's the whole payoff of mapped types: you write the relationship down once, and it can't drift.

3. Key remapping with as

Right. So far we've been changing the values and leaving the keys alone. But remember I said a mapped type can rename keys, unlike a photocopier?

Since TypeScript 4.1 you can put an as clause in the loop header, and whatever you write there becomes the key:

The syntax
type Renamed<T> = {
  [K in keyof T as NewKeyGoesHere]: T[K]
};

To do anything interesting with that we need one more small feature — and it's small, I promise.

Template literal types

You know template literals at runtime: ` hello ${name} `. TypeScript has the same thing in type-land. Backticks, ${}, but the things inside the holes are types:

Template literal types
type Greeting = `hello ${string}`;
const a: Greeting = "hello world";   // ✅
const b: Greeting = "goodbye world"; // ❌ not assignable

type Method = "get" | "post";
type Route  = `/api/${Method}`;
// → "/api/get" | "/api/post"   👈 unions multiply out

That last bit is the powerful part: a template literal type with a union in a hole expands to every combination. Two unions of three members each gives you nine literal types, for free.

TypeScript also ships four intrinsic string types that only exist in the compiler: Uppercase<S>, Lowercase<S>, Capitalize<S> and Uncapitalize<S>. These are genuine magic — you can't implement them yourself — but there are only four of them and they do exactly what their names say.

Decoding the scary snippet

We now have every piece. Let's go back to the thing from the top of the guide:

✅ Generating handler props
type Handlers<T> = {
  [K in keyof T as `on${Capitalize<string & K>}Change`]: (value: T[K]) => void
};

type FormProps = Handlers<{ email: string; age: number }>;
// → { onEmailChange: (value: string) => void;
//     onAgeChange:   (value: number) => void }

Piece by piece:

  • [K in keyof T — for each key in T. Just a loop.
  • as \`on${...}Change\` — but call the output key this instead.
  • Capitalize<...> — uppercase the first letter, so we get onEmailChange not onemailChange.
  • string & K — this is the only genuinely ugly bit. keyof T can technically include number and symbol keys, and Capitalize only accepts strings. Intersecting with string is how you tell the compiler "just the string ones, please."
  • (value: T[K]) => void — the value type is a function taking whatever type that field actually had.

Four ideas, none of them hard. It reads like a sentence now, right? That's the feeling to chase with all of this stuff.

The other use of as: deleting keys

Here's a genuinely surprising rule. If the as clause produces never for a key, that key is dropped from the result entirely. Which turns key remapping into a filter:

✅ Keep only the string-valued fields
type StringFieldsOnly<T> = {
  [K in keyof T as T[K] extends string ? K : never]: T[K]
};

type Searchable = StringFieldsOnly<{ name: string; age: number; city: string }>;
// → { name: string; city: string }   👈 age vanished

You'll notice we just used T[K] extends string ? K : never — a conditional type — before I've explained conditional types. That's on me, and it's the perfect segue.

4. Conditional types

An if statement, for types

The syntax is a ternary, and it means what it looks like it means:

The shape
T extends U ? X : Y

"If T is assignable to U, the answer is X, otherwise Y."

The word extends is doing something confusing here, so let's fix that immediately. In a class, extends means inheritance. In a conditional type, extends means "is assignable to" — is every value of T also a valid value of U? Read it as "fits into" and you'll never be confused again.

Reading "fits into"
type A = "hello" extends string ? true : false;   // → true
type B = string extends "hello" ? true : false;   // → false 👈 not every string is "hello"
type C = { a: 1; b: 2 } extends { a: 1 } ? true : false;  // → true

On its own this is a party trick. It becomes useful the moment the thing being tested is a type parameter, because then the type changes shape depending on what you pass in:

✅ A useful conditional
type Unpacked<T> = T extends Promise<unknown> ? "async thing" : "plain thing";

type X = Unpacked<Promise<string>>;  // → "async thing"
type Y = Unpacked<number>;            // → "plain thing"

infer — pulling a type back out

Now the good part. Detecting that something is a Promise is fine, but what you usually want is the thing inside the Promise. How do you get at it?

Take a guess at what the tool would have to do. You'd want to say something like: "match T against the pattern Promise<something>, and give me a name for whatever something turned out to be."

That's infer, exactly:

✅ Awaited, hand-built
type MyAwaited<T> = T extends Promise<infer Value> ? Value : T;

type A = MyAwaited<Promise<User>>;  // → User
type B = MyAwaited<string>;         // → string  👈 not a promise, pass it through

infer Value declares a brand new type variable inside the condition. If the match succeeds, Value is bound to whatever filled that slot, and you can use it in the true branch. If the match fails, Value never exists and you fall to the false branch.

The mental model I use: infer is a luggage tag. You're saying "I don't know what's in this slot, but stick a tag on it called Value so I can find it again on the other side of the conveyor belt." The analogy is imperfect — a real luggage tag doesn't disappear if the bag doesn't show up — but it captures the important bit, which is that infer names something you can't write down yourself.

Build ReturnType

Same pattern, different shape to match against. A function type is (...args) => Something, so put the tag on the Something:

✅ ReturnType from scratch
type MyReturnType<T> =
  T extends (...args: any[]) => infer R ? R : never;

function getUser() {
  return { id: "u_1", name: "Ada" };
}

type U = MyReturnType<typeof getUser>;
// → { id: string; name: string }

Note typeof getUser — that's how you get from a value (the function) to its type. And the same trick works on the arguments side with infer A in the parameter position, which is how Parameters<T> is built.

Build ElementType

✅ What's inside an array?
type ElementType<T> = T extends (infer E)[] ? E : never;

type A = ElementType<User[]>;              // → User
type B = ElementType<(string | number)[]>; // → string | number

The parentheses in (infer E)[] are load-bearing — they say "an array of infer E", not "infer an E[]".

Recursive conditional types

Conditional types can call themselves. That's how the real Awaited handles a Promise<Promise<string>>:

✅ Unwrap all the way down
type DeepAwaited<T> = T extends Promise<infer V> ? DeepAwaited<V> : T;

type A = DeepAwaited<Promise<Promise<number>>>;  // → number
🔧 Under the hood (skippable)

The real Awaited<T> in lib.es5.d.ts is chunkier than mine, because it also handles thenables — any object with a .then() method, not just actual Promise instances — and it has to deal with null and undefined. If you're curious, cmd-click Awaited in your editor and read it. Genuinely: reading the lib files is the fastest way to get good at this, because every technique in this guide is in there, used in anger.

Also worth knowing: recursion here isn't unlimited. TypeScript will bail with "Type instantiation is excessively deep and possibly infinite" if you go too far. That error usually means a recursive type didn't have a base case, not that you did something illegal.

🎤 In an interview: "What does infer do?"
Say this

"infer lets you pattern-match inside a conditional type and capture part of the matched type as a variable. So T extends Promise<infer V> ? V : T says 'if T is a Promise, give me whatever's inside it'. It's how ReturnType, Parameters and Awaited are all implemented — ReturnType is just T extends (...args: any[]) => infer R ? R : never. The variable only exists in the true branch, because if the match failed there's nothing to bind."

Why it lands: naming where the variable is scoped ("only in the true branch") is the detail that separates "I've seen infer" from "I've written infer."

5. Distributive conditional types

OK. This is the surprising one, and I want to set it up as a puzzle, because being surprised by it once is how you remember it forever.

Here's a conditional type that wraps something in an array:

Guess the output
type ToArray<T> = T extends unknown ? T[] : never;

type Result = ToArray<string | number>;
// → ???

Have a think. string | number extends unknown, obviously — everything does. So the answer should be (string | number)[], an array that can hold either. Right?

Show me the actual answer 
type Result = ToArray<string | number>;
// → string[] | number[]

Not an array of "string or number". Either an array of strings or an array of numbers. Those are very different types — ["a", 1] is valid for the first and invalid for the second.

What actually happened

When the thing on the left of extends is a naked type parameter — just T, not wrapped in anything — and you pass it a union, TypeScript doesn't evaluate the condition once. It splits the union apart, runs the whole conditional separately on each member, and unions the results back together.

The analogy I like: it's mail sorting. You hand the clerk a stack of envelopes and a rule ("if it's international, put it in the blue bin"). The clerk doesn't look at the stack as one object — they run the rule on each envelope. The rule was written for one envelope; the machinery applies it to all of them.

This is a feature, and it's how Exclude works

Distribution isn't a wart. It's the thing that makes union-filtering possible at all:

✅ Exclude and NonNullable, hand-built
type MyExclude<T, U> = T extends U ? never : T;

type Status = "idle" | "loading" | "error";
type Settled = MyExclude<Status, "loading">;
// → "idle" | "error"

type MyNonNullable<T> = T extends null | undefined ? never : T;
type A = MyNonNullable<string | null>;  // → string

Walk through MyExclude with distribution in mind: the union splits into three, each member is tested against "loading", the matching one becomes never, and — here's the last piece — never in a union disappears. "idle" | never | "error" collapses to "idle" | "error". Without distribution this type would be useless; the condition would evaluate once against the whole union and give you one answer for everything.

Turning distribution off: [T] extends [U]

Sometimes distribution is exactly wrong. Say you want to ask "is T exactly string?":

❌ Distributes, gives a weird answer
type IsString<T> = T extends string ? true : false;

type A = IsString<string | number>;
// → boolean   👈 what?!

Where did boolean come from? Distribution: string gave true, number gave false, and true | false is boolean. Technically correct, completely useless.

The fix is a rule I mentioned in passing: distribution only happens for a naked type parameter. So don't leave it naked. Wrap both sides in a one-element tuple:

✅ Distribution off
type IsString<T> = [T] extends [string] ? true : false;

type A = IsString<string | number>;  // → false ✅
type B = IsString<string>;           // → true  ✅

The tuple brackets are pure ceremony — they don't change the assignability check, they just hide T from the distribution machinery. Any wrapper works; [T] is the idiom.

(The other place you need it: testing for never. Since never is the empty union, distributing over it produces never rather than a boolean — so IsNever<T> has to be written [T] extends [never].)

A common misconception

"Conditional types distribute over unions." Not quite — they distribute when the checked type is a naked type parameter. Wrap it in anything ([T], { a: T }) and it doesn't. Nor does a concrete union written inline rather than passed as a parameter.

🎤 In an interview: "What's a distributive conditional type?"
Say this

"When a conditional type checks a naked type parameter and you pass it a union, TypeScript doesn't evaluate it once — it applies the condition to each member of the union separately and unions the results. So T extends unknown ? T[] : never given string | number gives you string[] | number[], not (string | number)[]. It's the mechanism behind Exclude and NonNullable, since never members drop out of a union. If you don't want it, wrap both sides in a tuple — [T] extends [U] — which stops the parameter being naked."

Why it lands: you gave the behaviour, a concrete example with the surprising output, why it exists, and the escape hatch. That's a complete answer, and the [T] extends [U] trick is the bit most candidates don't know.

6. Declaration merging

Switching gears. This one isn't about clever type transformations — it's about a rule that feels like a bug until you learn what it's for.

Declare the same interface twice and TypeScript doesn't complain. It merges them:

Interfaces merge
interface User { name: string }
interface User { age: number }

const u: User = { name: "Ada", age: 36 };  // ✅ both required

Try that with type and you get "Duplicate identifier 'User'". This is the single most concrete difference between the two, and it's why "interface and type are basically the same" is a slightly wrong thing to say in an interview.

The merge is a union of members, not an override. If the two declarations give the same property different types, that's an error — you can add, you can't contradict. (Methods are the exception: same-name methods become overloads rather than a conflict.)

(Functions and classes can also merge with namespace blocks, which is how older .d.ts files attach typed static properties to a function. You'll read it, you won't write it.)

Why this exists: you can't edit node_modules

Here's the actual point of the whole feature. You're using Express. Your auth middleware attaches a user to the request object:

❌ The compiler has never heard of req.user
app.use((req, res, next) => {
  req.user = decodeToken(req.headers.authorization);  // ❌ Property 'user'
  next();                                             //    does not exist
});

You know req.user is real. TypeScript doesn't, because Express's own type definitions don't mention it — and you can't go and edit them, because they live in node_modules and get blown away on every install.

So: module augmentation. You reopen the library's interface from your own file and add to it:

✅ types/express.d.ts
import "express";   // 👈 makes this file a module — required!

declare module "express-serve-static-core" {
  interface Request {
    user?: { id: string; role: "admin" | "member" };
  }
}

Now req.user is typed everywhere in the project, with no casts and no any. The merge happened across package boundaries, which is a genuinely remarkable thing for a type system to allow.

Wait — why the pointless-looking import "express" at the top?

Because of a rule that has burned every TypeScript developer at least once. A .ts file with no top-level import or export is a script, not a module — everything in it is global. And inside a script, declare module "x" { } means "declare a module called x", i.e. define it from scratch, which replaces the real types instead of adding to them. Inside a module, the same syntax means "augment the existing module x."

So if your augmentation seems to have deleted the library's types rather than extending them, you're missing an import or an export {} at the top of the file. That's the bug, every time.

Extending globals

Same idea, different keyword — declare global for Window and friends:

✅ globals.d.ts
export {};   // 👈 same rule: this file must be a module

declare global {
  interface Window { __APP_VERSION__: string }
}

window.__APP_VERSION__;  // → string, no cast needed

And here's the payoff, because it turns the whole section into a design principle. Every styled-components or Emotion codebase augments the library's DefaultTheme to get autocomplete on props.theme.colors.primary. That's only possible because the library authors declared it as an interface. Had they written type DefaultTheme = {}, you could not extend it. Full stop.

So the practical rule: interface for public object shapes consumers might reasonably need to extend; type for everything interface can't express — unions, tuples, mapped and conditional types — and for internal shapes you specifically don't want reopened.

🎤 In an interview: "When would you use declaration merging?"
Say this

"Almost always for one reason: adding to types I don't own. The classic is attaching req.user to Express's Request from auth middleware — I write a declare module "express-serve-static-core" block that reopens the Request interface. Same technique for filling in DefaultTheme for styled-components, or adding a property to Window via declare global. The gotcha is that the augmenting file has to be a module — needs an import or export {} — otherwise declare module defines a new ambient module instead of augmenting the real one, and you silently wipe out the library's types. It's also why interface and type aren't interchangeable: only interfaces merge, so a library's extension points have to be interfaces."

Why it lands: you've named a real problem, the real fix, the real footgun, and connected it back to a design decision. That's a story, not a definition.

7. Why seniors avoid enum

This one comes up constantly, and it's a trap in both directions: say "enums are bad" with no reasons and you sound like you're repeating a tweet; defend them with no awareness of the problems and you sound like you've never shipped one.

Let's earn the opinion properly. Here's the thing every other TypeScript feature has in common, and that enum breaks.

Problem 1: enums emit runtime JavaScript

The rule you've internalised is types are erased. Strip the annotations, get JavaScript. Interfaces, type aliases, generics — all gone at build time, zero bytes shipped.

enum is the exception:

What the compiler actually emits
// You write:
enum Status { Idle, Loading, Done }

// It emits (roughly):
var Status;
(function (Status) {
  Status[Status["Idle"] = 0] = "Idle";
  Status[Status["Loading"] = 1] = "Loading";
  Status[Status["Done"] = 2] = "Done";
})(Status || (Status = {}));

A real object, in your bundle, at runtime. It's small — but it means enum is the one piece of TypeScript syntax that isn't a type annotation at all. It's a language feature bolted onto JavaScript, which is a different thing, and it's the reason a `.ts` file using enums can't simply have its types stripped.

That last point has teeth now: Node's built-in TypeScript support and TypeScript's own erasableSyntaxOnly flag work by deleting type syntax, not compiling it. Under that flag, enum is a hard error. Same for namespace with runtime content and parameter properties. The ecosystem is moving toward "TypeScript is erasable annotations," and enums are on the wrong side of that line.

Problem 2: numeric enums have a hole in them

Look at that emitted object again. It maps names to numbers and numbers back to names — Status[0] === "Idle". That's "reverse mapping," and it means the object has six keys, not three, and iterating it gives you garbage unless you filter.

Worse, historically, numeric enums accepted numbers that weren't members at all:

❌ Unsound
enum Status { Idle, Loading, Done }

const s: Status = 47;   // no error in older TS — 47 is not a status!

TypeScript 5.0 tightened this for enums whose members are all literals, so plain cases now error. But enums with any computed member still behave loosely, and the reverse mapping is still there in every numeric enum you ship. The safe habit is: if you must use an enum, give every member an explicit string value.

Problem 3: enums are nominal, and TypeScript is structural

This is the one that actually bites teams. Everywhere else, TypeScript compares types by shape. Enums compare by identity:

❌ "But they're identical!"
enum Method { Get = "GET", Post = "POST" }

function request(m: Method) { /* ... */ }

request("GET");        // ❌ Type '"GET"' is not assignable to type 'Method'
request(Method.Get);   // ✅ only this works

So the enum is viral. Every caller — including callers in other packages, including test fixtures, including JSON you parsed — has to import the enum object to say a value it already knows. And if two copies of your library end up in the dependency tree, those are two distinct enums that don't accept each other's members, which produces one of the more baffling error messages you'll ever read.

Problem 4: const enum fixes one thing and breaks another

const enum tells the compiler to inline the values and emit no object — which solves the bundle-weight and tree-shaking complaints. But inlining requires the compiler to see the enum's declaration and the use site at the same time, and modern toolchains don't work that way. Babel, esbuild, swc and TypeScript's own isolatedModules mode all transpile one file at a time with no cross-file knowledge. Under isolatedModules, exported const enums are an error precisely because a single-file transpiler can't inline them correctly.

What to do instead

A union of string literals. That's it:

✅ The default
type Status = "idle" | "loading" | "done";

function setStatus(s: Status) {}
setStatus("loading");   // ✅ just write it
setStatus("loadng");    // ❌ caught, with a "did you mean" suggestion

Zero runtime output, structural so plain strings work, autocompletes at the call site, narrows perfectly in a switch, and JSON from your API matches it directly without translation.

When you also need a runtime value — to iterate the options, render a dropdown, or map to display labels — use an object with as const and derive the type from it:

✅ When you need runtime values too
const STATUS = {
  Idle: "idle",
  Loading: "loading",
  Done: "done",
} as const;

type Status = typeof STATUS[keyof typeof STATUS];
// → "idle" | "loading" | "done"

Object.values(STATUS);   // → ["idle", "loading", "done"]  ✅ iterable

That typeof STATUS[keyof typeof STATUS] line is worth decoding, since it's just the two operators from section 1: typeof STATUS gets the type of the object, keyof that gets "Idle" | "Loading" | "Done", and indexing with that union gives the union of the values. Without as const, TypeScript would widen every value to string and you'd get string back — the as const is what preserves the literals.

🎤 In an interview: "Why do seniors avoid enums?"
Say this

"Mainly because enum is the one TypeScript feature that isn't erased — it emits a real object into the bundle, which breaks the mental model that types are compile-time only, and it's banned outright under erasableSyntaxOnly and Node's type-stripping. On top of that, enums are nominally typed in an otherwise structural language, so you can't pass "GET" where a Method.Get is expected even though they're the same string, and two copies of a package produce two incompatible enums. Numeric enums also carry a reverse mapping and historically accepted any number. const enum avoids the runtime object but breaks under isolatedModules, Babel and esbuild, which is most build setups now."

"So my default is a union of string literals, plus an as const object when I need to iterate the values at runtime. That said, I wouldn't rip enums out of a codebase that already uses them consistently — a string-valued enum in an app that isn't bundle-sensitive is fine, and mixed conventions cost more than either convention alone."

Why it lands: the mechanism ("emits an object", "nominal not structural") shows you know why, and the last sentence shows judgment. Dogma reads as junior; "here's the tradeoff and here's when I'd leave it alone" reads as senior.

Trap

Don't say "enums are slow" or "enums bloat your bundle" as the headline. The object is a handful of bytes; that's not the real argument, and an interviewer who knows this will push back. The real arguments are erasability and nominal typing. Lead with those.

8. Making impossible states unrepresentable

This is the part I'd most want a senior candidate to be able to talk about, because it's not a feature — it's a way of using the features we've built up, and it changes how code feels to work in.

The shape almost everyone writes first

❌ The classic
type RequestState = {
  isLoading: boolean;
  error: Error | null;
  data: User[] | null;
};

Three independent fields. How many states does that describe? Two × two × two = eight. How many of those are real?

isLoadingerrordataMeaning
falsenullnullIdle — fine ✅
truenullnullLoading — fine ✅
falsenullsetSuccess — fine ✅
falsesetnullFailed — fine ✅
truesetnullLoading and errored? 🤨
truenullsetRefetching, maybe? Ambiguous 🤨
truesetsetNonsense ❌
falsesetsetNonsense ❌

Four real states, four states that are either meaningless or ambiguous. And the type system will happily let you construct every one of them, so every component that reads this state has to defensively guess:

❌ Defensive guessing, and a bug
if (state.isLoading) return <Spinner />;
if (state.error)     return <ErrorBox error={state.error} />;
return <List users={state.data!} />;   // 👈 that ! is a lie you're forced into

See the !? You know data is there by that line, but the type doesn't, so you assert. Every non-null assertion in a codebase is a little note saying "the type is less precise than reality." And the classic bug lives here too: a failed refetch that sets error but forgets to clear isLoading leaves you with a spinner forever, and nothing complained.

The fix: a discriminated union

Instead of describing the fields, describe the states, and give each one only the data that state actually has:

✅ Four states, exactly four
type RequestState =
  | { status: "idle" }
  | { status: "loading" }
  | { status: "success"; data: User[] }
  | { status: "failure"; error: Error };

The shared literal field — status here — is the discriminant. Because each member has a different literal value for it, TypeScript can look at state.status and know precisely which member you're holding.

The "impossible" states are now unspellable. There's no way to construct a value with both error and data, because no member of the union has both fields. You didn't add a validation rule or a lint check — you removed the states from existence.

And now narrowing does the work for you

✅ No assertions, no guessing
switch (state.status) {
  case "idle":    return <StartButton />;
  case "loading": return <Spinner />;
  case "failure": return <ErrorBox error={state.error} />;   // 👈 error is defined here
  case "success": return <List users={state.data} />;        // 👈 and data here
}

Inside case "success", state isn't RequestState any more — it's narrowed to exactly { status: "success"; data: User[] }. So state.data is User[], not User[] | null. The ! is gone, and it's gone because it was never needed, not because you got away with something.

Try to write state.error in the "success" branch and you get a compile error. The type system is now enforcing the state machine.

The same move, on a checkout flow

This scales past loading spinners. A multi-step flow has the same disease — a pile of optional fields that are only meaningfully optional at certain steps:

❌ Everything optional, forever
type Checkout = {
  step: number;
  items: CartItem[];
  address?: Address;
  payment?: PaymentMethod;
  orderId?: string;
};

Every function that touches address has to handle it being missing, even the ones that only ever run after the address was collected. So you get address! sprinkled everywhere, or defensive early-returns that can never fire.

✅ Each step carries exactly what it has
type Checkout =
  | { step: "cart";      items: CartItem[] }
  | { step: "shipping";  items: CartItem[]; address: Address }
  | { step: "payment";   items: CartItem[]; address: Address; method: PaymentMethod }
  | { step: "confirmed"; orderId: string };

function chargeCard(c: Extract<Checkout, { step: "payment" }>) {
  c.method;    // ✅ guaranteed present, by the type
  c.address;   // ✅ so is this
}

And look — that's Extract, which is a distributive conditional type, filtering a union by discriminant. All the pieces are connecting up.

Same story for permissions. Rather than { user: User | null; isLoggedIn: boolean } — which lets you have isLoggedIn: true with a null user — write:

✅ Sessions
type Session =
  | { state: "anonymous" }
  | { state: "authenticated"; user: User; permissions: Set<Permission> };

Guaranteeing you handled every case: exhaustiveness with never

Now the follow-up question. You've got four cases handled. Six months later somebody adds a fifth state — { status: "cancelled" }. How do you find every switch that needs updating?

You make the compiler find them. The trick uses never, and it's genuinely elegant once you see the mechanism.

First, the two facts it rests on. One: as you handle each case, TypeScript narrows the remaining possibilities — if you've handled all four, the type left over in default is never, the type with no values. Two: never is assignable to everything, but nothing is assignable to never. So a parameter typed never only accepts an argument that's already never.

Put them together:

✅ The exhaustiveness check
function assertNever(value: never): never {
  throw new Error(`Unhandled case: ${JSON.stringify(value)}`);
}

function render(state: RequestState) {
  switch (state.status) {
    case "idle":    return <StartButton />;
    case "loading": return <Spinner />;
    case "failure": return <ErrorBox error={state.error} />;
    case "success": return <List users={state.data} />;
    default:        return assertNever(state);   // 👈 state is `never` here
  }
}

Today this compiles, because all four are handled and state narrows to never in the default branch. Add "cancelled" to the union without adding a case, and state in default narrows to { status: "cancelled" } instead — which is not assignable to never:

❌ The error you want to see
// Argument of type '{ status: "cancelled" }' is not assignable
// to parameter of type 'never'.

Every switch in the codebase that forgot the new case lights up red, in the right file, on the right line. That's a refactor you can actually trust.

The throw matters too: it's your runtime safety net for when bad data sneaks past the type system, which — as we're about to discuss — it can.

Wait — do I need assertNever, or is there a compiler flag?

There's noFallthroughCasesInSwitch, but that's a different thing — it catches missing breaks, not missing cases. There's no built-in "this switch must be exhaustive" flag for statements.

You do get exhaustiveness for free in one situation: if the function has an explicit return type annotation and every case returns, a missing case makes the function implicitly return undefined, which fails the annotation. That works, but the error points at the function signature rather than the missing case, so it's a worse message. assertNever is three lines and points right at the problem — write the three lines.

Branded types, briefly

One more tool in the same family. Structural typing means a UserId and a PostId are both just string, so nothing stops you passing one where the other belongs — a bug that type-checks perfectly and blows up in production.

You can fake nominal typing by intersecting with a marker that nothing else has:

✅ Branded / opaque types
type UserId = string & { readonly __brand: "UserId" };
type PostId = string & { readonly __brand: "PostId" };

const asUserId = (raw: string) => raw as UserId;   // 👈 one blessed entry point

function getUser(id: UserId) {}

getUser(asUserId("u_1"));          // ✅
getUser("u_1");                    // ❌ plain string isn't branded
getUser(somePostId);               // ❌ wrong brand

The brand doesn't exist at runtime — it's string all the way down, which is exactly why you get all the string methods for free and zero overhead. The cost is that one as cast in the constructor function, which is fine if that function is the only way to make a UserId, ideally after validating the format. Use this sparingly — for IDs, for money amounts in cents versus dollars, for "this string has been HTML-escaped." Brand everything and you've just made your codebase annoying.

9. Types are erased — so what do you actually trust?

Here's the uncomfortable thing about everything we've just built. All of it vanishes at build time. Which means this:

❌ A confident lie
const res = await fetch("/api/users");
const users = (await res.json()) as User[];   // 👈 pure fiction

res.json() returns Promise<any>. That as User[] generates no code and performs no check. You have simply told the compiler to stop asking questions. If the API renamed name to fullName last Tuesday, TypeScript will keep insisting users[0].name is a string right up until it's undefined on someone's screen.

This is the honest limit of a static type system: it can only guarantee things about data that originated inside the program. Anything crossing the boundary — HTTP responses, localStorage, URL params, form input, postMessage, environment variables — is unknown at compile time and must be checked at runtime.

The standard answer in 2026 is a schema validation library — Zod, Valibot, ArkType, whichever — where you define the shape once and get both the runtime check and the static type out of it:

✅ Validate, don't assert
import { z } from "zod";

const UserSchema = z.object({
  id: z.string(),
  name: z.string(),
  role: z.enum(["admin", "member"]),
});

type User = z.infer<typeof UserSchema>;
// → { id: string; name: string; role: "admin" | "member" }

const res = await fetch("/api/users");
const users = z.array(UserSchema).parse(await res.json());
// ✅ throws right here if the API changed — not three components later

Two things to notice. First, z.infer<typeof UserSchema> — the type is derived from the validator, so they can't drift apart. That's the same "write the relationship once" principle as mapped types, applied at the boundary.

Second, the failure moves. Instead of undefined propagating silently into a component and producing a blank space or a crash in an unrelated file, you get a loud error at the exact moment the data arrived, naming the field that was wrong. Debugging time goes from an afternoon to a minute.

The mental model: types are the rules inside the building; validation is the security desk at the door. The rules are only meaningful if somebody checks badges on the way in. (The analogy leaks a bit — TypeScript's rules are enforced by the compiler, not by trust — but the shape is right: everything inside is only as trustworthy as what you let in.)

🎤 In an interview: "If types are erased, how do you trust API responses?"
Say this

"You don't — not from the type system alone. res.json() is any, so as User[] is just me promising the compiler something I can't actually guarantee; it emits no check. So I validate at the boundary with a schema library like Zod: I define the schema once, derive the TypeScript type from it with z.infer, and parse the response. Then the failure happens at the fetch with a message naming the bad field, instead of surfacing as undefined in a component three layers away. Inside the app I trust the types completely; at every boundary — network, localStorage, URL params, form input — I check."

Why it lands: "I trust types inside, I check at boundaries" is the exact framing experienced people use. Bonus points for naming boundaries beyond HTTP — localStorage especially, since it's a boundary people forget.

10. Interview follow-ups, answered

The model answers for the big questions are in the callouts above. Here are the ones interviewers reach for next, when they're probing for depth rather than recall — the "why not just—" family.

"Why not just use any when the types get hard?"

Because any isn't a wildcard, it's a hole — it disables checking for everything downstream of it, silently, including things you didn't intend. If you genuinely don't know a type, the right tool is unknown: it accepts anything going in, but forces you to narrow before you can do anything with it. The rule I use: unknown at boundaries, any essentially never in application code, and if I need an escape hatch I write a narrowly-scoped cast with a comment explaining why, so it's greppable.

"Why not just use as to fix a type error?"

Because as doesn't fix anything — it silences the compiler about a mismatch that still exists at runtime. It's appropriate in exactly two places: narrowing something you've genuinely just proven (usually better done with a type guard), and branding. If I'm reaching for as to make an error go away, that's a signal the model is wrong, and I should go fix the type rather than the symptom. The data! in the loading-state example is the perfect illustration: the assertion was hiding a badly-shaped type, and modelling it as a union made the assertion unnecessary.

"Isn't a discriminated union more verbose than a few booleans?"

Slightly, at the definition. But you get it back immediately at every use site: no non-null assertions, no defensive checks for combinations that can't happen, and no "did we forget to reset isLoading" bugs. And when the requirements grow — a fifth state, a step that needs extra data — the union grows in one place and the compiler tells you every consumer that needs updating. The boolean version grows by doubling the number of possible combinations each time you add a flag.

"Can't you just write a runtime guard instead of a mapped type?"

They solve different problems. A mapped type expresses a relationship between two types so they can't drift — Nullable<Form> updates itself when Form changes. A runtime guard checks a value. You want both, in different places: mapped and conditional types for internal consistency, runtime validation at the boundary. Neither substitutes for the other.

"When would you reach for a conditional type in app code, rather than library code?"

Honestly, less often than in library code — and I'd say so, because the wrong answer here is pretending you write infer daily. Where they earn their keep in an app is at typed API layers: a useQuery-style wrapper where the return type depends on the endpoint key, or a form library where field props are derived from the schema type. The rule of thumb is that a conditional type is worth it when it removes a whole category of casts for the callers. If it only makes the definition cleverer without making call sites safer, it's not paying for itself.

"What's the difference between keyof on an interface and on a Record<string, X>?"

keyof on a fixed shape gives you a union of literal keys. On an index-signature type like Record<string, X> it gives you string | number — because the type says any string is a valid key, so there's nothing more specific to report. That's a common source of confusion when someone expects autocompletion from a Record<string, ...> and gets nothing. If you want the specific keys, constrain the record's key type to a union of literals instead.

"How do you tell whether an interviewer wants depth or recall here?"

Listen for whether they ask "what is" or "how would you". "What is a mapped type" is recall — answer in two sentences and stop. "How would you implement Partial", "walk me through what happens when you pass a union to that" or "why would you avoid X" is depth — that's an invitation to show the mechanism and the tradeoff, and short answers there read as thin. When in doubt, give the crisp answer first and then offer: "want me to go through how that's actually implemented?" That's a very safe move.

11. Interview cheat sheet

Read this on the train. Each line is a thing you could say out loud.

keyof T / T[K]
Keys as a union of string literals; the type at a key. Index with a union, get a union back.
Mapped type
{ [K in keyof T]: ... } — a compile-time loop over keys that builds a new object type.
Partial
type Partial<T> = { [K in keyof T]?: T[K] }. The built-in utility types are ordinary mapped types in lib.es5.d.ts, not compiler magic.
Readonly / Pick / Record
{ readonly [K in keyof T]: T[K] } / { [P in K]: T[P] } / { [P in K]: V }.
Modifiers
-? strips optionality (that's Required), -readonly strips readonly (that's Mutable, which isn't built in).
Key remapping
[K in keyof T as NewKey]. Combine with template literals to generate on${Capitalize<K>}Change. Remap to never to delete a key — that's how you filter.
Conditional type
T extends U ? X : Y. extends here means "is assignable to", not inheritance.
infer
Pattern-matches and captures part of a type. T extends (...a: any[]) => infer R ? R : never is ReturnType. The variable exists only in the true branch.
Distributive conditional
A naked type parameter + a union = the condition runs per member and the results re-union. ToArray<string|number> → string[] | number[]. It's why Exclude works.
Turning distribution off
[T] extends [U]. Required for IsNever, since distributing over never (the empty union) gives never.
Declaration merging
Same-name interfaces combine. Used for augmenting types you don't own: declare module "express-serve-static-core", declare global, styled-components' DefaultTheme. The file must be a module (export {}) or you replace instead of augment.
interface vs type
Only interfaces merge, so public extension points must be interfaces. Only type can express unions, tuples, mapped and conditional types.
Why not enum
It emits runtime JS (so it isn't erasable — banned under erasableSyntaxOnly), it's nominal in a structural language, numeric enums carry reverse mappings, and const enum breaks under isolatedModules/Babel/esbuild. Default to a string-literal union plus an as const object when you need runtime values — but don't crusade against a codebase that uses them consistently.
Impossible states
Three booleans = eight combinations, half nonsense. A discriminated union on status permits exactly the real states, and narrowing then guarantees each state's data is present — no ! assertions.
Exhaustiveness
default: return assertNever(state) where assertNever(v: never). Handled cases narrow the remainder to never; an unhandled one doesn't, and nothing is assignable to never, so it's a compile error pointing at the right line.
Branded types
string & { __brand: "UserId" } fakes nominal typing for IDs and units. Zero runtime cost; needs one blessed constructor doing the cast.
Trusting external data
as User emits no check — it's a promise, not a proof. Validate at boundaries with Zod and derive the type via z.infer so schema and type can't drift. Trust types inside, check at the door.

One last thought before you close the tab. Almost everything here is the same idea wearing different hats: say the rule once, and let the compiler derive the consequences. Mapped types say it about shapes. Conditional types say it about branching. Discriminated unions say it about states. Zod schemas say it about the boundary. If an interviewer asks a question this guide didn't cover, that sentence is a genuinely good place to reason from. 🎯
