The problem Promise.all solves

You need a user, their orders, and their saved cards to render a dashboard. So you write this:

❌ Three seconds for three one-second requests
const user   = await fetchUser();     // 1s
const orders = await fetchOrders();   // 1s — starts only after user lands
const cards  = await fetchCards();    // 1s
// → 3 seconds

Each await parks the function until that request finishes. But none of these three depend on each other! They could all be in flight at once. That's what Promise.all is for:

✅ One second
const [user, orders, cards] = await Promise.all([
  fetchUser(), fetchOrders(), fetchCards(),
]);
// → ~1 second, the slowest one

Two rules you should be able to state cold, because the interviewer will ask:

  • It resolves with an array of results in input order — not completion order. If fetchCards comes back first, it still lands at index 2.
  • It rejects the instant any input rejects, with that first error. It does not wait for the others.

Building Promise.all

We're writing a function that takes an array and returns a promise. So the outer shape is forced on us — we need a promise we control, which means the constructor:

Step 1 — the shape
function promiseAll(promises) {
  return new Promise((resolve, reject) => {
    // ...decide when to call resolve / reject
  });
}

Everything left is bookkeeping: run all of them, collect the values, and figure out when we're done.

Step 2 — collect, in order
const results = [];
let completed = 0;

promises.forEach((item, i) => {
  item.then((value) => {
    results[i] = value;        // 👈 by index, not push
    completed++;
    if (completed === promises.length) resolve(results);
  });
});

Two lines there carry the whole answer.

results[i] = value, not results.push(value). The callbacks fire in completion order, which is whatever the network decides. Push would give you the fastest response at index 0. Writing to the loop index puts each value exactly where its promise sat in the input, no matter when it lands. That's rule one, implemented in one character.

Count completions; don't check results.length. Tempting, but broken: if index 2 finishes first, results is [<2 empty>, value] — length is already 3, and we'd resolve with holes. The completed counter only goes up when a value has actually arrived.

Step 3 — rejection
item.then(
  (value) => { /* as above */ },
  reject                       // 👈 that's the whole error path
);

Just hand reject over. No flag tracking "have we already failed?" — a promise ignores every settle call after the first. Once one input rejects, our promise is rejected forever; later resolves and rejects are silently dropped. Say that out loud in the interview, it's the bit people add unnecessary guards for.

Two loose ends

Promise.all([fetchUser(), 42]) is legal — non-promise values just come through as themselves. Our version would crash on 42.then. Fix: wrap every item in Promise.resolve(item), which passes promises through untouched and boxes plain values.

And Promise.all([]) resolves immediately with []. Our counter never gets incremented, so the loop body never runs and we'd hang forever. One early return.

✅ The answer
function promiseAll(promises) {
  return new Promise((resolve, reject) => {
    if (promises.length === 0) return resolve([]);

    const results = [];
    let completed = 0;

    promises.forEach((item, i) => {
      Promise.resolve(item).then((value) => {
        results[i] = value;                       // keeps input order
        completed++;
        if (completed === promises.length) {      // all in? done
          resolve(results);
        }
      }, reject);                                 // first failure wins
    });
  });
}

Fifteen lines, no cleverness. That's the version to write.

all vs allSettled vs race vs any

MethodResolves whenRejects when
allAll fulfil → array of valuesAny rejects (immediately)
allSettledAll settle → array of {status, value|reason}Never
raceFirst to settle fulfilsFirst to settle rejects
anyFirst to fulfilAll reject → AggregateError

Picking between them: all when you need every piece to render anything. allSettled when the page degrades gracefully and you want partial data plus a list of what broke. race for timeouts — race the real request against a promise that rejects after 5s. any for redundant sources, where the first working mirror wins.

The problem an EventEmitter solves

The cart badge in your header needs to update when someone adds an item from a product page. The obvious move is to have the product page import the header and call a method on it. Do that a dozen times and you've knitted every module to every other module.

What you want instead: the product page announces "item-added" and doesn't know or care who's listening. The header listens for "item-added" and doesn't know who announced it. That's pub/sub, and an EventEmitter is the object in the middle.

Think of a radio station. It broadcasts on a frequency; anyone tuned to that frequency hears it. The station doesn't keep a list of who's listening, and the listeners don't know each other. Where the analogy breaks: our emitter does keep an exact list — that's literally its only state — and listeners who tune in late hear nothing at all, because there's no recording of past broadcasts.

Building the EventEmitter

Before any code: what's the data structure? Get this right and the methods write themselves. We need, per event name, an ordered collection of functions. So: an object from event name → array of listeners.

on — subscribe

on(event, listener) {
  if (!this.events[event]) this.events[event] = [];   // first listener for this name
  this.events[event].push(listener);
}

emit — broadcast

Look up the array, loop it, call each one with whatever arguments came in. Return whether anyone was listening — that's what Node's emitter does, and it's a nice touch to add unprompted.

emit(event, ...args) {
  const listeners = this.events[event];
  if (!listeners || listeners.length === 0) return false;
  listeners.forEach((fn) => fn(...args));
  return true;
}

off — unsubscribe

off(event, listener) {
  if (!this.events[event]) return;
  this.events[event] = this.events[event].filter((fn) => fn !== listener);
}

Note what fn !== listener requires: the exact same function reference you passed to on. Two identical-looking arrow functions are two different objects, so this silently does nothing:

emitter.on('checkout', () => clearCart());
emitter.off('checkout', () => clearCart());   // 👈 different function. Still subscribed.

Exactly the same gotcha as removeEventListener. Keep a named reference.

once — subscribe for one broadcast

Wrap the listener in a function that calls it and then removes itself. The subtlety: what's actually stored in the array is the wrapper, so that's what off has to be given.

once(event, listener) {
  const wrapper = (...args) => {
    this.off(event, wrapper);   // 👈 remove the wrapper, not `listener`
    listener(...args);
  };
  wrapper.original = listener;  // so off(event, listener) can find it too
  this.on(event, wrapper);
}

wrapper.original lets someone cancel a once before it ever fires, by passing the function they actually wrote. Then off matches either one:

this.events[event].filter((fn) => fn !== listener && fn.original !== listener);
✅ The whole class
class EventEmitter {
  constructor() {
    this.events = {};                // name → array of listeners
  }

  on(event, listener) {
    if (!this.events[event]) this.events[event] = [];
    this.events[event].push(listener);
    return this;                     // chainable, like Node's
  }

  off(event, listener) {
    if (!this.events[event]) return this;
    this.events[event] = this.events[event].filter(
      (fn) => fn !== listener && fn.original !== listener
    );
    return this;
  }

  once(event, listener) {
    const wrapper = (...args) => {
      this.off(event, wrapper);
      listener(...args);
    };
    wrapper.original = listener;
    return this.on(event, wrapper);
  }

  emit(event, ...args) {
    const listeners = this.events[event];
    if (!listeners || listeners.length === 0) return false;
    [...listeners].forEach((fn) => fn(...args));   // copy — see below
    return true;
  }
}
const bus = new EventEmitter();
const updateBadge = (count) => console.log('badge:', count);

bus.on('item-added', updateBadge);
bus.once('item-added', (c) => console.log('first add!', c));

bus.emit('item-added', 1);   // → badge: 1   /   first add! 1
bus.emit('item-added', 2);   // → badge: 2
bus.off('item-added', updateBadge);
bus.emit('item-added', 3);   // → (nothing)  returns false
Why [...listeners] in emit

If a listener calls off while emit is running — and once does exactly that — you're mutating the array you're iterating. The index advances past a listener that shifted down, and it gets skipped for that emit. Iterating a shallow copy means the current broadcast reaches everyone who was subscribed when it started, and removals take effect next time. Mentioning this unprompted is a strong senior signal.

The interview layer

How it gets asked

  • "Implement Promise.all from scratch." / "Write your own myPromiseAll."
  • "These three requests don't depend on each other — make this faster."
  • "Build a pub/sub class with on, off, emit." (then "now add once" — it's always the follow-on)
  • "How would two components talk without importing each other?"
🗣 Model answer — "walk me through your Promise.all"

"I return a new promise, and inside it I loop the inputs. Each one gets a .then that writes its value to results at the loop index — that's what preserves input order, since they finish in whatever order the network gives me. I keep a separate completed counter rather than checking results.length, because a sparse array reports a misleading length. When the counter hits the input length I resolve. For failure I pass reject straight in as the rejection handler — no guard flag needed, since a promise ignores any settle after the first."

That lands because you named the two decisions that are actually load-bearing and justified each one. A candidate who just types the code and says "and that's it" gets a much shorter conversation.

Follow-ups

"Why does results[i] = value matter?"

Because completion order isn't input order. push would order results by whoever responded fastest, so destructuring [user, orders, cards] would hand you the wrong things under the right names — a bug that only shows up when latency shifts. The index is the promise's identity.

"When one promise rejects, what happens to the others?"

Nothing. They keep running to completion, and their results get thrown away. Promise.all just stops caring — it's already settled. There's no cancellation in JS promises; if you genuinely need to stop the work you need something like AbortController on each fetch.

"Now write allSettled instead."

Same skeleton, two changes: never call reject, and record an object rather than a raw value. Fulfilment stores { status: 'fulfilled', value }, rejection stores { status: 'rejected', reason }, and both bump completed. You resolve once everything has settled, whichever way.

"How would you limit it to 3 requests at a time?"

Promise.all fires everything at once, which will happily melt an API with 500 URLs. The standard fix is a worker pool: keep a shared cursor into the task list, start N workers, and each worker loops — take the next index, await it, write the result at that index, repeat until the list is exhausted. Then Promise.all the N workers. Roughly fifteen lines, and the result array stays in input order for the same reason as before.

"Why an object of arrays, not one array of {event, fn}?"

Lookup cost. emit is the hot path, and with the object it's a single key access to the exact listeners for that name. A flat array means scanning every subscription in the app on every emit. The object also makes "remove all listeners for this event" a single delete.

"How does this relate to addEventListener or Node's EventEmitter?"

It's the same pattern, and largely the same API — on/off versus addEventListener/removeEventListener, both keyed by string, both requiring the identical function reference to unsubscribe. The DOM adds things ours doesn't: bubbling through a tree, { once: true } and { signal } options, and preventDefault. Node's adds prependListener, a max-listeners warning to catch leaks, and the special 'error' event that throws if nothing is listening.

"What if a listener throws during emit?"

In our version the exception propagates out of emit and every listener after it is skipped — one bad subscriber breaks the rest, which is nasty for a shared bus. If you want isolation, wrap each call in try/catch and report the error rather than rethrowing. Worth naming the tradeoff: swallowing errors hides real bugs, so log loudly.

Traps

  • Using results.length as the done check. The single most common failure in this question.
  • Forgetting Promise.resolve(item). Non-promise inputs are legal and your version crashes on them.
  • Forgetting the empty array. It hangs forever instead of resolving.
  • Calling off(event, listener) inside once. The array holds the wrapper, so that removes nothing and it fires every time.
  • Saying "Promise.all runs them in parallel." It doesn't run anything — the promises were already started when you built the array. Promise.all only waits. This distinction gets probed a lot.

Cheat sheet

  • Promise.all — array of results in input order; rejects on the first rejection.
  • results[i] — index write is what preserves order.
  • completed counter — sparse arrays lie about length.
  • No guard flag — a promise ignores every settle after the first.
  • Edge cases — Promise.resolve(item), and empty array → [].
  • allSettled / race / any — never rejects / first to settle / first to fulfil.
  • EventEmitter — one object: event name → array of listeners.
  • off — needs the exact same function reference.
  • once — a wrapper that removes itself; store wrapper.original.
  • emit — iterate a copy, or removals mid-emit skip listeners.
function promiseAll(promises) {
  return new Promise((resolve, reject) => {
    if (promises.length === 0) return resolve([]);
    const results = [];
    let completed = 0;
    promises.forEach((item, i) => {
      Promise.resolve(item).then((value) => {
        results[i] = value;
        if (++completed === promises.length) resolve(results);
      }, reject);
    });
  });
}

class EventEmitter {
  constructor() { this.events = {}; }
  on(event, fn) {
    (this.events[event] ||= []).push(fn);
    return this;
  }
  off(event, fn) {
    this.events[event] = (this.events[event] || [])
      .filter((l) => l !== fn && l.original !== fn);
    return this;
  }
  once(event, fn) {
    const wrapper = (...args) => { this.off(event, wrapper); fn(...args); };
    wrapper.original = fn;
    return this.on(event, wrapper);
  }
  emit(event, ...args) {
    const listeners = this.events[event];
    if (!listeners || !listeners.length) return false;
    [...listeners].forEach((fn) => fn(...args));
    return true;
  }
}
