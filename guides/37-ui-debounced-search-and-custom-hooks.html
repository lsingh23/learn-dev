Debounced search, and the two hooks you'll write on the way

This is the most-asked React machine-coding question there is. It looks like "type, wait, show results." It's actually a state-shape question with a race condition hiding inside it, and the race condition is what they're really watching for.

The state shape is the whole answer

Same method as always — clarify, state shape, static, wire, polish. I'll spend almost all of my thirty seconds of clarifying on one question: "is the API mine to fake, and can it fail?" Because the answer decides whether I need error handling, and error handling is where the shape gets interesting.

Then, before any JSX, the comment block:

// state:
//   query          → string, what's in the input right now (controlled)
//   debouncedQuery → string, query as of 300ms ago
//   results        → array of records, [] when there's nothing
//   status         → 'idle' | 'loading' | 'error' | 'success'
// derived:
//   showDropdown   → status !== 'idle' && query.length >= 2

Four pieces. Let me defend two of them, because those are the two an interviewer pokes at.

debouncedQuery is state, even though it looks derived. Guide 34 says if you can compute it, don't store it — and this is the exception that proves the rule. debouncedQuery is a function of query and time, and you can't read time during render. Anything downstream of a timer or an async result has to be state. Say that sentence out loud and you've just answered a follow-up before they asked it.

status is one string, not three booleans. The version everyone writes first is isLoading, isError, hasSearched. That's eight combinations for four real situations, and half of them are nonsense — loading and error at the same time, error and success at the same time. Then you're writing setIsLoading(false); setIsError(true); in every branch and forgetting one, and your spinner never goes away.

Make illegal states unrepresentable

One status string can only ever hold one value, so "loading and errored" is structurally impossible rather than a promise you keep making and breaking. This is the exact accordion argument from guide 34, wearing a different hat. Name the principle when you make the choice — it's free points.

Build order: input → hook → effect → list

Four steps, in this order, and each one is visibly working before the next starts.

First the controlled input, with the results list hardcoded so you can see pixels. Then swap the hardcoded array for the real fetch. Here's the whole component as it exists after step three — deliberately naive, we're about to break it:

❌ Works in the demo, broken in real life
const [query, setQuery] = useState('');
const debouncedQuery = useDebounce(query, 300);
const [results, setResults] = useState([]);
const [status, setStatus] = useState('idle');

useEffect(() => {
  if (debouncedQuery.length < 2) { setStatus('idle'); return; }
  setStatus('loading');
  search(debouncedQuery)
    .then(r => { setResults(r); setStatus('success'); })
    .catch(() => setStatus('error'));
}, [debouncedQuery]);

The important structural bit: the effect is keyed on debouncedQuery, never on query. The input updates on every keystroke and stays instant; the network only hears about it when you pause. Those are two separate values on purpose. If you find yourself debouncing the setState instead, you've made the input laggy — that's the classic wrong turn.

I'm not going to re-derive how debounce works here; that's guide 28. What matters in this question is where it sits in the data flow.

The race condition

So. You type rea, pause a beat, keep typing react. Two requests go out. The network being the network, the first one takes 800ms and the second takes 100ms.

What do you think happens here?

The input says react. The list shows results for rea. Nothing threw, nothing logged, the code looks right, and the UI is lying. This is genuinely confusing the first few times you meet it — I still have to draw the timeline to convince myself. The reason it's hard is that the bug lives in the gap between two correct-looking lines, and you can't see a gap.

The fix that always works, and the one I'd write first in an interview, is a flag that the effect's cleanup flips:

✅ The ignore flag — five lines of change
useEffect(() => {
  let ignore = false;                     // 👈 fresh per run
  setStatus('loading');
  search(debouncedQuery)
    .then(r => { if (ignore) return; setResults(r); setStatus('success'); })
    .catch(() => { if (!ignore) setStatus('error'); });
  return () => { ignore = true; };        // 👈 runs before the next effect
}, [debouncedQuery]);

Why this works: every effect run gets its own ignore variable in its own closure. When debouncedQuery changes, React runs the previous run's cleanup before starting the new one, which sets that old closure's flag to true. Request A still comes back 800ms later — you can't un-send it — but its .then now returns immediately instead of writing. Only the newest effect's flag is still false, so only the newest response can touch state. Same trick covers unmount for free.

The better fix, and the one to mention right after: AbortController.

useEffect(() => {
  const ctrl = new AbortController();
  fetch(url, { signal: ctrl.signal })
    .then(r => r.json()).then(setResults)
    .catch(e => { if (e.name !== 'AbortError') setStatus('error'); });
  return () => ctrl.abort();
}, [debouncedQuery]);

Same shape — the cleanup is still what saves you — but this actually cancels the in-flight request instead of ignoring its answer, so you stop wasting the user's bandwidth and free up a connection slot. The one wrinkle is that aborting rejects the promise, so you have to filter out AbortError or you'll flash an error state on every keystroke. I'd say: "ignore flag first because it works with any async source, AbortController when it's fetch."

useDebounce, eight lines

Now extract it. Interviewers ask for this by name almost as often as they ask for the search box itself.

function useDebounce(value, delay = 300) {
  const [debounced, setDebounced] = useState(value);
  useEffect(() => {
    const id = setTimeout(() => setDebounced(value), delay);
    return () => clearTimeout(id);   // 👈 this line IS the debounce
  }, [value, delay]);
  return debounced;
}

That cleanup line is the entire mechanism, and it's worth saying so out loud. Every keystroke changes value, which tears down the previous effect — cancelling its pending timeout — and schedules a fresh one. Type ten characters fast and you create ten timers and cancel nine. Only a pause longer than delay lets a timer survive to fire. Delete clearTimeout and you don't get a slower search, you get every search, just late.

Named upgrades: real autocomplete

Ship the basic version, then offer these by name. Announcing "I'd add keyboard nav next" is worth nearly as much as writing it.

Keyboard navigation. Straight out of the four shapes: this is a pointer. activeIndex, a number, starting at -1 for "nothing highlighted." ArrowDown is i => Math.min(i + 1, results.length - 1), ArrowUp is the Math.max(i - 1, -1) mirror, Enter selects results[activeIndex] if it exists, Escape closes and clears the index. Reset it to -1 whenever results changes, or the highlight lands on a random new row. Do e.preventDefault() on the arrows so the caret doesn't jump around the input.

Click-outside to dismiss. A ref on the wrapper, a mousedown listener on document in an effect, close if !ref.current.contains(e.target), and remove the listener in the cleanup. Use mousedown rather than click so the dropdown doesn't vanish out from under a selection.

Caching. const cache = useRef(new Map()). Before fetching, check cache.current.get(q) and set results synchronously if it's there — that's what makes backspacing feel instant. A ref, not state, because writing to the cache should never trigger a render.

Minimum query length — two characters, already in the effect above — and ARIA: the input gets role="combobox", aria-expanded, aria-controls and aria-activedescendant pointing at the highlighted option's id; the list is role="listbox" with role="option" rows. Naming those four attributes takes ten seconds and reads as senior.

useLocalStorage and recent searches

Nice way to close out the exercise: when a user picks a result, remember it, and show recent searches when the input is empty. That's useLocalStorage, the other hook they ask for by name.

function useLocalStorage(key, initial) {
  const [value, setValue] = useState(() => {          // 👈 lazy: runs once
    try {
      const raw = localStorage.getItem(key);
      return raw ? JSON.parse(raw) : initial;
    } catch { return initial; }
  });
  useEffect(() => {
    try { localStorage.setItem(key, JSON.stringify(value)); } catch {}
  }, [key, value]);
  return [value, setValue];
}

Three things to point at while you write it. The lazy initialiser — passing a function to useState instead of a value means React calls it only on mount. Write useState(JSON.parse(localStorage.getItem(key))) and you hit the disk and parse JSON on every single render, and throw away the result every time but the first.

The try/catch, twice. Reading throws on malformed JSON and in browsers with site data blocked; writing throws on quota exceeded and in Safari private mode. Neither is exotic. A search box should not white-screen because someone's storage is full.

And the honest caveat: this doesn't sync across tabs. Two tabs open, one writes, the other has no idea — its React state is stale. The fix is a window.addEventListener('storage', ...) in the hook, which fires in other tabs on write. I'd mention it, and only build it if asked. Same for SSR: localStorage doesn't exist on the server, so under Next.js you'd read it in an effect instead.

Wiring it in is two lines — const [recent, setRecent] = useLocalStorage('recent', []), and on select, prepend the query, dedupe, slice to five. Render recent in the dropdown when query is empty. Now the hook is part of the component instead of a party trick.

Follow-ups

"Why debounce and not throttle?"

Throttle guarantees a call every N ms while the input is active — for search that means firing on r, rea, react, and I only care about the last one. Debounce waits for the user to stop, which matches the intent: search when they're done typing. Throttle's for things where the intermediate values matter, like scroll position or drag.

"Why is the debounced value state? Isn't it derived from query?"

It's derived from query and the clock, and render can't read the clock. Deriving during render has to be synchronous and pure, so anything time- or async-dependent has to be stored. That's also why the fetch results are state and not a computed value.

"What if the user clears the input while a request is in flight?"

The effect re-runs with an empty debouncedQuery, so the cleanup fires and the old response gets ignored or aborted — same machinery as the race fix. Then I early-return before fetching and set status back to idle. The bug to avoid is letting the in-flight response land and repopulate a dropdown over an empty input.

"Where would you put the cache?"

A useRef(new Map()) for the interview — it survives re-renders and mutating it doesn't cause one, which is exactly right for a cache. If it needed to be shared between components I'd lift it to a module-level Map or context, and in a real app I'd just use React Query, which is this whole guide plus cache invalidation.

"Why the lazy initialiser in useLocalStorage?"

useState(expensiveThing()) evaluates on every render and discards the value after the first; useState(() => expensiveThing()) runs once on mount. Reading and parsing localStorage sixty times a second during typing is a real cost, and it's a one-character fix.

Cheat sheet

  • Shape: query, debouncedQuery, results, status. Write it as a comment first.
  • One status string, never isLoading + isError + hasSearched.
  • Debounced value is state because it depends on time — the one legitimate exception to "don't store what you can compute."
  • Effect keys on debouncedQuery, input stays instant on query.
  • Race condition is the point of the question. Bring it up before they do.
  • let ignore = false + return () => { ignore = true } — five lines, always works. AbortController when it's fetch.
  • clearTimeout in the cleanup is the debounce.
  • Upgrades, by name: activeIndex pointer for keyboard nav · click-outside via ref + mousedown · Map in a ref for cache · min length · combobox roles.
  • useLocalStorage: lazy init, try/catch both ways, write in an effect, doesn't sync across tabs unless you listen to storage.
