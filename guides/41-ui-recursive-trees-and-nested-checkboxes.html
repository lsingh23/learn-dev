The word "nested" and what it means

Here's the failure mode I've watched more than once. Candidate gets "build a file explorer", looks at the sample JSON, sees folders inside folders, and writes a .map(). Then inside it, another .map(). Then a third, with a sad little {child.children && ...}. Around the fourth level they realise the data can go deeper than their code can, and there's no fix that isn't a rewrite.

So what's the shape of a thing that can be arbitrarily deep, where you don't know the depth in advance?

A component that renders itself. That's it. That's the whole trick. The data is recursive — a node contains nodes — so the render is recursive too. Node renders a row, then renders a Node for each child, and the structure of your code stops caring how deep the tree goes.

I'll admit it feels strange the first few times. Recursion in a function returning a number is fine; recursion in JSX looks like you've done something illegal. You haven't. A component is just a function, and functions can call themselves. Once that clicks, this whole family of questions collapses into one small component and a couple of state decisions.

Say this in the first thirty seconds

"The data's recursive, so I'll write one Node component that renders itself for each child. Let me pin down the data shape first."

Data shape first, before state

Guide 34 says state shape comes before JSX. Trees are the one family where something comes before that: the data shape. Get it wrong and every function you write afterwards is wrong with it.

// the shape everything below assumes
type Node = {
  id: string;
  name: string;
  children?: Node[];   // absent or [] → it's a leaf
};

Now the clarifying question, and it's a genuinely good one: "Am I given a nested tree already, or a flat list with parentId that I need to build into one?" Real APIs return the flat version constantly, and interviewers hand it to you as a curveball about fifteen minutes in.

Have this in your fingers. Two passes, one Map:

✅ flat list → tree, O(n)
function buildTree(rows) {
  const byId = new Map();
  for (const row of rows) byId.set(row.id, { ...row, children: [] });

  const roots = [];
  for (const row of rows) {
    const node = byId.get(row.id);
    if (row.parentId == null) roots.push(node);
    else byId.get(row.parentId)?.children.push(node); // 👈 ?. survives orphans
  }
  return roots;
}

Two passes, not one, because a child can appear in the array before its parent does. First pass creates every node so the second pass can always find the parent. Say that out loud — it's the only interesting line of reasoning in the function.

The component that renders itself

Static render, no handlers yet, exactly as the method says:

function Node({ node, depth = 0 }) {
  const isFolder = node.children?.length > 0;

  return (
    <li style={{ paddingLeft: depth * 16 }}>
      <span>{isFolder ? '📁' : '📄'} {node.name}</span>
      {isFolder && (
        <ul>
          {node.children.map(c => (
            <Node key={c.id} node={c} depth={depth + 1} />  // 👈 itself
          ))}
        </ul>
      )}
    </li>
  );
}

The base case is isFolder === false. A leaf renders its row and returns — nothing recurses, and the recursion terminates. This matters more than it looks: if there's no base case, or the data has a cycle (a node that's its own ancestor), you get an infinite render loop and the tab dies. If the data comes from a server you don't control, that's a real answer to give.

depth as a prop is the simplest indentation. The alternative is pure CSS — nested <ul> with padding-left: 16px — which is arguably nicer because the DOM nesting already encodes the depth. Either is fine; having a reason for the one you picked is the point.

Expand/collapse: where does that state live?

This is the real decision in the file-explorer version, and it's worth a beat because there are two defensible answers.

✅ Version 1: local state, inside each node
function Node({ node, depth = 0 }) {
  const [open, setOpen] = useState(false);   // each node owns its own
  ...
  <button onClick={() => setOpen(o => !o)}>{open ? '▾' : '▸'}</button>
  {open && isFolder && ( ...children... )}
}

Dead simple. Every node manages itself, there's no bookkeeping, and it's about four lines. It also has a genuinely nice property: collapsed subtrees aren't rendered at all, so a huge tree costs you nothing until you open it.

The limit: the root has no idea what's open, so "collapse all" is impossible. Same for persisting the open folders to localStorage or a URL, or expanding to reveal a search hit.

✅ Version 2: one lifted Set at the root
const [expanded, setExpanded] = useState(new Set());  // the "set" shape from guide 34

const toggle = (id) => setExpanded(prev => {
  const next = new Set(prev);
  next.has(id) ? next.delete(id) : next.add(id);
  return next;                                 // 👈 new Set, or React won't re-render
});

Now collapseAll is setExpanded(new Set()) and expandAll is a walk that collects every folder id. You pass expanded and toggle down through Node (or via context if the prop drilling annoys you).

Build version 1. Then say the sentence: "I'd lift this into a Set of expanded ids at the root if we needed collapse-all or persisted state." That one line tells them you know both options and chose deliberately, which is the difference between "wrote a tree" and "reasoned about a tree".

Nested comments — same thing, different chrome

Structurally identical: {id, author, text, replies: Comment[]}, one Comment component rendering itself over replies. The only new things are UI concerns.

A reply box is local state (const [replying, setReplying] = useState(false)) and an onReply(parentId, text) callback threaded down to the root, which owns the comment list. Collapsing a thread is exactly the expand/collapse above. And real products cap the indentation, because level 12 is a two-character-wide column:

const MAX_INDENT = 4;
const pad = Math.min(depth, MAX_INDENT) * 20;  // nest forever, indent up to 4

Mention that cap unprompted. It's a two-second remark that says you've shipped a comment thread and not just implemented one.

Nested checkboxes, the hard one

This is where the interesting question lives, and the crux is one sentence:

The whole question

A parent's checkbox isn't state. It's derived from its descendants. All checked → checked. None checked → unchecked. Some → indeterminate.

Which is just "if you can compute it, don't store it" wearing a hat. The tempting shape — a checked boolean on every node — means every single click starts a sync job: walk down setting descendants, walk up recomputing ancestors, and hope you didn't miss a branch. You will miss a branch.

✅ Store leaves only, derive everything else
const [checkedLeaves, setCheckedLeaves] = useState(new Set()); // leaf ids only

function statusOf(node) {                       // → 'all' | 'none' | 'some'
  if (!node.children?.length)
    return checkedLeaves.has(node.id) ? 'all' : 'none';
  const kids = node.children.map(statusOf);
  if (kids.every(s => s === 'all'))  return 'all';
  if (kids.every(s => s === 'none')) return 'none';
  return 'some';
}

Every parent's appearance now falls out of one recursive read, and it cannot ever disagree with the leaves, because there's nothing to disagree with. Checking the last unchecked sibling flips the parent for free — you didn't write code for that, it's just what every returns.

The trivia they're fishing for

There is no indeterminate HTML attribute. It's a DOM property only — you cannot write <input indeterminate> in JSX and have anything happen. So it has to be set imperatively, through a ref, after render:

const ref = useRef(null);
useEffect(() => {
  ref.current.indeterminate = status === 'some';
}, [status]);

<input type="checkbox" ref={ref}
       checked={status === 'all'} onChange={toggle} />

Note that checked stays a normal controlled prop; indeterminate is purely visual and rides on top. Knowing this cold is a small, specific, very gradeable win.

Checking a parent

The only write path: toggling a node sets all its leaf descendants at once.

function leafIds(node, out = []) {
  if (!node.children?.length) out.push(node.id);
  else node.children.forEach(c => leafIds(c, out));
  return out;                                  // same base case as the render
}

function toggle(node) {
  const ids = leafIds(node);
  const turningOn = statusOf(node) !== 'all';  // 'some' also means turn on
  setCheckedLeaves(prev => {
    const next = new Set(prev);
    ids.forEach(id => turningOn ? next.add(id) : next.delete(id));
    return next;
  });
}

That's the entire interaction model. One downward walk to write, one upward derivation to read, and no synchronisation anywhere. Decide the 'some' case out loud — I turn everything on, which is what Gmail and every file picker does — because it's the one behaviour question the interviewer actually cares about.

Performance, briefly

Every toggle re-renders the whole tree, and at interview scale — dozens or hundreds of nodes — that is completely fine, so don't pre-optimise it. If they push to thousands, the answer is: memoise Node with React.memo so untouched subtrees skip re-render, memoise the status computation, and past that stop rendering the tree as a tree — flatten the visible (expanded) nodes into a single array and virtualise it, which is what VS Code's explorer does.

Follow-ups, with answers

"How deep can this go before it breaks?"

Recursion depth is bounded by the JS call stack, so a few thousand levels — far beyond any real tree. The realistic failures are a cycle in the data, which loops forever, and rendering too many nodes at once. I'd guard with a depth cap and a visited Set if the data came from an untrusted source.

"How would you add collapse-all?"

That's the trigger to lift the expand state. Local useState per node can't be reached from the root, so I'd move to expanded: Set<id> at the top and pass a toggle down. Then collapse-all is setExpanded(new Set()) and expand-all is one walk collecting folder ids.

"Why is indeterminate special?"

Because it's a DOM property with no HTML attribute — React can't set it declaratively. You need a ref plus an effect. It's also purely cosmetic: the checkbox's actual value is still just checked or unchecked.

"How do you build a tree from a flat list?"

Two passes. First, put every row into a Map by id with an empty children array. Second, walk again and push each node into its parent's children, collecting the ones with no parent as roots. Two passes because a child can appear before its parent. O(n).

"Where should the checked state live?"

One Set of leaf ids at the root. Parent states are derived — all/none/some — so they can never drift. Storing a boolean on every node means syncing up and down on every click, which is where the bugs come from.

Cheat sheet

  • "Nested" → a component that renders itself. Recursive data, recursive component. Never nested .map()s.
  • Data shape before state shape: {id, name, children?}.
  • Ask: nested tree already, or flat list with parentId? Know the two-pass Map build.
  • Base case = no children. No base case, or a cycle, is an infinite render.
  • Expand state: local useState per node first, lift to a Set of ids the moment you need collapse-all or persistence — and say so.
  • Nested comments are the same component plus a reply box and an indent cap around level 4.
  • Checkboxes: store leaf ids in a Set, derive every parent. all / none / some.
  • indeterminate is a DOM property, not an attribute — set it in an effect via a ref.
  • Toggling a node writes all its leaf descendants; 'some' toggles on.
  • Don't optimise. At thousands of nodes: memo, then flatten + virtualise.
