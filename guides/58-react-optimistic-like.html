58. Like Button with Optimistic Update

Paint the result before the server confirms it — and undo cleanly when it lies.

The ask

Interviewer “Build a like button. It should feel instant — don’t make me wait for the network — but if the request fails, put it back the way it was and tell me.”

Update the UI first, ask the server after, roll back if it fails.

What we're building

Three states of one button
1 · Unliked
🤍 Like · 128

Idle. Click me.

2 · Liked instantly
❤️ Liked · 129

0 ms. Request still in flight.

3 · Rolled back
🤍 Like · 128
Couldn’t save your like. Try again.

↑ heart, label and count move together — they are one piece of truth, never three.

It should:

  • Flip heart + count on click, instantly
  • Send the request in the background
  • Restore the old value on failure
  • Show a message when it rolls back
  • Survive rapid double-clicks
  • Be a real toggle button for screen readers

The mental model

Pessimistic UI waits for the server, then paints. Optimistic UI paints the guess, then reconciles. The guess is right ~99% of the time, so you trade a rare rollback for always-instant feedback.

1 · SnapshotCopy the current liked and count.
2 · SetWrite the guessed value to state.
3 · AwaitFire the request, keep rendering.
4 · RestoreOn throw, write the snapshot back.
Snapshot, don’t un-flip “Just flip it back” breaks the moment clicks overlap or the server disagrees. The snapshot is the value that was actually on screen before this click — restoring it is always correct.

The shape of the state

// what the user sees right now — may be a guess
const [liked, setLiked] = useState(post.liked);
const [count, setCount] = useState(post.likeCount);

// rollback message; null = everything is fine
const [error, setError] = useState(null);

// a ref — a box that survives re-renders.
// holds a ticket number for the newest click.
const latest = useRef(0);

Rule of thumb: the snapshot is a local variable inside the handler, not state. It only needs to live as long as one request, so nothing should re-render because of it.

Build it in layers

In an interview Build L1 and L2 out loud first — that’s a working button in 90 seconds. Then say “want me to add the optimistic update and rollback?” and do L3. L4 only if there’s time.

L1 Static markup

The dumbest thing that renders. No state, no server.

function LikeButton() {
  return (
    <button className="like">
      <span>🤍</span> Like · 128
    </button>
  );
}

L2 Local toggle

Make it feel alive. Count and heart move together.

const [liked, setLiked] = useState(false);
const [count, setCount] = useState(128);

function toggle() {
  const next = !liked;
  setLiked(next);
  setCount(c => c + (next ? 1 : -1));   // updater form: safe under batching
}

<button className={liked ? "like on" : "like"}
        aria-pressed={liked} onClick={toggle}>
  {liked ? "❤️" : "🤍"} {liked ? "Liked" : "Like"} · {count}
</button>

L3 Optimistic + rollback

Snapshot, set, await, restore. This is the answer to the question.

async function toggle() {
  const snapshot = { liked, count };      // 1. remember
  const next = !liked;
  setLiked(next);                          // 2. paint the guess
  setCount(snapshot.count + (next ? 1 : -1));
  setError(null);

  try {
    await api.setLike(postId, next);       // 3. ask
  } catch {
    setLiked(snapshot.liked);              // 4. put it back
    setCount(snapshot.count);
    setError("Couldn't save your like.");
  }
}

L4 Survive rapid clicks

Give each click a ticket. Only the newest ticket is allowed to touch state.

const id = ++latest.current;               // this click's ticket
try {
  await api.setLike(postId, next);
  if (id !== latest.current) return;       // a newer click already won
} catch {
  if (id !== latest.current) return;       // stale failure — ignore it
  setLiked(snapshot.liked);
  setCount(snapshot.count);
  setError("Couldn't save your like.");
}

Simpler alternative: disabled={pending}. Cheap, but it makes a fast tapper feel blocked. Say you know both; last-click-wins is the nicer UX.

The whole thing

import { useState, useRef } from "react";

export default function LikeButton({ postId, initialLiked, initialCount }) {
  const [liked, setLiked] = useState(initialLiked);
  const [count, setCount] = useState(initialCount);
  const [error, setError] = useState(null);
  const latest = useRef(0);

  async function toggle() {
    const snapshot = { liked, count };
    const next = !liked;
    const id = ++latest.current;

    setLiked(next);
    setCount(snapshot.count + (next ? 1 : -1));
    setError(null);

    try {
      await api.setLike(postId, next);
      if (id !== latest.current) return;          // stale success
    } catch {
      if (id !== latest.current) return;          // stale failure
      setLiked(snapshot.liked);
      setCount(snapshot.count);
      setError("Couldn't save your like. Try again.");
    }
  }

  return (
    <div>
      <button
        className={liked ? "like on" : "like"}
        aria-pressed={liked}
        aria-label={liked ? "Unlike" : "Like"}
        onClick={toggle}
      >
        <span aria-hidden="true">{liked ? "❤️" : "🤍"}</span>
        {liked ? "Liked" : "Like"} · {count}
      </button>

      {error && <p role="status" className="toast">{error}</p>}
    </div>
  );
}

Styling barely matters here — logic and rollback are what’s scored.

Gotchas

Rolling back by flipping, not restoring. setLiked(l => !l) in the catch can land on the wrong value after a second click. Write the snapshot.
Reading count inside setCount(c => …) for the optimistic bump, then restoring a stale number. Derive both from the same snapshot so the pair can never disagree.
Silent rollback. The heart quietly un-fills and the user thinks the app is broken. Always pair a rollback with a role="status" message.
No stale-response guard. Click 5 times fast, five requests race, the slowest one lands last and sets the wrong state. Ticket number, or disable while pending.
Fake button. A <div onClick> isn’t focusable or keyboard-operable. Use <button> with aria-pressed.

If they push

“Do it the React 19 way.” useOptimistic holds a temporary value that auto-reverts when the action settles — no manual snapshot. 
const [optimisticLiked, setOptimisticLiked] = useOptimistic(liked);

async function toggle() {
  setOptimisticLiked(!liked);       // shown until the action ends
  await api.setLike(postId, !liked);
  setLiked(!liked);                  // on throw, React reverts for you
}
Must be called inside a transition or a form action.
“5 clicks shouldn’t be 5 requests.” Keep the UI instant, debounce only the network: on each click reset a 400ms timer, and send the final value once it fires. Net effect: 5 clicks → 1 request carrying the last state.
“What if they’re offline?” Push the intent onto a queue in localStorage, keep the optimistic UI, and flush on the online event. Send the desired state (liked: true), never a “toggle” — replaying a toggle twice inverts it.
“How does React Query do this?” Same four steps, named: 
useMutation({
  mutationFn: setLike,
  onMutate: async (next) => {
    await qc.cancelQueries({ queryKey: ["post", id] });
    const prev = qc.getQueryData(["post", id]);       // snapshot
    qc.setQueryData(["post", id], p => ({ ...p, liked: next }));
    return { prev };                                  // → context
  },
  onError: (e, next, ctx) => qc.setQueryData(["post", id], ctx.prev),
  onSettled: () => qc.invalidateQueries({ queryKey: ["post", id] }),
});
cancelQueries matters: an in-flight refetch would otherwise overwrite your guess.
“Many buttons on a feed?” Keep truth in one cache keyed by post id and let each button read its own entry, so two views of the same post can’t drift apart.

Say this out loud

  • “Optimistic just means: paint the guess now, ask the server after, undo if it says no.”
  • “I’ll snapshot the previous liked and count in a local variable — not state, it only lives for one request.”
  • “Count and liked are derived from the same snapshot, so they can never disagree.”
  • “Rapid clicks race, so I’ll tag each request and let only the newest one write state.”
  • “If it rolls back I show a status message — I don’t want to silently lie to the user.”
  • “It’s a real button with aria-pressed, so screen readers announce it as a toggle.”
