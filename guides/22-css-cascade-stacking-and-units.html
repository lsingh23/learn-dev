Why isn't my CSS applying?

You wrote a rule. It's right there in the stylesheet. You open DevTools and there it is in the Styles panel — with a line through it. Struck out. Ignored.

Everybody who writes CSS has had this moment, usually followed by adding !important, seeing it work, and feeling a small pang of shame. I want to replace that pang with actual understanding, because once you can predict which rule wins, CSS stops feeling arbitrary.

Here's the thing that trips people up: almost everyone thinks the answer is "specificity." And specificity is part of it — but it's the third tiebreaker, not the first. If you start reasoning at step three you'll get the wrong answer whenever steps one or two were the real decider.

So let's build the whole ladder, in order.

The browser's job is to answer one question, over and over, millions of times: for this element, for this specific property (say color), which of the declarations that mention it wins? Notice how narrow that question is. It's per-element and per-property. An element can take its color from one rule and its background from a completely different rule. There's no "winning rule" — there are only winning declarations.

A common misconception

"The more specific rule replaces the less specific rule." No — nothing gets replaced. Every matching declaration is collected into a big pile, and then each property is resolved independently. If a low-specificity rule sets padding and a high-specificity rule only sets color, that padding still applies. The high-specificity rule didn't beat it; they weren't even competing.

The pile-sorting happens in this order. The browser walks down the list and stops the moment it finds a difference:

1Origin & importance — who wrote this declaration (browser, user, you), and did they mark it !important?
2Cascade layers — @layer, if you're using it (we'll get there).
3Specificity — how precisely does the selector describe the element?
4Source order — last one written wins.

Let's take these one at a time, and I promise not to move on until each is genuinely clear.

Step 1: origin and importance

Before your CSS ever runs, the browser already has opinions. <h1> is big and bold. Links are blue and underlined. Lists have bullets and indentation. Nobody wrote that in your project — it comes from the user-agent stylesheet, a stylesheet baked into the browser itself.

There are three origins a declaration can come from:

  • User agent — the browser's built-in defaults.
  • User — styles the human viewing the page has set for themselves. Rare on desktop these days, but real: browser extensions, OS-level accessibility settings, custom stylesheets. This is the person who has, say, forced a minimum font size because they can't read 12px text.
  • Author — you. Your stylesheets, your <style> tags, your inline styles.

Normally the order of power is exactly what you'd guess:

author > user > user-agent

Which is why setting h1 { font-size: 1rem } works — you beat the browser's default. Good. Sensible.

Now here's the bit that's genuinely surprising, and it's a great interview detail because most candidates don't know it. !important doesn't just make a declaration stronger. It flips the origin order upside down.

The full order, weakest to strongest:

RankOriginImportance
1 (weakest)User agentnormal
2Usernormal
3Authornormal
4Author!important
5User!important
6 (strongest)User agent!important

Look at what happened. In the normal half, the author is on top. In the important half, the author is on the bottom — a user's !important beats an author's !important.

Why on earth would the spec do that? Because it's an accessibility guarantee. If a user with low vision writes * { font-size: 20px !important } in their personal stylesheet, no website should be able to override it. !important in the user origin means "I really mean it, and I outrank the site." The whole inversion exists to protect the person actually looking at the page. Once you see that, it stops being a weird spec quirk and becomes obviously correct.

Under the hood

There are a couple more origins in the real spec — transitions sit above everything (so a mid-transition value wins while it's animating), and animations sit between author-normal and author-important. That's why a running @keyframes animation can beat a normal rule but a well-placed !important can beat the animation. You almost never need this, but it explains the occasional "why won't my animation take effect" mystery.

Where inline styles fit

An inline style="..." attribute is still the author origin — it's just extremely specific, which we'll get to in a second. It is not a separate origin, and it loses to !important in a stylesheet. That surprises people:

<!-- the paragraph is red, not blue -->
<p style="color: blue">Hello</p>

p { color: red !important; } /* 👈 this wins */

Step 2: specificity (the tuple, not the number)

OK. Two declarations, same origin, both normal, both fighting over color. Now — and only now — we compare selectors.

Specificity is the browser asking: how precisely does this selector describe the element? A selector that could match half the page should lose to one that could only ever match one element. That's the intuition, and the scoring system is just a formalisation of it.

Every selector gets scored into three buckets. I'll write them as a tuple, (A, B, C):

BucketCountsExamples
A — IDsID selectors#checkout
B — classesclasses, attribute selectors, pseudo-classes.btn, [disabled], :hover, :nth-child(2)
C — elementstype selectors, pseudo-elementsdiv, a, ::before

Some people write it as four buckets, (inline, A, B, C), with inline styles occupying a bucket of their own to the left of IDs. Both framings are fine — the spec technically calls inline styles a separate step, but "inline styles beat everything selector-based" is the practical takeaway either way. I'll stick with three buckets and treat inline as "off the top of the scale."

Let's score some real selectors:

p                          → (0, 0, 1)
.card                      → (0, 1, 0)
.card p                    → (0, 1, 1)
nav ul li a:hover          → (0, 1, 4)   4 elements + :hover
#sidebar .card p           → (1, 1, 1)
a[href^="https"]           → (0, 1, 1)   attribute counts as a class
*                          → (0, 0, 0)   👈 the universal selector is free
.card > p + p               → (0, 1, 2)   combinators are free too

Two things worth pausing on. * scores zero — it adds nothing at all. And combinators (>, +, ~, and the space for descendant) also score zero. They change what the selector matches, but not how strongly. So .card p and .card > p have identical specificity, even though the second is "pickier" in an everyday sense. If both match, source order decides.

The comparison is left-to-right, and this is the whole point

Here's the question interviewers love: do eleven classes beat one ID?

/* Selector 1 */
.a.b.c.d.e.f.g.h.i.j.k  { color: red; }    → (0, 11, 0)

/* Selector 2 */
#title                    { color: blue; }   → (1,  0, 0)

Take a guess before you read on. If you're thinking in base 10 — "IDs are worth 100, classes are worth 10, so 11 classes = 110 > 100" — you'd say red.

It's blue. The ID wins. It would still win against a thousand classes.

The reason is that specificity is not a number. It's a tuple compared left-to-right, like version numbers or like sorting words alphabetically. You compare bucket A first. If there's a difference, you're done — buckets B and C are never even consulted. Only if A ties do you look at B; only if B ties do you look at C.

Think of it like comparing v2.0.0 against v1.99.99. Nobody argues that 99 minor versions add up to a major version. Same idea. Or, if you prefer something physical: it's a set of nested categories, like ranking army officers. A general outranks any number of sergeants. You don't get promoted to general by collecting sergeants.

A common misconception

You'll still see people teach specificity as "IDs = 100, classes = 10, elements = 1, add them up." That model gives the right answer most of the time, which is exactly what makes it dangerous — it fails silently at the boundary. Old CSS documentation really did describe it this way, and some very old browsers even implemented it that way. Modern browsers do not. If you say "add up the points" in an interview, a sharp interviewer will immediately ask the 11-classes question to see if you actually understand it. Say "tuple, compared left to right" and you've signalled you know the real model.

Pushing on the edges

Let's do a harder one. Which colour is the link?

<div id="page">
  <nav class="main-nav">
    <a class="link active" href="/">Home</a>
  </nav>
</div>

#page a                   { color: red; }     → (1, 0, 1)
.main-nav .link.active    { color: green; }   → (0, 3, 0)
nav a:hover               { color: blue; }    → (0, 1, 2)

Red, even while hovering. #page a has a 1 in the first bucket and the others have 0, so it wins before we look any further. This is the practical reason people say "avoid IDs in CSS": not because IDs are evil, but because a single ID selector creates a wall that no amount of sensible class-based CSS can climb, and the only ways over it are another ID or !important. You've painted yourself into a corner in exchange for basically nothing.

Step 3: source order

If two declarations have the same origin, the same importance, and the same specificity — the one that appears later in the source wins. That's it. That's the whole rule.

.btn { background: blue; }
.btn { background: green; }   /* 👈 green — it's later */

"Later" means later in the final concatenated order the browser sees: stylesheets are ordered by their <link> position in the HTML, and rules within a stylesheet by their position in the file. This is why "just move your override below the thing you're overriding" is often the correct, non-hacky fix — and why the order of your imports in a bundler can silently change your page's appearance.

It's also the reason for a classic bug. In CSS, :hover and :focus and :visited on a link all have the same specificity, so if you write a:hover before a:visited, visited links won't show a hover colour. Hence the old mnemonic LoVe HAte: :link, :visited, :hover, :active, in that order.

Wait — what about media queries?

A @media block adds no specificity. None. A rule inside a media query is exactly as specific as the same rule outside one. It wins purely by being later in the file. That's why your responsive override stops working the moment someone adds a more specific rule below it — and why putting all your media queries at the bottom of the file (or right after the rule they modify, if you're using a preprocessor) matters.

:not(), :is(), and the magic of :where()

These three functional pseudo-classes have specificity rules that seem fussy until you see the design intent behind them.

:is() takes a list of selectors and matches if any of them match. It's a shorthand: :is(h1, h2, h3) > p instead of writing three rules. Its specificity is the specificity of its most specific argument.

:is(#header, .nav) a     → (1, 0, 1)  the #header dominates, even
                             when it actually matched via .nav

That last part is the gotcha: the score is computed from the selector list, not from which branch actually matched. So one ID inside an :is() poisons the whole thing.

:not() works the same way — it takes the specificity of its most specific argument. And crucially, :not() itself contributes nothing; only its contents do.

.btn:not(.disabled)       → (0, 2, 0)  .btn + .disabled
p:not(#intro)             → (1, 0, 1)  ouch

And then there's :where(), which is identical to :is() in what it matches, with one difference that changes everything: :where() always has zero specificity. Whatever you put inside it contributes nothing at all.

:where(#header, .nav) a   → (0, 0, 1)  only the `a` counts

Why is that so useful? Imagine you're writing a component library, or the base styles for a design system. You want to say "links inside my card component are unstyled" — but you absolutely do not want your defaults to be hard for consumers to override. If you write:

❌ Hard to override
.card .content a { color: inherit; }   → (0, 2, 1)

…then a consumer who writes .my-link { color: red } — a perfectly reasonable, single-class selector — gets nothing. They have to escalate. They'll write .card .content .my-link, or give up and use !important, and now your library has made their codebase worse.

✅ Trivially overridable
:where(.card .content) a { color: inherit; }   → (0, 0, 1)

Now your default is as weak as a bare element selector. Any single class the consumer writes beats it. You've expressed "this is a default, not a decision" in the language of the cascade itself. That's the whole point of :where(), and it's a genuinely great thing to bring up in an interview because it shows you think about CSS as an API other people consume.

Under the hood

A neat trick that falls out of this: :where() is a clean way to lower the specificity of any selector you're stuck with. Need #legacy-widget in a selector but don't want the ID weight? :where(#legacy-widget) .thing gives you the match without the (1,0,0).

Inheritance is not the cascade

These two get conflated constantly, and keeping them separate will save you real debugging time.

The cascade answers: this element has several declarations competing for one property — which wins?

Inheritance answers: this element has no declaration for a property at all — now what?

Only when nothing in the cascade produced a value does inheritance kick in. And it only applies to inherited properties — a fixed list that's roughly "things about text": color, font-family, font-size, line-height, letter-spacing, text-align, visibility, cursor, list-style. Box-ish properties (border, padding, background, width, display) do not inherit, because inheriting them would be chaos — imagine every descendant of a bordered box getting its own border.

Here's the failure this distinction explains:

<div class="sidebar">
  <p>Some text</p>
</div>

#page .sidebar { color: red; }    /* (1,1,0) — super specific! */
p             { color: blue; }   /* (0,0,1) — barely anything */

The paragraph is blue. Not red. Take a moment with that, because it feels wrong.

The reason: those two rules were never competing. #page .sidebar targets the div, not the paragraph. For the paragraph, the cascade found exactly one declaration — p { color: blue } — and it won by default. Inheritance never even ran, because inheritance is the fallback for when the cascade comes up empty, and it didn't.

The rule to carry around: a directly-targeted declaration always beats an inherited value, no matter how weak the direct selector or how specific the ancestor's. Inherited values are the weakest thing in CSS. They lose to everything, including the user-agent stylesheet.

Wait — so why don't links inherit my body colour?

Exactly this. You set body { color: #333 } and every paragraph obeys, but links stay blue. That's because the user-agent stylesheet has a real declaration, a:-webkit-any-link { color: -webkit-link }, directly targeting the anchor. A direct declaration — even one from the weakest origin there is — beats an inherited value. To fix it you need to target the link yourself: a { color: inherit }, which explicitly asks for the inherited value.

Which brings up the four global keywords, all of which work on any property:

  • inherit — take the parent's computed value, even for a non-inherited property.
  • initial — reset to the property's spec default (note: display: initial is inline, not "whatever it was" — this catches people).
  • unset — behave like inherit if the property inherits, initial if it doesn't.
  • revert — roll back to what the previous origin said, i.e. the user-agent style. This is the one you usually actually want when "un-styling" something.

!important and the escape ladder

So why is !important treated as a code smell rather than just another tool?

Because it's not a level — it's a second, parallel cascade. Once you have two !important declarations, all the normal rules resume inside the important tier: specificity, then source order. So the person who needs to override your !important has exactly one move available, which is another !important with higher specificity. And then the next person needs one with higher specificity than that. It's an escalation ladder with no top rung, and every step makes the stylesheet harder to reason about for everyone who comes after.

The deeper problem: !important usually isn't fixing a cascade problem, it's hiding one. The real issue is normally "our selectors are too specific" or "these two stylesheets load in an order nobody controls."

The escape ladder — try these in order

When a style isn't applying and you're tempted to reach for !important, walk down this list. Stop at the first one that works.

  1. Actually read DevTools. Is the rule struck out (lost the cascade), or not listed at all (selector doesn't match / syntax error / the file didn't load)? These are completely different bugs and people misdiagnose them constantly. A typo'd property name silently kills only that line; a typo'd selector kills the whole block.
  2. Move the rule later. If specificity is tied, source order settles it. Free fix.
  3. Match the specificity, don't exceed it. If the winning rule is .card .title, write a selector that's also (0,2,0) and put it after. Now you're a peer, not an escalation.
  4. Lower the other rule instead. Often the honest fix. Wrap the over-specific ancestor part in :where() and the whole fight evaporates.
  5. Use @layer to declare, once and explicitly, which bucket of CSS outranks which. More on this next.
  6. Now consider !important — and if you do, leave a comment saying why.

When !important is actually the right call

There are legitimate uses, and knowing them is a good interview signal because it shows judgement rather than dogma:

  • Overriding third-party CSS you don't control — a widget, a payment iframe wrapper, an old plugin that ships !important itself. You're not in a cascade you can restructure.
  • Utility classes with one job. .sr-only (visually hidden for screen readers) or .hidden { display: none !important } — the entire point of the class is "this wins, always, regardless of context." Tailwind ships an !important mode for exactly this reason.
  • User stylesheets and accessibility overrides — the case the spec was literally designed for.
  • A firebreak in a crisis, with a ticket filed. Sometimes prod is broken at 4pm and honesty beats purity. Just write the comment.

@layer: the modern answer to specificity wars

Here's the structural problem @layer solves. You have reset styles, then a design system, then component styles, then page-specific overrides. You want them to win in that order, always. But the cascade doesn't know about your architecture — it only sees selectors. So a reset written as ul li can beat a component written as .menu-item, purely by accident, and you spend your afternoon on it.

Cascade layers let you declare that ordering explicitly, and layer order is checked before specificity. That's the key sentence.

/* declare the order once, up top — this line alone sets priority */
@layer reset, base, components, utilities;

@layer reset {
  #main ul li { margin: 0; }      /* (1,0,3) — enormous */
}

@layer components {
  .menu-item { margin: 8px; }      /* (0,1,0) — tiny, and it WINS */
}

The tiny class beats the ID selector, because components is a later layer than reset and layer order is consulted first. Specificity only breaks ties within a layer.

Two more things worth knowing. Unlayered CSS is stronger than any layer — it sits at the top, above all of them. That's deliberate: you can drop a third-party stylesheet into a low-priority layer with @import url(vendor.css) layer(vendor), and all your own ordinary CSS automatically outranks it without a single !important. That one trick alone justifies the feature.

And the inversion again: inside the !important tier, layer order reverses. An !important in an earlier layer beats an !important in a later one. It's the same protective logic as the user/author flip — the low-priority layer gets to say "no, I really mean this one."

Why Tailwind and CSS-in-JS exist

Before we leave the cascade, one thought that reframes a lot of tooling arguments — and it's a great thing to have ready, because it makes you sound like you've reasoned about the tools rather than picked a side.

The cascade is a brilliant design for documents: a few stylesheets, a few authors, global inheritance as a feature. It gets hard when hundreds of components by dozens of people share one global namespace and one flat ordering. Three pains show up: everything is global (name a class .card and you may have restyled another team's feature); specificity is a ratchet (the only reliable override is to be more specific, so it only ever climbs); and nothing can safely be deleted, because nobody can prove .legacy-promo-banner is unused.

Every modern styling approach is an answer to those three. Tailwind flattens the cascade — one declaration per class, all the same specificity, so it never has to arbitrate. CSS Modules and CSS-in-JS generate the names at build time, so collisions become impossible by construction. Same underlying question: how do we get module boundaries into a language that doesn't have them?

We compare them properly, tradeoffs and all, near the end of the guide.

In an interview

How this gets asked: "Walk me through how the browser decides which CSS rule applies." · "What's specificity?" · "Does an ID beat ten classes?" · "When would you use !important?"

Model answer — say this out loud

"The browser resolves each property independently, and it goes through a few steps in order. First origin and importance — browser defaults, then user styles, then author styles, with !important flipping that order so a user's important beats an author's. Then cascade layers if you're using @layer. Then specificity, which is a tuple of IDs, classes, and elements compared left to right — so one ID beats any number of classes, because it's not a base-10 sum. And if all of that ties, the last declaration in source order wins. I try to keep specificity flat and reach for :where() or @layer instead of !important."

Why it lands: you named the order and you knew specificity isn't step one. Most candidates start and end at specificity. Mentioning the !important origin inversion and @layer signals you've read the actual model rather than absorbed folklore.

Follow-ups:

"So does one ID beat ten classes?" Yes, always. Specificity is compared bucket by bucket from the left; the ID bucket differs, so the comparison stops there and the class bucket is never read. It's like version numbers — 2.0.0 beats 1.99.99.

"Why not just use !important when you're in a hurry?" Because it isn't a level, it's a parallel cascade. The only way anyone can override it later is another !important, so you've handed the next person a worse problem than the one you had. I'd try source order, matching specificity, or wrapping the offending selector in :where() first. I would use it for a genuine always-wins utility like .sr-only or to beat third-party CSS I don't control.

"My rule has higher specificity than the parent's but the child still isn't red — why?" Probably because they were never competing. Specificity only compares declarations targeting the same element. An inherited value loses to any direct declaration on the child, however weak — even the browser's own default. That's the cascade-versus-inheritance distinction.

"Does a media query add specificity?" No. Zero. It wins only by being later in the source, which is why a stray rule added below your breakpoint block can silently break responsive styles.

"What's :where() for?" Zero specificity. It's how you ship defaults in a library that consumers can override with a single plain class, instead of forcing them into an escalation war.

Trap: saying "IDs are 100 points, classes are 10." It's the folklore version, it's wrong at the boundary, and it's the exact thing the ten-classes question is designed to catch.

Stacking contexts and z-index

Time for the single most infuriating bug in frontend, the one I guarantee you will hit in real work: the modal that renders behind the header.

You've built a nice modal. It's position: fixed, it covers the screen, and you gave it z-index: 9999 because obviously that's higher than anything else on the page. And it renders behind the site header, which has z-index: 10.

You bump it to z-index: 999999. Still behind. You add more nines. Nothing changes. At this point the natural conclusion is "z-index is broken," and honestly, that's a reasonable thing to think — until you learn the one concept that explains it.

First: z-index doesn't work on everything

Before the big idea, clear a smaller misconception out of the way. z-index is ignored entirely on statically positioned elements. If an element has position: static (the default — i.e. you never set position), then z-index: 500 does literally nothing. The browser doesn't warn you. It just quietly discards it.

❌ z-index silently ignored
.tooltip { z-index: 100; }   /* no position → no effect */
✅ z-index applies
.tooltip { position: relative; z-index: 100; }

The one exception worth memorising: flex and grid children can use z-index without being positioned. A direct child of a display: flex or display: grid container honours z-index even when it's position: static. That's a genuinely useful little fact and a nice thing to know in an interview.

Now the big idea: a stacking context is a sealed box

Here's the mental model that makes all of this click.

Certain CSS properties cause an element to create a stacking context. Think of it as putting that element and everything inside it into a sealed, opaque box. Once something is in that box:

  • Its children can be layered relative to each other, freely, with any z-index values you like.
  • But the entire box is placed into its parent's layering as a single unit, at the box's own z-index.
  • Nothing inside the box can ever escape it. Not with z-index: 999999. Not with anything.

The analogy I like: it's a stack of numbered envelopes. Inside envelope #1 you can arrange a hundred sheets of paper in any order you want — page 999 on top of page 1, sure. But envelope #1 sits underneath envelope #2 in the pile, and no sheet of paper inside envelope #1 can rise above envelope #2, because it's inside an envelope. Its ordering only ever applies to its siblings in the same envelope.

(Where the analogy breaks down: envelopes are opaque, and stacking contexts are usually visually transparent — you can see through them fine. It's only the ordering that's sealed, not the pixels.)

Let's see it happen.

Green is stuck under red, despite its absurd z-index. Blue created a stacking context (it's positioned and has a z-index), sealing green inside it. The whole blue box sits at layer 1, and red's layer 2 covers it.

Now blue has z-index: auto, so it no longer creates a stacking context. Green is promoted into the page's stacking context, where it competes directly with red — and 999999 beats 2. Nothing about green changed. We only changed its parent.

Read that last sentence again, because it's the whole lesson: we fixed the child's layering by changing the parent. Nothing about the green element was wrong. The problem was never where you were looking.

This is exactly the modal bug. Your modal has z-index: 9999, but it's rendered inside some component — a card, a sidebar, a .page-content wrapper — that itself creates a stacking context with a low z-index. The modal is sealed inside that envelope. The header sits in a higher envelope. Adding nines is like writing a bigger number on a sheet of paper inside a sealed envelope and hoping the mail sorter notices.

What creates a stacking context?

This is the list that turns "z-index is haunted" into "oh, it's that transform on line 40." Some of these are notorious for catching people out.

  • The root element (<html>). Always. Everything lives in this one.
  • position: relative | absolute with a z-index other than auto. The classic. Note both halves are required — positioned with z-index: auto does not create one.
  • position: fixed or position: sticky — these create one always, z-index or not.
  • opacity less than 1. Yes, opacity: 0.99 counts. This one has ruined many afternoons.
  • Any transform other than none — including transform: translateZ(0), the old "GPU hack."
  • filter, backdrop-filter other than none.
  • will-change naming any property that would itself create one (e.g. will-change: opacity or transform).
  • isolation: isolate — creates one and does nothing else. That's its entire job.
  • mix-blend-mode other than normal.
  • Flex/grid children with a z-index other than auto.
  • contain: paint | layout | strict | content, and content-visibility.
  • Plus a few rarer ones: perspective, clip-path, mask, view-transition-name.

Notice the pattern that ties most of these together. opacity, transform, filter, mix-blend-mode — every one of them is an effect the browser must apply to the element and all its descendants as a single composited image. To fade a card to 50%, the browser has to render the entire card-plus-contents into one buffer and then fade that buffer. It cannot do that if some descendant is allowed to jump out and paint on top of an unrelated element elsewhere on the page. Creating a stacking context isn't a quirk — it's the necessary consequence of "this subtree is rendered as one image."

That's what makes this bug so nasty: the property that broke your layering is invisible.

A common misconception

"z-index: 9999 always puts something on top." It puts something on top of its siblings within its own stacking context — and that's all it has ever meant. The number is meaningless outside that box. Two elements' z-indexes are only ever comparable if they live in the same stacking context. Comparing a z-index of 9999 in one context to 2 in another is like comparing a page number in one book to a page number in a different book.

Painting order within a context

Within a single stacking context, the browser paints back-to-front in a defined order. You don't need to recite all seven layers, but knowing the shape of it explains several everyday behaviours:

1The context root's background and borders
2Child stacking contexts with negative z-index
3Non-positioned block descendants (backgrounds, borders)
4Non-positioned floats
5Inline content — text, images in text flow
6Positioned elements with z-index: auto or 0
7Child stacking contexts with positive z-index (ascending)

Two useful consequences fall out of this list.

Text paints above block backgrounds by default. That's why z-index: -1 on a decorative pseudo-element usually works nicely: layer 2 sits above the context root's own background (layer 1) but below the text (layer 5). Your decoration slides in behind the words without hiding the parent's background.

…unless the parent creates a stacking context. If the parent has, say, a transform, then the parent is the context root — its background is layer 1, and your z-index: -1 child at layer 2 now sits above it. The decoration that was invisible behind the card suddenly covers it. Same code, different parent.

And equal z-index ties break by DOM order — later elements paint on top. So two elements with z-index: 1 layer by whichever comes last in the HTML. If you've ever "fixed" an overlap by moving a div lower in the markup, this is why.

isolation: isolate — the deliberate tool

Since all the usual stacking-context triggers are side effects of something else, we needed a way to create one on purpose. That's isolation: isolate. It creates a stacking context and changes nothing else — no visual effect, no layout effect, no performance cost worth mentioning.

Why would you want more sealed boxes when they're the source of all this pain? Because containment cuts both ways. When you're shipping a component, sealing it means its internal z-indexes are guaranteed not to leak out and fight with the rest of the page:

.comment-card {
  isolation: isolate;   /* 👈 internal z-indexes stay internal */
}
.comment-card__badge { position: absolute; z-index: 10; }

Now that z-index: 10 means "on top of things inside this card," full stop. It can't accidentally cover the site nav. You've made the component's layering a private implementation detail — the same instinct that makes you scope class names.

The older trick for this was transform: translateZ(0) or opacity: 0.999, which worked by accident and confused everyone reading the code. isolation: isolate says what it means.

So how do we actually fix the modal?

Three approaches, in increasing order of how much I like them.

1. Find and remove the trapping context. Open DevTools, walk up the DOM from your modal, and look at each ancestor for anything on the list above — a stray transform, an opacity, a filter, a position: relative; z-index: 1. Chrome's Layers panel and the "computed" tab help. Sometimes the fix is simply deleting a z-index that was never needed. This works, but it's fragile: the next person to add a hover animation with a transform to that wrapper re-breaks it, and they'll have no idea why.

2. Render the modal in a portal. This is the real fix, and it's why React has createPortal and Vue has <Teleport>. Keep the modal component where it belongs logically in your component tree — state, props, event handlers all unchanged — but render its DOM node as a direct child of <body>.

import { createPortal } from 'react-dom';

function Modal({ children }) {
  return createPortal(
    <div className="modal-overlay">{children}</div>,
    document.body            // 👈 escapes every ancestor context
  );
}

Because the node is now a child of <body>, there are no trapping ancestors left. Its z-index is compared against the header's in the root stacking context, where the comparison actually means something. This also fixes the sibling problem of overflow: hidden on an ancestor clipping your modal.

The native version of this idea is the <dialog> element opened with showModal(). It renders in the browser's top layer, which sits above the entire page regardless of stacking contexts or z-index — plus you get focus trapping, Escape-to-close, and inert background content for free. If you're building a modal today and don't need to support ancient browsers, start there.

3. Stop inventing z-index numbers. Whatever else you do, don't let 9999, 10000, and 99999999 accumulate in a codebase. Define the layers once and use names:

:root {
  --z-dropdown: 100;
  --z-sticky-header: 200;
  --z-modal-backdrop: 300;
  --z-modal: 310;
  --z-toast: 400;
}
.modal { z-index: var(--z-modal); }

Now "should this be above the header?" is a question with a documented answer instead of a game of numeric chicken.

Units: px, em, rem, %, vh, ch, clamp()

CSS has an intimidating number of length units, and the usual advice ("use rem!") is right but unmotivated. Let's build up the reasons, because the differences genuinely matter — one of these choices affects whether your site is usable by someone with poor eyesight.

px — and the surprise that it isn't a pixel

px feels like the simple one. It's a pixel. Sixteen pixels is sixteen pixels.

Except a CSS pixel has not corresponded to a physical device pixel for well over a decade. On a modern phone, one CSS pixel might be three device pixels wide. That's the device pixel ratio — window.devicePixelRatio tells you what it is on the current screen. And when you pinch-zoom, one CSS pixel becomes even more device pixels.

So what is a CSS pixel? It's an angular unit — roughly, the size that subtends a consistent visual angle at a typical viewing distance for that kind of device. The spec anchors it to 1/96th of an inch at arm's length. That's why 16px text looks about the same physical size on your laptop and on a phone held closer to your face, even though the phone has vastly more device pixels per inch. If it were a real device pixel, phone text would be microscopic.

The practical upshot: px is an absolute-within-CSS unit. Fixed, predictable, unaffected by font sizes. Which is great for some things and a genuine accessibility problem for others — coming up.

em — relative to the element's own font-size

1em equals the computed font-size of the element the property is on. If the element's font-size is 20px, then padding: 1em is 20px.

There's a wrinkle that catches everyone exactly once: when you use em in the font-size property itself, there's no font-size on this element yet to reference — so it resolves against the parent's font-size. For every other property, em uses the element's own.

.card       { font-size: 20px; }
.card .title {
  font-size: 1.5em;   /* 1.5 × 20px (parent)  = 30px */
  padding: 0.5em;     /* 0.5 × 30px (its own) = 15px */
}

That self-referential quality is em's superpower and its trap. Superpower first: a button whose padding, border-radius, and gap are all in em scales as one coherent unit when you change only its font-size. One property, whole component resizes proportionally. That's lovely, and it's the right tool for it.

The trap is compounding. Because em in font-size multiplies against the parent, nesting multiplies repeatedly:

A rule like li { font-size: 0.9em } looks completely harmless until someone builds a three-level nested menu. Then the deepest items are at 73% and nobody knows why.

rem — relative to the root, and why it's the accessible default

rem means "root em." 1rem is always the computed font-size of the <html> element, no matter how deeply nested you are. No compounding, ever. One reference point for the whole document.

By default the root font-size is 16px in every major browser, so 1rem = 16px, 1.5rem = 24px, 0.875rem = 14px.

Now the important part — why rem is the accessibility-friendly choice, because this is the bit interviewers care about.

In every browser's settings there's a default font size. Users change it. People with low vision set it to 20px or 24px; it's one of the most-used accessibility features on the web, far more common than screen readers. That setting is the root font-size.

So: if you size your text in rem, a user who sets their browser to 24px gets your whole type scale multiplied by 1.5. Everything grows, proportionally, exactly as they asked. If you size your text in px, their setting does nothing. Your 14px caption stays 14px, unreadable, and their only remaining option is page zoom — which scales layout too and often produces horizontal scrolling on a design that wasn't tested that way.

Wait — doesn't browser zoom scale px anyway?

It does, and that's why this gets muddled. Zoom scales everything including px. But zoom and the font-size preference are two different controls. Zoom magnifies the whole page (including your carefully-tuned layout); the font-size setting adjusts text and leaves layout proportions alone. Many users prefer the latter, and a fair number don't know zoom exists but did find the "make text bigger" setting. Using rem means you respect both. Using px means you only respect one.

A common misconception

"Set html { font-size: 62.5% } so 1rem = 10px and the maths is easier." This was popular for years and it's a bad idea: it hard-codes an assumption that the user's base is 16px, and it scales down anyone who deliberately raised theirs. It doesn't fully break accessibility — everything still scales proportionally from their base — but it shrinks your whole design by 37.5% relative to the size the user asked for, which is precisely the opposite of what they wanted. If the arithmetic bothers you, let a preprocessor or a custom property do the conversion.

% — the shape-shifter

Percentages are the least consistent unit in CSS, because a percentage means a different thing for every property. It's not one unit; it's a family of units that share a symbol.

Property% is relative to…
width, max-width, left, rightthe containing block's width
height, top, bottomthe containing block's height (and if that height is auto, a percentage height is generally ignored)
padding and margin — all four sidesthe containing block's width. Yes, including padding-top.
font-sizethe parent's font-size (so 150% ≡ 1.5em)
line-heightthe element's own font-size
transform: translate()the element's own size

That third row is the one that surprises people every time: vertical padding and margin percentages resolve against width, not height. padding-top: 50% gives you padding equal to half the container's width.

Weird? Absolutely. But it's the mechanism behind the classic aspect-ratio trick — padding-top: 56.25% makes a box that's always 16:9 regardless of width, which is how we did responsive video embeds for a decade. (These days just write aspect-ratio: 16 / 9. But the old trick explains the rule.)

The reason for the rule, incidentally, is circularity avoidance: a block's height usually depends on its contents, so if vertical padding depended on height, and height depended on contents plus padding, you'd have an equation that eats itself. Width is determined before content is laid out, so it's a safe reference.

And line-height has its own famous footgun. line-height: 150% and line-height: 1.5 look equivalent, and they're not:

.parent { font-size: 20px; line-height: 150%; }  /* computes to 30px NOW, */
.parent .small { font-size: 10px; }               /* child inherits 30px 😬 */

.parent { font-size: 20px; line-height: 1.5; }   /* the RATIO inherits, */
.parent .small { font-size: 10px; }               /* child computes 15px ✅ */

A percentage line-height is computed on the parent and the result inherits. A unitless one inherits as a multiplier and is recomputed per element. Always use unitless line-height.

vw, vh, and the mobile address bar

1vw is 1% of the viewport width; 1vh is 1% of the viewport height. vmin and vmax take the smaller and larger of the two, which is handy for things that should behave sensibly in both orientations.

Two catches with vw worth knowing. First, on desktop 100vw includes the classic scrollbar's width, so width: 100vw on a page that scrolls vertically causes a horizontal scrollbar. Second — the big one — vh on mobile has been a mess for years.

Here's the problem. On a phone, the browser's address bar hides when you scroll down and reappears when you scroll up. So the visible viewport height changes as you scroll. What should 100vh be?

If it tracked the real height, every scroll would resize 100vh elements, reflowing and juddering the entire page continuously. Unacceptable. So browsers made 100vh equal the largest possible viewport — the height with the address bar hidden — and kept it stable. Which means when the bar is showing, your "full height" hero is taller than the screen and its bottom edge, along with your call-to-action button, is cut off. Every developer has hit this and hacked around it with JavaScript setting a --vh custom property on resize.

The modern fix is a set of viewport units that name what they mean:

  • svh — small viewport height: as if the address bar is showing. The smallest it gets. Stable.
  • lvh — large viewport height: as if the bar is hidden. Same as the old vh. Stable.
  • dvh — dynamic: tracks the actual current height, live. Never clipped, but it can cause reflow as you scroll.
.hero {
  min-height: 100vh;    /* fallback for old browsers */
  min-height: 100dvh;   /* 👈 later, so it wins where supported */
}

That two-line pattern is worth remembering: a browser that doesn't understand dvh throws the second declaration away as invalid and keeps the first. Progressive enhancement, using nothing but the cascade's source-order rule. (There are svw/lvw/dvw too, but width rarely changes like this.)

My default: dvh for full-screen heroes and mobile app shells where clipping the bottom would hide something important; svh when I need absolute stability and can live with a bit of extra space when the bar hides.

ch and ex — units made of type

1ch is the width of the 0 character in the current font. 1ex is the height of a lowercase x. They sound obscure but ch has one genuinely great use:

.article { max-width: 65ch; }   /* ≈ 65 characters per line */

Typographers put the ideal line length at roughly 45–75 characters — long enough to read in rhythm, short enough that your eye finds the next line. ch lets you express that directly instead of guessing a pixel width and re-guessing it every time the font changes. It's approximate (proportional fonts have varying widths, and "0" is usually a bit wider than average, so you'll fit slightly more characters than the number suggests) — but it's approximate in the right units.

clamp(), min(), max() — fluid without breakpoints

These three take the maths CSS could always almost do and finish the job.

min(a, b) resolves to whichever is smaller at that moment; max(a, b) the larger. This lets you mix unit types in a way nothing else can:

.container { width: min(90%, 1100px); }
/* 90% on small screens, capped at 1100px on large ones —
   one declaration instead of a width plus a max-width */

A useful mental flip: min() sets a maximum (nothing can exceed the smallest option) and max() sets a minimum. Reading them the intuitive way gets it backwards, and everyone gets it backwards at first.

Then clamp(minimum, preferred, maximum), which is the star. It's exactly max(minimum, min(preferred, maximum)), but readable.

h1 { font-size: clamp(1.75rem, 5vw + 1rem, 4rem); }

Read it as: never smaller than 1.75rem, never bigger than 4rem, and in between scale smoothly with the viewport. One line replaces a font-size plus three media queries, and the result is continuous rather than jumping at breakpoints.

If the preferred value is pure vw, the text ignores the user's font-size setting entirely — viewport width doesn't care what they set — and in some browsers that also breaks zoom. Adding a rem component keeps a piece of the size tied to the user's preference. It's a one-token change that makes the difference between fluid type that's accessible and fluid type that isn't.

CSS custom properties

If you've used Sass, you already have variables. So why did CSS add its own, years later, with clunkier syntax? Surely $brand beats var(--brand)?

They're not the same feature. They're not even really the same kind of thing, and the difference is the single most important thing to understand here.

The one difference that matters: Sass variables are gone by the time the page loads

A Sass variable is a compile-time find-and-replace. You write $brand: #3a6ea5, and the compiler substitutes that value everywhere $brand appears, then throws the variable away. The CSS file the browser downloads has no idea a variable ever existed — it's just hex codes. The browser cannot change it, JavaScript cannot read it, and a media query cannot alter it, because there is nothing there to alter.

A CSS custom property is a real property with a real value that lives in the browser at runtime. It participates in the cascade. It inherits. It can be recomputed, overridden, and read.

The analogy: a Sass variable is like using find-and-replace in a Word document before you print it. A custom property is like a live spreadsheet cell — change the cell, and every formula referencing it updates immediately.

Three concrete superpowers come from being alive at runtime.

1. They inherit through the cascade. A custom property set on an element is visible to all of its descendants — and can be overridden partway down the tree, for that subtree only.

2. They can be changed by a media query or a class, which means one declaration can restyle a whole page.

3. JavaScript can read and write them, giving you a supported bridge between JS state and CSS rendering:

card.style.setProperty('--tilt', `${angle}deg`);
getComputedStyle(card).getPropertyValue('--brand');

Here's number one and two in action. The toggle below changes two custom properties on one container element — nothing else. Watch how many things move:

Every border, every bit of coloured text, every radius updates — because those elements reference the property rather than holding a copy of its value. This is impossible with Sass: by the time the browser sees the CSS, the Sass value has already been baked into each rule.

Theming, properly

That demo is the entire mechanism behind modern theming. Define your tokens once at the root, then override the tokens — not the components — in a variant:

:root {
  --surface: #ffffff;
  --text: #1c2024;
  --border: #e4e0da;
}

[data-theme="dark"] {
  --surface: #16181d;      /* 👈 three lines re-theme the app */
  --text: #e8eaee;
  --border: #2c3038;
}

.card {
  background: var(--surface);
  color: var(--text);
  border: 1px solid var(--border);
}

Now document.documentElement.dataset.theme = 'dark' re-themes everything, instantly, with no re-render and no second stylesheet. Because custom properties inherit, that one attribute on <html> reaches every component in the tree.

And it composes with media queries, which Sass could never do:

@media (prefers-color-scheme: dark) {
  :root { --surface: #16181d; --text: #e8eaee; }
}
@media (min-width: 60em) {
  :root { --gutter: 2rem; }   /* one knob, whole layout responds */
}

Fallbacks and scoping

var() takes a second argument used when the property isn't defined:

.button { background: var(--btn-bg, #3a6ea5); }         /* simple fallback */
.button { background: var(--btn-bg, var(--brand, #3a6ea5)); } /* chained */

This turns a component into a small API. You publish which custom properties you read, and consumers style you by setting them — no selector gymnastics, no specificity fight, no !important:

/* the component defines its knobs, scoped to itself */
.avatar {
  --avatar-size: 48px;
  width: var(--avatar-size);
  height: var(--avatar-size);
}

/* a consumer turns the knob — no override war */
.comment-thread .avatar { --avatar-size: 32px; }

Note that scoping matters for hygiene: --avatar-size defined on .avatar is invisible to the rest of the page, whereas everything on :root is global. Put genuine design tokens at the root; keep component knobs on the component.

Wait — what happens if a var() is invalid?

Something unusual, and worth knowing because it produces confusing bugs. Normally an invalid declaration is discarded and the previous value stands. But a declaration containing a var() can't be validated until the variable is substituted, which happens later — so if the result is nonsense, the browser applies "invalid at computed-value time." The property is set to its inherited value (if it inherits) or its initial value. So a broken color: var(--oops) doesn't fall back to your earlier color rule — it can end up inheriting from the parent, or resetting to black. Fallbacks in var() are your defence.

The gotcha: they're just strings

By default, a custom property is an untyped token stream. The browser doesn't know --brand: #3a6ea5 is a colour; it's a bag of characters, substituted verbatim, and only checked for validity where it gets used.

The visible consequence is that you cannot transition or animate a plain custom property. There's no "halfway between" two strings:

.card {
  --glow: #3a6ea5;
  box-shadow: 0 0 20px var(--glow);
  transition: --glow 300ms;   /* 👈 does nothing by default */
}

The fix is @property, which lets you give a custom property an actual type, an initial value, and inheritance behaviour:

@property --glow {
  syntax: '<color>';      /* 👈 now the browser knows it's a colour */
  inherits: false;
  initial-value: #3a6ea5;
}

With that registration, --glow animates smoothly, invalid values are rejected instead of poisoning the computed value, and you get a guaranteed initial value. It's also what makes previously-impossible things like animated gradient angles work.

That's a genuine case for a Sass variable, or newer @custom-media-style tooling.

"Can you animate them?" Not plain ones — they're untyped token streams, so there's no interpolation between two strings. Register the property with @property, giving it syntax: '<color>' or '<length>', and it becomes animatable.

"What if a var() is undefined?" Use the second argument: var(--x, fallback). Without one you hit "invalid at computed-value time" — the property falls back to inherited or initial, not to your previous declaration, which is a surprisingly common source of mystery black text.

"Any downside?" They're dynamic, so the browser can't fold them away at build time, and a token changed high in the tree invalidates style for everything below it. It's rarely a real problem, but changing a root-level property inside a scroll handler on a huge page is a thing you can measure.

Responsive design and container queries

Start with the viewport meta tag, because nothing works without it

When phones first got real browsers, almost every site was a fixed 980px desktop layout. Showing that on a 320px screen would have meant a column of text one word wide. So mobile browsers cheated: they pretend to be about 980px wide, render the desktop layout, then zoom the whole thing out to fit. Site looks like a tiny postcard, but at least it's the right shape.

That fallback is still on by default. Which means if you omit the viewport meta tag, your media queries never fire — the browser reports itself as 980px wide, your min-width: 768px rule matches, and your responsive design is shown, shrunk to unreadability.

<meta name="viewport" content="width=device-width, initial-scale=1">

That says: use the device's real width, and start at 100% zoom. One line, and it's a prerequisite for everything below.

One thing not to add: user-scalable=no or maximum-scale=1. It blocks pinch-zoom, which is an accessibility failure — plenty of people zoom into small text or a low-contrast label — and it's a WCAG violation. Modern iOS ignores it anyway.

Mobile-first: why min-width composes and max-width doesn't

Both of these produce the same result at both sizes:

Desktop-first (max-width)
.sidebar { float: left; width: 300px; padding: 2rem; }

@media (max-width: 47.99em) {
  .sidebar { float: none; width: auto; padding: 1rem; }
}
Mobile-first (min-width)
.sidebar { padding: 1rem; }

@media (min-width: 48em) {
  .sidebar { float: left; width: 300px; padding: 2rem; }
}

Look at what the desktop-first version has to do: it sets three properties, then undoes all three. float: none, width: auto — those declarations exist purely to cancel earlier ones. The mobile-first version never undoes anything; it only ever adds.

That's what "composes better" means, and it compounds badly. With three breakpoints, desktop-first means every property you set at the top must be considered and possibly reset at each of the three. Mobile-first means each breakpoint layers new declarations on top, and the browser's normal source-order rule does the rest. Less code, and — more importantly — no "which reset am I missing?" archaeology when something looks wrong at 900px.

There's also a nasty detail unique to max-width: what value do you use? If your other query is min-width: 768px, the max must be 767px — or 767.98px, because browser zoom and high-DPI screens produce fractional widths and a device at exactly 767.5px would match neither query, leaving an unstyled dead zone one pixel wide that someone will eventually screenshot for you. Min-width queries have no gaps by construction.

And two practical arguments beyond code tidiness. Mobile is where the constrained device usually is — a mobile-first stylesheet means a phone only parses and applies the rules it needs, rather than parsing a full desktop layout and then overriding it. And designing mobile-first forces you to decide what's genuinely essential before you have room for everything, which tends to produce a better desktop layout too.

Breakpoints should come from your content, not from devices

You'll see breakpoint lists labelled "iPhone," "iPad," "desktop." Resist that. Device sizes are a moving target — there are foldables, split-screen tablets, 4K monitors, browser windows dragged to a third of a screen. Chasing them is a treadmill.

The better method: start at the narrowest width and slowly widen the browser. The moment the layout looks bad, that's a breakpoint. The line length got too long. The nav items started wrapping awkwardly. There's clearly room for a second column now. Put the breakpoint there, at whatever odd number it happens to be.

This is why breakpoint values in well-built sites look arbitrary — 38em, 52em, 71em. They're not arbitrary; they're where that design stops working. Using em for them is a nice touch, because then the layout also adapts for a user who's enlarged their text — their effective viewport in ems is narrower, so they get the roomier mobile layout, which is usually exactly right.

Container queries: the genuinely better model

Here's the flaw at the heart of media queries, and once you see it you can't unsee it.

A media query asks about the viewport. But a component doesn't care about the viewport — it cares about how much room it has been given. A product card in a full-width hero and the same card in a narrow sidebar should look different, and the viewport is identical in both cases. Media queries simply can't express that.

So for years we faked it, with modifier classes:

❌ The component's parent must know its layout
.card--compact { ... }
.card--full { ... }
/* every consumer must pick correctly, at every breakpoint,
   forever — and the card can't be dropped anywhere new safely */

The card isn't really reusable. It's reusable if you also know where you're putting it, which is a much weaker promise.

Container queries fix this by letting an element ask about its own container's size instead of the viewport's. Two steps: mark an element as a container, then query it.

✅ The component decides for itself
.card-wrapper {
  container-type: inline-size;   /* 👈 "measure my width" */
  container-name: card;
}

.card { display: block; }

@container card (min-width: 30rem) {
  .card { display: grid; grid-template-columns: 140px 1fr; }
}

Now the card lays itself out based on the space it actually got. Drop it in the sidebar: stacked. Drop it in the hero: side by side. Drop it in a layout that didn't exist when the card was written: still correct. Nobody has to remember to pass the right modifier.

That's a real architectural shift. Media queries make responsiveness a property of the page; container queries make it a property of the component — which is how we've written everything else in frontend for a decade.

Wait — why inline-size and not just size?

Because querying height would be circular. If the container's height depends on its children's layout, and the children's layout depends on the container's height, there's no answer. container-type: inline-size queries width only, which is safe because width is resolved before content is laid out. (Same reasoning as percentage padding resolving against width — the browser is consistently avoiding circular dependencies.) There is a container-type: size, but it requires you to fix the height explicitly, so it's rare.

One cost: container-type applies size containment, so the container no longer sizes itself from its children in that axis. Usually you put it on a wrapper rather than the component itself, exactly as above.

Media queries still have their jobs — page-level layout, print styles, and the whole family of preference queries that have nothing to do with size:

@media (prefers-reduced-motion: reduce) { /* respect vestibular disorders */ }
@media (prefers-color-scheme: dark)     { /* OS-level dark mode      */ }
@media (prefers-contrast: more)         { /* stronger borders        */ }
@media (pointer: coarse)                { /* bigger touch targets    */ }

That first one is worth taking seriously: for some people, large animations cause genuine nausea and dizziness. Wrapping non-essential motion in prefers-reduced-motion is a small amount of work and it's the kind of detail that reads very well in an interview.

BEM, CSS Modules, CSS-in-JS, utility-first

Earlier we named the three structural problems CSS has at scale: everything is global, specificity only ratchets upward, and you can never safely delete anything. Every methodology below is an attempt on those three. Let's be honest about what each one actually buys and costs, because "which do you prefer and why" is a very common interview question and the wrong answer is dogma in either direction.

BEM — solving it with discipline

BEM (Block, Element, Modifier) is a naming convention, nothing more. No tooling, no build step.

.card { }                 /* Block: standalone component  */
.card__title { }          /* Element: part of that block  */
.card--featured { }       /* Modifier: a variant          */
.card__title--large { }   /* element + modifier           */

The clever part isn't the naming — it's that BEM makes your CSS flat. Instead of .card .content h2 (0,2,1) you write .card__title (0,1,0). Every selector is one class. Every rule has identical specificity. Which means the cascade almost never has to arbitrate, and when you need to override something you just write a rule later in the file. The specificity ratchet is disarmed.

The cost is that it's convention, not enforcement. Nothing stops a new team member writing .card .title. The names get long. And it does nothing about dead code — .card__legacy-badge sits there forever.

CSS Modules — solving it with a build step

Write plain CSS in a .module.css file; the bundler rewrites every class name to something globally unique and hands you a mapping.

/* Card.module.css */
.card { padding: 1rem; }
.title { font-size: 1.25rem; }
import styles from './Card.module.css';

<div className={styles.card}>
  <h2 className={styles.title}>Hello</h2>   // → "Card_title__x7f2q"
</div>

Now collisions are impossible, not merely unlikely — the compiler guarantees it, so you can use short obvious names like .title without a second thought. It's still just CSS, so it's zero-runtime, works with any tooling, and any CSS feature you like is available. And because the mapping is explicit, tools can flag classes nothing references.

The cost is small: a build step, slightly awkward composition of multiple classes, and dynamic values still need inline styles or custom properties.

Honestly, for a lot of teams this is the sweet spot, and it's underrated relative to how much airtime the other two get.

CSS-in-JS — solving it with colocation

Styled-components, Emotion, and friends let you write styles in JavaScript, next to the component:

const Button = styled.button`
  padding: 0.5rem 1rem;
  background: ${p => p.$variant === 'danger' ? '#c0392b' : '#3a6ea5'};
`;

What you get: scoping by construction, plus real dynamic styling — styles that are a function of props and state, which is genuinely awkward in any other approach. And colocation: the styles live and die with the component, so deleting the file deletes the CSS. Dead code becomes structurally impossible.

The criticisms are real and you should know them, because "what are the downsides of CSS-in-JS?" is a favourite follow-up:

  • Runtime cost. Runtime libraries serialise template literals, hash them, generate a class, and inject a rule into the stylesheet — during render. On a page with thousands of styled elements that's measurable, and it's work the browser wouldn't otherwise do at all.
  • Bundle size. You're shipping a styling engine to every user.
  • SSR complexity. Styles have to be collected during server render and inlined into the HTML, or the page flashes unstyled. That machinery is fiddly and it collides badly with React Server Components, which don't run the client-side context these libraries depend on. That collision is a big part of why the ecosystem moved.
  • It inserts itself into the render path, so a styling change can trigger a re-render, and the browser can't just parse a static stylesheet in parallel.

Which brings us to zero-runtime CSS-in-JS — Linaria, vanilla-extract, Panda CSS, and StyleX. You write styles in TypeScript, with types and colocation, and the build step extracts them to a real static .css file. Nothing ships to the browser but CSS. You keep the authoring experience and drop the runtime.

The tradeoff: since extraction happens at build time, you can't compute arbitrary styles from runtime values. The standard answer is custom properties — the class is static, and the dynamic bit rides in a variable:

<div className={card} style={{ '--accent': user.color }}>

Which is a nice illustration that custom properties are the runtime escape hatch for build-time systems.

Utility-first — solving it by not naming things

Tailwind's bet is that most of the difficulty comes from the abstraction layer itself. Naming things is hard, deciding whether a style belongs to .card or .card__body is hard, and keeping a class name in sync with markup you edit six months later is hard. So: skip it.

<div class="flex gap-4 rounded-lg bg-white p-4 shadow-sm">

Every class is a single declaration, all at the same specificity, so the cascade essentially never arbitrates. Deleting the element deletes its styles, so dead CSS is impossible. A build step scans your templates and emits only the utilities you used, so the stylesheet is small and stops growing after a while — it converges, because there are only so many spacing values. And because the utilities come from a config, you get design-token constraints for free: p-4, not "someone typed 15px."

The honest costs: markup is noisy, and there's real cognitive load in learning the vocabulary. Repetition is handled by extracting a component, not a class, which is fine in React and awkward in a templating language with no component model. And the design-system constraint is a strength right up until you need a value that isn't in the scale.

Animation performance and the pixel pipeline

Last topic, and it's the one where a small piece of knowledge produces the biggest visible difference.

You've got a sidebar that slides in. Version one animates left. Version two animates transform: translateX(). They look identical in a screenshot. On a mid-range Android phone, one is silky and the other stutters.

To understand why, we need to know what the browser does to put pixels on screen.

The pixel pipeline

Every frame, the browser runs some or all of these steps:

1Style — work out which CSS rules apply to which elements and compute final values. (That's the cascade, from the start of this guide.)
2Layout (a.k.a. reflow) — calculate geometry: how big is everything, where does it sit. Expensive, and often affects many elements at once.
3Paint — fill in pixels: text, colours, shadows, borders. Done onto one or more layers.
4Composite — assemble the layers in the right order, with the right transforms and opacity, into the final image.

The critical fact: the pipeline is a cascade of consequences. Trigger an early step and every later step must run too. Change geometry and you must re-layout, then re-paint, then re-composite. But change something that only affects compositing, and steps 1–3 can be skipped entirely.

My analogy is a print shop. Layout is deciding where every element goes on the page — that's typesetting, and moving one paragraph can push everything after it. Paint is inking the plates. Composite is sliding already-printed transparent sheets over each other on a lightbox. If all you need is to move a sheet two inches to the left, you'd be mad to re-typeset and reprint the whole document.

Why transform and opacity are cheap

Now the payoff. transform and opacity are special: they are the two properties that can be handled entirely at the composite step.

Why those two specifically? Because neither changes the element's geometry as far as other elements are concerned. A transformed element still occupies its original box in layout; nothing else moves in response. A faded element still occupies its box too. So the browser can promote that element to its own compositor layer — a pre-painted bitmap — and then, for each frame, just tell the GPU "draw this existing bitmap 40 pixels further left" or "draw it at 60% alpha." No layout. No repaint. Just a matrix multiply and a blend, which is exactly what GPUs are built for.

And here's the part that really matters on a busy page: this work can happen on the compositor thread, separate from the main thread. So even if your JavaScript is blocking the main thread with an expensive render, a composited animation keeps running at 60fps. Animate left instead, and every frame needs layout — which is main-thread work — so your animation stutters exactly when the page is busiest, which is exactly when the user notices.

Animating…TriggersCost
width, height, top, left, margin, padding, font-sizeLayout → Paint → CompositeWorst

.drawer { left: -300px; transition: left 300ms; }

Same visual result. Completely different cost profile.

Wait — what if I really need to animate size?

Use transform: scale() instead of animating width and height, and accept that it scales the contents too (text gets blurry mid-animation, borders thicken). For expanding panels, the FLIP technique below handles it properly. And for the specific case of "animate to height: auto," which was impossible for years: modern CSS has interpolate-size: allow-keywords and calc-size() — still a layout-triggering animation, but at least an expressible one.

Layout thrashing

Now the JavaScript-side version of the same problem, and it's a favourite interview question because it separates people who've profiled a real page from people who haven't.

Browsers are lazy about layout on purpose. When you change a style from JavaScript, the browser doesn't recalculate immediately — it queues the change and batches everything up until it has to produce a frame. Very efficient.

Until you ask it a question it can't answer from the queue:

// ❌ Layout thrashing — read, write, read, write…
boxes.forEach(box => {
  const width = box.offsetWidth;        // READ  → forces layout NOW
  box.style.width = width / 2 + 'px';   // WRITE → invalidates layout
});

Reading offsetWidth means "give me the current geometry." The browser can't answer that with pending changes sitting in a queue — the answer might be wrong. So it must flush the queue and run layout synchronously, right now. That's a forced synchronous layout.

One of those is fine. The problem is the loop. Each write dirties the layout again, so the next read forces another full layout. With 100 boxes you've run 100 full layout passes in a single frame instead of one. That's layout thrashing, and it's usually the reason a scroll handler drops to 12fps.

The analogy: it's like calling the warehouse to check stock after every single item you add to an order, instead of writing the whole order down and calling once at the end. The phone call is expensive; the batching is the whole point.

The fix is simply to separate all reads from all writes:

// ✅ Read everything first, then write everything
const widths = boxes.map(box => box.offsetWidth);   // one layout
boxes.forEach((box, i) => {
  box.style.width = widths[i] / 2 + 'px';          // no reads → no flushes
});

One forced layout instead of a hundred. Same output.

The properties that force layout when read are the geometry ones: offsetTop/Left/Width/Height, clientTop/Left/Width/Height, scrollTop/Left/Width/Height, getBoundingClientRect(), getComputedStyle() in many cases, and window.getComputedStyle, plus scrollIntoView() and focus(). You don't need to memorise the list; you need the pattern — batch your reads, then batch your writes. In Chrome DevTools these show up in the Performance panel as purple "Layout" bars with a little red triangle warning about forced reflow.

will-change, and why more isn't better

Promoting an element to its own compositor layer isn't free — it takes GPU memory and setup. So browsers only do it when they think it's worth it, and they sometimes decide after your animation has started, causing a visible hitch on the first frame.

will-change lets you warn them in advance:

.card { will-change: transform; }

Sounds like free performance. It isn't, and overusing it actively backfires:

  • Every layer costs memory. A full-screen layer on a 3x-DPI phone is many megabytes. Do it to fifty elements and you can exhaust GPU memory, at which point the browser falls back to slower paths — or the tab crashes. You've made things worse in exchange for a smoother first frame you didn't need.
  • It creates a stacking context (remember that list?), so a stray will-change can silently break your z-index layering, in a way that's genuinely hard to trace back.
  • Leaving it on permanently defeats the point. It's a hint that something is about to change. If it's always on, the browser is permanently holding an optimisation for an event that may never come.

The right usage is narrow and temporary — turn it on just before, remove it after:

.card:hover { will-change: transform; }   /* hover = "probably about to animate" */

Honestly: don't reach for it until you've measured a problem. Animating transform and opacity already gets you most of the way, and browsers are good at this now.

FLIP, briefly

So how do you animate something that genuinely is a layout change — a card moving to a new grid position, a list reordering — while still only animating transform?

FLIP is the trick, and it's beautiful. Four steps:

  • First — measure the element's position before the change (getBoundingClientRect()).
  • Last — apply the change (add the class, reorder the DOM) and measure the new position.
  • Invert — compute the delta and apply a transform that moves it back to where it was. To the user, nothing has moved yet — but the element is now genuinely in its final layout position, just visually displaced.
  • Play — transition that transform to zero. It glides to its real position.

The insight is that we've converted a layout animation into a transform animation. The expensive layout happens exactly once, at the moment of the swap, and every frame after that is pure compositing. This is what libraries like Framer Motion's layout animations and the View Transitions API do under the hood — and in fact view-transition now gives you much of this declaratively.

If there's one idea to carry out of all this, it's that most CSS confusion comes from an invisible context you weren't accounting for. A rule loses because of an origin you forgot. A z-index does nothing because an ancestor sealed it in. An em is the wrong size because of where it's nested. A percentage means something different than you assumed because of which property it's on.

CSS isn't arbitrary — it's contextual. Once you know which context you're in, it's remarkably predictable. And "let me check what context this is in" is a genuinely great thing to say out loud in an interview, because it's exactly how someone who has debugged this stuff for real actually thinks. 🎨
