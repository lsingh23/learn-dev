Pagination and sortable tables

The data table is the most common "real product" prompt there is, and it's the one where people write the most state for the least reason. The whole family — paging, sorting, filtering — is four scalars and a pipeline.

The pipeline is the mental model

A table looks like four features stapled together. It isn't. It's one array going through one chain of pure transformations, recomputed on every render:

The order isn't arbitrary. Filter first so sorting only touches rows you'll show. Sort before slicing, because slicing first and then sorting sorts page 3, which is a real bug I've watched people ship. And the whole chain runs top to bottom on every render, from raw data plus four small values.

Which gives us the state, and this comment block goes into the file before any JSX:

// state (all of it):
//   query    → string, the filter box
//   sort     → { key: 'name', dir: 'asc' } | null   ← ONE object
//   page     → number, 1-based (saying this out loud now)
//   pageSize → number, 10
//
// derived every render — never stored:
//   filtered → rows matching query
//   sorted   → [...filtered].sort(comparator)
//   total    → sorted.length
//   pages    → Math.ceil(total / pageSize)
//   visible  → sorted.slice((page - 1) * pageSize, page * pageSize)

Four numbers and strings. Everything a user actually looks at is on the second half of that list, and none of it lives in useState. That's the whole guide, honestly — the rest is the details you'll get dinged on.

The one clarifying question

Ask this before you type anything, because it changes the architecture rather than the code: "do I have the whole dataset in memory, or am I fetching a page at a time?"

Client-side means the pipeline above, all local, instant. Server-side means page and sort become request parameters and the response hands you back both the rows and a total you can't compute yourself. Same state shape either way — that's the nice part — but a different data flow. Assume client-side unless told otherwise, say that you're assuming it, and mention you'd move it server-side past a few thousand rows.

Pagination, simplest version

Pick 1-based or 0-based once, and announce it. I use 1-based because it matches what the button says, and the only place it costs me is the - 1 in the slice. What you must not do is drift — 0-based state with a 1-based label is where off-by-ones breed.

const [page, setPage] = useState(1);          // 1-based
const pageSize = 10;

const total = rows.length;
const pages = Math.max(1, Math.ceil(total / pageSize));
const visible = rows.slice((page - 1) * pageSize, page * pageSize);

The Math.max(1, …) is there so an empty table reports "page 1 of 1" instead of "1 of 0". Small thing; interviewers notice it.

Then the controls. Disable at the ends rather than silently clamping:

<button disabled={page === 1} onClick={() => setPage(p => p - 1)}>Prev</button>
<span>Page {page} of {pages}</span>
<button disabled={page === pages} onClick={() => setPage(p => p + 1)}>Next</button>

Clamping inside the handler (Math.min(p + 1, pages)) makes a live button that does nothing, which feels broken. A disabled button tells the truth about the state. Do both if you like — belt and braces — but the disabled is the one that's user-facing.

Page 7 of 2

So you've got paging working, sorting working, a filter box working. You're on page 7. You type into the filter and the result set drops to eleven rows. What does the table show?

Nothing. Empty tbody, "Page 7 of 2", and a candidate quietly wondering if they broke React. The slice indices are past the end of the array, so .slice() cheerfully returns [].

The rule

Anything that changes the size or order of the result set resets page to 1. Filter changed → page 1. Sort changed → page 1. Page size changed → page 1. Do it in the same handler that sets the other thing, not in a useEffect watching the filter.

function onQueryChange(next) {
  setQuery(next);
  setPage(1);        // 👈 same event, same handler
}

Why not an effect? Because an effect renders once with the bad combination — page 7, eleven rows — and then renders again to fix it. You get a flash of empty table, and you've introduced a second source of truth for "what page are we on". Two state values that change together should change in the same event.

Sortable headers

Sort state is one object: { key, dir }. Not sortKey plus sortDir as separate states (they always change together, and split state lets you render with a stale pair), and definitely not a boolean per column, which is the accordion mistake wearing a different hat — it lets you represent "sorted by three columns at once", which is illegal.

The click handler is the three-state cycle, if they ask for one: ascending, descending, off.

function toggleSort(key) {
  setSort(s => {
    if (s?.key !== key) return { key, dir: 'asc' };   // new column
    if (s.dir === 'asc') return { key, dir: 'desc' };
    return null;                                      // third click → unsorted
  });
  setPage(1);
}

Now the sort itself, and here's the bug that costs people the round:

❌ Mutates the source array
const sorted = rows.sort(cmp);   // .sort() sorts IN PLACE and returns the same ref

You've just reordered the caller's array. If rows came from props you've mutated your parent's data; if it came from state you've mutated state directly, and since the reference never changed React has no reason to re-render. The symptom is maddening: the first click does nothing visible, the second click "works", and the original order is gone forever.

✅ Copy first
const sorted = sort
  ? [...filtered].sort((a, b) => cmp(a[sort.key], b[sort.key]) * (sort.dir === 'asc' ? 1 : -1))
  : filtered;

Note the direction trick: write the comparator for ascending only, then multiply by -1 for descending. One comparator, not two.

And the comparator needs to handle the types you actually have:

function cmp(a, b) {
  if (a == null) return 1;                       // nulls sink to the bottom, always
  if (b == null) return -1;
  if (typeof a === 'string') return a.localeCompare(b);  // "Ä" vs "z", case
  return a - b;                                  // numbers and Dates both work
}

localeCompare rather than < because 'apple' < 'Banana' is false in code-point order and true to a human. Dates subtract fine via coercion; if you're holding ISO strings, they sort correctly as strings anyway.

Under the hood — stability

Array.prototype.sort is required to be stable in every modern engine. That's why sorting by Department and then by Name gives you names grouped inside departments rather than a shuffle — equal elements keep their previous relative order. Worth saying out loud when they ask about multi-column sort; it's a one-line answer instead of a feature.

The header markup

Free points, and most candidates drop them. A clickable header is a real <button> inside the <th> — keyboard focus and Enter/Space come for nothing — and the <th> carries aria-sort:

<th aria-sort={sort?.key === col.key ? (sort.dir === 'asc' ? 'ascending' : 'descending') : 'none'}>
  <button onClick={() => toggleSort(col.key)}>
    {col.label} {sort?.key === col.key && (sort.dir === 'asc' ? '↑' : '↓')}
  </button>
</th>

Columns as data

When they ask "how would you make this reusable?", the answer is four lines and you should have it ready. Describe the columns as an array instead of hand-writing cells:

const COLUMNS = [
  { key: 'name',  label: 'Name',   sortable: true },
  { key: 'age',   label: 'Age',    sortable: true },
  { key: 'email', label: 'Email',  sortable: false, render: r => <a href={`mailto:${r.email}`}>{r.email}</a> },
];

The body is then two nested maps — rows outside, columns inside — and adding a column is a data change, not a code change. The optional render hook covers formatting and links without special-casing anything in the table itself.

Server-side, when it comes up

Same state, different pipeline. page and sort go into the request; rows and total come out of the response. You lose the local slice and gain loading and error states — the flag-plus-data shape you'd use for any fetch. Keep the previous page's rows on screen while the next loads rather than blanking the table; it reads as much faster.

One sentence that lands well: offset pagination (?page=3&size=20) is simple and lets you jump to any page, but it drifts when rows are inserted or deleted mid-browse — you'll see a row twice or miss one — and gets slow on deep offsets because the database still counts past everything it skipped. Cursor pagination (?after=abc123) is stable and fast at any depth, but only gives you next/previous, no page numbers. Feeds use cursors; admin tables use offsets.

Follow-ups

"It's 10,000 rows now. What changes?"

"Three steps, in order. First useMemo the filter and sort so they don't rerun when unrelated state changes — one line, no structural change. Then virtualise the body so I'm only mounting the ~20 visible rows instead of all of them. If it's still slow, or the data doesn't fit in memory, that's the signal to move filtering, sorting and paging to the server."

"Why not just store the sorted array in state?"

"Because then I've got two sources of truth. Every time a row is added, edited, or the filter changes, I have to remember to re-sort — and one day I won't, and the table shows stale order with no error. Sorting is a pure function of the rows and {key, dir}, so I compute it. If it ever gets expensive, useMemo gives me the caching without the syncing."

"How do you sort a column with missing values?"

"I decide once and apply it consistently: nulls go to the bottom in both directions. That means the null check happens before the direction multiplier, otherwise flipping to descending floats all the blanks to the top, which nobody wants. Same rule for empty strings if the product treats them as missing."

"How do you keep the page and sort in the URL?"

"Move that state into query params — ?page=3&sort=name&dir=asc — and read it with useSearchParams instead of useState. The URL becomes the source of truth, so the view is shareable, survives a refresh, and the back button steps through it. I'd keep pageSize there too, but the transient stuff like an open row menu stays in local state."

Say this when you start

"The state here is tiny — a page number, a sort object, a filter string. The visible rows are derived: filter, then sort, then slice, recomputed each render. So I'll write those four pieces of state down first and then the pipeline."

Cheat sheet

  • raw → filter → sort → slice → render. One direction, recomputed each render. Only the knobs are state.
  • State: query, sort {key, dir}, page, pageSize. Nothing else.
  • Ask first: whole dataset in memory, or a page at a time?
  • 1-based or 0-based — pick once, say it out loud.
  • Filter or sort changes → reset page to 1, in the same handler. Otherwise: page 7 of 2.
  • Disable prev/next at the ends instead of silently clamping.
  • Sort is one object, not two states and not a boolean per column.
  • [...rows].sort() — bare .sort() mutates props or state and may not re-render.
  • One ascending comparator × ±1 for direction. localeCompare for strings, nulls last, null check before the multiplier.
  • Columns as data — {key, label, sortable, render} — and the body is two nested maps.
  • Real <button> in the <th>, aria-sort on the <th>.
  • Scale answer: memoize → virtualise → move to the server. In that order.
