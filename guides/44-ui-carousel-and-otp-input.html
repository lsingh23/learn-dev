Carousel & OTP input

Two components, one state shape: a pointer — a single index — plus something the pointer alone can't do. Because scroll position and keyboard focus don't live in React state. They live in the DOM, and that's why these are the two components where reaching for useRef is the correct answer rather than a smell.

Why these two are a pair

Both are pointers, in the sense of the framework guide: one of N is active, so you store which one. For the carousel that's the visible slide. For the OTP input it's the box you're typing in.

The twist is that in both cases the pointer has a physical consequence that React state can't express. "Slide 3 is active" has to become "the track is shifted 300% to the left." "Box 4 is active" has to become "box 4 is actually focused" — and focus is a property of the document, not of your component tree. You can't return focus from a render function. So you keep the pointer in state, and you keep a handle on the DOM in a ref, and you push the one into the other.

Carousel: one number

Write the state comment first, as always:

// state:
//   index → number, which slide is showing (0..n-1)
// derived:
//   everything else. the transform, the active dot, the alt text.
// props:
//   slides → [{ id, src, alt }]

That's genuinely the whole model. Now the handlers — and this is where a very ordinary bug lives:

❌ Looks right, breaks on the first click
const prev = () => setIndex(i => (i - 1) % slides.length);

Quick question before you scroll: with five slides, sitting at index 0, what does (0 - 1) % 5 give you?

Not 4. It's -1. JavaScript's % is a remainder, not a modulo — it keeps the sign of the left operand. So the very first "previous" click from the start sends your track to translateX(100%) and the carousel slides cheerfully off screen into the void. Fix it by pushing the number positive before you wrap:

✅ The + n that everyone forgets
const n = slides.length;
const next = () => setIndex(i => (i + 1) % n);
const prev = () => setIndex(i => (i - 1 + n) % n); // 👈 + n keeps it non-negative

And ask the clarifying question out loud, because it's a real product decision: wrap or clamp? Wrapping is the modulo above. Clamping is Math.min(i + 1, n - 1) and Math.max(i - 1, 0), and it means you must also disable the arrow buttons at the ends — disabled={index === 0} — otherwise you've built a button that does nothing, which is worse than not having it.

The real decision: how you render slides

Here are the two approaches, and picking deliberately between them is most of the signal in this question.

(a) Render only the active slide. <img src={slides[index].src} />. Four lines, works immediately, and it's a perfectly good first pass in an interview. The cost is that there's nothing to animate — the old slide is gone from the DOM before the new one exists, so you can cross-fade at best, never slide.

(b) Render all slides in a row and move the row. This is the standard answer. You put every slide side by side in a flex track, hide the overflow, and translate the track.

<div style={{ overflow: 'hidden', width: '100%' }}>
  <div style={{
    display: 'flex',
    transform: `translateX(${-index * 100}%)`,
    transition: 'transform 300ms ease',
  }}>
    {slides.map(s => (
      <img key={s.id} src={s.src} alt={s.alt}
           style={{ flex: '0 0 100%' }} loading="lazy" />
    ))}
  </div>
</div>

Six lines of style and you get the animation for free, because the browser is already interpolating transform for you. Note flex: '0 0 100%' — without the 0 shrink factor flexbox squashes all the slides in to fit, and you'll spend five confused minutes wondering why every image is 25% wide.

Under the hood — why transform, not left

Animating left changes the element's geometry, so every frame the browser has to re-run layout and repaint. transform doesn't touch layout at all: the element gets promoted to its own compositor layer and the GPU just draws the same pixels at a different offset. Same visual result, wildly different frame budget. Say this in the interview — it's a one-sentence answer that reads as someone who has actually shipped animation.

Carousel upgrades, in the order I'd add them

All of these are derived from that one index, which is the point.

  • Dots. slides.map((s, i) => <button key={s.id} className={i === index ? 'dot active' : 'dot'} onClick={() => setIndex(i)} />). Real <button>s, not divs — you get focus, Enter and Space for free.
  • Keyboard arrows. An onKeyDown on the viewport mapping ArrowLeft/ArrowRight to prev/next.
  • Autoplay. A setInterval in an effect calling next, cleaned up in the return, and skipped entirely while paused is true — set by onMouseEnter/onMouseLeave and onFocus/onBlur, because keyboard users need the pause too. See guide 39 for the interval-in-an-effect mechanics; the trap there (a stale closure over index) is why next uses the updater form.
  • Lazy images. loading="lazy" on every <img>, since approach (b) renders all of them.
  • Infinite loop. Clone the last slide before the first and the first after the last, then after the transition ends jump the index silently with the transition disabled — one sentence is plenty in an interview.
The honest a11y answer

Put aria-live="polite" on the viewport so slide changes are announced, label the arrows (aria-label="Next slide"), and use real buttons throughout. Then say the true thing: a fully accessible carousel is genuinely hard — autoplay fights screen readers, offscreen slides stay focusable unless you manage inert. Interviewers know this. Naming the difficulty scores better than pretending it isn't there.

OTP input: index + an array of refs

This one is more fun, because almost all of the work is in four tiny handlers and each one is a behaviour the interviewer is specifically checking for.

// state:
//   digits → string[6], e.g. ['1','2','','','','']  one char per box
// refs:
//   inputsRef → the six DOM nodes, so we can .focus() them
// derived:
//   code       → digits.join('')
//   isComplete → digits.every(Boolean)

const [digits, setDigits] = useState(Array(6).fill(''));
const inputsRef = useRef([]);
const focus = (i) => inputsRef.current[i]?.focus();

Note what's not state: there's no activeIndex. The browser already tracks which box has focus, and duplicating that into React means keeping two things in sync forever. The pointer here is implicit — each handler receives its own i and moves focus relative to it.

The four behaviours you're graded on

1. Type a digit → fill and advance

function handleChange(e, i) {
  const char = e.target.value.replace(/\D/g, '').slice(-1); // digits only, last one
  if (!char) return;
  setDigits(d => d.map((v, j) => (j === i ? char : v)));
  focus(i + 1);
}

That .slice(-1) is doing quiet, useful work. If the box already contains 3 and the user types 7 without selecting first, the raw value is "37" — taking the last character means the new digit wins, which is what a person expects. focus(i + 1) on the last box is a no-op thanks to the ?..

2. Backspace → the two-case rule

This is the detail candidates miss. Backspace does two different things depending on whether the current box is empty:

function handleKeyDown(e, i) {
  if (e.key !== 'Backspace') return;
  if (digits[i]) {
    setDigits(d => d.map((v, j) => (j === i ? '' : v)));   // full → clear in place
  } else {
    setDigits(d => d.map((v, j) => (j === i - 1 ? '' : v))); // empty → clear the one before
    focus(i - 1);
  }
}

Handle only the second case and holding backspace deletes every other digit. Handle only the first and you get stuck on an empty box forever.

3. Paste → the differentiator

Everyone gets the code by SMS and pastes all six at once. If your component drops five of them, it's broken in the most common real usage.

function handlePaste(e, i) {
  e.preventDefault();
  const chars = e.clipboardData.getData('text').replace(/\D/g, '').split('');
  if (!chars.length) return;
  setDigits(d => {
    const next = [...d];
    chars.forEach((c, k) => { if (i + k < next.length) next[i + k] = c; });
    return next;
  });
  focus(Math.min(i + chars.length, digits.length - 1)); // last filled box
}

Spreading from the paste position rather than always from 0 is what makes "paste 4 digits into box 3" behave sanely: boxes 3–6 fill, the overflow is dropped, focus lands on the last one written.

4. Arrows and select-on-focus

Add ArrowLeft/ArrowRight to the same keydown handler (focus(i - 1) / focus(i + 1)), and put onFocus={e => e.target.select()} on each input so clicking a filled box selects its contents and typing replaces rather than appends.

Auto-submit and the attributes that matter

useEffect(() => {
  if (digits.every(Boolean)) onComplete(digits.join(''));
}, [digits]);

<input value={digits[i]} maxLength={1} inputMode="numeric"
       autoComplete="one-time-code" aria-label={`Digit ${i + 1} of 6`} />

inputMode="numeric" brings up the number pad on mobile. autoComplete="one-time-code" is the one to name out loud: it's what lets iOS offer the code straight from the SMS notification. It's a small attribute that says you've built this for real.

About that ref array

You collect the nodes with a callback ref in the map: ref={el => { inputsRef.current[i] = el; }}. Six named refs would work for exactly six boxes and then die the moment the length becomes a prop — and OTP lengths are 4, 6, or 8 depending on the vendor. One useRef([]) holding an array scales to any n, keeps the focus helper a one-liner, and mutating .current doesn't trigger a render, which is precisely what you want: focus is a side effect, not a visual state.

Follow-ups, with answers you can say

"Why does previous break at index 0?"

Because % in JavaScript is remainder, not modulo — it keeps the sign of the left side, so -1 % 5 is -1, not 4. Adding n first makes it non-negative before the wrap.

"Why transform instead of left?"

Transform is composited — it skips layout and paint, so it animates on the GPU. Animating left re-runs layout every frame and drops frames on cheap devices.

"What happens if the user pastes 4 digits into box 3?"

They spread forward from box 3, so boxes 3 to 6 fill and anything past the end is dropped. Then focus moves to the last box I actually wrote to.

"How do you handle backspace on an empty box?"

Two cases. If the box has a value, I clear it in place and stay. If it's already empty, I move focus back one box and clear that one — otherwise holding backspace skips every other digit.

"How would you make the carousel swipeable?"

Pointer events: record clientX on pointerdown, track a live drag offset on pointermove and add it to the transform with the transition off, then on pointerup either commit to the next index or snap back depending on whether the drag passed a threshold.

Cheat sheet

  • Both are pointers + refs. State holds the index; the ref pushes it into the DOM, because scroll and focus aren't renderable.
  • (i - 1 + n) % n — the + n is not optional. -1 % 5 === -1.
  • Ask wrap or clamp. If clamp, disable the end buttons.
  • Flex track in overflow:hidden, moved with translateX(-index * 100%), slides at flex: 0 0 100%. Free CSS transition, composited.
  • Dots, active class, alt text — all derived from index.
  • Autoplay pauses on hover and focus, with cleanup.
  • OTP state is Array(6).fill(''); the value is digits.join(''). Don't store the active index — the DOM has it.
  • Type: value.replace(/\D/g,'').slice(-1), write, focus i+1.
  • Backspace is two cases: full → clear in place; empty → clear i-1 and go there.
  • Paste: preventDefault, strip non-digits, spread from the paste index, focus the last filled box.
  • inputMode="numeric" + autoComplete="one-time-code" + a per-box aria-label.
  • One useRef([]) of nodes, not six named refs — the length is usually a prop.
