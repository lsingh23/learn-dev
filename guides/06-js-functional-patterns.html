1. A function is just a value

Let's start somewhere that feels almost too basic, because everything else in this guide is built on it, and I've watched a lot of people get quietly stuck here without realising it.

Here's a variable holding a number:

const cartTotal = 42;
console.log(cartTotal); // → 42

Nothing surprising. Now here's a variable holding a function:

const double = function (n) {
  return n * 2;
};

console.log(double);    // → ƒ (n) { return n * 2; }
console.log(double(5)); // → 10

Look carefully at those two console.logs, because the difference between them is the entire foundation of this topic.

double is the function itself — the recipe, sitting there, un-run. double(5) is the result of running it. Those parentheses aren't decoration; they're the "go" button. Without them, you're holding the recipe. With them, you've cooked the meal and you're holding a plate.

The analogy

Think of a function as a recipe card. You can hand a recipe card to a friend, put it in a drawer, photocopy it, stick it in an envelope, or write a recipe card whose only instruction is "go get another recipe card from the drawer." None of that involves cooking anything. Calling the function — double(5) — is the cooking part, and what you get back is food, not a card.

Where it breaks down: a real recipe card doesn't remember which kitchen it was written in. JavaScript functions do — they remember the variables that were in scope where they were defined. That memory is called a closure, and it's going to matter a lot later in this guide when we build debounce.

Because a function is a value, everything you can do with a number, you can do with a function:

const double = (n) => n * 2;

const alias = double;              // put it in another variable
const operations = [double];       // put it in an array
const math = { double };           // put it in an object
console.log(alias(4));             // → 8
console.log(operations[0](4));     // → 8
console.log(math.double(4));       // → 8

That's the whole trick. There is no special "function type" ceremony. A function is a value that happens to have a "go" button on it.

A common misconception

"Passing a function means passing what it returns." It doesn't, and this is the #1 source of confusion when people first meet callbacks. Compare:

setTimeout(sayHello, 1000);   // ✅ hand over the recipe; JS calls it in 1s
setTimeout(sayHello(), 1000); // ❌ cook it NOW, hand over the plate

The second line runs sayHello immediately and passes its return value (probably undefined) to setTimeout. A second later, setTimeout tries to call undefined and nothing happens. The bug is one pair of parentheses.

2. Higher-order functions

Once functions are values, a question falls out on its own: can a function take a function as an argument? Can it return one?

Yes to both. And a function that does either of those things has a name: a higher-order function. That's the whole definition. There's nothing more to it than "a function that takes and/or returns functions."

Taking a function

Here's the classic motivation. Suppose we want to greet everyone in a list:

function greetAll(names) {
  for (const name of names) {
    console.log('Hello, ' + name);
  }
}

Fine. But now we want to uppercase everyone's name instead. And later, to email each of them. We'd end up writing uppercaseAll, emailAll, logAll — three functions whose looping machinery is identical and whose only difference is what happens to each item.

So let's make that part swappable. We'll pass it in:

function forEachName(names, action) { // 👈 `action` is a function
  for (const name of names) {
    action(name);
  }
}

forEachName(['Ada', 'Linus'], (name) => console.log('Hello, ' + name));
forEachName(['Ada', 'Linus'], (name) => sendEmail(name));

forEachName is a higher-order function. It owns the boring part (walking the list) and delegates the interesting part (what to do with each item) to whoever calls it. The function you pass in is called a callback — it's a function you hand to someone else so they can call it back at the right moment.

Returning a function

The other half is stranger and much more powerful. A function can build and hand back a brand-new function:

function makeMultiplier(factor) {
  return function (n) {   // 👈 a brand-new function, every call
    return n * factor;    // 👈 it remembers `factor`
  };
}

const double = makeMultiplier(2);
const triple = makeMultiplier(3);

console.log(double(5)); // → 10
console.log(triple(5)); // → 15

Sit with this for a second, because it's genuinely a bit brain-bending the first few times. makeMultiplier(2) has already finished running by the time we call double(5). Its factor variable should logically be gone — the function it lived in returned ages ago. And yet double still knows that factor is 2.

That's the closure I mentioned earlier: the inner function keeps a live reference to the variables it was born surrounded by, and those variables stay alive for exactly as long as that inner function does. double and triple each carry their own private factor; they don't share one.

The mental model

A function factory is a label printer. You configure it once ("print these at 2× scale"), and it hands you back a printer that's pre-set. You can then hand that printer around; nobody who uses it needs to know or care about the scale setting. It's baked in, and it's private — nobody can reach in and change it.

Where it breaks down: a real printer's setting is fixed. A closure's captured variable can change if something inside still writes to it — which is exactly how debounce will keep track of a timer ID later on.

Almost everything else in this guide — currying, debounce, throttle, memoize, pipe — is this one pattern wearing different hats. A function that returns a wrapped-up function with something remembered inside it.

In an interview

If someone asks "what's a higher-order function?", the answer is one sentence, and then you immediately earn your keep by naming why we bother: it lets you factor out the part of an algorithm that varies. Array.prototype.map, addEventListener, setTimeout, and every React hook that takes a callback are all higher-order functions. Reaching for those examples unprompted is what separates "memorised the term" from "uses it daily."

3. map, filter, and the one everybody fumbles: reduce

You've almost certainly used the first two. Let's make sure the mental models are exact before we get to reduce, because reduce is best understood as the thing the other two are secretly made of.

map: same length, transformed items

const prices = [10, 20, 30];
const withTax = prices.map((price) => price * 1.2);

console.log(withTax); // → [12, 24, 36]
console.log(prices);  // → [10, 20, 30]  👈 untouched

map makes a new array of exactly the same length, where each slot is whatever your callback returned for the corresponding input. Three in, three out. Always. If you find yourself wanting map to sometimes skip an item, you want filter.

The picture in my head: a conveyor belt of boxes going through a machine. Every box goes in, every box comes out, but changed. The count never changes.

filter: fewer (or equal) items, unchanged

const users = [
  { name: 'Ada', active: true },
  { name: 'Linus', active: false },
  { name: 'Grace', active: true },
];

const activeUsers = users.filter((user) => user.active);
console.log(activeUsers.length); // → 2

filter keeps an item when your callback returns something truthy and drops it otherwise. The items themselves are untouched — the same object references come out the other side. So it's the opposite trade of map: length can change, contents can't.

A common misconception

"filter's callback should return the item." No — it should return a boolean-ish answer to "keep this?" This bites people:

users.filter((user) => user.name); // → keeps everyone with a non-empty name
                                   //   (a non-empty string is truthy)

That's not "give me the names." That's "keep users that have a name." To get names out, you want map.

reduce: the running total on a piece of paper

Right. This is the one people freeze on in interviews, and I think it's because it gets taught as a signature (reduce(callback, initialValue)) rather than as a picture. So let's do the picture first.

The mental model

You're a cashier with a single scrap of paper. Before the first customer walks up, you write a starting number on it — say 0. That's the initial value.

Then, for each item that comes down the belt, you look at what's currently on the paper, look at the item, do some arithmetic, cross out the old number, and write the new one. That's your callback. Its two important inputs are "what's on the paper right now" (the accumulator) and "the item in front of me."

When the belt runs out, you read whatever's on the paper. That's what reduce returns.

Where it breaks down: the scrap of paper doesn't have to hold a number. It can hold an array, an object, a string, a Map — anything. It's one slot that gets overwritten each round, and it can hold any shape of value you like. Hold onto that, it's the key to the interesting uses.

Here it is with the simplest possible example:

const prices = [12, 5, 8];

const total = prices.reduce((runningTotal, price) => {
  return runningTotal + price;  // 👈 the new value of the paper
}, 0);                          // 👈 what's written on the paper to start

console.log(total); // → 25

Let's trace it, round by round, exactly the way I'd want a candidate to trace it out loud:

RoundPaper (accumulator)Current itemReturned → new paper
start——0 (the initial value)
101212
212517
317825
endnothing left on the belt → return 25

The single most common bug in a reducer, by an enormous margin, is forgetting to return. If your callback returns undefined, you've just wiped the paper clean. Next round the accumulator is undefined, and everything downstream turns into NaN or a crash.

❌ Buggy 
const total = prices.reduce((runningTotal, price) => {
  runningTotal + price;   // 👈 no `return` — result is thrown away
}, 0);
console.log(total); // → NaN
✅ Fixed 
const total = prices.reduce((runningTotal, price) => {
  return runningTotal + price;
}, 0);
// or, with an implicit return:
const total2 = prices.reduce((sum, price) => sum + price, 0);
console.log(total, total2); // → 25 25

The paper can hold anything

Summing numbers is the boring case, and honestly if that's all reduce did, it wouldn't be worth its reputation. The real power shows up when the accumulator is an object.

Say we want to group users by role:

const users = [
  { name: 'Ada', role: 'admin' },
  { name: 'Linus', role: 'dev' },
  { name: 'Grace', role: 'admin' },
];

const byRole = users.reduce((groups, user) => {
  const bucket = groups[user.role] ?? [];
  return { ...groups, [user.role]: [...bucket, user.name] };
}, {});   // 👈 the paper starts as an empty object

// → { admin: ['Ada', 'Grace'], dev: ['Linus'] }

Same mechanic, exactly. Start with {} on the paper. Each round, take what's on the paper, produce a new object that also includes this user, write that back. At the end, read the paper.

Under the hood

That version copies the whole accumulator object every single round ({ ...groups }), which is O(n²) work over the array. For a list of 50 users, who cares. For 500,000, it'll hurt. Since the accumulator here is a brand-new object that nothing outside the reduce can see yet, mutating it is safe and much faster:

const byRole = users.reduce((groups, user) => {
  (groups[user.role] ??= []).push(user.name);
  return groups;   // 👈 still must return it!
}, {});

The rule I use: mutating the accumulator is fine when the accumulator was created by this reduce and never escapes it. Mutating something that came from outside is a side effect and a bug waiting to happen. There's also Object.groupBy(users, u => u.role) in modern runtimes, which does exactly this and reads better — mention it and you'll sound current.

The initial value is not optional (well — it is, and that's the trap)

You can leave off the second argument. Then reduce uses the array's first element as the starting value on the paper and begins iterating from the second. That's convenient for summing, and it's a landmine everywhere else:

[].reduce((a, b) => a + b);
// → TypeError: Reduce of empty array with no initial value

[].reduce((a, b) => a + b, 0);
// → 0  ✅

An empty array is not an exotic edge case — it's what your API returns on a user's first day. Always pass the initial value unless you have a specific reason not to. It also documents the accumulator's type at a glance, which is the other reason to do it: seeing , {}) at the end tells the reader "the paper holds an object" without them having to decode the callback.

map and filter are just reduce in disguise

Here's the thing that makes reduce click permanently. Both of the other two can be written with it, and writing them out is the best way I know to prove to yourself that you actually understand the accumulator.

map, rebuilt 
const map = (array, fn) =>
  array.reduce((result, item) => {
    result.push(fn(item));  // 👈 paper holds an array; add the transformed item
    return result;
  }, []);

map([1, 2, 3], (n) => n * 2); // → [2, 4, 6]
filter, rebuilt 
const filter = (array, predicate) =>
  array.reduce((result, item) => {
    if (predicate(item)) result.push(item);  // 👈 add it only if it passes
    return result;
  }, []);

filter([1, 2, 3, 4], (n) => n % 2 === 0); // → [2, 4]

Identical machinery. The paper starts as []. The only difference is whether you push unconditionally (map) or conditionally (filter). So reduce is the general-purpose engine, and map/filter are two pre-configured settings on it.

So when is reduce the wrong tool?

Constantly, actually — and knowing this is a stronger signal in an interview than being able to write a clever reducer.

Because reduce can do anything, it tells the reader nothing. When I see .map(, I know before reading the callback: same length, transformed. When I see .reduce(, I know nothing and have to read the whole body. So the practical rule is:

Use the most specific method that fits the job. find over filter()[0]. some over filter().length > 0. map over a reduce that pushes one item per input. Reach for reduce only when you're genuinely collapsing a list into a differently-shaped single value.

❌ Reduce doing map's job 
const names = users.reduce((acc, user) => {
  acc.push(user.name);
  return acc;
}, []);
✅ Just say what you mean 
const names = users.map((user) => user.name);

And one more: if your reducer body has grown past about ten lines, or it's doing async work, or it needs to break early — stop. A plain for...of loop is not a failure. It's frequently the clearest thing in the file. reduce can't short-circuit; it always visits every element. A loop can break.

4. The rest of the family — and forEach vs map

Quick tour, because these are the ones that make reduce unnecessary most of the time:

const nums = [3, 8, 12, 5];

nums.find((n) => n > 6);      // → 8      first match, or undefined
nums.findIndex((n) => n > 6); // → 1      its index, or -1
nums.some((n) => n > 10);     // → true   "is there at least one?"
nums.every((n) => n > 1);     // → true   "are they all?"

find, some, and every all short-circuit — they stop the moment they know the answer. some bails on the first true; every bails on the first false. That's a real performance difference on big arrays, and it's a nice detail to mention out loud.

flatMap is map followed by one level of flattening, which is the clean way to say "each item produces zero, one, or many results":

const orders = [
  { id: 1, items: ['mug', 'pen'] },
  { id: 2, items: [] },
  { id: 3, items: ['book'] },
];

orders.flatMap((order) => order.items);
// → ['mug', 'pen', 'book']

// Returning [] from flatMap is a neat "drop this one":
orders.flatMap((order) => (order.items.length ? [order.id] : []));
// → [1, 3]

forEach vs map — the return value is the whole story

These look interchangeable. They aren't, and the difference is exactly one thing: map returns a new array; forEach returns undefined.

const doubled  = [1, 2, 3].map((n) => n * 2);
const nothing  = [1, 2, 3].forEach((n) => n * 2);

console.log(doubled); // → [2, 4, 6]
console.log(nothing); // → undefined  👈 forEach always returns undefined

Which means forEach can't be chained (there's nothing to chain onto) and is only useful for side effects — logging, pushing into an external array, updating the DOM. That's what it's for and there's nothing wrong with it.

The code-review flag is using map when you're not using the result:

❌ Misleading 
users.map((user) => sendWelcomeEmail(user)); // building an array of nothing
✅ Honest 
users.forEach((user) => sendWelcomeEmail(user));
// or: for (const user of users) sendWelcomeEmail(user);

Both lines send the emails. The first also builds and throws away an array of return values, and — more importantly — it lies to the next person reading it, who will scan for where the result is used and find nothing.

Wait, what about async?

Neither one waits. await inside a forEach callback does nothing useful — forEach doesn't know what a promise is, so it fires all callbacks and returns immediately. If you need sequential async work, use for...of with await. If you want them in parallel, use await Promise.all(users.map(fn)) — note that's map, because you actually want the array of promises.

5. Chaining vs a single pass

Chaining reads beautifully:

const total = orders
  .filter((order) => order.status === 'paid')
  .map((order) => order.amount)
  .reduce((sum, amount) => sum + amount, 0);

Three lines, each doing one obvious thing. This is good code and you should write it.

But be aware of what it costs: each link is a separate full walk of the array, and each of the first two allocates a whole new intermediate array that gets thrown away immediately. Three chained methods on 10 orders is 30 steps and two garbage arrays — completely irrelevant. On 2,000,000 orders, it's 6,000,000 steps and two multi-megabyte arrays that exist only to be discarded, and now you might feel it.

The single-pass version does the same job in one walk with no intermediates:

let total = 0;
for (const order of orders) {
  if (order.status !== 'paid') continue;
  total += order.amount;
}
In an interview

If someone asks "is chaining bad for performance?", the mediocre answer is "yes, use a loop." The good answer is a trade-off with a threshold: "Each link is another O(n) pass plus an intermediate array. It's the right default because it's far more readable, and for typical UI-sized lists the cost is noise. I'd only collapse it into a single loop or a single reduce if profiling showed it mattered — big arrays, or a hot path like a scroll handler." That answer says you know the cost and that you don't optimise blindly, which is the signal they're actually after.

6. Pure functions, side effects, and why React cares

A function is pure when two things hold:

  1. Given the same inputs, it always returns the same output.
  2. It doesn't change anything outside itself while doing so.

That second one — changing things outside itself — is a side effect. Writing to a global, mutating an argument, logging to the console, writing to localStorage, making a network request, touching the DOM, reading Date.now() or Math.random(). (The last two break rule 1 too: same input, different output.)

✅ Pure 
function applyDiscount(cart, percent) {
  return { ...cart, total: cart.total * (1 - percent / 100) };
}
❌ Impure — mutates its argument 
function applyDiscount(cart, percent) {
  cart.total = cart.total * (1 - percent / 100);  // 👈 caller's object changed
  analytics.track('discount');                    // 👈 and it phones home
  return cart;
}

The second one works. It'll pass a happy-path test. But it has quietly modified an object that someone else owns, and now any other part of the app holding that same cart reference sees a different total than it did a moment ago, with no idea why.

The mental model

A pure function is a vending machine. Same coins, same button, same snack, every time. It doesn't matter what time it is, who's using it, or what happened yesterday. You can predict its behaviour completely from what you put in.

An impure function is a vending machine that sometimes also sends a text to your boss, occasionally restocks itself based on the weather, and once in a while reaches into your bag. It might still give you the snack! But you can no longer reason about it in isolation, which means you can no longer test it in isolation either.

Where it breaks down: side effects aren't evil — an app that never touches the network or the screen does nothing. The goal isn't purity everywhere; it's pushing effects to the edges so the core logic stays predictable.

Why testability follows for free

Testing the pure version is three lines with no setup: call it, check the return value. Testing the impure one means mocking analytics, and then asserting on the mutation, and then remembering to build a fresh cart for every test because the previous test contaminated it. Purity isn't an aesthetic preference — it's the thing that makes tests cheap.

Why React specifically cares

React's whole model is: your component is a function from props and state to a description of the UI, and React may call it whenever it likes. That last part is the load-bearing bit. React reserves the right to render your component:

  • Twice in a row — in Strict Mode during development, React deliberately double-invokes your component body to smoke out impure code. If your component pushes into an array outside itself, you'll see doubled entries. That's the point; it's a purity detector.
  • Speculatively, then throw the result away — with concurrent rendering, React can start rendering, decide something more urgent came up, abandon that work and redo it later. If rendering had a side effect, that effect happened for a render nobody ever saw.
  • Not at all — React.memo, useMemo and friends skip work when inputs haven't changed. That's only safe if "same inputs → same output" is true. If your render depends on a hidden mutable variable, memoization will happily serve stale UI.

So the rule "keep your render pure" isn't dogma. It's the contract that lets React do all three of those things safely. Side effects go in useEffect, in event handlers, or in the code you call from them — never in the component body. And the same applies to reducers: a useReducer reducer must be pure, for exactly the same reasons.

Model answer — "what's a pure function and why does React care?"

"A pure function always returns the same output for the same input and doesn't mutate anything outside itself. React cares because it treats your component as a function it can call whenever it wants — it double-invokes components in Strict Mode to catch impurity, it can start a render and abandon it under concurrent rendering, and memoization only works if the same props reliably produce the same output. So the render path stays pure and effects go in useEffect or event handlers."

Why it lands: you connected purity to three concrete React behaviours instead of saying "it's cleaner." That's the difference between having read the docs and having debugged a double-render.

7. Currying and partial application

These two get used interchangeably, and interviewers know it — "what's the difference between currying and partial application?" is a favourite Tier-3 follow-up precisely because most candidates use the words as synonyms. Let's make the distinction sharp.

Partial application: pre-filling some arguments

Start here, because it's the intuitive one. You've got a function that takes several arguments, and you want to lock in some of them now and supply the rest later.

function log(level, module, message) {
  console.log(`[${level}] ${module}: ${message}`);
}

const logError = log.bind(null, 'ERROR');       // 👈 fix 1 of 3 args
const logAuthError = logError.bind(null, 'auth'); // 👈 fix another

logAuthError('token expired');
// → [ERROR] auth: token expired

That's partial application: taking an n-argument function and producing a function of fewer arguments by fixing some of them. logError still takes two arguments at once. You didn't change the function's shape; you just pre-loaded part of it.

You can do it by hand without bind, which makes what's happening obvious:

const partial = (fn, ...fixed) => (...rest) => fn(...fixed, ...rest);

const logError = partial(log, 'ERROR');
logError('auth', 'token expired'); // → [ERROR] auth: token expired

Currying: changing the function's shape

Currying is a transformation. It takes f(a, b, c) and turns it into f(a)(b)(c) — a chain of functions that each take exactly one argument and return the next function in the chain, until the last one has everything it needs and finally runs the original.

// Written by hand, the long way:
function log(level) {
  return function (module) {
    return function (message) {
      console.log(`[${level}] ${module}: ${message}`);
    };
  };
}

log('ERROR')('auth')('token expired');
// → [ERROR] auth: token expired

Read that middle block slowly. log('ERROR') doesn't log anything — it returns a function that's remembered level. Call that with 'auth' and you get a third function that's remembered both. Only the final call has all three pieces and actually does the work. Every step is a closure holding one more piece of the puzzle.

With arrow chaining it collapses to something almost unreadable-in-a-good-way:

const log = (level) => (module) => (message) =>
  console.log(`[${level}] ${module}: ${message}`);

const logError = log('ERROR');
const logAuthError = logError('auth');

logAuthError('token expired'); // → [ERROR] auth: token expired
logAuthError('bad password');  // → [ERROR] auth: bad password

Every arrow after the first is "return a function." That's the trick to reading these: a => b => c => body means "give me a, I'll give you something that wants b."

So what's the actual difference?

CurryingPartial application
What it isA transformation of a function's shapeAn act of pre-filling arguments
Args per callExactly one, alwaysHowever many you like
ResultA chain of unary functionsOne function with fewer parameters
Examplef(a)(b)(c)f.bind(null, a) → g(b, c)

The one-liner I'd say out loud: currying is about the function's structure; partial application is about supplying arguments early. They're related because a curried function makes partial application trivial — calling log('ERROR') is partially applying it — but you can partially apply a function that was never curried, and currying a function you then call as f(a)(b)(c) in one go isn't partial application at all.

A generic curry helper

Libraries like Lodash and Ramda ship a curry that's more forgiving: it accepts arguments one at a time or several at a time. Being able to sketch it is a good party trick and a plausible whiteboard question.

function curry(fn) {
  return function curried(...args) {
    if (args.length >= fn.length) {  // 👈 fn.length = declared parameter count
      return fn.apply(this, args);
    }
    return (...rest) => curried.apply(this, [...args, ...rest]);
  };
}

const volume = curry((l, w, h) => l * w * h);

volume(2)(3)(4);  // → 24
volume(2, 3)(4);  // → 24
volume(2)(3, 4);  // → 24

The engine here is fn.length, which is how many parameters the function declares. We keep collecting arguments in a closure until we have at least that many, then fire. (Caveat worth naming out loud: fn.length ignores rest params and parameters with defaults, so curry can't handle variadic functions — which is exactly why Lodash's version lets you specify an arity manually.)

Why does any of this exist?

Fair question — the syntax is undeniably weird. Three honest reasons:

1. Configuration once, use many times. You've got a function whose first argument barely changes:

const request = (baseUrl) => (path) => fetch(baseUrl + path);
const api = request('https://api.example.com');

api('/users');
api('/orders');   // 👈 nobody has to remember the base URL again

2. Better callbacks. Curried functions slot into map/filter without a wrapper arrow:

const prop = (key) => (obj) => obj[key];
const names = users.map(prop('name'));   // instead of (u) => u.name

3. Generic event handlers. This one you'll actually use in React:

const handleChange = (field) => (event) =>
  setForm((form) => ({ ...form, [field]: event.target.value }));

<input onChange={handleChange('email')} />
<input onChange={handleChange('name')} />
Wait — doesn't that create a new function every render?

Yes. handleChange('email') runs on every render and produces a fresh function each time. For a plain DOM <input> that's genuinely fine — React swaps the handler reference cheaply, and you should not contort your code to avoid it. It only matters if that prop is going into a React.memo'd child, where a new function reference defeats the memoization. Knowing when it doesn't matter is as valuable as knowing when it does.

8. Composition and pipe

If small pure functions are the parts, composition is the bolt that joins them. pipe takes a list of functions and returns one function that runs them left to right, feeding each result into the next:

const pipe = (...fns) => (input) =>
  fns.reduce((value, fn) => fn(value), input);   // 👈 reduce again!

const trim = (s) => s.trim();
const lower = (s) => s.toLowerCase();
const slugify = (s) => s.replace(/\s+/g, '-');

const toSlug = pipe(trim, lower, slugify);
toSlug('  Hello World  '); // → 'hello-world'

Notice the implementation is a reduce where the accumulator is the value flowing through, and the items on the belt are the functions. That's a nice little proof that you've internalised the accumulator model.

compose is the same thing right-to-left, matching mathematical notation (f(g(x))):

const compose = (...fns) => (input) =>
  fns.reduceRight((value, fn) => fn(value), input);

const toSlug = compose(slugify, lower, trim); // reads bottom-up

I reach for pipe basically always, because reading order matching execution order is worth more than matching a maths convention.

9. Debounce vs throttle

Here's the problem that motivates both. You've got a search box that hits your API on every keystroke:

input.addEventListener('input', (event) => {
  fetch('/api/search?q=' + event.target.value);
});

Someone types "headphones". That's ten keystrokes, so ten network requests, nine of which are for prefixes nobody wants results for. Worse, they can come back out of order — the response for "headphone" might land after the one for "headphones", and now your UI is showing results for a query the user already finished typing.

The events are arriving faster than we want to act on them. We need a way to turn a fast stream of calls into a slower one. There are two fundamentally different ways to do that, and they answer two different questions:

  • Debounce asks: "has it gone quiet yet?" Wait until the events stop for a bit, then act once.
  • Throttle asks: "has enough time passed?" Act at a steady maximum rate no matter how many events arrive.
The analogies

Debounce is an elevator door. The door is set to close 5 seconds after the last person steps in. Someone new walks in? The 5-second timer resets from scratch. If people keep trickling in, the door never closes. It closes exactly once, 5 seconds after the last person. That reset-on-every-event behaviour is the entire essence of debounce.

Throttle is a metering light on a motorway on-ramp. One car every 3 seconds. Doesn't matter if there are two cars queued or two hundred — the light's rhythm is fixed. Cars that show up between greens just don't get through. Steady rate, regardless of demand.

Where they break down: a real elevator eventually forces the door shut no matter what (that's a maxWait option in Lodash's debounce, which most hand-rolled versions don't have). And a real on-ramp queues the cars — a leading-edge throttle discards the calls it skips, it doesn't queue them.

Seeing it: the same burst, both ways

Words only get you so far here. This is the diagram I'd draw on a whiteboard if I got this question, and drawing it is often worth more than the code:

Three things to take from that picture:

  1. Debounce fired nothing during the burst. Five keystrokes in quick succession produced zero calls until the typing stopped. If the user never stops, debounce never fires.
  2. Throttle fired immediately on the very first event, then rationed the rest. It's responsive from the first moment; debounce always has a delay baked in.
  3. Both reduced 8 calls to 3–4, but they chose different calls, and that choice is what makes them suited to different jobs.

Leading edge vs trailing edge

Both patterns have a knob: do you fire at the start of the activity or at the end?

  • Trailing edge (the default for debounce): fire after the quiet period. You get the final value, which is what you want for a search box — you want to search for "headphones", not "h".
  • Leading edge (the default for throttle): fire on the first call, immediately. You get responsiveness. This is what you want for a submit button, where the first click is the real one and the rest are impatience.

You can have both, or either, on either pattern. A leading-edge debounce fires immediately and then ignores everything until things go quiet — which is the classic "prevent double-submit" recipe. Lodash exposes these as { leading, trailing } options.

Implementing debounce

Let's build it. The whole thing is nine lines, and every one of them is doing something you already understand from section 2.

function debounce(fn, wait) {
  let timeoutId;                       // 👈 private, remembered between calls

  return function debounced(...args) {
    clearTimeout(timeoutId);           // 👈 cancel the previously scheduled run
    timeoutId = setTimeout(() => {
      fn.apply(this, args);            // 👈 run with the LATEST args
    }, wait);
  };
}

const search = debounce((query) => fetch('/api/search?q=' + query), 300);

Walk it through the way you would out loud in an interview:

  1. debounce is a higher-order function: takes a function, returns a function. Nothing runs yet.
  2. timeoutId lives in the closure. It's created once, when debounce is called, and every subsequent call to debounced sees and updates the same variable. That shared, private variable is the entire mechanism — remember it, because it's exactly what the React bug destroys.
  3. Every call cancels the pending timer and schedules a fresh one. That's the elevator door resetting.
  4. Only when wait milliseconds pass with no new call does the timer survive to completion and actually run fn.
  5. fn.apply(this, args) forwards whatever arguments and this the last call had, so the wrapper is a transparent stand-in for the original. (Note the wrapper is a function, not an arrow — an arrow would capture this lexically and break method usage.)

Two small details worth knowing: calling clearTimeout with undefined on the very first invocation is completely safe — it's a no-op, so we don't need a guard. And it's the last call's arguments that win, which is exactly right for a search box.

Implementing throttle

function throttle(fn, interval) {
  let lastRun = 0;                          // 👈 timestamp of the last real call

  return function throttled(...args) {
    const now = Date.now();
    if (now - lastRun < interval) return;   // 👈 too soon — drop this call
    lastRun = now;
    fn.apply(this, args);
  };
}

window.addEventListener('scroll', throttle(updateHeader, 100));

Same skeleton — a closure variable that persists across calls — but the logic inverts. Instead of "reset the timer," it's "look at the clock; if it's too soon, do nothing at all." No setTimeout needed for this version. It's leading-edge: the first call always goes through, since now - 0 is enormous.

Its one weakness is visible in the diagram: it drops the final call. If the user scrolls and stops 20ms after the last permitted run, that final position never gets handled. For a scroll handler that can leave the UI slightly stale. The fix is a trailing edge — schedule the last dropped call to run when the window opens:

function throttle(fn, interval) {
  let lastRun = 0;
  let timeoutId = null;

  return function throttled(...args) {
    const remaining = interval - (Date.now() - lastRun);

    if (remaining <= 0) {          // window is open → run now
      clearTimeout(timeoutId);
      timeoutId = null;
      lastRun = Date.now();
      fn.apply(this, args);
    } else if (timeoutId === null) { // window closed → book the trailing call
      timeoutId = setTimeout(() => {
        lastRun = Date.now();
        timeoutId = null;
        fn.apply(this, args);
      }, remaining);
    }
  };
}

You do not need to reproduce that from memory. But knowing why it exists — "the simple version drops the trailing call, which matters for scroll position" — is exactly the kind of depth that turns a passing answer into a strong one.

cancel and flush

A debounced function has a pending timer, which means there are two things you might want to do to it before it fires:

  • cancel() — throw away the pending call. Nothing runs. Essential on unmount: if a component schedules a search and then gets removed from the page, you don't want that fetch firing into a component that no longer exists.
  • flush() — run the pending call right now instead of waiting. Useful when a user hits Save while an autosave debounce is still pending: you want the save to happen immediately, not 2 seconds later.

Because a function is an object, we can just hang these on it:

function debounce(fn, wait) {
  let timeoutId;
  let lastArgs;                       // 👈 remember args so flush can use them

  function debounced(...args) {
    lastArgs = args;
    clearTimeout(timeoutId);
    timeoutId = setTimeout(() => {
      timeoutId = null;
      fn.apply(this, lastArgs);
    }, wait);
  }

  debounced.cancel = () => {
    clearTimeout(timeoutId);
    timeoutId = null;
  };

  debounced.flush = () => {
    if (timeoutId === null) return;   // nothing pending
    clearTimeout(timeoutId);
    timeoutId = null;
    fn.apply(this, lastArgs);
  };

  return debounced;
}

Which one for which job?

SituationPickWhy
Search-as-you-typeDebounce (trailing, ~300ms)You only care about the finished query. Intermediate prefixes are wasted requests and cause out-of-order results.
Scroll / resize handlerThrottle (~100ms)You want continuous feedback while scrolling. Debounce would freeze the UI until the user stopped — which is the whole time they're looking at it.
Infinite scroll "load more"ThrottleYou must check "are we near the bottom?" during the scroll, not after it ends.
Form autosaveDebounce (~1–2s)Save when they pause typing. Add flush() on explicit save and on navigate-away.
Button double-submitThrottle, or leading-edge debounceThe first click is the real one. Trailing debounce would be wrong — it'd delay the response to a deliberate click.
Validating a field on blurNeitherBlur fires once. Don't add machinery you don't need.
A trap worth avoiding

Saying "debounce for the search box" and stopping there is a fine answer, but it's the answer everyone gives. The follow-up that catches people is "why not throttle a search box?" — and the sharp answer is: throttle would fire mid-word. Typing "headphones" at 150ms throttle sends requests for "hea", "headph", "headphones" — you've cut the request count but you're still querying garbage, and you still have the out-of-order-response problem. Debounce is the right shape because the only query that matters is the one they stopped on.

Model answer — "debounce vs throttle?"

"Both limit how often a function runs, but they answer different questions. Debounce waits for a pause — every call resets the timer, so it fires once, after the activity stops. Throttle enforces a maximum rate — it fires immediately and then ignores calls until the interval has elapsed. So debounce for a search box, where I only care about the final query, and throttle for scroll or resize, where I need continuous updates but not sixty a second. The implementation difference is that debounce is a setTimeout you keep clearing, and throttle is a timestamp you compare against."

Why it lands: you gave the mechanism, not just the vibe, and you tied each to a use case with a reason. The last sentence in particular signals you've written both rather than read about them.

10. Why your debounce doesn't work in React

This is a real bug that a lot of people hit and can't explain, which makes it a great interview question. Here's the code:

❌ Buggy — debounces nothing at all 
function SearchBox() {
  const [query, setQuery] = useState('');

  // 👇 a NEW debounced function is created on every single render
  const debouncedSearch = debounce((value) => {
    fetch('/api/search?q=' + value);
  }, 300);

  return (
    <input
      value={query}
      onChange={(event) => {
        setQuery(event.target.value);
        debouncedSearch(event.target.value);
      }}
    />
  );
}

Type "headphones" into that and watch the network tab. Ten requests. The debounce did absolutely nothing.

Why? Think back to what makes debounce work: the timeoutId variable living in the closure, shared across every call to the returned function. clearTimeout(timeoutId) only cancels anything if it's looking at the same timeoutId that the previous call set.

But a React component body re-runs on every render. Typing a character calls setQuery, which triggers a render, which runs the component body again, which calls debounce(...) again, producing a brand-new function with a brand-new, empty timeoutId. That new function's clearTimeout(undefined) cancels nothing — certainly not the timer belonging to the previous render's function, which it has never heard of. So every keystroke schedules its own independent 300ms timer, and 300ms later they all fire.

The picture

Each render hires a brand-new receptionist who's told "hold this call for 300 seconds." The new receptionist doesn't know about the calls the previous ten receptionists are holding, and can't cancel them. You wanted one receptionist reconsidering; you got ten receptionists each patiently waiting their turn.

The fix, step one: keep the same function across renders

useMemo with an empty dependency array creates the debounced function once and hands back that same reference on subsequent renders:

✅ Fixed — one debounced function for the component's lifetime 
function SearchBox() {
  const [query, setQuery] = useState('');

  const debouncedSearch = useMemo(
    () => debounce((value) => fetch('/api/search?q=' + value), 300),
    []                                   // 👈 created once
  );

  useEffect(() => {
    return () => debouncedSearch.cancel(); // 👈 don't fire after unmount
  }, [debouncedSearch]);

  return (
    <input
      value={query}
      onChange={(event) => {
        setQuery(event.target.value);
        debouncedSearch(event.target.value);
      }}
    />
  );
}

Now every keystroke calls the same debounced function, which sees the same timeoutId, and the resetting actually resets. One request.

The useEffect cleanup matters more than it looks. Without it, a user who types and immediately navigates away leaves a timer that fires 300ms later into a dead component. In the best case you waste a request; in the worse case the callback touches state and you get a warning or a leak.

The fix, step two: the stale closure problem

There's a second bug lurking, and this is the level that impresses. Suppose the debounced callback needs something from state or props:

❌ Subtly buggy — captures the first render's values 
const debouncedSave = useMemo(
  () => debounce(() => saveDraft(userId, text), 1000),
  []   // 👈 created once, so it froze `userId` and `text` from render #1
);

Because the function was created on the first render and never recreated, its closure holds the first render's text — probably an empty string. Every autosave writes the wrong thing, forever. Adding [text] to the deps "fixes" the staleness but recreates the debounced function on every keystroke, putting us straight back into the original bug. It's a genuine tension.

The way out is to separate the two concerns: keep the debounced wrapper stable forever, but let it read the latest callback out of a ref at fire time.

✅ Fixed — stable wrapper, always-fresh callback 
function useDebouncedCallback(callback, wait) {
  const callbackRef = useRef(callback);

  // Keep the ref pointing at the newest version of the callback
  useEffect(() => {
    callbackRef.current = callback;
  });

  const debounced = useMemo(
    () => debounce((...args) => callbackRef.current(...args), wait),
    [wait]                                  // 👈 stable unless the delay changes
  );

  useEffect(() => debounced.cancel, [debounced]); // cleanup on unmount
  return debounced;
}

// Usage:
const debouncedSave = useDebouncedCallback(() => saveDraft(userId, text), 1000);

Read the key line again: debounce((...args) => callbackRef.current(...args), wait). The debounced function's closure captures callbackRef — an object that never changes identity — rather than callback itself. When the timer eventually fires, it reads .current at that moment, which is whatever the latest render put there. Stable outside, fresh inside.

Under the hood — why not just useMemo?

useMemo is documented as a performance hint, not a semantic guarantee — React reserves the right to throw away a cached value and recompute it (it does this when unmounting offscreen content, for instance). For a memoized calculation that's harmless. For something with identity that matters, like a debounced function holding a live timer, a discarded cache means a new timeoutId and a silently broken debounce.

The bulletproof version stores it in a ref, which React genuinely promises to preserve:

const ref = useRef(null);
if (ref.current === null) {
  ref.current = debounce((...args) => callbackRef.current(...args), wait);
}
const debounced = ref.current;

In practice useMemo works fine for this and is what most codebases (and most library hooks) do. But being able to say "useMemo isn't a guarantee, so strictly a ref is safer" is a genuinely senior-sounding observation.

11. Memoization

Last pattern, and it's the same shape as everything else in this guide: a higher-order function that wraps another function and keeps something private in a closure. This time the private thing is a cache.

function memoize(fn) {
  const cache = new Map();               // 👈 private, lives as long as the wrapper

  return function memoized(...args) {
    const key = JSON.stringify(args);
    if (cache.has(key)) {
      return cache.get(key);             // 👈 skip the work entirely
    }
    const result = fn.apply(this, args);
    cache.set(key, result);
    return result;
  };
}

const slowFib = (n) => (n < 2 ? n : slowFib(n - 1) + slowFib(n - 2));
const fib = memoize(slowFib);

fib(35); // slow the first time
fib(35); // → instant

The idea is trivial: remember what you computed, and if you're asked the same question again, recite the answer instead of redoing the work. The interesting parts are all in the failure modes.

Problem 1: the cache key

JSON.stringify(args) is the quick-and-dirty key, and it is wrong in several ways you should be able to name:

  • Key order matters. { a: 1, b: 2 } and { b: 2, a: 1 } stringify differently, so two logically identical calls get two cache entries and the second is a miss.
  • Values get silently mangled. undefined and functions disappear from objects, so f({ a: undefined }) and f({}) collide. NaN becomes null. Dates become strings, so a Date and its ISO string collide.
  • Circular references throw. Pass a DOM node or a React element and JSON.stringify crashes.
  • Stringifying can cost more than the function. If you memoize a cheap function that takes a big object, you're now serialising a big object on every call to avoid doing almost nothing. That's a net loss.

For the very common single-object-argument case, there's a much better answer: key on the object identity with a WeakMap.

function memoizeOne(fn) {
  const cache = new WeakMap();   // 👈 keys must be objects; held weakly

  return function (arg) {
    if (cache.has(arg)) return cache.get(arg);
    const result = fn(arg);
    cache.set(arg, result);
    return result;
  };
}

The magic word is weakly. A WeakMap doesn't stop its keys from being garbage collected — when the rest of your app drops the last reference to that object, the cache entry vanishes on its own. Which leads directly to the next problem.

Problem 2: an unbounded cache is a memory leak

The Map-based memoize above never removes anything. Ever. Memoize a function called with a user ID and run it across a million users, and you've built a structure holding a million entries that nothing will ever clean up, because the cache holds a strong reference to every key and value.

The usual fixes:

  • Cap it. An LRU (least-recently-used) cache keeps the N most recent entries and evicts the oldest. Bounded memory, most of the benefit.
  • Cache size 1. Sounds useless; it's often perfect. If calls repeat consecutively — which is exactly what happens in a React render loop — remembering only the last (args, result) pair captures nearly all the wins for constant memory. This is what the memoize-one library does, and it's the model behind useMemo.
  • WeakMap keys, as above, when the arguments are objects whose lifetime you don't control.

Problem 3: it only works for pure functions

Here's where section 6 pays off. Memoization replaces "call the function" with "maybe don't call the function." That substitution is only safe if calling it produces the same result and does nothing else observable.

Memoize something that reads Date.now(), or hits the network, or increments a counter, and you get a function that lies: it returns yesterday's answer, or skips the effect entirely on the second call. Purity is the precondition for memoization — and saying that sentence in an interview links two topics together in a way that reads as real understanding.

When memoization hurts

  • The function is already cheap. Hashing the arguments and doing a Map lookup isn't free. Memoizing (a, b) => a + b makes it slower and leaks memory.
  • Arguments rarely repeat. A cache with a 2% hit rate is pure overhead plus a growing heap.
  • The underlying data changes. A cache keyed on a user ID goes stale the moment that user is edited. Now you need invalidation, which is a whole problem of its own.
  • Long-lived module-scope caches. A memoized function at module scope lives for the entire session. Inside a component instance, at least it dies with the component.
Model answer — "how would you memoize an expensive function?"

"I'd write a higher-order function that closes over a cache — a Map from a key derived from the arguments to the result. On each call, check the cache, return the hit, otherwise compute and store. The two things I'd think hard about are the key and the eviction policy: JSON.stringify is a fine default but breaks on key ordering and circular references, so for a single object argument I'd use a WeakMap keyed on identity. And an unbounded cache is a memory leak, so in production I'd cap it with an LRU — or just cache the last result, which covers most real cases. It also only works if the function is pure."

Why it lands: anyone can write the ten-line memoize. Naming the key problem, the eviction problem, and the purity precondition unprompted is what separates a junior answer from a senior one.

12. Interview follow-ups, answered

These are the second questions — the ones that come after you've given the textbook answer and the interviewer wants to know whether you've actually used this stuff. I'd read this section twice.

"Walk me through implementing debounce."

Narrate the structure before you write a line: "It's a higher-order function. It takes a function and a wait time and returns a wrapper. The wrapper needs one piece of state that survives between calls — the pending timer ID — and a closure is exactly how you get that." Then: every call clears the pending timer and sets a new one; only a call that isn't followed by another within wait ms survives to fire. Forward ...args and use fn.apply(this, args) so the wrapper is a transparent stand-in, and use a function expression rather than an arrow so this isn't captured lexically. Mention that clearTimeout(undefined) is a safe no-op so the first call needs no guard. If you have time, add .cancel() — unprompted, that's a strong signal.

"And throttle?"

Same skeleton, different bookkeeping. Instead of a timer ID you keep a timestamp of the last real run; on each call compare Date.now() - lastRun against the interval and return early if it's too soon. Then volunteer the weakness before they ask: "This is leading-edge only, so it silently drops the final call. For a scroll handler that can leave the UI one frame stale, so a production version schedules a trailing call with the remaining time." Also worth mentioning: for anything that touches layout or paints, requestAnimationFrame is often a better throttle than a timer, because it syncs with the browser's paint cycle instead of guessing at an interval.

"Which would you use for a search box, and why?"

Debounce, trailing edge, around 300ms. The reason: the only query worth sending is the one the user stopped on. Throttle would fire mid-word — you'd cut the request count but still be querying prefixes nobody typed on purpose. Then add the bit most people miss: even with debounce you can get out-of-order responses if the user resumes typing, so you want an AbortController to cancel the in-flight request, or a check that the response matches the current query before rendering it. And say what happens on submit: hit flush() or bypass the debounce so pressing Enter doesn't wait 300ms.

"Why not just throttle everything? It's simpler."

Because throttle guarantees the wrong thing for tail-sensitive work. Throttle promises "at most once per interval" but promises nothing about the last event — with a leading-edge throttle, the final keystroke or the final scroll position can be dropped entirely. When you specifically care about the settled, final state (search query, autosave, resize-then-recalculate), you want debounce. When you care about a steady stream of intermediate updates (scroll position, drag, progress bar), you want throttle. They're not two settings of the same dial; they optimise for opposite ends of the burst.

"What's the difference between currying and partial application?"

Currying transforms a function's shape: f(a, b, c) becomes f(a)(b)(c), a chain of one-argument functions each returning the next. Partial application is the act of fixing some arguments now and getting back a function that takes the rest — f.bind(null, a) gives you a function still taking (b, c) together. They're related because calling a curried function with fewer than all its arguments is partial application, but you can partially apply a function that was never curried. One-liner: currying is about structure, partial application is about supplying arguments early.

"What's a pure function, and why does React care?"

Same input → same output, and no observable side effects. React cares because it treats your component as a function it can call whenever it likes: Strict Mode deliberately double-invokes component bodies in development to surface impurity, concurrent rendering can start a render and throw it away, and memo/useMemo only produce correct results if identical inputs reliably produce identical output. Break purity in the render path and you get doubled effects, stale memoized UI, or bugs that only appear under load. So effects live in useEffect and event handlers, and the same purity rule applies to useReducer reducers.

"When is reduce the wrong tool?"

Whenever a more specific method says what you mean. If you're producing one output per input, that's map. If you're keeping a subset, that's filter. If you want the first match, find; existence, some; universality, every. reduce is maximally general, which means it communicates the least — the reader has to decode the callback to know what shape comes out. It also can't short-circuit, so a search over a huge array with reduce visits every element where find stops at the first hit. And if the reducer's grown past ten lines, or needs await, or needs to break early, a plain for...of loop is the honest answer. Reserve reduce for genuinely collapsing a list into a differently-shaped value.

"map vs forEach?"

map returns a new array of the same length built from the callback's return values; forEach returns undefined and exists purely for side effects. Practically: if you're using the result, map; if you're not, forEach or a for...of. Using map and discarding the result builds a throwaway array and misleads the reader into hunting for where it's used. Neither awaits promises, so for async work use for...of with await for sequential, or Promise.all(items.map(fn)) for parallel — and note that's map, because there you genuinely want the array of promises back.

"Why doesn't my debounce work inside a React component?"

Because the debounced function is being recreated on every render. Debounce works by keeping a timeoutId in a closure and clearing it on the next call — if each render calls debounce() again, each keystroke gets a fresh function with a fresh, empty timeoutId, so clearTimeout cancels nothing and every call eventually fires. The fix is to create it once, with useMemo(() => debounce(fn, 300), []) or a ref, plus a useEffect cleanup that calls .cancel() on unmount. Then flag the second-order bug: with empty deps the callback captures the first render's props and state, so the robust version keeps the callback in a ref that each render updates, and the stable debounced wrapper reads ref.current when it fires.

"How would you memoize an expensive function?"

A higher-order function closing over a Map from an argument-derived key to a result: check, return on hit, compute and store on miss. Then immediately raise the two hard parts — the key (JSON.stringify breaks on object key order, undefined, NaN, Dates and circular refs; a WeakMap keyed on object identity is better for a single object argument) and eviction (unbounded caches are memory leaks; cap with an LRU, or cache just the last result). Close by noting it's only valid for pure functions — memoize something that reads the clock or hits the network and you've built a bug.

"Why not just use a library — Lodash has all of this."

You should, in production, and saying so is a strength rather than a dodge: Lodash's debounce handles leading/trailing edges, maxWait, cancel and flush, and years of edge cases you won't think of on a whiteboard. The reason to know the implementation is that the bugs are in how you use it, not in the library — recreating it every render in React, forgetting to cancel on unmount, choosing debounce where you needed throttle. Being able to reason about the closure is what lets you debug that.

"Are higher-order functions slower than loops?"

Marginally, yes — there's a function call per element and, for chained calls, an intermediate array per link. Modern JIT compilers inline a lot of that away, so the gap is usually small and swamped by whatever the callback does. The honest answer names the trade-off and the threshold: it's the right default for readability, and I'd convert a chain to a single loop only for very large arrays or a hot path like a scroll or animation handler, and only after measuring. Volunteering "after measuring" matters — the trap here is sounding like someone who micro-optimises by reflex.

Pure functionSame input → same output, no side effects. Trivially testable.
Why React caresStrict Mode double-invokes, concurrent rendering can discard a render, and memoization assumes purity. Effects go in useEffect / handlers.
Curryingf(a, b, c) → f(a)(b)(c). A shape change into one-argument functions.
Partial applicationFix some arguments now, supply the rest later. f.bind(null, a). About arguments, not shape.
pipeRun functions left to right, feeding each result to the next. It's a reduce over functions.
Debounce"Wait until it goes quiet." Every call resets the timer; fires once after the pause. clearTimeout + setTimeout.
Throttle"At most once per interval." Fires immediately, then rations. Compare against a stored timestamp.
Leading vs trailingLeading = fire on the first call (responsive, good for buttons). Trailing = fire after the burst (final value, good for search).
Search boxDebounce, trailing, ~300ms. Plus abort in-flight requests, plus flush on submit.
Scroll / resizeThrottle, ~100ms — or requestAnimationFrame if it touches layout.
cancel / flushcancel drops the pending call (use on unmount); flush runs it now (use on explicit save).
React debounce bugRecreated every render → new empty timeoutId → nothing ever cancelled. Fix with useMemo/useRef, plus a ref for the latest callback, plus cleanup.
MemoizeClosure over a cache. Hard parts: the key (WeakMap for object identity) and eviction (LRU or cache-size-1). Only valid for pure functions.

If there's one thread to pull through all of this, it's the one from section 2: a function that returns a function, with something private remembered in between. Debounce remembers a timer. Throttle remembers a timestamp. Memoize remembers a cache. A curried function remembers the arguments you've supplied so far. Once you can see that same shape underneath all four, you're not memorising four patterns any more — you're recognising one, four times. 🎯
