I want to start with a piece of code that has confused literally every JavaScript developer at some point. Read it, and take an actual guess at what it logs. Don't skip ahead — the guessing is the part that makes this stick.

What does this log?
const user = {
  name: 'Priya',
  greet() {
    console.log(`Hi, I'm ${this.name}`);
  },
};

user.greet();              // ?
const greet = user.greet;
greet();                   // ?
setTimeout(user.greet, 0); // ?
Show me the answer

The first one logs Hi, I'm Priya. The second logs Hi, I'm undefined. The third also logs Hi, I'm undefined (in a browser — in Node it's a little different, but still not Priya).

Here's what makes this genuinely weird. We didn't modify user. We didn't modify the function. We pulled the exact same function out of the exact same object and called it, and it behaved differently. Nothing about the function changed — and yet this.name went from 'Priya' to undefined.

That's not a bug. It's the single most important fact about this, and once you internalise it, ninety percent of the confusion evaporates. Let's build up to it.

The thing nobody tells you about this

Most tutorials introduce this as "a reference to the current object." That definition is not just incomplete — it's actively misleading, because it implies this is a property of the function, something baked in when the function was written.

It isn't. Here's the real deal:

this is an extra, invisible argument that gets passed to a function every time you call it. Its value is decided at the moment of the call — not when the function was defined, not by where the function lives, but by how you called it.

Think of it like a delivery address on a package. 📦 The package (the function body) is written once and sealed. But the shipping label — where it's going, whose hands it lands in — is stuck on at the moment of dispatch. Same package, different label, different destination. Ship the identical package twice with two different labels and it ends up in two different houses.

That's this. The function is the package. The call site sticks on the label.

This is why the code above behaves the way it does. user.greet() and greet() are two different call sites, so two different labels get stuck on.

Wait, what about…?

"Where does the analogy break down?" Good instinct. A shipping label is attached by you, deliberately. With this, the label is usually stuck on automatically by the shape of the syntax you used — you often don't realise you're addressing it at all. That's exactly why it bites people. There is a way to write the label by hand, and that's call/apply/bind, which we'll get to.

So: to work out what this is, you never look at where the function was written. You look at the line where it was called. Every time. Even years in, when I read unfamiliar code I still catch myself looking at the wrong place — the definition instead of the call. That reflex takes a while to retrain.

The four binding rules, as a decision procedure

There are exactly four ways this can get its value, and they have a strict priority order. If you memorise nothing else from this guide, memorise this ladder — you literally run it top to bottom at any call site and stop at the first match.

Now let's do each rung properly, but in the order that's easiest to learn — which is bottom to top, simplest to trickiest.

Rung 4: default binding

A plain function call, nothing to the left of it:

default binding
function whoAmI() {
  console.log(this);
}

whoAmI();  // → undefined   (in a module or 'use strict')
           // → Window      (in a plain non-strict script)

When there's no other information, this falls back to a default. In sloppy mode (old-school scripts without 'use strict') that default is the global object — window in a browser, globalThis generally. In strict mode it's undefined.

You should assume strict mode, because you're almost certainly in it. ES modules (anything with import/export) are strict automatically. Class bodies are strict automatically. Anything bundled by Vite, webpack, or Next.js is strict. So in modern code, "no label on the package" means this is undefined, and touching this.name throws:

TypeError: Cannot read properties of undefined (reading 'name')

That error message is one of the most common in all of frontend, and now you know what it usually means: somebody called a method without its object.

Rung 3: implicit binding

This is the everyday one. If the call has an object to the left of the dot, that object becomes this.

implicit binding
const cart = {
  items: ['mug', 'poster'],
  count() {
    return this.items.length;
  },
};

cart.count();  // → 2   this === cart

The mental shortcut people use is "look immediately left of the dot." That's mostly right, and it's a fine thing to say in an interview. But be careful: it's the last dot that counts, not the first.

const app = {
  ui: {
    label: 'Checkout',
    render() { return this.label; },
  },
};

app.ui.render();  // → 'Checkout'   this === app.ui, NOT app

Only the final .ui is doing the binding. The app. part just got us to the object; it doesn't stick around.

And here's the crucial detail: implicit binding is a property of the call expression, not of the function. The moment you separate the function from the dot — by assigning it to a variable, passing it as an argument, returning it — the binding is gone. It was never attached to the function. It only ever existed in that one call expression.

A common misconception

"The function belongs to the object, so it remembers the object."

It doesn't. user.greet is not a special "method object." It's an ordinary function that happens to be stored in a property, exactly like a number stored in a property. When you write const g = user.greet, you copy the function reference out — and a function reference carries no memory of where it was found. This is the whole reason the "lost this" bug exists, and we'll hit it head-on in a minute.

Rung 2: explicit binding

Sometimes you want to write the shipping label by hand. That's what call, apply, and bind are for.

explicit binding
function introduce(greeting) {
  console.log(`${greeting}, I'm ${this.name}`);
}

const dev = { name: 'Sam' };

introduce.call(dev, 'Hey');   // → Hey, I'm Sam
introduce.apply(dev, ['Yo']); // → Yo, I'm Sam

Notice introduce isn't stored on dev at all. There's no dot relationship here. We simply handed the function an object and said "use this as this." That's why it's called explicit — it beats implicit binding because you asked for it out loud. Full section on these three coming up.

Rung 1: new binding

The top of the ladder. When you call a function with new, JavaScript builds a brand-new empty object and makes that the this inside the call.

new binding
function Product(title, price) {
  this.title = title;
  this.price = price;
  // no return statement — but we still get an object back
}

const mug = new Product('Enamel mug', 12);
mug.title;  // → 'Enamel mug'

The function looks like it returns nothing, and yet mug is a fully-formed object. new did that. Exactly how it did it is one of the classic interview questions, and it involves prototypes, so I'm deliberately holding it until we've built the prototype half of this guide. We'll come back and take it apart line by line.

Running the ladder on a nasty example

Let's push on it. What does this log?

const timer = {
  seconds: 30,
  report() { console.log(this.seconds); },
};

const other = { seconds: 99 };

timer.report.call(other);   // ?
Work it out, then check

99. Run the ladder: not new (rung 1, no). Called with call? Yes — stop. Rung 2 wins, and this is other. The timer. dot looks like it should matter, and a naive "left of the dot" model gets this wrong. Explicit beats implicit, always.

Arrow functions: the fifth non-rule

Arrow functions break the entire ladder, and they break it in the best possible way: an arrow function has no this of its own at all.

Not "it has a special this." Not "its this defaults to the outer one." It genuinely does not have the binding. So when you write this inside an arrow function, JavaScript does exactly what it does with any other variable it can't find locally — it looks in the enclosing scope. And the one outside that. And so on, until it finds a function that does have a this.

Here's the analogy I like. A regular function is a person with their own phone number; call them and you reach them. An arrow function is more like a desk extension in an open-plan office — it has no line of its own, so calls route to whoever's sitting at the nearest real desk. Where the desk is installed decides who picks up, and that's fixed when the office was built. (Where it breaks down: a real extension can be re-patched by IT. An arrow's this can never be changed, by anyone, ever — see below.)

lexical this
const clock = {
  label: 'Session',
  start() {
    setTimeout(() => {
      console.log(`${this.label} finished`);  // 👈 which `this`?
    }, 1000);
  },
};

clock.start();  // → Session finished

The arrow has no this, so it borrows from start. And start was called as clock.start() — implicit binding, rung 3 — so this is clock. The arrow inherits that. This works no matter how deeply you nest arrows.

Swap in a regular function and it falls apart:

❌ Buggy
start() {
  setTimeout(function () {
    console.log(`${this.label} finished`);
    // → TypeError: Cannot read properties of undefined
  }, 1000);
}

Why? setTimeout calls that function later, on its own, with no object to the left of any dot. Rung 4: default binding. this is undefined.

Under the hood

Because arrows have no this slot, call, apply and bind cannot change an arrow's this. They don't error — they just silently do nothing to it:

const show = () => this;
show.call({ a: 1 });  // → still the outer this, not { a: 1 }

Same story for arguments and new: arrows don't have their own arguments object, and new (() => {}) throws TypeError: ... is not a constructor.

Trap

Don't write object methods as arrows when you need this to be the object:

const user = {
  name: 'Priya',
  greet: () => console.log(this.name),  // 👈 wrong
};
user.greet();  // → undefined

The arrow is created in the module/global scope — the object literal is not a scope — so it inherits this from there, not from user. Candidates get dinged for confidently claiming "arrows always fix this." Arrows fix this when the surrounding scope already has the right one.

The "lost this" problem, and three fixes

Now we're equipped to properly explain the snippet we opened with. This bug has a shape, and once you see the shape you'll spot it everywhere:

You hand a method to something else, and that something else calls it later, plainly. The dot never travels with the function.

❌ Buggy — three flavours of the same bug
setTimeout(user.greet, 100);          // greet() later, no dot
element.addEventListener('click', user.greet);
[1, 2, 3].forEach(counter.add);       // add(item) — no dot
<button onClick={this.handleClick}>  // React class component

In every case, the receiving code eventually does something like callback() or callback(arg). Rung 4. this is undefined, and any this.something in the body throws.

Wait, what about…?

"Why doesn't DOM addEventListener break, then? I've seen this work in event handlers." Because the DOM is a special case: when a listener fires, the browser explicitly calls your handler with this set to the element the listener is attached to. That's explicit binding done on your behalf. Which is also why an arrow handler gives you the surrounding this instead of the element — the arrow ignores what the DOM tried to hand it. Use event.currentTarget if you want the element regardless.

Fix 1: bind in the constructor

The classic React-class-component fix, and the one you'll see in older codebases.

✅ Fixed
class SearchBar extends React.Component {
  constructor(props) {
    super(props);
    this.handleClick = this.handleClick.bind(this);  // 👈
  }
  handleClick() {
    console.log(this.props.query);
  }
}

What's happening: this.handleClick finds the shared method, .bind(this) returns a new function permanently welded to this instance, and we store that new function directly on the instance. From then on, this.handleClick finds the bound copy first, and you can pass it anywhere safely.

Fix 2: arrow function as a class field

The modern one, and the one I'd write today.

✅ Fixed
class SearchBar extends React.Component {
  handleClick = () => {          // 👈 class field, arrow
    console.log(this.props.query);
  };
}

Class fields are initialised per instance, during construction, so the arrow is created in a scope where this is already the instance. It captures that and never lets go. No constructor boilerplate, and it's impossible to forget.

The trade-off — and interviewers love this trade-off: a class-field arrow is a separate function object per instance, stored on the instance itself. A normal method lives once on the prototype and is shared by all instances. So field arrows cost a bit more memory, and they're not on the prototype, which means you can't call them via super.handleClick() from a subclass and they're harder to stub in tests. In practice, for React components, nobody cares. For a class you instantiate 100,000 times, you might.

Fix 3: the arrow wrapper at the call site

✅ Fixed
setTimeout(() => user.greet(), 100);
<button onClick={() => this.handleClick()}>

This one's sneaky-clever. We don't pass the method at all — we pass a brand-new arrow whose body contains a proper user.greet() call, dot and all. The dot is preserved because we delayed it. Implicit binding does its job at the moment the arrow runs.

Bonus: this is also how you pass arguments — onClick={() => deleteItem(item.id)}. The cost is that a fresh function is created on every render, which can defeat React.memo on a child component. That's a real but usually-overrated concern; mention that you know about it and you'll sound like you've shipped things.

In an interview

How it gets asked: "Why does this become undefined in an extracted method?" or "This React handler throws cannot read props of undefined — why, and how do you fix it?"

Say something like: "Because this isn't part of the function — it's set by the call site. user.greet() binds this to user because of the dot, but once I pass user.greet as a callback, the receiving code just calls it plainly, so there's no dot and no binding. In strict mode, which class bodies and modules always are, that means this is undefined. I'd fix it with a class-field arrow so it captures this lexically, or bind it in the constructor if I'm in an older codebase."

Why it lands: you named the mechanism (call site, not definition site), you knew strict mode is why it's undefined rather than window, and you offered a fix with an awareness of context. That's a conversation, not a recital.

call vs apply vs bind

Three methods that every function has. Two of them are nearly identical, and the third is the odd one out — and that's the whole answer to the question.

MethodArgumentsCalls the function?Returns
fn.call(obj, a, b)listed out, comma-separatedYes, immediatelywhatever fn returns
fn.apply(obj, [a, b])one arrayYes, immediatelywhatever fn returns
fn.bind(obj, a)listed outNoa new function

Little mnemonic that has never failed me: Apply takes an Array. Call takes a Comma list. Bind gives you it Back for later.

all three, same function
function order(size, extra) {
  return `${size} ${this.drink} with ${extra}`;
}

const cafe = { drink: 'flat white' };

order.call(cafe, 'large', 'oat milk');    // → 'large flat white with oat milk'
order.apply(cafe, ['large', 'oat milk']); // → same thing

const orderAtCafe = order.bind(cafe);
orderAtCafe('small', 'honey');            // → 'small flat white with honey'

When you'd actually reach for each

apply used to be the way to spread an array into arguments — Math.max.apply(null, numbers) — but spread syntax replaced that in ES6, so Math.max(...numbers) is what you'd write now. apply survives mostly in library internals and in code that forwards an unknown argument list.

call shows up when borrowing a method from one object for another. The classic is borrowing array methods for array-like things (objects with a length and numeric keys, like the old arguments object or a NodeList):

Array.prototype.slice.call(arguments);   // real array from arguments
Object.prototype.toString.call([]);      // → '[object Array]'

That second line is how people used to do reliable type-checking, because typeof [] unhelpfully says 'object'.

bind is the one you'll use most, because it's the one that fits the callback problem: you need to hand a function to someone else and guarantee its this.

Partial application with bind

Here's the underused half of bind. Any arguments you pass after the this value get permanently pre-filled:

partial application
function log(level, message) {
  console.log(`[${level}] ${message}`);
}

const warn = log.bind(null, 'WARN');  // 👈 pre-fill the first arg

warn('Cart is empty');       // → [WARN] Cart is empty
warn('Payment retrying');    // → [WARN] Payment retrying

We passed null as the this value because log doesn't use this — a common idiom when you only want the argument pre-filling. The bound arguments always go first, ahead of whatever the caller supplies later.

Trap

A bound function can't be re-bound. The first bind wins, permanently:

const bound = greet.bind(userA);
bound.call(userB);       // → still userA
bound.bind(userB)();     // → still userA

People assume the second bind overrides. It doesn't. The one exception is new: calling new bound() does ignore the bound this, because new is rung 1 and outranks everything. Bound arguments still get pre-filled, though.

Implementing bind yourself

This is asked constantly, so let's build it. Start with the version that gets you most of the credit:

myBind — the version to write on a whiteboard
Function.prototype.myBind = function (thisArg, ...boundArgs) {
  const fn = this;                 // 👈 `this` is the function we're binding
  return function (...callArgs) {
    return fn.apply(thisArg, [...boundArgs, ...callArgs]);
  };
};

Read the first line again, because it's the bit that makes people pause: inside myBind, what is this? We called it as greet.myBind(user) — there's an object left of the dot, and that object is the function greet. Implicit binding, rung 3. So this is the function we want to bind. Functions are objects; this is legal and it's the whole trick.

Then we return a closure that remembers fn, thisArg, and boundArgs, and forwards everything through apply. Bound args first, call-time args after — matching real bind.

If you want the version that handles the new edge case too:

myBind — new-aware
Function.prototype.myBind = function (thisArg, ...boundArgs) {
  const fn = this;
  function bound(...callArgs) {
    const calledWithNew = this instanceof bound;   // 👈
    return fn.apply(calledWithNew ? this : thisArg, [...boundArgs, ...callArgs]);
  }
  bound.prototype = Object.create(fn.prototype || null);
  return bound;
};

Don't worry if Object.create and instanceof are fuzzy right now — that's the entire second half of this guide, and this snippet will read as obvious by the end. Saying "and if you want to be thorough you also handle being called with new" in an interview is a strong signal even if you don't write it perfectly.

Before prototypes: what an object really is

Right — this is done. Now the other half. And I want to start somewhere more basic than most explanations do, because the prototype confusion almost always traces back to a shaky picture of what an object is.

A JavaScript object is a bag of key–value pairs. That's it:

const song = { title: 'Blue Monday', minutes: 7 };

When you write song.title, the engine looks in the bag for a key called title, finds it, hands you the value. When you write song.publisher, it looks, doesn't find it, and hands you undefined.

Except… that's not quite what happens. Try this:

const song = { title: 'Blue Monday' };
song.toString();  // → '[object Object]'

Hang on. We never put a toString in that bag. We put exactly one key in it. So where did toString come from?

This is the question the whole prototype system exists to answer, and the answer is genuinely elegant.

The hidden link, and how lookup walks it

Every object has a hidden link to another object. The spec calls it the [[Prototype]] internal slot. When you look up a property and it isn't in the bag, the engine follows that link and looks in the next bag. And if it's not there, it follows that object's link. It keeps going until it either finds the property or reaches the end of the chain — which is always null — and only then gives up and returns undefined.

That path is the prototype chain.

Here's the analogy. Imagine you work in an office and you need a stapler. 📎 You check your own desk drawer. Nothing. So you check the shared shelf your team uses. Still nothing. So you check the building's supply cupboard. If it's not there either, there's nowhere else to look — you go without.

Crucially: when you find the stapler on the shared team shelf, it does not get copied into your drawer. You use it where it lives. If someone swaps it for a better stapler tomorrow, you get the better one, automatically, without doing anything. Hold on to that — it's the difference between prototypal and classical inheritance, and we'll come back to it.

So for our song: toString isn't in song's own bag. But song's hidden link points at Object.prototype, which is a real object that ships with the language, and that object has a toString. Found it. Done.

You can inspect the link. The proper way is Object.getPrototypeOf:

Object.getPrototypeOf(song) === Object.prototype;                  // → true
Object.getPrototypeOf(Object.prototype);                           // → null
Object.getPrototypeOf(song).hasOwnProperty('toString');            // → true
song.hasOwnProperty('toString');                                   // → false 👈

That last pair is worth sitting with. song.toString gives you a function — the property is reachable. But song.hasOwnProperty('toString') is false — the property is not own. "Reachable" and "own" are different questions, and the whole prototype system lives in that gap.

Under the hood

You'll also see song.__proto__, with two underscores on each side, which reads the same link. It's a legacy accessor that browsers all implemented, then the spec grudgingly standardised in an appendix so the web wouldn't break. It works everywhere, it's great for poking around in a console, and you should use Object.getPrototypeOf(obj) / Object.setPrototypeOf(obj, p) in real code. Naming it correctly in an interview is a small, cheap credibility win.

Also: Object.create(null) makes an object with no link at all. No toString, no hasOwnProperty, nothing. People use it for pure dictionaries where a key like "constructor" would otherwise collide with inherited stuff.

prototype vs __proto__ (the big one)

OK. Deep breath. This is the confusion that trips up basically everyone, including people who've shipped JavaScript for a decade, and it exists almost entirely because of a catastrophically bad naming decision made in 1995.

Two different things share almost the same name:

__proto__ (or Object.getPrototypeOf(x)) is the actual link. Every object has it. It points to the object we look in next when a lookup misses. This is the real mechanism.

prototype is an ordinary property that exists only on functions. It is not that function's own link. Instead, it's a box the function holds, and its job is: "when someone calls me with new, this is the object I'll set as the new instance's link."

Let me say the thing that makes it click: Fn.prototype is not Fn's prototype. It's the prototype-to-be of Fn's future instances. It's misnamed. If it had been called Fn.instanceBlueprint or Fn.sharedMethods, nobody would ever have been confused.

The single most useful equation in this whole topic:

const rex = new Dog('Rex');

Object.getPrototypeOf(rex) === Dog.prototype;  // → true  ✅
rex.prototype;                                 // → undefined  (instances don't have one)
Dog.__proto__ === Dog.prototype;               // → false (Dog's own link is Function.prototype)

Read those three lines a few times. The first is the relationship that matters. The second kills the "everything has a .prototype" idea. The third kills the "__proto__ and prototype are the same thing" idea.

A common misconception

"obj.prototype gives me an object's prototype."

Nope — on a plain object that's just undefined, because prototype is a property functions have, not objects in general. If you catch yourself typing someInstance.prototype, you almost certainly wanted Object.getPrototypeOf(someInstance). This mix-up in an interview reads as "learned the words, not the model," so it's worth being precise here.

The chain, drawn out

Now let's see the full path a lookup walks. Say we have this:

function Dog(name) {
  this.name = name;
}
Dog.prototype.bark = function () {
  return `${this.name} says woof`;
};

const rex = new Dog('Rex');

So rex.bark() misses on rex, hits on Dog.prototype. rex.toString() misses twice and hits on Object.prototype. And rex.fly misses all the way to null and returns undefined.

And here's a lovely connection back to the first half of this guide: when bark finally runs, what is this? The function lives on Dog.prototype, but we called it as rex.bark(). Rung 3 — object left of the dot. this is rex. Which is exactly why one shared function on the prototype can serve a thousand different dogs and print the right name each time. The chain finds the function; the call site supplies the data.

Object.create and pure delegation

Everything so far has involved constructors and new. But you can build a chain by hand, with no functions involved at all — and honestly, this is the clearest way to see what's really going on.

Object.create
const animal = {
  describe() {
    return `${this.name} is a ${this.species}`;
  },
};

const cat = Object.create(animal);  // 👈 cat's link points at animal
cat.name = 'Mochi';
cat.species = 'cat';

cat.describe();                    // → 'Mochi is a cat'
cat.hasOwnProperty('describe');    // → false
Object.getPrototypeOf(cat) === animal;  // → true

Object.create(proto) does exactly one interesting thing: it makes a fresh empty object whose hidden link points at proto. That's it. No constructor, no new, no .prototype anywhere. Objects linked directly to objects.

This style is sometimes called OLOO — Objects Linked to Other Objects — and it's the version of prototypal inheritance that Douglas Crockford and Kyle Simpson argued we should have been using all along. You don't need to advocate for it in an interview, but understanding it proves you know that constructors are optional decoration on top of a simpler mechanism.

What new actually does

Promised you we'd come back. Now we have the vocabulary. When you write new Dog('Rex'), the engine does four things:

  1. Creates a brand-new, empty object.
  2. Sets that object's hidden link ([[Prototype]]) to Dog.prototype.
  3. Calls Dog with this bound to the new object, passing along your arguments.
  4. Returns the new object — unless the constructor explicitly returned an object of its own, in which case that one wins.

Steps 1 and 3 are the this half; step 2 is the prototype half. That's why this question is such an interview favourite — it's the exact hinge between the two topics, so it tests whether you understand both.

You can write it yourself in about six lines:

myNew
function myNew(Constructor, ...args) {
  const obj = Object.create(Constructor.prototype);   // steps 1 + 2
  const result = Constructor.apply(obj, args);        // step 3
  return typeof result === 'object' && result !== null
    ? result                                          // step 4, the override
    : obj;
}

const rex = myNew(Dog, 'Rex');
rex.bark();               // → 'Rex says woof'
rex instanceof Dog;       // → true

Look how Object.create(Constructor.prototype) does steps 1 and 2 in one go, and apply does step 3. Every piece of this is something we've already built up. Being able to write these six lines cold is a genuinely strong interview moment.

Wait, what about…?

"Step 4 seems bizarre — why would a constructor return an object?" It's rare and mostly a historical wart, but it powers a real pattern: a factory that hands back a cached or wrapped instance instead of the fresh one. Also note the asymmetry — returning a primitive (return 42) is silently ignored and you still get the new object. Only objects can hijack the result.

Trap

Forgetting new on a constructor function used to be a silent disaster: Dog('Rex') in sloppy mode ran with this as the global object and quietly created a global name variable. In strict mode you get a TypeError instead, which is much better. And an ES6 class throws immediately — TypeError: Class constructor Dog cannot be invoked without 'new'. That's one of the places where class is more than sugar.

Method shadowing

Because lookup stops at the first match walking up, anything closer to the start of the chain hides what's further along. That's shadowing.

shadowing
rex.bark = function () {
  return 'REX SAYS WOOF (loudly)';
};

rex.bark();                            // → the loud one (own property wins)
Object.getPrototypeOf(rex).bark.call(rex);  // → 'Rex says woof' (still there)

delete rex.bark;
rex.bark();                            // → 'Rex says woof'  the shadow lifts

Notice that the prototype's method was never touched, damaged, or replaced. We just put something in front of it. Delete the shadow and the original is right there, unharmed. Back to the office analogy: you bought your own stapler for your desk, so you stop reaching for the shared one — but the shared one is still on the shelf for everybody else.

Trap

Assignment always creates an own property on the target object. It never writes through to the prototype. So this bites people:

const base = { count: 0 };
const a = Object.create(base);
const b = Object.create(base);

a.count++;        // reads base.count (0), writes a.count = 1
a.count;          // → 1
b.count;          // → 0  👈 unchanged
base.count;       // → 0  👈 also unchanged

Reads walk the chain; writes land locally. This asymmetry is worth being able to state crisply.

How instanceof works

People describe instanceof as "checks the type of an object." It doesn't — there's no type-checking anywhere. What it actually does is a walk:

x instanceof Fn walks up x's prototype chain, asking at every step: "are you Fn.prototype?" If it ever gets a yes, the answer is true. If it hits null first, false.

myInstanceof
function myInstanceof(obj, Fn) {
  let current = Object.getPrototypeOf(obj);
  while (current !== null) {
    if (current === Fn.prototype) return true;
    current = Object.getPrototypeOf(current);
  }
  return false;
}

myInstanceof(rex, Dog);     // → true
myInstanceof(rex, Object);  // → true 👈 Object.prototype is on the chain too

Two consequences fall straight out of that definition, and both make good interview talking points.

It's a chain check, not an identity check. rex instanceof Object is true, because Object.prototype is up there. So instanceof tells you "somewhere in this object's ancestry," not "was made by exactly this."

It can lie across realms. An array created inside an <iframe> has a chain ending in that frame's Array.prototype, not yours. So arrFromIframe instanceof Array is false even though it's obviously an array. That's why Array.isArray() exists — it checks an internal marker instead of the chain, and works across realms. Mentioning this is a nice depth signal.

You can even break it deliberately, which proves it's just a chain walk:

Dog.prototype = {};          // point .prototype at a fresh object
rex instanceof Dog;          // → false 👈 rex's link points at the OLD object
Under the hood

There's an escape hatch: Symbol.hasInstance. If a constructor defines a static method under that symbol, instanceof calls it instead of doing the walk. It's how you'd make instanceof lie on purpose — worth knowing the name exists, rarely worth using.

Is class "real" inheritance?

ES6 gave us class, and the standard line is "it's just syntactic sugar over prototypes." That line is mostly right and it's what interviewers want to hear first — but the interesting conversation is where it stops being true.

First, the sugar part. These two are near-identical in behaviour:

the old way
function Dog(name) {
  this.name = name;
}
Dog.prototype.bark = function () {
  return `${this.name} says woof`;
};
the class way
class Dog {
  constructor(name) {
    this.name = name;
  }
  bark() {
    return `${this.name} says woof`;
  }
}

typeof Dog;                                   // → 'function' 👈 still a function!
Object.getOwnPropertyNames(Dog.prototype);    // → ['constructor', 'bark']

The class body isn't a new kind of thing. Dog is a function. bark is on Dog.prototype. new Dog() does the same four steps. And class Puppy extends Dog just wires Puppy.prototype's link to Dog.prototype, so lookups walk one level further. Same machinery, nicer notation, and — importantly — one obvious place to put shared methods, which the old syntax scattered.

Where the sugar is not just sugar

Now the part that separates a memorised answer from an understood one. Classes do several things you genuinely cannot replicate with plain constructor functions:

  • Calling without new throws. A constructor function called plainly just runs. A class refuses.
  • Class bodies are always strict mode, whether or not the surrounding file is.
  • Classes are not hoisted-usable. They're in the temporal dead zone, so using one before its declaration throws a ReferenceError. Function declarations hoist fine.
  • Methods are non-enumerable, so they don't show up in for...in. Manually-assigned Dog.prototype.bark is enumerable and does.
  • Private fields (#balance) are truly private — enforced by the engine, invisible to Object.keys, un-reachable from outside. There is no prototype trick that gives you this; the old convention was an underscore and a pinky promise.
  • super works properly. Methods carry an internal [[HomeObject]] reference that super uses to find the right parent method. You can't hand-roll that.
  • Extending built-ins actually works. class MyArray extends Array gives you a real array with a working length. The ES5 equivalent silently doesn't — because super() lets the base constructor create the exotic object, whereas Array.call(this) can't retrofit array-ness onto a plain object. Same for extends Error.
In an interview

How it gets asked: "Is class real inheritance in JavaScript?" or "What's the difference between class and a constructor function?"

Say something like: "Mostly it's syntactic sugar — typeof Dog is still 'function', methods still land on Dog.prototype, and extends just links one prototype to another, so lookup is still a chain walk, not a copy. But it's not only sugar. Classes throw if you call them without new, they're always strict, they're in the TDZ rather than hoisted, methods are non-enumerable, and private # fields and correct super aren't things you can hand-roll. The big practical one is that extends Array or extends Error actually works with classes and never really did with ES5 constructors."

Why it lands: you gave the expected headline, then immediately showed you know its limits with concrete, checkable examples. Interviewers use this question to separate people who read a blog post from people who've hit the edges.

Delegation vs. copying — why this is a different model

Here's the conceptual heart of it, and the question behind most "explain prototypal inheritance" prompts.

In a classical language like Java or C++, a class is a blueprint. At instantiation time, the structure described by the blueprint gets stamped out into a new object. The relationship is a copy: the blueprint's job finishes the moment the instance exists. Change the blueprint afterwards and existing instances neither know nor care.

JavaScript doesn't copy anything. An object holds a live link to another object, and missing properties are delegated up that link at lookup time — every single time. The relationship never finishes.

Which means this works, and it's genuinely startling the first time:

live delegation
const rex = new Dog('Rex');
rex.fetch;                       // → undefined

Dog.prototype.fetch = function () {  // 👈 added AFTER rex existed
  return `${this.name} fetches the ball`;
};

rex.fetch();                     // → 'Rex fetches the ball'

We taught an existing object a new trick by editing a different object. No re-instantiation, no recompile. In a copy-based model this is impossible; in a delegation model it's not even surprising — rex never had a fetch, and it still doesn't. It just knows where to ask.

Blueprint vs. stapler shelf. The blueprint is consulted once at construction. The shelf is consulted every time you need a stapler. (Where the shelf analogy breaks down: real shelves are shared physical space, whereas here the "shelf" is itself just another ordinary object that can have its own shelf behind it, all the way up. Chains of shelves. The analogy runs out around there.)

In an interview

How it gets asked: "Explain prototypal inheritance." Almost always phrased exactly like that, and it's a depth question disguised as a recall question.

Say something like: "Every object has a hidden link to another object. When you read a property, the engine checks the object's own keys, and if it's not there it follows that link and checks the next object, and keeps going until it finds it or hits null. That path is the prototype chain. The key difference from classical inheritance is that nothing is copied — it's live delegation, resolved at lookup time. So I can add a method to Dog.prototype after instances already exist and they'll all pick it up immediately."

Why it lands: you described a mechanism (a walk that terminates at null) rather than a vibe, you named the contrast, and the live-addition example proves you actually hold the model instead of the vocabulary.

What happens if you add a method to Array.prototype?

Since built-ins are just objects with prototypes, nothing stops you from editing them:

❌ Please don't
Array.prototype.last = function () {
  return this[this.length - 1];
};

[1, 2, 3].last();   // → 3   ...it works!

Every array in your program, including ones created before this line ran and ones inside your dependencies, now has .last(). That's live delegation doing its thing. So why does everybody flinch? Four reasons, and being able to give them is the actual answer to this question:

1. Collisions. Your last and a library's last can't coexist — the second one silently wins, and now one of them is subtly broken with no error message pointing anywhere useful.

2. It leaks into for...in. A plain assignment creates an enumerable property, so any code doing for (const i in arr) now iterates 'last' alongside the indices. This broke real websites in the 2000s and is a big part of why for...in has a bad reputation with arrays. If you must patch, use Object.defineProperty with enumerable: false.

3. The future will overtake you. TC39 tried to add Array.prototype.contains and had to rename it to includes because a widely-used library had patched in an incompatible contains and thousands of sites would have broken. That episode is affectionately called "SmooshGate" (the same thing happened with flatten → flat). Bringing this up is a really strong signal — it shows you know why the norm exists, not just that it exists.

4. It's action at a distance. A future maintainer reads items.last(), greps for it, finds nothing, and loses an hour.

The alternative is boring and correct: a plain function (last(items)), or a subclass, or just items.at(-1), which is now standard. Adding a genuine polyfill for a standardised method that a browser lacks is fine and normal — that's implementing an agreed spec, not inventing one.

Interview follow-ups, answered

These are the ones that come after the main question, when the interviewer is probing for depth. Try to answer each before opening it.

"What does new do under the hood?"

Four steps: creates an empty object; sets that object's [[Prototype]] to Constructor.prototype; calls the constructor with this bound to the new object; returns the new object unless the constructor returned an object of its own, which would override it. Returning a primitive is ignored. The whole thing is about six lines with Object.create and apply.

"How would you implement bind yourself?"

Capture this (which is the function itself, because you called it as fn.myBind(...)) and the bound arguments in a closure, and return a new function that applys the original with the stored this and bound-args-first. Mention that a fully-correct version also handles being called with new — check this instanceof bound and prefer the new object over the bound one — and links the returned function's prototype to the original's.

"Why not just use arrow functions everywhere, then?"

Because sometimes you want dynamic this. Object methods and class prototype methods need to receive the instance from the call site — an arrow would freeze in whatever this surrounded the definition, which for an object literal is the module scope. Arrows also can't be used as constructors, have no arguments, can't be bind-ed, don't get the DOM's element-as-this, and can't be generators. Arrows are the right default for callbacks, not for everything.

"Arrow function or regular function for a class method — which and why?"

Regular method by default: it lives once on the prototype, is shared by every instance, is reachable via super, and is easy to spy on in tests. Reach for an arrow class field specifically when the method will be detached and passed as a callback — a React event handler being the canonical case — because it captures this at construction and can never lose it. The cost is one function object per instance, and it's an own property rather than a prototype one. In modern React you mostly sidestep the whole thing by writing function components with hooks.

"Why does this become undefined in an extracted method?"

Because this comes from the call site, and extracting the method throws the call site away. user.greet() has an object before the dot, so implicit binding applies; const g = user.greet; g() is a bare call, so default binding applies. In strict mode — which every module and every class body is — default binding gives undefined rather than the global object, so the first this.anything throws a TypeError.

"What's the difference between __proto__ and prototype?"

__proto__ (properly: Object.getPrototypeOf) is the actual link every object has to the next object in its lookup chain. prototype is an ordinary property that only functions have, and it's not that function's own link — it's the object that will be used as the [[Prototype]] for instances the function creates with new. The equation to remember is Object.getPrototypeOf(new Dog()) === Dog.prototype. Plain objects and instances have no .prototype at all.

"How does instanceof work?"

It walks the left operand's prototype chain looking for the exact object that is the right operand's .prototype. Found it before null → true. So it's an ancestry check, not an identity check, which is why rex instanceof Object is true. It also fails across realms — an array from an iframe isn't instanceof your Array — which is why Array.isArray exists. A constructor can override the behaviour entirely via Symbol.hasInstance.

"What happens if you add a method to Array.prototype?"

Every array everywhere gets it instantly, including ones already created and ones inside dependencies — that's live delegation. But it's discouraged: name collisions with libraries resolve silently, a plain assignment is enumerable so it pollutes for...in, and you can conflict with future standard methods, which is exactly what happened with contains/includes and flatten/flat. Use a standalone function or a subclass. Polyfilling an actual standardised method is the acceptable exception.

"Why not just use Object.setPrototypeOf to change chains at runtime?"

You can, but it's a serious performance footgun. Engines optimise objects by assuming their "shape," including their prototype, is stable; mutating a prototype after the fact invalidates inline caches and can deoptimise every site that touched that object. MDN explicitly warns about it. If you need a different chain, create the object with the right one via Object.create or new in the first place.

"What is this at the top level of a module?"

undefined in an ES module. In a classic non-module script it's the global object. In CommonJS (Node's require) it's module.exports, which is an empty object. Three different answers, which is a nice illustration that this is always contextual. If you need the global object reliably, globalThis works everywhere.

"If two objects share a prototype, does changing one change the other?"

Not through assignment — writes always create an own property on the target, so a.count = 5 only affects a. But if the shared prototype holds a mutable value, mutating it in place does affect everyone: a.tags.push('x') reads the shared array off the prototype and pushes into it, and now b.tags shows it too. That's why you initialise arrays and objects per-instance in the constructor, never on the prototype.

Cheat sheet

The morning-of version. If you can say each of these in one breath, you're in good shape.

  • this — decided by the call site, not the definition site. Look at how the function was called.
  • The ladder — new → explicit (call/apply/bind) → implicit (object left of the last dot) → default (undefined in strict mode, global otherwise).
  • Arrow functions — have no this of their own; they inherit it lexically from the enclosing scope, and call/apply/bind can't change it.
  • Lost this — passing a method as a callback drops the dot. Fix with a class-field arrow, a constructor bind, or an arrow wrapper at the call site.
  • call / apply — invoke now; call takes a comma list, apply takes an array.
  • bind — invokes nothing; returns a new permanently-bound function, and pre-fills any extra args (partial application). Can't be re-bound.
  • Prototype chain — every object has a hidden link; property lookup walks it until it finds a match or hits null.
  • __proto__ vs prototype — __proto__ is the real link on every object; prototype is a property only functions have, holding the object that will become their instances' link. Object.getPrototypeOf(new Dog()) === Dog.prototype.
  • Object.create(p) — fresh object whose link is p. The whole mechanism, with no constructors involved.
  • new — new object → link it to Fn.prototype → run Fn with this as that object → return it unless an object was explicitly returned.
  • Shadowing — own properties hide prototype ones. Reads walk up; writes always land locally.
  • instanceof — walks the chain looking for Fn.prototype. Ancestry, not identity. Breaks across iframes.
  • class — sugar over prototypes, except: must use new, always strict, TDZ not hoisted, non-enumerable methods, real private # fields, working super, and extends Array/Error that actually works.
  • Delegation vs. copying — classical inheritance copies structure at instantiation; prototypes delegate live at lookup, so adding to a prototype updates existing instances instantly.
  • Monkey-patching built-ins — works, discouraged: collisions, for...in pollution, and future-standard conflicts (SmooshGate).

One last thought. Both of these topics feel arbitrary while you're memorising rules, and then stop feeling arbitrary the moment you have the two pictures: a shipping label applied at dispatch, and a walk up a chain of shelves. Interviewers can tell which of those two states you're in within about thirty seconds — memorised rules come out as a list, a model comes out as a story. Go tell the story. 🚀
