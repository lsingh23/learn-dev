Star rating, accordion, tabs

Three prompts, one state shape. This is the pointer family from guide 34 — exactly one of N is selected — and once you see that, you stop memorising components and start recognising them.

  1. Star rating — the hover trick is the whole question
  2. Accordion — one openId, and the height problem
  3. Tabs — id vs index, mount vs hide, roving tabIndex
  4. They're the same component in different clothes
  5. Cheat sheet

I'm not going to re-teach the method — that's guide 34: clarify → state shape → static render → wire → polish, and make illegal states unrepresentable. What I want to show you here is the actual thinking, in order, for the three prompts you're most likely to get.

Star rating

What they're testing: whether you can hold two values at once — what the user has chosen and what they're previewing — without tangling them.

Ask: "Should hovering preview the rating?" (they'll say yes, and now you've signalled you know it's the hard part) and "controlled, or does it own its value?"

State shape first

// state:
//   rating   → number   the committed value, survives mouseleave
//   hovered  → number | null   preview only, null when the pointer is away
// derived:
//   display  → hovered ?? rating      👈 this line is the component

Why two values and not one? Because if you only keep rating and set it on hover, the user's real choice is destroyed the moment their mouse drifts. And if you keep a single "current" value plus a flag, you've made an illegal state possible: hovering with no pointer on screen. Two values, one nullable, and the nullability is the "am I hovering" flag.

Simplest thing that works

✅ ~12 lines, and it's genuinely done
const [rating, setRating] = useState(0);
const [hovered, setHovered] = useState(null);
const display = hovered ?? rating;

return (
  <div onMouseLeave={() => setHovered(null)}>
    {[1, 2, 3, 4, 5].map((n) => (
      <button key={n} onClick={() => setRating(n)}
              onMouseEnter={() => setHovered(n)}>
        {n <= display ? '★' : '☆'}
      </button>
    ))}
  </div>
);

Note onMouseLeave sits on the container, not each star. On each star you'd fire leave/enter on every crossing between stars — flicker, and a pointless extra render.

Why ?? and not ||?

hovered || rating looks the same until hovered is 0, which is exactly what "hovering the clear-rating zone" would be. 0 is falsy, || throws it away, and you get a bug you'll stare at for four minutes. Say "nullish coalescing, because zero is a valid rating" and move on.

The upgrades, in the order they earn their place

Half stars. Don't add a second state field. The value just becomes a half-step: 0.5, 1, 1.5…. Each star renders one of three faces from display, and the click handler asks which half of the star the pointer is in:

function valueFromEvent(e, n) {
  const { left, width } = e.currentTarget.getBoundingClientRect();
  const isLeftHalf = e.clientX - left < width / 2;
  return isLeftHalf ? n - 0.5 : n;   // → 3.5 or 4
}

Then both onClick and onMouseMove use it. Same two state values. That's the payoff of getting the shape right: a feature that sounds like a rewrite is a new helper function.

Readonly. A readOnly prop that skips the handlers — but render <span>s instead of <button>s, because a button nobody can press is a lie to a screen reader.

Keyboard. Five buttons in a row is already tabbable, which is fine but wrong semantically — this is a single control with five options. The honest answer is role="radiogroup" on the container, role="radio" + aria-checked on each star, and arrow keys moving the value. If you're short on time, say that sentence instead of writing it.

Follow-ups

"Make it controlled." — "The value ?? internal pattern: rating comes from the prop when it's defined, otherwise from internal state, and onChange fires either way. hovered stays internal — it's UI ephemera, the parent doesn't want it."

"Now it's 100 stars, is this performant?" — "Every mouseenter re-renders all 100. In practice that's nothing, but if it mattered I'd drive the fill from CSS with a single width overlay instead of per-star state, so hovering is one style change."

"How do you support touch?" — "Hover doesn't exist there. Preview degrades to nothing and tap commits directly, which is the right behaviour anyway."

Accordion

What they're testing: whether you pick a state shape that makes "only one open" impossible to break — and whether you know the height animation is a real problem.

Ask: "Single-open or can several be open at once?" That one question decides your entire state shape, so it's the first thing out of your mouth.

State shape first

// single-open:  openId → string | null       ("which one?")
// multi-open:   openIds → Set<string>        ("which ones?")
// derived:      isOpen(id) → openId === id  |  openIds.has(id)

Guide 34 already made the case against N booleans, so I'll just note the part people underrate: openId and the Set are the same code apart from the toggle. Write the single-open version, and when they ask for multi, you change two lines. That's a very good look.

✅ single-open toggle — clicking the open one closes it
const [openId, setOpenId] = useState(null);

<button onClick={() => setOpenId(id === openId ? null : id)}>
✅ multi-open — copy the Set, never mutate it
setOpenIds((prev) => {
  const next = new Set(prev);        // 👈 new identity or React won't re-render
  next.has(id) ? next.delete(id) : next.add(id);
  return next;
});

That copy is the one thing people get wrong. prev.add(id) mutates and returns the same Set — React compares references, sees no change, and your UI freezes while your state is technically correct. Miserable to debug, so just always copy.

The upgrade that actually bites: animating height

You want the panel to slide open. So you transition height from 0 to auto… and nothing happens. CSS transitions need two numbers, and auto isn't one. Your options, cheapest first:

  • grid-template-rows: 0fr → 1fr on a wrapper with an inner overflow: hidden div. Pure CSS, animates to intrinsic height, works today. This is the answer to give.
  • Measure with a ref — scrollHeight into an inline height. Works everywhere but goes stale when the content changes.
  • max-height to a guessed large value. The old hack. The timing is wrong for short panels because it spends the transition animating empty space. Mention that you know it and know why it's bad.
And the accessibility bit that's nearly free

Header is a <button> with aria-expanded={isOpen} and aria-controls={panelId}; the panel gets that id. If a panel is collapsed by height alone it's still in the tab order — hide it with hidden or display:none when closed. Native <details>/<summary> gives you most of this for free, and saying so is a good moment even if you then build it by hand.

Follow-ups

"Nested accordions?" — "Each level owns its own openId. The child doesn't know it's nested; recursion falls out for free."

"Data comes from an API with no ids." — "I'd generate stable ids when I normalise the response, not at render. Index-as-id breaks the second the list reorders."

Tabs

What they're testing: almost nothing about state — it's one line — and almost everything about whether you know the two design decisions underneath.

Ask: "Are all panels mounted and hidden, or only the active one rendered?"

State shape first

// state:  activeId → string   (an id, not an index)
// data:   tabs = [{ id, label, content }]
// derived: activePanel = tabs.find(t => t.id === activeId)

Id, not index. An index is a pointer into an array that can be filtered, sorted or reordered underneath you — and when it is, "tab 2" silently becomes a different tab. An id is a pointer to the thing. Same argument as React keys, same reason.

Mount only the active panel, or render all and hide?

Only active mountedAll rendered, inactive hidden
Panel state on switchLost — inputs reset, scroll resetsPreserved
Initial costOne panelAll of them, including their fetches
Ctrl-F / SEOInvisibleFindable if hidden with CSS
Good forHeavy panels, fresh-data tabsForms, anything with typed input

There's no right answer, which is the point of the question. Just pick one, say why in a sentence, and note the tradeoff you accepted. That single sentence is worth more than the code.

The polish they're fishing for: roving tabIndex

If you render five tab buttons normally, Tab steps through all five, then into the panel. The ARIA pattern says a tablist is one stop: Tab gets you in, arrows move between tabs.

✅ exactly one tab is tabbable at a time
<button role="tab" id={`tab-${t.id}`} aria-controls={`panel-${t.id}`}
        aria-selected={t.id === activeId}
        tabIndex={t.id === activeId ? 0 : -1}   // 👈 the "roving" part
        onKeyDown={onKeyDown}
        onClick={() => setActiveId(t.id)}>
function onKeyDown(e) {
  const delta = e.key === 'ArrowRight' ? 1 : e.key === 'ArrowLeft' ? -1 : 0;
  if (!delta) return;
  const i = tabs.findIndex((t) => t.id === activeId);
  const next = tabs[(i + delta + tabs.length) % tabs.length];  // wraps
  setActiveId(next.id);
  document.getElementById(`tab-${next.id}`)?.focus();  // 👈 don't forget this
}

That focus call is the fiddly bit and it's where people stumble: changing tabIndex doesn't move focus, so without it the user's focus stays on a button that just became tabIndex={-1}. Doing it imperatively after setState is a little grubby — the cleaner version stores refs and focuses in an effect — but in a 45-minute round, the grubby version that works and a one-line acknowledgement beats a clean version you didn't finish.

Follow-ups

"Sync the active tab to the URL." — "Read the initial value from the query string, and push on change. It stops being local state and becomes derived from the router — which also gives me back/forward and shareable links for free."

"What if there are too many tabs to fit?" — "Horizontal scroll with scroll-snap first, an overflow menu only if they insist. Both leave activeId completely untouched, which is the sign the shape was right."

They're the same component in different clothes

Line them up:

Star ratingAccordion (single)Tabs
Staterating + hoveredopenIdactiveId
Can be "none"?Yes (0)Yes (null)No — always one
Selecting againRe-commitsCloses itNo-op
Renders asFill up to NOne panel expandedOne panel shown
Preview state?Yes — hoverNoNo

One pointer, five rows of costume. The differences that matter are: can it be empty, what does re-selecting do, and is there a preview layer. Answer those three in the first two minutes and you've specced the component.

And it generalises further than these three. A carousel is tabs with the strip replaced by prev/next. A wizard is tabs where the pointer only moves ±1 and the guard is validation. A segmented control is tabs with no panels. A traffic light is a pointer on a timer. When the next prompt lands, don't ask "have I built this before" — ask "which of the four shapes is this?" 🌟

Cheat sheet

  • Pointer family = exactly one of N. One state value; the rest is rendering.
  • Star rating: hovered ?? rating. Committed + nullable preview. ??, never || — zero is a real rating.
  • onMouseLeave on the container, enters on the stars.
  • Half stars are a value change (0.5 steps), not a state change.
  • Accordion: one openId, not N booleans. Multi-open = a Set, and copy it before mutating or React won't re-render.
  • height: auto doesn't animate. grid-template-rows: 0fr → 1fr is the modern answer.
  • Tabs: id, never index. Indices break under sort/filter/reorder.
  • Mount-active vs render-all-hidden is a real tradeoff — pick, and say why in one sentence.
  • Roving tabIndex: active tab 0, rest -1, arrows move — and call .focus() yourself.
  • Free a11y points: aria-expanded/aria-controls on accordions, role="tab"/aria-selected on tabs.
  • Ask first: can it be empty · what does re-selecting do · is there a preview.
