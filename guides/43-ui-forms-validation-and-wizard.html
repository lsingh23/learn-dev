Forms: validation, and the multi-step wizard

Forms are the machine-coding round's favourite trap. Not because they're hard, but because the naive version works for about four minutes and then collapses under the fifth requirement. Here's the shape that doesn't.

One state object, not five useStates

You get "build a contact form: name, email, message, with validation." Almost everyone starts here:

❌ One useState per field
const [name, setName] = useState('');
const [email, setEmail] = useState('');
const [message, setMessage] = useState('');
// ...and now one onChange per field, forever

It's not wrong, exactly. It's just that every new field costs you three lines and a new handler, and when the interviewer says "add a phone number and a company" you're doing clerical work in front of an audience. Worse: there's no way to say "reset the form", "here are the values to submit", or "which fields has the user touched" without listing all five names again. The state is scattered, so every operation over the whole form is scattered too.

✅ One object, one handler
const [values, setValues] = useState({ name: '', email: '', message: '' });

function handleChange(e) {
  const { name, value } = e.target;
  setValues(v => ({ ...v, [name]: value }));
}

Then every input is <input name="email" value={values.email} onChange={handleChange} />. The input's name attribute — the one you were writing anyway — is what routes the update. Adding a field is now one line of JSX and one key in the initial object. Zero new handlers.

Say this out loud when you write it, because it's the load-bearing decision of the whole problem: this single handler is what makes everything after it cheap. Reset, serialise, validate, mark-all-touched, prefill from a server — each becomes a one-liner over one object instead of a loop over five variables you have to remember to keep in sync.

The three parallel objects

Now the actual state shape. Write it as a comment before you write any JSX:

// state:
//   values      → { name, email, message }   what the user typed
//   touched     → { email: true }            fields the user has left at least once
//   isSubmitting→ boolean                    in-flight guard
//   serverError → { email: 'taken' } | null  errors only the server can know
// derived (NOT state):
//   errors  → validate(values), merged with serverError
//   isValid → Object.keys(errors).length === 0
//   show(f) → errors[f] && (touched[f] || submitted)

Two of those three objects are state. errors is not, and that's the bit people get wrong. If you store errors in state, you now have to remember to recompute them in every change handler, and the moment you forget one, the form shows a stale error next to a field the user already fixed. Errors are a pure function of values. If you can compute it, don't store it.

So why does touched exist? Here's the question that gives it away: if errors is computed on every render from the values, and the form starts empty, then the very first paint has an error on every single field. Do you really want to greet someone with three red "this is required" messages before they've typed a character?

Of course not. So: validate on change, display on blur. The error is always known; whether it's visible is gated by whether the user has finished with that field. A field becomes touched in onBlur:

function handleBlur(e) {
  setTouched(t => ({ ...t, [e.target.name]: true }));
}
const showError = f => errors[f] && (touched[f] || submitted);

The lovely consequence: on submit you don't need any new mechanism. You just mark everything touched at once, and every error that was already computed becomes visible simultaneously. Same rendering path, no special case.

Validation as data

The version that loses points is a wall of ifs inside the component. The version that wins is a rules table, because it's obviously extensible and it reads like the spec:

const required = v => (!v.trim() ? 'Required' : null);
const isEmail  = v => (/.+@.+\..+/.test(v) ? null : 'Enter a valid email');
const minLen   = n => v => (v.length < n ? `At least ${n} characters` : null);

const RULES = { name: [required], email: [required, isEmail], message: [required, minLen(10)] };

function validate(values) {
  const out = {};
  for (const [field, rules] of Object.entries(RULES)) {
    for (const rule of rules) {
      const msg = rule(values[field] ?? '');
      if (msg) { out[field] = msg; break; } // first failure wins
    }
  }
  return out;
}

Every rule is value => message | null. That uniformity is the whole trick: adding "password must contain a digit" is a one-line function and one array entry, not a surgical edit to a branching mess. And the regex doesn't need to be RFC-correct — say "real email validation is a server round-trip; this is a typo catch" and move on.

Now the payoff:

const errors  = validate(values);
const isValid = Object.keys(errors).length === 0;

The submit button's disabled state is one expression. Free, and it can never disagree with the errors on screen, because it is the errors on screen.

Should the submit button be disabled when invalid?

Careful — this is a small trap. A permanently disabled button with no visible errors is a dead end for the user: nothing tells them why. I prefer enabled, and let submit mark everything touched and reveal the reasons. Disable it only while isSubmitting. Saying this trade-off out loud is worth more than either choice.

Submit, and everything that goes wrong there

async function handleSubmit(e) {
  e.preventDefault();
  setSubmitted(true);
  setTouched(Object.fromEntries(Object.keys(RULES).map(k => [k, true])));
  if (!isValid || isSubmitting) return;        // invalid, or already flying
  setIsSubmitting(true);
  try {
    const res = await api.send(values);
    if (res.fieldErrors) setServerError(res.fieldErrors); // merged into errors
    else setStatus('success');
  } catch { setStatus('error'); }
  finally { setIsSubmitting(false); }          // always, even on throw
}

isSubmitting is the double-submit guard: an impatient double click on a slow network is how you get two support tickets from one person. Server field errors ("that email is already registered") get merged into the same errors object — {...validate(values), ...serverError} — so there's exactly one code path rendering messages, whatever their origin. Clear a field's server error as soon as that field changes, or it'll haunt a value the user already fixed.

And the line you should say without being asked: client validation is a UX feature, not a security boundary. Anyone can POST straight past it. The server validates the same rules again, always.

The cheap accessibility points

This costs about ninety seconds and is disproportionately rewarded, because most candidates skip it entirely.

<label htmlFor="email">Email</label>
<input id="email" name="email" value={values.email}
       onChange={handleChange} onBlur={handleBlur}
       aria-invalid={!!showError('email')}
       aria-describedby={showError('email') ? 'email-err' : undefined} />
{showError('email') && <p id="email-err" role="alert">{errors.email}</p>}

Four things: a real <label htmlFor> (clicking the label focuses the input, and screen readers announce it), aria-invalid, aria-describedby so the error text is read as part of the field rather than as orphaned prose, and a real <form onSubmit> so Enter submits. Then on a failed submit, focus the first invalid field — document.querySelector('[aria-invalid="true"]')?.focus() — so a keyboard user isn't hunting for the problem in a long form.

The wizard is a pointer

"Now make it three steps." The corner people paint themselves into is one state object per step, plus a pile of booleans for which step is showing. Then "let me go back and change my email" becomes a data-plumbing nightmare.

The reframe: a wizard is nothing new. It's a pointer over an array of step configs, sitting on top of the exact same single values object you already have. Every step reads and writes the same bag.

const STEPS = [
  { id: 'account', fields: ['email', 'password'] },
  { id: 'profile', fields: ['name', 'company'] },
  { id: 'review',  fields: [] },
];
const [step, setStep] = useState(0);        // the pointer. that's it.

const errors    = validate(values);         // still the whole form
const stepFields = STEPS[step].fields;
const stepValid = stepFields.every(f => !errors[f]);

See what happened: validate didn't change at all. "Is this step valid" is just the full error object filtered to the current step's fields. One rules table serves both the wizard and the review page.

function next() {
  setTouched(t => ({ ...t, ...Object.fromEntries(stepFields.map(f => [f, true])) }));
  if (stepValid) setStep(s => s + 1);
}
function back() { setStep(s => s - 1); }    // never validates, never clears

back() is two words long and both of them matter. Going back must never validate — punishing someone for a field they haven't reached yet is hostile — and it must never wipe data, which is automatic here because there's only one values object and nobody's resetting it. Separate-state-per-step is exactly where that guarantee dies.

The progress indicator is derived, obviously: (step + 1) / STEPS.length. No state, no syncing. And submit only exists on the last step, guarded by isValid over the whole form rather than the current step.

Two things worth mentioning even if you don't build them. The browser back button will leave your wizard, not step backwards — so put the step in the URL (?step=2) if that matters, which also makes the flow linkable and refresh-proof. And a half-finished wizard is a lot of typing to lose: persist values to localStorage on change (debounced) and rehydrate on mount, so a refresh at field nineteen doesn't send someone back to field one. Naming these two costs ten seconds and sounds like you've shipped a real onboarding flow.

Say this out loud

"In production I'd reach for React Hook Form with a Zod schema — uncontrolled inputs, fewer re-renders, and one schema shared with the server. I'm building it by hand here because that's the exercise." Naming the real tool and still building it yourself reads as senior. Naming it instead of building it reads as dodging.

Follow-ups you'll actually get

Controlled or uncontrolled inputs — which, and why?

"Controlled here: React state is the source of truth, so validation, cross-field rules and the disabled button all just read from values. The cost is a re-render per keystroke, which is irrelevant at this size. Uncontrolled — refs or FormData — is what libraries use for big forms because it avoids that, and it's what I'd switch to if the form had fifty fields or a measured typing lag."

Why isn't errors in state?

"Because it's a pure function of values. Storing it gives me two sources of truth that I'd have to keep in sync in every handler, and the first one I forget shows a stale error next to a field the user already fixed. Computing it every render is one pass over a handful of fields."

When do you show the error?

"Validate on every change, display on blur or after a submit attempt. That's what touched is for. Nobody should be told their email is invalid before they've finished typing it. One nuance: once a field is touched and showing an error, I switch it to live-updating on change, so the message disappears the moment they fix it."

Why one state object instead of five useStates?

"Because a form is one value, not five. With one object plus one name-driven handler, adding a field is one line, and whole-form operations — reset, submit payload, mark-all-touched — are one line each instead of five. With five useStates every one of those becomes a list I can forget to update."

How do you validate one step without validating the whole form?

"I don't, really — I validate everything and then filter. errors is the full object; step validity is STEPS[step].fields.every(f => !errors[f]). One rules table, no duplicated logic, and the final submit reuses the same object. Splitting the validator per step would mean maintaining it twice."

How would you handle async validation, like "username taken"?

"That one genuinely needs state, because it depends on a network result — you can't compute it during render. I'd debounce the field by ~400ms, keep a per-field pending flag so I can show a spinner and block submit while it's in flight, and keep the result in asyncErrors which merges into the same errors object. Two gotchas: ignore a stale response if a newer request has started, and re-check server-side on submit, because the name could be taken in the seconds between."

Cheat sheet

  • One values object + one handler keyed off e.target.name. Never one useState per field.
  • Three objects: values (state), touched (state), errors (derived — never state).
  • Validate on change, display on blur or after submit. That's the entire job of touched.
  • Rules as data: { email: [required, isEmail] }, every rule value => message | null.
  • isValid is one line off the derived errors object.
  • Submit: preventDefault → mark all touched → bail if invalid → isSubmitting guard → merge server field errors → success state.
  • The server validates too. Client validation is UX, not security.
  • A11y for free: label htmlFor, aria-invalid, aria-describedby, focus the first invalid field.
  • A wizard is a pointer (step) over step configs, over one shared values.
  • next() validates the current step's fields only. back() validates nothing and loses nothing.
  • Progress is derived from step / STEPS.length. Persist to URL or localStorage so a refresh doesn't nuke twenty fields.
  • Name React Hook Form + Zod out loud — then build it by hand anyway.
