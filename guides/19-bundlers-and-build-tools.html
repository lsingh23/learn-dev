Bundlers: Webpack, Vite & What Actually Happens on Build

You type npm run build, a progress bar chugs along, and a dist/ folder appears with files named index-a4f9c2b1.js. This guide is about the several thousand things that happened in between — and how to talk about them out loud.

Here's the uncomfortable thing about build tools: almost every frontend developer uses one every single day, and almost none of us can explain what it does. We copied a config from a template three years ago, it worked, and we never looked again.

Interviewers know this. That's exactly why they ask. "What does a bundler actually do?" is a fantastic question precisely because it separates people who've internalised how the web works from people who've memorised commands. And the good news is that the underlying ideas are genuinely simple — much simpler than webpack's config file makes them look.

We're going to build the whole thing up from a web page with no build step at all. By the end you'll be able to hold a real conversation about tree shaking, code splitting, why Vite feels like magic, and why putting your Stripe secret key in a .env file is one of the fastest ways to leak it.

1. Life before bundlers (and why we couldn't stay there)

Let me show you a real index.html from about 2012. This is not a strawman; this is what a serious app looked like.

<script src="js/jquery.js"></script>
<script src="js/underscore.js"></script>
<script src="js/backbone.js"></script>
<script src="js/utils.js"></script>
<script src="js/models/user.js"></script>
<script src="js/models/cart.js"></script>
<script src="js/views/cart-view.js"></script>
<script src="js/app.js"></script>
<!-- ...and 30 more of these -->

Take a second and look at that. There are four separate problems hiding in it, and I want to name each one properly, because every single feature of a modern bundler exists to solve one of them.

Problem 1: the ordering is load-bearing and invisible

Those <script> tags run top to bottom. cart-view.js uses Backbone, so backbone.js has to come first. backbone.js uses _, so underscore.js has to come before that.

The dependency information is real — it exists — but it lives nowhere except in a developer's head and in the ordering of an HTML file. Move one line and you get Uncaught ReferenceError: Backbone is not defined at runtime, in production, on a Friday. There's no compiler checking this. There's no import statement to grep for.

Problem 2: everything shares one global namespace

In that world, the only way for cart.js to give something to cart-view.js is to hang it off window:

// cart.js
var Cart = { items: [] };   // 👈 this is now window.Cart, globally, forever

Two libraries both wanting the name $? One silently overwrites the other. A junior dev writes var utils = ... at the top level of a file? Congratulations, you've just replaced the app's shared utils object. Every file can reach into and clobber every other file's variables. There is no privacy and no encapsulation.

Under the hood: the IIFE workaround

People got clever about this before modules existed. You'd wrap a file in an immediately-invoked function expression — (function(){ ... })() — so its variables were trapped inside a function scope instead of leaking globally, and then deliberately export just one name to window at the end. That's the "module pattern". It worked, but it was a convention people had to remember, not something the language enforced.

Problem 3: one HTTP request per file

Forty script tags is forty round trips to the server. Under HTTP/1.1 browsers only opened about six connections per domain, so those requests queued up in batches. Each one carried its own headers, its own latency. On a phone on 3G, the network round-trip time dwarfed the actual download time — you spent more time saying "hello, may I have utils.js please" than you spent receiving utils.js.

So people wrote build scripts (Grunt, Gulp, or a bash one-liner) that literally concatenated all the files into one app.js. That's the primordial bundler: cat *.js > app.js. It fixed the request count and did absolutely nothing for problems 1 and 2 — in fact it made ordering worse, because now the order lived in a Gruntfile.

Problem 4: you can't use anything from npm

This one is the killer. npm has a few million packages. Essentially all of them are written as modules — they say require('lodash') or import React from 'react'. A browser has no idea what 'lodash' means. It's not a URL. There's no node_modules folder on the web. Without a tool, the entire npm ecosystem is off-limits.

Then modules arrived — and only solved half of it

ES Modules (ESM) landed in the language around 2015 and they're genuinely lovely. Each file gets its own scope. Dependencies are declared explicitly, in the file that needs them:

// cart-view.js
import { formatPrice } from './utils.js';
import { cart } from './cart.js';

Problems 1 and 2 — gone. Ordering is now derivable by a machine, and nothing leaks to window.

But hm. Problems 3 and 4 are still sitting right there, and modules actually made problem 3 worse. If every file imports two other files and the browser fetches each one separately as it discovers them, you don't get 40 requests — you get 900, arriving in waves, each wave blocked until the previous one parses. And import React from 'react' is still not a URL a browser can fetch.

That gap — "modules are a beautiful way to write code and a terrible way to ship code" — is the bundler-shaped hole.

2. The four jobs of a bundler

Here's the mental model I want you to carry around. A bundler is given one starting file — the entry point, usually src/main.jsx — and it does this:

Let's name the four jobs explicitly, because interviewers love it when you can enumerate them.

Job 1 — Module resolution

When the bundler sees import { formatPrice } from './utils', it has to turn that string into an actual file on disk. Is it ./utils.js? ./utils.ts? ./utils/index.js? And when it sees import React from 'react' — a "bare specifier", with no ./ — it walks up looking for node_modules/react, opens that package's package.json, and reads fields like main, module, or the modern exports map to decide which file is really the entry point.

This is the job the browser fundamentally cannot do. The browser has no filesystem and no node_modules. Resolution is the reason you can't just delete your build step.

Job 2 — Transformation

Your source files often aren't things a browser understands. JSX isn't JavaScript. TypeScript isn't JavaScript. A .css file isn't JavaScript at all, and neither is that PNG you imported. Each file gets run through whatever transformation it needs on the way into the graph: JSX compiled to function calls, TS types stripped, Sass compiled to CSS, small images inlined as base64 data URLs.

Job 3 — Bundling

Now the bundler has a graph of modules in the right order. It flattens them into one or more output files, wrapping each module so it keeps its own scope, and wiring the imports up to actual references. Roughly — very roughly — it produces something with this shape:

// a wildly simplified picture of bundle output
const modules = {
  './utils.js': (exports) => { exports.formatPrice = (n) => `$${n}`; },
  './cart.js':  (exports, require) => {
    const { formatPrice } = require('./utils.js');  // 👈 import became a lookup
    // ...
  },
};
require('./main.js');  // kick it off at the entry point

The key insight: each module ends up inside a function, so its variables stay private. The bundler has recreated module scope using nothing but plain function scope. That's how bundlers shipped ESM semantics to browsers that had never heard of ESM.

Job 4 — Optimisation

Finally the output gets squeezed. Minification strips whitespace, comments, and shortens things. Mangling renames local variables — const currentUserProfile becomes const e — which is safe precisely because module scope guarantees nobody outside can be referencing that name. Dead code is dropped (that's tree shaking, section 4). And each output file gets a content hash in its filename.

Wait — why the weird hash in the filename?

It's for caching, and it's a lovely trick. You tell the CDN "cache index-a4f9c2b1.js forever, it will never change" — because if the contents ever change, the hash changes, so it's a different filename. Users get aggressive caching with zero risk of stale code. If you shipped a plain app.js you'd have to choose between caching it (and serving stale code after a deploy) or not caching it (and re-downloading it every visit). The hash lets you have both. This is called long-term caching or cache busting, and it's a great thing to mention unprompted.

3. "But we have HTTP/2 and native modules now — do we still need a bundler?"

This is a genuinely good question and an increasingly common interview probe, because it sounds like a gotcha. Every browser has supported <script type="module"> since 2018. HTTP/2 multiplexes requests over one connection, so the "six connections" limit is gone. So can we just… ship source files?

The honest answer is: for a small side project, yes, genuinely. For a real app, no — and here's specifically why.

Give five reasons and you've answered better than 90% of candidates:

  1. npm resolution. import React from 'react' still isn't a URL. Import maps help, but you'd be hand-maintaining a map of every transitive dependency your dependencies have. Something has to walk node_modules.
  2. Non-JS assets. CSS modules, SVG-as-component, TypeScript, JSX, importing a JSON file. None of that is native.
  3. Minification. Unminified React app source is routinely 3–5× larger over the wire. HTTP/2 doesn't make bytes smaller.
  4. Tree shaking. Only possible when someone analyses the whole graph and drops what's unused. Nothing at runtime does that for you.
  5. Request count still matters. HTTP/2 removed the connection limit, not latency. A thousand small modules means a thousand request/response cycles, each with a discovery step — the browser can't request c.js until it has parsed b.js and seen the import. You get a waterfall: a deep dependency chain becomes a deep sequential chain of round trips. Ten levels deep on a 100 ms connection is a full second of doing nothing.

In an interview: "Why do we still need bundlers?"

Say something like

"Bundling started out as a workaround for HTTP/1 request limits, and that specific reason is mostly gone. But four other reasons aren't. Browsers can't resolve node_modules, so something has to turn bare imports into real paths. Browsers can't handle JSX, TypeScript, or CSS imports. Minification and tree shaking need a tool that sees the whole graph. And even on HTTP/2, deep import chains cause a request waterfall, because the browser can only discover a module after parsing the one that imports it. So the reason changed, but the need didn't."

Why this lands: you're showing you know the history and that you've reasoned about whether the old justification still holds. The waterfall point in particular signals you understand how the browser discovers modules, not just that "bundling is faster".

4. Tree shaking, and why CommonJS ruins it

Let's start with the surprise. You import one tiny function:

import _ from 'lodash';

const total = _.sumBy(cart.items, 'price');

You used one function. You shipped about 70 KB minified of lodash to every user. Meanwhile your colleague wrote this:

import { sumBy } from 'lodash-es';

const total = sumBy(cart.items, 'price');

…and shipped about 2 KB. Same library. Same function. Same bundler. Why?

The name first, because the name is the mental model

Picture your app as a tree. The entry point is the trunk. Every import branches off it, and those branch further, until you reach leaves — individual functions and constants. Now grab the trunk and shake it. Anything still firmly attached — anything actually reachable from the trunk — stays. The dead stuff, the bits not really connected, falls off.

That's it. Tree shaking is dead-code elimination across the whole module graph: if nothing reachable from the entry point uses this export, don't include it in the bundle.

(The analogy breaks down in one place worth knowing: a real tree's dead leaves fall because they're weakly attached, whereas the bundler is making a deliberate reachability decision. And unlike a tree, this analysis happens without ever running the code — which turns out to be the whole ballgame.)

Why it requires ESM — the actual reason

This is the follow-up interviewers use to sort people, so let's get it precisely right.

ES Module imports are static. That's a specific technical claim, not a vibe. It means:

  • They can only appear at the top level of a module — never inside an if, never inside a function.
  • The module specifier must be a string literal. You cannot write import x from someVariable.
  • Which names are imported and exported is fixed and knowable before the code runs.

Those restrictions felt annoying when ESM shipped. They're the entire point. Because imports are static, a tool can parse your file, build the complete graph of who-uses-what, and prove that sumBy is used and debounce isn't — without executing a single line. That's called static analysis.

Now here's CommonJS, the module system Node invented years before ESM existed and which most of npm still ships:

// CommonJS — this is all just... normal runtime code
const _ = require('lodash');

if (user.isAdmin) {
  const admin = require('./admin-tools');   // 👈 conditional import!
}

const name = process.env.WIDGET;
const widget = require(`./widgets/${name}`);   // 👈 the path is computed at runtime

require is not syntax. It's a function call. It can be called anywhere, conditionally, in a loop, with a path built from a template string, from a variable, from data fetched off the network. And module.exports is just an object you can mutate at runtime — a module can add exports inside an if statement.

So ask yourself: could a tool look at that third example and tell you which widget files are used? It cannot. It would have to run the program, with the real environment, with all possible inputs, to know. That's not static analysis; that's just… running your app. Which the bundler can't do.

A common misconception

"CommonJS can't be tree-shaken because bundlers didn't bother implementing it." No — it's not a missing feature, it's an information-theoretic limitation. The information a bundler needs (which exports are used) genuinely does not exist in a CommonJS file until runtime. Modern bundlers do try heuristic analysis of simple CJS patterns, but they must be conservative: when in doubt they keep everything, because dropping a module that might be needed would break your app. Being safe means being fat.

So back to lodash. The lodash package on npm is CommonJS. The bundler sees an opaque blob it can't safely take apart, so it includes the whole thing. lodash-es is the exact same library published as ES Modules — now every function is a separate statically-analysable export, and everything you didn't reference gets shaken out.

Wait — what about import { sumBy } from 'lodash' (no -es)?

Good instinct, and it's a trap. Writing named-import syntax doesn't magically make the target package ESM. Your bundler will still resolve 'lodash' to a CommonJS file and — depending on the bundler and settings — likely pull in the whole thing. The named-import syntax only helps if the package you're importing is ESM. Check the package's package.json for a "module" field or an "exports" map with an "import" condition. That's the real signal.

Why side effects break tree shaking

Here's the second half of the story, and it's the part people miss.

Suppose you import one function from a module, and that module also does this at the top level:

// analytics.js
export function trackEvent(name) { /* ... */ }

window.__ANALYTICS_READY__ = true;   // 👈 a side effect
document.body.classList.add('analytics-on');

Now imagine you import trackEvent but never call it. Can the bundler delete this module entirely? No. Because merely evaluating the module changes the world outside itself. Deleting it would remove a class from the body. The bundler has no idea whether your app depends on that.

A "side effect" here means exactly that: anything a module does when it's evaluated, beyond defining its exports. Mutating a global. Registering a custom element. Adding a polyfill to Array.prototype. Importing a CSS file (yes — import './styles.css' is pure side effect; it has no exports at all, and that's the point of it).

So bundlers are conservative: if a module might have side effects, it stays. And this is where the package author has to help you:

// package.json
{
  "name": "@acme/ui-kit",
  "sideEffects": false    // 👈 a promise, not a setting
}

"sideEffects": false is the author saying: "I promise that importing any file in this package and not using its exports does nothing observable. Feel free to delete any of it." It's a contract. If it's a lie, you get bugs that only appear in production builds — the classic "works in dev, broken after build" nightmare, because dev servers usually don't tree-shake.

If a package has some side-effectful files (nearly always CSS), you list them instead of lying:

  "sideEffects": ["**/*.css", "./src/polyfills.js"]

In an interview: "Why can't CommonJS be tree-shaken?"

Say something like

"Tree shaking is static analysis — the bundler has to know which exports are used without running the code. ESM makes that possible because imports are syntax: top-level only, string literal specifiers, fixed binding names. CommonJS require is just a function call, so it can be conditional, in a loop, or take a computed path, and module.exports can be mutated at runtime. The bundler can't prove what's unused, and since guessing wrong breaks the app, it keeps everything. That's why lodash bloats a bundle and lodash-es doesn't."

Why this lands: the phrase "guessing wrong breaks the app, so it keeps everything" shows you understand why the tool is conservative. That's the difference between recall and reasoning, and it's usually what the interviewer is actually testing here.

Trap: "tree shaking removes unused code" — why that answer gets dinged

It's not wrong, it's just shallow, and it invites the follow-up you can't answer. Two things elevate it. First, name the mechanism: static analysis of ESM imports at build time. Second, name the limits: it only removes module-level exports that are provably unreachable, and side effects block it. It will not remove an unused branch inside a function you do call — that's the minifier's job (and the minifier can only see one file at a time). Knowing the boundary between "tree shaker" and "minifier" is a genuinely senior distinction.

5. Code splitting and dynamic import()

We spent section 1 celebrating the fact that a bundler squashes everything into one file. Now let's un-celebrate it a bit.

Imagine an e-commerce app. There's a product listing page, a checkout flow, and an admin dashboard with a heavyweight charting library. All of it goes into one bundle.js that comes out at 1.4 MB.

A user lands on the homepage. Their browser must download all 1.4 MB, then parse and execute all of it, before anything meaningful appears — because your ReactDOM.render call is at the bottom of it. They're waiting on the admin charting library to be parsed in order to see a list of shoes. They will never open the admin dashboard. They don't have an admin account.

That's the problem. The fix is called code splitting: instead of one bundle, emit several, and load each one only when it's actually needed.

The mechanism: import() as a function

Static import is syntax. There's also a dynamic import(), which looks like a function call and returns a Promise:

button.addEventListener('click', async () => {
  const { renderChart } = await import('./charts.js');  // 👈 a split point
  renderChart(salesData);
});

Here's the crucial bit, and it's the thing to say out loud in an interview: import() is a signal to the bundler, not just a runtime feature. When the bundler walks the graph and hits a dynamic import(), it doesn't inline that module. It says "ah — a split point" and puts charts.js and everything only it depends on into a separate output file, a chunk. Then it rewrites your import() into code that injects a <script> tag (or does a native module import) for that chunk on demand and resolves the promise when it's loaded.

Where should you split? Routes, by default.

"How do you decide where to code-split?" is a common interview question, and the good answer starts with a principle rather than a list: split at boundaries the user won't cross in a single session, and where the deferred code is large enough that the extra request is worth it.

In practice that ranks like this:

  1. Routes. Almost always the right first move, and often the only one you need. A user on /products demonstrably isn't running /admin code. Route boundaries are natural, obvious, and align with navigation, which the user already expects to take a moment.
  2. Heavy conditional UI. A rich text editor inside a modal that opens 5% of the time. A charting library on a tab. A date picker. If it's big and behind an interaction, split it.
  3. Vendor chunks. Separate your node_modules dependencies from your own code. Your app code changes daily; React doesn't. If they share a file, one typo invalidates the content hash and every returning user re-downloads React. Split them and the vendor chunk stays cached for months.

And a caution, because interviewers like to hear that you know where the idea stops being good: don't split small things. Each chunk is another request, and — worse — a chunk that is only discovered after its parent has loaded and run creates exactly the waterfall we complained about in section 3. Fifty 4 KB chunks are meaningfully slower than one 200 KB chunk. Splitting has a fixed cost per split; it only pays off when the deferred payload is big.

React's version: lazy + Suspense

React wraps the dynamic import in an API that fits its rendering model:

import { lazy, Suspense } from 'react';

const AdminDashboard = lazy(() => import('./AdminDashboard'));

function App() {
  return (
    <Suspense fallback={<Spinner />}>      {/* 👈 shown while the chunk downloads */}
      <AdminDashboard />
    </Suspense>
  );
}

lazy takes a function that returns the import promise. React renders the fallback until that promise resolves, then swaps in the real component. There must be a Suspense boundary somewhere above a lazy component, or React throws — and where you put that boundary determines how much of the screen goes blank during the load. Put it too high and clicking a tab blanks the whole page; put it around just the tab panel and only the panel shows a spinner.

Preloading: getting the chunk before you need it

Lazy loading has an obvious downside — the user clicks and then waits for a network request. But you often know what's coming next before the user commits to it. So fetch it early:

// start downloading the checkout chunk when they hover the button
<button
  onMouseEnter={() => import('./CheckoutFlow')}   // 👈 warms the cache
  onClick={goToCheckout}
>
  Checkout
</button>

Calling import() and throwing away the result still downloads and caches the chunk. By the time the click lands, it's already there. Hover-intent, viewport visibility (via IntersectionObserver), or "idle time after first paint" are all common triggers.

There are also declarative hints the bundler can emit into your HTML: <link rel="preload"> means "I need this for the current page, fetch it at high priority now", while <link rel="prefetch"> means "I'll probably need this for a future navigation, grab it at lowest priority when you're idle". Prefetch is the right one for a route chunk you expect them to visit next.

6. Webpack vs Vite: the real difference

If you take one thing from this guide into an interview, make it this section. It's the single most asked build-tool question right now, and there's a crisp answer.

Start with the observation everyone has felt. On a large app, webpack serve takes 40 seconds to start, and saving a file takes 3 seconds to reflect. vite starts in 300 milliseconds and updates instantly. And it stays that way as the app grows. What on earth is going on?

Webpack's dev server: bundle first, then serve

Webpack has one strategy and it uses it everywhere. To serve your app in development, it does the full graph walk from section 2 — resolve every module, transform every module, bundle it all — and holds the result in memory. Only then can it answer the browser's first request.

So the startup cost is proportional to the size of your entire app. Two thousand modules? You process two thousand modules before you see anything, even though the page you're looking at uses forty of them.

It's like a restaurant that cooks every dish on the menu before it will let the first customer order.

Vite's dev server: serve on demand over native ESM

Vite's insight is that browsers already support modules. So in development, Vite doesn't bundle your source at all. It starts a server, hands the browser an HTML file with <script type="module" src="/src/main.jsx">, and then waits.

The browser parses main.jsx, sees it imports ./App.jsx, and requests /src/App.jsx. Vite receives that request, transforms that one file (JSX → JS), and sends it back. The browser sees App's imports, requests those. And so on.

The browser is doing the graph walking. Vite is a transform-on-demand server. Startup work is essentially zero, and — this is the part to emphasise — it's independent of app size. A 50-module app and a 5,000-module app both start instantly, because in both cases Vite has done nothing yet.

The catch Vite had to solve: dependency pre-bundling

"Just serve everything as native ESM" doesn't quite work, for two reasons — and knowing both of them is what makes you sound like you've actually read about this rather than heard about it.

Reason one: much of npm is still CommonJS. The browser cannot execute module.exports = .... If a dependency ships CJS, native ESM serving is dead on arrival.

Reason two: the request explosion. Some packages are made of hundreds of tiny internal modules. lodash-es is over 600 files. If the browser fetched each one natively, opening your dev server would fire off thousands of requests, and the dev experience would be worse than webpack's.

So Vite splits the world in two. Your source code changes constantly and is served on demand, unbundled. Your dependencies barely ever change, so Vite bundles them once, on first start, using esbuild. That step:

  • converts CommonJS packages into ESM the browser can run, and
  • collapses each package into a single file, so lodash-es becomes one request instead of 600.

The result is cached in node_modules/.vite and only redone when your dependency list changes. That's why the first npm run dev after an install takes a few seconds and every one after is instant.

The nuance interviewers probe: Vite bundles in production

Ask a candidate "does Vite use a bundler for production?" and a surprising number say no, because they've absorbed "Vite is bundleless". It isn't. Vite is bundleless in development only. For vite build, it runs a full production bundle through Rollup — code splitting, tree shaking, minification, hashed filenames, CSS extraction, the lot.

Why not serve unbundled in production too, if native ESM is so good? Everything from section 3: the request waterfall on real-world latency, no tree shaking, no minification. Unbundled is great when the server is on localhost with sub-millisecond latency and you're loading a handful of files. It's terrible over a mobile network with hundreds.

A common misconception: "Vite is fast because it's written in Go/Rust"

Partly, but mostly no — and this is a great correction to make out loud. Vite's dev server is Node.js. The speed comes from the architecture: doing almost no work at startup and only transforming files that are actually requested. esbuild (which is Go) is used for dependency pre-bundling and for transpiling individual files quickly, so it contributes — but if Vite bundled your whole app at startup using esbuild, it'd still be slower than not bundling at all. Architecture first, language second.

Wait — if dev and prod use different pipelines, isn't that risky?

Yes, and this is the honest tradeoff you should volunteer rather than wait to be asked. In dev, your code runs unbundled with no tree shaking and no minification. In prod it runs through Rollup with all of it. That means a class of bug exists that only appears in production: a module dropped because of a wrong "sideEffects": false, code that breaks under variable mangling, a subtle difference in module evaluation order, or a dependency whose CJS→ESM interop behaves differently after pre-bundling versus after a Rollup build. Webpack's dev-and-prod both bundle, so it has less of this gap (though not zero — minification is still prod-only). The mitigation is boring and effective: run vite build && vite preview in CI and smoke-test the real production output before you ship.

In an interview: "Why is Vite's dev server so much faster than webpack's?"

Say something like

"They have fundamentally different dev architectures. Webpack bundles the entire app before it serves the first byte, so startup time scales with how many modules you have. Vite doesn't bundle your source in dev at all — it serves files over native ES modules and transforms each file only when the browser actually requests it, so startup is basically constant regardless of app size. The one thing it does pre-bundle is node_modules, using esbuild, because a lot of npm is still CommonJS and because packages like lodash-es would otherwise be hundreds of separate requests. And it's worth saying that for production Vite does bundle, with Rollup — the bundleless part is dev only."

Why this lands: you named the architectural difference in one sentence, explained the non-obvious pre-bundling step and why it's needed, and pre-empted the follow-up about production. That last move — answering the next question before it's asked — is what makes an answer feel senior.

7. Loaders vs plugins

This is webpack vocabulary, and it's a favourite question because it's a quick check on whether you've ever actually opened a config or just copy-pasted one.

Here's the distinction in one line: a loader transforms one file; a plugin can do anything, at any point in the build.

Loaders: a pipeline per file type

A loader is a function that takes the contents of a file and returns transformed contents. That's it. You configure them by matching a file pattern:

module: {
  rules: [
    { test: /\.tsx?$/,  use: 'ts-loader' },
    { test: /\.css$/,   use: ['style-loader', 'css-loader'] },  // 👈 note the order
  ],
}

The use array is a pipeline, and it runs right to left (or bottom to top, if written vertically). That trips everyone up the first time. In the CSS rule: css-loader runs first — it reads the CSS file, resolves any @import and url() references, and turns the result into a JavaScript module. Then style-loader takes that and wraps it in code that injects a <style> tag into the document at runtime.

Why right-to-left? Think of it as function composition: style(css(source)). You read the innermost call first, and that's the one that runs first. Once you see it that way it stops feeling backwards.

Other loaders you'll meet: babel-loader (JSX and modern syntax → older JS), sass-loader (Sass → CSS), svgr (an SVG file → a React component). The pattern is always the same: this file type isn't JavaScript; make it JavaScript.

Plugins: hooks into the whole build

A plugin isn't scoped to a file. It taps into webpack's compilation lifecycle — events like "compilation starting", "all modules resolved", "about to emit output files", "done" — and can do arbitrary work at any of them. It sees the whole build, not one file.

plugins: [
  new HtmlWebpackPlugin({ template: './index.html' }),
  new MiniCssExtractPlugin(),
  new webpack.DefinePlugin({
    'process.env.NODE_ENV': JSON.stringify('production'),
  }),
]

Look at what each of those actually does, because they're wildly different kinds of work — which is the point:

  • HtmlWebpackPlugin generates a brand new file (your index.html) and injects <script> tags for the hashed bundle names. It has to run at the end, because it can't know the hashes until everything is built. No loader could ever do this — a loader only ever sees one input file and returns one output.
  • MiniCssExtractPlugin collects all the CSS that css-loader turned into JS modules and pulls it back out into a real .css file, so it can load in parallel with your JS instead of being injected by JavaScript after the fact. It's a cross-module, whole-build operation.
  • DefinePlugin does a global find-and-replace of expressions across every module, which is how process.env.NODE_ENV becomes the literal string "production" everywhere (more on that in section 10).

In an interview: "What's the difference between a loader and a plugin?"

Say something like

"Loaders are per-file transformers — they run as a module is imported, matched by a file-pattern rule, and their job is to turn a non-JS file into something webpack can put in the graph. TypeScript, Sass, SVG-to-component, all loaders. They chain right-to-left, like function composition. Plugins are much broader: they hook into the compilation lifecycle and can act on the whole build. HtmlWebpackPlugin emitting an index.html with the hashed script tags injected is the clearest example, because that's something no per-file transformer could do — you don't know the hashes until every module is built."

Why this lands: the HtmlWebpackPlugin example proves the distinction rather than restating it. "It needs information that only exists after the whole build" is exactly the reason plugins have to exist as a separate concept.

8. Babel, transpiling, and polyfills

"What does Babel do that a bundler doesn't?" People blur these together constantly, so let's draw the line hard.

A bundler deals with the relationships between files. Which file imports which, how to find them, how to combine them, what to emit.

A transpiler deals with the contents of a single file. Given this file's source text, produce equivalent source text using different syntax. It has no idea other files exist.

They're orthogonal, which is why they compose: the bundler calls the transpiler (via babel-loader or Vite's transform step) once per file as it walks the graph.

What Babel actually does to your code

Two things, mainly. First, syntax that isn't JavaScript at all:

// you write JSX
const el = <Button onClick={save}>Save</Button>;

// Babel emits plain JS (modern React runtime)
const el = _jsx(Button, { onClick: save, children: "Save" });

Second, modern syntax your target browsers don't support:

// you write
const city = user?.address?.city ?? 'Unknown';

// Babel emits, for older targets
var _user$address;
var city = (_user$address = user == null ? void 0 : user.address) == null
  ? void 0 : _user$address.city;
if (city === null || city === void 0) city = 'Unknown';

Same behaviour, uglier, works in more places. That's transpiling.

The distinction that gets you points: syntax vs APIs

Here's the follow-up. Babel can rewrite ?. into old-style checks because ?. is grammar — a way of writing something the old language could already express. But consider:

const hasFreeShipping = cart.items.some(i => i.freeShipping);
const grouped = Object.groupBy(orders, o => o.status);
const res = await fetch('/api/cart');

Object.groupBy and fetch aren't syntax. They're APIs — functions that either exist on the platform or don't. There's no clever rewriting that makes a missing function appear. Babel can't help; it would have to write an implementation of Object.groupBy and add it to the page.

Which is exactly what a polyfill is: real code that defines a missing API at runtime, if it's absent. The standard source is core-js.

So the rule to remember, and it's a clean one to say out loud:

The one-liner

Transpiling handles syntax. Polyfills handle APIs. New syntax gets rewritten at build time and costs you nothing at runtime. Missing APIs need actual implementation code shipped to the browser, which costs bytes. That's also why polyfills should be conditional — you don't want to ship an Object.groupBy implementation to browsers that already have one.

Browserslist: how the tools know what "old" means

None of this works unless the tooling knows which browsers you care about. That's Browserslist — a shared config that Babel, Autoprefixer, and modern bundlers all read:

// package.json
"browserslist": [">0.5%", "last 2 versions", "not dead"]

Babel's @babel/preset-env takes that list, cross-references a compatibility database, and works out the minimum set of transforms needed. Loosen the targets (drop IE11, drop old Safari) and your bundle genuinely gets smaller and faster, because whole categories of transform and polyfill stop being necessary. Auditing your browserslist is one of the highest-value, lowest-effort bundle wins there is — good thing to mention in a performance conversation.

Wait — doesn't TypeScript also compile my code? Do I need Babel too?

Often not. There are three ways to strip TypeScript types: tsc, Babel with @babel/preset-typescript, or the fast native tools (esbuild/SWC). Most modern setups use esbuild or SWC and skip Babel entirely. But note something important: tsc is the only one that type-checks. Babel, esbuild, and SWC just delete the type annotations file-by-file — they never look at another file, so they can't know if your types actually agree. That's why so many projects run a separate tsc --noEmit in CI: the build strips types fast, and a separate process verifies them properly.

9. Source maps

Let's start with the pain, because it's visceral. You get an error report from production:

TypeError: Cannot read properties of undefined (reading 'id')
    at t (index-a4f9c2b1.js:1:48210)
    at o (index-a4f9c2b1.js:1:12904)

One file. One line (minifiers strip newlines). Functions called t and o. This is useless. Your actual code lived in CartSummary.tsx at line 34 in a function called calculateTotal, but every trace of that was destroyed by minification and mangling.

A source map is the undo. It's a separate JSON file — index-a4f9c2b1.js.map — that says, in effect: "position 1:48210 in the generated file came from line 34, column 12, of src/components/CartSummary.tsx, and the thing called t was originally called calculateTotal."

It's a lookup table from generated positions back to original ones. The positions are stored in a compact encoded string (base64 VLQ) so the file doesn't become enormous — a source map is often larger than the bundle it maps, and would be far worse stored naively.

The generated file points at its map with a comment on the last line:

//# sourceMappingURL=index-a4f9c2b1.js.map

DevTools sees that comment, fetches the map (only when DevTools is open — regular users never download it), and transparently shows you your original source in the Sources panel and in stack traces. The browser is still running the minified code; you're just seeing it through a translation layer.

Under the hood: maps compose

Your code goes through several transforms — TS → JS → bundled → minified. Each step produces a map from its output back to its input. The build chains them together so the final map points all the way back to your original .tsx, not just to the previous stage. When source maps are subtly wrong (off by a few lines, or landing you in a compiled intermediate), it's almost always a broken link in this chain.

The devtool options, and the tradeoff

Webpack exposes about a dozen devtool values, and Vite has a similar (smaller) set. You don't need to memorise the matrix — you need to understand the axis they vary along: build speed vs. fidelity vs. output size.

SettingWhat you getUse for
eval-cheap-module-source-map Fast rebuilds. Line-accurate but not column-accurate, mapped back to your original source. Development. The usual default.
source-map Full fidelity, separate .map file. Slowest to generate. Production, when you're uploading maps to an error tracker.
hidden-source-map Generates the map but omits the sourceMappingURL comment. Production where you want traces decoded server-side but not by anyone with DevTools.
false / none No maps at all. Fastest build. When you truly don't need debuggability.

The "cheap" in those names means "line-only, no column mappings", which is much cheaper to compute. The "module" means "map back to your pre-loader source rather than post-loader output" — without it you'd be debugging Babel's output, which is not what you want. And eval means each module is wrapped in eval() with its map inlined, which makes rebuilds very fast because only changed modules need re-wrapping.

Should you ship source maps to production?

This is the interview question, and the correct answer is "it depends, and here's the axis" — not yes or no.

The case against: a public source map is your original source code, with original filenames, comments, and structure. Anyone can open DevTools and read your entire frontend. That's not a catastrophe — your JS is already public, just obfuscated, and anyone determined can reverse it — but it removes all friction. If your source contains internal API endpoints, feature-flag names, unreleased feature code, or comments like // TODO: the admin check here is bypassable, you've handed that over.

The case for: without maps, production errors are unreadable, and you will be debugging real incidents blind.

The answer most teams land on: generate full source maps at build time, upload them to your error tracker (Sentry, Rollbar, Datadog — they all have a CLI step for exactly this), and then delete them from the deployed assets so they're never served publicly. Your stack traces get symbolicated server-side by the tracker, and no visitor can fetch the map. You get the debugging without the exposure.

In an interview: "Would you ship source maps to production?"

Say something like

"I'd always generate them, but I wouldn't usually serve them publicly. The standard setup is to build with full source maps, upload them to the error tracker as part of the deploy, then strip them from what actually ships. That way production stack traces are symbolicated and readable, but visitors can't just open DevTools and read our whole source. If it's an open-source or marketing site where the code isn't sensitive, serving them publicly is fine and makes debugging easier for everyone. The thing I'd never do is turn them off entirely — then you're debugging incidents from minified traces, which is miserable."

Why this lands: you gave a default, gave the exception, and named the failure mode of the opposite choice. Interviewers are checking whether you've been on-call for a production frontend — the "upload then strip" workflow is the tell that you have.

10. Environment variables (the one people get wrong)

Let me open with the question, because I want you to answer it in your head before you read on.

You put STRIPE_SECRET_KEY=sk_live_abc123 in a .env file. .env is in .gitignore, so it's never committed. You use it in your React app as process.env.STRIPE_SECRET_KEY. Is that key safe?

Think about it, then open this.

It is not safe even slightly. That key is now sitting in plain text inside your deployed JavaScript, and anyone can find it in about fifteen seconds by opening DevTools and searching the bundle for sk_live. Keeping .env out of git protected it from your repo. It did nothing at all to protect it from your users, because the build copied the value into the bundle.

Why it happens: inlining

Here's the mechanical explanation, and once you see it the whole thing is obvious.

There is no process object in a browser. process.env is a Node.js thing. So when your bundler sees process.env.API_URL in browser code, it can't leave it there — the code would throw process is not defined. Instead, at build time, it performs a textual substitution:

// what you write
const apiUrl = process.env.REACT_APP_API_URL;
if (process.env.NODE_ENV !== 'production') console.log('debug');

// what is literally in your shipped bundle
const apiUrl = "https://api.example.com";   // 👈 baked in as a string literal
if ("production" !== 'production') console.log('debug');

That's webpack's DefinePlugin (or Vite's define) doing a find-and-replace across every module before bundling. Your environment variable is not read at runtime — it was replaced at build time. The bundle contains the value, not the lookup.

Think of it like a mail merge. You write a template letter that says "Dear [NAME]". The mail-merge program runs once, and out come ten thousand letters that each say "Dear Priya". There's no [NAME] left in the printed letters, and you can't change Priya's name by editing the template afterwards — you'd have to reprint everything.

Two consequences fall straight out of that:

  1. Anything in a frontend env var is public. Not "hard to find" — public. It's a string literal in a file you serve to the world. No secrets, ever. Not API secret keys, not database URLs, not private tokens.
  2. Changing the value requires a rebuild. You cannot change your API URL by setting an env var on the server and restarting. The old value is printed into the letters. You must rebuild and redeploy.

Under the hood: this is also a performance feature

That second line above became if ("production" !== 'production'). The minifier evaluates that constant comparison, sees it's always false, and deletes the entire branch. This is how all of React's development warnings and prop-type checks vanish from production builds — they're wrapped in if (process.env.NODE_ENV !== 'production'), which inlining turns into dead code that the minifier removes. Inlining isn't just a compatibility hack; it's what makes build-time dead-code elimination possible.

Why the VITE_ / NEXT_PUBLIC_ / REACT_APP_ prefixes exist

Now the prefix makes sense. Consider what would happen if a build tool inlined every environment variable it could see. Your CI machine's environment contains AWS_SECRET_ACCESS_KEY, NPM_TOKEN, database passwords, deploy keys. Blindly inlining all of that into a public JS file would be a spectacular breach — and it would happen silently.

So these tools default to exposing nothing, and only inline variables whose names carry an explicit prefix:

# .env
DATABASE_URL=postgres://...        # never reaches the browser ✅
STRIPE_SECRET_KEY=sk_live_abc      # never reaches the browser ✅

VITE_API_URL=https://api.example.com   # inlined into the bundle
VITE_SENTRY_DSN=https://...            # inlined into the bundle

The prefix is a guardrail, not a security mechanism. It doesn't encrypt anything or hide anything. It forces you to make an explicit, deliberate, visible choice to publish a value — so leaking a secret requires actively typing VITE_ in front of it, rather than happening by accident. Saying exactly that sentence in an interview is a strong signal.

Wait — so what can go in there?

Anything that's fine for the public to see, which is more than you might think: your public API base URL, a Stripe publishable key (pk_live_... — designed to be public), a Sentry DSN, a Google Analytics ID, a Mapbox public token, feature-flag defaults. The rule of thumb: if you'd be comfortable printing it on a billboard, it can be an env var in a frontend build. If it grants the ability to do something on your behalf, it belongs on a server, behind an endpoint you control.

How to do genuine runtime configuration

"But I want to build one artifact and deploy it to staging and production with different API URLs" is a real requirement, and inlining fights it. Three real answers:

1. Fetch config at boot. Before rendering, request a small JSON document from your own server and use it:

const config = await fetch('/config.json').then(r => r.json());
// → { apiUrl: "https://api.staging.example.com", features: { newCart: true } }

Costs you one round trip before the app starts, so keep it tiny and don't put it behind the main bundle.

2. Inject into the HTML at request time. Your server (or edge function) serves index.html and stamps a small script into it:

<script>window.__APP_CONFIG__ = { apiUrl: "https://api.staging.example.com" };</script>

The HTML is generated per-request and shouldn't be cached anyway, so this costs nothing extra. This is the most common approach for containerised single-page apps that need to be environment-agnostic.

3. Read it server-side. In Next.js, Remix, Nuxt and friends, code that runs on the server can read any env var directly, with no prefix and no inlining, because it never ships to the browser. That's the cleanest answer when you have a server: keep the secret on the server and expose a narrow endpoint instead of the key.

In an interview: "Is it safe to put an API key in a .env for a React app?"

Say something like

"No — and the reason matters. In a frontend build, env vars aren't read at runtime; the bundler substitutes them as string literals at build time, so the value is baked into the JavaScript you serve. .gitignore keeps it out of the repo but does nothing about the bundle — anyone can find it with ctrl-F in DevTools. That's exactly why Vite requires a VITE_ prefix and Next requires NEXT_PUBLIC_: it's a guardrail forcing you to explicitly opt a value into being public. If something genuinely needs to stay secret, it lives on a server and the client calls an endpoint that uses it. And if I needed the same build to run against different environments, I'd fetch config at boot or inject it into the HTML at request time rather than inlining it."

Why this lands: three distinct signals in one answer — you understand build-time vs runtime, you know why the prefix convention exists (rather than just following it), and you have a real solution for the environment-agnostic-build problem instead of just a "no".

11. How HMR actually works

Hot Module Replacement is the thing that makes modern dev feel good, and almost nobody can explain it. Which makes it a lovely differentiator.

The model: invalidation and accept boundaries

The problem is familiar: you're five steps into a checkout form and you nudge a button's padding by 2px. A plain live-reload server calls location.reload() and every bit of that state is gone. HMR's promise is to swap the changed module's code into the already-running app, so component state, scroll position and your half-filled form all survive.

Two pieces make it work.

A live connection. The dev server injects a client that holds a WebSocket open, and on save sends "the module at /src/Button.jsx changed".

The module graph, walked upward. The server knows who imports whom. It marks the changed module invalid and asks: does anything know how to handle a new version of this? Modules opt in by registering a callback:

// Vite's HMR API (webpack's is module.hot.accept, same idea)
if (import.meta.hot) {
  import.meta.hot.accept((newModule) => {
    // I know how to swap myself out. Don't reload the page.
    render(newModule.Button);
  });
}

A module that does this is an accept boundary. When a change happens, the server walks up the import chain from the changed module — Button → Toolbar → Page → App — looking for the nearest ancestor that has accepted. It sends the update to that boundary, and the boundary re-executes with the new code. Everything above the boundary is untouched and keeps its state.

Why React needs a special layer: Fast Refresh

Plain HMR has a gap for UI frameworks. Swapping a module gives you a new component function — and React's state lives in a fiber keyed to component identity, so its natural reaction to "different component type" is to unmount and remount, throwing away exactly the state you were trying to save.

React Fast Refresh closes that gap. A Babel/SWC plugin registers each component export with a stable identity plus a signature of its hooks, so on update React can swap the implementation in place and reuse the existing fiber. And because it knows the hook signature, it's honest about when it can't: add, remove or reorder hooks and it deliberately remounts rather than corrupting state.

When HMR gives up and reloads

Because "why did my page just refresh?" is a daily experience: nothing up the chain accepted the update; the file has module-level side effects that can't be safely re-run; the config changed (vite.config.js, .env) so the server restarted; or the update itself errored and a clean slate is the safe recovery.

One of these is actionable: a file that exports both a component and something else often forces a reload, because Fast Refresh can only reliably hot-swap component exports. That's the quiet reason "one component per file" improves your dev loop.

12. Module federation & micro-frontends

This one only shows up at a certain scale, and it's fine to know it at name-recognition depth. The problem: 200 engineers across eight teams in one React app, where a failing billing test blocks the search team's release and builds take eleven minutes. Splitting into independently deployed apps fixes the org problem but costs you a full page load between apps, and each ships its own React.

Module federation (a webpack feature, since adopted elsewhere) tries to get the split without those costs — one deployed app imports a module from another separately deployed app, at runtime, over the network:

// in the "host" app's config — declaring what it consumes
new ModuleFederationPlugin({
  remotes: {
    checkout: 'checkout@https://checkout.example.com/remoteEntry.js',
  },
  shared: { react: { singleton: true } },   // 👈 the interesting part
});
// then, in app code — this import crosses a deployment boundary
const Checkout = lazy(() => import('checkout/CheckoutFlow'));

At runtime the host fetches remoteEntry.js — a manifest describing what the remote exposes — then fetches the actual chunk. The checkout team deploys whenever they like, and the host picks up the new version on the next page load with no rebuild.

The shared config is the clever bit: at runtime, the apps negotiate. If the host already loaded React 18.2, the remote uses that instance instead of downloading its own. That's what makes it different from an iframe or a script tag — you get one React, one context tree, shared state.

The costs, which are very real

Say these unprompted. Enthusiasm for federation without awareness of its costs reads as inexperience.

  • Shared dependency versioning is genuinely hard. Host on React 18, remote built against 19 — singleton: true means one wins and the other breaks in untested ways; not-singleton means two copies of React, which breaks hooks and context. Either way you need coordinated cross-team upgrades, which is precisely the coupling you split up to escape.
  • Runtime failure modes a monolith doesn't have. A remote's CDN goes slow, or ships a breaking change. You need per-remote error boundaries and fallbacks, and integration bugs surface in production instead of at build time.
  • It's an organisational solution, not a technical one. If you have twelve engineers, you don't have this problem — route-based code splitting gets you most of the loading benefit with none of the cost. Saying that is the answer.

13. esbuild, SWC, Turbopack: the native rewrite

For a decade, JavaScript tooling was written in JavaScript. Then esbuild appeared and did the same work 10–100× faster, and everything shifted. Why?

Why Go and Rust win here

Four reasons, and it's worth being able to name them rather than hand-waving "it's compiled":

  1. Real parallelism. Bundling is embarrassingly parallel — hundreds of independent files, each needing parse and transform. Go and Rust use all your CPU cores natively with shared memory. Node is single-threaded by default; worker threads exist but can't cheaply share a complex object graph like an AST, so you pay serialisation costs to move work between threads.
  2. No JS VM overhead. A JS tool has to be parsed, JIT-compiled, and warmed up before it runs at full speed — and a build is short enough that a lot of it runs in the slow, un-optimised tier. Compiled binaries are at full speed from the first instruction.
  3. No GC pressure. Parsing produces enormous numbers of small AST objects. In JS those are all garbage-collected heap objects, and the GC spends real time tracing them. Go and Rust let you lay data out compactly and control allocation — esbuild in particular is written to pass over the AST as few times as possible and reuse memory.
  4. Designed for the task, not accumulated. Some of the win is honestly just that these are fresh rewrites with a decade of hindsight, rather than a language advantage.

Who uses what

ToolLanguageWhat it's actually used for
esbuildGoExtremely fast bundler and transformer. Vite uses it for dependency pre-bundling and for stripping TS/JSX per file in dev. Also a fine standalone bundler for simpler projects.
SWCRustA Babel replacement — transpiling and minifying, with a Babel-ish plugin model. Next.js replaced Babel with SWC by default; also what Jest/Vitest often use to transform test files quickly.
TurbopackRustVercel's incremental bundler for Next.js. Its distinguishing idea is fine-grained caching of every unit of work, so a rebuild only redoes what genuinely changed.
RolldownRustA Rust rewrite of Rollup, intended to become Vite's single engine for both dev and prod — which would close the dev/prod gap we flagged in section 6.

The honest tradeoff

Speed isn't free, and interviewers like hearing the caveat:

  • Plugin ecosystems lag. Webpack and Rollup have a decade of plugins for every conceivable need. A Rust tool's plugins must be written in Rust, or cross a language boundary (WASM, or a JS bridge) that erodes the speed advantage. Migrating a mature webpack config often stalls on one obscure plugin with no equivalent.
  • Edge cases take years to match. The long tail of weird CommonJS interop, unusual exports maps, decorator semantics, and broken-but-widely-used packages is where mature tools have spent a decade accumulating fixes. New tools rediscover these one bug report at a time.
  • Not everything is equally deep. esbuild's minifier, for instance, is very fast but historically less aggressive than Terser on some optimisations — a real bytes-vs-build-time tradeoff, not a strict win.

14. "Why is my bundle so big, and how would you find out?"

This one is worth its own section because it's a favourite closing question — it's open-ended, and it tests whether you measure or guess. The wrong answer starts with a fix. The right answer starts with a measurement.

Step 1: look at it. Generate a treemap of what's in the bundle. webpack-bundle-analyzer, or rollup-plugin-visualizer for Vite/Rollup. You get a picture where rectangle area is byte size. In my experience the answer is visible within about ten seconds — there's one enormous rectangle you didn't expect. It's usually moment.js with all its locales, or an icon library imported wholesale, or a charting library, or a duplicate copy of a dependency.

Step 2: check for duplicates. Two versions of the same library is startlingly common — your app depends on date-fns@2, and a UI kit depends on date-fns@3, so both get bundled. npm ls date-fns shows the tree; deduping or aligning versions can cut a lot for very little work.

Step 3: check your import style. Look for the section-4 problem: whole-package default imports where a named or deep import from an ESM build would tree-shake. Icon libraries are the classic offender — import { FiUser } from 'react-icons/fi' can pull in thousands of icons depending on the build.

Step 4: check what's loading eagerly that shouldn't be. Is the admin dashboard in the main chunk? The rich-text editor? Anything behind a route or an interaction is a code-splitting candidate.

Step 5: check your browserslist. If you're still targeting very old browsers you're shipping transforms and polyfills for no one. Modern targets can shave a meaningful chunk.

Step 6: prevent regression. Add a bundle-size budget to CI that fails the build if the main chunk grows past a threshold. Bundles don't get big in one commit; they get big through fifty commits that each added 8 KB and nobody noticed.

In an interview: "Our bundle is 3 MB. What do you do?"

Say something like

"First I'd measure rather than guess — run a bundle analyzer to get a treemap, because usually one or two dependencies dominate and it's obvious on sight. Then I'd check the cheap wins in order: duplicate copies of the same library from mismatched versions, whole-package imports that should be named imports against an ESM build, and anything loading eagerly that could be route-split — an admin area or a heavy editor. After that I'd look at browserslist targets, since old targets add transforms and polyfills. And I'd add a size budget to CI, because bundles grow 10 KB at a time and the real fix is noticing before it's 3 MB."

Why this lands: you led with measurement, gave an ordered plan instead of a grab-bag, and finished with prevention. That last part especially reads as someone who has maintained an app rather than just optimised one once.

Interview cheat sheet

The morning-of version. One crisp line each.

What a bundler does
Starts at an entry file, walks every import to build a dependency graph, resolves each specifier to a real file, transforms non-JS into JS, and emits optimised files a browser can load. Four jobs: resolution, transformation, bundling, optimisation.
Do we still need one with HTTP/2 + native ESM?
Yes: browsers can't resolve node_modules, can't handle JSX/TS/CSS imports, don't minify, don't tree-shake, and deep import chains still cause request waterfalls because each module is only discovered after its parent parses.
Tree shaking
Build-time dead-code elimination across the module graph — drop exports nothing reachable from the entry uses.
Why CommonJS can't be tree-shaken
Tree shaking is static analysis. ESM imports are syntax — top-level, string-literal, fixed. require is a runtime function call that can be conditional or computed, so the bundler can't prove what's unused, and being wrong breaks the app, so it keeps everything.
"sideEffects": false
A package author's promise that importing a file without using its exports does nothing observable, so unused modules can be deleted entirely. Usually written as an array excluding CSS files.
Code splitting
Dynamic import() returns a promise and tells the bundler to emit a separate chunk loaded on demand. Default strategy: split by route. Don't over-split — each chunk is a request and can create a waterfall.
Where to split
Route boundaries first, then heavy conditional UI (modals, editors, charts), then a vendor chunk so rarely-changing deps stay cached across deploys.
Webpack vs Vite in dev
Webpack bundles the whole app before serving, so startup scales with app size. Vite serves source over native ESM and transforms only the file the browser requests, so startup is near-constant.
Vite dependency pre-bundling
esbuild bundles node_modules once on first run — converts CommonJS to ESM, and collapses packages made of hundreds of files into one request each.
Does Vite bundle for production?
Yes — Rollup, with tree shaking, splitting, minification and hashed filenames. Bundleless is dev-only. The dev/prod difference is a real tradeoff; run vite build && vite preview before shipping.
Loader vs plugin
Loaders transform one file as it's imported, matched by pattern, chained right-to-left. Plugins hook the whole compilation lifecycle — e.g. HtmlWebpackPlugin emits an index.html with hashed script tags, which needs whole-build knowledge no loader has.
Babel vs bundler
Babel transforms the contents of one file (JSX → JS, modern syntax → older). The bundler handles relationships between files. The bundler invokes the transpiler per module.
Transpiling vs polyfilling
Transpiling rewrites syntax at build time and costs nothing at runtime. Polyfills ship real implementations of missing APIs (core-js) and cost bytes. Browserslist targets decide how much of each you need.
Source maps
A mapping from generated positions back to original file/line/column/name, so minified stack traces and the debugger show your real source. Devtool options trade build speed against fidelity.
Ship source maps to prod?
Generate them always; upload to the error tracker; strip them from deployed assets. Readable production traces without publishing your source.
Env vars in a frontend build
Inlined as string literals at build time, so they're baked into the bundle and fully public — never a secret, and changing one requires a rebuild.
Why VITE_ / NEXT_PUBLIC_
A guardrail, not security: tools expose nothing by default so a CI machine's secrets can't leak in, and publishing a value requires an explicit deliberate prefix.
Real runtime config
Fetch a small /config.json at boot, inject a config object into the HTML at request time, or read the var server-side and expose a narrow endpoint.
HMR
WebSocket tells the client which module changed; the update walks up the import graph to the nearest module that registered an accept handler and re-runs from there. No boundary found → full reload.
React Fast Refresh
A layer above HMR that registers component identities and hook signatures so React can swap a component's implementation in place and keep its state — remounting deliberately if the hook order changed.
Module federation
Import modules from another independently deployed app at runtime, with negotiated shared dependencies. Solves org-scale coordination; costs you shared-version pain, runtime failure modes, and ops complexity.
esbuild / SWC / Turbopack
Go/Rust rewrites: true parallelism, no JS VM warm-up, no GC pressure on huge ASTs. esbuild for pre-bundling and fast transforms, SWC as a Babel replacement, Turbopack as Next's incremental bundler. Tradeoff: thinner plugin ecosystems and edge-case gaps.
Diagnosing a big bundle
Analyzer treemap first, then duplicate versions, then whole-package imports, then eager code that should be split, then browserslist, then a CI size budget so it doesn't regress.

One last thing

If you remember nothing else, remember this: almost every build tool feature exists to solve one of the four problems from section 1. Resolution exists because browsers have no node_modules. Bundling exists because requests have latency. Tree shaking and minification exist because bytes cost time. Content hashes exist because caching is a tradeoff between freshness and speed.

Configs are intimidating because they're a flat list of options with no visible structure. But once you can sort each option into "which of the four problems is this solving?", webpack's config stops being an incantation and becomes something you can reason about. That's the shift interviewers are listening for — and honestly, it's the shift that makes the tools stop being scary at work, too. 🛠️
