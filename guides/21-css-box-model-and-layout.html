The Box Model, Flexbox, Grid & Positioning

Everything visual on the web comes down to boxes: how big they are, how they line up, and where they sit. Get these four ideas properly in your head and CSS stops feeling like guesswork.

Let me start with the single most common CSS bug in the world. You write this:

The setup 
.card {
  width: 100%;
  padding: 20px;
  border: 1px solid gray;
}

Reasonable, right? “Fill the available space, and give me a bit of breathing room inside.” And then the card pokes out past the right edge of its container, a horizontal scrollbar appears at the bottom of the page, and you spend twenty minutes adding overflow: hidden to things until the symptom goes away.

That bug is not a browser quirk. It is the box model working exactly as specified, and once you can see why it happens, an enormous amount of CSS becomes predictable instead of magical. So let’s start there, and build up from it.

A quick promise about how this guide works: I’m not going to use a term before I’ve explained it. If you’ve never confidently explained what a “containing block” is, or why position: sticky sometimes just… doesn’t, you’re in the right place. And because this guide is itself an HTML file, almost every idea here comes with a live demo — real boxes, laid out by your real browser, right there in the page. When I say “look at what happens,” you can actually look.

Part 1The box model, and why your width is a lie

Every single element on a page — a paragraph, a button, an image, a <div>, even a lone <span> of text — is drawn by the browser as a rectangle. Not “kind of like” a rectangle. It is a rectangle, and if you open your browser’s devtools and hover over anything, you’ll see the browser draw that rectangle in coloured layers.

Those layers are the box model, and there are four of them, nested inside each other like a parcel:

The parcel analogy is the one I’d use in an interview, because it maps almost perfectly. You’re shipping a mug. The mug is the content. The bubble wrap you stuff around it is the padding — it’s inside the box, it takes up space in the box, and it’s there to stop the mug touching the walls. The cardboard is the border. And the margin is the space you leave between this parcel and the next parcel on the shelf — it isn’t part of the parcel at all, it just stops them touching.

Where the analogy breaks down: with real parcels, if you put bubble wrap in a box, the mug has to get smaller. In CSS it’s the other way round by default — adding padding makes the box get bigger and leaves the mug alone. That is precisely the bug we opened with, and we’ll fix it in a minute.

Here’s a real element with all four layers made visible. This is live CSS — nothing is faked with images:

That last point trips people up constantly, so let me say it plainly: backgrounds extend under the padding but never into the margin. If you want the coloured area of a button to be bigger, you add padding. If you want space between two buttons, you add margin. Choosing the wrong one is the difference between a chunkier button and a button that’s the same size but further away.

Wait, what about… the shorthand order?

padding: 10px 20px 30px 40px goes top, right, bottom, left — clockwise starting at the top. Two values means vertical, horizontal. Three means top, horizontal, bottom. The mnemonic everyone uses is TRouBLe. This applies identically to margin, border-width, and inset.

Part 2content-box vs border-box

Now the important question. When you write width: 200px, which of those four boxes are you setting to 200px?

Take a guess before you scroll. It genuinely could be either — the content box, or the whole visible box out to the border.

The answer, by default, is the content box. Just the innermost blue rectangle. Padding and border are then added on top of that number. So this element:

The default: box-sizing: content-box 
.box {
  width: 200px;
  padding: 20px;
  border: 5px solid;
}
/* actual space taken on screen:
   200 + 20 + 20 + 5 + 5 = 250px  <-- not 200 */

You asked for 200. You got 250. And now imagine that width was 100% instead. “100% of my parent” means 100% of the parent’s content width — and then we bolt 50px of padding and border onto the outside of that. The element is now 50px wider than the thing it’s sitting inside. It overflows. Horizontal scrollbar. That’s the opening bug, fully explained.

So CSS gives us a switch: box-sizing. Set it to border-box and width changes meaning — it now describes the whole visible box, out to the outer edge of the border. Padding and border get subtracted from the inside instead of added to the outside. Here are those exact same declarations, side by side, with the only difference being box-sizing:

Look at the right-hand one again. With border-box, the number you type is the number you get on screen. Padding and border rearrange the inside of the box rather than inflating it. That is what everyone actually wants, essentially always, which is why almost every stylesheet written in the last decade opens with some version of this:

✓ The line at the top of every modern stylesheet 
*, *::before, *::after {
  box-sizing: border-box; /* 👈 the whole trick */
}

The *::before, *::after part is there because pseudo-elements aren’t matched by * on its own, and they’re real boxes too. Get one without the other and you’ll eventually chase a mysterious 2px in a tooltip arrow.

Under the hood — why is content-box the default at all?

Because the original CSS spec said so in 1996, and the web is not allowed to break. Ironically, old Internet Explorer implemented it the other way (border-box), which everyone at the time called a bug — and which we have all now agreed was the better design. The spec couldn’t just change the default without re-laying-out every page ever written, so instead we got box-sizing as an opt-in in CSS3. Every single one of us opts in.

One nice detail: border-box does not include margin. Margin is always outside, always added on, under both modes. So width: 100%; margin: 0 10px still overflows by 20px. If you catch yourself writing that, you probably want padding on the parent instead.

A common misconception

“border-box makes the padding disappear.” It absolutely does not. The padding is still there, still 20px, still pushing your text inwards, still filled with the background colour. What changes is who pays for it — the content area shrinks to make room, instead of the element growing. If you set width: 30px; padding: 20px under border-box, the padding wins: 40px of padding cannot fit in a 30px box, so the element renders 40px wide and your declared width is quietly ignored. Padding and border are never sacrificed.

In an interview

“Why does width: 100% plus padding overflow?” is a screening question. It takes ten seconds to answer and it cleanly separates people who have a mental model from people who pattern-match on Stack Overflow answers. Don’t just say “because of box-sizing” — say what the two values mean.

Say this out loud

“By default, width only sets the content box — padding and border get added on top of it. So width: 100% means ‘as wide as my parent’s content area’, and then the padding pushes past that, and you overflow. Setting box-sizing: border-box changes what width refers to: now it’s the whole box out to the border, and padding eats inwards instead of outwards. That’s why nearly every stylesheet starts with a universal border-box reset — it makes sizing behave the way people intuitively expect.”

Why it lands: you named the mechanism (which box width refers to), not just the fix. That signals you could debug a sizing problem you’ve never seen before, rather than reaching for a remedy you memorised.

Follow-ups they’ll actually ask

“So does border-box fix everything? Why would anyone want content-box?

Rarely, but it exists. If you genuinely need the inner area to be an exact size — a canvas, an embedded map, an image slot that must be exactly 300×200 regardless of how thick a decorative border you add — then content-box is expressing exactly that intent. Some third-party widgets also ship assuming it. In your own layout code you will basically never want it.

“Is box-sizing inherited?”

No, and this is a real gotcha. That’s why the reset uses the universal selector * rather than setting it on html and hoping. There is a well-known variant that makes it inheritable on purpose:

html { box-sizing: border-box; }
*, *::before, *::after { box-sizing: inherit; }

The advantage is that a third-party component can flip itself and its whole subtree back to content-box with one declaration. It’s a nice answer to give because it shows you’ve thought about the reset rather than copy-pasted it.

“How would you fix the overflow without box-sizing?”

Three ways, and the ranking matters. Best: don’t set a width at all. A <div> in normal flow already fills its parent’s width, and unlike width: 100% it correctly shrinks its content area to accommodate padding. width: 100% on a block element is usually redundant and harmful. Second: width: calc(100% - 40px) — works, but you now have to keep two numbers in sync forever. Third: move the padding to a wrapper element. Mentioning the first option is the strong answer, because it shows you understand that block elements are already full-width in flow layout.

Part 3Margin collapsing

Right. This one is genuinely weird, and I want to say up front: margin collapsing confuses everybody. I’ve been writing CSS for years and I still occasionally have to stop and reason it through from first principles. If it feels slippery, that’s not you being slow — it’s a genuinely unintuitive rule that exists for historical reasons.

Here’s the setup. Two paragraphs, stacked. Each has margin: 30px 0. How much space is between them?

The obvious answer is 60px — 30 from the bottom of the first, 30 from the top of the second. Let’s check.

In normal flow, adjacent vertical margins collapse: instead of adding, they overlap, and you get the larger of the two. 30 and 30 gives 30. 30 and 50 would give 50, not 80.

The mental model: margins are minimum clearances, not springs

The picture that made this click for me is personal space. Imagine each element is a person standing in a queue, and each one has a rule: “I need at least 30cm of empty space in front of me.” The person behind them says the same thing. Do you end up with 60cm between them? No — you end up with 30cm, and both people’s requirements are satisfied simultaneously. The space is shared, not stacked. If one person needed 50cm and the other needed 30cm, you’d leave 50cm, which satisfies both.

That’s exactly what collapsing is. A margin is a minimum clearance request, not a physical block of matter that gets stacked. Two overlapping requests resolve to whichever is larger.

Where the analogy breaks down: real people don’t stand inside each other, but negative margins do genuinely pull elements together and overlap. With negative values the rule is: take the largest positive and the most negative, and add them. margin-bottom: 30px meeting margin-top: -10px gives 20px of space.

And why does this exist? Because the web was built for documents. Imagine a page of headings and paragraphs where each has sensible top and bottom margins. Without collapsing, the gap between a heading and a paragraph would be the sum of both, and every document would be full of inconsistent, doubled-up whitespace. Collapsing makes prose look right by default. It’s a typography feature, not a layout feature — which is exactly why it doesn’t apply in the layout-oriented modes.

The one that surprises people: parent and child

Collapsing doesn’t only happen between siblings. Margins also collapse through a parent. Watch:

The setup 
.parent { background: green; }   /* no padding, no border */
.child  { margin: 34px; }

What do you expect? Probably: a green box, with the child floating 34px inside it. What you actually get is the child’s top margin escaping the parent and pushing the parent down instead. The green box hugs the child with no gap at all on the top and bottom edges.

Back to the queue analogy: the parent here is a completely transparent, zero-thickness rope around the child. The child says “I need 34cm of clearance above me”, and since the rope has no thickness of its own, that clearance has to come from outside the rope. There’s literally nothing between the child’s margin and the world.

What stops collapsing

This is the practically useful half, and the half that interviewers push on. Collapsing needs the two margins to be touching, with nothing in between. So anything that puts something in between stops it:

What stops itWhy
padding or border on the parentPhysically separates the child’s margin from the parent’s outer edge. Even 1px works, which is why you sometimes see the padding: 0.05px hack.
The parent is a flex or grid containerFlex and grid are different layout algorithms. Margin collapsing is a rule of flow layout only, so it simply doesn’t exist there.
overflow not visible (hidden, auto, scroll)Creates a block formatting context — a self-contained layout bubble whose margins can’t interact with the outside.
display: flow-rootThe modern, side-effect-free way to make that same bubble. Purpose-built for exactly this.
position: absolute or fixed, or a floatThe element leaves normal flow entirely, so there’s no adjacency to collapse.
Anything between the siblingsEven an empty element with a 1px border will break a sibling collapse.
Wait, what about horizontal margins?

They never collapse. margin-left and margin-right always add up normally. Two side-by-side elements with 20px horizontal margins each will sit 40px apart. This asymmetry is a real thing and it’s worth stating in an interview — collapsing is a vertical-only, flow-layout-only phenomenon. (In a vertical writing mode it’s the block axis that collapses, which happens to be horizontal, but nobody will push you on that.)

The modern answer: mostly, stop using margins for spacing

Here’s the thing that makes all of this much less painful in practice. The reason margin collapsing was a daily source of pain is that for twenty years, margin was the only tool for putting space between things. Now it isn’t. Flexbox and grid both support gap, which sets space between children directly — no collapsing, no doubling, no escaping, no negative-margin tricks.

✗ The old way — margins that fight you 
.list > * + * { margin-top: 16px; } /* the "lobotomised owl" */
✓ The modern way 
.list { display: flex; flex-direction: column; gap: 16px; }

Margin is still the right tool for one thing: an element expressing its own spacing needs relative to whatever comes next, like a heading that always wants breathing room above it, in a container it doesn’t control. But for laying out a set of siblings, gap is better in every way.

Say this out loud — “what is margin collapsing?”

“In normal flow, vertical margins that touch each other merge into one, and you get the largest of them rather than the sum. It happens between adjacent siblings, and it also happens between a parent and its first or last child, where the child’s margin can escape the parent and push the parent instead. It’s a flow-layout rule inherited from CSS’s document-typesetting roots, so it stops happening as soon as the parent is flex or grid, or has padding, a border, or a non-visible overflow. In practice I mostly sidestep it now by using gap on a flex or grid container instead of margins.”

Why it lands: most candidates know the sibling case only. Mentioning parent/child collapse, naming why the rule exists, and finishing with what you do about it in modern code takes you from “has read the docs” to “has debugged this at 2am.”

“My footer has a huge gap above it that I can’t find in devtools. What’s happening?”

Classic escaped-margin symptom. Some deeply nested last child has a margin-bottom, and because none of its ancestors have padding, a border, or an overflow value, that margin has collapsed all the way up through every ancestor and is now acting on the outermost container. Devtools shows the gap on the outer element, so you look there and find nothing. The fix is to give one of the containers a display: flow-root, or remove the stray margin at the source.

“What’s a block formatting context, in one sentence?”

A self-contained layout region: floats inside it don’t escape it, outside floats don’t intrude, and its margins can’t collapse with anything outside it. You create one with overflow: hidden/auto, display: flow-root, position: absolute, a float, or by being a flex/grid item. display: flow-root is the one to name, because it does only that, with no clipping or scrollbar side effects.

“Do empty elements collapse?”

Yes — and this is the deepest cut. An empty <div> with margin: 20px 0 and no height, no padding, and no border has its own top and bottom margins collapse into each other, producing a single 20px margin. And then that can collapse with its siblings’ margins too. This is called “collapsing through”, and it means an empty spacer div often contributes far less space than you’d expect.

Part 4Flexbox: distributing space along one axis

Everything so far has been about a single box in isolation. Now: how do boxes arrange themselves relative to each other?

By default they use flow layout — block elements stack vertically and fill the width, inline elements sit next to each other and wrap like words in a sentence. That’s fine for an article. It is terrible for a navbar, where you want three things spread across a row with the logo left and the buttons right.

So we switch the container into a different layout algorithm:

One declaration changes everything 
.navbar { display: flex; }

The moment you write that, the browser stops using flow layout for that element’s children and starts using the flexbox algorithm instead. The children become flex items, and a whole new set of properties starts meaning something.

Here’s the one-sentence version of what flexbox is for, and I’d lead with it in an interview: flexbox arranges items along a single axis and distributes the leftover space between them. That’s it. That’s the whole idea. Everything else is a knob on “how should the leftover space be handed out?”

Main axis and cross axis — the thing everyone gets wrong

A flex container has two axes, and their names are relative, not absolute. This is the single biggest source of flexbox confusion, so let’s nail it properly.

The main axis is the direction items flow in. The cross axis is perpendicular to it. Which physical direction each of those points in depends entirely on flex-direction:

flex-directionMain axisCross axis
row (the default)horizontal →vertical ↓
columnvertical ↓horizontal →

And here is the rule that unlocks everything:

  • justify-content always works on the main axis.
  • align-items always works on the cross axis.

So justify-content: center centres horizontally in a row, and vertically in a column. Same property, same value, perpendicular result. If you’ve ever set justify-content: center and watched nothing happen the way you wanted, this was almost certainly why.

Wait, why not just call them horizontal and vertical?

Because flexbox was designed to work in languages that aren’t left-to-right, and in vertical writing modes. flex-start means “where the line begins”, which in an Arabic or Hebrew interface is the right side. The axis-relative naming is what lets a single stylesheet work correctly in both directions with no changes. Slightly more to learn, considerably less to maintain.

Now, justify-content is the “how do we hand out leftover space along the main axis” knob. Here are the values, live, so you can see the difference between space-around and space-evenly — which is nearly impossible to remember from prose:

flex-grow, flex-shrink, flex-basis — and what flex: 1 really is

So far we’ve moved items around within leftover space. The other option is to let the items absorb that space by getting bigger. That’s what the three flex-* properties control, and they are three answers to three separate questions:

  • flex-basis — “before any distribution happens, how big do I want to be?” It’s the starting size along the main axis. Default is auto, meaning “use my width, or if I have none, my content’s natural size.”
  • flex-grow — “if there’s space left over, how greedy am I?” Default 0: don’t grow at all.
  • flex-shrink — “if we don’t all fit, how willing am I to give ground?” Default 1: shrink proportionally with everyone else.

The key insight about flex-grow is that it’s a ratio applied to the leftover space, not a ratio applied to the total width. Say the container is 600px and the items naturally take 300px. There’s 300px left over. If item A has flex-grow: 2 and B and C have 1, the leftover 300 is split 150/75/75 — and each item ends up at its natural size plus its share.

Which brings us to the question you will be asked. What does flex: 1 actually mean? It’s a shorthand, and it expands to:

The expansion that trips people up 
flex: 1;
/* is exactly equivalent to: */
flex-grow: 1;
flex-shrink: 1;
flex-basis: 0%;   /* 👈 NOT auto. This is the surprise. */

That flex-basis: 0 is the whole story. It says “pretend I have zero width to begin with.” So all of the container is leftover space, and it gets divided purely by the grow ratios. Content size becomes irrelevant. That’s why flex: 1 on three items gives three exactly equal columns even when one contains far more text — you saw it in the demo above.

Compare with flex: auto, which is 1 1 auto. Here each item starts at its natural content width, and only the surplus is shared equally. Items with more content stay wider. And flex: none is 0 0 auto — a rigid item that neither grows nor shrinks, which is exactly what you want for an icon or an avatar that must never be squashed.

A common misconception

“flex: 1 means the item takes up 1 fraction of the space, like 1fr in grid.” Close, but the analogy leaks. flex: 1 only behaves like 1fr because its basis is zero. Write flex-grow: 1 on its own — without the shorthand — and the basis stays auto, so you get content width plus an equal share of the surplus, which is a completely different result. This is the single most common flexbox surprise: flex: 1 and flex-grow: 1 are not the same thing.

flex-shrink and the item that refuses to squash

Shrinking is the mirror image. When items don’t fit, the overflow is taken back from them in proportion to flex-shrink (weighted by their basis, but you don’t need that detail in an interview). The useful move is flex-shrink: 0, which means “take it from someone else”:

Under the hood — the min-width: auto trap

Flex items have an implicit min-width: auto, which means a flex item will refuse to shrink below the size of its content. The classic symptom: a flex item containing a long unbreakable string or a table blows out the whole layout, and no amount of width or overflow: hidden on it helps. The fix is min-width: 0 on the flex item (or overflow: hidden, which implies it). This is a genuinely senior-flavoured answer — if you can produce it when someone describes a mysterious overflowing flex layout, it lands very well.

Wrapping, gap, and per-item overrides

By default flexbox will squash everything onto one line forever rather than wrap. flex-wrap: wrap lets items spill onto new lines when they hit their minimum size. Combine it with a flex-basis and you get responsive columns with no media queries at all:

One flexbox trick worth knowing because it looks like magic: margin-left: auto on a flex item pushes it, and everything after it, to the end of the main axis. An auto margin in flexbox absorbs all available free space in that direction. It’s the cleanest way to do “logo on the left, everything else on the right” in a navbar.

Say this out loud — “explain flexbox”

“Flexbox is a one-dimensional layout algorithm: you put items in a line and it distributes the free space along that line. The container has a main axis, set by flex-direction, and a cross axis perpendicular to it — justify-content positions along the main axis and align-items along the cross, which is why they swap physical direction when you switch to column. On the items, flex-grow says how greedily you absorb leftover space, flex-shrink how readily you give it up, and flex-basis your starting size. The shorthand flex: 1 is 1 1 0 — zero basis is what makes items come out equal regardless of content.”

Why it lands: the axis explanation shows you understand why the properties behave differently in a column, and the flex: 1 expansion is a small, specific fact that’s hard to fake. Both signal real usage rather than tutorial memory.

Part 5Grid: structure in two dimensions

Flexbox thinks in terms of a line. Grid thinks in terms of a sheet of graph paper.

That’s the fundamental difference and it’s worth sitting with for a second. With flexbox, you don’t declare a structure — you drop items in a row and let their content and their flex settings decide how wide each one ends up. With grid, you declare the structure first, on the container, independently of what goes in it. You say “there are three columns and the middle one is twice as wide”, and then items fall into those cells.

Think of a printed newspaper. The columns are ruled onto the page before a single word is typeset, and articles then flow into them. Grid is that. Flexbox is more like a shelf where you keep sliding books along until they fit.

The minimum viable grid 
.layout {
  display: grid;
  grid-template-columns: 1fr 1fr 1fr;
  gap: 16px;
}

The fr unit, and why it’s better than percentages

The new thing here is fr — short for fraction. It means “one share of whatever space is left after the fixed stuff and the gaps are accounted for.” That last clause is what makes it so much nicer than percentages.

Three columns at 33.33% plus two 16px gaps overflows, because percentages don’t know about gaps. Three columns at 1fr fit perfectly, because fr is computed from the leftover space after gaps are subtracted. You never do the arithmetic. Similarly, 200px 1fr gives you a fixed sidebar and a main column that takes literally everything else — try expressing that in percentages.

Two helpers make templates readable. repeat() saves you typing: repeat(12, 1fr) is a twelve-column grid. And minmax(min, max) gives a track a floor and a ceiling: minmax(200px, 1fr) means “never narrower than 200px, otherwise take a fair share.”

auto-fit vs auto-fill — the senior follow-up

Put those together with a keyword instead of a number and you get responsive layout with no media queries at all:

✓ A responsive card grid, in one declaration 
.cards {
  display: grid;
  grid-template-columns: repeat(auto-fit, minmax(200px, 1fr));
  gap: 16px;
}

That reads as: “fit as many 200px-minimum columns as you can, and share out any extra.” At 900px wide you get four columns; at 500px you get two; at 300px you get one. No breakpoints.

Now — there are two keywords, auto-fit and auto-fill, and the difference only shows up when you have more room than items. Both create as many tracks as will fit. The difference is what happens to the tracks that ended up empty:

  • auto-fill keeps the empty tracks. They stay in the grid as real, invisible columns, taking up their share of space.
  • auto-fit collapses the empty tracks to zero width. With 1fr as the max, the remaining items then expand to soak up the freed space.

Which do you want? Almost always auto-fit — you want a lone card to fill the row, not huddle in the corner. auto-fill is right when you want a stable grid rhythm regardless of how many items you have, like a calendar or a seat-map where a half-empty row should still line up with the full ones.

Named areas — layout you can read

Here’s grid’s party trick, and my favourite feature in all of CSS. You can name regions and then draw the layout in your stylesheet:

✓ The holy grail layout, drawn out in ASCII 
.page {
  display: grid;
  grid-template-columns: 150px 1fr 130px;
  grid-template-rows: auto 1fr auto;
  grid-template-areas:
    "header header header"
    "nav    main   aside"
    "footer footer footer";
}
.page > header { grid-area: header; }
.page > nav    { grid-area: nav; }
.page > main   { grid-area: main; }

It’s worth pausing on how hard that layout used to be. This is the “holy grail” layout — header, footer, three equal-height columns, fixed side rails, fluid centre, and the source order sensible for screen readers. In the float era this required negative margins, a wrapper per column, and a technique with a name (“faux columns”) for the equal-height problem. It was fragile enough that people wrote blog posts about it. With grid it is nine lines and you can see the shape by squinting at the stylesheet.

Explicit vs implicit grid

The tracks you define in grid-template-columns and grid-template-rows are the explicit grid. But what if you put in more items than you defined cells for? Grid doesn’t overflow or complain — it quietly creates new tracks. Those are the implicit grid.

The practical consequence: grid-template-rows styles the rows you declared, and grid-auto-rows styles the ones that get invented. For a list of unknown length, you usually only declare columns and let rows be implicit. If your grid rows are mysteriously the wrong height, it’s often because you styled the wrong one of those two.

Placing items explicitly

By default items flow into cells in order, one per cell. But any item can claim a specific patch of the grid with grid-column and grid-row. The values are line numbers, not cell numbers — a three-column grid has four vertical lines, numbered 1 to 4. So grid-column: 1 / 3 means “from line 1 to line 3”, spanning two columns. The span keyword saves you counting: grid-column: span 2.

Wait, what about aligning things inside grid cells?

Grid uses the same alignment vocabulary as flexbox, with one extra dimension. justify-* works on the inline (column) axis, align-* on the block (row) axis. justify-items and align-items set the default for every item within its cell; justify-self and align-self override per item. And place-items: center is shorthand for both at once, which is the tidiest centring technique in CSS. Unlike flexbox, grid does have justify-self, because each item owns its own cell.

Say this out loud — “explain grid”

“Grid is two-dimensional: you define the container’s row and column structure up front, and items are placed into that structure — so you control both axes at once, and items can span multiple rows and columns. The fr unit distributes leftover space after fixed tracks and gaps are subtracted, which makes things like 200px 1fr trivial. And repeat(auto-fit, minmax(200px, 1fr)) gives you a fully responsive card grid with no media queries. Tracks you declare are the explicit grid; if you add more items than cells, grid generates implicit tracks sized by grid-auto-rows.”

Why it lands: “structure defined on the container, items placed into it” is the conceptual core, and mentioning the explicit/implicit distinction unprompted marks you as someone who’s built real grids rather than copied a snippet.

Part 6Flex or grid? The decision rule

“Would you use flexbox or grid for this?” is a near-guaranteed question, and the trap is answering with a preference. Interviewers aren’t checking which one you like; they’re checking whether you have a rule. Here it is:

The rule, in one line

If the content should decide the sizes, and you only care about one direction — flexbox. If you want to impose a structure, and you care about both directions — grid.

Or, more memorably: flexbox is content-out, grid is layout-in.

Let’s make that concrete, because “one-dimensional vs two-dimensional” is a slogan people repeat without being able to apply it.

A navbar: logo, links, a buttonflexOne row. Sizes come from the content. You just need to distribute leftover space.
The whole page: header, sidebar, main, footergridYou have a shape in mind, in two dimensions, and it shouldn’t change based on how much text is in the sidebar.
A row of tags of varying length that wrapsflexEach tag is as wide as its word. Grid would force them into columns of equal width.
A photo gallery of uniform cardsgridYou want tidy columns and aligned rows. auto-fit + minmax and you’re done.
An icon next to a label, vertically centredflexTwo items, one axis, sizes from content. Grid is overkill.
A form where all labels line up in a columngridAlignment across rows is a two-dimensional requirement. Flex rows can’t see each other.
A dashboard where one widget is double-widthgridSpanning cells. Flexbox has no way to express it.

That form row is worth dwelling on, because it’s the crispest demonstration of the difference. If you build a form as a stack of flex rows, each row is an independent flex container — row two has no idea how wide row one’s label was, so the inputs won’t line up. In a grid, every row shares the same column tracks, so the label column is one width for the whole form, automatically. Flex lines can’t see each other; grid tracks are shared. That’s the real meaning of “two-dimensional.”

And they compose

Critically, this isn’t a choice you make once. Real applications use both, at different scales: grid for the page skeleton, flex inside each component. A card grid where each card is a flex column with the button pushed to the bottom by margin-top: auto. A grid-based page whose header is a flex row. A grid item is itself a perfectly ordinary box, so it can be display: flex for its own children.

If you say “grid for the macro layout, flex within components, and they nest happily”, you have answered the question better than the person asking probably expected.

A common misconception

“Grid replaced flexbox — it’s newer, so it’s better.” They solve different problems and neither is a superset. Grid genuinely cannot do what flexbox does with content-sized items on a wrapping line: a tag list in grid gives you rigid equal columns, and every tag looks wrong. Flexbox genuinely cannot align across lines. Saying “I just use grid for everything now” reads as inexperience, not modernity.

“Can you centre something with grid more easily than flex?”

Yes, marginally: display: grid; place-items: center is two declarations, versus flexbox’s display: flex; align-items: center; justify-content: center. There’s a place-content in flexbox too but it doesn’t cover align-items, so grid genuinely wins on brevity here. It’s the single case where “use grid, it’s shorter” is a legitimate answer.

“Is there a performance difference?”

Not meaningfully, and reaching for performance as the reason to pick one is a small red flag. Both are highly optimised native layout algorithms. Grid does slightly more work because it has to resolve two axes and can require multiple passes for auto and content-based tracks, and deeply nested flex containers can be expensive because sizing an item may depend on its children which depend on the container. But the number of DOM nodes and how often you trigger layout dwarf the choice of algorithm. Pick based on what you’re expressing, not on speed.

Part 7Positioning: static, relative, absolute, fixed, sticky

Everything up to now has been about elements living in flow — taking up space, pushing their neighbours around, being arranged by flex or grid. Positioning is the set of tools for taking an element and moving it somewhere else, sometimes without disturbing anything around it.

There are five values and it’s worth understanding them as a progression from “fully in flow” to “fully out of it.”

static — the default

Every element starts as position: static. It sits where flow, flex, or grid puts it. Crucially, top, right, bottom, left, and z-index do nothing at all on a static element. If you’ve ever set top: 20px and had absolutely nothing happen, this is why — you forgot to set a position first. It’s the most common CSS false start there is.

relative — nudged, but still occupying its space

position: relative does two things, and one of them is much more important than the other.

The obvious thing: top/left/etc. now work, and shift the element relative to where it would otherwise have been. But here’s the part that matters — the space it originally occupied is still reserved. Nothing reflows. The element is visually moved but the layout still believes it’s in the old place.

The other thing relative does — and honestly this is what it’s used for 90% of the time, usually with no offsets at all — is establish a containing block for absolutely positioned descendants. Which we need to define properly, right now, because it’s the concept the next three sections all depend on.

What is a containing block?

When you set position: absolute and then say top: 0; left: 0, the obvious question is: zero from what? The top-left of the page? Of the parent? Of the screen?

The answer is: from the element’s containing block. That’s the rectangle that all its percentage sizes and offsets are measured against. Every positioned element has exactly one, and finding it is a simple search.

For an element with position: absolute, the browser walks up the ancestor chain and picks the first ancestor that is itself “positioned” — meaning it has a position value other than static. If it walks all the way to the top without finding one, it uses the initial containing block, which is essentially the page.

The analogy I like: an absolutely positioned element is a note stuck to a noticeboard, and it’s looking for the nearest noticeboard above it. Ordinary static elements are just wall — you can’t pin to them. Setting position: relative on an ancestor is the act of hanging a noticeboard there. The note pins itself to the closest one it can find, and if there are none in the whole building, it pins to the outside wall of the building itself.

This is why position: relative with no offsets is one of the most-written declarations in CSS. You’re not moving anything; you’re saying “absolute children, measure yourselves against me.”

Under the hood — position isn’t the only thing that creates a containing block

This is the follow-up that separates the confident answers from the memorised ones. A non-static position is the usual way, but several other properties also make an element into a containing block for absolute and fixed descendants:

  • transform with any value other than none — including translateZ(0) or scale(1)
  • filter, backdrop-filter
  • will-change naming any of the above
  • perspective
  • contain: paint / contain: layout, and content-visibility

The reason is coherent: all of these change the coordinate system or the paint boundary of the subtree. If an element is rendered scaled or blurred, its descendants have to be positioned inside that transformed space, or they’d visually detach from it.

absolute — out of flow entirely

Where relative keeps its seat, absolute gets up and leaves. The element is removed from normal flow: it no longer takes up space, siblings close up as though it were deleted, and it positions itself against its containing block.

Two consequences worth knowing. First, an absolutely positioned block element shrinks to fit its content instead of filling its parent — it’s no longer in flow, so “fill the width” doesn’t apply. Second, if you set no offsets at all, it stays exactly where it would have been in flow (its “static position”) but stops taking up space. That’s occasionally useful and frequently the cause of a mysterious overlap.

Absolute positioning is for things that genuinely sit on a layer above the layout: a badge on an avatar, a close button in a modal corner, a dropdown panel under a menu button, a custom checkbox graphic over a hidden input. If you find yourself absolutely positioning things to build a page layout, stop — that’s what grid is for, and absolute layouts can’t respond to content size.

fixed — pinned to the viewport

position: fixed is like absolute in that it’s out of flow, but its containing block is normally the viewport — the visible window. So it doesn’t move when you scroll. Sticky headers, cookie banners, chat bubbles in the corner, modal backdrops.

This is one of the great CSS mysteries when you hit it in the wild, because the broken element’s CSS is perfect. The culprit is always an ancestor, often several levels up, and often something you didn’t write — an animation library adding will-change: transform, a filter: blur() on a backdrop, a translateZ(0) someone added years ago to “force GPU acceleration.”

In an interview

“Why did my position: fixed element stop being fixed?” is a debugging question, and they want to see your process, not just the fact. The answer to give: “Something in the ancestor chain created a containing block — almost always a transform, filter, or will-change. I’d walk up the tree in devtools looking for one, and fix it either by moving the fixed element out of that subtree entirely, usually to a portal at the body level, or by removing the property if it isn’t needed.” Naming the portal fix is a nice touch if the codebase is React — it’s exactly why modals are usually portalled.

sticky — the hybrid

position: sticky is the newest and the strangest. It behaves like relative — in flow, taking up its space — until the user scrolls it to a threshold you define, at which point it behaves like fixed, but only within its parent. When the parent scrolls out of view, the sticky element goes with it.

The analogy: a sticky element is a passenger on a train with an assigned seat. It sits in its seat normally. When the train reaches a certain point, it gets up and stands by the door — but it can never leave the carriage. When the carriage leaves the station, so does it.

A sticky section header 
.section-header {
  position: sticky;
  top: 0;   /* 👈 the threshold. Without this, nothing sticks. */
}

Sticky fails silently — no error, no warning, it simply doesn’t stick — so knowing the three causes by heart is genuinely useful:

  1. No threshold. You must set at least one of top, right, bottom, or left. Unlike absolute, sticky with no offsets does nothing at all. This is the most common cause by a mile.
  2. An ancestor with overflow set to hidden, auto, or scroll. Sticky positions itself against the nearest scrolling ancestor. If some wrapper has overflow: hidden, that becomes the scroll container — and it doesn’t scroll, so nothing ever sticks. This one is brutal because overflow: hidden is often added far away for an unrelated reason, like clipping a rounded corner.
  3. The parent is too short. Sticky can only travel within its parent’s box. If the parent is exactly as tall as the sticky element — which is what happens when you make a sticky sidebar the direct child of a flex or grid container that stretches it to full height — there is no room to move, so it never appears to stick. The fix is usually align-self: start on the sticky item so it doesn’t get stretched.
Wait, what about height: 100% on a parent?

Same family of problem. A common one: html, body { height: 100% } combined with overflow: auto somewhere makes the scroll container something other than the document, and every sticky thing on the page breaks at once. If nothing sticky works anywhere, look at your root element styles before you look at the component.

Say this out loud — “what’s a containing block?”

“It’s the rectangle an element’s percentages and offsets are resolved against. For an absolutely positioned element it’s the padding box of the nearest ancestor that’s positioned — anything other than position: static — and if there isn’t one it falls back to the initial containing block, effectively the viewport. That’s why you so often see position: relative with no offsets: it’s just there to become the containing block for a child. And it’s not only position — transform, filter, and will-change also create a containing block, which is the usual reason a position: fixed element mysteriously stops being fixed.”

Why it lands: you connected a definition to two things the interviewer cares about — the position: relative idiom they see in every codebase, and a real debugging scenario. That’s the difference between recall and understanding, and it’s usually the thing they’re grading.

Follow-ups on positioning

“What’s the difference between top: 0 on relative and on absolute?”

On relative, offsets are measured from the element’s own normal position, so top: 0 is a no-op and top: 20px means “20px lower than you would have been.” On absolute, they’re measured from the edges of the containing block, so top: 0 means “flush with the top of my containing block.” Same property, two different reference frames.

“If I set both top: 0 and bottom: 0 on an absolute element, what happens?”

It stretches to fill that whole dimension, as long as height is auto. Setting all four of top/right/bottom/left to 0 (or the shorthand inset: 0) makes an element exactly cover its containing block — the standard way to build a modal backdrop or an overlay on an image. If you also set an explicit height, the conflict is resolved by ignoring bottom.

“Does position: absolute take an element out of the accessibility tree or the tab order?”

No — and this catches people out. It only removes the element from layout flow. It’s still in the DOM, still focusable, still read by screen readers, still tabbable, in source order, not visual order. That’s a real accessibility hazard: if you visually reorder things with positioning (or with flexbox’s order, or grid placement), keyboard users will tab through them in an order that doesn’t match what they see. The rule is to keep DOM order matching the meaningful reading order, and only use layout to make small visual adjustments.

“Why is my sticky header jumping or flickering?”

Usually one of two things. Either the sticky element has a margin that collapses differently once it sticks, or you have two sticky elements at the same top value overlapping each other. Also check that you haven’t got a transform on the sticky element itself — sticky and transforms interact badly, since sticky is repositioning the same box the transform is offsetting.

Part 8Centering a div, properly

“How do you centre a div?” is a joke question now, which is exactly why it still gets asked — it’s a fast way to find out whether someone reasons about layout or reaches for a memorised snippet. The good answer is never a single technique. It’s “it depends, and here’s what it depends on.”

First, a bit of history, because it explains why this was ever hard. Before flexbox, CSS had no concept of “distribute this space around my child.” Horizontal centring worked, sort of — margin: 0 auto on an element with a declared width does exactly that, because auto horizontal margins split the leftover space evenly. But there was no vertical equivalent, because in flow layout a block element’s height comes from its content, so there is no “leftover” vertical space to split. margin: auto 0 computes to zero. Vertical centring therefore needed hacks: table cells with vertical-align: middle, an invisible full-height pseudo-element with display: inline-block, or absolute positioning plus a negative margin equal to half the element’s height — which required you to know the height in advance.

Flexbox and grid fixed this by introducing algorithms that do have a notion of free space on both axes. Here are the modern options, live:

TechniqueUse it whenWatch out for
display: grid; place-items: center The default answer. Two declarations, both axes, works on any content size. Makes the parent a grid, which affects all its children. Fine when it has one child.
display: flex; align-items: center; justify-content: center When the parent is already flex, or you have several children to lay out as well as centre. Three declarations. Remember the axes swap in column.
position: absolute; top: 50%; left: 50%; transform: translate(-50%, -50%) When the element must sit on top of other content without affecting layout — a modal, a loading spinner over a panel. Needs a positioned ancestor. The -50% translate is relative to the element’s own size, which is what makes it work without knowing the height.
margin-inline: auto (or margin: 0 auto) Horizontal only: centring a fixed-width content column on a page. Still the right tool for this. Requires a constrained width — a full-width block has no leftover space to split. Does nothing vertically in flow layout.
margin: auto on a flex item Genuinely centres on both axes, because in flexbox auto margins absorb free space in both directions. Only works inside a flex or grid container. Surprising but very elegant.
text-align: center Centring inline content — text, inline images, inline-block buttons — inside a block. It centres the element’s inline children, not the element itself. It also inherits, which surprises people three components down.
Say this out loud — “how many ways can you centre a div?”

“My default is display: grid; place-items: center on the parent — two declarations, both axes, works regardless of the child’s size. If the parent’s already a flex container I’ll use align-items and justify-content instead. If the thing needs to sit on top of other content without affecting layout, like a modal, that’s position: absolute; top: 50%; left: 50%; transform: translate(-50%, -50%) — the translate is a percentage of the element itself, so it works without knowing its height. And for the plain case of centring a fixed-width content column on a page, margin-inline: auto is still the right tool. The reason there are so many options is that before flexbox there was no way to talk about free space on the vertical axis at all.”

Why it lands: you gave a default plus the conditions under which you’d deviate, and the closing sentence shows you know why the question is a meme. That reads as someone who’s made a lot of layout decisions, not someone reciting a listicle.

A common misconception

“margin: auto doesn’t work vertically.” Not quite — it doesn’t work vertically in flow layout, because there's no free vertical space to distribute. Inside a flex or grid container there is, and margin: auto on a flex item centres it on both axes perfectly. Being precise about “in flow layout” is exactly the kind of qualification that makes an answer sound senior, and it sets up the last section of this guide nicely.

Part 9CSS has several layout algorithms

Let me finish with the idea that ties everything together, because once you see it, a lot of previously random-feeling CSS behaviour snaps into place.

Here’s the framing. CSS is not one layout system with a big pile of properties. It’s several distinct layout algorithms, and at any given moment, one of them is responsible for arranging a particular set of boxes. The main ones:

AlgorithmTurned on byIts job
Flow (block & inline)The defaultStack blocks vertically, flow inline content like words in a sentence. Built for documents.
Flexboxdisplay: flexDistribute space along one axis.
Griddisplay: gridPlace items into a two-dimensional structure.
Table<table> or display: tableSize columns so every row agrees. Older, but genuinely good at that one thing.
Positionedabsolute / fixedTake an element out of flow and place it against a containing block.

And the crucial consequence: a property’s meaning depends on which algorithm is running. Not whether it works — what it means. We’ve already seen this several times without naming it:

  • margin: auto centres horizontally in flow, and on both axes in flexbox.
  • Vertical margins collapse in flow, and never in flex or grid.
  • width: 100% fills the parent in flow; on a flex item, flex-basis takes precedence over it.
  • z-index does nothing on a static element in flow, but works on flex and grid items even when they’re static.
  • A block element fills its parent’s width in flow, but shrinks to fit its content the instant it becomes absolutely positioned.

This is why the honest answer to “why isn’t this CSS doing anything?” is so often “because you’re in the wrong layout mode.” vertical-align does nothing on a flex item. float does nothing on a grid item. gap does nothing in flow layout. None of these are bugs — the properties simply aren’t part of the algorithm that’s running.

Under the hood — why the holy grail was so hard before grid

Flow layout has no concept of “these three boxes are peers in a row that should be the same height.” Blocks stack; that’s the whole algorithm. So to get columns, we co-opted float, which was designed for wrapping text around an image, and made it do something it was never meant to do. Floats are removed from flow for sizing purposes, so parents collapsed to zero height and we invented clearfix. Floated columns don’t know about each other’s heights, so backgrounds didn’t reach the bottom and we invented faux columns. Source order was tied to visual order, so the main content had to come after the sidebar in the HTML, which was bad for accessibility, so we invented negative-margin reordering tricks.

Every one of those hacks exists because we were using an algorithm designed for magazine text-wrap to build a page skeleton. Grid is an algorithm that was actually designed for page skeletons — equal-height tracks, source order independent of visual placement, and space distribution on both axes are all built into the model rather than emergent from a hack. That’s why the answer collapses from forty lines of fragile CSS to nine.

“Should you ever use tables for layout?”

For page layout, no — it’s semantically wrong, it’s bad for screen readers, and grid does the job better. But two nuances make this a better answer than a flat no. First, <table> is absolutely correct for actual tabular data, and reaching for divs and grid there is the real mistake. Second, HTML email is still a genuine exception — many email clients strip modern CSS, so table-based layout remains standard practice there. Knowing that boundary is worth more than the reflexive “tables are bad.”

“What does display: flex actually change — the element, or its children?”

Both, and the distinction matters. display is really two values: an outer display type, which controls how the element behaves in its parent’s layout, and an inner one, which controls how it lays out its children. display: flex means “outer: block, inner: flex” — the element itself is still a block in its parent’s flow, but its children are laid out by the flex algorithm. The modern two-value syntax spells this out: display: block flex. It also explains inline-flex: outer inline, inner flex. Bringing this up is a strong signal that you understand the layout-algorithm model rather than just the property names.

Part 10Interview cheat sheet

The morning-of version. If you can say each of these in your own words, you’re in good shape.

QuestionThe crisp answer
Why does width: 100% plus padding overflow? Because by default width sets only the content box; padding and border are added outside it. So you get 100% of the parent, plus the padding, which is more than 100%.
What is border-box and why does everyone set it? width now means the whole visible box out to the border; padding and border eat inwards. The number you type is the number on screen. Reset it on *, *::before, *::after.
What is margin collapsing? Touching vertical margins in flow layout merge into one, and you get the larger, not the sum. Happens between siblings and between parent and first/last child. Stopped by padding, border, non-visible overflow, flow-root, or a flex/grid parent. Horizontal margins never collapse.
Flexbox in one sentence? One-dimensional: distribute free space along a single axis. justify-content = main axis, align-items = cross axis, and flex-direction decides which is which.
What does flex: 1 mean exactly? flex-grow: 1; flex-shrink: 1; flex-basis: 0. The zero basis is why items come out equal-width regardless of content — unlike bare flex-grow: 1, which keeps basis: auto.
Grid in one sentence? Two-dimensional: define row and column structure on the container, then place items into it. Tracks are shared across rows, so things line up across the whole grid.
auto-fit vs auto-fill? Both create as many tracks as fit. auto-fill keeps empty tracks (items stay small); auto-fit collapses them (items stretch to fill). You usually want auto-fit.
Flexbox or grid for X? Content-driven distribution along one axis → flex. Layout-driven structure in two axes → grid. They compose: grid for the page, flex inside components.
What is a containing block? The rectangle an element’s offsets and percentages resolve against. For absolute: the nearest non-static ancestor, else the viewport. Also created by transform, filter, will-change, contain.
relative vs absolute? relative nudges from its own position and keeps its space. absolute leaves flow entirely, takes no space, shrinks to fit, and positions against its containing block.
Why did my fixed element stop being fixed? An ancestor has transform, filter, or will-change, which creates a containing block — so it’s now fixed to that ancestor and scrolls with it. Fix: portal it out, or remove the property.
Why isn’t my sticky working? Three causes: no threshold (top/bottom/etc. not set), an ancestor with overflow: hidden/auto/scroll, or a parent no taller than the element so there’s nowhere to travel.
How do you centre a div? display: grid; place-items: center by default. Flex if the parent is already flex. absolute + translate(-50%, -50%) if it must float above the layout. margin-inline: auto for a fixed-width column.
Why does the same property behave differently in different places? CSS has multiple layout algorithms — flow, flex, grid, table, positioned — and a property’s meaning depends on which one is laying out that box.
