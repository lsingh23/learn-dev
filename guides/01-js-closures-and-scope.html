Closures, Scope & Hoisting

The three things that show up in nearly every frontend interview — and the mental model that makes all three of them obvious at the same time.

Let me start with a piece of code that has ruined a lot of interviews.

What does this log? 
for (var i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 100);
}

Take a guess before you scroll. Genuinely — commit to an answer in your head. Most people say 0 1 2, because that's obviously what the loop is doing.

Show me the actual output 
3
3
3

Three threes. Not 0 1 2. And if you change exactly one word — var to let — you get 0 1 2 again.

That single word changing the output is deeply weird if you think of var and let as "the same thing, but one's newer." They're not. And the reason they're not is the same reason closures work, which is the same reason hoisting works, which is the same reason the Temporal Dead Zone exists.

All of it is one idea wearing four different hats. We're going to build that idea from the ground up, and by the end that loop won't just make sense — you'll be able to explain it out loud to a stranger in an interview room without hedging.

I'm not going to assume you know what "scope" means. We start there.

Part 1Where do variables actually live?

Here's a question that sounds too simple to be worth asking: when you write const cartTotal = 40, where does that value go?

"In memory" is true but useless. The useful answer is: JavaScript keeps a lookup table for every region of your code. Name on the left, value on the right. When the engine needs to know what cartTotal is, it looks in the table.

The spec calls this table an Environment Record. Everybody else calls it a scope. They're the same thing, and I'll use "scope" because that's the word the interviewer will use.

Every time the engine enters a new region of code, it makes a fresh table:

const currency = "CAD";          // goes in the GLOBAL table

function checkout(items) {
  const cartTotal = 40;         // goes in checkout's OWN table
  return `${cartTotal} ${currency}`;
}

Two tables. The global one holds currency and checkout. The one created when checkout runs holds items and cartTotal.

But hm — checkout uses currency, and currency isn't in checkout's table. How does that work?

Tables have a parent

Each table carries a pointer to the table it was born inside. When the engine looks up a name and doesn't find it, it doesn't give up — it follows that pointer up to the parent table and looks again. Then that table's parent. And so on, until it either finds the name or runs out of tables and throws ReferenceError.

That chain of tables is the scope chain. Here's what it looks like for the code above:

That last sentence matters more than it looks. The chain only goes up. Global code can't see inside checkout, because checkout's table isn't on global's chain. That's why the inside of a function is private by default — and that privacy is the seed of everything we'll build later.

Under the hood

The tables I've been drawing are really Lexical Environments, each containing an Environment Record plus an [[OuterEnv]] reference. The engine also doesn't literally re-walk a linked list at runtime in optimized code — modern engines resolve most lookups to a fixed slot index ahead of time. But the linked-list model predicts the observable behaviour perfectly, and it's the model interviewers expect you to describe.

Part 2Lexical scope: written, not called

So each table has a parent. Which raises the obvious next question: who decides which table is the parent?

There are two plausible answers, and one of them is wrong in a way that's worth feeling.

Plausible answer A: the parent is whoever called the function. Plausible answer B: the parent is whatever scope the function was physically written inside.

Let's test it:

const greeting = "hello from module scope";

function speak() {
  console.log(greeting);   // 👈 which greeting?
}

function runIt() {
  const greeting = "hello from runIt";
  speak();
}

runIt();
What gets logged? 
"hello from module scope"

Answer B wins. speak was written next to the outer greeting, so that's its parent scope — forever, no matter who calls it or from where.

This is lexical scope. "Lexical" comes from lexis, meaning word or text — it's scope determined by the text of your program. Where the curly braces sit on the page. You could work out the entire scope chain of a program with a printout and a highlighter, without ever running it.

The analogy

A function is like a person who grew up in a particular house. Wherever they move later in life, when you ask them "what's home?", they mean the house they grew up in. Calling a function is sending that person somewhere new to do a job; it doesn't change where they grew up.

Where this breaks down: a person can eventually change what they call home. A function can't. Its parent scope is locked in at creation and can never be reassigned. Also — and this is the classic gotcha — this does not work this way in regular functions; this is decided by the caller. Scope is lexical; this (in non-arrow functions) is dynamic. Interviewers love that distinction.

Block scope vs function scope

So far I've been drawing a new table per function. But blocks make tables too — sometimes.

A "block" is just a pair of curly braces that isn't a function body: the inside of an if, a for, a while, or a bare { } floating on its own.

Blocks make tables — for let and const 
if (user.isAdmin) {
  let auditNote = "admin action";
  var legacyFlag = true;
}

console.log(legacyFlag);   // → true
console.log(auditNote);    // → ReferenceError

Same block, same braces, two completely different outcomes. let respected the braces. var walked straight through them like they weren't there.

That's the actual, load-bearing difference between them, and it's what Part 3 is about.

Part 3var vs let vs const

var is function-scoped. Its table is the nearest enclosing function — full stop. If there's no enclosing function, it lands in global scope. Blocks are invisible to it.

let and const are block-scoped. Their table is the nearest enclosing pair of braces, whatever kind those braces are.

The other two differences

Scoping is the big one, but there are two more the interviewer will probe.

Redeclaration. var lets you declare the same name twice in the same scope and just... shrugs. let and const throw a SyntaxError.

var total = 10;
var total = 99;      // fine. no warning. good luck finding this bug.

let count = 10;
let count = 99;      // → SyntaxError: Identifier 'count' has already been declared

That SyntaxError is thrown before a single line of your program runs, because it's caught while parsing. Which is a nice preview of hoisting: the engine clearly knows about your declarations before it executes anything.

Reassignment. var and let can be reassigned. const cannot.

let attempts = 0;
attempts = 1;              // fine

const maxAttempts = 3;
maxAttempts = 4;           // → TypeError: Assignment to constant variable.

Note the different error types — SyntaxError for redeclaring, TypeError for reassigning a const. Small detail, but naming it correctly in an interview reads as "this person has actually hit this."

Part 4Is const immutable? No.

This one has its own section because it's asked constantly, and because the wrong answer is so intuitive.

const user = { name: "Ada" };
user.name = "Grace";

console.log(user.name);   // → "Grace"  😬

If const means constant, how did that change?

Because const makes a promise about the binding, not the value. Let me define binding, because it's the word that makes this click and most explanations skip it.

A binding is the row in the lookup table — the arrow between the name and the value. const freezes the arrow. It says: this name will point at this exact value for its whole life. It says nothing at all about whether that value is itself allowed to change internally.

The analogy

const is a house number painted on a mailbox. const home = 42 means: this mailbox is nailed to house number 42 and can never be moved to number 43. It does not mean nobody can rearrange the furniture inside house 42, or paint the walls, or knock down a wall.

Where it breaks down: primitives (numbers, strings, booleans) have no "inside" to rearrange, so for those, const genuinely does look like immutability. That coincidence is exactly why the misconception spreads.

So the rule is mechanical: the left-hand side of the = can never change; anything to the right of a dot can.

const cart = [];

cart.push("laptop");     // ✅ mutating what cart points at
cart.length = 0;         // ✅ still mutating
cart = [];               // → TypeError: Assignment to constant variable.

If you actually want the value frozen too, that's a separate tool:

const config = Object.freeze({ retries: 3, nested: { deep: 1 } });

config.retries = 99;
console.log(config.retries);      // → 3   (silently ignored, or throws in strict mode)

config.nested.deep = 99;
console.log(config.nested.deep);  // → 99  👈 freeze is shallow!
In an interview

"Is const immutable?" is a recall question with a depth trapdoor. Saying "no, it's the binding not the value" gets you the point. Adding "and Object.freeze is only shallow, so for real deep immutability you'd need a recursive freeze or a library like Immer" is what separates you from the other four candidates who also said "it's the binding."

Part 5Hoisting: what actually happens

Time for another guess-the-output. Two snippets, one word different.

Snippet A 
console.log(shippingFee);
var shippingFee = 5;
Snippet B 
console.log(shippingFee);
let shippingFee = 5;
Both outputs

A logs undefined. B throws ReferenceError: Cannot access 'shippingFee' before initialization.

Neither of them throws ReferenceError: shippingFee is not defined — which is what you'd get if you referenced a name that genuinely didn't exist anywhere. Read those two error messages again; the difference between them is the whole story.

You'll often hear hoisting explained as "declarations get moved to the top of the file." I want you to drop that phrasing, because it's a lie that will cost you on the follow-up. Nothing moves. Your source code is not rewritten.

The real mechanism: two passes

Before JavaScript executes a single line of a scope, it does a quick setup pass over that scope. Two phases, in order:

In the creation phase, the engine walks the scope and registers every declared name in the table. Crucially, it registers them differently depending on how they were declared:

  • Function declarations get registered with the entire function ready to go. That's why you can call a function above where you wrote it.
  • var gets registered and immediately initialized to undefined.
  • let and const get registered but left uninitialized — a special marker meaning "this name is claimed, but there's nothing here yet."

Then the execution phase runs your code line by line, filling in the real values as it reaches each assignment.

Now go back to the two snippets. In A, the creation phase already put undefined in the box, so reading it early gives you undefined — no error, just a meaningless value. In B, the box exists but is marked uninitialized, and reading an uninitialized box is an error by design.

A common misconception

"let and const aren't hoisted."

They absolutely are. If they weren't hoisted, this would log the outer value instead of throwing:

const theme = "dark";
{
  console.log(theme);      // → ReferenceError, not "dark"
  const theme = "light";
}

The only way the engine can throw there is if it already knows the block has its own theme. That knowledge is the hoisting. What let/const lack isn't hoisting — it's initialization during the creation phase.

Function declarations vs function expressions vs arrows

This is where hoisting bites people in real code.

✅ Works — function declaration 
formatPrice(9.99);       // → "$9.99"

function formatPrice(n) {
  return `$${n.toFixed(2)}`;
}
❌ Breaks — function expression 
formatPrice(9.99);       // → TypeError: formatPrice is not a function

var formatPrice = function(n) {
  return `$${n.toFixed(2)}`;
};
❌ Breaks differently — arrow function 
formatPrice(9.99);       // → ReferenceError: Cannot access 'formatPrice' before initialization

const formatPrice = (n) => `$${n.toFixed(2)}`;

Here's the thing to internalise: arrow functions and function expressions aren't "less hoisted." Only the declaration hoists, and in those two cases the declaration is a var or a const — a plain variable that happens to be assigned a function later. The function itself is created during the execution phase, when that line runs.

Which is why the three errors differ so precisely:

  • Declaration → the function is fully ready in the creation phase. Works.
  • var + function expression → the name holds undefined. You're calling undefined(), so: TypeError.
  • const + arrow → the name is uninitialized. You can't even read it, so: ReferenceError.

Being able to explain why the error type differs is a genuinely strong signal. It shows you're reasoning from a model, not memorizing outcomes.

In an interview

The trap: saying "hoisting moves declarations to the top of the file." The follow-up that kills you is "okay, so if declarations move to the top, why does let throw?" If things literally moved, let x = 5 at the top would just work. Lead with two phases instead and the follow-up answers itself.

Part 6The Temporal Dead Zone

We've already met it — we just haven't named it.

The Temporal Dead Zone is the stretch of time between a let/const name being registered (start of the scope) and the line that initializes it actually running. Touch the variable during that window and you get a ReferenceError.

{
  // ── TDZ for `apiKey` starts here ──────────
  console.log(apiKey);            // → ReferenceError
  typeof apiKey;                  // → ReferenceError (!)  even typeof throws
  // ── TDZ ends on the next line ─────────────
  const apiKey = "sk_live_…";
  console.log(apiKey);            // → "sk_live_…"
}

Note the word temporal — it's about time, not lines. Which sounds pedantic until you see this:

function getTotal() {
  return subtotal * 1.13;    // written ABOVE the declaration…
}

const subtotal = 100;
console.log(getTotal());       // → 113   …but works fine 👍

The reference to subtotal sits physically above its declaration, and it's completely fine — because by the time getTotal() is actually called, the declaration has run. The TDZ closed. Position on the page never mattered; only the clock did.

Why the TDZ is a feature, not an annoyance

The obvious question: why not just let let be undefined too, like var? Wouldn't that be less annoying?

It would be less annoying and much worse. Three reasons:

1. undefined is a legitimate value. If early access silently gave you undefined, you could never distinguish "I read this too early — a real bug" from "this genuinely holds undefined." The TDZ turns a silent wrong value into a loud, precisely-located error. That's the trade every good language design makes: fail fast, fail near the cause.

2. const would be incoherent without it. A const is supposed to be assigned exactly once. If it were auto-initialized to undefined at creation, then your const rate = 0.13 would be its second assignment — which is precisely what const forbids. The TDZ is what lets const keep its promise.

3. It catches a whole class of ordering bugs at the moment they happen rather than three functions downstream where undefined finally causes a crash.

Wait — is a TDZ error the same as "not defined"?

No, and interviewers do check this. Compare:

typeof neverDeclared;   // → "undefined"  (no error!)
typeof inTdz;          // → ReferenceError
let inTdz = 1;

typeof on a name that doesn't exist anywhere is famously safe — it returns the string "undefined". But typeof on a TDZ variable throws. So the TDZ made typeof unsafe for the first time in JS history. That's a deliberate trade: the committee decided catching real bugs beat preserving the typeof guard trick.

Part 7Closures

Everything so far has been foundation. Here's the payoff.

We established in Part 1 that a function's scope table is created when the function runs, and that lookups walk up the chain to the parent table. Fine. But that raises a question I skipped: what happens to a scope table when its function finishes?

The reasonable guess is: it's garbage. The function returned, its local variables are done, clean it up. And usually, that's exactly right.

Except:

function createGreeter(name) {
  const greeting = `Hey ${name}!`;

  return function sayHi() {
    console.log(greeting);        // 👈 reaches into a scope that's "over"
  };
}

const greetAda = createGreeter("Ada");
greetAda();      // → "Hey Ada!"

createGreeter finished. It returned. Its table should be gone. And yet greeting is still there, alive, years of CPU cycles later.

That's a closure.

The definition, now that it can't mislead you

A closure is a function bundled together with the scope it was created in. Because scope is lexical (Part 2), the inner function's parent table was decided when it was written — and the function holds a live reference to that table. As long as the function is alive, the table it points to can't be garbage collected.

So the accurate phrasing isn't "the function remembers its variables." It's: the function keeps its parent scope alive.

The analogy

Think of a function as a person leaving an office job. On the way out they take a backpack containing exactly the desk drawers they were still using. The office (the call) closes, the lights go off — but they're walking around with those drawers, and they can open them any time.

Where it breaks down (and this part matters): a backpack implies they took a copy. They didn't. It's more like they kept a key to a storage locker. If two people leaving the same office kept keys to the same locker, and one of them changes what's inside, the other sees the change. Closures share the live scope, they don't snapshot it. That single fact explains the loop puzzle, so hold onto it.

Proving it's shared, not copied

function makeAccount() {
  let balance = 0;
  return {
    deposit: (n) => { balance += n; },
    getBalance: () => balance,
  };
}

const account = makeAccount();
account.deposit(50);
account.deposit(25);
account.getBalance();     // → 75

Two different functions, one shared balance. If each had grabbed a copy, getBalance would still say 0. It says 75, so they're both looking at the same live table.

And notice something else: there is no way to reach balance from outside. Not account.balance, not anything. The scope chain only goes up, remember — outside code has no path in. That's genuine privacy, built out of nothing but a function boundary.

Under the hood

In V8, a closed-over variable is moved into a heap-allocated context object instead of living on the stack. V8 also only captures the variables the inner function actually references — so a closure over one variable from a scope containing a hundred usually keeps just the one. Usually. Debug builds and eval defeat this optimization, and some engines have historically over-captured. Don't design around it.

Part 8The loop puzzle, finally

Back to where we started:

❌ Logs 3, 3, 3 
for (var i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 100);
}

You now have every piece you need. Let's assemble them.

Piece one: var is function-scoped, so i is not inside the loop body's block. There is exactly one i, sitting in the enclosing function (or global) scope. The loop doesn't create three variables. It creates one and changes it three times.

Piece two: closures share the live scope, they don't snapshot it. All three arrow functions were written in the same place, so all three have the same parent table — the one containing that single i.

Piece three: setTimeout doesn't run its callback now. It schedules it. The loop finishes completely — running i++ a final time to 3, which is what makes i < 3 false and ends the loop — and only then do the callbacks fire.

So by the time the first callback runs and looks up i, it walks up to the one shared table and finds... 3. Same for the second. Same for the third.

The callbacks were never "wrong." They read i correctly. It's just that i had moved on without them.

What let does differently

✅ Logs 0, 1, 2 
for (let i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 100);
}

let in a for header gets special treatment in the spec: the engine creates a fresh binding for every iteration, copying the value forward before running the update expression. Three iterations, three separate i variables, three separate tables.

A common misconception

"Use an arrow function and it'll capture the right value."

Nope. Look at the broken snippet again — it is an arrow function. Arrow functions close over scope exactly like regular functions do; the only things they treat differently are this, arguments, and super. Swapping function(){} for () => changes nothing about this bug in either direction. The fix is let, or a new scope — never the arrow.

How we fixed this before let existed

If you're stuck with var, you have to manufacture a new scope per iteration yourself. Since var only respects function boundaries, that means creating a function per iteration:

✅ The pre-2015 fix (IIFE) 
for (var i = 0; i < 3; i++) {
  (function(captured) {
    setTimeout(() => console.log(captured), 100);
  })(i);                    // 👈 i is passed by value → a fresh copy per iteration
}
// → 0, 1, 2

Each call to that wrapper creates its own table with its own captured parameter. The number was copied in as an argument, so each timeout closes over a different box.

You'll basically never write this today, but interviewers ask for it as a way of checking whether you understand the mechanism or just memorized "use let."

In an interview

The trap answer is "because setTimeout is asynchronous." That's a factor but not the cause, and a good interviewer will push: "so if I remove setTimeout and just store the functions in an array, then call them after the loop — what then?" Same result: three 3s, no async anywhere. The cause is one shared binding. Say that word — binding — and the follow-up disappears.

Part 9Real use cases (please, not another counter)

Every tutorial demonstrates closures with a counter. So every candidate says "counter" in the interview. So interviewers now ask, almost word for word: "give me a use case for a closure that isn't a counter."

Here are five you can actually reach for. Learn two properly.

1. once() — run this exactly one time

Real scenario: a "Place order" button. If a user double-clicks, you charge them twice. You need a guarantee that the handler runs once, ever.

function once(fn) {
  let called = false;
  let result;

  return function (...args) {
    if (called) return result;
    called = true;
    result = fn.apply(this, args);
    return result;
  };
}

const placeOrder = once(() => { console.log("charging card…"); return "order-123"; });

placeOrder();    // → logs "charging card…", returns "order-123"
placeOrder();    // → logs nothing, returns "order-123"

The flag lives in the closure. It can't be reset from outside, can't collide with another once-wrapped function, and doesn't pollute any object with a _hasBeenCalled property. This is the single best answer to give, because it's short enough to write on a whiteboard in 40 seconds and it's obviously real code.

2. Memoization — don't recompute what you already know

function memoize(fn) {
  const cache = new Map();          // 👈 lives in the closure, one per wrapped fn

  return (arg) => {
    if (!cache.has(arg)) cache.set(arg, fn(arg));
    return cache.get(arg);
  };
}

const slugify = memoize((title) => title.toLowerCase().replace(/\s+/g, "-"));

slugify("Hello World");   // → "hello-world"   (computed)
slugify("Hello World");   // → "hello-world"   (from cache)

Every memoized function gets its own private cache automatically. No naming collisions, no global cache object, no cleanup code.

3. Function factories — configure once, call many times

function createFormatter(currency, locale) {
  const nf = new Intl.NumberFormat(locale, { style: "currency", currency });
  return (amount) => nf.format(amount);
}

const formatCAD = createFormatter("CAD", "en-CA");
const formatJPY = createFormatter("JPY", "ja-JP");

formatCAD(1234.5);   // → "$1,234.50"
formatJPY(1234.5);   // → "￥1,235"

There's a real performance angle here: Intl.NumberFormat is expensive to construct. The closure builds it once and every subsequent call reuses it. This one is nice to mention because it shows closures as a performance tool, not just a privacy trick.

4. Debounce and throttle — the closure you've definitely used

function debounce(fn, delay) {
  let timerId;                   // 👈 survives between calls, private to this debounced fn

  return (...args) => {
    clearTimeout(timerId);
    timerId = setTimeout(() => fn(...args), delay);
  };
}

searchInput.addEventListener("input", debounce(runSearch, 300));

Every keystroke calls the returned function, which needs to know about the timer the previous keystroke set. That state has to live somewhere between calls. A closure is the natural home for it — and it's per-debounced-function, so two debounced handlers never interfere.

5. Event handlers that need context

function attachRemoveButtons(products) {
  products.forEach((product) => {
    const btn = document.querySelector(`#remove-${product.id}`);
    btn.addEventListener("click", () => {
      removeFromCart(product.id);       // 👈 closed over, per iteration
    });
  });
}

The click happens minutes after attachRemoveButtons returned. The handler still knows which product it belongs to — because forEach's callback gives each iteration its own scope, and each handler closes over its own product. (Note that forEach sidesteps the whole var loop problem for free, since every iteration is a real function call.)

In an interview

Don't recite all five. Pick one, write it, and explain what the closed-over variable is doing. Then say: "the general shape is — any time you need state that outlives a function call but shouldn't be visible to anyone else, that's a closure. Debounce, memoize, once, module privacy, React hooks — all the same shape." Naming the shape is what makes you sound senior.

Part 10Do closures cause memory leaks?

Short answer: closures don't leak, but they make it easy for you to leak.

Here's the mechanism. JavaScript's garbage collector frees anything unreachable from your running code. A closure is, by definition, a live reference to a scope. So as long as the closure is reachable, everything it captured is reachable too — and therefore uncollectable.

That's the entire feature. It's also the entire risk.

❌ Leaks — a handler pinning a big object forever 
function setupPreview(imageBlob) {       // imageBlob: 40 MB
  const smallThumb = makeThumb(imageBlob);

  window.addEventListener("resize", () => {
    repaint(smallThumb);                 // only needs the thumb…
    console.log(imageBlob.size);         // 👈 …but this pins all 40 MB
  });
}

The listener is attached to window, which lives for the whole page. The listener closes over imageBlob. So imageBlob lives for the whole page too. Call setupPreview on twenty images and you're holding 800 MB of blobs you'll never look at again.

✅ Fixed — capture only what you need, and clean up 
function setupPreview(imageBlob) {
  const smallThumb = makeThumb(imageBlob);
  const size = imageBlob.size;           // 👈 capture the number, not the blob

  const onResize = () => { repaint(smallThumb); console.log(size); };
  window.addEventListener("resize", onResize);

  return () => window.removeEventListener("resize", onResize);  // 👈 teardown
}

Two fixes, and they're the two you should always name:

  1. Capture the smallest thing. Pull out the number, the id, the string — don't close over the whole object when you need one field of it.
  2. Give every long-lived subscription a teardown. Remove the listener, clear the interval, unsubscribe. This is literally what a React useEffect cleanup function is for.
Wait — so is holding memory a leak?

Worth being precise, because it's a great thing to say out loud: a leak is memory that's unreachable-in-spirit but reachable-in-fact — you're done with it, but the GC can't prove that. Closures holding data you still use aren't leaking, they're just using memory. The failure is when the closure outlives your need for what it captured. So the real question is never "does this closure hold memory?" but "how long does this closure live?"

A common misconception

"Closures leak in old IE, so avoid them."

That was a real bug — IE6/7 had a reference-counting GC for DOM objects that couldn't collect cycles between JS closures and DOM nodes. It's been irrelevant for well over a decade. If you cite it as a current reason to avoid closures, you'll sound like you learned JavaScript from a 2009 blog post. Cite it as history if you want; don't cite it as advice.

Part 11IIFEs and the module pattern

A bit of history, because it explains why older code looks the way it does — and interviewers who've been around a while love it when you know this.

Before 2015, JavaScript had no modules and no block scope. Every <script> tag dumped its variables into one shared global namespace. Load jQuery, a carousel plugin, and your own app.js, and if two of them declared var config, the last one silently won. Silently.

The only tool that created a private scope was a function. So people started wrapping entire files in a function and calling it immediately:

(function () {
  var config = { apiUrl: "/api" };   // 👈 invisible to everything outside
  // …the whole file…
})();

That's an IIFE — Immediately Invoked Function Expression. Function expression: it's written in a position where JS expects a value, so it's an expression, not a declaration. Immediately invoked: the () on the end calls it right away.

Wait — why the wrapping parentheses?

If a statement starts with the word function, the parser commits to reading a function declaration, and declarations can't be invoked on the spot. The wrapping parens put it in expression position, where the parser is expecting a value. You'll also see !function(){}() and ;(function(){})() in old minified code — same trick, different characters.

The module pattern

Combine an IIFE with a returned object and you get a module before modules existed:

var cartModule = (function () {
  var items = [];                       // 👈 private. no way in from outside.

  function total() {
    return items.reduce((sum, i) => sum + i.price, 0);
  }

  return {                              // 👈 the public API
    add: function (item) { items.push(item); },
    getTotal: total,
  };
})();

cartModule.add({ price: 30 });
cartModule.getTotal();     // → 30
cartModule.items;          // → undefined  ✅ genuinely private

Everything inside stays inside. Only what you put in the returned object is reachable. One global name (cartModule) instead of a dozen.

And notice what's holding it together: add and getTotal escaped the IIFE, and they're keeping its scope alive so they can still reach items. The module pattern is just a closure. The entire module system of an era was built on the one idea we spent Part 7 on.

Today you'd write export / import and get real module scope from the language. But this is why closures loomed so large in JS culture — for fifteen years they were the only encapsulation mechanism the language had.

Part 12Why closures matter in React

Keeping this tight, since it deserves its own guide — but you will get asked, so here's enough to hold a conversation.

The key fact: a React function component is a function, and it runs again on every render. Every render creates a brand new scope, with brand new local variables — including a brand new value for every useState variable, and brand new function definitions for every handler and effect.

Which means every function you define inside a component is a closure over that particular render's scope. Not over "the component." Over one render.

❌ The stale closure 
function Timer() {
  const [count, setCount] = useState(0);

  useEffect(() => {
    const id = setInterval(() => {
      setCount(count + 1);      // 👈 closed over count from render #0, forever
    }, 1000);
    return () => clearInterval(id);
  }, []);                       // 👈 empty deps: this effect never re-runs

  return <p>{count}</p>;         // → sticks at 1 forever
}

The effect ran once, on the first render, where count was 0. The interval callback closed over that render's scope. It doesn't matter how many times the component re-renders afterwards — that callback is still looking at that table, where count is eternally 0. So every tick computes 0 + 1.

This is exactly the var loop bug wearing a React costume. Same cause: a function outliving the moment its captured value was correct.

✅ Two ways out 
// A) Don't read the stale value — let React hand you the fresh one.
setCount(c => c + 1);           // functional update, no closure over count

// B) Or let the effect re-run so it closes over a fresh scope.
useEffect(() => { /* … */ }, [count]);

That's also the honest answer to "why does the exhaustive-deps lint rule exist?" — it's protecting you from stale closures. Every value from the render scope that your effect reads must be in the deps array, or the effect keeps looking at an old scope.

In an interview

Connecting these two — "the React stale closure bug and the var loop bug are the same bug" — is one of the highest-value sentences you can say in a frontend interview. It shows you understand the mechanism well enough to recognise it in an unfamiliar costume, which is the actual thing they're screening for.

Part 13The follow-up questions

This is the part that decides the interview. The first question is usually recall; the follow-ups are where they find out whether you understand it. Answers are collapsed so you can quiz yourself.

How this gets asked

The literal phrasings, so none of them surprise you:

  • "What's a closure? Can you give me an example?"
  • "What's the difference between var, let, and const?"
  • "What does this log?" (the loop, every single time)
  • "Explain hoisting."
  • "What's the Temporal Dead Zone?"
  • "How would you make a private variable in JavaScript?"
  • "Implement once / debounce / memoize." (a closure question in disguise)

The model answer for "what's a closure?"

"A closure is a function together with the scope it was created in. In JavaScript scope is lexical, so a function's parent scope is fixed by where it's written, not where it's called — and it keeps a live reference to that scope. So when a function outlives the call that created it, the variables it captured are still alive and still shared, not copied. Practically, I use that any time I need state that survives between calls but shouldn't be public — a cache in a memoize wrapper, the timer id in a debounce, or a hasRun flag in a once helper."

Why that lands: it defines the thing without using the word "remembers", names the mechanism (lexical, live reference, shared not copied), and lands on real code instead of a counter. It also plants three follow-ups you're ready for. Roughly 25 seconds spoken — long enough to show depth, short enough that you're not monologuing.

"Why not just use let everywhere? Is var ever OK?"

Do use let and const everywhere in new code — const by default, let when you genuinely reassign. That's not controversial.

But the honest answer to "is var ever OK" isn't a flat no, it's: there's no case where var is better, but there are cases where it's deliberate. Its one distinguishing behaviour is that a top-level var creates a property on window, which old scripts occasionally relied on to expose globals across <script> tags. Modern code uses modules and explicit exports instead. And you'll still read var constantly in legacy code and transpiler output, which is why you need to understand it even though you won't write it.

The strong version: "I'd never reach for var, but I don't treat it as forbidden knowledge — the function-scoping is the thing you have to hold in your head when reading older code."

"Do closures cause memory leaks?"

"Not by themselves. A closure holds its captured scope alive as long as the closure itself is reachable — that's the feature, not a bug. It becomes a leak when the closure lives longer than you need what it captured: an event listener on window, a setInterval, a subscription that's never torn down. The fixes are to capture the smallest thing you need rather than a whole large object, and to give every long-lived subscription an explicit teardown — which is exactly what a useEffect cleanup is."

Bonus if they push: mention that you'd confirm with a heap snapshot in DevTools rather than guessing — take a snapshot, do the thing, take another, and compare retained size. Naming a diagnostic tool is a strong senior signal.

"Is const immutable?"

"No — const freezes the binding, not the value. The variable can never be reassigned to point at something else, but if it points at an object or array, the contents are completely mutable. Object.freeze gets you a shallow freeze of the value itself; for deep immutability you'd need a recursive freeze or a library."

Trap to avoid: saying "yes, const means constant." That's the single most common wrong answer to this question.

"What's the output of the loop?" (and the two variants they'll try)

var version: 3 3 3. let version: 0 1 2. Reason: one shared binding vs. a fresh binding per iteration.

Variant 1 — no async at all:

const fns = [];
for (var i = 0; i < 3; i++) fns.push(() => i);
fns.map(f => f());     // → [3, 3, 3]

Still three 3s. This is the trap for anyone who answered "because setTimeout is async."

Variant 2 — what about a for…of or forEach? Both give 0 1 2 even with sloppy code: forEach because every iteration is a real function call with its own scope, and for…of with let/const because it creates a fresh binding per iteration too.

"Implement a private counter — and now do it without a closure." 
// With a closure:
function createCounter() {
  let count = 0;
  return { increment: () => ++count, get value() { return count; } };
}

// Without — private class fields (ES2022):
class Counter {
  #count = 0;
  increment() { return ++this.#count; }
  get value() { return this.#count; }
}

The interesting comparison: closures give one private copy per call, and the privacy comes from the scope chain being one-directional. # fields give one per instance, enforced by the language, and they're inspectable in DevTools while closure variables largely aren't. Closure-based privacy also costs one function object per method per instance; class methods are shared on the prototype. Knowing that trade-off is well past what most candidates offer.

"Why do closures matter in React specifically?"

"Because a function component re-runs top to bottom on every render, so every render creates a fresh scope. Every handler, effect and callback you define inside closes over that render's variables. If a function outlives its render — an interval, an event listener, an effect with empty deps — it keeps reading that old scope, and you get a stale closure. That's what the exhaustive-deps lint rule is protecting you from, and it's why the functional form of setState exists: setCount(c => c + 1) never reads a captured value at all."

"Are let and const hoisted?"

"Yes — they're registered in the scope during the creation phase, they're just not initialized. That gap is the Temporal Dead Zone. You can prove they're hoisted: if a block declares its own const theme, then a reference above that line throws instead of finding the outer theme — which means the engine already knew about the inner one."

Why this lands: most candidates say "no, only var is hoisted." Being able to prove the opposite with a three-line snippet is memorable.

"Why does the TDZ exist? Isn't it just annoying?"

"Two reasons. First, if early access silently gave you undefined, you couldn't tell a real ordering bug from a variable that legitimately holds undefined — the TDZ turns a silent wrong value into a loud error at the exact line that caused it. Second, const couldn't work otherwise: auto-initializing it to undefined would mean your actual assignment is the second one, which is the thing const forbids."

"Does every function create a closure?"

Technically yes — every function is created with a reference to its outer scope, so every function is a closure in the spec sense. But in practice engines only allocate a heap context when the inner function actually references something from the outer scope, and colloquially we say "closure" when that captured state outlives the outer call. Both answers are right; showing you know both is the point.

"Two closures from the same call — do they share state or each get a copy?"

They share. Same scope table, same live variables — that's the makeAccount example, where deposit and getBalance both see the same balance. Two separate calls to the factory produce two independent tables. So: one call = one shared private state; N calls = N independent states. Getting this backwards is the most common way people misuse factory functions.

"Does an arrow function fix the loop bug?"

"No. Arrow functions close over scope identically to regular functions — the only things they handle differently are this, arguments, and super. The broken loop example usually already uses an arrow. The fix is let, or manufacturing a new scope per iteration with an IIFE."

Traps, collected

The specific wrong answers that get people dinged:

  • "Hoisting moves declarations to the top." → It's a two-phase setup; nothing moves.
  • "let and const aren't hoisted." → They are; they're just uninitialized.
  • "const makes it immutable." → Binding, not value.
  • "The loop logs 3,3,3 because setTimeout is async." → It's the shared binding; remove the async and it still happens.
  • "A closure remembers the values of its variables." → It shares the live scope. Values change under it.
  • "Closures cause memory leaks." → Long-lived closures over large data do. That's a lifetime problem, not a closure problem.
  • "Arrow functions fix the loop." → They're irrelevant to it.

Part 14Interview cheat sheet

Read this on the train. One crisp line each.

Scope

A lookup table of names → values, created per function call and per block. Lookups walk up the chain of parent tables, never down.

Lexical scope

A function's parent scope is decided by where it's written, not where it's called. (Unlike this in a regular function, which is decided by the caller.)

var

Function-scoped, redeclarable, initialized to undefined during the creation phase, creates a window property at top level.

let / const

Block-scoped, not redeclarable, hoisted but uninitialized (TDZ). const additionally can't be reassigned.

const

Freezes the binding, not the value. Objects and arrays behind a const are fully mutable. Object.freeze is shallow.

Hoisting

Two phases per scope. Creation: register all declared names (functions ready, var = undefined, let/const = uninitialized). Execution: run lines, fill in values.

Function declaration vs expression vs arrow

Declarations are fully usable before their line. Expressions/arrows hoist only the variable — so calling early gives TypeError with var, ReferenceError with const.

Temporal Dead Zone

The window between a let/const being registered and being initialized. Access throws — even typeof. It exists so ordering bugs fail loudly and so const's one-assignment rule holds.

Closure

A function plus a live reference to the scope it was created in. It keeps that scope alive after the outer call returns. Shared, not copied.

The loop

var → 3 3 3 (one binding). let → 0 1 2 (fresh binding per iteration). Not about async.

Closure use cases

once, memoize, debounce/throttle, function factories, event handlers with context, module privacy. Shape: state that outlives a call but stays private.

Memory

Closures retain what they capture for as long as they're reachable. Capture the smallest thing; tear down long-lived subscriptions.

IIFE / module pattern

Pre-ES6 encapsulation: wrap a file in an immediately-called function, return a public API object. It's a closure. ES modules replaced it.

React

Every render is a new scope. Functions defined in a render close over that render. Effects with stale deps read old scopes — hence exhaustive-deps and setState(prev => …).

If you only keep one sentence from all of this, keep this one:

A function is permanently attached to the scope it was written in, and that attachment keeps the scope alive.

Hoisting is what fills those scopes in. The TDZ is the gap before they're filled. var vs let is a disagreement about how many scopes there are. And a closure is what you call it when a function walks off with one.
