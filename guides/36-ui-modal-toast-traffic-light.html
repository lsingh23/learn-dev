Modal, toasts, and a traffic light

Three prompts that look unrelated, and share one nasty property: they involve time, or DOM that lives outside your component, or both. Same five-step method as always — but these are the ones where step 5 is where the interview actually happens.

What makes these three different

Everything in the framework guide still applies: clarify, state shape, static render, wire, polish. The four shapes still cover it — a modal is a flag, toasts are a list of records, a traffic light is a pointer. Honestly, the state on all three is a two-minute job.

So what are they testing? Two things the earlier components never touch. A modal has to reach outside your component — outside the React tree, outside the CSS stacking context, outside your keyboard focus. Toasts and the traffic light have to deal with time: timers that must be cancelled, timers that must not leak, timers that must survive a re-render.

Modal — a flag, and a lot of etiquette

// state:
//   isOpen → boolean, owned by the PARENT (not the modal)
// if there are several modals in one screen, upgrade to:
//   openModal → 'confirm-delete' | 'share' | null   ← one pointer, illegal states gone

Note who owns the flag. The modal is a dumb, controlled component: it takes isOpen and onClose and holds nothing. If it owned its own isOpen, the parent couldn't open it — which is the entire point of a modal.

✅ The simplest version that's worth showing
function Modal({ isOpen, onClose, title, children }) {
  if (!isOpen) return null;
  return (
    <div className="backdrop" onClick={(e) => {
      if (e.target === e.currentTarget) onClose();   // 👈 backdrop only
    }}>
      <div className="panel" role="dialog" aria-modal="true" aria-label={title}>
        {children}
      </div>
    </div>
  );
}

That e.target === e.currentTarget line is small and interviewers watch for it. Clicks inside the panel bubble up to the backdrop, so a naive onClick={onClose} closes the modal when you click your own Save button. Comparing target to currentTarget means "the click started on me, not on a child."

Upgrade 1: put it in a portal

Rendering the modal where it's used is asking for trouble, and the reason isn't React — it's CSS. If any ancestor has overflow: hidden, your modal gets clipped. If any ancestor has a transform, filter or will-change, it becomes the containing block for position: fixed, so your full-screen overlay is now sidebar-sized. And an ancestor with its own z-index traps you in a stacking context you can never escape, no matter how many nines you add.

return createPortal(markup, document.body); // escapes all three problems at once

The portal moves the DOM node to document.body while keeping it in the React tree, so props, context and event bubbling all still work. Say that sentence out loud.

Upgrade 2: Escape, and a tiny reusable hook

function useOnEscape(enabled, onEscape) {
  useEffect(() => {
    if (!enabled) return;
    const onKey = (e) => e.key === 'Escape' && onEscape();
    document.addEventListener('keydown', onKey);
    return () => document.removeEventListener('keydown', onKey); // always
  }, [enabled, onEscape]);
}

Bind it on document, not the panel — a keypress only reaches the panel if focus is already inside it, which it might not be. And note the cleanup; the toasts need the same discipline in a minute.

Upgrade 3: scroll lock, focus trap, restore focus

Scroll lock is one line and its cleanup: set document.body.style.overflow = 'hidden' on open, restore it on close. Do it in an effect so the restore happens even if the modal unmounts abruptly.

Focus is the fiddly part, and I'd rather you say so than fake it. Three obligations: move focus into the dialog on open, keep Tab from escaping it, and put focus back on the element that opened it when it closes. That last one is the most-forgotten and the most noticeable — a keyboard user who closes a modal and lands at the top of the page has lost their place entirely.

const opener = useRef(null);
useEffect(() => {
  if (!isOpen) return;
  opener.current = document.activeElement;      // remember
  panelRef.current?.focus();
  return () => opener.current?.focus();          // restore
}, [isOpen]);

The Tab-cycling trap itself — query the focusable children, wrap Tab on the last and Shift+Tab on the first — is genuinely tedious to write from memory. In a real interview I'd write the sketch above, then say: "a full focus trap needs a focusable-elements query and wrap logic on Tab; in production I'd use focus-trap-react or the native dialog." That's a better answer than twelve shaky lines.

"So why not just use <dialog>?"

You should, in production. <dialog>.showModal() gives you the top layer (no z-index fights at all), a real backdrop pseudo-element, Escape, focus containment and inertness on everything behind it, for free. Interviewers still ask for the manual version because the manual version is the one that reveals whether you know what a modal owes the user. Name <dialog>, explain that it's the right production answer, then build it by hand anyway. You get credit for both.

Toasts — a list of records, each with its own clock

// state:
//   toasts → [{ id, message, type }]   ids generated at PUSH time
// lives in a context provider near the root, so anything can call toast()
// derived: nothing. removal is always BY ID.

The clarifying question: "does any component need to fire a toast, or just this page?" If it's anything, you need a provider — the toast list has to live above everything that triggers it, while the trigger has to be reachable from anywhere below.

const ToastCtx = createContext(null);

export function ToastProvider({ children }) {
  const [toasts, setToasts] = useState([]);
  const push = useCallback((message, type = 'info') => {
    setToasts((t) => [...t, { id: crypto.randomUUID(), message, type }]);
  }, []);
  const remove = useCallback((id) => {
    setToasts((t) => t.filter((x) => x.id !== id));   // 👈 by id, never index
  }, []);
  return (
    <ToastCtx.Provider value={push}>{children}
      <div className="toast-stack" role="status" aria-live="polite">
        {toasts.map((t) => <Toast key={t.id} {...t} onDone={remove} />)}
      </div>
    </ToastCtx.Provider>
  );
}

Now the timer. Where does it go? Not in the provider — in each Toast. One timer per toast, owned by the component that it kills.

function Toast({ id, message, onDone, ms = 4000 }) {
  useEffect(() => {
    const t = setTimeout(() => onDone(id), ms);
    return () => clearTimeout(t);         // unmount early? no ghost callback
  }, [id, ms, onDone]);
  return <div className="toast" onClick={() => onDone(id)}>{message}</div>;
}

The cleanup is not optional politeness. Without it, a toast dismissed manually still fires its timeout four seconds later, calling onDone on an id that's already gone. It happens to be harmless here, and it is absolutely not harmless in the general case — say so.

Upgrade: pause on hover

Nobody wants a toast to vanish while they're reading it. The cheap version: a paused flag in the toast, hovering sets it, and the effect returns early while paused — restarting a fresh full-length timer on mouse-leave.

useEffect(() => {
  if (paused) return;                     // effect re-runs when paused flips
  const t = setTimeout(() => onDone(id), ms);
  return () => clearTimeout(t);
}, [paused, id, ms, onDone]);

Exact? No — it restarts the full duration instead of resuming the remainder. Say so: "for true resume I'd track the remaining time in a ref." Knowing your own code's limitation beats not having one.

Traffic light — a pointer over a config array

Here's the trap. Almost everyone starts with three booleans, or a color string and a ladder of if (color === 'red') setColor('green'). It works, it's ten times longer than it needs to be, and adding a blinking amber breaks it.

❌ Three booleans and a ladder of ifs
const [red, setRed] = useState(true);
const [amber, setAmber] = useState(false);
const [green, setGreen] = useState(false);
// nothing stops all three being true. now write the advance handler. good luck.

The whole component is one idea: the sequence is data, and the state is just a finger pointing at a row.

✅ Config-driven, and that's the entire component
const LIGHTS = [
  { color: 'red',   ms: 4000 },
  { color: 'green', ms: 3000 },
  { color: 'amber', ms: 1000 },
];

function TrafficLight() {
  const [i, setI] = useState(0);                 // state: a pointer. that's all.
  useEffect(() => {
    const t = setTimeout(() => setI((n) => (n + 1) % LIGHTS.length), LIGHTS[i].ms);
    return () => clearTimeout(t);
  }, [i]);
  return LIGHTS.map((l, n) =>
    <Lamp key={l.color} color={l.color} on={n === i} />);
}

Adding "flashing amber before red"? A row in the array. Making it configurable by props? Pass LIGHTS in. A pedestrian button that jumps to red? setI(0). This shape generalises to any timed sequence — a carousel that auto-advances, an onboarding tour, a slideshow, a Pomodoro timer. Recognise it once and you get four components for free.

Under the hood — why [i] in the deps is the right call

Each render with a new i tears down the old timeout and schedules the next one with that phase's duration. Per-phase timing falls out for free, and there's never more than one timer alive. A single setInterval can't do variable durations without extra bookkeeping — that's the trade you're making, and it's worth saying out loud.

The follow-ups you'll actually get

"Why a portal? Can't you just set z-index: 9999?"

No — z-index only competes inside its own stacking context. If an ancestor created one, my 9999 loses to a sibling's 1. And an ancestor with overflow: hidden clips me, while an ancestor with a transform re-anchors my position: fixed. A portal sidesteps all three by moving the node to document.body, and I keep React context and event bubbling because the React tree is unchanged.

"Why not one shared timer for all toasts instead of one each?"

Because they don't share a deadline. Each toast is born at a different moment and may have its own duration, and hovering pauses one without pausing the others. One interval ticking over the whole list means storing per-toast expiry timestamps and re-rendering every tick — more state, more code, and lower resolution. One timer owned by the component it dismisses is the simpler thing, and it cleans itself up on unmount.

"What breaks if you remove a toast by index?"

Everything, intermittently. The index is captured when the timeout is scheduled, but the array shifts every time another toast is added or dismissed — so a toast that expires after its neighbour was removed dismisses the wrong one. Ids are stable from creation, so filter(t => t.id !== id) is always right. Same reason ids make better keys.

"How do you stop the traffic light drifting?"

For a UI demo I wouldn't bother — a few milliseconds of setTimeout lag per phase is invisible. If it had to stay honest over hours, I'd stop trusting the delay and compute from wall-clock: record the phase's start with Date.now(), and schedule the next tick for start + ms - Date.now() so each correction absorbs the previous error instead of accumulating it. Same fix for a countdown timer, which is where this actually gets asked.

"Should the modal render null when closed, or stay mounted and hide with CSS?"

Return null by default — unmounting drops the DOM, releases focus and leaves no hidden focusable elements to tab into. The one reason to stay mounted is an exit animation, since you can't animate a node that's already gone; then I'd delay the unmount until transitionend. A real trade-off, not an oversight.

Cheat sheet

  • Modal = a flag the parent owns. Several modals? One openModal: id | null pointer, not several booleans.
  • Portal because of CSS, not React: overflow:hidden clips, transform re-anchors fixed, stacking contexts trap z-index.
  • e.target === e.currentTarget — close on backdrop, not on clicks inside the panel.
  • Modal owes the user four things: Escape closes, scroll locks, focus enters and is trapped, focus is restored to the opener.
  • role="dialog" + aria-modal="true" + a label. Name <dialog>.showModal() as the modern answer, then build it by hand.
  • Toasts = list of records with ids at push time. Remove by id, never index.
  • Provider + context so any component can call toast(); the list lives above everything that fires it.
  • One setTimeout per toast, in an effect, with clearTimeout in the cleanup. Pause-on-hover = a flag in the deps array.
  • role="status" / aria-live="polite" on the stack, or screen readers never hear it.
  • Traffic light = a pointer into a config array. setI(n => (n + 1) % LIGHTS.length), per-phase ms in the data.
  • Any timed sequence is that same shape — auto-carousel, tour, slideshow, Pomodoro.
  • Every timer and every listener gets a cleanup. If you can't point at the cleanup, you've written a leak.
