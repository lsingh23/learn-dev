1. The frozen input box

I want to start with a bug you have almost certainly experienced as a user, even if you've never built it yourself.

You're on a page with a search box. Below it, a list of a few thousand things. You start typing, and… the letters lag. You type "chair" and for a beat the box shows "cha", then it catches up and slams in "ir". The cursor stutters. The page feels broken, even though nothing is broken.

Here's the code that causes it. It looks completely reasonable:

❌ Types like it's underwater 
function ProductSearch({ products }) {   // products.length === 10000
  const [query, setQuery] = useState('');

  const matches = products.filter(p => p.name.includes(query));

  return (
    <>
      <input value={query} onChange={e => setQuery(e.target.value)} />
      <ProductList items={matches} />   // 👈 renders ~10,000 rows
    </>
  );
}

Take a second and ask yourself: why does the input lag? The filter itself is fast — filtering ten thousand small objects is a millisecond or two. The expensive part is rendering ten thousand list items. But rendering happens after the state update, right? So why does that block the letter from appearing?

Because — and this is the whole reason concurrent React exists — the letter appearing in the input box is a render. It's a controlled input. The character shows up only once React re-renders with the new query. And in the same render pass, React also renders the ten thousand rows. They're welded together. One `setQuery` call, one render, and that render takes 300ms.

Now the deeper problem. Before React 18, once React started a render, it could not stop. It walked the entire component tree, top to bottom, building the new UI description, and only when it finished did it hand control back to the browser. The browser could not paint. It could not process your next keystroke. It just… waited.

2. Concurrent rendering: the premise

So here's the idea, in one sentence:

React can start rendering, pause partway through to deal with something more urgent, and then either resume where it left off or throw the half-finished work in the bin and start over.

That's it. That's concurrent React. Everything else — useTransition, useDeferredValue, Suspense's smarter behaviour, streaming SSR — is built on that one capability.

Let me give you the analogy I use, because the word "concurrent" sends people down a completely wrong path.

The analogy: one chef, not many

Imagine a small restaurant with exactly one chef. A big catering order comes in: 200 identical sandwiches. The chef starts making them.

In the old world, that chef is stubborn. Once started, they will not stop until all 200 sandwiches are done. A customer walks in and asks for a glass of water. Too bad — they stand there for twenty minutes while the chef assembles sandwich #47.

In the new world, the chef works in short bursts. After every few sandwiches they look up and ask: "anyone need anything urgently?" Glass of water? Sure, here you go, five seconds, back to sandwiches. The catering order still takes roughly twenty minutes — maybe a hair longer, because of the interruptions — but nobody standing at the counter feels ignored.

And sometimes something better happens. Halfway through the catering order, the client calls: "actually make it 200 wraps, not sandwiches." The chef bins the half-finished tray and starts on wraps. All that sandwich work is thrown away — and that's fine, because nobody ever saw it. It was never served.

That last part is the bit people miss. React's paused, half-finished render is not on screen. It exists only in memory. So React is free to discard it, and often does — every time you type another letter, the in-progress filtered-list render for the previous letter becomes garbage.

A common misconception

"Concurrent React uses multiple threads / Web Workers." No. There is one chef. JavaScript in the browser runs on a single main thread, and React does not change that. Nothing is running in parallel — ever.

"Concurrent" here means concurrency in the computer-science sense: multiple pieces of work in flight, interleaved on one worker. Like a single person alternating between two books, not two people each reading one. React achieves it by chopping the render into small chunks and yielding back to the browser between them (roughly every 5ms), which lets the browser process input events and paint.

This misconception is the single most common wrong answer on this topic, so it's worth having the correction ready as a sentence you can say out loud.

Urgent vs. transition

If React can pause work to do something more important first, it needs to know what "more important" means. React can't figure that out on its own — filtering a list and typing a letter are, to React, both just setState calls. You have to tell it.

React groups updates into two buckets:

  • Urgent updates — the direct, physical response to something the user just did. Typing a character. Toggling a checkbox. A button visually depressing. If these lag, the app feels broken, because the user's fingers and the screen disagree.
  • Transition updates — the consequence of that interaction, which can take a moment. Re-filtering 10,000 rows. Switching to a new tab that renders a heavy chart. Navigating to a different page. If these lag by 150ms, the app feels busy, which is completely acceptable.

Everything is urgent by default. You opt specific updates into the transition bucket. That default is deliberate — an update that's accidentally urgent is merely slow, but an update that's accidentally deprioritised could feel unresponsive.

In an interview

If someone asks "what problem does concurrent mode solve?", the trap is answering "it makes React faster." It does not. The catering order still takes twenty minutes. Concurrent React does strictly more total work (interruptions have overhead, and discarded renders are wasted). What it buys you is responsiveness — the ability to keep the urgent 5% of work from getting stuck behind the slow 95%. Say "perceived performance", not "performance", and you've already separated yourself from most candidates.

3. useTransition

Let's fix the search box. The API:

const [isPending, startTransition] = useTransition();

Two things come back. startTransition is a function you wrap state updates in to say "this one's not urgent." isPending is a boolean that's true while a transition you started is still rendering — so you can show a subtle spinner or dim the stale content.

✅ Typing stays smooth 
function ProductSearch({ products }) {
  const [query, setQuery] = useState('');        // urgent: the input
  const [filter, setFilter] = useState('');      // transition: the list
  const [isPending, startTransition] = useTransition();

  function handleChange(e) {
    setQuery(e.target.value);                    // 👈 urgent, always instant
    startTransition(() => {
      setFilter(e.target.value);                 // 👈 interruptible
    });
  }

  const matches = products.filter(p => p.name.includes(filter));

  return (
    <>
      <input value={query} onChange={handleChange} />
      <div style={{ opacity: isPending ? 0.6 : 1 }}>
        <ProductList items={matches} />
      </div>
    </>
  );
}

Notice what we had to do: split one piece of state into two. query drives the input and is urgent. filter drives the list and is a transition. Most of the time they're identical; while you're typing fast, filter lags behind query by a render or two — and that lag is exactly the responsiveness we bought.

Walk through what happens when you type "chair" quickly:

  1. You press c. setQuery('c') is urgent — React renders the input immediately. The letter appears. setFilter('c') starts rendering the list in the background.
  2. Before that finishes, you press h. React throws away the in-progress "c" list render, immediately renders the input showing "ch", then starts a fresh "ch" list render.
  3. …and so on. Only when you actually pause does a list render get to finish and commit.

You never see a partial list. React only shows finished work.

Wait, what about… the callback? Does it have to be synchronous?

Yes, and this catches people. React marks as a transition only the setState calls that happen synchronously inside the callback. This does not work:

startTransition(() => {
  setTimeout(() => setFilter(value), 0);  // ❌ not a transition
});

By the time the timeout fires, React has stopped listening. Same problem with await in older React: updates after the first await escaped the transition. React 19 fixed this specific case — startTransition now accepts an async function and keeps isPending true across awaits (this is the machinery behind "Actions" and useActionState). But the mental model stays: put the update in the callback, not in a callback inside the callback.

startTransition outside a component

Hooks can only run inside components. But sometimes the code that triggers the expensive update isn't in a component at all — it's in a router, a store subscription, a plain event handler on window. For that, React exports a standalone version:

import { startTransition } from 'react';

router.subscribe(url => {
  startTransition(() => {
    store.setRoute(url);   // 👈 same priority marking, no hook needed
  });
});

Identical behaviour, one thing missing: no isPending. That flag has to live in a component's state, so if you want it, you need the hook. This is genuinely the only difference.

Trap: candidates sometimes say "useTransition debounces the update." It doesn't, and the distinction matters. A debounce delays starting the work by a fixed wall-clock time — during that delay React is idle and the UI is stale for no reason. A transition starts immediately and just yields politely while it runs. Concretely: with a 300ms debounce and a fast typist, the list is always 300ms behind. With a transition, if the user pauses for 40ms and the render only needs 40ms, the list is already there. They also compose fine — debounce a network request, transition the render.

4. useDeferredValue

Now here's a wrinkle. Our fix required us to own the setState call — we had to reach into handleChange and wrap it. What if we don't own it?

Say you're writing a chart component. Someone passes you a data prop that changes rapidly, and rendering the chart takes 200ms. You have no access to their state setter. You can't wrap anything.

useDeferredValue attacks the same problem from the other end. Instead of marking the update as low priority, you take a value and ask React for a lagging copy of it:

function ProductSearch({ products }) {
  const [query, setQuery] = useState('');
  const deferredQuery = useDeferredValue(query);   // 👈 the lagging copy

  const matches = products.filter(p => p.name.includes(deferredQuery));

  return (
    <>
      <input value={query} onChange={e => setQuery(e.target.value)} />
      <ProductList items={matches} />
    </>
  );
}

Here's the mechanic. When query changes to "ch", React does two renders:

  1. Urgent render: query is "ch", but deferredQuery is still the old value, "c". The input updates instantly. The list doesn't move — it still shows the "c" results.
  2. Background render: React then re-renders with deferredQuery = "ch", at transition priority — interruptible, discardable.

The analogy: think of useDeferredValue as a photocopy that's always one page behind. You keep feeding pages in at the top; the copy that comes out the bottom catches up whenever the machine has a spare moment. If you feed pages faster than it can copy, it just skips the intermediate ones and copies the latest — you never get a queue of stale copies.

This analogy breaks down in one place worth naming: a real photocopier processes every page it's given. React genuinely abandons intermediate renders. If you type five letters fast, React may only ever finish rendering the list for the fifth.

The "stale content while new content renders" pattern

Because the deferred value lags, you can detect the lag and style around it:

const deferredQuery = useDeferredValue(query);
const isStale = query !== deferredQuery;   // 👈 the whole trick

return (
  <div style={{ opacity: isStale ? 0.5 : 1, transition: 'opacity 0.2s' }}>
    <ProductList items={matches} />
  </div>
);

This produces something genuinely nicer than a spinner: the old results stay visible and readable, just faded, while the new ones render. Compare that to the usual approach, where results vanish and get replaced by a skeleton, the page height collapses and jumps, and your eyes lose their place. Keeping stale content on screen is almost always the better UX, and this is the cleanest way to get it.

Under the hood

Both of these are the same machinery. useDeferredValue is essentially "re-render me with the new value, but schedule that render as a transition." You could hand-roll something similar with useState + useEffect + startTransition. The reason to use the built-in is that React can do it without the extra committed render an effect would cause, and it participates properly in interruption and Suspense.

React 19 added a second argument: useDeferredValue(value, initialValue), which controls what the deferred copy reads on the very first render instead of just mirroring value.

So which one do I reach for?

The one-line rule: if you can wrap the setter, use useTransition. If all you have is the value, use useDeferredValue. They are not competitors — they're the same idea with different ergonomics, and it's normal for one app to use both.

In an interview

"useTransition vs useDeferredValue?" is a depth question, not a recall question. The interviewer wants to know if you understand they're the same priority system. A great answer is short: "Same mechanism, different handle. useTransition lets you mark the update as non-urgent, so you need to own the setter and you get isPending for free. useDeferredValue lets you mark the read as non-urgent, which is what you use when the value arrives as a prop and you can't touch the setter. If I own the state I reach for useTransition; in a leaf component receiving a hot prop I reach for useDeferredValue."

5. Suspense

Different problem now. Let's talk about loading states.

Here is what basically every React component looks like when it fetches something:

function UserProfile({ id }) {
  const { data, loading, error } = useUser(id);

  if (loading) return <Spinner />;
  if (error) return <ErrorMessage />;
  return <h1>{data.name}</h1>;
}

Nothing's wrong with that. But notice: every single component that loads anything has to repeat that three-branch dance. And when a page has six such components, you get six independent spinners popping in at six different moments, which looks like a slot machine. Coordinating them — "wait until all of these are ready, then show the page" — means lifting all the loading flags up somewhere, and now your components are all tangled together.

Suspense flips the responsibility. Instead of each component handling its own not-ready-ness, a component simply declares that it isn't ready, and some ancestor decides what to show meanwhile.

What "a component suspends" actually means

This phrase gets used constantly and rarely explained, so let's do it properly.

Normally, React calls your component function and it returns some JSX. Suspending means: instead of returning JSX, the component signals "I can't render yet — here's a promise; come back when it resolves." Mechanically, in classic React internals, it throws a promise. React catches that the same way a try/catch would, walks up the tree looking for the nearest <Suspense> boundary, and renders that boundary's fallback instead of the subtree. It also subscribes to the thrown promise; when it resolves, React retries rendering the component.

The analogy: it's a waiter taking your order and finding the kitchen out of an ingredient. The waiter doesn't stand at your table apologising. They go back to the manager and say "table 4 is blocked." The manager puts a bowl of bread on the table (the fallback) and sends the waiter back when the ingredient arrives.

Wait, what about… throwing a promise? That's bizarre.

It is! It's an unusual use of the throw mechanism — throwing is normally for errors. React chose it because it's the only way to interrupt a function call from arbitrarily deep in a call stack and unwind back to the caller, without every component in between having to know or cooperate.

You should never write throw promise yourself. It's an internal contract between React and data libraries. In modern React you go through the use() hook, or through your framework's data loading. But knowing that "suspends" means "unwinds to the nearest boundary" is what makes Suspense's behaviour predictable instead of magic.

Boundaries: the loading equivalent of error boundaries

The shape is deliberately parallel, and pointing this out in an interview reads well:

<ErrorBoundary fallback={<p>Something broke.</p>}>
  <Suspense fallback={<ProfileSkeleton />}>
    <UserProfile id={userId} />
  </Suspense>
</ErrorBoundary>

An error boundary catches errors thrown by its subtree. A Suspense boundary catches not-ready-yet thrown by its subtree. Both are declarative, both handle a whole subtree regardless of depth, both let the components underneath be written as if nothing can go wrong and everything is already loaded.

And that's the real payoff: UserProfile gets to be three lines. No loading, no error, no early returns.

Nesting boundaries, and the "everything pops in at once" problem

A boundary's granularity is your loading design. One boundary at the top of the page means one spinner and an all-or-nothing reveal — the page shows nothing until the slowest thing on it is done. That's often worse than what you had.

That last point deserves emphasis because it's a real-code detail interviewers like: your fallback should reserve the same space as the content it replaces. A skeleton the same height as the loaded component means the swap is invisible. A tiny centred spinner means the page lurches. This is the same layout-shift problem you'd otherwise measure as CLS.

6. React.lazy and code splitting

Every reader of this guide will hit this one, so let's do it in detail.

Your bundler produces one big JavaScript file. The user lands on the login page and downloads the admin dashboard, the PDF exporter, the chart library, and the emoji picker — none of which they will open. That's a lot of bytes to parse before anything is interactive.

Code splitting means cutting the bundle into chunks that load on demand. React.lazy is React's hook into that:

const Dashboard = React.lazy(() => import('./Dashboard'));  // 👈 dynamic import

function App() {
  return (
    <Suspense fallback={<PageSkeleton />}>
      <Dashboard />
    </Suspense>
  );
}

How does it actually work?

Piece by piece, because this is a direct interview question:

  1. import('./Dashboard') is a dynamic import — a JavaScript language feature, not a React one. It returns a promise for the module. Crucially, your bundler sees this syntax at build time and splits Dashboard (and everything only it imports) into a separate chunk file.
  2. React.lazy takes that loader function and returns a component. It doesn't call the loader yet — nothing is downloaded at this point.
  3. The first time React tries to render <Dashboard />, lazy calls the loader, gets back a pending promise, and suspends. Which is exactly the mechanism from the last section.
  4. React finds the nearest <Suspense> and shows PageSkeleton. The network fetches the chunk.
  5. The promise resolves with the module. lazy caches the resolved component and React retries. This time <Dashboard /> renders for real. Subsequent renders hit the cache — no second download.

So React.lazy is not a separate feature bolted on. It's the canonical example of Suspense, and it's why Suspense shipped as stable long before Suspense-for-data-fetching did.

Wait, what about… the default export?

React.lazy requires the module to have a default export that is a component. If you use named exports, you re-shape it inline:

const Dashboard = React.lazy(() =>
  import('./Dashboard').then(m => ({ default: m.Dashboard }))
);

Also: define lazy() at module scope, never inside a component body. Inside a component you'd create a brand-new lazy component on every render, which React sees as a different component type — it unmounts and re-downloads, and your app flickers forever. This is a genuinely common bug.

Trap: "code split every component." Don't. Each chunk is an extra network round trip, and a 2KB component split out costs more in latency than it saves in bytes. Split along the seams where users genuinely branch: routes first, then heavy modals and editors, then big third-party libraries (a chart lib, a rich text editor, a date picker). Nice thing to add: you can preload a chunk on hover or focus — call the same import() function in an onMouseEnter — so by the time the click lands, the code is already there.

Data fetching with Suspense: where it actually stands

Let's be honest about this, because it's a place candidates get caught pretending.

Suspense for code has been stable and boring since React 16.6. Suspense for data took much longer, because the hard part isn't suspending — it's the cache. If a component fetches during render and suspends, and React retries the render, it must not fetch again. You need something that remembers "I already started this request" across render attempts. React deliberately did not ship that cache.

So the honest state of things today:

  • Frameworks do it. Next.js (App Router), Remix/React Router, and friends provide the caching layer and wire Suspense up for you. In a React Server Components setup you write an async server component and it just works.
  • Data libraries do it. React Query (useSuspenseQuery), SWR (suspense: true), Relay, Apollo — they own the cache, so they can safely suspend.
  • The use hook (React 19) is the official primitive: const user = use(userPromise) reads a promise and suspends if it's pending. Unlike other hooks it can be called conditionally, inside if blocks and loops. But note what it doesn't do — it does not create or cache the promise. The promise has to be created somewhere stable (a server component, a cache, a framework loader). Creating it inline during render still gives you an infinite loop.
  • Rolling your own — a hand-written throw-a-promise cache — is a fun exercise and a bad production decision.

The interview-safe framing: "Suspense for code splitting is stable and I use it every day. Suspense for data is stable as a mechanism, but React doesn't ship a cache, so in practice you get it through a framework or a data library rather than writing it yourself."

7. Streaming SSR & selective hydration

Conceptual level, but these two terms come up and you want to be able to hold a conversation.

Quick grounding first, in case it's fuzzy. Server-side rendering means the server runs your components and sends real HTML, so the user sees content before any JavaScript loads. Hydration is what happens next on the client: React walks that server-rendered HTML, matches it to the component tree, and attaches the event handlers and state — turning static markup into a working app. Josh's line for it is watering the dry HTML with the water of interactivity.

Classic SSR had two hard stalls, and they're both all-or-nothing:

  1. The server can't send anything until it has everything. One slow database query for the comments section, and the entire HTML document waits.
  2. The client can't hydrate anything until all the JS has loaded, and it hydrates in one uninterruptible pass. During that pass, the page is visible but dead — you can click and nothing happens.

Streaming SSR: send HTML in pieces

With renderToPipeableStream, the server sends the shell immediately, with a placeholder wherever there's a Suspense boundary whose data isn't ready:

<main>
  <h1>Product page</h1>         <!-- sent at 30ms -->
  <div id="B:0"><Skeleton/></div> <!-- the fallback, sent at 30ms -->
</main>
<!-- ...connection stays open... -->
<template id="S:0"><Reviews/></template>  <!-- arrives at 900ms -->
<script>$RC("B:0","S:0")</script>          <!-- tiny inline script swaps them -->

The connection stays open. When the slow data resolves, the server renders that boundary and pushes the real HTML down the same response, plus a few bytes of inline script that swap the placeholder for the real thing. Your <Suspense> boundaries are the streaming chunk boundaries — the same tags that control client loading states control what the server can send early. One concept, two payoffs.

Selective hydration: hydrate in pieces, in the right order

The client side of the same idea, and it does two distinct things:

One: React no longer needs all the JavaScript before it hydrates anything. Content inside a Suspense boundary can hydrate independently as its code arrives. The header becomes interactive while the comments are still downloading.

Two — and this is the part that makes interviewers nod: React watches where the user interacts. If you click a button inside a boundary that hasn't hydrated yet, React reprioritises: it hydrates that boundary first, ahead of everything else in the queue, then replays your click so it isn't lost.

The analogy: hydration used to be a plumber who insists on connecting every tap in the building before turning the water on. Selective hydration is a plumber who connects taps one at a time — and if you walk over and turn a handle, they come do that tap next.

Note the dependency chain, since it's the elegant bit: all of this is possible because rendering is interruptible. Hydration is a render. If React couldn't pause a render partway through, it couldn't abandon hydrating the footer to go hydrate the button you just clicked. Concurrent rendering is the foundation; streaming and selective hydration are what got built on it.

8. Error boundaries

Let's break something. What do you think happens here?

function UserBadge({ user }) {
  return <span>{user.name.toUpperCase()}</span>;  // user.name is null
}

Your instinct is probably "that little badge doesn't render, and the rest of the page is fine." Reasonable. It's also wrong.

Since React 16, an uncaught error during render unmounts the entire component tree. Not the badge — the whole app. The user gets a blank white page.

That sounds brutal, and it was a deliberate decision. The React team's reasoning: a component that threw mid-render has left the UI in an unknown, partially-updated state. For a banking app, showing a corrupted UI that says the wrong balance is worse than showing nothing. So the default is to bail out completely — and to give you a tool to catch it before it gets that far.

What an error boundary is

A component that catches errors thrown anywhere in the tree beneath it and renders a fallback instead of crashing the app. It's try/catch, for a subtree of your UI.

class ErrorBoundary extends React.Component {
  state = { error: null };

  static getDerivedStateFromError(error) {
    return { error };                        // 👈 render the fallback
  }

  componentDidCatch(error, errorInfo) {
    logToSentry(error, errorInfo.componentStack);  // 👈 side effects go here
  }

  render() {
    if (this.state.error) return this.props.fallback;
    return this.props.children;
  }
}

Two methods, two jobs, and interviewers do ask why there are two:

  • getDerivedStateFromError runs during the render phase. It must be pure — no logging, no network calls, no side effects at all. Its only job is to return new state so the fallback renders. It's pure because the render phase can be run more than once, or thrown away, thanks to concurrent rendering.
  • componentDidCatch runs during the commit phase, after the DOM has been updated. Side effects are safe here, so this is where error reporting goes. It receives errorInfo.componentStack — the React component stack, which is far more useful for debugging than the JS stack trace.

The four things error boundaries do NOT catch

This is a favourite follow-up, so let's make it stick. The unifying principle: error boundaries only catch errors that happen while React is rendering, in the subtree below them. If React isn't the one running your code, React can't catch what it throws.

Not caughtWhyWhat to do instead
Event handlers An onClick runs long after render, triggered by the browser. React is not on the stack. A plain try/catch inside the handler.
Async code — setTimeout, promises, fetch, requestAnimationFrame Callback runs in a later task with a fresh stack. React's try/catch unwound long ago. try/catch with async/await, or .catch(). Or store the error in state and re-throw it during render.
Server-side rendering There's no mounting, no commit phase, no re-render to swap in a fallback. (Streaming SSR does handle errors, but through the stream API, not this.) Handle errors in your SSR entry / framework error handling.
Errors in the boundary itself A try/catch can't catch an error thrown by its own catch block. If your fallback UI throws, there's nothing left to save it. Nest a second boundary above it. Keep fallback UI dead simple — no data access, no fetching.

The trick for remembering the third one is that it's the odd one out — the first two are about when the code runs, and SSR is about where. Say the principle first, then the list, and it sounds like understanding rather than memorisation.

How do you catch an error in an event handler, then?

Two answers, and the second one is the good one.

The obvious one 
async function handleSubmit() {
  try {
    await saveOrder(cart);
  } catch (err) {
    setSaveError(err);   // show an inline message
  }
}
✅ Route it back into the boundary 
const [error, setError] = useState(null);
if (error) throw error;   // 👈 now thrown DURING render — boundary catches it

async function handleSubmit() {
  try {
    await saveOrder(cart);
  } catch (err) {
    setError(err);
  }
}

Catch the async error yourself, park it in state, and re-throw it during the next render. Now it's a render-phase error, so the boundary sees it and you get one consistent error path instead of two. This is exactly what react-error-boundary's useErrorBoundary().showBoundary(err) does, and mentioning that pattern unprompted is a strong signal.

Why are error boundaries still class components?

Because there is no hook equivalent — getDerivedStateFromError and componentDidCatch have never been ported. That's the honest one-line answer, and the follow-up they want is why not.

The reason is that a hook runs inside the component that calls it. An error boundary has to intercept an error thrown while React is rendering some descendant — code that runs after the boundary's own function has already returned. Hooks have no vocabulary for "wrap my children's rendering in a try/catch"; that's a lifecycle capability, not a state capability. React has said a hook version is wanted, but it needs a genuinely new API shape, so it keeps not shipping.

In practice nobody writes the class. You install react-error-boundary, which gives you a component with onError, onReset, resetKeys, a FallbackComponent that receives resetErrorBoundary, and the useErrorBoundary hook above. Saying "still class-only, so I use react-error-boundary" is the expected senior answer — the person asking is checking that you know the constraint, not that you enjoy writing classes.

Under the hood

React 18 added root-level hooks for observability that people forget: createRoot(container, { onCaughtError, onUncaughtError, onRecoverableError }). onCaughtError fires for errors a boundary handled, onUncaughtError for ones that crashed the app, and onRecoverableError for things React recovered from itself (most famously hydration mismatches). These are for logging every error app-wide — they don't replace boundaries, which are what actually renders a fallback.

Where to put them

Placement is a design decision, and this is where the question separates people who've shipped from people who've read the docs.

  • Top-level, one per app. The safety net. Full-page "something went wrong, reload" screen. You always want this one — it's the difference between a white screen and an apology.
  • Per route. A crash in /settings shouldn't take down the nav, and the user can click away to somewhere that works.
  • Around independently-failing widgets. The recommendation carousel, the third-party embed, the analytics chart. If it dies, the rest of the page shrugs and carries on.

Granularity has the same tradeoff as Suspense boundaries, incidentally: too coarse and one bad widget nukes the page; too fine and your app becomes a mosaic of tiny error messages. The question to ask is "if this subtree vanished, would the page still be worth looking at?" If yes, it's a boundary.

For recovery: the fallback should offer a way out — a retry button that resets the boundary's state so it re-renders children. react-error-boundary's resetKeys handles the common case automatically, resetting whenever a value like the route or user ID changes, because that error probably doesn't apply to the new context. And do wire up reporting — componentDidCatch / onError to Sentry or similar, with the component stack. An error boundary that silently swallows failures is worse than a crash, because now you don't know it's happening.

9. Portals

Time for a very specific, very annoying CSS problem.

You build a modal. It lives inside a card component, deep in the tree. It has position: fixed, a big z-index, the works. And it renders… clipped in half, trapped inside the card, or underneath the sticky header.

Two CSS mechanics cause this, and neither is React's fault:

  • overflow: hidden on an ancestor. Anything that overflows that ancestor's box gets cut off. Your modal is bigger than the card, so it's clipped.
  • Stacking contexts. If any ancestor has transform, filter, opacity below 1, or its own z-index with positioning, it creates a new stacking context. Your modal's z-index: 9999 is then only "9999 within that ancestor" — the whole ancestor still sits below the header. This is why bumping the z-index never works, and it's the moment most developers discover stacking contexts exist.

The DOM fix is obvious: put the modal at the end of <body>, where no ancestor can clip or trap it. But then it's not a child of your card anymore, so how does it get the card's props, context, and state?

That's the trick a portal performs. The element gets rendered into a different DOM node, while staying exactly where it is in the React tree.

import { createPortal } from 'react-dom';

function Modal({ onClose, children }) {
  return createPortal(
    <div className="backdrop" onClick={onClose}>
      <div className="dialog">{children}</div>
    </div>,
    document.body            // 👈 where in the DOM it lands
  );
}

The analogy: a portal is mail forwarding. You've moved to a new address (the DOM node), so physical letters arrive there. But you're still on your family's contact list — you still get invited to the reunion, still inherit the family recipes, still get called when there's news. Your relationships didn't move; only your street address did.

Why do portal events bubble to the React parent?

This is the portal question. Setup: your Card has an onClick. Your modal is portalled to document.body. You click a button inside the modal. Does Card's handler fire?

Take a guess before reading on. The DOM says no — div.backdrop is not inside div.card, so a real DOM event bubbling up from the button will never pass through the card.

But it fires. Yes, really.

Here's why. React doesn't attach an onClick listener to your button. It attaches a small number of listeners at the root container, waits for real DOM events to bubble up there, and then synthesises the propagation itself. And when React builds the list of handlers to call, it walks up the fiber tree — its own internal component tree — not the DOM tree.

In the fiber tree, Modal is still a child of Card. So Card's onClick is on the path, and it gets called. React also attaches a listener to the portal's container node so events originating outside the root container still reach the system in the first place.

And this is correct, not a quirk. It's the entire point of the feature. Portals exist so a component can escape CSS constraints without escaping its component relationships. If events followed the DOM tree, a portalled modal would silently lose context-like behaviour — and everything you write would need to know whether its children happened to be portalled. Consistency with the React tree is what makes portals composable.

Wait, what about… my "click outside to close" handler?

Excellent instinct, and here's the sharp edge. The DOM event also genuinely bubbles through the real DOM. So if you attached a native listener with document.addEventListener('click', closeDropdown), clicks inside your portalled dropdown will hit document and close it instantly.

So you get both propagation paths at once: React handlers follow the React tree, native listeners follow the DOM tree. When they disagree, that's your bug. The usual fixes are to check ref.current.contains(e.target) before closing, or to listen on the root container rather than document.

What portals don't do for you

A portal solves exactly one problem: DOM placement. It does not make your modal accessible — and a senior interview often goes here next. The missing pieces are a focus trap (focus moves in, Tab cycles inside), focus restoration on close, role="dialog" + aria-modal + a label so a screen reader announces it, making the background inert, and Esc-to-close plus scroll lock.

That's a lot, which is why "just use Radix / React Aria / Headless UI" is the right production answer. Have this line ready: "createPortal fixes the CSS problem. The accessibility problem is separate and much larger, so I'd reach for a headless dialog primitive rather than hand-rolling a focus trap."

Same reasoning covers tooltips, dropdowns, and toasts — anything floating that a scrollable or transformed ancestor would otherwise clip.

10. HOCs and render props

These are legacy. You will still get asked, for two reasons: the interviewer wants to know if you understand why hooks exist, and half the codebases you'd join still contain them.

So let's go back to 2017, before hooks. You have this problem: three different components each need to know the current user, and each needs to redirect to login if there isn't one. The logic is identical. How do you share it?

Not with a regular function — the logic involves state and lifecycle, and in a class component those live in this.state and componentDidMount. You can't pull them out into a plain helper. And this was genuinely the biggest unsolved problem in React at the time. Two answers emerged.

Answer 1: the higher-order component

A function that takes a component and returns a new component that wraps it, injecting extra props.

function withAuth(WrappedComponent) {
  return function WithAuth(props) {
    const [user, setUser] = useState(null);
    const [loading, setLoading] = useState(true);

    useEffect(() => {
      fetchCurrentUser().then(u => { setUser(u); setLoading(false); });
    }, []);

    if (loading) return <Spinner />;
    if (!user) return <Redirect to="/login" />;
    return <WrappedComponent {...props} user={user} />;  // 👈 inject
  };
}

const Dashboard = withAuth(RawDashboard);

The analogy: HOCs are gift wrapping. The present inside is unchanged; you've added a layer around it that carries extra information. And like gift wrapping, one layer is charming and five layers is a nuisance.

The problems, which are why we don't do this anymore:

  • Wrapper hell. Real components accumulated them: withRouter(withTheme(withAuth(connect(mapState)(Dashboard)))). Your React DevTools tree becomes a ten-deep tower of WithX components around one real one. Debugging is miserable.
  • Prop collisions. withAuth gives you a user prop. So does withProfile. One silently overwrites the other, depending on composition order, and nothing warns you. Static typing helps but doesn't eliminate it.
  • You can't see where props come from. Open RawDashboard, see it uses props.user — where's that from? Not from the parent in JSX. You have to go find the HOC chain.
  • Plumbing you have to remember. Static methods aren't copied across. Refs don't pass through without forwardRef. Display names need setting manually or DevTools shows Unknown.

Answer 2: the render prop

Same problem, opposite shape. Instead of wrapping a component, you pass a function as a prop (usually children) and call it with the data.

function Auth({ children }) {
  const [user, setUser] = useState(null);
  const [loading, setLoading] = useState(true);

  useEffect(() => {
    fetchCurrentUser().then(u => { setUser(u); setLoading(false); });
  }, []);

  if (loading) return <Spinner />;
  if (!user) return <Redirect to="/login" />;
  return children(user);          // 👈 children is a FUNCTION
}

// used like:
<Auth>{user => <Dashboard user={user} />}</Auth>

This fixed real things. No prop collisions — you name the argument yourself. Totally explicit about where user comes from; it's right there in the JSX. Dynamic, since you decide at call time what to render.

But it introduced its own misery: the pyramid. Need three of them?

<Auth>{user =>
  <Theme>{theme =>
    <Router>{router =>
      <Dashboard user={user} theme={theme} route={router.path} />
    }</Router>
  }</Theme>
}</Auth>

Callback hell, wearing a JSX costume. Your indentation grows with your dependencies, and there's no way to use one value in a condition outside the JSX tree without more contortions.

Answer 3 (2019): the hook

function useAuth() {
  const [user, setUser] = useState(null);
  const [loading, setLoading] = useState(true);

  useEffect(() => {
    fetchCurrentUser().then(u => { setUser(u); setLoading(false); });
  }, []);

  return { user, loading };
}

function Dashboard() {
  const { user, loading } = useAuth();     // 👈 explicit, flat, renameable
  const theme = useTheme();
  const route = useRoute();

  if (loading) return <Spinner />;
  if (!user) return <Redirect to="/login" />;
  return <h1>Hi {user.name}</h1>;
}

Look at what happened. Three shared behaviours, three lines, zero nesting. No collision — useAuth() returns a value and you name it, so two hooks returning user is a non-issue. No mystery props — you can see the source of every value on the line where it's defined. No extra components in the tree at all: hooks add zero nodes, which is why the DevTools tree finally became readable again.

That's the story to tell if you're asked "why did hooks happen?" Both older patterns worked around the same limitation — stateful logic could only live in a component — by creating extra components. Hooks removed the limitation instead of working around it. Everything else about hooks follows from that.

In an interview

Bonus point if you name the fourth pattern: mixins, from React.createClass, the pre-2016 answer. They were removed because mixins could silently stomp on each other's state, and you couldn't tell which mixin owned which method. The React team's blog post "Mixins Considered Harmful" is what motivated HOCs in the first place. Every pattern in this section is an attempt at the same problem, and the arc — mixins → HOCs → render props → hooks — is a very satisfying 90-second answer.

When would you still write an HOC?

Not "never" — and "never" is the answer that gets you a follow-up. There are cases where hooks genuinely can't help, because they can only run inside a component, and sometimes you need to change something about a component from the outside.

  • You use them daily already. React.memo(Component) is an HOC. So is forwardRef, and connect() from react-redux.
  • Wrapping a subtree in structure it can't wrap itself in. withErrorBoundary(Widget) — by the time a hook runs, the component is already rendering, so it can't put a boundary around itself. Same for deciding not to render the component at all.
  • Feeding a class component. Classes can't call hooks, so an HOC is the only route — including for error boundaries, which are still classes.

The crisp version: use a hook when you're sharing logic; use an HOC when you're wrapping the component in structure it can't wrap itself in.

Render props, meanwhile, aren't fully dead either — they're just narrower. Any time the shared thing includes JSX rather than only data, the pattern reappears: virtualised list libraries call you back per row, <Formik>-style form libraries hand you field state, and the modern descendant is the "children as a function" API you see in headless component libraries. Same idea, better taste about when to use it.

11. Model answers

Say these out loud once. They're written for speaking, not reading.

Model answer — concurrent rendering

"Before React 18, rendering was one synchronous, uninterruptible pass — once React started walking the tree, the browser couldn't paint or handle input until it finished. So a heavy render would visibly freeze the input box. Concurrent rendering means React can start a render, yield back to the browser to handle something urgent, and then resume or throw the partial work away. It's all still one thread — this is prioritisation, not parallelism. The way you use it is by telling React which updates are urgent, like typing, and which are transitions, like re-filtering a big list."

Why it lands: it starts from the problem rather than the API, it explicitly kills the multithreading misconception before they can ask, and it ends on the practical hook — which invites the natural useTransition follow-up on your terms.

Model answer — Suspense

"Suspense is a boundary that catches 'not ready yet' from anywhere in its subtree, the same way an error boundary catches errors. A component suspends by signalling that it's waiting on a promise — internally it throws one — and React renders the nearest boundary's fallback until that resolves, then retries. The everyday use is React.lazy for code splitting. For data, the mechanism is stable but React doesn't ship a cache, so in practice you get it through a framework or a library like React Query. On the server, the same boundaries are also the streaming chunks — the shell goes out immediately and slow sections stream in later."

Why it lands: it defines Suspense by its mechanism, not its syntax, and the honest note about the missing cache signals you've actually built with it rather than read the announcement post.

Model answer — error boundaries

"An error boundary is a component that catches errors thrown during rendering, in lifecycle methods, and in constructors anywhere below it, and renders a fallback instead of letting the whole app unmount. The rule for what it doesn't catch is simple: if React isn't on the stack, React can't catch it — so event handlers, anything async like setTimeout or a promise, server-side rendering, and errors thrown by the boundary itself. It has to be a class because there's still no hook version of getDerivedStateFromError, so in practice I use react-error-boundary. For async errors I catch them myself, put them in state, and re-throw during render so they land in the same boundary."

Why it lands: the four exclusions are the follow-up they were already planning, and giving the principle before the list shows understanding. The re-throw pattern is the detail that reads as production experience.

12. Remaining follow-ups

Click to reveal. Try to answer each before you open it.

Does concurrent React make my app faster?

No — usually marginally slower in total work. Interruption has overhead, and abandoned renders are wasted computation. What it improves is perceived performance: the urgent work stops being stuck behind the slow work. If your render is slow because of an O(n²) loop, concurrency won't save you; fix the loop. Concurrency is a scheduling tool, not an optimisation.

How does React actually yield to the browser mid-render?

It renders in small units of work (one fiber at a time) and checks a deadline — roughly every 5ms — asking "should I yield?" If yes, it stops, schedules a continuation via a task (MessageChannel is the mechanism the scheduler uses), and lets the browser process input and paint. Then it picks up where it left off. This is why it's called "time slicing." Note it only works during the render phase — the commit phase, where React actually mutates the DOM, is still synchronous and uninterruptible, because a partially-committed DOM would be visibly broken.

Do I have to opt into concurrent features?

You opt into the concurrent renderer by using createRoot instead of the old ReactDOM.render — that alone gives you automatic batching and makes concurrent features available. But no update is treated as a transition until you mark it, so an app that just switches to createRoot behaves almost identically. There's no "concurrent mode" switch anymore; that was the old, abandoned framing. It's "concurrent features", adopted one at a time.

Can I put a Suspense boundary anywhere?

Anywhere above the suspending component. The one that surprises people: a boundary doesn't catch a component that suspends if you place the boundary in the same component that suspends — it has to be an ancestor in the tree. Also, if there's no boundary at all, the suspension propagates to the root and you get an error telling you a component suspended while no fallback was shown. And a boundary you add inside the lazy component's own module won't help it load, since that module isn't there yet.

What happens to state inside a Suspense boundary when it re-suspends?

This is a nice depth question. When an already-visible boundary suspends again (say a filter change triggers a new fetch), React hides the existing DOM with display: none rather than unmounting it, and shows the fallback. State is preserved, so when it un-suspends you get your scroll position and inputs back. If you'd rather avoid the fallback flash entirely on a subsequent update, wrap the update in startTransition — React then keeps showing the old content while the new content loads. That's the same "stale while revalidating" feel as useDeferredValue, and it's not a coincidence.

Why does React unmount the whole tree on an uncaught error instead of just that component?

Because a component that threw mid-render left React unable to know what the correct UI is. Rendering the rest of the tree around a hole risks showing something wrong — the classic example being a payments or banking UI displaying a stale or partial value. The React team judged that a blank screen is a loud, visible failure, whereas a subtly corrupted UI is a silent one. The whole point is to make you add boundaries where you've decided a partial failure is acceptable.

Can an error boundary catch errors from a component inside a portal?

Yes. Everything about a portal follows the React tree, and error boundaries operate on the React tree. So a boundary above the component that calls createPortal catches errors thrown inside the portalled content, even though that content lives elsewhere in the DOM. Same for context, same for Suspense. If you can state that as a general rule — "portals move the DOM node, nothing else" — you've answered three questions at once.

Can I render a portal into a node that doesn't exist yet?

No — createPortal needs a real DOM node at the moment it renders. If you do document.getElementById('modal-root') and that div isn't in your HTML, you get null and a crash. Two common fixes: put a permanent <div id="modal-root"></div> in index.html, or create the node in an effect and render null on the first pass. Watch out with SSR too: document doesn't exist on the server, so portal code needs to be client-only or effect-guarded.

Isn't useDeferredValue just a debounce?

No, and it's a better answer than "yes, sort of." A debounce waits a fixed number of milliseconds regardless of how fast the device is — on a fast machine you've added pointless delay; on a slow one 300ms still isn't enough. useDeferredValue has no timer at all. It starts immediately and adapts to the actual machine: if the render finishes in 10ms the value updates in 10ms. It's also interruptible, so a fast typist never queues up work. Different tool, different mechanism, similar-looking result.

If hooks replaced HOCs, why does React.memo still exist as one?

Because memo changes something about the component from the outside — whether React bothers to call it at all. A hook runs inside the component, which means by the time a hook could run, the re-render already happened; it's too late to skip it. That's the general dividing line: hooks share logic that runs during a render, HOCs change the rules around the render. forwardRef is the same story — though React 19 makes ref a normal prop, so that particular HOC is on its way out.

What's the difference between a render prop and just passing children?

Plain children is JSX the parent renders as-is; it can't receive anything from the parent. A render prop is a function, so the parent can call it with values only the parent knows — the current user, a row index, the open/closed state. The one-line distinction: children is a value, a render prop is a function of a value. And the pattern is not dead, just narrow — it's still the right tool whenever the shared thing is "how to render each item", not just "here's some data."

What's the difference between hydration and selective hydration, in one line each?

Hydration: React attaches event handlers and state to server-rendered HTML so it becomes interactive. Selective hydration: React does that per Suspense boundary rather than all at once, and reprioritises to hydrate whichever boundary the user just interacted with — replaying the event so the click isn't lost.
