Props, State, Controlled Components & Data Flow

How data actually moves through a React app — and the six or seven bugs that come from getting it slightly wrong.

I want to start with a bug. Not a definition — a bug. Because this particular bug has bitten literally every React developer I know, including me, more than once, and it sits exactly on the fault line between the two ideas this whole guide is about.

Here's a tiny component. It shows a user's display name in an editable text box:

EditName.jsx 
function EditName({ user }) {
  const [name, setName] = useState(user.name); // 👈 keep an eye on this

  return (
    <input
      value={name}
      onChange={(event) => setName(event.target.value)}
    />
  );
}

Looks completely reasonable, right? We take the name that was handed to us, put it in a piece of state so the user can edit it, and wire it up to an input.

Now the parent switches which user we're editing. It was showing Ada, now it's showing Grace. The parent re-renders, passes down user = { name: "Grace" }, and…

The input still says Ada.

Take a second with that. It's not a typo, it's not a stale cache, it's not a missing await. React did exactly what it was told. And if you can explain why — really explain it, not just recite "useState only reads its argument once" — then you understand the props/state boundary better than a lot of people who've been shipping React for years.

We're going to build up to that answer properly. By the end of this guide you'll have a mental model that makes that bug obvious in hindsight, plus the whole surrounding territory: controlled inputs, lifting state up, prop drilling and how to dodge it without Context, and how all the old class lifecycle methods map onto hooks (and why that map is a bit of a lie).

Section 1First, what a component actually is

I promised to assume nothing, so let's spend ninety seconds here. If this is old news, skim — but don't skip, because the framing I'm about to use is the one everything else in this guide rests on.

A React component is a function that takes an object and returns a description of some UI. That's it. That's the whole thing.

A component is a function 
function Greeting(props) {
  return <h1>Hello, {props.name}!</h1>;
}

// When you write this in JSX...
<Greeting name="Ada" />

// ...React essentially does this:
Greeting({ name: "Ada" });
// → a description of <h1>Hello, Ada!</h1>

Two things to notice, and they matter a lot later.

First: the thing you write between angle brackets — name="Ada" — becomes a property on a plain object that gets passed in as the function's argument. That object is props. "Props" is just short for properties, and it is genuinely, boringly, an ordinary JavaScript object. There's no magic in it.

Second: the component doesn't return DOM. It returns a description of DOM — a lightweight object tree that React then compares against what's on screen and uses to make the minimum set of real DOM changes. When people say a component "renders," they mean React called the function again to get a fresh description.

And React calls it again a lot. Every time a prop changes, every time state changes, every time a parent re-renders. Your component function is not a one-time setup script; it's a thing that gets run over and over, and each run is a fresh, independent function call with its own local variables.

Under the hood

If your component function runs top-to-bottom on every render, and its local variables are wiped each time — how does useState remember anything? The answer is that the value doesn't live in the function. It lives in a data structure React keeps outside your component, attached to that component's position in the tree. useState is a lookup into that structure. That's also why the rules of hooks exist (same hooks, same order, every render) — React matches your hook calls to its stored slots by call order.

Section 2Props vs state — the real distinction

Here's the sentence you'll see in every tutorial: "Props are passed in from the parent; state is managed inside the component." That's true, and it's also nearly useless, because it describes the plumbing rather than the meaning.

Let me give you the framing I actually use.

The analogy: a vending machine

Think of a component as a vending machine.

Props are the coins you push into the slot. They come from outside. The machine can read them, count them, react to them — but it cannot reach into your wallet and change how much money you have. And the machine doesn't decide when it gets coins; you do.

State is what's inside the machine. The current stock levels. Whether the "sold out" light is on. How much change is loaded. That belongs to the machine, the machine changes it as things happen, and nobody outside can reach in and adjust it directly — they can only push coins (props) or press buttons (events).

The analogy isn't perfect: a real vending machine hangs onto coins forever, whereas a component's props are handed to it fresh on every single render — more like the coins evaporating and being re-inserted each time you look at the machine. But the ownership part is exactly right, and ownership is the whole game.

So the crisp version:

Props are arguments. State is memory.
Props are owned by whoever rendered you. State is owned by you.

"Read-only" — what that really means

You'll hear "props are read-only" or "props are immutable." Let's be precise, because interviewers poke at this.

React does not freeze the props object in production. If you write props.user.name = "Grace", JavaScript will happily do it. Nothing throws. So what does read-only actually mean?

It means: mutating props is a broken thing to do, and React will not help you. Three reasons:

  1. It won't re-render anything. React only schedules a re-render when you call a state setter (or a couple of other specific triggers). Mutating an object doesn't notify anyone. Your screen goes stale.
  2. You just corrupted the parent's data. That object is the parent's object. You were handed a reference to it, not a copy. Editing it is like a house guest reorganising your kitchen — the change is real, and you didn't ask for it.
  3. The next render overwrites you anyway. The parent re-renders, builds props again from its source of truth, and hands them down. Whatever you scribbled on gets replaced.

Notice how weak the reassignment case is too. props.name = "Grace" inside the function body only changes a local object for the remainder of this one function call. Next render, brand new props object, brand new call. Your edit is gone. Props are effectively write-once-per-render from above.

In an interview

"Can a child modify its props?" — This is a recall question with a depth trap sitting under it. The bad answer is just "no, props are immutable." The good answer is: "Not meaningfully. JavaScript won't stop you from mutating the object, but React won't re-render, you'd be mutating data the parent owns, and the parent will overwrite it on its next render. If a child needs to change something, it calls a function the parent passed down — the parent changes its own state and the new value flows back down as a prop." That last sentence is the one that shows you understand the model rather than the rule.

State: memory that survives between renders

Because a component function runs from scratch every render, ordinary variables are useless for remembering things:

❌ Buggy — this counter never counts 
function Counter() {
  let count = 0; // 👈 reset to 0 on every single render

  return (
    <button onClick={() => { count = count + 1; }}>
      Clicked {count} times
    </button>
  );
}
// → always renders "Clicked 0 times"

Two separate failures here, and it's worth naming both: the value doesn't persist across renders, and changing it doesn't trigger a render. useState fixes both at once.

✅ Fixed 
function Counter() {
  const [count, setCount] = useState(0);

  return (
    <button onClick={() => setCount(count + 1)}>
      Clicked {count} times
    </button>
  );
}

That's the two-part job description of state, and it's a genuinely good thing to be able to say out loud: state persists across renders, and updating it schedules a render. A value that needs only the first of those (persistence, but no re-render) wants a ref, not state — we'll come back to that in the decision procedure.

Section 3"Should this be state?" — a decision procedure

Most React messes I've cleaned up come from the same root cause: too much state. People reach for useState reflexively, and every extra piece of state is another thing that can get out of sync with the others.

So here's a checklist. Run a candidate value through it in order. The first "yes" tells you the answer.

Let me walk each one, because each corresponds to a real class of bug.

Question 1: can I just calculate it?

If a value is a pure function of props or other state, it should not be state. Compute it during render.

❌ Buggy 
const [items, setItems] = useState([]);
const [total, setTotal] = useState(0);

function addItem(item) {
  setItems([...items, item]);
  setTotal(total + item.price);
  // 👆 two sources of truth,
  //    one forgotten call away
  //    from disagreeing
}
✅ Fixed 
const [items, setItems] = useState([]);

const total = items.reduce(
  (sum, item) => sum + item.price,
  0
);
// 👆 can never be wrong.
//    Recalculated every render.

"But isn't recalculating on every render slow?" Almost never. Summing a shopping cart is nanoseconds. If you genuinely measure a hot, expensive calculation, useMemo exists for exactly that — and notice that useMemo caches a derived value, it doesn't turn it into state. The source of truth stays singular.

Question 2: does it ever change?

If it's the same forever, it's a constant. Move it outside the component so it isn't re-created each render:

Constants live outside 
const SORT_OPTIONS = ["newest", "price", "rating"]; // 👈 outside

function ProductList() {
  // ...
}

The subtler version: a value that must persist across renders and can change, but that no visible output depends on. A setInterval ID. A previous scroll position. A "have I already fired the analytics event?" flag. Those want useRef, because a ref persists but doesn't trigger a re-render when you change it.

That gives us a clean three-way split, which is a nice thing to be able to rattle off:

NeedPersists across renders?Triggers re-render?Use
Scratch value for this renderNo—plain const
Remember, but nothing on screen depends on itYesNouseRef
Remember, and the UI shows itYesYesuseState

Question 3: does someone else need it?

If a sibling needs to read the value, it can't live in your component — siblings have no way to see into each other. It has to move up to a shared ancestor. That's "lifting state up," and it gets its own section shortly.

Section 4Derived state, and the bug from the intro

"Derived state" is the name for the antipattern in Question 1: copying or computing a value into state when it could have been read or calculated directly. The classic form is copying a prop into state.

Now let's go back to that opening bug, because we finally have the tools to dismantle it.

❌ Buggy — the input won't update when `user` changes 
function EditName({ user }) {
  const [name, setName] = useState(user.name);
  return <input value={name} onChange={(e) => setName(e.target.value)} />;
}

Why doesn't it update? Because of what the argument to useState actually is. It is not a binding. It is not a subscription. It's an initial value — used exactly once, on the very first render of this component instance, to seed the state slot React keeps for it. On every render after that, React looks in the slot, finds a value already there, and ignores the argument entirely.

So on render #1, user.name is "Ada", the slot gets seeded with "Ada". On render #7, the parent passes user.name === "Grace", React looks in the slot, sees "Ada" sitting there, shrugs, and hands you "Ada". The expression user.name is still evaluated — JavaScript has to evaluate arguments before calling a function — but its result is thrown away.

An analogy that makes this stick: useState(user.name) is like writing your name on a nametag when you arrive at a conference. Someone changing your name in the attendee database later doesn't rewrite your nametag. The nametag was a snapshot at the door.

A common misconception

"React must not have noticed the prop changed." React noticed perfectly well — the component re-rendered, that's why you're seeing this at all. The prop is the new value inside the function. It's the state that's stale, because state's whole job is to survive re-renders. This is state doing exactly what state does. The bug is that we asked state to do a prop's job.

So what's the fix?

There are three, and picking the right one is a great signal in an interview because it shows you're thinking about ownership rather than reaching for a patch.

Fix 1 — don't copy it at all. If the component doesn't truly need independent local memory, just use the prop. Boring, and correct more often than people expect.

Fix 2 — lift the state to the parent. If the edited name matters to anyone outside this component (it usually does — you're going to save it), the parent should own it and pass down value and onChange. Now there's one source of truth and no copy to go stale.

✅ Fixed — parent owns it 
function EditName({ name, onNameChange }) {
  return <input value={name} onChange={(e) => onNameChange(e.target.value)} />;
}

Fix 3 — the key trick. Sometimes the local state genuinely is local (a draft that's meaningless until submitted), and what you actually want is: when the user changes, throw this component away and start fresh. React has a built-in way to say that.

✅ Fixed — reset by changing the key 
<EditName key={user.id} user={user} />
{/* 👆 different id → React unmounts the old instance
       and mounts a brand new one, with brand new state */}

This deserves a proper explanation, because "use a key" sounds like folklore until you know the mechanism. React identifies elements by their position in the tree plus their key. When it re-renders and finds a different key in the same position, it doesn't try to update the existing component — it concludes this is a different component, unmounts the old one (destroying its state and running cleanup) and mounts a fresh one. The state resets not because key is a "reset" feature, but because you gave React a brand new component instance. It's the same mechanism you already use in lists, pointed at a different problem.

Wait, what about — isn't there a hooks way?

There is, and the React docs mention it, but it's the last resort: adjust state during render by tracking the previous prop in another piece of state, and calling the setter directly in the render body when it differs. React handles this specially — it re-runs the component immediately, before touching the DOM. It works, it's rarely the clearest option, and I'd only bring it up in an interview as "and there's an adjust-during-render escape hatch if you only want to reset part of the state, but I'd try key first." Saying that shows range without looking like you'd actually reach for it.

Trap

The instinct almost everyone has first is useEffect(() => setName(user.name), [user]). Please don't. It renders once with the stale value, paints that to the screen, then immediately renders again with the right value — a visible flash on slow devices, plus an extra render every time. React docs explicitly call this out. If you propose it in an interview, expect "can we do that without an effect?" as the follow-up, so get ahead of it.

Model answer — "Why is derived state an antipattern?"

"Because it creates a second source of truth that can drift out of sync with the first. If I copy a prop into state with useState(props.value), that argument is only an initial value — React ignores it on every subsequent render — so when the prop changes, my state keeps the old value and the UI is stale. The fix depends on ownership: if it's just calculable, calculate it during render; if the parent needs it, lift it up and pass value plus a change handler; and if I genuinely want the local state to reset when the prop changes, I pass a key so React remounts the component with fresh state."

Why it lands: you named the mechanism (initial-value-only), not just the symptom, and you gave three fixes indexed by who owns the data. That's an architecture answer, not a trivia answer.

Section 5Unidirectional data flow: data down, events up

Everything so far has been circling one architectural decision React made early and never wavered on: data flows in exactly one direction, downward.

A child can never reach sideways to a sibling, and it can never reach up and mutate the parent. When a child needs something to change, it calls a function the parent gave it. The parent decides what to do, updates its own state, and the new value comes back down as a prop.

The postal analogy: props are mail delivered to your address. You can read your mail. You cannot walk into the sorting office and edit the letters other people are about to receive. If you want something changed, you post a reply — a callback — and let the sender decide.

Why React chose this, and what it buys you

The alternative is two-way binding, which older frameworks leaned on heavily (AngularJS's ng-model is the famous example, and Vue's v-model is a modern, more disciplined descendant). With two-way binding you glue a variable to an input and they update each other automatically. It's genuinely lovely for about the first two weeks.

The problem is debugging. When a value is wrong, the question you always ask is "who changed this?" With one-way flow, that question has a bounded answer: find where the state lives, then look at every setX call in that one component. There is exactly one place a given value can be written. With two-way binding, anything holding a binding can write to it, so "who changed this?" becomes a search across the whole app, and you get cascades where a change in one place silently triggers a change somewhere else that triggers another. AngularJS had an actual digest cycle that looped until values stopped changing, and could throw "infinite digest" errors.

So the trade React made: more typing, radically more predictability. You write value and onChange by hand instead of one directive. In exchange, rendering becomes something close to a pure function of state, which means you can reason about the screen by reading the state, and time-travel debugging and dev tools state inspection actually work.

Wait — doesn't React have two-way binding for forms?

No, and this trips people up because controlled inputs feel two-way. But look at it closely: you pass value down, and you pass a callback that receives the typed character and calls setState yourself. It's a loop made of two one-way arrows that you wired manually. Vue's v-model is sugar that writes that loop for you; React makes you see it. Same shape, different level of visibility.

Section 6Lifting state up (and what it costs you)

Here's the situation that forces the pattern. Two siblings need the same value.

Say we're building a temperature widget. One component is a slider that sets a temperature in Celsius. Another is a panel that says whether water would boil. They're siblings.

❌ Doesn't work — the state is stuck inside one sibling 
function TemperatureInput() {
  const [celsius, setCelsius] = useState(20); // 👈 trapped in here
  return <input type="range" value={celsius}
           onChange={(e) => setCelsius(Number(e.target.value))} />;
}

function BoilingVerdict() {
  // ...how would this ever see `celsius`? It can't.
}

There is no mechanism for BoilingVerdict to peek at its sibling's state. Data flows down, not sideways. So the value has to move to somewhere that is above both of them — their closest common parent.

✅ Fixed — state lifted to the common parent 
function TemperatureWidget() {
  const [celsius, setCelsius] = useState(20); // 👈 now it lives up here

  return (
    <>
      <TemperatureInput celsius={celsius} onCelsiusChange={setCelsius} />
      <BoilingVerdict celsius={celsius} />
    </>
  );
}

function TemperatureInput({ celsius, onCelsiusChange }) {
  return <input type="range" value={celsius}
           onChange={(e) => onCelsiusChange(Number(e.target.value))} />;
}

function BoilingVerdict({ celsius }) {
  return <p>{celsius >= 100 ? "Water boils. 🔥" : "No boiling here."}</p>;
}

Read what happened to the two children: they both became controlled by their parent. Neither owns anything. They take data in and report events out. In React vocabulary they're now "presentational" or "dumb" components — and that's a compliment, because a component with no state is trivially testable and trivially reusable.

The general recipe, which is worth memorising because it's a common whiteboard question:

  1. Find the value that more than one component needs.
  2. Find their closest common ancestor.
  3. Move the useState there.
  4. Pass the value down as a prop to everyone who reads it.
  5. Pass a setter (or a handler wrapping one) down to everyone who changes it.

The costs — and yes, the interviewer wants these

"Lift state up" is the textbook answer, so the interesting question is always the follow-up: what's wrong with it? Three real costs.

1. Prop drilling. Common ancestor is right next door? Fine. Common ancestor is six levels up? Now the value has to be threaded through six components, and four of them don't care about it at all — they're just couriers. That's noisy, it makes every intermediate component's prop list a lie about what it actually does, and renaming the prop means touching seven files.

2. Re-rendering a bigger subtree. State changing re-renders the component that owns it and, by default, everything below it. Move state from a leaf to the root and a keystroke now re-renders your entire app instead of one input. Usually React is fast enough that nobody notices; on a big form or a big list, people very much notice.

Under the hood

"Re-render" means React calls those component functions again and diffs the result. It does not mean it touches the DOM — if the output is identical, no DOM changes happen. That's why most unnecessary re-renders are harmless. They stop being harmless when the subtree is large, or when a component does expensive work during render. React.memo lets a component skip re-rendering when its props are shallow-equal to last time, which is the standard mitigation — and it's exactly why passing a fresh inline arrow function as a prop can defeat memo, since a new function identity every render means props are never equal.

3. The parent accumulates responsibility it doesn't want. Lift enough things and your once-simple layout component becomes a 300-line state depot for its descendants, holding form values, modal open/closed flags and hover states that have nothing to do with each other. This is how "smart parent, dumb children" degrades into "one enormous component."

So the honest framing is: lift state as high as it needs to go, and not one level higher. The right owner is the closest common ancestor, not the top.

Section 7Composition: beating prop drilling without Context

When someone hits prop drilling, the reflex is "time for Context." And Context is a fine tool. But there's a simpler technique that solves a big chunk of drilling cases with zero new API, and forgetting it is one of the most common gaps I see. If you produce this in an interview, you'll stand out, because most candidates jump straight to Context or Redux.

The insight: props don't have to be data. They can be UI.

Let's set up the drilling problem concretely. We have a user object at the top, and a deeply nested avatar that needs it.

❌ Prop drilling — `user` passed through components that don't use it 
function App() {
  const [user, setUser] = useState(currentUser);
  return <Layout user={user} />;
}

function Layout({ user })  { return <Sidebar user={user} />; }  // doesn't use it
function Sidebar({ user }) { return <UserPanel user={user} />; } // doesn't use it
function UserPanel({ user }) { return <Avatar src={user.avatarUrl} />; } // finally!

Layout and Sidebar are pure overhead. They accept a prop, do nothing with it, and hand it on. Now watch what happens when we let App build the avatar itself and pass it as a prop.

✅ Composition — the element is created where the data lives 
function App() {
  const [user, setUser] = useState(currentUser);

  return (
    <Layout>
      <Sidebar>
        <UserPanel>
          <Avatar src={user.avatarUrl} />  {/* 👈 built right here */}
        </UserPanel>
      </Sidebar>
    </Layout>
  );
}

function Layout({ children })  { return <div className="layout">{children}</div>; }
function Sidebar({ children }) { return <aside>{children}</aside>; }
function UserPanel({ children }) { return <div className="panel">{children}</div>; }

user now appears in exactly one file. Layout and Sidebar never hear about it. They got simpler — they're now generic containers that will work with any content, forever.

How this actually works

Anything you nest between a component's opening and closing tags arrives as a prop called children. It's not special syntax; children is an ordinary prop with a reserved name, holding an already-created element.

And that's the mechanism that matters: the element is created in App, where user is in scope, and merely carried by the components in between. They're holding a sealed envelope. They don't need to know what's inside to deliver it. That's the whole trick — you moved the point of creation up to the data, instead of moving the data down to the point of creation.

Wait — what if I need two slots?

Then use regular props that happen to hold elements. There's nothing magic about the name children; any prop can hold JSX. This is often called the "slots" or "component as prop" pattern, and it's how basically every UI library builds layouts:

<PageShell
  header={<SearchBar query={query} onQueryChange={setQuery} />}
  sidebar={<FilterList filters={filters} />}
  main={<Results items={results} />}
/>

function PageShell({ header, sidebar, main }) {
  return (
    <div className="shell">
      <header>{header}</header>
      <aside>{sidebar}</aside>
      <main>{main}</main>
    </div>
  );
}

PageShell knows nothing about search, filters or results. It knows about boxes.

When composition isn't enough

Be honest about the limits — an interviewer will respect it more than an oversell.

Composition works when the data is needed at a known place in the tree that an ancestor can construct. It stops working when the consumers are many, scattered, and unpredictable — theme, current user, locale, auth. You can't reasonably hoist every button that needs the theme up into the app root. That's Context's actual job description: values that a wide, unknowable slice of the tree needs.

It also gets awkward when the child needs data the parent can't compute — for example, an item inside a list rendered by an intermediate component. Sometimes the render-prop shape (passing a function that receives the item) covers it; sometimes Context is genuinely the cleaner answer.

Model answer — "How do you avoid prop drilling without Context?"

"Usually by restructuring with composition rather than adding a new data channel. Instead of passing data down through layers that don't use it, I create the element where the data already lives and pass it down as children or as a prop — so the intermediate components just carry an opaque element and never learn about the data at all. That removes the drilling and actually makes the middle components more reusable. I'd reach for Context when the consumers are wide and scattered — theme, auth, locale — where hoisting every consumer to a common ancestor isn't realistic."

Why it lands: it shows you treat Context as a deliberate choice with a cost, not the default reaction to any inconvenience. Naming the boundary — "known place in the tree" vs "wide and scattered" — is what separates this from a memorised tip.

Section 8Controlled vs uncontrolled components

Now to forms, which is where all of this stops being theoretical, because HTML inputs have a rude property: they already have their own state.

A <input> in a plain HTML page remembers what you typed. Nobody wrote any JavaScript for that. The DOM node itself holds a value, and it updates as you type. So the moment React shows up wanting to be the single source of truth, we have two things that both think they own the value. Something has to give.

The two answers to "who wins?" are exactly what controlled and uncontrolled mean.

Controlled: React holds the value

A controlled input 
function SearchBox() {
  const [query, setQuery] = useState("");

  return (
    <input
      value={query}                                    {/* 👈 React tells the DOM what to show */}
      onChange={(e) => setQuery(e.target.value)}        {/* 👈 DOM tells React what happened */}
    />
  );
}

Follow one keystroke through this, because the loop is the entire concept:

That last line is the bit that surprises people. In a controlled input, the letter appearing on screen is not the letter your keyboard produced. Your keystroke is an event; React takes it, updates state, re-renders, and writes the value back into the DOM node. The visual result is identical, so it feels the same — but the value on screen is always React's value.

Which is precisely why the read-only bug happens.

"Why can't I type in my input?"

Roughly the most-asked React question on the internet:

❌ Buggy — the input appears frozen 
const [query, setQuery] = useState("");

<input value={query} />   {/* 👈 no onChange */}
// → typing does nothing. React logs a warning about
//    providing `value` without `onChange`.

Walk the loop and it's obvious. You type "h". The DOM briefly holds "h". React re-renders (or reconciles) and sees that value should be "" — because query never changed, because nothing called setQuery — so it writes "" back into the node. Your character is erased faster than the screen can show it. The input isn't broken; it's being held at "" by an authority you gave it.

Three legitimate fixes, depending on intent:

  • You want editing → add onChange and update state. (What you meant.)
  • You want a genuinely read-only field → add the readOnly attribute, which is honest about the intent and doesn't warn.
  • You want an initial value that the user can then edit freely → you wanted defaultValue, not value. Which brings us to the other half.

Uncontrolled: the DOM holds the value

Uncontrolled means you let the input keep its own value, the way plain HTML always did, and you go ask for it when you need it — usually on submit.

An uncontrolled input 
function SearchBox() {
  const inputRef = useRef(null);

  function handleSubmit(event) {
    event.preventDefault();
    console.log(inputRef.current.value); // 👈 ask the DOM, at the moment we care
  }

  return (
    <form onSubmit={handleSubmit}>
      <input ref={inputRef} defaultValue="" />   {/* 👈 defaultValue, not value */}
      <button>Search</button>
    </form>
  );
}

Two new pieces there, so let's be sure they're clear.

useRef gives you a stable box ({ current: null }) that survives re-renders. Attach it to a DOM element with the ref attribute, and React puts the actual DOM node into .current. So inputRef.current.value is just reading the real DOM node's value — plain old DOM API, reached through React.

defaultValue is React's way of saying "seed this input's value once, then leave it alone." Using the plain HTML value attribute here wouldn't work as expected in React, so React gives you defaultValue (and defaultChecked for checkboxes and radios) as the uncontrolled counterpart.

Notice the shape: defaultValue is to value exactly what useState(initial) is to a prop you keep passing. Both mean "initial only, ignored afterwards." Same idea, two places. Once you see that, the intro bug and the defaultValue semantics stop being two facts and become one.

So which one, and when?

Go controlled when something else on the page depends on the value as you type. Live search results. A character counter. Formatting a phone number mid-typing. Greying out "Submit" until the email looks valid. Showing "passwords don't match" the instant they don't. In every one of these, React has to know the current value at every keystroke to render correctly — which is the definition of "it should be state."

Go uncontrolled when nothing needs the value until submit. A login form. A search box where you only search on Enter. Any form with a lot of fields where per-keystroke re-rendering starts to hurt. Also when you're integrating a non-React widget (a legacy jQuery date picker, say) that insists on owning its own DOM.

The React docs' own guidance is to prefer controlled by default — it keeps everything in one model — and reach for uncontrolled when you have a reason. That's the balanced thing to say in an interview: "controlled by default, uncontrolled when the value isn't needed until submit or when re-render cost actually shows up."

A common misconception

"Controlled inputs are slow, so I should use uncontrolled everywhere." For most forms this is nonsense — re-rendering one small component per keystroke is nothing. The cost appears when the state lives high up and a keystroke re-renders a huge subtree. Note that the real culprit there is where the state lives, not controlled-ness itself. Often the fix isn't going uncontrolled — it's pushing the state down into a smaller component so the re-render is local. Saying that out loud is a strong signal, because it shows you diagnose before you prescribe.

Don't switch between the two

If you've ever seen this warning, here's what caused it:

❌ Buggy — switches from uncontrolled to controlled 
const [name, setName] = useState();   // 👈 undefined!

<input value={name} onChange={(e) => setName(e.target.value)} />
// → Warning: A component is changing an uncontrolled input to be
//    controlled.

useState() with no argument gives undefined. When React sees value={undefined} it can't distinguish that from "no value prop at all," so it treats the input as uncontrolled and lets the DOM drive. Then you type, state becomes a string, and suddenly value is defined — so React switches modes mid-life. React warns because the change is almost always accidental and the behaviour around it is confusing.

✅ Fixed 
const [name, setName] = useState("");  // 👈 always a string
// Same fix for values from an API: value={name ?? ""}

The same applies to null. Rule: for a controlled input, the value must never be undefined or null. Empty string, always.

Wait — what about file inputs?

Great follow-up, and a favourite because it catches people who learned the rules without the reasons. <input type="file" /> is always uncontrolled. You cannot set its value from React.

Why? Security. If a page could set a file input's value programmatically, it could point it at C:\Users\you\tax-return.pdf and silently upload your files. So browsers make the value read-only to scripts — only a real user gesture can set it. React can't control what the browser won't let it write. (You can clear it by setting it to the empty string, which is the one allowed write and the standard "reset the file picker" move.) You read files via onChange from event.target.files, or with a ref: fileRef.current.files[0].

Mixing the two

You can absolutely have both styles in one form — a controlled email field with live validation next to three uncontrolled fields read on submit. That's fine and sometimes ideal. What you must not do is make a single input half-controlled: passing both value and defaultValue to the same element gets you a warning, because you've given React two contradictory instructions about who owns the value. Pick one per input.

How React Hook Form exploits this

This is a great thing to bring up unprompted, because it shows you've connected a concept to real ecosystem design.

Form libraries used to keep every field in React state — controlled — meaning every keystroke in any field re-rendered the whole form. On a 30-field checkout, on a mid-range phone, that's noticeable.

React Hook Form's core move is to go uncontrolled by default. Its register() attaches a ref to each input and lets the DOM hold the values. Typing produces zero React re-renders, because nothing is in React state to update. The library reads values out of the DOM when it needs them — on submit, or when a validation rule triggers.

React Hook Form, roughly 
const { register, handleSubmit } = useForm();

<form onSubmit={handleSubmit(onValid)}>
  <input {...register("email")} />   {/* 👈 spreads a ref + handlers onto the input */}
  <input {...register("password")} />
</form>
// Typing here causes no re-renders at all.

The trade-off is real, and mentioning it makes the point land harder: because values aren't in React state, anything that needs to react to a value as you type needs an explicit opt-in — that's what the library's watch and useWatch are for, and using them re-introduces re-renders for exactly the fields you're watching. So it isn't magic, it's a deliberate default: pay for reactivity only where you actually use it. (Formik, by contrast, was built controlled-first, which is why its performance story on large forms is different.)

Section 9Class lifecycle methods, mapped to hooks

Two reasons to know this: you will one day open a file that starts with class Something extends React.Component, and interviewers with a few years on them still ask, partly to see if you understand what effects are actually for.

Quick orientation for anyone who's only written function components. Before hooks (React 16.8, early 2019), a component with state had to be a class. State lived on this.state, you changed it with this.setState(), and instead of hooks you got a set of methods React would call at specific moments in the component's life: when it mounted, when it updated, when it was about to be removed.

The same counter, as a class 
class Counter extends React.Component {
  constructor(props) {
    super(props);
    this.state = { count: 0 };            // 👈 initial state
  }
  componentDidMount() {
    document.title = `Count: ${this.state.count}`;
  }
  componentDidUpdate(prevProps, prevState) {
    if (prevState.count !== this.state.count) {
      document.title = `Count: ${this.state.count}`;   // 👈 note the duplication
    }
  }
  componentWillUnmount() {
    document.title = "My App";
  }
  render() {
    return <button onClick={() => this.setState({ count: this.state.count + 1 })}>
      {this.state.count}
    </button>;
  }
}

Here's the mapping table. Memorise the left two columns; the third column is where the marks are.

In an interview

"Is there anything you still can't do with hooks?" The answer they're fishing for is error boundaries. There is no useErrorBoundary; catching render errors in a subtree requires a class component implementing getDerivedStateFromError (to render a fallback) and/or componentDidCatch (to log). In practice most teams write one small class once, or install react-error-boundary, and never think about it again. Worth adding: error boundaries don't catch errors in event handlers, async code, or during SSR — those need ordinary try/catch.

Now the important part: the mapping is a bit of a lie

If the interview stops at the table, you've answered a recall question. The senior answer is the next paragraph, so let's make sure it's genuinely clear rather than a slogan.

The table implies useEffect is "the hook you use to do lifecycle things," with the dependency array selecting which lifecycle moment. That framing will actively mislead you. Effects are not about moments in time. They're about keeping something outside React in sync with your React state.

Here's the concrete case that proves it. A chat room component connects to a server:

Written as synchronisation 
useEffect(() => {
  const connection = createConnection(roomId);
  connection.connect();
  return () => connection.disconnect();   // 👈 cleanup
}, [roomId]);

Read that with lifecycle eyes and you get: "connect on mount, disconnect on unmount, and… something about roomId?" Read it with synchronisation eyes and it says one sentence: "While this component is on screen, there should be a live connection to roomId." React's job is to make reality match that statement. If roomId changes, reality no longer matches, so React tears down the old connection and builds a new one. Mount and unmount are just the first and last time reality has to be brought in line.

The lifecycle-minded developer writes this instead:

❌ Buggy — thinking in moments 
useEffect(() => {
  const connection = createConnection(roomId);
  connection.connect();
  return () => connection.disconnect();
}, []);   // 👈 "connect once on mount" — leaks a connection to the old room

Switching rooms leaves you talking to the previous room forever. The empty array wasn't a description of the world, it was an instruction about timing — and it lied.

Three more ways the lifecycle mindset leads people astray, all of which are worth having ready:

It makes cleanup feel like "the unmount handler." It isn't. Cleanup runs before every re-run of the effect. Once you see it as "undo what this effect did, so the next run starts clean," the double-fire in Strict Mode stops being scary and becomes a test: if mount → unmount → mount breaks your component, you had a cleanup bug that would have shown up in production anyway.

It makes the dependency array feel like a trigger list. "Run this when userId changes" invites you to leave things out to control timing — and omitted dependencies are how you get stale closures reading last render's values. The array isn't a trigger list; it's a declaration of what the effect reads. If you're fighting it, the honest read is usually that this shouldn't be an effect at all.

It makes people use effects for things that aren't effects. The single biggest one: effects that only update React state in response to other React state. That's not synchronising with an external system — that's a calculation wearing a costume, and it should be plain code in the render body. Same for event responses: code that should run because the user clicked belongs in the click handler, not in an effect watching a flag the click set.

Model answer — "How do lifecycle methods map to hooks?"

"Roughly: the constructor's state becomes useState, componentDidMount becomes useEffect with an empty dependency array, componentDidUpdate becomes useEffect with dependencies, componentWillUnmount becomes the cleanup function you return, and shouldComponentUpdate becomes React.memo. Error boundaries are the one thing with no hook equivalent — getDerivedStateFromError and componentDidCatch still require a class. But I'd add that the mapping is approximate and a bit misleading: an effect isn't a lifecycle moment, it's a way of keeping something external in sync with state, and the dependency array describes what the effect reads rather than when it should fire. Thinking in mount-and-update is how you end up with empty dependency arrays that leak subscriptions."

Why it lands: the first half proves you can work in a legacy codebase. The second half is the part junior candidates never say, and it's the difference between "knows the API" and "knows the model."

Section 10The follow-up questions, with answers

These are the ones that actually come up. Some restate things above — that's on purpose, since answering out loud is a different skill from recognising. Each answer is written roughly as you'd say it.

"When would you use an uncontrolled component?"

When nothing needs the value until the user submits. A login form is the classic case — I don't need to react to each keystroke, so I'll let the DOM hold the values and read them on submit with a ref or from the form. The other big case is performance on large forms, which is exactly why React Hook Form is uncontrolled by default: no state means no re-render per keystroke. And file inputs, which are always uncontrolled because browsers won't let scripts set their value. My default is still controlled, since it keeps one source of truth — I go uncontrolled deliberately, not out of habit.

"Why is my input not updating / read-only?"

Almost always because value was passed without an onChange. That makes React the source of truth but never lets the value change, so on every render React writes the same value back into the DOM node and your keystroke gets wiped. Fix is to add onChange and update state; if it's genuinely meant to be read-only, use the readOnly attribute; if I just wanted an initial value the user can edit, I wanted defaultValue. The other flavour of this is useState() with no initial value, which starts as undefined — React treats that as uncontrolled and then warns when it flips to controlled.

"Can a child modify its props?"

No, not in any useful sense. JavaScript won't stop me from mutating the object, but React won't re-render from it, the object belongs to the parent, and the parent overwrites it next render anyway. If a child needs a value to change, the parent passes down a callback, the child calls it, and the parent updates its own state — the new value comes back down as a prop. Data down, events up.

"How do two sibling components share state?"

They can't talk directly — data only flows down — so the state moves up to their closest common ancestor, which passes the value down to both and a setter down to whichever one changes it. That's lifting state up. If the common ancestor is far away and the value would have to thread through a lot of uninterested components, I'd look at restructuring with composition first, and reach for Context when the consumers are genuinely wide and scattered.

"Why is derived state an antipattern?"

It creates a second copy of a value that can drift from the original. The classic version is useState(props.value): that argument is only an initial value, so once the prop changes the state keeps the old one and the UI goes stale. If it can be calculated, calculate it during render — a value you compute can't be out of sync. If it needs to be shared, lift it. If I want a genuine reset, use key. What I'd avoid is a useEffect that syncs the prop into state, since that renders twice and can flash the stale value.

"How do you reset a component's state when a prop changes?"

Pass a key that changes with the prop — <EditName key={user.id} user={user} />. React identifies a component by position plus key, so a new key means it treats it as a different component: it unmounts the old instance, runs its cleanup, and mounts a fresh one with fresh state. It's the same mechanism as keys in lists, used deliberately. If I only want to reset part of the state I'd adjust state during render while tracking the previous prop, but key is cleaner and I'd try it first.

"What replaced componentWillReceiveProps, and why was it deprecated?"

It was replaced by getDerivedStateFromProps in classes, and in hooks the answer is usually "nothing, because you shouldn't need it" — calculate during render or use key.

It was deprecated for two reasons. The first is that it, along with componentWillMount and componentWillUpdate, ran before render, in the phase React wanted to make interruptible for concurrent rendering. React needed to be free to start rendering, pause, and restart — which means anything in that phase might run multiple times per commit. Any side effect in there, like kicking off a fetch or setting up a subscription, would fire more than once. So they were renamed with an UNSAFE_ prefix and pushed out of the way. The replacement, getDerivedStateFromProps, is static, which is the giveaway: no this, so you physically cannot do side effects or read instance state in it.

The second reason is that it was chronically misused for derived state. People wrote if (nextProps.value !== this.props.value) this.setState({ value: nextProps.value }), which introduces exactly the two-sources-of-truth bug we've been talking about, plus a subtle one: it compares against the incoming props rather than current state, so it silently blows away user edits whenever the parent re-renders for an unrelated reason.

"What are the downsides of lifting state up?"

Three. Prop drilling, if the common ancestor is far from the consumers — the value threads through components that don't use it, which is noisy and makes those components' APIs misleading. Wider re-renders, because updating state re-renders that component and its subtree, so a keystroke that used to re-render one input now re-renders a whole page. And responsibility creep: the parent accumulates unrelated state until it's a dumping ground. So I lift to the closest common ancestor, not the top, and if performance shows up as a real problem I look at pushing state back down into a smaller component or memoising the expensive children.

"How do you avoid prop drilling without Context?"

Composition. Instead of passing data down through layers, I create the element where the data already lives and pass it down as children or as an element-valued prop. The intermediate components carry an opaque element and never learn about the data — which removes the drilling and makes them more reusable, since they now work with any content. Context is still right when consumers are wide and scattered, like theme or auth, but for a known destination in the tree, composition solves it with no new machinery.

"Why not just use two-way binding? It's less code."

It is less code, and that's a real benefit. What you give up is the ability to answer "who changed this value?" cheaply. With one-way flow, a value is written in exactly one place — the component that owns the state — so debugging is a bounded search. With two-way binding, anything holding a binding can write, and updates can cascade into each other. React took the more-typing-for-more-predictability trade, and it's what makes rendering close to a pure function of state, which is what dev tools and time-travel debugging rely on. Controlled inputs give you the two-way feel anyway; you just write the loop yourself.

"Why not just put every value in state? It's simpler to reason about."

The opposite, actually — every extra piece of state is another thing that can disagree with the others. If a value can be computed from props or other state, computing it during render means it's structurally impossible for it to be wrong, whereas storing it means every code path that changes the source has to remember to update the copy. I keep state as the minimal set of values that everything else can be derived from. If a derivation is genuinely expensive, that's what useMemo is for — and note it caches a derived value rather than making a second source of truth.

Traps to avoid saying
  • "Props are immutable, state is mutable." State isn't mutable either — you replace it via the setter. Mutating a state object directly is just as broken, and often won't re-render because React compares by reference.
  • "useEffect is componentDidMount." Only approximately, and the differences (runs after paint, cleanup between runs, Strict Mode double-invoke) are exactly what gets probed next.
  • "Controlled is slow." Too broad. Say what's slow — a re-render of a large subtree per keystroke — and note that pushing state down often fixes it without going uncontrolled.
  • "Use Context to avoid prop drilling." Fine as a second sentence, never as the first. Composition first shows judgement.
  • "State updates are asynchronous, so you can't read the new value." Close but muddled. The precise version: setters queue an update and don't change the current render's variable, because that variable is a const captured by this render. Use the updater form setCount(c => c + 1) when the new value depends on the old.

One last thing

If you remember one sentence from all of this, make it this one: every bug in this guide is a question about ownership.

Stale copied prop? Two owners for one value. Input you can't type in? React owns the value but nothing ever updates it. Siblings that can't communicate? The value is owned too low. Prop drilling? The value is owned too high, or created in the wrong place. Leaked chat connection? An effect that described a moment instead of describing what it depends on.

So when something's behaving strangely, don't start by asking what React is doing wrong. Ask: who owns this value, and is that the right owner? That question resolves an unreasonable share of React confusion — including, I'll admit, most of my own. 🙂
