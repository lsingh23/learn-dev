57. Sortable Table

Click a header to sort ascending, click again for descending. Tests one thing: do you derive, or do you store?

The ask

Interviewer "Here's an array of user objects. Render a table. Clicking a column header sorts by that column — first click ascending, second click descending. Show which column is active."

Plain English: keep which column and which direction. Sort a copy at render time.

What we're building

Sorted by Age, descending
Name ↕ Age ▼ Joined ↕
Priya412021-03-02
Owen342019-11-20
Ada292022-07-14
Sam—2020-01-08

▼ = active column + direction ↕ = sortable, not active null rows sink to the bottom

It should:

  • Every header clickable.
  • 1st click → ascending. 2nd click → descending.
  • New column → back to ascending.
  • Arrow shows active column + direction.
  • Strings, numbers and dates each compare correctly.
  • Empty / null values always last.
  • Original rows array never changes.

The mental model

The sorted list is not state. State is two tiny strings; the rows on screen are a function of them. Store the sorted array and you now have two truths to keep in sync — that's the bug they're hunting for.

The shape of the state

const [sort, setSort] = useState({
  key: 'name',        // which column — matches a column's key
  direction: 'asc',   // 'asc' | 'desc'
});
// that's it. No sortedRows state. No isDescending booleans per column.

And the columns, declared once, so headers and cells can't drift apart:

const columns = [
  { key:'name',   label:'Name',   type:'string' },
  { key:'age',    label:'Age',    type:'number' },
  { key:'joined', label:'Joined', type:'date'   },
];
Rule of thumb If you can compute it from other state, it isn't state. sortedRows is computed.

Build it in layers

In an interview, build L1 and L2 first, out loud, then ask "want me to add the arrow and proper type-aware comparing?"

L1 Static table, no state

Prove the render loop works before anything moves.

<table>
  <thead><tr>{columns.map(c => <th key={c.key}>{c.label}</th>)}</tr></thead>
  <tbody>
    {rows.map(r => (
      <tr key={r.id}>{columns.map(c => <td key={c.key}>{r[c.key]}</td>)}</tr>
    ))}
  </tbody>
</table>

L2 Click to sort, one direction

Two strings of state, and a copy before sorting.

const [sort, setSort] = useState({ key:'name', direction:'asc' });

const sorted = [...rows].sort((a, b) =>      // copy! .sort mutates
  a[sort.key] > b[sort.key] ? 1 : -1
);

<th onClick={() => setSort({ key: c.key, direction:'asc' })}>{c.label}</th>

L3 Toggle direction + arrow

Same column flips; a different column starts fresh at asc.

function onSort(key) {
  setSort(s => s.key === key
    ? { key, direction: s.direction === 'asc' ? 'desc' : 'asc' }  // flip
    : { key, direction: 'asc' });                                 // new col → asc
}

const arrow = c => sort.key !== c.key ? '↕' : sort.direction === 'asc' ? '▲' : '▼';

L4 A real comparator

Nulls last, then compare by type, then apply direction once at the end.

function compare(a, b, type) {
  if (a == null && b == null) return 0;
  if (a == null) return 1;              // nulls always sink…
  if (b == null) return -1;             // …in BOTH directions
  if (type === 'string') return a.localeCompare(b);   // "Ä" vs "z", case
  if (type === 'date')   return new Date(a) - new Date(b);
  return a - b;                                        // number
}
Careful Nulls are compared before the direction multiplier, so flipping to desc doesn't drag empty cells to the top.

The whole thing

import { useState, useMemo } from 'react';

const columns = [
  { key:'name', label:'Name', type:'string' },
  { key:'age',  label:'Age',  type:'number' },
  { key:'joined', label:'Joined', type:'date' },
];

function compare(a, b, type) {
  if (a == null && b == null) return 0;
  if (a == null) return 1;
  if (b == null) return -1;
  if (type === 'string') return a.localeCompare(b);
  if (type === 'date') return new Date(a) - new Date(b);
  return a - b;
}

export default function SortableTable({ rows }) {
  const [sort, setSort] = useState({ key:'name', direction:'asc' });

  const sorted = useMemo(() => {
    const col = columns.find(c => c.key === sort.key);
    const dir = sort.direction === 'asc' ? 1 : -1;
    return [...rows].sort((a, b) => dir * compare(a[col.key], b[col.key], col.type));
  }, [rows, sort]);

  const onSort = key => setSort(s =>
    s.key === key
      ? { key, direction: s.direction === 'asc' ? 'desc' : 'asc' }
      : { key, direction: 'asc' });

  return (
    <table>
      <thead>
        <tr>
          {columns.map(c => {
            const active = sort.key === c.key;
            return (
              <th key={c.key}
                  aria-sort={active ? (sort.direction === 'asc' ? 'ascending' : 'descending') : 'none'}>
                <button onClick={() => onSort(c.key)}>
                  {c.label} {!active ? '↕' : sort.direction === 'asc' ? '▲' : '▼'}
                </button>
              </th>
            );
          })}
        </tr>
      </thead>
      <tbody>
        {sorted.map(r => (
          <tr key={r.id}>
            {columns.map(c => <td key={c.key}>{r[c.key] ?? '—'}</td>)}
          </tr>
        ))}
      </tbody>
    </table>
  );
}

Styling barely matters here. The state shape and the comparator are what's scored.

Gotchas

Sorting state instead of a copy. rows.sort() mutates the array in place — the prop, or the state array. Always [...rows].sort().
Storing sortedRows in state. Now new rows arrive and the table shows stale data. Derive it every render.
Default comparator on numbers. [10,9,100].sort() → [10,100,9] — it compares as strings. Pass a comparator, always.
Comparing strings with >. 'apple' > 'Banana' is true (capitals sort first). Use localeCompare.
Using array index as the row key. Rows reorder on every sort, so React reuses the wrong DOM and inputs/selection jump. Key by row.id.

If they push

"Make it fast with 10,000 rows." useMemo on sorted, keyed on [rows, sort] — so an unrelated re-render doesn't re-sort. Beyond ~50k, sort on the server or virtualise the rows.
"Sort by two columns." State becomes an array. Compare in order, first non-zero wins. 
const [sorts, setSorts] = useState([{ key:'dept', direction:'asc' }]);
[...rows].sort((a,b) => {
  for (const s of sorts) {
    const r = (s.direction==='asc'?1:-1) * compare(a[s.key], b[s.key], typeOf(s.key));
    if (r !== 0) return r;
  }
  return 0;
});
Shift-click a header to append instead of replace.
"Now add search and pagination." Order matters — each stage is derived from the one before:
rows→ filter→ sort→ paginate→ page rows
Filter first (sort less), sort the whole filtered set (not the page, or page 2 is nonsense), slice last. Also: reset to page 1 whenever the filter or sort changes.
"The data lives on the server." Same state, different consumer — send it as a query instead of sorting locally: ?sort=age&order=desc&page=2. The component stops owning sorted entirely; keep the sort state in the URL so the view is shareable.
"Is it accessible?" Put a real <button> inside the <th> so it's keyboard-reachable, and set aria-sort="ascending" | "descending" | "none" on the <th> itself — that's what screen readers announce. The arrow glyph alone says nothing.

Say this out loud

  • "My only state is which column and which direction — the sorted rows are derived, not stored."
  • "I'm spreading into a new array first, because .sort mutates in place and that array is a prop."
  • "Clicking the same header flips direction; a different header resets to ascending."
  • "The comparator branches on column type — localeCompare for strings, subtraction for numbers and dates."
  • "Nulls I push to the bottom before applying direction, so they don't float up in descending."
  • "I'll wrap the sort in useMemo, and put aria-sort on the header with a real button inside it."
