42. Progress Bar

Two divs and one number. The interview is really about clamping, animation cost, and ARIA.

The ask

Interviewer "Build a ProgressBar that takes a value from 0 to 100 and animates a fill to that width. Then show me N of them filling one after another."

Plain English: draw a bar, fill value% of it, animate the change.

What we're building

Single bar — value = 62

Indeterminate — we don't know the %

It should:

  • Fill to value% of the track.
  • Animate smoothly when value changes.
  • Clamp anything outside 0–100.
  • Never overflow the rounded track.
  • Announce itself: role="progressbar".
  • Work with no label, or a label.

Colours and radii don't score points. Logic, clamping and ARIA do.

The mental model

There is no "progress" state. There is one number, and the bar is a pure function of it: width = clamp(value) + "%". Everything else — the label, the colour, the aria attribute — is read off that same number.

The shape of the state

For the single bar, there is none — it's all props:

// ProgressBar owns nothing. Parent owns the number.
function ProgressBar({ value, max = 100, label }) { ... }

For the "N bars in sequence" version:

const [progress, setProgress] = useState([0,0,0,0]); // % of each bar
const [active, setActive]     = useState(0);         // which bar is filling now
Rule of thumb One source of truth — derive the rest. Don't store percentText, isDone, or widthStyle. They're all value in disguise.

Build it in layers

In an interview: build L1 and L2 out loud, then ask "want me to add the sequence / a11y?"

L1 Static markup, no state

Two divs. Prove the shape works.

<div className="track">
  <div className="fill" style={{ width: "62%" }} />
</div>

/* .track { height:14px; background:#eee; border-radius:99px; overflow:hidden }
   .fill  { height:100%; background:blue } */

L2 Take a value prop, clamp it, animate

One expression does the whole job.

const clamp = (n, lo, hi) => Math.min(hi, Math.max(lo, n));

function ProgressBar({ value }) {
  const pct = clamp(Number(value) || 0, 0, 100);
  return (
    <div className="track">
      <div className="fill" style={{ width: `${pct}%` }} />
    </div>
  );
}
// .fill { transition: width .4s ease }  ← the animation is pure CSS

L3 Accessibility + label

A screen reader must hear a number, not a coloured box.

<div
  className="track"
  role="progressbar"
  aria-valuenow={pct}
  aria-valuemin={0}
  aria-valuemax={100}
  aria-label={label ?? "Progress"}
>
  <div className="fill" style={{ width: `${pct}%` }} />
</div>
Indeterminate? Drop aria-valuenow entirely — its absence is the signal for "unknown". Keep the role.

L4 Cheaper animation: transform instead of width

Same picture, but the browser skips layout on every frame.

<div className="track">
  <div
    className="fill"
    style={{ transform: `scaleX(${pct / 100})`, transformOrigin: "left" }}
  />
</div>

// .fill { width:100%; transition: transform .4s ease; will-change: transform }
AnimatingBrowser work per frame
widthlayout → paint → composite 3 steps
transformcomposite only — runs on the GPU, off the main thread

width changes the element's box, so the browser must re-measure it and anything near it. transform just stretches an already-painted layer. Fine for one bar; noticeable with fifty.

The scaleX catch Scaling squashes the fill's children and its border-radius. Only use it when the fill is a plain colour block.

The whole thing

import { useState, useEffect } from "react";

const clamp = (n, lo, hi) => Math.min(hi, Math.max(lo, n));

export function ProgressBar({ value, label, indeterminate = false }) {
  const pct = clamp(Number(value) || 0, 0, 100);
  return (
    <div>
      {label && (
        <div className="barlabel">
          <span>{label}</span>
          {!indeterminate && <span>{Math.round(pct)}%</span>}
        </div>
      )}
      <div
        className="track"
        role="progressbar"
        aria-label={label ?? "Progress"}
        aria-valuemin={0}
        aria-valuemax={100}
        aria-valuenow={indeterminate ? undefined : Math.round(pct)}
      >
        <div
          className={indeterminate ? "fill indeterminate" : "fill"}
          style={indeterminate ? undefined : { width: `${pct}%` }}
        />
      </div>
    </div>
  );
}

// N bars, filling one after another
export function ProgressList({ count = 4 }) {
  const [bars, setBars] = useState(() => Array(count).fill(0));
  const [active, setActive] = useState(0);

  useEffect(() => {
    if (active >= count) return;                // all done
    const id = setInterval(() => {
      setBars(prev => {
        const next = [...prev];
        next[active] = Math.min(100, next[active] + 5);
        if (next[active] === 100) setActive(a => a + 1);   // hand off
        return next;
      });
    }, 100);
    return () => clearInterval(id);              // always clean up
  }, [active, count]);

  return bars.map((v, i) => <ProgressBar key={i} value={v} label={`Bar ${i + 1}`} />);
}

Gotchas

Forgetting to clamp. value={143} gives width:143% — the fill spills out of the track. Clamp once, at the top, and use only pct below it.
No overflow:hidden on the track. The fill's square corners poke past the track's rounded ones. One CSS line fixes it.
Animating from 0 with no first paint. If a bar mounts already at 60%, there's nothing to transition from — it just appears. Mount at 0, then set the real value in an effect if you want the entry animation.
Not clearing the interval. setInterval without a cleanup keeps ticking after unmount and warns/leaks. Always return () => clearInterval(id).
Stale state in the tick. setBars(prev => …), never setBars([...bars]) — the interval closure captures an old bars.

If they push

"Now run 3 at a time, not one." (concurrency limit) Swap the single active pointer for a set of running indexes. Each time one finishes, pull the next waiting index in. 
const LIMIT = 3;
const running = bars
  .map((v, i) => ({ v, i }))
  .filter(b => b.v < 100)
  .slice(0, LIMIT)               // first 3 unfinished bars
  .map(b => b.i);

// in the tick: bump every index in `running` by 5
"Why is this janky with 100 bars?" Each width change forces layout. Switch to transform: scaleX(), and drive all bars from one interval instead of one per bar.
"Make it indeterminate." Fixed-width fill, animated with a looping transform: translateX() keyframe. Drop aria-valuenow.
"Support a max other than 100." const pct = clamp(value / max, 0, 1) * 100; and pass the real max to aria-valuemax.
"Users who dislike motion?" @media (prefers-reduced-motion: reduce) { .fill { transition: none } }.

Say this out loud

  1. "It's two divs — a track and a fill — and the fill's width is just the value as a percent."
  2. "I'll clamp the value to 0–100 right at the top, so nothing downstream can overflow the track."
  3. "The animation is CSS, not JS — a transition on width means I only ever set the final value."
  4. "If we had a lot of bars I'd animate transform: scaleX instead, since that skips layout and composites on the GPU."
  5. "I'm adding role=progressbar with aria-valuenow, min and max so a screen reader hears a number."
  6. "For the sequential version I keep one array of percentages plus an index of which bar is active — one source of truth."
