Currying and memoize

Two classic closure puzzles. One asks you to split a function's arguments across several calls; the other asks you to remember answers you've already computed. Both are under a dozen lines — the interview is about whether you can explain them.

Making add(1)(2)(3) work

Here's the exact thing you'll be asked. Write an add such that this works:

add(1)(2)(3);  // → 6

Read the syntax literally and it tells you the answer. add(1) is called, and the result of that is immediately called with 2. So add(1) must return a function. And that function's result gets called with 3, so it returns a function too. Only the last one returns a number.

✅ Three lines
function add(a) {
  return (b) => (c) => a + b + c;
}

add(1)(2)(3);   // → 6
add(10)(20)(5); // → 35

The only thing making this work is that a function returned from another function remembers the variables it was born with. When we call add(1), that a = 1 doesn't evaporate when add returns — the inner function is still holding a reference to it. Same for b. By the time we reach a + b + c, all three are in scope, collected across three separate calls at three separate moments.

Think of it like filling in a form one field at a time. Each call hands back a partially-filled form; nothing is submitted until the last field is in.

Wait — can I just write it as nested functions?

Yes, identical behaviour: function add(a) { return function (b) { return function (c) { return a + b + c; }; }; }. The arrow version is shorter and reads as a chain, which is why I'd write it on a whiteboard. Nothing deeper than that.

A generic curry(fn)

Hardcoding three levels is fine for one function. The real question is the general one: take any function and let its arguments arrive in any number of calls.

const sum = (a, b, c) => a + b + c;
const curried = curry(sum);

curried(1)(2)(3);   // → 6
curried(1, 2)(3);   // → 6
curried(1)(2, 3);   // → 6
curried(1, 2, 3);   // → 6

To write this we need to answer one question: how do we know when we have enough arguments? And JavaScript hands us the answer for free — every function has a .length property holding its declared parameter count.

sum.length;                // → 3
((a, b) => a).length;      // → 2

That's the whole trick. Collect arguments as they come in; compare the pile against fn.length; call the original once the pile is big enough.

✅ The version to write in an interview
function curry(fn) {
  return function curried(...args) {
    if (args.length >= fn.length) {     // 👈 enough? run it
      return fn.apply(this, args);
    }
    return (...more) => curried.apply(this, [...args, ...more]);
  };
}

Six lines. Walk curried(1)(2)(3) through it. First call: args is [1], one is less than three, so we return a function that's waiting. Call that with 2 and it re-enters curried with [1, 2] — still short, so another waiting function. Call that with 3 and we re-enter with [1, 2, 3]. Now the check passes and sum actually runs.

And curried(1, 2)(3) works with no extra code, because we never assumed one argument per call — we only ever compare the total. The named function expression (function curried) is what lets us recurse back into ourselves by name.

If they push: the infinite chain

A nastier variant asks for add(1)(2)(3)(4)… with no fixed arity, ending in either add(1)(2)(3)() or a bare add(1)(2)(3) that prints 6. The trick is that you can't return a number and a function at the same time — so you return a function and give it a valueOf (or toString) that returns the running total. When JavaScript coerces it, via +chain or a template string, that method fires and yields the sum. Name that trick out loud; you rarely need to finish writing it.

Currying vs partial application

These get conflated constantly, and the distinction is small. Currying transforms an n-argument function into a chain of single-argument functions — it's driven by arity, and strictly speaking one argument at a time. Partial application just pre-fills some arguments and hands back a function wanting the rest, in one step, with no chain.

You already use partial application: fn.bind(null, 1) returns a function with the first argument locked in. Most "curry" implementations you'll see in the wild — including the one above, which happily takes curried(1, 2) — are really doing partial application with a chain on top. Say that; it reads as precision, not pedantry.

Where you'd actually use it

The honest answer: pre-configured helpers. You have createLogger(level, message) and you don't want to pass 'error' at forty call sites, so you make const logError = createLogger('error') once and call logError('Payment failed') everywhere. Same for an API client bound to a base URL, or a formatter bound to a locale. That pattern is genuinely useful — but you'll reach for an arrow function or bind for it far more often than a generic curry. Full currying is common in FP-heavy codebases (Ramda, point-free pipelines) and rare in everyday React work. Interviewers ask it because it tests closures and fn.length, not because you'll ship it.

The problem memoize solves

Here's the classic naive fibonacci:

function fib(n) {
  return n < 2 ? n : fib(n - 1) + fib(n - 2);
}

fib(40);   // → 102334155, and it takes about a second

A second, to add up some small integers. The reason is that it recomputes everything, constantly: fib(40) calls fib(38) twice, fib(37) three times, fib(30) hundreds of thousands of times — always with the same input, always producing the same answer. It's a student re-deriving the same equation on every page instead of writing it on the inside cover once.

So: keep a notepad. Before computing, check if we've seen this input; if we have, hand back the saved answer.

✅ memoize
function memoize(fn) {
  const cache = new Map();               // 👈 private, survives between calls

  return function (...args) {
    const key = JSON.stringify(args);
    if (cache.has(key)) return cache.get(key);

    const result = fn.apply(this, args);
    cache.set(key, result);
    return result;
  };
}

Same closure move as currying: cache lives in memoize's scope, so it's private and it persists across every call to the returned function. JSON.stringify(args) turns the argument list into a string we can use as a key, so (2, 3) and (3, 2) land in different slots.

Now wire it into fibonacci. The subtle bit: recurse through the memoized version, not the original, or the inner calls skip the cache entirely.

const fib = memoize(function (n) {
  return n < 2 ? n : fib(n - 1) + fib(n - 2);   // 👈 calls the memoized fib
});

fib(40);   // → 102334155, now instant

From roughly a billion calls to 41. Every value is computed exactly once.

The caveats that matter

JSON.stringify is a rough key. It's perfect for primitives, which covers most real use. But it drops functions and undefined, it treats {a:1, b:2} and {b:2, a:1} as different keys because key order is preserved, and on a large object it's slow enough to cost more than the function you're caching. For a single-primitive-argument function, just use args[0] as the key and skip stringify entirely.

Only memoize pure functions. Same input must always mean same output, with no side effects. Memoize something that reads the clock, hits the network, or mutates state, and you've frozen the first answer forever — and silently deleted the side effect on every call after the first.

The cache grows forever. Nothing ever evicts, so a memoized function called with many distinct inputs is a memory leak with good intentions. Bound it — cap the size and drop the oldest entry (an LRU), or, when the argument is a single object, use a WeakMap keyed on that object so entries disappear when the object is garbage-collected.

The interview layer

How it gets asked

  • "Write an add function so that add(1)(2)(3) returns 6."
  • "Implement a generic curry." Then: "make it handle curried(1, 2)(3)."
  • "What's the difference between currying and partial application?"
  • "Implement memoize." Often paired with "…now speed up this fibonacci."
🗣 Model answer — "implement memoize"

"I'd return a wrapper that closes over a Map. On each call I build a key from the arguments — JSON.stringify(args) is the quick version — and if that key's in the cache I return the stored value, otherwise I run the real function, store the result, and return it. The closure is what makes it work: the cache is private to that wrapper and survives between calls. Two things I'd flag: it's only safe for pure functions, since anything time- or network-dependent gets frozen at the first answer, and the cache never evicts, so for unbounded inputs I'd cap it with an LRU or key it on an object with a WeakMap."

That lands because you named the mechanism, the key strategy, and the two failure modes without being asked. Reciting the eight lines gets you a pass; volunteering the caveats is what signals you've actually shipped one.

Follow-ups

"Why does curry use fn.length?"

It's the function's declared parameter count — the only built-in way to know how many arguments the original expects. That's the stopping condition: keep returning collectors until the pile reaches that number, then call through.

"What breaks if the function has default params or rest args?"

fn.length stops counting at the first parameter with a default, and doesn't count a rest parameter at all. So (a, b = 2, c) => … reports 1 and (...args) => … reports 0 — currying fires after the first call, or immediately, with arguments missing. Fix it by taking the arity explicitly: curry(fn, arity = fn.length). Mentioning this unprompted is a strong signal.

"How would you key the memo cache for object arguments?"

If it's a single object argument, a WeakMap keyed on the object itself — no serialisation, and it doesn't leak. Downside: it's identity-based, so two structurally identical objects are two cache entries. If you need value equality, you need a stable serializer that sorts keys, and at that point you should check the key is cheaper than the computation.

"When is memoizing a bad idea?"

When the function is cheap (the key-building costs more than the work), when inputs rarely repeat (you're paying memory for a cache that never hits), or when the function isn't pure. The default should be "don't", until a profile says otherwise.

"How does this relate to useMemo and React.memo?"

Same core idea — cache a result keyed on inputs — with two big differences. React's caches hold one entry, not a map: change the dependency array and the previous value is gone, so alternating between two inputs misses every time. And they're tied to a component instance's render lifecycle, so the cache dies on unmount. Our memoize is a module-level cache with unlimited entries and no lifecycle.

"Is memoize safe for a function that fetches?"

Not with this implementation. It caches the returned promise, which is actually a nice request-deduplication trick while it's in flight — but the promise is stored forever, so you keep serving stale data, and a rejected promise gets cached as a permanent failure. Real request caching needs a TTL and eviction on error, which is what libraries like React Query exist for.

Traps

  • Recursing into the original function instead of the memoized one — the cache gets exactly one entry and the speedup vanishes.
  • Using args.length === fn.length in curry. Use >=, or extra arguments hang the chain forever.
  • Saying "currying is the same as bind." Close, but bind is partial application — one step, no chain, and it also sets this.
  • Claiming memoization is a general speedup. It trades memory for time, and only for pure functions with repeating inputs.

Cheat sheet

  • Currying — one argument at a time; each call returns a function holding the arguments so far.
  • fn.length — declared parameter count. The stopping condition. Broken by defaults and rest params → take arity explicitly.
  • Partial application — pre-fill some args in one step. That's bind.
  • Memoize — closure over a Map; key from the args; return the cached value on a hit.
  • Pure only — no clock, no network, no mutation.
  • Unbounded cache = leak — cap it (LRU) or use a WeakMap on an object arg.
  • React — useMemo/React.memo are the same idea with a one-entry cache tied to render.
