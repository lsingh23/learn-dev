A click that fires twice

Let's start with something small and slightly annoying. Here's some markup — a card with a button inside it:

HTML 
<div class="card">
  <button class="buy">Buy now</button>
</div>

And here's some JavaScript that listens for clicks on both of them:

JS 
document.querySelector('.card').addEventListener('click', () => {
  console.log('card clicked');
});

document.querySelector('.buy').addEventListener('click', () => {
  console.log('button clicked');
});

Now you click the button — the actual pixels of the button, nothing else. What gets logged? Take a guess before you scroll. It's genuinely worth guessing, because whichever answer you picked tells you which mental model you're currently carrying.

Show me what actually logs 
button clicked
card clicked

Both handlers run, and the button's runs first — even though your finger only ever touched one element.

This trips people up because most of us start out with the wrong picture in our heads. The wrong picture is: a click is an arrow that hits one element, and that element's handler runs. Nice and simple. Also wrong.

The real picture is that a click doesn't hit an element. It travels a path — and every element on that path gets a turn. Let me build that picture up properly, because everything else in this guide falls out of it.

First, the tree

Quick foundation, and I promise it's short. When the browser parses your HTML, it doesn't keep a big string of text around. It builds a tree of objects in memory called the DOM (Document Object Model). Nesting in your HTML becomes parent/child relationships in the tree.

So this HTML:

HTML 
<html>
  <body>
    <div class="card">
      <button class="buy">Buy now</button>
    </div>
  </body>
</html>

...becomes a chain: html has a child body, which has a child div.card, which has a child button.buy. Above html sits the document object, and above that sits window, the global object representing the tab itself.

That gives every element exactly one route to the top:

window → document → html → body → div.card → button.buy

Hold onto that chain. It is the event path. There's nothing more to it than that — the browser walks up and down this exact line.

The three phases

Here's the mental model, and I'd encourage you to actually picture it rather than memorise it.

Imagine an office building. A courier arrives with a package addressed to Maya, in office 604. The courier doesn't teleport to Maya's desk. They walk in through the front door, past the security desk, into the lift, out onto the sixth-floor reception, down the corridor, and finally to Maya's door. Then, having handed the package over, they walk back out the same way: corridor, reception, lift, security, front door.

Everyone the courier passes — twice — gets a chance to look at the package. Security can inspect it on the way in. The floor receptionist can log it on the way out. Any of them could, in principle, confiscate it so it never reaches Maya at all.

That's an event. The trip inward, from window down toward the element you actually clicked, is called the capturing phase. The moment the event arrives at the clicked element itself is the target phase. The trip back outward, from the clicked element up to window, is the bubbling phase.

Now go back to our mystery. We attached two handlers. Neither of them asked for the capturing phase, so both are bubbling handlers — the default. The event goes down through steps 1–5 firing nothing, reaches the button at step 6 and runs the button's handler, then bubbles up and hits div.card at step 7, running the card's handler.

button clicked, then card clicked. Not mysterious any more — just the courier walking back out past reception.

Where the analogy breaks down

A courier physically moves; an event doesn't. The browser has already worked out the full path before it fires anything, and then it just calls your functions in order. And unlike a package, the event object is shared — every handler on the path gets a reference to the same object, so if one handler sets event.foo = 1, later handlers see it. That shared-object detail is exactly why stopPropagation() can work at all.

Under the hood

The event object knows where it is. event.eventPhase is 1 during capturing, 2 at the target, 3 during bubbling. And event.composedPath() returns the whole array of nodes the event will visit, target first. Logging composedPath() once in a confusing situation is the fastest way to see reality instead of guessing at it.

Why both directions exist

Reasonable question: why on earth would a system need to deliver the same event twice, in two directions? That seems like a design nobody would choose.

And you're right — nobody did choose it. It's a peace treaty. 🕊️

Back in the late '90s, Netscape Navigator and Internet Explorer were building event systems independently and landed on opposite answers. Netscape said events should travel from the outside in: the window sees it first, and it trickles down to the element. That's capturing. Microsoft said the opposite: the element you clicked is obviously the most relevant thing, so it should go first, and then the news should spread outward to its ancestors. That's bubbling.

When the W3C sat down to standardise the DOM, they couldn't pick a winner without breaking a browser's worth of existing code. So they specified both, in sequence: capture down, then bubble up. Bubbling became the default for addEventListener because that's what the overwhelming majority of real code had been written against.

So the answer to "why both?" isn't an elegant engineering reason. It's history. Say that out loud in an interview and it lands well, because it signals you know the platform rather than just the API surface.

The third argument, and the options object

By default, addEventListener registers a bubbling listener. To listen during the capturing phase instead, you pass true as a third argument:

JS 
card.addEventListener('click', handleCard, true);   // 👈 capturing
card.addEventListener('click', handleCard, false);  // bubbling (the default)
card.addEventListener('click', handleCard);         // same as false

Let's prove the ordering. Same card and button, but now the card listens on the way down:

JS 
card.addEventListener('click', () => console.log('card (capture)'), true);
button.addEventListener('click', () => console.log('button'));
card.addEventListener('click', () => console.log('card (bubble)'));

// Clicking the button logs:
// → card (capture)
// → button
// → card (bubble)

The card gets two turns, because the card is on the path twice. That's the whole trick.

The options object

That bare boolean is the old signature. The modern form passes an object, which is strictly more capable:

JS 
element.addEventListener('click', handleClick, {
  capture: false,   // fire during capturing instead of bubbling
  once: true,       // auto-remove itself after firing one time
  passive: true,    // promise never to call preventDefault()
  signal: someSignal // an AbortSignal that can remove this listener later
});

Two of these deserve real explanations rather than a one-line gloss.

once

once: true means the browser removes the listener for you immediately after it fires. It's the tidy version of a pattern you've probably hand-rolled:

❌ Fiddly 
function onFirstScroll() {
  loadAnalytics();
  window.removeEventListener('scroll', onFirstScroll);
}
window.addEventListener('scroll', onFirstScroll);
✅ Same thing, no bookkeeping 
window.addEventListener('scroll', loadAnalytics, { once: true });

passive — and why scrolling cares

This one needs a bit of background, so let's get it.

Some events have a default action the browser performs on its own. A touchmove or a wheel event normally scrolls the page. But your JavaScript is allowed to cancel that, by calling event.preventDefault() inside the handler. Carousels and custom gesture libraries do exactly this: "no, don't scroll, I'm handling this swipe myself."

Now think about the browser's problem. You start swiping. The browser fires touchmove. It cannot know whether your handler is going to cancel the scroll until your handler has finished running. So it has to wait. It runs your JavaScript on the main thread, waits for it to return, checks whether preventDefault() was called, and only then does it scroll.

If your handler takes 100ms, the page freezes for 100ms before it moves a pixel. On a slow phone with a few of these registered, scrolling feels like dragging a fridge.

passive: true is you making a promise: "this handler will never call preventDefault()." With that promise in hand, the browser doesn't have to wait. It can start scrolling on the compositor thread immediately and run your handler whenever it gets around to it. Scrolling stays at 60fps regardless of how slow your handler is.

✅ Fast scroll tracking 
window.addEventListener('scroll', updateProgressBar, { passive: true });
el.addEventListener('touchstart', trackGesture, { passive: true });

If you break the promise and call preventDefault() inside a passive listener, it doesn't throw — it's simply ignored, and you get a console warning. That's a good thing to mention: passive isn't enforced by an exception, it's enforced by the browser ignoring you.

Wait, what about…?

"If passive is so much better, why isn't it the default?" For touchstart, touchmove, wheel and mousewheel on window, document and document.body, browsers did make it the default, precisely because so much of the web was suffering. Elsewhere it can't be the default without silently breaking every carousel that relies on cancelling scroll. So: default-passive on the big scroll containers, default-non-passive everywhere else.

target vs currentTarget vs this

This is the single most-asked detail in this whole area, and it's asked constantly because it's the hinge that delegation swings on. Get it solid.

Every handler receives an event object. Two of its properties sound identical and are not:

  • event.target — the element the event originated on. The deepest thing you actually clicked. This is the same value for every handler on the path.
  • event.currentTarget — the element whose listener is currently running. This changes as the event travels. It's always the element you called addEventListener on.

Back to the courier: target is the name on the package's address label — it says "Maya, office 604" the whole way. currentTarget is whoever is holding the package right now.

JS 
card.addEventListener('click', (event) => {
  console.log('target:', event.target.className);
  console.log('currentTarget:', event.currentTarget.className);
});

// Click the button inside the card:
// → target: buy      👈 what you clicked
// → currentTarget: card  👈 who's listening

// Click the card's padding, missing the button:
// → target: card
// → currentTarget: card

When you click directly on the listening element, they're the same. When you click something nested inside it, they differ. That difference is the entire foundation of delegation, which is why interviewers keep poking at it.

And this?

Inside a listener added with addEventListener, this equals currentTarget. The browser calls your function with the listening element as the receiver.

Unless you used an arrow function. Arrow functions don't get their own this — they inherit it from wherever they were written. So:

❌ Surprising 
card.addEventListener('click', () => {
  console.log(this); // → Window (or undefined in a module) — NOT the card
});
✅ Predictable 
card.addEventListener('click', function () {
  console.log(this); // → <div class="card">
});

// ...or just don't rely on `this` at all:
card.addEventListener('click', (event) => {
  console.log(event.currentTarget); // → <div class="card"> ✅ always works
});

My honest recommendation: use event.currentTarget and never think about this in a handler again. It works with arrows, with regular functions, with class methods, with everything. But know the this rule, because interviewers ask it.

A common misconception

"event.target is the element I attached the listener to." This belief works fine right up until someone nests an <span> or an icon inside your button — and then event.target is the span, your target.dataset.id is undefined, and you spend twenty minutes confused. target is where the event came from. currentTarget is where you're standing.

stopPropagation, stopImmediatePropagation, preventDefault

Three methods that people mash together into a vague notion of "cancel the event." They do three genuinely different jobs, and conflating them is a classic ding.

Before we can separate them, we need one term nailed down.

What "the default action" actually means

Some events cause the browser to do something on its own, with no JavaScript involved at all. Turn off JS entirely and these still happen — they're built into the browser:

  • Clicking an <a href> navigates to the URL.
  • Clicking a submit button submits the form and reloads the page.
  • Clicking a checkbox toggles it.
  • Typing a character into an input inserts that character.
  • Pressing Space scrolls the page down.
  • Right-clicking opens the context menu.
  • Dragging a link starts a drag operation.

That built-in behaviour is the default action. event.preventDefault() cancels it. That's all it does.

JS 
form.addEventListener('submit', (event) => {
  event.preventDefault(); // 👈 don't reload the page
  submitViaFetch(new FormData(form));
});

Critically: preventDefault does not stop the event from travelling. The event keeps right on bubbling to every ancestor. You cancelled the browser's built-in reaction, not the journey.

stopPropagation

event.stopPropagation() is the mirror image: it stops the journey and leaves the default action completely alone.

JS 
button.addEventListener('click', (event) => {
  event.stopPropagation(); // card's handler will NOT run
});

// Clicking the button now logs only:
// → button clicked

The courier gets confiscated at Maya's door. Nobody further along the route ever sees the package.

One subtlety worth knowing: stopPropagation() stops the event moving to the next element, but every other listener on the current element still runs. If you attached three click handlers to the same button and the first calls stopPropagation(), all three still fire — the event just doesn't go anywhere afterwards.

stopImmediatePropagation

Which is exactly what this one fixes. event.stopImmediatePropagation() does everything stopPropagation() does, plus it skips the remaining listeners on the current element.

JS 
button.addEventListener('click', (e) => {
  console.log('first');
  e.stopImmediatePropagation(); // 👈
});
button.addEventListener('click', () => console.log('second'));
card.addEventListener('click', () => console.log('card'));

// → first
// (that's it — "second" and "card" never run)

Swap in plain stopPropagation() and you'd get first and second, but still no card.

MethodStops travel to ancestors?Stops other listeners on the same element?Stops the browser's default action?
preventDefault()NoNoYes
stopPropagation()YesNoNo
stopImmediatePropagation()YesYesNo
Trap

return false from a handler is not a general "cancel everything." In an old-style inline handler (onclick="return false") or a jQuery handler it means preventDefault + stopPropagation. In a plain addEventListener callback it means absolutely nothing — the return value is discarded. Saying "you can just return false" in an interview is a small but real red flag.

A common misconception

"I'll add stopPropagation() to be safe." Please don't. stopPropagation() is not a defensive measure — it's an offensive one. It silently breaks any delegated listener higher up the tree: analytics, "click outside to close" handlers, focus management, third-party widgets. It's a common source of the bug report "the dropdown won't close when I click the thing inside the modal." Reach for it only when you genuinely mean "no ancestor should know about this."

Event delegation

Now we can build the thing all of that was setup for.

Say we have a to-do list, and every item has a delete button:

HTML 
<ul id="todo-list">
  <li>Buy milk       <button data-id="1">Delete</button></li>
  <li>Renew passport <button data-id="2">Delete</button></li>
  <!-- ...498 more -->
</ul>

The obvious approach is to loop and attach a listener to each button:

❌ 500 listeners 
document.querySelectorAll('#todo-list button').forEach((button) => {
  button.addEventListener('click', () => {
    deleteTodo(button.dataset.id);
  });
});

This works. It also has three problems, and they get worse as the app grows.

One: it's 500 listeners. Each one is a function object plus an entry in the browser's internal listener table, held in memory for as long as the elements live. For 500 rows that's survivable; for a big table or an infinite-scroll feed it's real memory and real setup time.

Two — and this is the big one — it only works on the elements that existed at the moment the loop ran. Add a new to-do after page load and its delete button is dead. It looks identical, it just has no listener. This is the single most common "my button doesn't work" bug in vanilla JS.

Three: teardown is a chore. When the list is destroyed you're supposed to remove 500 listeners, and you need a reference to each original function to do it. Most codebases quietly skip this and accumulate leaks.

The delegation move

So here's the idea. We know a click on a button bubbles up through the <li> to the <ul>. And we know event.target tells us what was actually clicked. So we can put one listener on the <ul> and ask, each time, "what did you actually click?"

✅ 1 listener 
document.querySelector('#todo-list').addEventListener('click', (event) => {
  const button = event.target.closest('button[data-id]');
  if (!button) return; // 👈 clicked something else in the list — ignore it

  deleteTodo(button.dataset.id);
});

That's the whole technique. Listen on a common ancestor, and use the event to figure out which descendant was involved. The name comes from the fact that the ancestor delegates the actual work based on what it's told.

The three reasons, stated plainly

When an interviewer asks "why delegation?", these are the three answers, in roughly this order of importance:

  1. Dynamically-added elements just work. The listener is on the parent, which was always there. New children inherit the behaviour without any wiring, because there's nothing to wire. This is the reason that actually changes how you write code.
  2. Fewer listeners, less memory, faster setup. One function object instead of N. No loop over the DOM on every render. Meaningful on large lists and tables.
  3. Teardown is trivial. One removeEventListener — or one abort() — instead of tracking N function references. Fewer chances to leak.
Wait, what about…?

"Isn't it slower, since every click in the list runs my handler even when it's irrelevant?" Technically yes — you do a closest() call on clicks you end up ignoring. But closest() walks a handful of parent nodes in native code; it's a rounding error next to the cost of holding hundreds of listeners and re-attaching them on every re-render. And the event was going to bubble through that ancestor regardless — you're not adding a trip, you're just showing up for one that already happens.

closest(), and the child-click trap

Let me show you the bug that closest() exists to fix, because you will absolutely hit it.

Here's a naive delegated handler:

❌ Buggy 
list.addEventListener('click', (event) => {
  if (event.target.tagName === 'BUTTON') {
    deleteTodo(event.target.dataset.id);
  }
});

Works perfectly. Then a designer adds an icon inside the button:

HTML 
<button data-id="1">
  <svg class="trash-icon">...</svg>
  <span>Delete</span>
</button>

And now delete is broken — but only sometimes. Click the button's padding and it works. Click the word "Delete" and nothing happens.

Why? Because event.target is the deepest element under the pointer. Click the text and target is the <span>, not the <button>. span.tagName is 'SPAN', the check fails, and the click is silently dropped. (With an SVG icon it's even nastier — tagName comes back as lowercase 'svg'.)

What we actually want to ask isn't "is the target a button?" It's "is the target inside a button?" And that's precisely what closest() answers.

✅ Fixed 
list.addEventListener('click', (event) => {
  const button = event.target.closest('button[data-id]');
  if (!button) return;
  deleteTodo(button.dataset.id);
});

element.closest(selector) starts at the element itself, then walks up through its ancestors, and returns the first one matching the selector — or null if it reaches the top without a match. It checks the element itself first, which is exactly the behaviour we want: click the button directly and it returns the button; click the span inside it and it returns the button too.

Trap

closest() walks all the way up the document, not just to your listening element. If you have nested delegated regions, you can match a button outside the container you're listening on. In practice: use a selector specific enough that it can't match elsewhere ('[data-action="delete-todo"]', not 'button'), and if you want to be rigorous, add if (!event.currentTarget.contains(button)) return;.

The scalable version: data attributes as a router

Once you have one delegated listener, the natural next step is to let it handle several actions. A data-action attribute turns it into a tiny router:

✅ One listener, many behaviours 
const actions = {
  delete: (el) => deleteTodo(el.dataset.id),
  edit:   (el) => openEditor(el.dataset.id),
  pin:    (el) => pinTodo(el.dataset.id),
};

list.addEventListener('click', (event) => {
  const trigger = event.target.closest('[data-action]');
  if (!trigger) return;

  actions[trigger.dataset.action]?.(trigger);
});

Adding a fourth action is now one line of markup and one line of JS. No new listeners, ever. This pattern is the core of how libraries like Stimulus work, and mentioning that connection is a nice signal of breadth.

Events that don't bubble

Delegation depends entirely on bubbling. So it's worth knowing that a handful of events don't bubble — and if you try to delegate them, you'll get silence and no error, which is the worst kind of failure.

The main offenders:

Doesn't bubbleBubbling counterpartWhat it means
focusfocusinAn element gained keyboard focus
blurfocusoutAn element lost keyboard focus
mouseentermouseoverPointer entered an element
mouseleavemouseoutPointer left an element
load, error (on <img>, <script>)— (use capture)Resource finished / failed loading
scroll (on elements)— (use capture)An element scrolled

So this quietly does nothing:

❌ Never fires 
form.addEventListener('focus', (e) => {
  highlightField(e.target); // 👈 focus doesn't bubble to the form
});
✅ Works 
form.addEventListener('focusin', (e) => {
  highlightField(e.target);
});

There's a second escape hatch that works even where no bubbling counterpart exists: listen in the capturing phase. Capturing goes top-down and doesn't depend on the event bubbling, so an ancestor can catch a non-bubbling event on the way in:

✅ Also works — catch it on the way down 
form.addEventListener('focus', handleFocus, true);

// The classic use: detect broken images anywhere on the page
document.addEventListener('error', (e) => {
  if (e.target.tagName === 'IMG') e.target.src = '/placeholder.png';
}, true);
Under the hood

Why don't mouseenter/mouseleave bubble? Because they were designed to mean "the pointer entered this specific element," which is what you want for hover effects. mouseover/mouseout bubble, and they also fire every time the pointer crosses into a child — so a hover menu built on mouseout flickers as you move over its own contents. That flicker is the historical reason mouseenter was invented. If you delegate hover with mouseover, you must compare event.relatedTarget to filter out moves between children.

You can check any event yourself: event.bubbles is a boolean on the event object.

How React does events

Everything so far has been the browser's own system. React sits on top of it and does something clever, and interviewers love asking about the seam between the two.

Here's the thing that surprises people. When you write this:

JSX 
<button onClick={handleBuy}>Buy now</button>

...React does not call addEventListener('click', handleBuy) on that button. There is no click listener on that DOM node. If you inspected it in DevTools' Event Listeners panel, you'd find nothing.

Instead, React does event delegation for you — the same technique we just built by hand, applied to your entire app. React attaches a small set of listeners to one container, and when a click bubbles up to it, React looks at event.target, figures out which component that DOM node belongs to, and then simulates the whole capture-and-bubble journey through your React component tree, calling the onClick props it finds along the way.

Your onClick is not a DOM listener. It's a prop that React consults when it replays the event through its own tree.

The React 17 change (this is the version detail they ask about)

Through React 16, those container listeners were attached to document. As of React 17, they're attached to the root container — the DOM node you passed to createRoot (typically #root).

Why the change? So you can run two React versions on one page, or embed React inside a jQuery/Angular app, without the two fighting over document. It also made stopPropagation behave the way people always expected.

What this means when you mix React with native listeners

Three consequences worth being able to state:

1. A native listener on an ancestor inside the root runs before your React handler. If you do someDiv.addEventListener('click', fn) on a wrapper div and a React button inside it is clicked, fn runs first — the native event has to bubble all the way to #root before React even hears about it. That ordering surprises everyone the first time.

2. Calling stopPropagation() in a native listener kills your React handler entirely. If the event never reaches #root, React never learns it happened. This is the classic "my onClick doesn't fire and there's no error" bug when integrating a third-party library.

3. Calling stopPropagation() in a React handler does stop listeners on document — in React 17+. React's synthetic stopPropagation forwards to the native event, and since React's listener sits at #root (below document), stopping there prevents the event ever reaching document. In React 16 this didn't work, because React's own listener was the one on document. If you ever wondered why a click-outside handler broke on a React upgrade, that's why.

JSX 
function Modal() {
  // Stops the click reaching a document-level "close on outside click"
  return <div onClick={(e) => e.stopPropagation()}>...</div>;
}
Trap

React portals render DOM somewhere else (say, directly under <body>) but events still propagate through the React tree, not the DOM tree. So a click inside a portalled modal fires the onClick of the component that rendered the portal, even though those nodes aren't DOM ancestors. This is deliberate and extremely useful, and it's a great "do they really understand it?" question.

Under the hood

A few more React details, in case they push: the object you receive is a SyntheticEvent, a cross-browser wrapper — e.nativeEvent gets you the real one. React 17 removed event pooling, so you no longer need e.persist() to read an event asynchronously. And not everything is delegated: React attaches onScroll, media events, and a few others directly to the node, because those don't bubble. onMouseEnter/onMouseLeave are synthesised from mouseout/mouseover for the same reason.

Removing listeners without leaking

Let's finish the lifecycle. Adding listeners is easy; removing them is where the bugs are.

Here's a piece of code that looks completely reasonable and does nothing at all:

❌ Buggy — the listener is never removed 
window.addEventListener('resize', () => recalculate());
// later...
window.removeEventListener('resize', () => recalculate());

Take a second with that one. The two functions look identical. Why doesn't it work?

Because they aren't the same function. Every time you evaluate a function expression, JavaScript creates a brand new function object. Two functions with identical source code are two different objects, the same way {} === {} is false. removeEventListener finds the listener to remove by identity — same type, same function reference, same capture flag — and there's no listener matching this second, freshly-minted function. So it removes nothing, silently, with no error.

The fix is to hold onto the reference:

✅ Fixed 
const handleResize = () => recalculate(); // 👈 one function, stored

window.addEventListener('resize', handleResize);
window.removeEventListener('resize', handleResize);

Same trap in a subtler costume — .bind() also returns a new function every time:

❌ Buggy 
el.addEventListener('click', this.handleClick.bind(this));
el.removeEventListener('click', this.handleClick.bind(this)); // different object!
✅ Fixed 
this.boundClick = this.handleClick.bind(this); // bind once, in the constructor
el.addEventListener('click', this.boundClick);
el.removeEventListener('click', this.boundClick);

And the capture flag counts as part of the identity, which catches people out:

❌ Buggy 
el.addEventListener('click', onClick, true);
el.removeEventListener('click', onClick);       // removes nothing — capture mismatch
el.removeEventListener('click', onClick, true); // ✅ this one works

(once and passive are not part of the identity. Only capture is.)

Why leaked listeners matter

Here's the mechanism, because "memory leak" is a phrase people say without being able to explain.

A listener attached to a long-lived object — window, document, a global event bus — is a reference held by that long-lived object. Your handler function closes over whatever it uses: component state, a big data array, a DOM node. So as long as the listener is registered, the garbage collector can see a live path to all of it and cannot free any of it.

Mount and unmount a component 200 times in a single-page app without cleaning up, and you now have 200 dead components' worth of state pinned in memory, and 200 handlers all running on every scroll event. The app gets slower the longer you use it, which is the signature symptom.

Wait, what about…?

"What if I just remove the element from the DOM?" Then the listener goes with it — if nothing else references either. Modern browsers happily collect a detached node along with its listeners. The leak comes from listeners on things that don't get removed: window, document, IntersectionObservers, timers, and anything holding a closure over your removed component.

AbortController: the modern way

Since 2021 there's a much nicer approach. AbortController — the same object used to cancel fetch requests — can cancel listeners, via the signal option.

✅ One abort() removes all of them 
const controller = new AbortController();
const { signal } = controller;

window.addEventListener('resize', handleResize, { signal });
window.addEventListener('scroll', handleScroll, { signal });
document.addEventListener('keydown', handleKey, { signal });
el.addEventListener('click', () => toggle(), { signal }); // 👈 inline is fine now!

// Teardown — removes all four:
controller.abort();

Three things this buys you. You don't need to keep a named reference to every handler, so inline arrow functions become safe. You clean up N listeners with one call instead of N. And the same controller can cancel in-flight fetches at the same time, so "everything this component started" becomes a single cancellation unit.

In React it's the tidiest effect cleanup you'll write:

✅ React effect cleanup 
useEffect(() => {
  const controller = new AbortController();
  const { signal } = controller;

  window.addEventListener('resize', onResize, { signal });
  document.addEventListener('keydown', onKey, { signal });

  return () => controller.abort(); // 👈 that's the whole cleanup
}, []);

Recipe: click-outside-to-close

This gets asked as a live-coding exercise all the time, and it's a lovely one because it exercises delegation, contains/closest, propagation, and cleanup all at once.

The requirement: a dropdown that closes when you click anywhere outside it. Since a click anywhere bubbles up to document, that's where we listen.

Here's the version almost everyone writes first, and it has a great bug:

❌ Buggy — the menu opens and instantly closes 
toggleButton.addEventListener('click', () => {
  menu.hidden = false;

  document.addEventListener('click', () => {
    menu.hidden = true;
  }, { once: true });
});

Can you see it? The click that opened the menu is still bubbling. It leaves the button, continues up to document, and hits the listener we just added — one that's now looking for the next click and finds the current one. The menu closes in the same tick it opened.

The fix isn't stopPropagation() (that would break other delegated handlers on the page). The fix is to ask where the click came from — which is exactly the delegation mindset:

✅ Fixed 
const controller = new AbortController();
const { signal } = controller;

document.addEventListener('click', (event) => {
  if (menu.hidden) return;

  const clickedInside = menu.contains(event.target)
    || toggleButton.contains(event.target); // 👈 the toggle counts as "inside"

  if (!clickedInside) menu.hidden = true;
}, { signal });

document.addEventListener('keydown', (event) => {
  if (event.key === 'Escape') menu.hidden = true;
}, { signal });

// teardown: controller.abort();

Because the document listener now checks contains(), the opening click harmlessly matches "inside the toggle" and the menu stays open. One persistent listener, no re-registration, and Escape handled too — which is the accessibility detail that makes an interviewer nod.

Wait, what about…?

"Why contains() rather than closest()?" Either works; they ask the same question from different ends. menu.contains(event.target) starts from the menu and looks down; event.target.closest('.menu') starts from the click and looks up. Use contains when you already hold the element reference, closest when you only have a selector.

Two upgrades worth mentioning if you want to show polish: use pointerdown instead of click so the menu closes the instant the press starts (feels snappier, and dodges edge cases where the target is removed before click fires), and consider focusout so keyboard users tabbing away also close it.

The interview layer

How this gets asked

The phrasings you'll actually hear:

  • "Explain event bubbling."
  • "What is event delegation and why would you use it?"
  • "What's the difference between event.target and event.currentTarget?"
  • "I have a list where items get added dynamically. How do you handle clicks on them?"
  • "What does preventDefault do? How is it different from stopPropagation?"
  • "How does React handle events differently from the DOM?"
  • "What's a passive event listener?"
  • "Build a dropdown that closes when you click outside it." (live coding)

The first two are recall. Everything after is depth — they're checking whether the model in your head is real or memorised.

Model answer — "What is event delegation?"

"Instead of putting a listener on every item, I put one listener on a shared ancestor and use event.target to work out what was actually clicked — usually with closest(), so it still works if you click an icon inside the button. It relies on bubbling: the click travels from the element up through its ancestors, so the parent sees every click in its subtree. The big win isn't really performance, it's that elements added later work automatically, because there was never anything attached to them in the first place. And teardown is one listener instead of hundreds."

Why that answer lands: it names the mechanism (bubbling), names the modern tool (closest), pre-empts the child-element gotcha without being asked, and — crucially — ranks the benefits correctly. Candidates who lead with "it's faster" sound like they read it on a flashcard. Leading with "dynamic elements work" sounds like someone who has shipped it.

Follow-ups, with answers

"Why use delegation instead of just adding listeners to each element?"

Three reasons, and I'd give the memory one last. Dynamically-added elements work with no extra wiring — that's the one that changes how you write code. Teardown is a single removal rather than tracking N function references, so you leak less. And yes, one function object instead of hundreds, plus no DOM loop on every render. The trade-off is a slightly less direct handler and a dependency on the event bubbling, so it doesn't work for focus or mouseenter without switching to focusin/mouseover.

"target vs currentTarget?"

target is where the event originated — the deepest element clicked. It's the same for every handler on the path. currentTarget is the element whose listener is running right now, so it changes as the event travels and always equals the element you called addEventListener on. In a non-arrow handler, this equals currentTarget; in an arrow function it doesn't, so I just use event.currentTarget and never worry about it. Delegation is exactly the case where they differ, and that difference is the whole point.

"How do you handle a click on a dynamically added element?"

Delegate. Put the listener on a container that exists at load time and check event.target.closest(...) inside it. The alternative — re-running an attach loop after every DOM update — means double-binding bugs and stale listeners. If for some reason I truly had to attach directly, I'd attach at creation time in whatever function builds the element, not in a rescanning loop.

"Does stopPropagation stop the default action?"

No — they're independent. stopPropagation stops the event travelling to other elements; the browser's built-in behaviour still happens. Call it on an anchor's click and the page still navigates. preventDefault is the opposite: it cancels the built-in behaviour but the event keeps bubbling. If you want both you call both. And stopImmediatePropagation additionally skips the other listeners registered on the same element, which plain stopPropagation doesn't.

"Why doesn't my removeEventListener work?"

Almost always because it isn't being given the same function reference. An arrow function or a .bind() call creates a new object each time it's evaluated, so the remove call passes a function that was never registered — and it fails silently, no error. The fix is to store the handler in a variable, or bind once. The other cause is a capture mismatch: if you added with capture: true you must remove with capture: true, since capture is part of the listener's identity. These days I'd sidestep the whole thing with an AbortController signal — one abort() removes everything, and inline arrows become safe.

"How does React handle events differently?"

React does delegation for you. Your onClick isn't a real listener on that DOM node — React attaches a set of listeners at the root container, and when a native event bubbles up there, it maps the target back to a component and replays capture-and-bubble through the React tree, calling the props it finds. Since React 17 those listeners are on the root container rather than document, which lets multiple React versions coexist on a page and makes stopPropagation in a React handler correctly block a document-level listener. The practical gotcha is mixing: a native listener on a DOM ancestor inside the root fires before your React handlers, and if it calls stopPropagation your onClick never fires at all. Also, portals propagate through the React tree, not the DOM tree.

"What's a passive event listener?"

It's a promise to the browser that the handler won't call preventDefault(). Normally, for events like touchmove or wheel, the browser has to run your handler and wait to see whether you cancelled the scroll before it can scroll — so a slow handler blocks scrolling and you get jank. With { passive: true } it can scroll immediately on the compositor thread and run your handler whenever. Browsers already default to passive for touchstart, touchmove and wheel on window, document and body because of how widespread the problem was. If you call preventDefault in a passive listener it's ignored with a console warning rather than throwing.

"How would you implement a click-outside-to-close dropdown?"

One listener on document for clicks. Inside it, bail early if the menu is closed, then check whether event.target is inside the menu or inside the toggle using contains() or closest() — if not, close. The bug people hit is registering the document listener inside the open handler, because the opening click is still bubbling and immediately closes the menu; checking contains on a persistent listener avoids that entirely, and it's better than stopPropagation, which would break other delegated handlers on the page. I'd also close on Escape, and register both with an AbortController signal so cleanup is one abort(). If I wanted extra polish, pointerdown instead of click feels snappier.

"Can you delegate a focus event?"

Not with focus — it doesn't bubble. Use focusin/focusout, which are the bubbling equivalents, or listen for focus in the capturing phase with addEventListener('focus', fn, true), since capturing doesn't depend on bubbling. Same story for mouseenter/mouseleave, where the bubbling counterparts are mouseover/mouseout — though those also fire when moving between child elements, so you have to filter on relatedTarget.

"If I add a capturing and a bubbling listener on the same element, which runs first?"

Capturing, since the capture phase happens first. The exception is when that element is the target itself: at the target, the two phases collapse, and listeners fire in registration order regardless of the capture flag. That's a nice detail to know, but I wouldn't rely on it in real code.

Traps — the answers that get you dinged

Trap 1

"Delegation is mainly a performance optimisation." It's technically true and strategically wrong — it makes you sound like you learned it from a list. The dominant benefit is that dynamic content works for free. Say that first, then mention memory.

Trap 2

"preventDefault stops the event." It stops the browser's reaction, not the event's travel. Being fuzzy here is the fastest way to signal that you've been copy-pasting e.preventDefault(); e.stopPropagation(); without knowing which one you needed.

Trap 3

"React attaches listeners to document." True for React 16 and earlier, wrong since React 17. If you're not sure of the version, say "React 17 moved them from document to the root container" — that phrasing is correct either way and shows you know the history.

Trap 4

Checking event.target.tagName === 'BUTTON' in a live-coding round. The interviewer will nest a <span> in the button and watch what happens. Reach for closest() immediately and, ideally, say why as you type it.

Trap 5

Reaching for stopPropagation() to fix a click-outside handler. It works locally and quietly breaks analytics, focus management, and any other delegated listener above you. The senior answer is "check where the click came from," not "stop the click."

One last thing

If you remember nothing else from this guide, remember the courier. A click doesn't hit an element — it walks a path from the top of the document down to the thing you touched and back out again, and every element on that path gets a turn.

Bubbling, capturing, delegation, stopPropagation, click-outside handlers, React's whole synthetic event system: all of it is just different things you can do while standing somewhere along that path. Once the path is real in your head, you're not memorising eight rules any more. You're reading one picture. 🎯
