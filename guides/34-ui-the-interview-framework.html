The 60 seconds where people lose the interview

You get the prompt: "Build a star rating component." And your hand goes straight to the keyboard, and you start typing <div className="stars">.

That's the mistake. Not a fatal one, but you've just committed to a structure before you know what the thing needs to remember, and in about eight minutes you'll be deleting it.

Here's the reframe that makes all of this easy. A UI component is a function from state to pixels. That's the whole thing. React even makes it literal: UI = f(state). So there are only ever two questions:

  1. What does this thing need to remember? (the state)
  2. How does the screen look for any given value of that memory? (the render)

Everything else — the event handlers, the CSS, the edge cases — is downstream of getting those two right. If you nail the state, the JSX writes itself. If you guess at the state, no amount of clever JSX saves you.

Say this out loud in the first minute

"Before I write anything, let me figure out what state this needs." Then think out loud for thirty seconds. Interviewers love this. It's the single cheapest signal of seniority available to you, and it costs you half a minute.

The five steps

Every single component in this series gets built the same way. Memorise this order, not the components.

1. Clarify — two questions, no more

You're not gathering requirements, you're showing you know where the ambiguity lives. Two questions, then move. Good ones are almost always some version of:

  • "Where does the data come from — hardcoded array or an API?" This decides whether you need loading/error states, which is half the complexity.
  • "Controlled or self-contained?" i.e. does the parent own the value and pass value/onChange, or does the component own it internally? (More on this in a second — it's a bigger deal than it sounds.)

2. State — say it out loud, then write it as a comment

Literally type the state into your file as a comment before any JSX:

// state:
//   rating   → number, the committed value
//   hovered  → number | null, the preview value while the mouse is over
// derived:
//   filled   → hovered ?? rating

This comment is your spec. Now everything else is transcription.

3. Static render — no handlers, no interactivity

Hardcode the state to a realistic value and get pixels on the screen. const [rating] = useState(3) and render five stars where three are gold. Don't wire anything yet.

Why this matters: it separates "can I render this?" from "can I update this?" If both are broken at once you can't tell which is which. Get one working, then the other.

4. Wire — each event handler is one line that sets state

Now add the handlers. And here's the rule that keeps you out of trouble: a handler's only job is to describe the new state. Not to touch the DOM, not to compute layout. onClick={() => setRating(i + 1)}. If a handler is more than a few lines, your state shape is probably wrong — go back to step 2.

5. Polish — and narrate it even if you don't finish

Keyboard support, ARIA roles, empty states, the "what if the array is empty" case. You will often run out of time here, and that is completely fine as long as you say what you'd do. "I'd add role="radiogroup" here and arrow-key navigation" scores nearly as well as writing it, and costs eight seconds.

Step 2 is the whole interview: state shape

Let me convince you with a comparison. Same component — an accordion — two ways to hold the state.

❌ State that fights you
// one boolean per section
const [aOpen, setAOpen] = useState(false);
const [bOpen, setBOpen] = useState(false);
const [cOpen, setCOpen] = useState(false);

Now the interviewer says "only one section open at a time." You have to write a handler that sets one true and two false, and if they add a fourth section you have to edit four places. It doesn't scale, and worse, it lets you represent a state that's illegal — all three open at once, which the requirements say can't happen.

✅ State that works for you
// which one is open? that's the actual question.
const [openId, setOpenId] = useState(null); // → 'shipping' | null

"Only one open" is now structurally impossible to violate. The handler is one line. Adding a fourth section requires zero changes. And if they later say "allow multiple open", you swap it for a Set and change one line.

The principle worth stating in the interview

Make illegal states unrepresentable. If the requirements say two things can't be true at once, find a shape where they can't be, rather than a shape where you promise to keep them in sync. Say this sentence out loud and watch the interviewer's face.

The four state shapes that cover almost everything

Here's the shortcut. Nearly every component in this series is one of four shapes. When you get a prompt, ask "which of these four is it?" and you'll be right most of the time.

ShapeLooks likeUse whenComponents
A flag useState(false) One thing is on or off Modal, like button, show/hide password
A pointer useState(id) or an index Exactly one of N is selected Tabs, accordion (single), carousel, star rating, traffic light, wizard step
A set useState(new Set()) Any number of N are selected Nested checkboxes, multi-open accordion, expanded tree folders
A list of records useState([]) of objects with id Items get added, removed, edited Cart, toasts, todos, comments, search results

Two notes that will save you real time:

For a pointer, prefer an id over an index. Indices break the moment the list is filtered, sorted or reordered — your "selected" item silently becomes a different item. An id survives all of that.

For a list of records, every item needs a stable id from birth. Generate it when you create the item (crypto.randomUUID(), or a useRef(0) counter), not at render time. That id is your React key, your removal target, and your update target. Getting this right on line one prevents about four different bugs later.

Under the hood — why index keys bite

React uses key to decide "is this the same component as last render, or a new one?" With key={index}, deleting the first of three items means item 2 keeps key 1 — so React reuses the old component instance, and any internal state (a focused input, a half-typed value, a CSS transition) stays attached to the wrong item. With stable ids, React correctly unmounts the removed one.

Don't store what you can compute

The second most common state mistake, after bad shape, is storing too much. Cart total is the classic:

❌ Two sources of truth
const [items, setItems] = useState([]);
const [total, setTotal] = useState(0); // 👈 now you must update this everywhere
✅ One source of truth
const [items, setItems] = useState([]);
const total = items.reduce((sum, i) => sum + i.price * i.qty, 0); // just compute it

The second version cannot ever be out of sync, because there's nothing to sync. Every render recomputes it from the one thing that's true.

"But isn't that slow?" No. It's an array pass over a handful of items, and React was going to re-render anyway. If the list is genuinely huge you wrap it in useMemo — but do that when you measure a problem, not before. Reaching for useMemo unprompted in a machine-coding round reads as cargo-culting, and interviewers notice.

So the test for "should this be state?": can I calculate it from other state or props? If yes, it's not state. Filtered lists, sorted lists, totals, "is the form valid", counts, the currently-visible page of results — all derived, none of them state.

Wait — what about the debounced value, isn't that derived?

Good catch, and it's the exception that proves the rule. A debounced value is derived from the input value plus time, and you can't compute time during render. Anything that depends on time, or on an async result, genuinely needs to be state. That's why useDebounce holds state internally.

Two worked run-throughs

Let's run the method on two prompts, fast, so you see the shape of the thinking rather than the shape of the code.

"Build a tabs component"

Clarify: "Are the tab panels all rendered and hidden with CSS, or only the active one mounted?" (This is a great question — it's the actual design decision, and it shows you know they're different.) Shape: a pointer — activeId. Static: render the tab strip from an array of {id, label, content}, hardcode activeId to the first. Wire: onClick={() => setActiveId(tab.id)}. Polish: role="tablist", arrow-key navigation, roving tabIndex.

Total genuine decisions: one. Everything else was transcription.

"Build a toast notification system"

Clarify: "Should toasts stack, and do they auto-dismiss on a timer?" Shape: a list of records — [{id, message, type}], ids generated at push time. Static: hardcode two toasts and get them stacked in the corner. Wire: addToast appends, removeToast(id) filters by id, and each toast sets a setTimeout in an effect with a cleanup that clears it. Polish: pause the timer on hover, role="status" so screen readers announce it, exit animation.

Notice the pattern: the moment you said "list of records with ids", remove became obvious. That's what a good state shape does — it hands you the handlers.

What to build first, second, never

Time management is graded, even when nobody says so. Here's the priority order I'd hold in my head:

  1. The happy path, ugly. Unstyled, one hardcoded array, clicking works. A working ugly thing beats a beautiful broken thing every single time.
  2. The stated requirements, all of them. If they said "and show the total", the total must exist before you make anything pretty.
  3. Obvious edge cases. Empty list, single item, the last item removed.
  4. Accessibility. Real semantic elements — <button> for clickable things, always. This one is nearly free and disproportionately rewarded.
  5. Styling. Enough that it reads as the thing it is. No more.

And the things to not do, which is equally important:

  • Don't reach for a reducer on a two-field component. useReducer earns its keep when several fields change together in defined ways (a wizard, a game board). On a star rating it's ceremony.
  • Don't build an abstraction for the second case. Two similar things is not a pattern. Wait for the interviewer to ask.
  • Don't optimise anything unprompted. See above.
  • Don't go silent. Ten quiet minutes reads as ten stuck minutes, even if you're flying. Narrate: "okay, now I need the remove handler, so I'll filter by id."
What they're actually scoring

Almost never "did it work perfectly." It's: did you decompose sensibly, did you pick a state shape that scales, can you talk while you code, and do you know what you'd do next. A candidate who finishes 70% and clearly explains the remaining 30% usually beats one who silently finishes 100%.

The one follow-up you will definitely get

Whatever you build, there's a decent chance of: "How would you make this reusable / controlled?"

The answer is the same every time. An uncontrolled component owns its state inside; you use it as <StarRating /> and it just works, but the parent can't read or set the value. A controlled one takes value and onChange props and holds no state at all — the parent owns it, which is what you need for forms, resets, and syncing to a server.

// support both: internal state, overridden by the prop when present
const [internal, setInternal] = useState(defaultValue);
const isControlled = value !== undefined;
const current = isControlled ? value : internal;

function commit(next) {
  if (!isControlled) setInternal(next);
  onChange?.(next);            // 👈 always tell the parent either way
}

That's the same six lines every native-feeling component uses, and knowing it cold turns a scary follow-up into a two-minute win.

Cheat sheet

  • UI = f(state). Get the state right and the JSX is transcription.
  • Order: clarify (2 questions) → state shape → static render → wire handlers → polish.
  • Four shapes: flag (boolean) · pointer (selected id) · set (many selected) · list of records (items with ids).
  • Pointer by id, not index. Indices break under filter/sort/reorder.
  • Ids at creation time, not render time. They're your key, your remove target, your update target.
  • Make illegal states unrepresentable — one openId, not three booleans.
  • If you can compute it, don't store it. Totals, filtered lists, validity.
  • Handlers set state and nothing else. A fat handler means a wrong shape.
  • Working and ugly beats pretty and broken.
  • Controlled vs uncontrolled is the universal follow-up — know the value ?? internal pattern cold.
  • Narrate. Silence is indistinguishable from being stuck.
