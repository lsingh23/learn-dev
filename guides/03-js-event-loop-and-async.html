The Event Loop, Promises & Async/Await

How JavaScript does several things at once while only ever doing one thing at a time — and how to talk about it without freezing up.

I want to start with a puzzle, because this whole topic is best learned by getting something wrong first.

What does this print?
console.log('A');

setTimeout(() => console.log('B'), 0);

Promise.resolve().then(() => console.log('C'));

console.log('D');

Take a real guess. Say it out loud, or type it somewhere. Most people who've written JavaScript for a year say A B C D or A D B C. Both are wrong.

The answer is A D C B. That setTimeout with a delay of zero milliseconds loses a race to a promise that also has nothing to wait for. If you can explain exactly why, in about ninety seconds, you have already passed the most commonly-asked JavaScript interview question in the industry.

By the end of this guide you'll be able to. But I'm not going to hand you a rule to memorise — rules evaporate under interview pressure. I'm going to build you a picture, and then the answer falls out of the picture every time.

1. "JavaScript is single-threaded" — what that actually means

You've heard this sentence. It gets repeated so often that it's become a kind of incantation people say without inspecting. And it causes a very specific confusion, which goes like this:

If JavaScript can only do one thing at a time, how does setTimeout work? Something has to be counting while my code keeps running. And how do I download three files at once?

Great question. The confusion comes from a sloppy sentence. Here's the precise version:

There is exactly one thread that executes your JavaScript. One. At any given instant, exactly one line of your JS is running, and nothing else in your JS runs until that line finishes.

That's it. That's the whole claim. Notice what it does not say:

  • It does not say the browser is single-threaded. Chrome is a huge multi-threaded program. There are threads for networking, threads for parsing images, threads for compositing pixels onto your screen, threads for timers.
  • It does not say your program can only do one thing at a time. Three HTTP requests can absolutely be in flight simultaneously — the network stack handles them, and the network stack is not JavaScript.
  • It does not say JavaScript can never use more than one core. Web Workers give you genuinely parallel JS — but each worker has its own separate single thread and its own memory, and they communicate by passing messages, never by sharing variables.

Here's the analogy I want you to carry through this whole guide.

The one-cook kitchen

Picture a small restaurant with one cook. The cook is the JS thread. The cook can only do one thing at a time — chop, stir, plate. Nothing gets done in the kitchen unless the cook does it.

But the restaurant has appliances: an oven, a kettle, a delivery driver who fetches ingredients. The cook puts a tray in the oven and sets a timer, then walks away and does something else. The oven does not need the cook to stand there. When the timer dings, the cook doesn't drop the knife mid-chop — the ding goes onto a ticket spike, and the cook picks it up when they finish the current task.

The oven, kettle and driver are the browser's other threads. The ticket spike is a queue. The rule "finish the current task before picking up the next ticket" is the event loop.

Where the analogy breaks: a real cook can glance at the oven and abandon a task halfway. The JS thread genuinely cannot. It runs a task to completion, no exceptions, no interruptions. Hold onto that — it's the source of every surprise in this topic.

So: concurrency, not parallelism. JavaScript is concurrent (many things in progress at once) without being parallel (many things executing at once). That distinction is worth a lot of points in an interview and it costs you one sentence to say.

A common misconception

"setTimeout spawns a thread that runs my callback." No. Your callback is always run by the one JS thread. The browser's timer thread only does the counting; when the time is up it does nothing more dramatic than push your callback onto a queue. Your callback then waits its turn like everybody else.

2. The four pieces of machinery

To predict output order you need four things in your head. Let me build them one at a time, and I promise not to use any of them before I've explained it.

2a. The call stack

When you call a function, JS pushes a frame onto a stack: a little record of "I am inside this function, and here's where to return to." When the function returns, that frame is popped off.

Stack in slow motion
function formatPrice(cents) {
  return '$' + (cents / 100).toFixed(2);
}

function renderTotal(cart) {
  return 'Total: ' + formatPrice(cart.totalCents);
}

renderTotal({ totalCents: 4250 });  // → "Total: $42.50"

At the deepest moment, the stack is: renderTotal on the bottom, formatPrice on top. formatPrice returns, its frame pops. renderTotal returns, its frame pops. Stack is empty again.

"The stack is empty" is the single most important state in this whole guide. It's the moment the cook has plated the dish and is free. Everything asynchronous happens at that moment and never before it.

2b. Web APIs (the host environment)

Here's something that surprises people: setTimeout is not part of JavaScript. Neither is fetch, or addEventListener, or localStorage. Open the JavaScript language spec and you will not find them. They're provided by the host environment — the browser, or Node, or Deno.

The language itself gives you objects, functions, Math, JSON, promises. Everything that touches the outside world — time, network, screen, disk — is a capability the host lends you. And crucially, those capabilities are implemented in the host's own code, running on the host's own threads, not on the JS thread.

So when you write setTimeout(saveDraft, 3000), what happens is: JS hands a function reference and a number to the browser, and the browser says "cool, I'll take it from here" and JS immediately moves on. The browser has a timer thread doing the counting.

2c. The task queue (a.k.a. the macrotask queue, callback queue)

When the browser finishes a job you asked for — the 3000ms elapsed, the HTTP response arrived, the user clicked — it can't just run your callback. The JS thread might be busy. So it puts the callback in a line: the task queue.

It's a FIFO queue — first in, first out. Fair, orderly, boring. That's the ticket spike from the kitchen.

2d. The microtask queue

There is a second queue, and it is not equal to the first. It's a VIP line. Promise callbacks go here, and so do queueMicrotask() callbacks and MutationObserver callbacks.

The microtask queue has one rule that changes everything: it gets drained completely, right down to empty, before the event loop is allowed to take a single item from the task queue. And if draining it adds more microtasks, those get drained too, in the same pass.

That's the whole reason C beat B in the opening puzzle. Now let's see all four pieces in one picture.

3. The diagram

Draw this on the whiteboard when they ask. Seriously — reach for the pen. Interviewers love a candidate who diagrams, because it shows you're reasoning from a model rather than reciting.

4. The loop algorithm, precisely

Here is the actual cycle. Learn these five lines and you can answer almost any ordering question by hand-simulating them.

  1. Run the current task to completion. The JS on the stack runs until the stack is empty. Nothing preempts it. (The very first "task" is the initial evaluation of your <script>.)
  2. Drain the entire microtask queue. Pull microtasks off one by one and run each to completion. If running one adds new microtasks, they go on the end of the same queue and also get run, in this same pass. Keep going until the queue is genuinely empty.
  3. Maybe render. If the browser thinks it's time to paint a frame (roughly 60 times a second), it now runs requestAnimationFrame callbacks, recalculates styles, does layout, and paints. This is the only window in which the screen can update.
  4. Take exactly ONE task from the task queue and run it.
  5. Go back to step 2. Forever.

Read step 2 and step 4 next to each other. That asymmetry — all the microtasks, but one macrotask — is the engine of every trick question on this topic.

Wait — why the asymmetry? Why not drain both?

Because of step 3. The browser wants to get back to rendering as often as it can, so the screen stays responsive. If it drained the whole task queue every turn, a burst of a hundred click events or timers would lock the UI until every last one had run.

Taking one macrotask per turn means the browser gets a chance to paint between them. Microtasks are treated as "the rest of the thing you were just doing" — the leftover crumbs of the current task — so it finishes them all first to reach a consistent state before showing anything to the user. A half-resolved promise chain is not a state you want to paint.

5. Macrotasks vs microtasks

Time to sort things into buckets. This is one of the few places where a table genuinely beats prose, because it's reference material you'll want to skim the morning of the interview.

Macrotasks (tasks)Microtasks
setTimeout callbacks .then / .catch / .finally callbacks
setInterval callbacks the code after an await
DOM/UI events: click, keydown, scroll queueMicrotask(fn)
I/O completion (in Node), setImmediate (Node) MutationObserver callbacks
the initial <script> evaluation process.nextTick (Node — even higher priority)
One per loop turn. Browser may render between them. All of them, every turn. No render until the queue is empty.

Wait — where does fetch go?

Both, in a sense, and this trips people up. The arrival of the network response is a task — the browser queues a macrotask that resolves the promise. But your .then(...) callback attached to that promise is a microtask, which runs during the drain immediately after that task. So a fetch costs you one macrotask turn to settle, then your handlers run as microtasks.

One more thing worth stating plainly, because interviewers ask it: "microtask" doesn't mean "small" and "macrotask" doesn't mean "big." The names are about priority and scheduling, not size. A microtask that runs a million-iteration loop will block everything just as hard as a macrotask doing the same.

6. Puzzle 1, solved step by step

Back to where we started. Now we have the machine, let's run it by hand.

The opening puzzle
console.log('A');
setTimeout(() => console.log('B'), 0);
Promise.resolve().then(() => console.log('C'));
console.log('D');
  1. The whole script is one macrotask. It starts running on the stack.
  2. console.log('A') → prints A.
  3. setTimeout(fn, 0) → JS hands fn and 0 to the browser's timer service and immediately continues. Nothing is printed. The browser will put fn in the task queue once the timer fires.
  4. Promise.resolve() creates an already-fulfilled promise. Calling .then(fn) on an already-fulfilled promise schedules fn onto the microtask queue right now. Still nothing printed.
  5. console.log('D') → prints D.
  6. Script ends. Stack is empty. The task is complete.
  7. Step 2 of the loop: drain microtasks. There's one — the C callback. Prints C. Queue is now empty.
  8. Step 4: take one macrotask. The timer's callback is sitting there. Prints B.

A D C B. And notice you never had to memorise a rule — you just walked the machine.

Let's push on the edges with a nastier one that tests whether you really understood "drain entirely, including newly-added."

Puzzle 1b — predict before you open the answer
setTimeout(() => {
  console.log('timeout 1');
  Promise.resolve().then(() => console.log('micro in timeout 1'));
}, 0);

setTimeout(() => console.log('timeout 2'), 0);

Promise.resolve().then(() => {
  console.log('micro 1');
  Promise.resolve().then(() => console.log('micro 2'));
});

console.log('sync');
Reveal the answer and the walkthrough 
sync
micro 1
micro 2
timeout 1
micro in timeout 1
timeout 2

Both timers get queued. The .then gets queued as a microtask. sync prints, script task ends.

Drain microtasks: micro 1 runs and — this is the bit — adds another microtask. We do not stop. The queue isn't empty, so we keep going: micro 2 runs. Now it's empty.

One macrotask: timeout 1 runs and queues a microtask. That task finishes, so we're back at step 2 — drain microtasks — and micro in timeout 1 runs before the second timer, even though the second timer was queued long before it existed.

Then, finally, the next macrotask: timeout 2.

The takeaway to say out loud in an interview: "After every single macrotask, the microtask queue is drained again. Microtasks always jump the line."

7. Why setTimeout(fn, 0) is never actually 0ms

Three separate reasons, and a good answer names at least two.

1. It's a minimum, not a promise. The delay says "don't queue this callback before 0ms have passed." It says nothing about when it will run. If the stack is busy for 5 seconds, your 0ms timer fires after 5 seconds. The browser physically cannot interrupt running JS.

A 0ms timer taking 2 seconds
setTimeout(() => console.log('finally!'), 0);

const start = Date.now();
while (Date.now() - start < 2000) {}  // 👈 blocking the thread

console.log('done blocking');
// → done blocking
// → finally!      (about 2 seconds later)

2. The spec mandates a 4ms floor for nested timers. If you chain setTimeout inside setTimeout five levels deep, browsers clamp any delay below 4ms up to 4ms. It's an old anti-runaway-loop protection. So a naive setTimeout(loop, 0) recursion runs at roughly 250 iterations per second, not as fast as possible.

3. Background tabs get throttled hard. Move the tab to the background and browsers clamp timers to about once per second, sometimes far less for deeply backgrounded tabs.

Wait — so what is setTimeout(fn, 0) good for?

It means "run this after the current task and its microtasks are completely finished, and after the browser has had a chance to render." It's a yield. Classic uses: letting the browser paint a loading spinner before you start heavy work, or breaking a long computation into chunks so the UI stays alive. If all you want is "after the current synchronous code but before rendering", use queueMicrotask instead — it's more precise and doesn't cost you a frame.

8. Microtask starvation

"Drain the microtask queue entirely" has a dark side. What if it never empties?

❌ Freezes the page, permanently
function loop() {
  queueMicrotask(loop);  // 👈 each one schedules another
}
loop();

The loop reaches step 2, starts draining, and every microtask it runs adds another. The queue never empties. The event loop never reaches step 3 (render) or step 4 (next task). Your page is frozen forever — clicks do nothing, animations stop, the tab has to be killed. There's no escape hatch, because "drain entirely" has no budget or timeout.

Compare with the macrotask version:

✅ Runs forever, but the page stays alive
function loop() {
  setTimeout(loop, 0);  // 👈 one per loop turn
}
loop();

Here each iteration is one macrotask, so between every iteration the browser gets to render and process input. Wasteful, but not fatal.

This is a lovely thing to bring up unprompted, because it proves you understand the consequence of the drain rule rather than just having memorised it.

9. Blocking the event loop — the practical reason anyone cares

Here's the thing to understand about the browser: rendering and JavaScript share the same thread. Look at step 3 of the algorithm — the paint happens between tasks, never during one. So while your JS is running, the screen is frozen. Not "slow." Frozen.

❌ The UI dies for 3 seconds
button.addEventListener('click', () => {
  const results = [];
  for (let i = 0; i < 50_000_000; i++) {
    results.push(expensiveScore(i));   // 👈 ~3 seconds of pure JS
  }
  render(results);
});

During those three seconds: CSS animations stop mid-motion. Hover states don't change. The user clicks again — the click is queued, not lost, so it fires later and they get a double submission. Text can't be selected. Chrome may show "Page unresponsive."

This is why interviewers care. It isn't trivia. It's the difference between an app that feels snappy and one that feels broken. And the fixes all come straight from the model:

  • Chunk it. Do 1,000 items, then setTimeout(..., 0) to yield so the browser can paint, then do the next 1,000.
  • Move it off-thread. A Web Worker runs on a genuinely separate thread with its own event loop. It can't touch the DOM, but it can crunch numbers and postMessage the result back. This is the real answer for heavy CPU work.
  • Don't do it at all. Paginate, virtualise the list, or ask the server to do the aggregation.

A common misconception

"I'll wrap the heavy loop in a promise / an async function and it won't block." It absolutely will. Promises don't create threads — they only control when your code runs, never where. A 3-second synchronous loop inside a .then blocks the thread for 3 seconds, exactly like everywhere else. Only a Worker gets you off the main thread.

10. Promises, from first principles

Let's put the loop down for a moment and build promises properly, because half of the event-loop questions are really promise questions in disguise.

A promise is an object representing a value that isn't here yet. That's it. It's a receipt. You hand it around, you attach instructions to it — "when the value shows up, do this" — and at some point it gets filled in.

The coat check ticket

You give your coat to the attendant and get a numbered ticket. The ticket is not the coat. But it will get you the coat, and you can hand it to a friend, or put it in your pocket and forget about it, or write on the back "when you collect this, also grab my umbrella."

Two things can happen: the coat comes back (fulfilled) or the attendant tells you there was a fire and it's gone (rejected). Either way, once the ticket is settled, that's it — it's settled forever. You can't un-collect a coat.

Where it breaks: a real ticket is single-use. A promise can be "cashed in" any number of times — attach ten .thens and all ten fire, and you can attach one an hour after it settled and it'll still fire immediately.

The three states

  • pending — nothing has happened yet. The starting state.
  • fulfilled — it worked; there's a value.
  • rejected — it failed; there's a reason (conventionally an Error).

Two words that make you sound precise: a promise that is either fulfilled or rejected is settled. And resolved is subtly different from fulfilled — a promise is "resolved" once its fate is locked in, which might mean it's locked to another promise and is still pending. Don't over-index on that, but knowing it exists is a nice signal.

The crucial property: state transitions are one-way and permanent. Pending → fulfilled, or pending → rejected. Never back to pending, never fulfilled → rejected. Once settled, the value is frozen.

Only the first settle counts
const order = new Promise((resolve, reject) => {
  resolve('pizza');
  reject(new Error('kitchen fire'));  // 👈 completely ignored
  resolve('salad');                   // 👈 also ignored
});

order.then(console.log);  // → pizza

This immutability is exactly what makes promises safe to pass around. Callbacks had no such guarantee — a badly-written library could call your callback twice, or call it with both an error and a result. Promises make that structurally impossible.

Creating one

Most of the time you don't — fetch and friends hand you promises already. But you write the constructor when wrapping an old callback-based API:

Promisifying a callback API
function wait(ms) {
  return new Promise((resolve) => {
    setTimeout(resolve, ms);
  });
}

function readFile(path) {
  return new Promise((resolve, reject) => {
    fs.readFile(path, 'utf8', (err, data) => {
      if (err) reject(err);
      else resolve(data);
    });
  });
}

One detail people miss: the function you pass to new Promise runs synchronously, immediately. It's called the executor. It is not deferred, not queued. Only the .then callbacks are asynchronous. This shows up in ordering puzzles constantly.

11. Chaining: every .then makes a brand new promise

This is the idea that unlocks promises, and it's the one most tutorials rush past.

.then() does not modify the promise you called it on. It returns a completely new promise.

That's why chains work. Each link is a fresh promise whose fate depends on what the previous callback did. And there are exactly three things your callback can do:

1. Return a plain value

The new promise fulfills with that value.

Return a value
Promise.resolve(5)
  .then((n) => n * 2)      // returns 10 → new promise fulfills with 10
  .then((n) => n + 1)      // returns 11
  .then(console.log);      // → 11

Return nothing, and the new promise fulfills with undefined. That's the source of a very common bug — forgetting the return in a chain and getting undefined downstream.

2. Return a promise

Now the magic: the new promise waits for yours and adopts its outcome. This is called unwrapping or assimilation, and it's what makes chains flat instead of nested.

Return a promise — the chain waits
fetch('/api/user/42')
  .then((response) => response.json())   // 👈 returns a promise; chain waits for it
  .then((user) => fetch(`/api/orders?u=${user.id}`))
  .then((response) => response.json())
  .then((orders) => console.log(orders.length));

You never get a promise-of-a-promise. If a .then callback returns a promise, the outer one flattens onto it. It's a bit like how a nested array in flat() collapses — one level of "promise-ness" disappears.

Trap: forgetting to return

Write .then((r) => { r.json(); }) with braces and no return, and you've silently produced a promise for undefined. The chain doesn't wait for the JSON, and the next handler gets undefined. This is one of the most common real-world promise bugs, and mentioning it unprompted signals that you've actually shipped code.

3. Throw

The new promise rejects with whatever you threw. A throw inside a .then is exactly equivalent to returning a rejected promise.

Throw → rejection
fetch('/api/user/42')
  .then((response) => {
    if (!response.ok) throw new Error(`HTTP ${response.status}`);  // 👈
    return response.json();
  })
  .then((user) => console.log(user.name))
  .catch((err) => console.error('Failed:', err.message));

That's worth pausing on. fetch only rejects on network failure — a 404 or a 500 is a perfectly successful HTTP round-trip as far as fetch is concerned, so response.ok is false but the promise fulfils. Checking response.ok and throwing is how you fold HTTP errors into the rejection path. Interviewers love this one.

12. Errors, .catch, .finally, and unhandled rejections

Here's the mental model: a promise chain has two tracks, a success track and a failure track. A value flows down the success track. A rejection flows down the failure track. .then handlers are stations on the success track — a rejection skips straight past them until it finds a .catch, which is a station on the failure track.

Rejections skip .then handlers
Promise.reject(new Error('boom'))
  .then(() => console.log('never runs'))
  .then(() => console.log('also never runs'))
  .catch((err) => console.log('caught:', err.message))
  .then(() => console.log('back on the happy track'));

// → caught: boom
// → back on the happy track

Notice that last line. .catch handles the error and returns to the success track, exactly like a try/catch block in synchronous code. If you don't want to recover, re-throw inside the catch.

And .catch(fn) is literally just sugar for .then(undefined, fn) — nothing more. Which explains a subtle gotcha:

❌ The second argument doesn't catch its own sibling
somePromise.then(
  (value) => { throw new Error('handler blew up'); },
  (err) => console.log('this will NOT see it')   // 👈 same .then, can't catch
);
✅ A separate .catch sees everything upstream
somePromise
  .then((value) => { throw new Error('handler blew up'); })
  .catch((err) => console.log('caught it'));      // → caught it

Rule of thumb: put .catch at the end of the chain, so it covers every link above it.

.finally

.finally(fn) runs whether the chain succeeded or failed. It's for cleanup — hiding a spinner, closing a connection. Two things make it different from just adding a .then:

  • Its callback receives no arguments. It doesn't know or care what happened.
  • It is transparent: it passes the value or the rejection straight through untouched. Returning something from finally doesn't change the chain's value (unless you throw, or return a rejected promise — those do take over).
Cleanup that can't accidentally swallow the result
setLoading(true);

fetchUser(id)
  .then((user) => render(user))
  .catch((err) => showError(err))
  .finally(() => setLoading(false));   // 👈 always runs, changes nothing

Unhandled rejections

What happens if a promise rejects and nobody ever attached a .catch?

In the browser, the rejection is silent at first — the engine can't know you won't attach a handler a moment later. But once the microtask queue has drained and no handler has appeared, the environment fires a global unhandledrejection event and typically logs a scary red error to the console. The rest of your app keeps running, so the failure is quiet, which is worse: a request failed, the spinner spins forever, and nothing tells you.

In Node, unhandled rejections have crashed the process since Node 15. So on the server, forgetting a .catch can take down your service.

A global safety net (not a substitute for real handling)
window.addEventListener('unhandledrejection', (event) => {
  reportToSentry(event.reason);
  event.preventDefault();   // 👈 stops the default console error
});

Wait — does attaching .catch late still work?

Yes for handling, no for the warning. A promise keeps its settled value forever, so attaching a handler an hour later still fires it immediately. But if the microtask queue drained with no handler attached, the "unhandled rejection" warning has already gone out. You'll see a console error and your handler will run. Slightly confusing, entirely by design.

13. async / await — sugar over the exact same machine

Now the good part. async/await is not a new concurrency mechanism. It is syntax that compiles down to promises and microtasks. Nothing new happens at runtime. If you're solid on the previous two sections, you already understand it.

Rule 1: an async function always returns a promise

Always. No exceptions. Even if the body has no await and returns a number.

async wraps the return value
async function getTotal() {
  return 42;               // 👈 not a number to the caller
}

console.log(getTotal());          // → Promise { 42 }
getTotal().then(console.log);     // → 42

Why must it? Because the function might suspend at an await. The caller needs something back immediately — it can't be made to wait, that would block the thread. So the caller gets a receipt, and the receipt is filled in later. For consistency, that's true even when the function never suspends.

Two corollaries that fall out of this: return value fulfils the promise; throw err inside an async function rejects it rather than propagating a synchronous exception. So you can't wrap an async call in a plain synchronous try/catch and expect to catch its failure — the function already returned a (later-rejecting) promise by then.

Rule 2: await means "pause here, resume in a microtask"

This is the sentence to memorise. When execution hits await somePromise:

  1. The async function suspends. Its frame comes off the stack, but its state is saved.
  2. Control returns to whoever called it, which keeps running normally.
  3. When the awaited promise settles, the rest of the async function is scheduled as a microtask.
  4. Once the stack empties and the drain begins, the function resumes right where it left off, with the awaited value.

Here's the desugaring, side by side. These two are essentially the same program:

async/await
async function loadDashboard(id) {
  const user = await fetchUser(id);
  const orders = await fetchOrders(user.id);
  return { user, orders };
}
…is roughly this
function loadDashboard(id) {
  return fetchUser(id).then((user) => {
    return fetchOrders(user.id).then((orders) => {
      return { user, orders };
    });
  });
}

Everything after an await is "the callback." That's the whole trick. The compiler is doing the .then nesting for you, and giving you back straight-line code that you can read top to bottom.

Under the hood (skippable)

Under the hood, an async function is a state machine, essentially a generator driven by a runner. Each await is a yield point; the runner attaches a .then to the yielded promise and resumes the generator with the value when it settles. That's why the function can "pause" without blocking — pausing a generator is just returning, with the local variables preserved in a closure-like frame.

One nuance worth knowing: await of a non-promise value (like await 5 or await null) still costs you exactly one microtask tick. It doesn't run synchronously. Modern engines optimised this from three ticks down to one back in 2018, which is why some old blog posts give different puzzle answers than your browser does.

Rule 3: try/catch works again

Because await re-throws a rejection as a real exception at the await point, ordinary try/catch just works — and this is the single biggest ergonomic win over .then chains.

✅ Familiar error handling
async function loadDashboard(id) {
  try {
    const user = await fetchUser(id);
    const orders = await fetchOrders(user.id);
    return { user, orders };
  } catch (err) {
    logError(err);           // catches EITHER fetch failing
    return { user: null, orders: [] };
  } finally {
    setLoading(false);
  }
}

Trap: the un-awaited call

If you forget the await, try/catch silently stops working. try { doThing(); } catch {} where doThing is async catches nothing — doThing() returns a pending promise without throwing, the try block completes successfully, and the rejection arrives later with nobody listening. You get an unhandled rejection and a catch block that looks fine in code review.

What happens if you forget to await?

Three distinct problems, and naming all three is a strong answer:

  1. You get the promise, not the value. const user = fetchUser(id) gives you a Promise, so user.name is undefined and user.id is undefined. Everything downstream quietly corrupts.
  2. Ordering breaks. Code that assumed the write finished runs before it did. Classic in tests and in "save then redirect" flows.
  3. Errors become unhandled rejections. As above — nothing catches them, and in Node the process may die.

The fix, beyond being careful, is tooling: TypeScript plus the no-floating-promises ESLint rule catches essentially all of these. And when you genuinely want fire-and-forget, say so explicitly with void doThing() or attach a .catch, so the next reader knows it was deliberate.

14. Puzzle 2 — the hard one

Now let's combine everything. This is very close to what actually gets put on a whiteboard. Work it out before opening the answer; use the five-step algorithm.

Predict the output
console.log('script start');

setTimeout(() => console.log('setTimeout'), 0);

async function greet() {
  console.log('greet start');
  await null;                     // 👈 still yields!
  console.log('greet end');
}

greet();

new Promise((resolve) => {
  console.log('promise executor');
  resolve();
}).then(() => console.log('promise then'));

console.log('script end');
Reveal the answer and the walkthrough 
script start
greet start
promise executor
script end
greet end
promise then
setTimeout
  1. script start — plain sync log.
  2. setTimeout handed to the browser. Its callback will land in the task queue. Nothing printed.
  3. greet() is called. An async function's body runs synchronously until the first await — so greet start prints immediately.
  4. await null. Even though null isn't a promise, the function suspends and the remainder is queued as a microtask. Control returns to the top level.
  5. new Promise(...) — the executor runs synchronously, so promise executor prints. Then resolve() settles it. The .then callback goes onto the microtask queue, behind the greet continuation.
  6. script end prints. The script task is done; the stack is empty.
  7. Drain microtasks in order: greet end, then promise then.
  8. One macrotask: setTimeout.

The two lines that catch people: async bodies run synchronously up to the first await, and promise executors run synchronously too.

15. Awaiting in a loop — the mistake everyone makes

await is so readable that it seduces you into writing accidentally sequential code.

❌ 3 seconds — each request waits for the last
async function loadAll(userIds) {
  const users = [];
  for (const id of userIds) {
    users.push(await fetchUser(id));   // 👈 blocks the loop each time
  }
  return users;
}
// 3 users × ~1s each = ~3 seconds

Read it literally: "start request 1, wait for it, then start request 2." The requests never overlap. If each takes a second, three users take three seconds — even though the network could easily have handled all three at once.

The fix is to start all the work first, then await. Separating "kick it off" from "wait for it" is the key move:

✅ ~1 second — all in flight at once
async function loadAll(userIds) {
  const promises = userIds.map((id) => fetchUser(id));  // 👈 all started NOW
  return Promise.all(promises);
}
// 3 users in parallel = ~1 second

The moment you call fetchUser(id), the request is on the wire. await doesn't start anything; it only decides when you look at the result. So calling three functions and awaiting them afterwards gives you overlap for free.

The same fix without Promise.all, which sometimes reads more clearly for a fixed set:

✅ Start both, then await both
async function loadPage(userId) {
  const userPromise = fetchUser(userId);      // 👈 both requests
  const feedPromise = fetchFeed(userId);      // 👈 are already running

  const user = await userPromise;
  const feed = await feedPromise;
  return { user, feed };
}

Wait — is sequential always wrong?

No, and saying so is a mark of seniority. Await in a loop is correct when: request N+1 depends on the result of request N (pagination cursors, for instance); or you're deliberately rate-limiting so you don't hammer an API with 500 simultaneous requests; or ordering matters because of side effects. The bug isn't sequential code — it's sequential code you didn't intend. If it's deliberate, leave a comment saying so.

Trap: await inside .forEach

ids.forEach(async (id) => { await save(id); }) does not wait for anything. forEach ignores the returned promises entirely, so the surrounding function moves on immediately and you get zero error handling. Use for...of with await (sequential) or map + Promise.all (parallel). This is a favourite interview snippet.

16. all vs allSettled vs race vs any

Four static methods, all taking an iterable of promises and returning one promise. The differences are entirely about when they settle and what they settle with.

Fulfils when…Rejects when…Fulfils with
Promise.all all fulfil any one rejects (immediately) array of values, in input order
Promise.allSettled all settle, either way never array of {status, value} / {status, reason}
Promise.race the first to settle fulfils the first to settle rejects that one value
Promise.any the first to fulfil all reject that one value

Promise.all — "I need everything, or nothing"

All-or-nothing
const [user, settings, perms] = await Promise.all([
  fetchUser(id),
  fetchSettings(id),
  fetchPermissions(id),
]);
// Any one failing → the whole await throws.

Use it when the page is meaningless without every piece. Note the results come back in input order, not completion order — that's what makes destructuring safe. And it fails fast: the returned promise rejects the instant the first input rejects, without waiting for the rest.

Wait — do the other requests get cancelled when one fails?

No! This is a great follow-up and most candidates get it wrong. The other requests keep running to completion; Promise.all just stops listening. Promises have no cancellation built in. If those other requests reject later with nobody watching, you can even get unhandled rejection warnings. Cancelling requires AbortController — see section 19.

Promise.allSettled — "tell me how each one went"

Partial success is fine
const results = await Promise.allSettled(
  widgets.map((w) => fetchWidgetData(w.id))
);

results.forEach((result, i) => {
  if (result.status === 'fulfilled') renderWidget(widgets[i], result.value);
  else                               renderWidgetError(widgets[i], result.reason);
});

The all-vs-allSettled tradeoff is the thing to nail. Say it like this:

all is for when the results are a package — a checkout page needs the cart, the address and the payment methods, and two out of three is a broken page, so failing fast and showing one error is correct. allSettled is for when the results are independent — a dashboard of six widgets, where one analytics service being down shouldn't blank the other five.

The cost of allSettled: it never fails fast, so you always wait for the slowest one, even if the first thing errored instantly. And you can't destructure comfortably — every result is wrapped in an envelope you must unwrap.

Promise.race — "whoever finishes first, good or bad"

Timeouts, the classic use
function withTimeout(promise, ms) {
  const timeout = new Promise((_, reject) =>
    setTimeout(() => reject(new Error('Timed out')), ms)
  );
  return Promise.race([promise, timeout]);  // 👈 first to settle wins
}

const user = await withTimeout(fetchUser(id), 5000);

The subtlety worth mentioning: race settles on the first thing to settle, including rejecting. So if your fastest promise fails, race rejects even if a slower one would have succeeded. If you want "first success", that's any, not race.

Promise.any — "first one that works"

Redundant sources
const price = await Promise.any([
  fetchFromPrimaryCDN(sku),
  fetchFromBackupCDN(sku),
  fetchFromOriginServer(sku),
]);
// If ALL reject → throws an AggregateError with an .errors array

Use it for redundancy: several mirrors, and you want whichever answers first successfully. If every single one rejects, you get an AggregateError whose .errors property holds every individual failure — a nice detail to know.

17. Callback hell → promises → async/await

Interviewers sometimes ask "why do promises exist?" — and the honest answer is a story. Telling it well shows you understand the motivation, not just the API.

Act 1: callbacks

❌ The pyramid of doom
getUser(userId, (err, user) => {
  if (err) return handleError(err);
  getOrders(user.id, (err, orders) => {
    if (err) return handleError(err);
    getShipping(orders[0].id, (err, shipping) => {
      if (err) return handleError(err);
      render(user, orders, shipping);
    });
  });
});

Everyone points at the indentation, but the shape is the least of the problems. The real ones:

  • Error handling is manual and repeated at every level, and one forgotten if (err) silently swallows a failure.
  • You can't use try/catch, because by the time the callback runs, the try block has long since exited the stack.
  • Inversion of control. You hand your callback to someone else's function and trust them to call it exactly once, with sensible arguments, at a sensible time. A buggy library can call it twice, or never.
  • Combining is painful. "Run these three in parallel and continue when all are done" means hand-rolling a counter every single time.

Act 2: promises (ES2015)

Flat, with one error path
getUser(userId)
  .then((user) => getOrders(user.id))
  .then((orders) => getShipping(orders[0].id))
  .then((shipping) => render(shipping))
  .catch(handleError);          // 👈 one handler for the whole chain

Control is inverted back: the function hands you an object, and you decide what to do with it. State transitions are guaranteed one-way, so double-calls are impossible. Errors propagate down one path. And because a promise is a value, you can put promises in arrays and hand them to Promise.all — combinators become trivial.

What promises still didn't fix: you're writing callbacks. Sharing a variable between the first and third .then means hoisting it out of the chain or nesting again. Loops and conditionals over async work stay awkward.

Act 3: async/await (ES2017)

✅ Reads like synchronous code
try {
  const user = await getUser(userId);
  const orders = await getOrders(user.id);
  const shipping = await getShipping(orders[0].id);
  render(user, orders, shipping);        // 👈 all three still in scope
} catch (err) {
  handleError(err);
}

Same promises underneath — no new runtime machinery at all. But now normal if, for, try/catch and ordinary block scoping all work again. The key sentence for an interview: "async/await didn't replace promises, it's syntax over them — an async function returns a promise and await consumes one."

And the honest downside, worth volunteering: await makes it very easy to write accidentally sequential code, which is exactly the trap in section 15. Sometimes the explicit Promise.all is clearer about intent.

18. Implementing Promise.all yourself

A genuinely common whiteboard exercise. It's short, but there are four details that separate a decent answer from a great one.

✅ A solid implementation
function promiseAll(items) {
  return new Promise((resolve, reject) => {
    const results = [];
    let remaining = items.length;

    if (remaining === 0) return resolve([]);      // 👈 detail 1

    items.forEach((item, i) => {
      Promise.resolve(item).then(                 // 👈 detail 2
        (value) => {
          results[i] = value;                     // 👈 detail 3
          remaining -= 1;
          if (remaining === 0) resolve(results);  // 👈 detail 4
        },
        reject                                    // first rejection wins
      );
    });
  });
}

Talk through these as you write — that's what earns the points:

  1. The empty array. With no inputs, nothing ever calls resolve and your promise hangs forever. Promise.all([]) fulfils immediately with []. Handle it up front.
  2. Promise.resolve(item). The input may contain plain values, not just promises — Promise.all([1, fetchUser()]) is legal. Wrapping normalises everything so .then is always safe to call.
  3. Index assignment, not push. Results must come back in input order, not completion order. results[i] = value preserves position; push would scramble it based on which network request happened to win.
  4. A counter, not results.length. Because of sparse-array assignment, results.length jumps to 5 as soon as index 4 lands, even with holes at 0–3. Count down explicitly.

And the free bonus: passing reject directly as the rejection handler gives you fail-fast for free — the first rejection calls reject, and every later call to resolve/reject is ignored, because promise state is permanent. Say that out loud; it shows you're using the immutability property deliberately.

Bonus: allSettled is a two-line change 
function promiseAllSettled(items) {
  return promiseAll(
    items.map((item) =>
      Promise.resolve(item).then(
        (value)  => ({ status: 'fulfilled', value }),
        (reason) => ({ status: 'rejected', reason })   // 👈 never rejects
      )
    )
  );
}

By converting every rejection into a fulfilled envelope object, no input can ever reject, so the underlying all can never fail fast. Elegant, and a very strong thing to notice unprompted.

19. Can you cancel a promise?

No. That's the correct one-word answer, and then you explain why.

A promise represents an eventual result, not the operation producing it. It's the coat-check ticket, and the ticket has no power over the cloakroom. By the time you hold a promise, whoever created it has already started the work, and there's no channel back. Add to that: promise state is one-way and permanent, so there's nowhere for a "cancelled" state to live.

What people usually mean by "cancel" is one of two things.

1. Stop caring about the result

Just don't act on it. A common React pattern for avoiding a state update after unmount:

Ignore a late result
let cancelled = false;

fetchUser(id).then((user) => {
  if (cancelled) return;    // 👈 result arrives, we drop it
  setUser(user);
});

// on cleanup:
cancelled = true;

The request still completes and still costs bandwidth. You've only muted it.

2. Actually abort the underlying operation — AbortController

This is the real answer, and it lives at the API level, not the promise level:

✅ Genuinely aborting a request
const controller = new AbortController();

fetch('/api/search?q=shoes', { signal: controller.signal })
  .then((r) => r.json())
  .then(render)
  .catch((err) => {
    if (err.name === 'AbortError') return;   // 👈 expected, not a bug
    showError(err);
  });

controller.abort();   // network request is genuinely torn down

The controller has a signal, you hand the signal to an API that understands it, and abort() tells that API to stop. The promise then rejects with an AbortError — note that it rejects rather than entering some special cancelled state, which preserves the two-state model.

The killer use case is search-as-you-type: every keystroke aborts the previous in-flight request, so you don't get stale results overwriting fresh ones. AbortController also works with addEventListener (pass { signal } to remove listeners in bulk) and any library that accepts a signal.

Wait — is the promise "cancelled"?

No, and this is exactly the distinction to draw in an interview. The operation was cancelled; the promise settled normally, into the rejected state, with an AbortError. Promises stay two-outcome. That framing — "cancellation belongs to the operation, not the result" — is a genuinely senior-sounding answer.

20. The interview layer

How this gets asked

Almost always one of these, roughly in order of frequency:

  • "What's the output of this snippet?" (a console.log/setTimeout/Promise mix)
  • "Can you explain the event loop?"
  • "What's the difference between a microtask and a macrotask?"
  • "JavaScript is single-threaded — so how does it do asynchronous work?"
  • "How would you fire three API requests in parallel?"
  • "What's the difference between Promise.all and Promise.allSettled?"
  • "Implement Promise.all."

In an interview: the core model answer

For "explain the event loop" — say this, and draw the diagram while you do:

Say this out loud

"JavaScript executes on a single thread, so there's one call stack and only one thing runs at a time. But the browser isn't single-threaded — when I call setTimeout or fetch, that work is handed off to the host environment, which runs it on its own threads. When it finishes, my callback gets put in a queue, not run immediately.

The event loop's job is to move things from those queues onto the stack, and it only does that when the stack is empty. There are two queues: the macrotask queue for timers, I/O and UI events, and the microtask queue for promise callbacks and anything after an await. The important asymmetry is that the loop drains the entire microtask queue after every task, but takes only one macrotask per turn — so promise callbacks always run before a setTimeout, even a zero-delay one.

That's also why blocking matters: rendering happens between tasks on the same thread, so a long synchronous function freezes the whole UI."

Why this answer lands: it corrects the "single-threaded" oversimplification without being pedantic, it names all four components in the right relationships, it states the one rule that actually predicts output, and it closes with practical consequence. That last move — from mechanism to "so here's why it matters" — is what separates a candidate who memorised a blog post from one who has debugged a janky page.

Follow-up questions, with answers

"Is JS really single-threaded if it does async work?"

Yes — execution of your JS is single-threaded. Asynchrony comes from delegating to the host environment, which is multi-threaded, and getting callbacks back through queues. So it's concurrent, not parallel. The one exception is Web Workers, which give you genuine parallelism — but each worker has its own thread, its own event loop and its own memory, and they only communicate by message-passing.

"Why does the distinction between microtask and macrotask matter?"

Two reasons. Ordering: promise callbacks always run before the next timer or event, which decides the output of every one of these puzzle questions. And responsiveness: the browser can render between macrotasks but never in the middle of a microtask drain, so an unbounded chain of microtasks freezes the page while an unbounded chain of timers doesn't.

"How do you run three requests in parallel?"

Start them all before awaiting any of them — const [a, b, c] = await Promise.all([f1(), f2(), f3()]). The requests are in flight the moment the functions are called; await only controls when I read the results. Awaiting each one in a loop makes them sequential, which is the classic mistake. If I want partial results rather than all-or-nothing, I'd use allSettled instead.

"What happens if you forget to await?"

Three things. The variable holds a pending promise instead of the value, so property access gives undefined. Ordering guarantees disappear — code that assumed the work was done runs early. And any rejection becomes unhandled, which logs a warning in the browser and can crash a Node process. TypeScript with no-floating-promises catches nearly all of these.

"Why does an async function always return a promise?"

Because it can suspend at an await, and the caller can't be made to block waiting for it — that would freeze the thread. So the caller needs something to hold immediately, and that's the promise. The engine wraps whatever you return; throw becomes a rejection rather than a synchronous exception.

"What happens to a rejected promise with no .catch?"

Nothing stops. The rejection sits there, and once the microtask queue drains without a handler appearing, the environment fires an unhandledrejection event and logs an error. In the browser your app keeps running with a silent failure — usually a spinner that never stops. In Node 15+ it terminates the process by default. The value isn't lost, though: attach a .catch later and it still fires, because settled state is permanent.

"Why not just use setTimeout(fn, 0) instead of a promise, if I just want to defer something?"

Different timing and different cost. setTimeout(fn, 0) is a macrotask — it yields to rendering and to any pending events, and it's clamped to at least 4ms when nested. A microtask via queueMicrotask or Promise.resolve().then runs before the next render, at the end of the current task. If I want "after the current code but before the browser paints," that's a microtask. If I want "let the browser breathe and paint first," that's a timeout.

"Can you cancel a promise?"

Not the promise itself — it represents a result, not an operation, and its state is one-way. What you cancel is the underlying work, with AbortController: pass signal to fetch, call abort(), and the promise rejects with an AbortError. Without that, the best you can do is ignore the result when it arrives.

"Does Promise.all cancel the others when one rejects?"

No. It rejects immediately, but the other operations keep running to completion — it just stops listening. If you need actual cancellation, wire an AbortController through to each request and abort in the catch.

"Where does await put the rest of my function?"

On the microtask queue. The function's frame comes off the stack, control returns to the caller, and when the awaited promise settles, the continuation is queued as a microtask. Even await on a non-promise costs one microtask tick.

Traps — the specific wrong answers

Trap 1: "setTimeout runs the callback on another thread"

Wrong, and it's a load-bearing misunderstanding. Only the timing happens elsewhere. Your callback is always run by the single JS thread, from the task queue. Say instead: "The browser's timer thread counts, then queues my callback for the main thread to run when it's free."

Trap 2: "Promises are asynchronous, so they don't block"

Promises control scheduling, not threading. A heavy synchronous loop inside a .then blocks exactly as hard as anywhere else. Say instead: "Promises decide when code runs, not where. For CPU-heavy work I'd need a Web Worker."

Trap 3: "setTimeout(fn, 100) runs after exactly 100ms"

It's a minimum delay to being queued, not a guarantee of execution time. Say instead: "At least 100ms, then it waits for the stack to clear and for its turn in the queue."

Trap 4: answering an output puzzle with a memorised rule

"Promises come before timeouts" gets you the easy version and fails the hard one. Walk the machine out loud instead: what's synchronous, what got queued where, what happens when the stack empties. Interviewers are testing whether you have a model — that's depth — not whether you memorised an ordering, which is recall. If you narrate the simulation, you'll get nested and edge cases right too.

Trap 5: reaching for async on the new Promise executor

new Promise(async (resolve) => { ... }) is an anti-pattern — if the async body throws, nothing rejects the promise and the error vanishes. Also watch for the explicit promise construction antipattern: wrapping a function that already returns a promise in new Promise. If it's already a promise, just return it.
