Polyfilling call, apply and bind

Three methods that exist for one reason: to let you choose what this means. Writing them yourself is a five-line trick — and a sneaky test of whether you actually understand this.

The problem: a method that falls off its object

Here's a perfectly normal object with a perfectly normal method:

const user = {
  name: 'Priya',
  greet() {
    console.log('Hi, ' + this.name);
  }
};

user.greet();   // → Hi, Priya

Now pull that method out into a variable — something you do all the time when passing a callback:

❌ It breaks
const log = user.greet;
log();          // → Hi, undefined  (or a TypeError in strict mode)

Nothing about the function changed. We copied a reference; the body is identical. So why is this.name gone?

Because this isn't decided when a function is written — it's decided at the moment it's called, by what sits to the left of the dot. In user.greet() the thing to the left is user, so this is user. In log() there's nothing to the left of a dot at all, so this falls back to globalThis (sloppy mode) or undefined (strict mode / modules).

Think of this like the word "here" in a sentence. The word never changes; its meaning depends entirely on where you're standing when you say it. Move the function, and "here" means somewhere else. (Where the analogy breaks: you can't force "here" to mean a different room. With functions, you can — that's exactly what call, apply and bind are for.)

What the three of them do

All three answer "run greet, but pretend it was called on this object." They differ only in how you hand over the arguments, and whether it runs now.

function greet(greeting, punctuation) {
  console.log(greeting + ', ' + this.name + punctuation);
}

const user = { name: 'Priya' };

greet.call(user, 'Hi', '!');          // → Hi, Priya!   args listed out
greet.apply(user, ['Hi', '!']);       // → Hi, Priya!   args in an array

const greetPriya = greet.bind(user);  // doesn't run — returns a new function
greetPriya('Hi', '!');                // → Hi, Priya!

call and apply are the same thing with different plumbing — apply takes an array, that's the whole mnemonic. bind is the odd one out: it doesn't call anything. It hands you back a new function with the context permanently glued on, to call whenever you like.

Polyfilling myCall

We want greet.myCall(user, 'Hi', '!') to work. Since it's called on a function, it lives on Function.prototype, which means inside it this is the function we're operating on — greet itself.

Step 1 — the shape
Function.prototype.myCall = function (thisArg, ...args) {
  // `this` in here is the function being called (greet)
};

Now the interesting bit. We need greet's body to see this === user. But we just said the only way this gets set is by what's left of the dot at the call site. So… let's just build that call site. Put the function on the object, call it as a method, then clean up after ourselves.

Step 2 — attach, call, delete
Function.prototype.myCall = function (thisArg, ...args) {
  thisArg.fn = this;              // 👈 now it's a method of thisArg
  const result = thisArg.fn(...args);   // left of the dot = thisArg ✅
  delete thisArg.fn;              // tidy up — don't leave litter
  return result;
};

That's the whole trick, and it's worth saying out loud in an interview: we're not overriding this, we're staging a normal method call so the engine binds it for us.

One thing to patch. greet.myCall(null) would explode on null.fn = ..., and the real call treats null/undefined as "use the global object" (in sloppy mode). One line:

✅ The version to write
Function.prototype.myCall = function (thisArg, ...args) {
  const context = thisArg ?? globalThis;
  const key = Symbol('fn');            // 👈 can't collide with a real property

  context[key] = this;
  const result = context[key](...args);
  delete context[key];
  return result;
};

The Symbol is a nicety, not a requirement: a plain string key like 'fn' would silently clobber an existing fn property on the object and then delete it. Mentioning that trade-off is free points.

Under the hood

The real Function.prototype.call doesn't touch your object at all — the engine sets the this binding directly when it builds the call frame. Our version simulates that from userland, which is why we need the attach-and-delete dance.

Polyfilling myApply

Identical, except the arguments arrive as one array instead of a list. So we spread that array instead of a rest parameter:

✅ myApply
Function.prototype.myApply = function (thisArg, argsArray = []) {
  const context = thisArg ?? globalThis;
  const key = Symbol('fn');

  context[key] = this;
  const result = context[key](...argsArray);   // 👈 the only difference
  delete context[key];
  return result;
};

The = [] default matters: greet.apply(user) with no second argument is legal, and without the default you'd spread undefined and throw. Small, and interviewers notice it.

Polyfilling myBind

bind doesn't call — it returns. So the shape is a function that returns a function, and the returned one remembers two things: the context, and any arguments supplied at bind time.

That second part is partial application. You can pre-fill some arguments now and supply the rest later:

const sayHi = greet.bind(user, 'Hi');   // 'Hi' locked in
sayHi('!');                             // → Hi, Priya!   '!' supplied later

So the returned function has to concatenate the bind-time args with the call-time args, in that order. Everything else we already have — we can lean on apply:

✅ myBind
Function.prototype.myBind = function (thisArg, ...boundArgs) {
  const fn = this;                     // 👈 capture it now — inside the
                                       //    returned fn, `this` is different
  return function (...callArgs) {
    return fn.apply(thisArg, [...boundArgs, ...callArgs]);
  };
};

Read the return line slowly, because it's the whole answer: call the original function, with the context we saved, passing the bind-time arguments followed by the call-time ones.

Wait — why const fn = this?

Because the inner function gets its own this when it's called, which will be whatever the call site says — not our original function. We grab it in the outer scope while it still means what we want, and the closure keeps it alive. (You could use an arrow for the inner function and skip the capture, but you'd lose the ability to handle new later, and the explicit version reads better.)

If they push: new

Real bind has one exotic rule — if you call the bound function with new, the bound this is ignored and the fresh instance wins. Handling it means detecting this instanceof the bound function and switching behaviour. Say that you know it exists and that you'd add it if they want; don't write it unprompted. It's noise in a whiteboard answer.

The interview layer

How it gets asked

  • "Implement Function.prototype.myCall / myBind from scratch."
  • "What's the difference between call, apply and bind?"
  • "This method logs undefined when I pass it as a callback — why, and how do you fix it?" (the same question in scenario form)
🗣 Model answer — "how would you implement call?"

"The key insight is that this is set by the call site — specifically by whatever is to the left of the dot. So instead of trying to override this, I stage a call site that produces the binding I want. I temporarily attach the function as a property of the context object, invoke it as a method so the engine binds this naturally, then delete the property and return the result. I'd use a Symbol as the key so I can't clobber an existing property, and default a null context to globalThis."

That lands because you led with the reason the trick works rather than reciting the code. Anyone can memorise four lines; explaining that you're manufacturing a call site is the signal they're after.

Follow-ups

"Why does myCall attach the function to the object?"

Because from inside JavaScript there's no other lever. The engine decides this when it evaluates the call expression, based on the reference used to make the call. A method call is the only form that sets this to an object we choose — so we create one temporarily.

"call vs apply — does it matter for performance?"

Not meaningfully in modern engines; both are heavily optimised. Pick whichever fits the data you're holding — apply when you already have an array, call when you have loose values. In new code, spread (fn(...args)) usually replaces apply anyway, unless you also need to set this.

"What does bind return, and can you re-bind a bound function?"

It returns a brand new function — the original is untouched, so bind is not a mutation. And no: the first bind wins. greet.bind(a).bind(b) still uses a, because the second bind sets this for the wrapper, and the wrapper ignores its own this and calls the original with a. You can see it in our polyfill — thisArg is baked into the closure.

"How is bind different from an arrow function?"

Both fix this, but at different times and from different sources. An arrow captures this lexically, from where it's written, at definition time — you don't choose the value. bind lets you pass any object you like, at runtime, and also supports partial application. Arrows cover the common case; bind is what you need when the context is a value, not a scope.

"Why did we need bind before arrow functions?"

React class components are the classic example. <button onClick={this.handleClick}> passes the method as a bare function reference — exactly our first broken snippet — so this.setState would be undefined. Everyone wrote this.handleClick = this.handleClick.bind(this) in the constructor. Class fields with arrows, and later hooks, made that boilerplate disappear.

"Why delete the property afterwards?"

Otherwise we've permanently mutated the caller's object as a side effect of calling a function on it. It would show up in Object.keys, in JSON.stringify, in a React diff. A polyfill has to be invisible.

Traps

  • Using an arrow function for the polyfill itself. Function.prototype.myCall = (thisArg) => {...} has no this of its own, so you lose the very function you're trying to call. Instant fail.
  • Forgetting to return the result. call and apply return whatever the function returns.
  • Forgetting to delete. Silent mutation of the caller's object.
  • Saying "bind calls the function with a different this." It doesn't call anything. That one word tells them you've mixed it up with call.
  • Ignoring bind-time arguments. A myBind that drops partial application is only half the implementation, and it's the half they're checking.

Cheat sheet

  • this — decided at the call site, by what's left of the dot. Detach a method and it's lost.
  • call(ctx, a, b) — run now, args listed.
  • apply(ctx, [a, b]) — run now, args in an array.
  • bind(ctx, a) — returns a new function; supports partial application; first bind wins.
  • The trick — attach the function to the context, call it as a method, delete it.
  • Symbol key — so you can't clobber an existing property.
  • Arrow vs bind — lexical & automatic vs. explicit & chooseable.
