I want to start with a bug. Not a definition — a bug, from the era before any of this existed, because every single design decision in the rest of this guide is a reaction to it.

1. The module problem (and how we got to ESM)

Tier 2 · asked constantly

Here's a web page from about 2009. Two scripts, written by two different people.

index.html
<script src="carousel.js"></script>
<script src="analytics.js"></script>
carousel.js
var config = { speed: 300 };

function init() {
  console.log('carousel at', config.speed);
}
analytics.js
var config = { endpoint: '/track' }; // 👈 uh oh

function init() {
  fetch(config.endpoint);
}

What do you think happens when the carousel calls init()?

It sends an analytics request. Then it crashes, because config.speed is undefined.

Here's why. A classic <script> tag doesn't create a private world for its file. Every var and every function declared at the top level of any script lands in one single shared namespace — the global object, which in a browser is window. Both files declared config. Both declared init. The second file loaded, and it simply overwrote the first. No error, no warning. The browser thinks this is completely normal, because as far as it's concerned, both files are just… more lines of the same program.

Two script tags on a page aren't two programs. They're one program, split across two files, sharing one enormous global drawer that anyone can reach into.

This is global scope pollution, and in a codebase of any size it's genuinely unmanageable. You can't rename a variable safely because you don't know who else reads it. You can't tell what a file depends on without reading every other file. And load order becomes load-bearing: move a script tag and the app breaks.

Attempt one: hide things inside a function (the IIFE)

JavaScript has always had one reliable way to make a private space: a function body. Variables declared inside a function aren't visible outside it. So people wrapped entire files in a function and immediately called it. That pattern got a name — the IIFE, or Immediately Invoked Function Expression.

✅ carousel.js, wrapped
var Carousel = (function () {
  var config = { speed: 300 };   // private — nobody outside can see this

  function init() {
    console.log('carousel at', config.speed);
  }

  return { init: init };         // 👈 the only thing we expose
})();

Now config is sealed inside. The only global we create is Carousel, and we chose that name deliberately. This is the whole idea of a module in miniature: everything is private by default, and you explicitly publish the small part you want others to use.

It's a real improvement, and it's still not enough. We still have to pick global names and hope nobody collides. We still have to order our script tags by hand — if analytics.js needs Carousel, it must come after it. And nothing in analytics.js says that it needs Carousel; the dependency exists only in the head of whoever wrote the HTML.

Attempt two: make dependencies explicit (CommonJS)

The missing piece is declaring what you need. Two solutions appeared. One, AMD (RequireJS), was built for the browser and used a callback that fired once your listed dependencies had downloaded — you'll see it in old code, and that's all you need to know about it.

The one that mattered was CommonJS, built for Node, where "fetching a file" means reading local disk — fast enough to do synchronously, mid-line:

CommonJS — the Node answer
const analytics = require('./analytics');  // blocks until loaded, then continues

function init() { analytics.track('open'); }

module.exports = { init };

CommonJS won by force of ecosystem: npm was built on it, and npm ate the world. But it was designed for a server reading local files. In a browser, "stop everything and synchronously fetch this file over the network" is not an option. So we bolted on bundlers — Browserify, then webpack — tools that read your require calls ahead of time, follow the whole dependency graph, and glue everything into one file the browser can load with a single script tag.

Under the hood

A CommonJS module isn't magic. Node wraps every file in a function before running it, roughly like this:

function (exports, require, module, __filename, __dirname) {
  // ...your file's code goes here...
}

That's why require, module, and exports appear out of nowhere in every file — they're just function parameters. And it's why top-level var in a Node file isn't global: it's a local inside that wrapper. CommonJS is the IIFE pattern, formalised and automated. That's a genuinely useful thing to say out loud in an interview.

Attempt three: put it in the language (ESM)

Everything so far was a convention — patterns built on top of plain functions and objects. require is just a function somebody wrote. The language itself had no idea modules existed.

ES2015 changed that. ES Modules (ESM) added import and export as real syntax, understood by the parser, with rules baked into the language spec. Today it works natively in every browser (<script type="module">) and in Node, and it's what every bundler is optimised for.

And because it's syntax rather than a function call, it can do something CommonJS structurally cannot. That's the next section, and it's the part interviewers care most about.

2. import/export vs require/module.exports

Let's get the mechanics down before the theory. ESM has two kinds of export.

Named exports — as many as you like per file, each with a name that both sides must agree on:

cart.js
export const TAX_RATE = 0.2;

export function subtotal(items) {
  return items.reduce((sum, item) => sum + item.price, 0);
}

// or gather them at the bottom, which is the same thing:
// export { TAX_RATE, subtotal };
checkout.js
import { subtotal, TAX_RATE } from './cart.js';
import { subtotal as cartSubtotal } from './cart.js';   // renaming is allowed
import * as cart from './cart.js';                      // grab everything as one object

Default exports — at most one per file, and the importing side picks whatever name it likes:

Button.js / App.js
// Button.js
export default function Button(props) { /* ... */ }

// App.js — no braces, and the name is entirely up to me
import Button from './Button.js';
import LiterallyAnything from './Button.js';   // also works. that's the problem.

So which should you use? The honest tradeoff:

Named exports are better most of the time. The name is fixed, so grep and "find all references" actually work; your editor can auto-import them by name; a typo in the import is caught immediately rather than silently giving you undefined; and refactoring tools can rename across the codebase. Named exports also play best with tree shaking, which we'll get to shortly.

Default exports read nicely when a file has exactly one obvious thing in it — a React component, a config object. The cost is that every import site can spell the name differently, so in a large codebase the same component ends up imported under four names. Many teams (and most style guides I've worked with) ban default exports for this reason. Both are fine; just be able to say why you'd pick one.

CommonJS has no such distinction. There's just one thing, module.exports, and it's an ordinary object you mutate or replace:

CommonJS
exports.TAX_RATE = 0.2;              // add a property (a "named export")
exports.subtotal = subtotal;

module.exports = subtotal;           // or replace the whole thing (a "default export")

// consuming side:
const { subtotal } = require('./cart');   // this is just object destructuring!
Wait, what about exports vs module.exports?

exports starts out as a shortcut variable pointing at the same object as module.exports. Adding properties to it works fine. But exports = something just repoints the local variable and exports nothing — because what actually gets returned to the caller is module.exports. This has confused every Node developer at least once. Rule of thumb: assign to module.exports, always.

3. Static vs dynamic — the idea that explains everything else

Here's the sentence to memorise, and then we'll earn it:

ESM is static. Imports are resolved when the file is parsed, before a single line runs. CommonJS is dynamic. require() is a function call that happens while your code runs.

Watch what that means in practice. This is legal CommonJS:

Perfectly valid CommonJS
if (user.isAdmin) {
  const admin = require('./admin-panel');   // conditional!
  admin.mount();
}

const plugin = require('./plugins/' + pluginName);  // computed path!

And this is a syntax error in ESM — it won't even parse:

❌ Illegal in ESM
if (user.isAdmin) {
  import admin from './admin-panel.js';   // SyntaxError
}

In ESM, import statements must be at the top level of the file, and the path must be a plain string literal. You can't compute it, you can't wrap it in an if, you can't put it in a function. That feels like a restriction — and it is — but it's a restriction with a purpose. It means a tool can read your file without running it and know, with certainty, the complete list of what it imports and exports. Hold that thought.

Imports are also hoisted: they're processed before any other code in the file, so this works fine:

greet();                       // → "hi" — the import already ran
import { greet } from './greetings.js';

(You shouldn't write it that way. But it explains why an import at the bottom of a file still works.)

Live bindings vs copies

Now the part that actually shows up in interviews. Take a guess at what each of these logs.

counter.js (ESM)
export let count = 0;
export function increment() { count += 1; }
main.js (ESM)
import { count, increment } from './counter.js';

console.log(count);   // → 0
increment();
console.log(count);   // → 1   👈 it changed. I never reassigned it.

Now the CommonJS version of exactly the same program:

counter.cjs (CommonJS)
let count = 0;
function increment() { count += 1; }

module.exports = { count, increment };
main.cjs (CommonJS)
const counter = require('./counter.cjs');

console.log(counter.count);   // → 0
counter.increment();
console.log(counter.count);   // → 0   👈 still zero!

Same logic, different answer. Why?

Because in CommonJS, module.exports = { count, increment } built an ordinary object, and count: 0 copied the value 0 into a property of that object. When increment() later changes the module's internal count variable, it has no idea that some object out there once took a photocopy of its value. The photocopy doesn't update.

In ESM, import { count } doesn't copy anything. It creates a live binding — a read-only window onto the variable in the other module. When the variable changes, everyone looking through the window sees the new value immediately.

The analogy, and where it breaks

Think of a CommonJS require as photocopying a page from a colleague's notebook, and an ESM import as looking through a window into their office. If they scribble a new number on the page, your photocopy still shows the old one — but through the window you'd see it change.

Where it breaks down: if the exported thing is an object rather than a number or string, CommonJS copies the reference, so mutations to that object are visible on both sides. counter.state.value = 5 would work fine in CJS. The difference only bites on reassignment of the exported variable itself. And ESM's window is read-only from your side: count = 5 in the importing file is a TypeError. Only the owning module can change it.

A common misconception

"ESM imports are just syntactic sugar for require." They really aren't, and this answer gets candidates dinged. require returns a value at runtime; import establishes a binding at link time, before execution. That's why one supports tree shaking and top-level await and cycles-with-function-declarations, and the other doesn't.

4. Tree shaking, and why CommonJS structurally can't have it

You import one tiny helper from a big utility library:

import { formatCurrency } from './utils.js';   // utils.js exports 40 functions

Should your bundle contain all 40 functions, or just one? Obviously just one. Tree shaking is the bundler's job of walking your module graph and deleting every export nobody imports. (The name is the picture: shake the dependency tree, and the dead leaves fall off.)

Now — how can a bundler know which leaves are dead? It has to be certain. Delete a function that turns out to be needed and you've shipped a broken app.

With ESM, it can be certain, because of the restriction we complained about earlier. Every import is a top-level statement with a literal path and a fixed set of names. The bundler reads the source text — without executing it — and builds the complete graph: this file exports these 40 names; across the whole app, exactly three of them are ever imported; the other 37 are unreachable; delete them.

Now try to do the same with CommonJS:

❌ Statically un-analysable
const utils = require('./utils');

const fnName = getUserPreference();   // runtime value
utils[fnName]();                      // 👈 which export is this? nobody knows.

if (isProduction) {
  module.exports.logger = require('./noop');   // exports change at runtime!
}

The bundler would have to run your program, with every possible input, to know which exports are used. That's not a hard problem — it's an undecidable one. module.exports is a plain object; it can be mutated, reassigned, spread, passed around, and indexed with a computed string. Any of the 40 functions might be reached in a way no static analysis can see. So a correct bundler must keep them all.

Tree shaking isn't a feature ESM added. It's a capability that falls out of ESM being static — you get it for free the moment the dependency graph is knowable without running the code.

Wait — so why doesn't my bundle shrink?

Two very common reasons, both worth knowing.

Side effects. If a module does something on import — mutates a global, registers a polyfill, injects CSS — the bundler can't safely drop it even if nothing imports its exports. That's what the "sideEffects": false field in package.json is for: it's you promising the bundler "importing my files does nothing observable, feel free to delete unused ones."

The library ships CommonJS. Plenty of npm packages still publish CJS as their main entry point. If you import from one, your bundler transparently handles it — but it's still CJS underneath, so it can't be shaken. This is why libraries ship an ESM build alongside (the module or exports field), and why "does it have an ESM build?" is a real criterion when picking a dependency.

5. Dynamic import() and code splitting

Static imports are great for analysis and terrible for one specific thing: sometimes you genuinely don't want to load code until you need it. Your app has a giant PDF-export module that 2% of users ever touch. Shipping it in the initial bundle makes the first page load slower for everyone.

So ESM has an escape hatch: import() as a function call rather than a statement. It returns a promise for the module.

✅ Load it only when the user asks for it
exportButton.addEventListener('click', async () => {
  const { generatePdf } = await import('./pdf-export.js');   // 👈 fetched now, not at startup
  generatePdf(invoice);
});

Note the shape: await import(...) resolves to the module namespace object — the same thing you'd get from import * as mod. So named exports come off it as properties, and a default export is on .default:

const mod = await import('./Chart.js');
mod.render;     // a named export
mod.default;    // 👈 the default export lives here. easy to forget.

When a bundler sees a dynamic import(), it doesn't inline that module — it splits it into a separate file (a "chunk") that gets fetched over the network on demand. That's code splitting, and it's the single highest-leverage bundle-size technique there is. In React it's wrapped up as React.lazy(() => import('./Dashboard')) plus a <Suspense> boundary for the loading state, and route-based splitting (one chunk per route) is the standard first move.

Wait — doesn't import() ruin static analysis?

Partly, and deliberately. The bundler can still analyse it if the path is a literal string — that's how it knows to make a chunk. If you write import('./pages/' + name + '.js'), the bundler can't know which file, so it does something pragmatic: it bundles every file matching that pattern into chunks and picks at runtime. That works, but it can quietly pull in far more than you expected. Keep dynamic import paths as literal as you can.

6. Circular dependencies

a.js imports b.js, and b.js imports a.js. This happens more often than you'd think in real codebases — usually via a shared types file or a barrel index.js. It doesn't crash outright in either system, but it goes wrong differently in each, and knowing the difference is a nice depth signal.

In CommonJS, the loader keeps a cache of modules it's currently building. When a requires b, and b requires a right back, the loader doesn't re-run a — it hands b whatever a.module.exports happens to contain at that exact moment. Which is usually a half-finished object:

❌ CommonJS cycle: silently undefined
// a.cjs
const b = require('./b.cjs');
module.exports.name = 'A';

// b.cjs
const a = require('./a.cjs');
console.log(a.name);   // → undefined  (a hasn't reached its assignment yet)

No error. Just undefined, showing up somewhere far away, at 4pm on a Friday.

In ESM, loading happens in phases: first the whole graph is fetched and parsed, then all the bindings are linked, and only then does code execute. Because bindings are hoisted and linked before execution, function declarations across a cycle work fine — they're hoisted too. But a const or let that hasn't been evaluated yet is in the temporal dead zone, so you get a loud, immediate ReferenceError: Cannot access 'name' before initialization.

Which is better? ESM's, unambiguously — an error at the point of the mistake beats undefined leaking through your app. But the real answer for both is: break the cycle. Usually by extracting the shared thing into a third module that both depend on.

7. The practical mess: .mjs, type: module, and dual packages

Recognition, not mastery. Nobody will ask you to recite Node's resolution algorithm. They might ask "have you felt this pain?", and the answer should be yes — so here's the shape of it in one pass.

Node supports twenty years of CommonJS and ESM in one runtime, and a .js file doesn't say which it is. So the file's meaning depends on config: "type": "module" in package.json makes .js mean ESM, otherwise it means CommonJS — and .mjs/.cjs are unambiguous overrides that ignore the setting entirely.

Two consequences you'll actually hit. In ESM, Node demands full file extensions in relative imports ('./cart.js', not './cart') — bundlers are lenient, Node isn't, which is a classic works-locally-breaks-in-production trap. And require()-ing an ES module used to be flatly impossible (ERR_REQUIRE_ESM), because require is synchronous and ESM loading isn't; recent Node has loosened this, but you'll still meet the error in the wild.

The one term worth remembering is the dual package hazard: a library shipping both a CJS and an ESM build can end up loaded twice in one app — once via each — giving you two independent module instances. If the library holds any state (a singleton, a registry, a cache), it now exists twice, and the bugs are baffling. It's why many maintainers now ship ESM only.

8. Interview layer: modules

How this gets asked

"What's the difference between ESM and CommonJS?" · "Why can't you tree shake CommonJS?" · "What's a live binding?" · "How would you reduce this app's bundle size?" · "What does import() return?" · "Why does this package have a .mjs file?"

The first one is a recall question with a depth trapdoor. Almost everyone says "different syntax, one's browser one's Node." If you get to static-vs-dynamic in your first three sentences, you've separated yourself from the pack.

Say something like this

"The syntax difference is the surface; the real difference is that ESM is static and CommonJS is dynamic. In ESM, imports are resolved at parse time — they have to be top-level with literal paths — so a tool can build the full dependency graph without executing anything. That's what makes tree shaking and code splitting possible. CommonJS require is just a function call at runtime, so it can be conditional or computed, and module.exports is a mutable object — a bundler can't prove which exports are unused, so it has to keep them all. The other consequence is live bindings: an ESM import is a read-only view of the exporter's variable, so if it changes you see the change, whereas require gives you a snapshot of the value at require time."

Why this lands: it explains a capability (tree shaking) in terms of a design property (staticness), which is what senior reasoning sounds like. It also pre-answers the follow-up they were about to ask.

Follow-ups

"Why exactly is tree shaking impossible with CommonJS?"

Because determining which exports are used would require running the program. require() can take a computed path and can be called inside a conditional; the object it returns can be indexed with a runtime string like utils[name](); and module.exports can be reassigned or mutated at any point during execution. A bundler doing static analysis can't rule out that any given export is reached, so removing one risks breaking the app. It's not that tooling authors haven't got around to it — it's that the information genuinely isn't there in the source text. ESM's restrictions (top-level only, literal paths, fixed export names) are what make the information available.

"What's a live binding — show me where it matters?"

An ESM import isn't a copy of a value, it's a reference to the exporting module's variable. If the module reassigns that variable, importers immediately see the new value; the importer can't write to it. Where it matters practically: a module that exports a mutable currentUser or a lazily-initialised config object works with ESM but silently goes stale with CommonJS, because require copied the value. It also makes ESM circular dependencies survivable — the binding exists before it has a value, rather than the importer holding a snapshot of a half-built exports object.

"Why not just use dynamic import() everywhere, then? It's more flexible."

Because you'd give up everything static analysis buys you. Every module becomes its own network request resolved at runtime, so the bundler can't hoist, can't shake, can't inline, and can't preload — and you'd turn synchronous code paths asynchronous throughout your app, which is a large refactor for no gain. Dynamic import is a targeted tool for things that are genuinely optional or deferred: routes, heavy modals, an editor, a charting library. Static imports should be your default and dynamic ones the exception you can justify.

"Are named or default exports better?"

I default to named. The name is fixed at both ends, so search, "find all references", auto-import, and automated renames all work; a typo fails loudly at import rather than giving you undefined; and it's the friendliest shape for tree shaking. Default exports are fine when a file has one obvious thing in it — a component, say — but every import site can name it differently, which in a large codebase means the same module appears under several aliases. It's a consistency call more than a correctness one, so the important thing is that the team picks one and lints it.

"Do circular imports break things?"

They don't hard-crash, but they degrade differently. In CommonJS you get whatever the partially-populated exports object contained at the moment the cycle closed — usually undefined properties, failing silently far from the cause. In ESM, bindings are hoisted and linked before execution, so function declarations across a cycle are fine, but touching a const/let that hasn't been evaluated throws a temporal-dead-zone ReferenceError right at the offending line. I prefer ESM's behaviour because it fails loudly, but either way the fix is to extract the shared piece into a third module rather than to work around the cycle.

"Why do bundlers still exist if browsers support ESM natively?"

Because native ESM in the browser means one network request per module, and a real app has thousands. Even over HTTP/2 that's a lot of round-trips and a deep dependency waterfall — the browser can't discover a module's imports until it has fetched and parsed it. Bundlers also do things the browser won't: tree shaking, minification, deliberate code splitting with preload hints, transpiling, and resolving bare specifiers like 'react' (which browsers only handle via import maps). Native ESM is genuinely great in development, which is exactly what Vite exploits — unbundled dev, bundled production.

Traps

"ESM is for the browser, CommonJS is for Node." Outdated by years. Node has supported ESM since v12, and bundlers happily consume CommonJS for the browser. Say "historically" if you mention it at all.

"Tree shaking removes unused code." Close but imprecise, and interviewers notice. It removes unused exports from the module graph. It won't remove an unused function inside a module you did import (that's the minifier's dead-code elimination), and it won't remove anything from a module with unmarked side effects.

9. How garbage collection actually works

Tier 2 · the "do you understand the runtime" question

Let's start with a question that sounds trivial and isn't. Here's some code:

function loadProfile() {
  const user = { name: 'Ada', avatar: /* a 2MB blob */ };
  render(user);
}

loadProfile();   // what happens to `user` now?

You know the answer is "it gets cleaned up." But how does the engine know? Nobody told it. There's no free(). The function just… ended.

The mechanism is reachability, and it's genuinely elegant. The engine keeps a set of roots — starting points that are always considered alive:

  • the global object (window / globalThis) and everything hanging off it
  • the current call stack: every local variable in every function that's currently executing, plus its closure scopes
  • a handful of engine-held things — pending timers, live DOM nodes attached to the document, in-flight promises

Periodically, the collector starts at the roots and walks every reference it can follow, painting each object it reaches as "reachable." That's the mark phase. Then it goes through the heap and frees everything it never painted. That's the sweep phase. Hence mark-and-sweep.

So the answer to our question: while loadProfile is running, its stack frame is a root, so user is reachable. When the function returns, the frame is gone. Nothing points at that object any more. The next time the collector runs, the object isn't painted, and its 2MB goes back to the heap.

An object isn't freed when you're "done with it." It's freed when it becomes unreachable from the roots. Those are very different conditions, and every memory leak in JavaScript lives in the gap between them.

A common misconception: "JavaScript uses reference counting"

Lots of people believe the engine keeps a counter on each object and frees it at zero. It doesn't — and this belief leads straight to a wrong answer on a favourite follow-up question.

Reference counting has a fatal flaw: cycles. If a.partner = b and b.partner = a, each object's count is 1 forever, even after nothing else in your program can reach either of them. Under reference counting, that pair leaks permanently. Old IE had exactly this problem where DOM nodes and JS objects referenced each other across two separately-managed heaps, and it leaked memory notoriously.

Mark-and-sweep doesn't care about counts at all. It asks a completely different question: can I walk to this object starting from a root? Two objects pointing at each other in an isolated island are never painted during the mark phase, so they get swept like anything else. Circular references do not leak in modern JavaScript. Say that plainly when asked.

Under the hood — one sentence of depth, if you want it

Real engines don't do one naive pass over the whole heap, because that would freeze the page. V8 is generational (most objects die young, so new ones go in a small nursery collected cheaply and often; survivors get promoted to a rarely-collected old generation) and does much of its marking concurrently and incrementally so pauses stay short. "Generational, incremental, concurrent mark-and-sweep" is a nice phrase to have ready — but reachability is the part that changes how you write code.

Wait — can I force a collection?

No, by design; the engine decides. Which means bigThing = null doesn't free anything — it drops one reference, which may or may not make the object unreachable, which may or may not be noticed on the next cycle. So it's worth doing when the variable is long-lived (a module-level cache, a closure that outlives the work), and pointless for a local in a function that's about to return anyway.

10. The four classic leaks

A leak, given the model above, has exactly one shape: something long-lived is still holding a reference to something you're finished with. That's it. Every leak below is a variation on that sentence, and the fix is always "let go of the reference."

Leak 1: timers that never stop

❌ Buggy
function startPolling(dashboard) {
  setInterval(() => {
    dashboard.refresh();     // closure keeps `dashboard` alive
  }, 5000);
}

startPolling(bigDashboard);
// user navigates away. the interval keeps running. forever.

A pending timer is a root. The browser must keep the callback alive to run it later, and the callback's closure holds dashboard, and dashboard holds its data and its DOM references. Nothing here can ever be collected while the interval lives — and an interval lives until you clear it or the page unloads. In a single-page app, "the page unloads" might be hours away.

✅ Fixed
function startPolling(dashboard) {
  const id = setInterval(() => dashboard.refresh(), 5000);
  return () => clearInterval(id);     // 👈 hand back a way to stop
}

const stop = startPolling(bigDashboard);
// later, when the view is torn down:
stop();

The pattern to internalise: anything that starts something should return the way to stop it. That single habit prevents most of this category.

Leak 2: detached DOM nodes

This is the one most specific to frontend, and the one interviewers love.

❌ Buggy
const rowCache = [];

function renderRow(data) {
  const row = document.createElement('tr');
  row.innerHTML = template(data);
  rowCache.push(row);                     // 👈 we keep a reference...
  table.appendChild(row);
}

function clearTable() {
  table.innerHTML = '';                   // ...and this doesn't remove it
}

Removing a node from the document does not delete it. It just detaches it from the tree. The node is now a plain JavaScript object floating in memory — and because rowCache still points at it, it's reachable, so it stays.

Worse: DOM nodes hold references to their children and their parent. So keeping one reference to one detached row keeps that row's entire subtree alive. Hold a reference to a detached table and you've retained every cell in it. This is why a slow SPA that re-renders a big list a hundred times can be sitting on tens of thousands of invisible DOM nodes.

Leak 3: event listeners that are never removed

❌ Buggy
class Tooltip {
  constructor(el) {
    this.el = el;
    window.addEventListener('resize', () => this.reposition());   // 👈
  }
  destroy() {
    this.el.remove();   // the listener is still on window, holding `this`
  }
}

window lives as long as the page does, and it's holding your arrow function, which closes over this, which is the whole tooltip instance, which holds this.el. Create and "destroy" a thousand tooltips and you have a thousand live instances and a thousand detached elements.

✅ Fixed
class Tooltip {
  constructor(el) {
    this.el = el;
    this.onResize = () => this.reposition();       // keep a stable reference
    window.addEventListener('resize', this.onResize);
  }
  destroy() {
    window.removeEventListener('resize', this.onResize);   // 👈 the important line
    this.el.remove();
  }
}

Note the detail that trips people up: removeEventListener needs the same function reference you added. Passing a fresh inline arrow removes nothing and fails silently. (The modern alternative is AbortController: pass { signal } to every addEventListener and call controller.abort() once to remove them all — much harder to get wrong.)

Wait — if I remove the element, doesn't its listener go away?

A listener attached to a node that becomes unreachable does get collected along with the node — that part is fine. The leak is specifically about listeners on long-lived targets: window, document, body, a WebSocket, an event bus, a store. Those targets outlive your component, so the handler (and everything it closes over) outlives it too.

Leak 4: unbounded caches and greedy closures

❌ Buggy
const cache = new Map();

async function getUser(id) {
  if (!cache.has(id)) cache.set(id, await fetchUser(id));
  return cache.get(id);   // grows forever. nothing is ever evicted.
}

A cache with no eviction policy isn't a cache, it's a memory leak with good intentions. In a long-lived SPA or a Node server this grows without limit. The fix is a bound: an LRU with a max size, a TTL, or — when the key is an object — a WeakMap, which is exactly where we're headed in the next section.

The subtler cousin is the greedy closure, where a function keeps something alive that you'd never guess it needed:

❌ Buggy — the closure keeps far more than it uses
function makeFormatter() {
  const hugeDataset = loadTenMegabytesOfStuff();
  const currency = hugeDataset.settings.currency;   // all we actually need

  return (amount) => format(amount, currency);
}
// depending on the engine's optimisations, `hugeDataset` may stay alive
// for as long as the returned formatter does.

Engines do try to only capture what a closure references, but it's not something to rely on — especially if anything in the scope uses eval or a debugger is attached. If a closure is going to be long-lived, extract the small value you need and let the big thing fall out of scope.

11. Leaks in React specifically

React doesn't have a separate memory model — it's all the same reachability rules — but it has a specific place where the "start something / stop something" pairing lives: the effect cleanup function.

❌ Buggy
useEffect(() => {
  const id = setInterval(() => setTick(t => t + 1), 1000);
  window.addEventListener('scroll', handleScroll);
  const sub = priceFeed.subscribe(setPrice);
}, []);   // 👈 nothing returned. nothing is ever torn down.
✅ Fixed
useEffect(() => {
  const id = setInterval(() => setTick(t => t + 1), 1000);
  window.addEventListener('scroll', handleScroll);
  const sub = priceFeed.subscribe(setPrice);

  return () => {                          // 👈 runs on unmount and before every re-run
    clearInterval(id);
    window.removeEventListener('scroll', handleScroll);
    sub.unsubscribe();
  };
}, []);

The mental rule: if an effect starts anything that outlives the render, it must return a function that stops it. Timers, listeners, subscriptions, observers (IntersectionObserver, ResizeObserver, MutationObserver), WebSockets, animation frames — all the same shape.

And note the second half of that comment: cleanup doesn't only run at unmount. It runs before every re-run of the effect. So an effect with a changing dependency that subscribes without cleaning up doesn't leak one subscription — it leaks one per render.

The fetch-after-unmount case (with a nuance worth knowing)

✅ Cancel the work, not just the state update
useEffect(() => {
  const controller = new AbortController();

  fetch(`/api/users/${id}`, { signal: controller.signal })
    .then(r => r.json())
    .then(setUser)
    .catch(err => { if (err.name !== 'AbortError') setError(err); });

  return () => controller.abort();   // 👈 cancels the request itself
}, [id]);

You may remember an old React warning: "Can't perform a React state update on an unmounted component. This is a no-op, but it indicates a memory leak." Here's the honest version, and saying it well is a strong signal: that warning was misleading and React removed it. Calling setState after unmount doesn't itself leak — React just ignores it.

What does leak is the thing that was still running: the in-flight request holding your response, the subscription still pushing values, the interval still ticking. So the fix isn't an isMounted flag to suppress the warning (that's a code smell that hides the problem) — it's aborting or unsubscribing so the work actually stops. Same fix, much better reasoning behind it.

Wait — does useState or useRef leak?

Not on their own. When a component unmounts, React drops its fiber, and everything hanging off it becomes unreachable in the normal way. Leaks come from references held outside React's tree: a module-level array, a global cache, a listener on window, a store subscription. If the only thing pointing at your data is React, unmounting is enough.

12. Finding a leak with DevTools

"How would you find a memory leak?" is a process question. They want to hear a repeatable method, not a tool name. Here's the one I'd describe.

Step 1: confirm it's actually a leak. Memory going up isn't a leak — caches fill, GC hasn't run yet. Open the Performance monitor (or record a Performance trace with "Memory" ticked) and look at the JS heap over time while you repeat an action. Healthy memory looks like a sawtooth: up, then a sharp drop when GC runs. A leak looks like a staircase — each sawtooth bottoms out higher than the last. That rising floor is the signal.

Step 2: find a reproduction loop. A leak you can trigger on demand is a leak you can find. "Open the modal, close it, ten times." "Navigate to the dashboard and back." Keep it short and repeatable.

Step 3: the three-snapshot technique. In the Memory panel, take a Heap snapshot. Taking one forces a garbage collection first, which is exactly what you want — it means everything left in the snapshot genuinely survived collection. Then:

  1. Snapshot 1 — baseline, before doing anything.
  2. Run your repro loop 10 times.
  3. Snapshot 2.
  4. Run the loop 10 more times, then Snapshot 3.

Now switch the view to Comparison and compare snapshot 3 against snapshot 2. Sort by "Delta" — the count of objects that were created and never freed. Anything whose count climbs steadily with each round of the loop, in lockstep, is your leak. One constructor name usually stands out immediately: Detached HTMLDivElement, or your own Tooltip, or closures.

Step 4: for DOM leaks, filter for detached nodes. In the snapshot's filter box, type Detached. Chrome groups nodes that are no longer in the document but still retained in memory. If you see thousands of them after ten modal opens, you've found it. (Newer Chrome versions also expose a "Detached elements" view that does this in one click.)

Step 5: read the Retainers pane. This is the payoff and the part people skip. Select the leaking object and look at the Retainers (or "Retained by") panel at the bottom. It shows the actual chain of references keeping the object alive, all the way back to a root — something like window → app → tooltipRegistry → [3] → this.el. That chain is your bug. Somewhere along it is a line of code you need to delete.

Shallow size vs retained size

Two columns in the snapshot that confuse everyone. Shallow size is the memory the object itself occupies — usually tiny. Retained size is how much memory would be freed if that object went away, including everything only it keeps alive. Always sort by retained size when hunting: an array with a shallow size of 200 bytes can retain 40MB.

13. Interview layer: memory

How this gets asked

"How does garbage collection work in JavaScript?" · "Do circular references cause leaks?" · "What are common causes of memory leaks in a SPA?" · "This page gets slower the longer you use it — how would you debug that?" · "Why do you need to return a cleanup function from useEffect?"

The GC question is testing recall. The debugging question is testing depth — they want a method, and they're listening for whether you've ever actually opened the Memory panel.

Say something like this (GC)

"JavaScript engines use mark-and-sweep based on reachability, not reference counting. There's a set of roots — the global object, the current call stack and its closures, plus things the engine holds like pending timers and attached DOM nodes. The collector walks out from the roots marking everything it can reach, then sweeps whatever it didn't mark. The practical consequence is that an object isn't freed when you stop needing it, it's freed when nothing can reach it — so every leak is really 'something long-lived is still holding a reference.' It also means circular references are fine: two objects pointing at each other with nothing pointing at them are unreachable, so they get collected."

Why this lands: you name the model, then immediately translate it into the rule that governs real code. Volunteering the cycles point pre-empts their next question and quietly demonstrates you know why reference counting isn't the answer.

Follow-ups

"Do circular references leak in JavaScript?"

No. That's a reference-counting problem, and JS engines use reachability instead. If a and b point at each other but no root can reach either, the mark phase never visits them and they're swept normally. The historical reason people believe otherwise is old IE, where the DOM and the JS engine had separately managed heaps and a cycle spanning both couldn't be resolved — that genuinely leaked, and the folklore outlived the bug by twenty years.

"How would you actually find a memory leak?"

First I'd confirm it is one: record the JS heap in the Performance panel while repeating an action and look for a rising baseline between GCs rather than a flat sawtooth. Then I'd find a tight repro — open and close the modal ten times. Then heap snapshots in the Memory panel: one baseline, one after ten iterations, one after ten more, and compare the last two by delta to find objects whose count grows in lockstep with the loop. For DOM leaks I filter the snapshot for "Detached". The key step is the Retainers pane on the leaking object — it shows the exact reference chain back to a root, which tells you the line of code holding on. In practice it's nearly always a listener on window, an uncleared interval, or a cache with no eviction.

"Why not just set things to null when you're done?"

It's occasionally useful but it's not a general strategy. Nulling a reference doesn't free memory — it removes one edge in the object graph, and the object is collected only if that was the last path from a root. For a local variable in a function that's about to return it's pure noise, since the whole frame disappears anyway. It's worth doing when the holder is long-lived: clearing a module-level cache entry, or dropping a reference to a big object held by a closure that will outlive it. The higher-leverage habit is not creating the long-lived reference in the first place.

"Is a memory leak always a bug worth fixing?"

It depends on lifetime and rate. On a page a user has open for thirty seconds, a small leak is invisible. On a dashboard someone leaves open all day, or a Node process running for weeks, the same leak takes the process down. Frontend leaks also don't just show up as memory — they show up as slowness, because every leaked listener still fires and every detached subtree still costs GC time to traverse. So I'd triage by the app's usage pattern, and treat a leak that grows per user interaction as much more urgent than a fixed one-time retention.

"What's the difference between a leak and just high memory usage?"

High usage is a level; a leak is a slope. Loading a 50MB dataset uses a lot of memory but releases it when you're done. A leak means memory retained by a completed operation is never released, so usage grows monotonically with time or interaction count. The diagnostic difference is exactly what you look for in the heap timeline: high-but-flat with clean sawteeth versus a baseline that climbs after every GC.

14. WeakMap and WeakSet

Tier 3 · the "have you thought about this" question

Everything in the last section was about accidentally holding references. This section is about a data structure designed specifically to not hold one.

Here's the problem. I want to attach some bookkeeping to DOM nodes — say, how many times each one has been clicked — without touching the elements themselves. Natural first attempt:

❌ Buggy — this is a leak
const clickCounts = new Map();

function trackClick(element) {
  clickCounts.set(element, (clickCounts.get(element) ?? 0) + 1);
}

Works perfectly. And it leaks every element you ever track.

Why? Because clickCounts is a long-lived module-level object — a root, effectively — and a Map holds strong references to its keys. When those elements are removed from the DOM, the Map is still pointing at them. Detached, invisible, un-collectable, forever. Our metadata store has quietly become the thing keeping the data alive.

And there's no good fix with a Map. You'd have to manually delete each entry at exactly the moment the element is removed — which means writing teardown code everywhere, and getting it wrong once means the leak is back.

Change one word:

✅ Fixed
const clickCounts = new WeakMap();   // 👈 that's the entire fix

function trackClick(element) {
  clickCounts.set(element, (clickCounts.get(element) ?? 0) + 1);
}

A WeakMap holds its keys weakly. A weak reference is one the garbage collector ignores when deciding reachability. So if the only thing left pointing at an element is a WeakMap key, the element counts as unreachable, gets collected — and the entry vanishes from the WeakMap along with it. Automatically. No cleanup code.

The analogy, and where it breaks

A normal Map key is a hand gripping the object. A WeakMap key is a sticky note with the object's address written on it: useful while the object exists, but it doesn't stop the object from being demolished, and when it is, the note is thrown away too.

Where it breaks down: a sticky note with a stale address is still a note you could read and get confused by. A WeakMap entry disappears atomically with the object — you can never observe a WeakMap key pointing at something collected. That guarantee is the whole point, and it's what the next bit depends on.

Why WeakMaps aren't iterable (this is asked)

A WeakMap has exactly four methods: get, set, has, delete. No .size, no forEach, no for...of. That looks like an unfinished API, and the reason it isn't makes a great short answer.

To list the keys, the WeakMap would have to tell you which ones still exist — which depends on whether the garbage collector has run yet. So weakMap.size could return 3, then return 1 a moment later with your program having done nothing at all. That would make GC timing observable, and the same code would behave differently across runs and browsers. Keeping WeakMaps opaque is what lets the collector stay invisible.

The practical version: a WeakMap is a lookup table, not a collection. It's only useful when you already have the key. Need to enumerate? You need a Map, and you need an eviction policy.

Where you'd actually use one

Three places, and they're all the same shape — data whose lifetime should match an object you don't control:

  • Metadata on objects you don't own — the click counter above; libraries attaching internal state to a DOM node or a user-supplied object without mutating it.
  • Per-object caching — layoutCache.set(element, expensiveMeasure(element)). This cache can never grow unboundedly, because each entry dies with its element. Compare the Map cache from the leaks section, which needed explicit eviction.
  • Private data — privates.set(this, { balance }) inside a class, the classic pre-#private pattern. Worth recognising in older code; modern code uses #balance.

WeakSet is the same thing without values — just "have I seen this object before?", without keeping it alive.

One constraint: keys must be objects (or unregistered symbols), never strings or numbers. That's inherent rather than arbitrary — weakness is about identity and lifetime, and 'user-42' isn't an allocated thing that can become unreachable.

Name-recognition: WeakRef and FinalizationRegistry

ES2021 added a weak reference to a single object (.deref() gives it back, or undefined if collected) and a post-collection callback. Both are explicitly non-deterministic and shouldn't drive program logic. Knowing they exist — and knowing to reach for WeakMap first — is the whole answer.

How this gets asked

"What's a WeakMap and when would you use one?" · "Why WeakMap over Map?" · "Why can't you iterate a WeakMap?" · "How would you attach data to a DOM node without leaking?"

Say something like this

"A Map holds strong references to its keys, so anything you use as a key can never be garbage collected while the Map is alive. If I'm using DOM nodes or component instances as keys in a long-lived Map, I'm building a leak — every node I ever touched stays in memory after it's removed from the page. A WeakMap holds keys weakly: the collector ignores those references, so once nothing else points at the key, the object is collected and the entry disappears on its own. That's why it's the right tool for metadata or per-object caching. The tradeoff is that it isn't iterable and has no size — which has to be true, because reporting its contents would expose GC timing to your program and make behaviour non-deterministic."

Why this lands: you frame it as a leak-prevention tool rather than "a Map with weird limitations," and you explain the non-iterability as a necessary consequence rather than a missing feature. That's the difference between having read the docs and having understood the design.

15. localStorage vs sessionStorage vs cookies

Tier 2 · nearly guaranteed

Now we move from "how long does my object live in memory" to "what survives a refresh." Same family of question, different timescale.

Cookies came first, in 1994, and their original purpose was not storage — it was telling the server who you are. HTTP is stateless: every request arrives with no memory of the last one. A cookie fixes that by being automatically attached to every request to its domain. That single design decision explains almost everything about how cookies behave, and every problem they have.

The trouble is that people started using cookies for client-side data too, and they're terrible at it: about 4KB each, and every byte gets uploaded with every request — including every image, script, and API call. Storing a user's theme preference in a cookie means shipping that string to your server thousands of times a day for no reason.

So HTML5 added Web Storage: localStorage and sessionStorage. Purely client-side key/value stores, never sent anywhere, with roughly 5–10MB of room. Same tiny API:

localStorage.setItem('theme', 'dark');
localStorage.getItem('theme');     // → 'dark'
localStorage.getItem('missing');   // → null  (not undefined)
localStorage.removeItem('theme');

localStorage.setItem('user', JSON.stringify(user));   // 👈 strings only!
const user = JSON.parse(localStorage.getItem('user'));

Let's go through the axes an interviewer probes, one at a time, because "just memorise the table" is exactly how you fail the follow-up.

Lifetime — when does it disappear?

localStorage persists indefinitely: across refreshes, tab closes, browser restarts, reboots. It's gone only when your code removes it or the user clears site data. sessionStorage lives as long as the tab — close the tab, it's gone. A cookie's lifetime is whatever you set: with Expires or Max-Age it persists to that date; without either it's a "session cookie" that dies when the browser closes.

Scope — who can see it?

This is the axis people get wrong most often, and it splits in two directions.

localStorage is scoped to the origin — scheme + host + port. https://app.example.com and https://www.example.com are different origins, so they have completely separate localStorage. Every tab and window on the same origin shares the same store.

sessionStorage is scoped to origin and the browsing context — effectively per tab. Two tabs on the same site have separate sessionStorage that cannot see each other. (One wrinkle: duplicating a tab copies the sessionStorage into the new tab, whereas opening a fresh tab to the same URL starts empty.)

Cookies don't use origins at all, because they predate the concept. They're scoped by domain and path. A cookie set with Domain=example.com is sent to example.com and every subdomain — which is how single sign-on across app., www., and api. works, and something localStorage simply cannot do. Cookies also ignore port. This mismatch matters: two apps on the same host but different ports share cookies while having separate localStorage.

Sent with requests?

Cookies: yes, automatically, on every matching request, whether you wanted it or not. Web Storage: never — the browser doesn't know it exists from a networking standpoint; if you want it on the server you attach it yourself in a header or body.

That automatic attachment is a double-edged thing. It's why cookies can authenticate a plain <img> request or a form post. It's also the entire basis of CSRF: if evil.com can make your browser send a request to yourbank.com, the cookie rides along and the request looks authenticated. Hence SameSite, below.

Synchronous or not?

localStorage and sessionStorage are fully synchronous, and they hit disk. Every getItem blocks the main thread — no rendering, no input handling, until it returns. For a few small keys that's microseconds and irrelevant. Writing a 3MB JSON blob on every keystroke will visibly jank your app. They're also unavailable in web workers for exactly this reason. document.cookie is synchronous too, and worse: it hands you one big string you have to parse yourself. IndexedDB is asynchronous, works in workers, and is the right answer at scale.

Accessible to JavaScript?

Web Storage: always, by definition — it's a JS API. Cookies: only if you let them be. This is the one genuine security capability in this whole comparison. A cookie set by the server with the HttpOnly flag is invisible to document.cookie. Your JavaScript cannot read it, and therefore neither can any script an attacker injects.

Three cookie flags to know cold:

  • HttpOnly — JS can't read it. Blunts XSS token theft.
  • Secure — only sent over HTTPS. Blocks network eavesdropping.
  • SameSite — controls whether the cookie goes on cross-site requests. Strict means never; Lax (the modern default) means only on top-level navigations, not on background requests or form posts from other sites; None means always, and requires Secure. This is the primary defence against CSRF.

Wait — what about IndexedDB?

When you outgrow 5MB of strings, that's the answer. IndexedDB is a real transactional database in the browser: asynchronous (so it doesn't block rendering), works in web workers and service workers, stores structured data — objects, arrays, Blobs, Files, ArrayBuffers — without JSON.stringify, supports indexes and queries, and has quotas in the hundreds of megabytes or more. Its raw API is famously unpleasant, so people use a wrapper like idb or Dexie. Use it for offline-first apps, cached API responses at volume, media, and anything a service worker needs to touch. Mentioning IndexedDB unprompted in the storage question is a small, reliable way to sound like you've shipped something.

The cross-tab, incognito, and subdomain questions

These get asked as quick checks, so have crisp answers.

Across tabs. localStorage is shared by every tab on the origin, and there's a bonus: writing to it fires a storage event in the other tabs (never in the one that wrote it). That's the classic way to sync logout across tabs:

window.addEventListener('storage', (event) => {
  if (event.key === 'authToken' && event.newValue === null) {
    redirectToLogin();   // another tab logged out — follow it
  }
});

(BroadcastChannel is the modern, purpose-built alternative for cross-tab messaging.) sessionStorage does none of this — it's per-tab, so there's nothing to sync.

In incognito / private browsing. localStorage works normally, with two catches: it's a separate, empty store from the normal session, and it's destroyed when the last private window closes. So it behaves like sessionStorage with a longer leash. Quotas are sometimes smaller. Don't design around it — but do handle it, because storage can also throw: Safari's stricter privacy modes and browsers with site data blocked can make setItem throw a QuotaExceededError, and it throws when you exceed the quota anywhere. Always wrap storage writes in try/catch. An unhandled throw here has taken down more apps than it should have.

Across subdomains. localStorage: not shared, full stop — different origin, different store, and there's no Domain-style opt-in. If app.example.com and shop.example.com need shared client state, you either use a cookie with Domain=example.com, or do the hidden-iframe-plus-postMessage dance (increasingly blocked by browsers' third-party storage partitioning), or keep the state on the server. Cookies, by contrast, share across subdomains happily — which is a feature for SSO and a liability if a subdomain gets compromised.

16. Where do you store an auth token?

This is the storage question interviewers actually care about, and it's a trap dressed as a lookup. There's no clean answer, and the signal they're looking for is whether you know that.

The two candidates come with two different attacks.

Put the JWT in localStorage, and you're exposed to XSS (cross-site scripting — an attacker gets script running on your page, via a dependency, a user-generated content hole, an ad). That script can read localStorage in one line and exfiltrate the token. Now the attacker has your token on their machine and can use it at leisure, long after the user closed the tab.

Put it in a cookie with HttpOnly, and JavaScript can't read it — so XSS can't steal it. But the browser now attaches it automatically to every request to your domain, which opens CSRF: a malicious page can cause the user's browser to fire off a request to your API, and the cookie rides along. Mitigated well by SameSite=Lax or Strict, plus a CSRF token for state-changing requests.

So: XSS risk versus CSRF risk. Here's the honest senior read on it.

The cookie is the better default. CSRF has a mature, well-understood defence — SameSite plus a token — that's largely handled by frameworks. XSS token theft from localStorage has no defence at the storage layer at all; if the attacker's script runs, the token is simply readable.

But be honest about the limits of that. If an attacker has XSS on your origin, HttpOnly doesn't save you — they can't read the token, but they don't need to. They can just make authenticated requests from your page, with the cookie attached automatically, doing whatever the user could do. HttpOnly downgrades "permanent token theft" to "session hijack while the tab is open." That's a meaningful improvement, not a cure. Saying this out loud is what separates a memorised answer from an understood one.

So the real answer is that XSS prevention is the actual control — a strict Content Security Policy, escaping output, framework auto-escaping, avoiding innerHTML and dangerouslySetInnerHTML, and auditing dependencies. Storage choice is defence in depth on top of that.

Say something like this

"It's a tradeoff rather than a right answer. localStorage is trivially readable by any script on the page, so an XSS anywhere in the app — including in a dependency — means the token is exfiltrated and usable indefinitely. An HttpOnly, Secure, SameSite cookie can't be read by JavaScript, which closes that off, but it's sent automatically so you take on CSRF, which you handle with SameSite=Lax or Strict plus a CSRF token on state-changing requests. I'd default to the cookie, because CSRF has a well-understood fix and XSS-reading-localStorage doesn't. The pattern I'd actually reach for is a short-lived access token held in memory only, with a long-lived refresh token in an HttpOnly cookie scoped to the refresh endpoint. And I'd be clear that if you have XSS, the attacker can make authenticated requests from the page regardless — so the real control is preventing XSS with a CSP and proper escaping. Storage choice is defence in depth."

Why this lands: you name both threats and both mitigations, commit to a recommendation instead of hedging, and then acknowledge its limit. Interviewers are specifically listening for candidates who claim HttpOnly "solves XSS" — declining that trap is the highest-value moment in the answer.

17. Interview layer: storage

How this gets asked

"Difference between localStorage, sessionStorage and cookies?" · "Where would you store a JWT?" · "Is localStorage secure?" · "How do you share state between tabs?" · "What happens to localStorage in incognito?" · "When would you use IndexedDB?"

The first is pure recall — get it out fast and structured, don't ramble. The JWT one is the depth question, and it's really a security question wearing a storage costume.

Say something like this (the comparison)

"They differ on lifetime, scope, and whether they touch the network. localStorage is per-origin, persists until you clear it, is shared across all tabs, and is never sent to the server. sessionStorage is the same API but scoped to a single tab and wiped when that tab closes. Cookies are much smaller, around 4KB, but they're attached automatically to every request to the domain — that's their whole purpose, server state — and they're scoped by domain and path rather than origin, so they're shared across subdomains. The security difference that matters is that only cookies can be made HttpOnly, which hides them from JavaScript. And both Web Storage APIs are synchronous and block the main thread, so for anything large or structured I'd use IndexedDB."

Why this lands: you organise by axes instead of reciting three unrelated paragraphs, and you volunteer HttpOnly, the synchronous cost, and IndexedDB — three things that show you've hit these in production rather than in a blog post.

Follow-ups

"Is localStorage secure?"

No, and it's important to be precise about what that means. It's not encrypted, it's plain text on disk, and — the part that actually matters — any JavaScript running on the origin can read all of it. That includes every third-party script and every transitive npm dependency you've shipped. So it's fine for a theme preference or a draft, and wrong for anything sensitive: tokens, personal data, anything you'd mind seeing exfiltrated by one compromised package. It is protected by the same-origin policy, so another site can't read it — but that's a much weaker guarantee than people assume it to be.

"Why not just put everything in localStorage? It's simpler."

Three reasons. It's synchronous and disk-backed, so every read and write blocks the main thread — fine for a few small keys, a jank source for anything big or frequent. It's strings only, so you're paying JSON.parse and stringify on every access and losing types like Date. And there's a hard ~5MB ceiling per origin, where exceeding it throws rather than degrading. It's also unavailable in web workers. Once your data is more than a handful of small values, IndexedDB gives you async access, structured data, and far more room.

"What happens to localStorage across tabs, and how would you sync them?"

All tabs on the same origin share one store, so a write in one tab is immediately visible to the others — but they won't know unless you tell them. The storage event fires in every other tab on the origin when a key changes, deliberately not in the tab that made the change. That's the classic mechanism for syncing logout: clear the token, and the other tabs see the event and redirect. For richer cross-tab messaging I'd use BroadcastChannel, which is purpose-built and doesn't abuse storage as a message bus. sessionStorage doesn't participate at all, since each tab has its own.

"What about incognito mode?"

localStorage still works, but it's a separate empty store from the normal session and it's destroyed when the last private window closes — so it effectively behaves like sessionStorage with a longer life. Quotas can be smaller, and some privacy configurations make setItem throw immediately. That's the real lesson: storage writes can throw — from quota, from private modes, from users blocking site data — so I always wrap them in try/catch and degrade gracefully rather than letting an exception take out a render.

"Can app.example.com and shop.example.com share localStorage?"

No. localStorage is keyed by full origin — scheme, host, and port — and there's no way to widen that. Cookies can, because they use a Domain attribute: set Domain=example.com and the cookie goes to every subdomain, which is how cross-subdomain SSO works. If you need shared client-side state across subdomains without cookies, the options are keeping it server-side, or a hidden iframe on a shared origin with postMessage — and that second one is increasingly unreliable as browsers partition third-party storage. Worth noting the flip side: cookie sharing across subdomains means a compromised subdomain can affect the others.

"When does a cookie beat localStorage, apart from auth?"

Whenever the server needs the value on the very first request. Classic cases are theme or locale for server-rendered pages: if the preference lives in localStorage, the server renders the default and JavaScript corrects it after hydration, which is a visible flash. A cookie arrives with the initial HTML request, so the server can render the right thing immediately. Same logic for A/B test buckets and feature flags that affect the initial HTML. The cost is that every byte rides along on every request, so keep it tiny.

Traps

"Cookies are less secure than localStorage." Backwards, and it gets flagged instantly. Cookies are the only one of the three that can be hidden from JavaScript via HttpOnly.

"HttpOnly protects against XSS." It protects against token theft via XSS. It does not stop an injected script from making authenticated requests from the page. Say the precise version.

"localStorage is 5MB." It's approximately 5–10MB and varies by browser, and it's per origin. Say "around 5 megabytes, browser-dependent" — false precision on a number you can't be sure of is a worse look than a range.

Forgetting it's strings only. localStorage.setItem('user', user) stores the literal string "[object Object]". It's a real bug people ship, and mentioning it shows hands-on experience.

18. Interview cheat sheet

The morning-of version. If you can say each of these in one breath, you're in good shape.

Why modules exist
Script tags share one global scope, so files silently overwrite each other's variables and load order becomes load-bearing. IIFEs gave privacy; CommonJS and AMD added explicit dependencies; ESM put it in the language.
ESM vs CommonJS, in one line
ESM is static — resolved at parse time, imports are live read-only bindings. CommonJS is dynamic — require() is a runtime function call returning a snapshot object.
Live binding
An ESM import is a window onto the exporter's variable, so reassignments are visible to importers. A CJS require copies the value at require time and goes stale.
Why CommonJS can't tree shake
Because you'd have to run the program to know which exports are used — require can be conditional or computed, and module.exports is a mutable object indexable by a runtime string.
Dynamic import()
A function call returning a promise for the module namespace object. It's the escape hatch from staticness, and it's what bundlers turn into separate chunks — i.e. code splitting.
Circular deps
CJS gives you a half-built exports object and silent undefined. ESM hoists bindings, so functions work but touching an uninitialised const throws a TDZ ReferenceError. Fix by extracting a third module.
Node interop
"type": "module" switches .js to ESM; .mjs/.cjs force it either way. ESM needs full file extensions and has no __dirname. Dual packages risk loading two copies with two sets of state.
Garbage collection
Mark-and-sweep from roots (globals, call stack + closures, pending timers, attached DOM). Reachable = kept. Not reference counting — so cycles are collected fine.
What a leak actually is
Something long-lived still holds a reference to something you're done with. Four sources: uncleared timers, detached DOM still referenced, listeners on long-lived targets, unbounded caches/closures.
Finding a leak
Confirm a rising baseline in the heap timeline, find a repro loop, take three heap snapshots and compare deltas, filter for Detached, then read the Retainers pane for the reference chain back to a root.
React cleanup
If an effect starts something that outlives the render, return a function that stops it. Cleanup runs before every re-run, not just on unmount. setState after unmount isn't the leak — the un-aborted work is.
WeakMap vs Map
Map keys are strong and block collection; WeakMap keys are weak, so entries vanish when the key object is collected. Keys must be objects. Not iterable and no .size, because exposing contents would leak GC timing into your program.
Storage in one line each
localStorage: per origin, forever, all tabs, never sent. sessionStorage: per tab, dies with the tab. Cookies: ~4KB, auto-sent on every request, scoped by domain+path so shared with subdomains, and the only one that can be HttpOnly.
Auth token
localStorage → XSS steals it permanently. HttpOnly cookie → safe from reading, exposed to CSRF, fixed with SameSite + CSRF token. Prefer the cookie; best is a short-lived in-memory access token plus an HttpOnly refresh cookie; and remember XSS beats both, so the real control is CSP and escaping.
Is localStorage secure?
No — plain text, readable by any script on the origin including every dependency. Same-origin policy protects it from other sites, and nothing else.
Edge cases
Incognito: works, separate store, wiped when the last private window closes. Tabs: shared, and the storage event fires in the other tabs. Subdomains: not shared (use a Domain cookie). Always try/catch your writes.

One last thought to tie the three topics together, because they really are the same question at three timescales. Modules ask where does this code live and who can see it. Garbage collection asks who is still holding this object. Storage asks what survives when the page goes away. In all three, the bugs come from the same place: something is being held onto longer, or seen more widely, than you intended.

If you find yourself stuck on a question in any of these areas, fall back to that. Ask out loud: what's holding a reference to this, and for how long? It's a genuinely good question, and thinking through it in front of an interviewer looks a lot better than a memorised definition. 🙂
