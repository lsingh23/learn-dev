The 12-line component that has nine bugs

I want to start with a piece of code you have almost certainly written. Not a contrived example — the real thing, the one that ships:

function UserProfile({ userId }) {
  const [user, setUser] = useState(null);
  const [isLoading, setIsLoading] = useState(true);
  const [error, setError] = useState(null);

  useEffect(() => {
    setIsLoading(true);
    fetch(`/api/users/${userId}`)
      .then(res => res.json())
      .then(data => { setUser(data); setIsLoading(false); })
      .catch(err => { setError(err); setIsLoading(false); });
  }, [userId]);

  if (isLoading) return <Spinner />;
  if (error) return <ErrorMessage />;
  return <h1>{user.name}</h1>;
}

Take a second and actually look at it. It's clean. It handles loading. It handles errors. It re-fetches when userId changes. By the standards of a code review at most companies, this passes.

And it is, genuinely, broken in about nine different ways. Not "could be nicer" — broken. Users will hit these.

Here's my favourite of the nine, because it's so easy to miss. Imagine a user list where hovering a row shows that user's profile in a panel. The user sweeps their mouse down the list: user 1, user 2, user 3. Three fetches go out. But the network doesn't guarantee order — request 1 might take 800ms while request 3 takes 40ms. So the responses come back 3, 2, 1. And since each response just calls setUser(data) with no awareness of the others, the last one to arrive wins.

The panel now shows user 1 while the mouse is sitting on user 3. Nothing crashed. No error in the console. The UI is just quietly, confidently lying.

You could fix that specific bug. There's a well-known pattern with an ignore flag in the effect cleanup. But then there are eight more bugs, and each one has its own well-known pattern, and by the time you've applied all nine you have written — and I mean this literally — a cache library. A bad one. In every component.

That's the whole story of this guide. But to see why it keeps happening, we need to back all the way up and ask a question that sounds almost too simple.

The big idea: two kinds of state

Here's the framing question, and I want to flag clearly: this is the thing interviewers are actually probing for. Everything else in this guide — staleTime, invalidation, optimistic updates — is downstream of it. Candidates who've read the React Query docs can list the features. Candidates who've understood this can explain why the features exist. Those are very different interviews.

The question is: is all state the same kind of thing?

Think about the state in a typical app. Whether a modal is open. What the user has typed into a search box. Which tab is selected. Dark mode on or off. Now think about a different set: the list of products from the API, the logged-in user's profile, the current cart contents as the server knows them.

React's useState treats these identically. They're both "state." But they behave nothing alike, and the differences are not small.

Client state: you own it

Take "is the modal open." Where does the truth about that live? In your browser tab. Nowhere else. Nobody else on Earth has an opinion about whether your modal is open.

Three consequences follow, and they're the good kind:

It's synchronous. You call setIsOpen(true) and the new truth exists immediately. There's no waiting, no network, no failure mode. There's no such thing as a "loading" modal-open-state.

You're the only writer. Nothing can change it behind your back. If you don't set it, it doesn't change.

Therefore it's always correct. This is the big one. Your copy of the value is the value. There's no original somewhere else that yours might have drifted from. Asking "is my modal state stale?" is a nonsense question — stale relative to what?

Server state: you're borrowing it

Now take "the list of products." Where does the truth live? On a database, in a datacentre, on a machine you don't control, being written to right now by other people.

What you have in useState is not the truth. It's a photocopy of the truth, taken at a moment in the past.

And that changes everything:

It's asynchronous. Getting it takes time and can fail. So every piece of server state drags along two extra pieces of state — are we fetching? and did it fail? — which is why you keep writing those same three useState calls.

It's shared. Other users are reading and writing the same data. Another admin can delete a product while you're staring at it.

And this is the killer: your copy is potentially stale the instant it arrives. Not "might go stale eventually." The response was already a snapshot of the past by the time it left the server. Somebody could have changed the row during the 200ms the response spent in flight.

Wait, what about…?

"Isn't that a bit dramatic? If nobody's editing products right now, my copy is fine."

Sure — usually it's fine. The point isn't that your data is constantly wrong. It's that you have no way of knowing. Correctness is no longer something you can guarantee by reasoning about your own code; it's a probability that decays with time. That's a completely different engineering problem, and it needs completely different tooling. Client state you prove correct. Server state you manage the staleness of.

The analogy: your notebook vs a library book

Client state is a notebook you carry around. Whatever's written in it is what's true, because you're the only one who writes in it. If you want to know what it says, you look.

Server state is a book you've photocopied at the library. The library still has the original. Someone might be correcting it, replacing it, or throwing it away. Your photocopy is useful — instantly readable, no trip required — but it comes with an unavoidable question that the notebook never had: how old is this, and do I need a fresh copy?

And notice the shape of the answer. You don't run back to the library before every single sentence you read — that would be absurd, and slow. You read the photocopy, and you go get a fresh one when it seems worth it: when you come back to your desk, when a while has passed, when you know someone just edited it.

That policy — read the copy now, refresh in the background when it makes sense — is essentially the entire design of React Query. Everything else is detail.

Where does the analogy break? A photocopy can't tell you it's out of date, and it can't quietly update itself while you're reading. React Query's copy can do both, because it can keep talking to the library. So it's better than a photocopy — but the ownership part, the part where the original is somewhere else and can change without telling you, is exactly right.

In an interview

"What's the difference between client state and server state?" is a question with an obvious-sounding answer ("one's local, one's from the API") and a good answer. Here's the good one:

Say this out loud

"Client state is state I own — it's synchronous, I'm the only writer, so it's correct by construction. Server state I don't own; it lives on a machine I don't control, it's shared with other users, and my copy is a snapshot that's potentially stale the moment I receive it. So server state needs a whole set of things client state never needs: caching, deduplication, background refresh, and invalidation. If I keep it in useState or Redux, I end up hand-writing all of that myself — which is exactly what a library like React Query already is."

Why it lands: you named ownership as the root cause and derived the feature list from it, rather than reciting the feature list. That's the signal that you've hit the problem in production rather than skimmed a README.

Every bug in the naive fetch, named

Let's go back to that UserProfile component with the new lens on. Each of these is a direct consequence of pretending a photocopy is a notebook.

1. There is no cache. The data lives in that component's state and dies with it. Navigate away and back and it's gone forever, even though you had it two seconds ago.

2. It refetches on every mount. Which follows from #1: with nowhere to keep the data, the only option is to ask again. Every tab switch, every route change, full spinner, from zero.

3. Race conditions. The one we drew above. Responses can arrive out of order and the stale one wins.

4. No deduplication. If <Header /> and <Sidebar /> and <ProfileCard /> all need the current user, that's three identical requests on the same render pass. They don't know about each other. There's no shared place for them to meet.

5. No retry. One flaky mobile connection, one dropped request, and the user gets an error screen with no way out except a manual page reload — even though a retry 500ms later would have worked.

6. No background refresh. Leave the dashboard open on a second monitor for three hours and it faithfully shows you three-hour-old numbers, with no visual hint that anything's wrong.

7. No invalidation story. This one is worth sitting with. You edit the user's name in a settings form somewhere else in the app. The PATCH succeeds. Now: how does UserProfile find out? It has its own private user in its own private useState. There is no mechanism. Your options are to lift the state up until it's shared (and now you're building a store), or to pass a callback down through six components, or to just... reload the page. Everyone picks reload the page.

8. Loading and error handling are re-implemented, differently, everywhere. Three useState calls per fetch, times every component that fetches, each with slightly different edge-case behaviour. Does yours set isLoading back to true when userId changes? This one does. The one your colleague wrote doesn't, so it shows the previous user's name during the fetch.

9. Memory leak / warning on unmount. If the component unmounts while the request is in flight, the .then still fires and calls setUser on a component that no longer exists. React used to shout at you about this in the console. It doesn't anymore, but the underlying waste is real: you're holding a closure over a dead component and doing work nobody will see.

A common misconception

"Okay, but I can fix all of those. It's just a custom hook."

You can! And people do. But look at what you'd need: a module-level store to hold data across unmounts (#1, #2, #4), keyed by something so different params don't collide, with reference counting so entries get cleaned up eventually (#9), plus request tracking so only the newest response applies (#3), plus a subscription mechanism so every component using a key re-renders together (#4, #7), plus retry with backoff (#5), plus refetch-on-focus (#6), plus a pub/sub API for marking entries out of date (#7).

That's not a custom hook. That's a caching library with a React binding — which is precisely what React Query is. The question was never "library or no library." It was "the well-tested one, or the one you maintain at 6pm on a Friday."

So what is React Query, really?

Quick vocabulary, because the names get used loosely. TanStack Query is the current name of the library everyone still calls React Query (it grew adapters for Vue, Svelte, Solid and Angular, so it dropped "React" from the name). SWR is a smaller, similar library from Vercel. I'll use React Query for the examples and cover the differences later.

Here's the one-sentence version I'd want you to carry out of this guide:

React Query is a cache that lives outside React, keyed by whatever you say, that lets components subscribe to entries and tells you the status of each entry.

It is not a data fetching library. It never makes a network request itself — you hand it a function that returns a promise, and it doesn't care whether that function uses fetch, axios, GraphQL, or reads from a local file. It manages the lifecycle around your function: when to call it, whether to call it at all, what to do while it's pending, and how long to keep the result.

Our nine-bug component becomes this:

✅ Fixed — and every one of the nine is handled
function UserProfile({ userId }) {
  const { data: user, isPending, isError } = useQuery({
    queryKey: ['user', userId],           // 👈 the cache address
    queryFn: () => fetchUser(userId),      // 👈 just a promise
  });

  if (isPending) return <Spinner />;
  if (isError) return <ErrorMessage />;
  return <h1>{user.name}</h1>;
}

Same shape, roughly the same line count. The difference is that useState put the data inside this component, while useQuery puts it in a shared cache and gives this component a view of it. Ten components can hold the same view. One network request feeds all of them. Any of them can mark it out of date and they all update together.

Two of those lines are doing all the work, and the first one deserves its own section.

Query keys: addresses in a cache

A cache is a box of things, and a box of things is useless unless you can find one again. The queryKey is how you find one again. It's the address.

Mentally, the cache is a Map:

['user', 7]            →  { name: 'Ada', ... }
['user', 9]            →  { name: 'Linus', ... }
['todos']              →  [ ... ]
['todos', { done: true }] →  [ ... ]

Keys are arrays, and they're compared by deep value equality, not by reference. So ['user', 7] written in two different files hits the same cache entry — which is exactly how deduplication works, and why you never have to wire components together.

Two rules make key design almost automatic:

Rule 1: every input to queryFn belongs in the key. If your fetch reads userId, userId is in the key. If it reads a page number and a filter, those are in the key too. Break this and you get the classic bug: switching users shows the previous user's data forever, because the key never changed so the cache never looked for anything new.

Rule 2: order keys from generic to specific, like a file path.

['todos']                                // everything todo-ish
['todos', 'list', { status: 'done' }]      // one filtered list
['todos', 'detail', todoId]               // one todo

Why does the order matter so much? Because invalidation matches on prefixes. Ask React Query to invalidate ['todos'] and it marks every key starting with 'todos' — the lists, the details, all of it. That's a single line that correctly refreshes a whole feature area, and you only get it if your keys are structured hierarchically.

Under the hood

The key is hashed into a stable string with a JSON serialiser that sorts object properties. That's why { page: 1, sort: 'asc' } and { sort: 'asc', page: 1 } are the same key. It's also why keys must be JSON-serialisable — don't put a Date, a class instance, or a function in there. And don't put anything that changes identity every render (a fresh object literal is fine — it's compared by value — but Date.now() is not, since it makes a new key every render and every key misses the cache).

staleTime vs gcTime (the confusing pair)

Right. This is the one. If an interviewer asks you exactly one detail question about React Query, there's a very good chance it's this one, and there's a very good chance the person before you got it wrong.

Both are durations in milliseconds. Both are about time and caching. They sound like synonyms. They answer completely different questions, and the trick to never mixing them up again is to hold both questions in your head at once:

staleTimegcTime
Question How long is this data allowed to be trusted without re-checking? How long do we keep data nobody is currently using before deleting it?
About Network traffic — should I refetch? Memory — should I delete?
Clock starts When the data arrives When the last component using it unmounts
Default 0 — stale immediately 5 * 60 * 1000 — 5 minutes
When it expires Data stays in cache, just gets refetched in the background on the next trigger Data is deleted from the cache entirely

The line I'd memorise: staleTime is about freshness, gcTime is about eviction. One decides whether to ask the server again. The other decides whether to free the memory.

And crucially — gcTime's clock only runs while the query is inactive, meaning zero mounted components are using it. As long as something's on screen watching that key, gcTime is irrelevant; the data is never collected.

Why the default staleTime: 0 feels so aggressive

The first time people use React Query they open the Network tab and get a fright: requests firing on every mount, every time they click back into the browser window. "I thought this thing was supposed to cache!"

It is caching. staleTime: 0 means data is considered stale the moment it lands, so any refetch trigger will refetch. But — and this is the part that makes the default defensible — you still get the cached data instantly while that refetch happens. No spinner. The refetch is silent, and if the data hasn't changed, nothing re-renders visibly.

So the default is "always show something immediately, always verify in the background." It's the maximally-correct default: you can never be looking at old data for long. It's also chatty.

Tuning it is a product question, not a technical one — how out of date is this data allowed to be?

// A list of countries. It has not changed since 2011.
useQuery({ queryKey: ['countries'], queryFn: fetchCountries,
           staleTime: Infinity })

// A product page. Minutes-old is fine.
useQuery({ queryKey: ['product', id], queryFn: () => fetchProduct(id),
           staleTime: 5 * 60 * 1000 })

// A live order book. Never trust it. (the default)
useQuery({ queryKey: ['orders'], queryFn: fetchOrders,
           staleTime: 0 })
Wait, what about…?

"What if staleTime is longer than gcTime? Isn't that a contradiction?"

Nope, and this is a great way to prove you've separated them. Say staleTime: Infinity and gcTime: 5min (a very common combo). While something's on screen using the data, it's never refetched. Unmount everything, wait five minutes, and the entry is deleted. Mount again and it fetches — not because it went stale, but because there's nothing in the cache anymore. Freshness and existence are independent properties.

Trap

The wrong answer that gets people dinged: "staleTime is how long data is cached, and gcTime is how long it's cached in the background." That's two vague sentences describing the same imaginary thing. Say freshness vs eviction, and say what event starts each clock. Bonus point available for knowing gcTime was called cacheTime before v5 — the rename happened precisely because "cacheTime" made everyone think it meant staleTime.

The query lifecycle & refetch triggers

Put the two clocks together and you get four states a cache entry moves through:

Notice that stale doesn't mean gone, and it doesn't mean a refetch happens right now. Stale means "eligible for refetching." Something has to actually pull the trigger. By default there are four triggers:

  • A new component mounts with that key (refetchOnMount)
  • The window regains focus — you tab back to the app (refetchOnWindowFocus)
  • The network reconnects after being offline (refetchOnReconnect)
  • An interval fires, if you set refetchInterval (off by default — this is polling)

Refetch-on-focus is the one people either love or immediately disable, and it's worth understanding rather than just switching off. The reasoning: if you've been looking at another tab for ten minutes, your app's data is ten minutes old, and the moment your eyes come back is exactly when you'd want it current. It's the digital version of glancing at the arrivals board again when you look up. If it feels excessive, that's usually a sign your staleTime is too low — raise that rather than killing the trigger, because a focus refetch on fresh data does nothing at all.

Stale-while-revalidate

Time to name the pattern that all of this is built on — the one SWR is literally named after.

Classic fetching gives the user a binary: either you have data, or you have a spinner. Every navigation back to a page you've already visited resets you to the spinner, even though you had perfectly good data for that page thirty seconds ago.

Stale-while-revalidate says: show the stale data immediately, and revalidate in the background. Two steps, both of which happen:

// t = 0ms    user clicks back to the product page
//            → cache hit, render instantly with 40-second-old data
//            → in parallel, a silent refetch goes out
// t = 180ms  fresh response arrives
//            → identical? nothing visibly changes.
//            → different? the price quietly updates in place.

The user perceives this as instant, because it is instant. There was never a moment without content. And the data is never more than one round-trip out of date.

Compare that to the two alternatives. "Always show a spinner" is correct but feels slow every single time. "Only fetch once and trust the cache forever" feels fast but shows wrong data. Stale-while-revalidate takes the perceived speed of the cache and the correctness of the refetch, and the only cost is a brief window where you're showing data that's about to be replaced.

React Query gives you a flag to reflect this in the UI when you want it:

const { data, isPending, isFetching } = useQuery({ ... });

// isPending  → no data at all yet. Show a skeleton.
// isFetching → a request is in flight (may be a background one).

if (isPending) return <Skeleton />;
return (
  <div style={{ opacity: isFetching ? 0.7 : 1 }}>   // 👈 subtle "updating…" hint
    <ProductPrice value={data.price} />
  </div>
);

Getting isPending and isFetching the right way round is a small thing that reads as real experience. isPending means we have nothing. isFetching means we're checking, and we might well have perfectly good data on screen while it's true.

Under the hood

Stale-while-revalidate didn't start in JavaScript. It's an HTTP caching directive from RFC 5861:

Cache-Control: max-age=60, stale-while-revalidate=600

Which tells a browser or CDN: for 60 seconds serve this from cache with no questions asked; for the following 600 seconds keep serving the cached copy and quietly fetch a new one. Compare with the React Query pair — max-age plays the role of staleTime, and the cache holds the entry beyond it just like gcTime does. Same idea, different layer: HTTP applies it per URL in the browser's HTTP cache, React Query applies it per query key in memory, and they compose happily. Knowing this is the same principle at two layers is a nice thing to drop into an interview.

Invalidation: the three tools

Caching is easy. Knowing when your cached copy is wrong is the hard part — hence the old joke about the two hard problems in computer science being cache invalidation and naming things.

React Query gives you three ways to say "this entry is no longer trustworthy," and mixing them up is a very common interview stumble because they sound interchangeable and aren't.

invalidateQueries — the one you want 90% of the time

queryClient.invalidateQueries({ queryKey: ['todos'] });

Say precisely what this does, because the name undersells it. It does two things:

  1. Marks every matching entry as stale, regardless of staleTime.
  2. For entries that are active (something is on screen using them), immediately refetches.

Inactive entries aren't refetched — that would be wasteful, since nobody's looking. They're just flagged, so the next time a component mounts and needs them, it refetches. And remember the prefix match: that one line hits ['todos'], ['todos', 'list', {...}] and ['todos', 'detail', 5] together.

This is the right default because it's declarative. You're not saying "go fetch now" — you're saying "what I have is out of date," and letting the library decide what's worth acting on.

refetch — the imperative hammer

const { data, refetch } = useQuery({ ... });
<button onClick={() => refetch()}>Refresh</button>

Refetches this query, now, ignoring staleness entirely. It's for user-initiated refreshes — a pull-to-refresh, a "reload" button. It doesn't do prefix matching and it doesn't communicate anything to the rest of the cache. Reaching for refetch after a mutation is a small smell: you'll refresh the one query you remembered and miss the four related ones.

setQueryData — write directly into the cache

queryClient.setQueryData(['todo', todo.id], updatedTodo);

No network request. You're putting a value into a cache slot by hand, and every component subscribed to that key re-renders immediately. Two good uses: seeding a detail cache from a list you already fetched (so clicking a row renders instantly), and optimistic updates, which we'll get to next.

The catch: you've now made a claim about server data without asking the server. If your local guess doesn't match what the server actually stored — a computed field, a normalised address, a server-side timestamp — your cache is now confidently wrong. Which is why the standard move is setQueryData for the instant feel, invalidateQueries afterwards for the truth.

In an interview

"How do you invalidate related caches after a mutation?"

Say this out loud

"In the mutation's onSuccess I call invalidateQueries with the broadest key that covers everything affected — usually the feature prefix, like ['todos'], since keys match by prefix so that catches the list and every detail in one call. Invalidating marks them stale and refetches whichever ones are actually on screen; the rest just refetch next time they mount. If a mutation touches more than one area — say, adding a todo changes both the list and a counter — I invalidate both keys. And that's exactly why I design keys hierarchically from generic to specific: it makes invalidation a one-liner instead of a list of individual refetches I have to keep in sync."

Why it lands: you connected key design to invalidation ergonomics. That's the causal link that separates "I've used the API" from "I've maintained a codebase using the API."

Why not just put it in Redux?

Here comes the classic "why not just—". And it deserves a real answer, not a dismissal, because for about a decade putting API data in Redux was the standard advice.

Here's the shape of the problem. A Redux store (or Zustand, or a Context provider — same argument) is a notebook: a place for state you own. The moment you write server data into it, you've made a claim of ownership over something you don't own. And you inherit the full job:

You now own freshness. The store has no concept of "this value arrived at 14:32 and might be old." It's just a value. Any answer to "should we refetch?" has to be built by you — timestamps in the slice, comparisons, refetch decisions in thunks.

You now own deduplication. Two components dispatch fetchUser(7) in the same tick. Redux will happily run both thunks. Preventing that means tracking in-flight requests by key in the store and having the thunk bail if one is pending. That's real code, and you'll write it once per resource.

You now own invalidation. After updateUser succeeds, which slices are wrong? users, obviously. Also currentUser, if it's the logged-in user. Also the teamMembers list, which embedded a copy of the name. Also the recentActivity feed. Nothing tells you this. You find out from a bug report.

And that last point is the real killer: two slices can disagree. Once the same user's name is stored in three places, they will drift. The header says "Ada Lovelace," the sidebar says "A. Lovelace," and both are technically in your state tree. This is the cache-sync problem, and it's not a discipline issue — it's structural. Copies of shared data that update independently diverge. React Query avoids it by having exactly one entry per key that everyone subscribes to; a value can't disagree with itself.

Then there's the boilerplate multiplier, which is less profound but more felt day to day:

❌ One resource, hand-rolled in a store
// slice: data, isLoading, error, lastFetchedAt, inFlight
// actions: fetchStart, fetchSuccess, fetchFailure, invalidate
// a thunk with try/catch, dedup check, staleness check
// selectors: selectUser, selectUserLoading, selectUserError
// ~80 lines. Now do it again for products. And orders.
✅ Same behaviour, plus retries and background refresh
const { data, isPending, isError } = useQuery({
  queryKey: ['user', userId],
  queryFn: () => fetchUser(userId),
});

But — and this matters — sometimes you do want it in the store

An absolutist answer here is a weaker answer. If you say "never put server data in Redux," a good interviewer will push, and they should. Real cases:

Heavily derived or transformed data. If the API response is raw material that you normalise, cross-reference against other responses, and reshape into a client-side model — a graph editor, a spreadsheet, a design tool — then what you're holding isn't really the server's data anymore. It's your model, derived from a fetch. That's client state with a network-shaped origin, and a store is a fine home for it. (Common hybrid: React Query fetches, and the transformed result feeds a store or a useMemo.)

Offline-first apps. If the app must work with no network for hours, with a local write queue that syncs later, then your local copy is temporarily authoritative — the source of truth genuinely is on the device. That inverts the ownership argument. Query libraries have persistence plugins that cover a lot of this, but a serious offline-first app often wants explicit control.

Data the user is actively editing. A long form pre-filled from the server: the moment they type, the draft is client state. Background-refetching it out from under them would be hostile. Fetch with a query, copy into local state to edit, mutate on save.

In an interview

"Why is it bad to store API data in Redux?"

Say this out loud

"Because a store is designed for state you own, and API data is state you don't. Putting it there means you personally take on freshness, deduplication, and invalidation — and once the same entity is copied into several slices, they drift, so the header and the sidebar end up showing different names for the same user. That's the cache-sync problem, and it's structural rather than a discipline issue. Plus it's roughly eighty lines of slice, thunk and selectors per resource to get something worse than a five-line useQuery. That said, I wouldn't say never — if the data is heavily transformed into a client-side model, or the app is offline-first where the local copy is genuinely authoritative, a store makes sense. My default is server state in a query cache, client state in a store, and honestly most apps need far less client state than they think once server state moves out."

Why it lands: the last sentence is the one that gets remembered. Teams that adopt React Query routinely delete most of their Redux, and noticing that shows you've been through the migration rather than read about it.

Mutations & optimistic updates

Queries read. Mutations write. They're different enough to need a different hook: a read is idempotent and can be retried freely and fired automatically, while a write has side effects, should generally run once, and must be triggered by an action.

const { mutate, isPending } = useMutation({
  mutationFn: (newTodo) => api.post('/todos', newTodo),
  onSuccess: () => {
    queryClient.invalidateQueries({ queryKey: ['todos'] }); // 👈 the important bit
  },
});

<button disabled={isPending} onClick={() => mutate({ title: 'Buy milk' })}>
  Add
</button>

Note that mutations do not retry by default, while queries retry three times with exponential backoff. That asymmetry is deliberate: retrying a failed GET is free, retrying a failed POST might create two orders.

Optimistic updates

Normally after clicking "Add" you wait — 200ms, maybe 2s on a train — and the item appears. An optimistic update flips that: put the item in the UI immediately, assume the server will agree, and undo it if you were wrong.

Think of a restaurant. You order a coffee, and the waiter writes it on your bill straight away rather than waiting for the barista to hand it over. Almost always fine. But if the machine is broken, the waiter has to come back and cross the line off the bill. That crossing-off is the part people forget, and it's the part that makes optimism safe. An optimistic update without a rollback isn't optimism; it's just a bug that usually doesn't happen.

The full flow has five steps, and the first two exist for reasons that aren't obvious:

useMutation({
  mutationFn: updateTodo,

  // ── 1 & 2 & 3: fires BEFORE the request goes out ──
  onMutate: async (newTodo) => {
    // 1. cancel in-flight refetches, or one could land
    //    mid-flight and overwrite our optimistic value
    await queryClient.cancelQueries({ queryKey: ['todos'] });

    // 2. snapshot the old value — this IS the undo button
    const previous = queryClient.getQueryData(['todos']);

    // 3. write the optimistic value into the cache
    queryClient.setQueryData(['todos'], (old) =>
      old.map(t => t.id === newTodo.id ? newTodo : t));

    return { previous };  // 👈 handed to onError as `context`
  },

  // ── 4: it failed. Cross the line off the bill. ──
  onError: (err, newTodo, context) => {
    queryClient.setQueryData(['todos'], context.previous);
  },

  // ── 5: win or lose, go ask the server what's actually true ──
  onSettled: () => {
    queryClient.invalidateQueries({ queryKey: ['todos'] });
  },
});

Step 1 catches a genuinely nasty bug. If a background refetch was already in flight when you wrote your optimistic value, its response arrives after your write and clobbers it with the old server data — the item you just added flickers out of existence. cancelQueries kills that in-flight request first. Mentioning step 1 unprompted is a strong signal; most people list snapshot-update-rollback and stop.

Step 5 catches the opposite problem. Even on success, your optimistic guess may not match reality — the server assigned a real ID, set updatedAt, trimmed whitespace, applied a rule. Invalidating on settle means the last word always belongs to the server.

When optimism is a bad idea

Optimism is a bet that the mutation will succeed, and the cost of losing is showing the user something that wasn't true. So don't bet when the odds are poor or the stakes are high:

High failure rate. If a mutation fails 10% of the time — server-side validation you can't predict, conflict-prone concurrent edits — then one in ten users watches the UI change and change back. That's worse than a spinner, because it looks like a glitch.

Money. Never optimistically show a payment as taken, a balance as updated, or an order as placed. If it rolls back, the user has already screenshotted it and is drafting a message to support. Real confirmation only.

Irreversible or externally-visible actions. Sending an email, publishing a post, deleting an account. Rolling the UI back doesn't unsend the email — and worse, if the mutation actually succeeded but the response was lost, rolling back tells the user it failed when it didn't.

The heuristic: optimism suits small, reversible, high-success, high-frequency actions. Toggling a checkbox, liking, reordering a list, marking as read. Those are exactly the interactions where the latency is most annoying and the downside is smallest.

Retries, dedup, pagination, infinite queries

Four smaller things worth being able to speak to.

Retries. Queries retry 3 times by default with exponential backoff (roughly 1s, 2s, 4s, capped at 30s). Sensible for flaky networks; less sensible for a 404, where retrying three times just delays the error screen by seven seconds. So it's common to make retries conditional:

retry: (failureCount, error) => {
  if (error.status >= 400 && error.status < 500) return false; // 👈 don't retry client errors
  return failureCount < 3;
}

Deduplication. Worth being precise about the mechanism, because it's a favourite follow-up. If a query for a key is already in flight and another component asks for the same key, React Query does not start a second request — it attaches the new subscriber to the existing promise. One request, one response, every subscriber re-rendered. It's not throttling or debouncing; it's a lookup in a map of in-flight requests. Ten components, one network call, no coordination code anywhere.

Pagination. Since page number lives in the key, changing pages means changing keys — which means an empty cache and a spinner on every page change. placeholderData: keepPreviousData fixes that: while page 3 loads, keep showing page 2 with isFetching true. The table stops jumping around.

useQuery({
  queryKey: ['projects', page],
  queryFn: () => fetchProjects(page),
  placeholderData: keepPreviousData,  // 👈 no flash of empty table
});

Infinite queries. Different shape entirely, so a different hook. Pagination replaces the visible set; infinite scroll accumulates it. useInfiniteQuery stores an array of pages under one key and gives you fetchNextPage plus a getNextPageParam function that reads the last page to work out the next cursor. Choosing between them is a UX decision: a table with page numbers wants useQuery; a feed wants useInfiniteQuery.

How I'd actually choose:

Already all-in on Redux? Use RTK Query. It's already in the bundle, the devtools story is unified, and the tag-based invalidation is genuinely the most declarative of the three — you describe which endpoints provide and invalidate which tags, and the refetching wires itself. Greenfield, or no strong Redux attachment? TanStack Query. Small app, or you want the smallest thing that solves it? SWR. A few kilobytes, one main hook, and it covers the 80% case — cache, dedup, revalidate on focus — beautifully. If you're in Next.js and mostly reading data, it's plenty. You'll feel the limits when mutations get complicated.

Trap

"I'd use TanStack Query because it's the best one" is a non-answer. Every one of these questions is really can you reason about trade-offs? Name the axis you're optimising — existing stack, bundle size, mutation complexity, multi-framework future — and pick along it. "RTK Query, because this team already runs Redux everywhere and a second cache is a worse cost than a slightly more opinionated API" beats a ranking every time.

Interview follow-ups, answered

Each of these is a real question people get asked. Try answering before you open it.

"What's wrong with useEffect + fetch?"

Nothing, for a one-off. The problem is that it puts server state inside a component, so the data dies on unmount, refetches from scratch on every mount, can't be shared with other components, and can't be told it's out of date after a mutation. On top of that you get race conditions when params change fast, no retry, no background refresh, and loading/error handling re-implemented slightly differently in every component. Every fix for those is a piece of a cache — so you either write a bad cache yourself or use a good one.

"staleTime vs gcTime?"

staleTime is freshness: how long data is trusted without re-checking. Its clock starts when the data arrives, and when it expires the data is still in the cache — it just becomes eligible for a background refetch on the next trigger. gcTime is eviction: how long data with no mounted subscribers is kept in memory before deletion. Its clock starts at the last unmount, and when it expires the entry is gone. Defaults are 0 and 5 minutes. They're independent — staleTime: Infinity with a 5-minute gcTime is a normal, sensible config.

"Why is it bad to store API data in Redux?"

Because a store is built for state you own, and API data is state you don't. You take on freshness, dedup and invalidation yourself, and once an entity is copied into multiple slices they drift, so two parts of the UI show different values for the same thing. Plus it's a large amount of boilerplate per resource. It's not absolute though — heavily transformed client-side models, or offline-first apps where the local copy is authoritative, are legitimate reasons to keep it in the store.

"How do you keep two components from firing the same request twice?"

Give them the same query key. The cache is keyed by a deep-equality comparison on the key array, so both components resolve to the same entry. If a request for that key is already in flight, the second component subscribes to the existing promise rather than starting a new one — one request, both components re-render on the response. There's no coordination code and the components don't need to know about each other. Hand-rolled fetching can't do this because the data lives inside each component, so there's no shared place to check.

"What happens when a mutation fails after an optimistic update?"

You roll back — and that's your responsibility to arrange, it isn't automatic. In onMutate, before writing the optimistic value, you snapshot the current cache with getQueryData and return it; that snapshot arrives in onError as context, and you restore it with setQueryData. You also want cancelQueries at the top of onMutate, otherwise an in-flight background refetch can land after your optimistic write and clobber it. Then in onSettled — success or failure — you invalidate, so the server has the final say either way. And I'd only be optimistic for small reversible actions; never for payments or anything irreversible.

"How do you handle a race condition when the user types fast?"

Two layers. First, the key: if the search term is part of the query key, each term is its own cache entry, so a late response for "ca" writes into the "ca" entry and can't overwrite the "cat" entry the UI is rendering. That structurally eliminates the last-response-wins bug. Second, volume: debounce the input so you're not firing a request per keystroke, and set a staleTime so backtracking to a previous term is served from cache instantly. Add placeholderData: keepPreviousData so results don't blank out between keystrokes. Hand-rolled, you'd fix this with an ignore flag in the effect cleanup — which works, but only for that one component, and you have to remember it every time.

"When would you not use React Query?"

When there's no server state to manage. If the app is a calculator, an editor, a game — pure client state — a query cache adds a dependency and solves nothing. Also when your data isn't request/response shaped: a WebSocket or SSE feed is a push stream, and while you can pipe messages into the cache with setQueryData, the library's model of fetch-and-cache isn't buying you much. If you're already on RTK Query or your framework's own loader — Next.js server components with revalidation, or Remix loaders — adding a second cache is redundant. And for genuinely one or two fetches in a tiny app, a hook is fine; the library pays off with scale, not at N=1.

"How do you invalidate related caches after a mutation?"

In the mutation's onSuccess or onSettled, call invalidateQueries with the broadest key that covers what changed — keys match by prefix, so ['todos'] catches every list and detail under it in one call. That marks them stale and refetches the ones currently on screen; inactive ones refetch on their next mount. If a mutation crosses feature boundaries, invalidate each root key. This is why keys are designed generic-to-specific. With RTK Query the same job is done declaratively with providesTags/invalidatesTags instead.

"Why not just set a huge staleTime and never refetch?"

Then you've turned a cache back into a copy, and you're showing users data that can be arbitrarily old with no path to correction short of a page reload. staleTime should reflect how out of date the data is allowed to be for the product: Infinity for a country list is right; Infinity for inventory levels sells things you don't have. And it's not just about the number — you can keep a long staleTime and still stay correct, because mutations invalidate explicitly regardless of staleness. Long staleTime plus disciplined invalidation is a great combination; long staleTime with no invalidation is just a stale app.

"Does React Query replace Redux?"

It replaces the part of Redux that was caching server data — which in most apps was the majority of the store. What's left is genuine client state: a theme, a sidebar toggle, a multi-step wizard's progress, unsaved form drafts. That's often small enough for useState plus a little Context, or a lightweight store like Zustand. So: not a replacement in principle, usually a big deletion in practice.

Interview cheat sheet

The morning-of version. If you can say each of these in one breath, you're ready.

Client state vs server state
Client state I own — synchronous, single writer, correct by construction. Server state I don't own — asynchronous, shared, and my copy is potentially stale the moment it arrives. Different problem, different tool.
What's wrong with useEffect + fetch
No cache, refetch on every mount, race conditions, no dedup, no retry, no background refresh, no invalidation story, inconsistent loading/error handling, work done after unmount. Fixing all nine is writing a cache library.
What React Query is
A cache outside React, keyed by query key, that components subscribe to. It doesn't fetch — you give it a promise; it manages when to call it and how long to keep the result.
staleTime
Freshness. How long data is trusted without re-checking. Clock starts on arrival. Default 0. Expiring doesn't delete anything — it just allows a background refetch.
gcTime (was cacheTime)
Eviction. How long unused data stays in memory. Clock starts at the last unmount. Default 5 minutes. Expiring deletes the entry.
Query lifecycle
fresh → stale (staleTime elapses) → inactive (last unmount) → deleted (gcTime elapses). Refetch triggers: mount, window focus, reconnect, interval.
Stale-while-revalidate
Serve the cached copy instantly, refetch silently in the background, update in place if it changed. No spinner, never more than one round-trip out of date. Also an HTTP Cache-Control directive — same idea, different layer.
Query keys
Cache addresses, compared by deep value equality. Every input to the fetch goes in the key. Order generic → specific, because invalidation matches by prefix.
invalidate vs refetch vs setQueryData
invalidateQueries: mark stale + refetch the active ones (the default choice). refetch: force this one query now, imperative. setQueryData: write the cache directly, no network.
Deduplication
Same key = same cache entry. A second subscriber attaches to the in-flight promise instead of starting a request. Ten components, one network call.
Why not Redux for API data
You'd own freshness, dedup and invalidation, and duplicated copies across slices drift out of sync. Exceptions: heavily transformed client-side models, and offline-first where the local copy is authoritative.
Optimistic updates
cancelQueries → snapshot → setQueryData optimistically → rollback from the snapshot in onError → invalidate in onSettled. Good for small reversible actions; never for money or anything irreversible.
Mutations vs queries
Queries are idempotent reads: automatic, retried 3× by default. Mutations are writes: triggered manually, no retry by default (a retried POST can double-charge).
Pagination vs infinite
Pagination replaces the set — useQuery with the page in the key plus keepPreviousData. Infinite accumulates it — useInfiniteQuery with getNextPageParam.
Which library
RTK Query if the team is already all-in on Redux (free in the bundle, tag-based invalidation). TanStack Query as the feature-complete default (best devtools, framework-agnostic). SWR when you want the smallest thing that works and mutations are simple.
When not to use one
No server state at all; push-based data like WebSockets; a framework loader or RTK Query already doing the job; an app with two fetches total.

If you remember one thing, make it the first line of that sheet. Every feature in these libraries — the two clocks, the keys, the invalidation, the optimism and its rollback — is a consequence of one fact: the data isn't yours, and your copy started going out of date the instant it arrived.

Once that's the picture in your head, you don't have to memorise the API. You can derive most of it. And that's the difference an interviewer is listening for. 🎯
