55. API List with Loading & Error States

Fetch a list of jobs, render cards. The real test: do you remember all four states?

The ask

Interviewer "Fetch jobs from /api/jobs and show them as a list. Handle loading and errors."

Plain English: one fetch, four possible screens, one Retry button.

What we're building

Every fetch UI is these four screens. Draw this box on the whiteboard first.

It should:

  • Fetch once on mount.
  • Show placeholders while loading.
  • Show an error message + Retry.
  • Show "no jobs" when the array is empty.
  • Render a card per job, keyed by id.
  • Never show two states at once.

The mental model

One status string moves through a track. Wherever it stops, that's the screen.

Why one string, not three booleans isLoading + isError + hasData gives 8 combinations, 5 of them impossible ("loading AND error"). One status makes those unrepresentable. Empty is derived, not stored — it's just success with a length of 0.

The shape of the state

// 'idle' | 'loading' | 'error' | 'success'
const [status, setStatus] = useState('loading'); // which of the 4 screens
const [jobs,   setJobs]   = useState([]);        // the data, only valid on success
const [error,  setError]  = useState(null);      // message to show on error

// derived — never stored:
const isEmpty = status === 'success' && jobs.length === 0;

Rule of thumb: if two pieces of state can disagree, collapse them into one.

Build it in layers

In an interview, build L1 and L2 first, out loud — then ask "want me to add retry and empty state?" They almost always say yes, and now it's your idea.

L1 Static list, no state

The dumbest thing that renders. Proves your markup and keys.

const JOBS = [{ id: 1, title: 'Frontend Engineer', company: 'Acme' }];

<ul>{JOBS.map(j => (
  <li key={j.id}><b>{j.title}</b> — {j.company}</li>
))}</ul>

L2 Fetch on mount

useEffect with [] — a list of dependencies; empty means "run once".

useEffect(() => {
  fetch('/api/jobs')
    .then(res => {
      if (!res.ok) throw new Error(res.status); // fetch does NOT throw on 404/500
      return res.json();
    })
    .then(data => { setJobs(data); setStatus('success'); })
    .catch(e => { setError(e.message); setStatus('error'); });
}, []);

L3 Render all four branches

Early returns. One screen at a time, in this order.

if (status === 'loading') return <Skeletons />;
if (status === 'error')   return <Error msg={error} onRetry={load} />;
if (jobs.length === 0)    return <p>No jobs found.</p>;
return <ul>{jobs.map(...)}</ul>;

L4 Retry + cleanup

Pull the fetch into a named function so a button can call it again. Add an ignore flag — a boolean that says "this component is gone, drop the response".

const load = useCallback(async () => {
  setStatus('loading');
  try { ... } catch (e) { ... }
}, []);

useEffect(() => { let ignore = false; ... ; return () => { ignore = true; }; }, [load]);

The whole thing

function JobBoard() {
  const [status, setStatus] = useState('loading');
  const [jobs, setJobs] = useState([]);
  const [error, setError] = useState(null);
  const [tick, setTick] = useState(0); // bump to retry

  useEffect(() => {
    let ignore = false;                // unmounted? drop the result
    setStatus('loading');
    (async () => {
      try {
        const res = await fetch('/api/jobs');
        if (!res.ok) throw new Error(`Request failed (${res.status})`);
        const data = await res.json();
        if (!ignore) { setJobs(data); setStatus('success'); }
      } catch (e) {
        if (!ignore) { setError(e.message); setStatus('error'); }
      }
    })();
    return () => { ignore = true; };
  }, [tick]);

  if (status === 'loading')
    return <ul aria-busy="true">{[1,2,3].map(i => <li key={i} className="skeleton" />)}</ul>;

  if (status === 'error')
    return (
      <div role="alert">
        <p>Couldn't load jobs. {error}</p>
        <button onClick={() => setTick(t => t + 1)}>Retry</button>
      </div>
    );

  if (jobs.length === 0) return <p>No jobs found.</p>;

  return (
    <ul>
      {jobs.map(j => (
        <li key={j.id}><b>{j.title}</b><div>{j.company} · {j.location}</div></li>
      ))}
    </ul>
  );
}

Styling barely matters here — they're scoring the state machine.

Gotchas

fetch does not reject on 404 or 500. A failed HTTP status still resolves. Without if (!res.ok) throw you call .json() on an error page and land in success with garbage. This is the #1 miss.
Forgetting the empty state. [] renders as nothing — a blank screen that looks broken. Always branch on jobs.length === 0.
Three booleans that contradict. isLoading && isError is a bug you can't see. One status string makes it impossible.
setState after unmount. Navigate away mid-request and the late response still calls setJobs. The ignore flag in the cleanup fixes it (or AbortController).
Error state with no way out. A dead-end error message loses points. Retry button, always.

If they push

"Add pagination / load more." Keep page in state, add it to the deps, and append instead of replace: setJobs(prev => [...prev, ...data]). Track a separate isLoadingMore so the button spins without blanking the list.
"Filter by title as I type." Client-side first: filter the array at render, don't store a second copy. 
const shown = jobs.filter(j => j.title.toLowerCase().includes(q.toLowerCase()));
Empty state now needs two messages: "no jobs" vs "no matches for q". Server-side search means debouncing and cancelling stale requests.
"Now cache it." Say the words: this is what React Query / SWR exist for — cache, dedupe, retry, stale-while-revalidate, all four states as one { data, isLoading, error }. Hand-rolling it is fine for one screen, not for an app.
"Why did it fetch twice?" StrictMode in dev mounts, unmounts, remounts every component to surface missing cleanup. Dev only — not in production. Your ignore flag is exactly the thing it's testing for.
"Spinner or skeleton?" Skeletons for known layouts — they hold the space so nothing jumps; a spinner for unknown or very short waits.

Say this out loud

  • "Every fetch UI has four states — loading, error, empty, success. Let me handle all four."
  • "I'll use one status string instead of separate booleans, so it can't be loading and errored at once."
  • "Careful here — fetch doesn't reject on a 404, so I check res.ok myself."
  • "Empty isn't stored, it's derived: success with a zero-length array."
  • "Cleanup flag so a late response can't set state on an unmounted component."
  • "The error state gets a Retry button and role="alert" so screen readers announce it."
  • "In a real app I'd reach for React Query rather than hand-rolling the cache."
