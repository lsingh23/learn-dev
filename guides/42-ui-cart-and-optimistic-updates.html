Cart, and the moment your state has to agree with a server

The cart state shape

You already know it's a list of records. But there are two versions of that, and picking between them out loud is free seniority points.

Option A — self-contained items
// state:
//   items → [{ id, name, priceCents, qty }]
const [items, setItems] = useState([]);
Option B — quantities only, product data separate
// state:
//   qtyById → { [productId]: qty }   ← the cart
//   products → from the API / props  ← the catalogue
// derived:
//   lines → Object.entries(qtyById).map(([id, qty]) => ({ ...products[id], qty }))
const [qtyById, setQtyById] = useState({});

My recommendation: B whenever products come from an API, A when the cart is a self-contained toy. Three reasons, and I'd say all three: the price lives in exactly one place so it can't go stale in the cart while the catalogue updates; lookup is O(1) instead of a find; and "add something that's already in the cart" becomes qty + 1 instead of a branch. Option B is literally the "make illegal states unrepresentable" move — a duplicate line for the same product can't exist, because the key is the product id.

In practice: state the trade-off, pick A for the demo, say you'd move to B the moment prices come from a server. Below I use A, because that's what you'll be typing.

Four handlers, two lines each

Good shape hands you the handlers. All four are immutable, all four are short.

const add = (p) => setItems(prev =>
  prev.some(i => i.id === p.id)
    ? prev.map(i => i.id === p.id ? { ...i, qty: i.qty + 1 } : i)  // 👈 the forgotten case
    : [...prev, { ...p, qty: 1 }]);

const remove  = (id)      => setItems(prev => prev.filter(i => i.id !== id));
const setQty  = (id, qty) => setItems(prev => prev.map(i => i.id === id ? { ...i, qty } : i));
const clear   = ()        => setItems([]);

The one candidates drop is the first branch of add. They append blindly, and now the cart has two identical rows and the interviewer has their first note. Say it out loud as you write it: "adding something that's already in there should increment, not duplicate."

Now — quick question. What's wrong with this, given that it's fewer characters and does "the same thing"?

❌ Nothing re-renders and you'll lose ten minutes
const item = items.find(i => i.id === id);
item.qty++;          // mutated the object in place
setItems(items);     // same array reference as before
✅ New object, new array
setItems(prev => prev.map(i =>
  i.id === id ? { ...i, qty: i.qty + 1 } : i));

React compares the new state to the old with Object.is. You handed it the exact same array reference, so it bails out and doesn't re-render — even though the data underneath genuinely changed. The screen shows a stale number and everything you try next looks broken. This is the single most expensive bug in a cart round, because the symptom ("clicking does nothing") points nowhere near the cause.

Under the hood

It's not just the array. Even with a fresh array, if you reuse the same item object, any memoized row component (React.memo) sees an identical prop and skips its render. That's why the fix is a new object and a new array: identity is the signal.

Quantity edge cases

Three of these come up almost every time, and handling them unprompted is cheap.

Zero should remove, not linger. A row showing "0 × Keyboard" is a ghost. Fold it into setQty so there's one path:

const setQty = (id, qty) => {
  if (qty <= 0) return remove(id);
  setItems(prev => prev.map(i =>
    i.id === id ? { ...i, qty: Math.min(qty, i.stock ?? Infinity) } : i));
};

Clamp against stock in the same place — clamping in the handler rather than in the input means it holds no matter which caller (button, input, keyboard) triggered it.

The empty-string problem. Backspacing the field gives e.target.value === "", and Number("") is 0 — so the row vanishes mid-edit. Keep the raw string in local state while the field is focused and commit on blur, or use −/+ buttons and dodge the whole class of bug, which is what most real carts do.

Totals are derived. Always.

❌ A second source of truth you must remember to update
const [items, setItems] = useState([]);
const [total, setTotal] = useState(0);   // wrong in four handlers' worth of ways
✅ Computed every render, can never drift
const subtotal = items.reduce((s, i) => s + i.priceCents * i.qty, 0);
const discount = subtotal > 5000 ? Math.round(subtotal * 0.1) : 0;
const shipping = subtotal - discount > 5000 ? 0 : 499;
const tax      = Math.round((subtotal - discount) * 0.2);
const total    = subtotal - discount + shipping + tax;

Notice these chain: discount depends on subtotal, shipping on the discounted subtotal. That chain is exactly why the state version rots — one new rule and you've got five setters to keep in step. As plain consts in render order, it's impossible to get out of sync, and "where does shipping come from" has a one-line answer.

On money: keep prices as integer cents and format at the edge. 0.1 + 0.2 is famously not 0.3, and a cart accumulating floats will be one cent off on somebody's order. Do all arithmetic in integers, then new Intl.NumberFormat('en-GB', { style: 'currency', currency: 'GBP' }).format(total / 100) at the point you render it.

Where the cart lives

Start in the component that owns the cart UI. When the product list also needs to add to it, lift to the nearest common parent. Reach for Context (or Zustand, or whatever the codebase uses) at exactly one moment: when two components far apart in the tree need the same cart and lifting would mean threading props through parts of the app that don't care. The header badge showing "3" plus the cart page is the canonical trigger. Not before — a Context added at minute four reads as over-engineering.

The like button, and optimistic updates

Same guide-34 method, simplest possible shape: a flag. The naive version is what everyone writes first.

❌ Correct, and feels broken
async function toggle() {
  await fetch(`/api/like/${id}`, { method: 'POST' });  // 300ms of nothing
  setLiked(l => !l);
}

Nothing happens for a third of a second. The user taps again. Now you have two problems.

The fix is to stop treating the server as the source of truth for the next paint. Flip the state immediately, fire the request, roll back in the catch.

✅ Optimistic
async function toggle() {
  const prev = liked;              // 👈 capture BEFORE the flip
  setLiked(!prev);                 // UI updates this frame
  try {
    const res = await fetch(`/api/like/${id}`, {
      method: 'POST', body: JSON.stringify({ liked: !prev }),
    });
    if (!res.ok) throw new Error(res.status);
  } catch {
    setLiked(prev);                // roll back to the snapshot
    setError("Couldn't save your like — try again.");
  }
}

Ten lines. But three things make this genuinely hard, and how you handle them is the actual signal.

1. Snapshot the previous value; don't recompute it. The tempting rollback is setLiked(l => !l) in the catch — "just flip it back." That's wrong, because by the time the request fails the value may have moved for other reasons, and you'd be flipping from whatever it is now rather than restoring what it was. Capture prev before the optimistic write. Same rule for a cart: snapshot the whole items array.

2. Races. Two fast clicks fire two requests. If the first fails after the second succeeded, its rollback writes a stale value and the heart is now lying about what's on the server. Three ways out, and I'd name all three: debounce so only the settled value is sent; send the desired final state ({liked: true}) rather than a "toggle" command, so requests are idempotent and last-write-wins is correct; or tag each request with an incrementing id and ignore any response that isn't the latest. The middle one is the cheapest and the most robust — a toggle endpoint is the real bug here.

3. Tell the user. A silent rollback is the worst outcome in the whole pattern: the heart fills, then un-fills half a second later with no explanation, and the user assumes your app is haunted. You owe them a toast, an inline message, something. This is the point most candidates never reach, and mentioning it unprompted lands hard.

One line on the modern built-in

React 19's useOptimistic gives you exactly this — an optimistic value that automatically reverts when the underlying transition settles, so you don't hand-roll the snapshot. Worth naming; don't spend the round on it.

Follow-ups

"Why isn't the total state?"

"Because it's fully determined by the items — if I stored it, I'd have two sources of truth and four handlers that all have to remember to update the second one. Computing it each render means it literally cannot drift. If the list were huge I'd wrap it in a useMemo, but I'd want to measure first."

"The user has two tabs open. Now what?"

"Two independent React trees writing to the same localStorage key, so last write wins and one tab silently loses items. I'd listen for the storage event — it fires in the other tabs — and re-read the cart when it does. If the server owns the cart, then the server is the tiebreaker and I'd refetch on window focus rather than trusting local state."

"How do you persist the cart?"

"localStorage for a guest, keyed by cart id, written in an effect on change. But I'd persist ids and quantities only — not prices. On load I re-fetch the products and rebuild the lines, so a stale cart from three weeks ago picks up current prices and drops anything that's been discontinued. Persisting the price is how you end up honouring a price that no longer exists. For a signed-in user, the server owns it and localStorage is just a cache to merge on login."

"When is optimistic UI a bad idea?"

"When the action is expensive or irreversible, or when being wrong for 300ms is worse than waiting. Payments, deletions, anything that sends an email, anything the user would make a decision on. Optimism is right for cheap, reversible, high-frequency actions — likes, follows, reorder, quantity bumps. If I can't cleanly undo it in the client, I shouldn't pretend it's done."

"Two likes race. What happens?"

"With a toggle endpoint, chaos — two toggles might land as one net change or two, depending on ordering. So I'd make the request carry the desired state instead of a toggle, which makes it idempotent, and I'd either debounce to the settled value or track a request id and ignore stale responses. And the rollback has to restore the snapshot from that request, not re-flip whatever the current value happens to be."

Cheat sheet

  • Cart is a list of records. Prefer { [id]: qty } + a separate catalogue when products come from an API; a flat array when it's self-contained.
  • add increments if present, appends otherwise. The forgotten case.
  • Never mutate. item.qty++ then setItems(items) is the same reference — React bails out and nothing renders.
  • qty ≤ 0 removes the row. Clamp against stock in the handler, not the input.
  • Totals, tax, shipping, discount are all derived. Never state.
  • Integer cents for arithmetic, Intl.NumberFormat at the edge.
  • Context only when two distant components need it — header badge + cart page.
  • Optimistic = flip now, fire, roll back in the catch.
  • Snapshot before the flip. Don't recompute the old value in the catch.
  • Send desired state, not a toggle — idempotent requests survive races.
  • A silent rollback is a bug. Always surface the failure.
  • Don't be optimistic about payments or anything irreversible.
