56. useFetch with Cleanup & Abort

Take the loading/error/data dance out of a component and put it in one hook — without stale data landing on screen.

The ask

Interviewer "Write a useFetch(url) hook. It should refetch when the url changes, and it must not set state after the component unmounts or after a newer request has started."

Plain English: one hook, many components, and only the latest request is allowed to win.

It should:

  • Fetch on mount, refetch when url changes
  • Return loading, error and data
  • Clear old data the moment the url changes
  • Ignore results from outdated requests
  • Abort the in-flight request on unmount
  • Expose refetch() for a retry button

(Guide 55 covers rendering the four states — loading / error / empty / data. Here we only move that logic into a hook.)

The mental model

An effect is a subscription with an expiry date. React hands you a cleanup function; whatever you started in the effect must be cancelled there. A fetch you can't cancel is a fetch that lands late — on the wrong url.

The bug in one line Responses come back in whatever order the network feels like. Last response wins, not last request.
Two fixes, use both ignore flag in cleanup → stale response can't call setState. AbortController → the request itself is cancelled, saving bandwidth.

The shape of the state

const [data, setData]       = useState(null);   // the parsed JSON, null until it arrives
const [error, setError]     = useState(null);   // an Error, null when things are fine
const [isLoading, setLoading] = useState(true); // true while a request is in flight
const [tick, setTick]       = useState(0);      // bump it to force a refetch

return { data, error, isLoading, refetch };

Why this shape? Three independent slots the caller can render directly, plus one verb. No status string to keep in sync — and never a single object, or one setState would clobber the others.

Build it in layers

In an interview build L1 and L2 out loud, then say "this has a race condition — want me to fix it?" That sentence is most of the score.

L1 Fetch once, no safety

The dumbest version that works.

function useFetch(url) {
  const [data, setData] = useState(null);
  useEffect(() => {
    fetch(url).then(r => r.json()).then(setData);
  }, [url]);
  return { data };
}

L2 Loading + error + reset

Reset on every url change, so you never show the old resource.

useEffect(() => {
  setData(null); setError(null); setLoading(true); // ← reset first
  fetch(url)
    .then(r => { if (!r.ok) throw new Error(r.status); return r.json(); })
    .then(setData)
    .catch(setError)
    .finally(() => setLoading(false));
}, [url]);

L3 The ignore flag

A local boolean the cleanup flips. Stale responses arrive and do nothing.

useEffect(() => {
  let ignore = false;
  fetch(url).then(r => r.json())
    .then(d => { if (!ignore) setData(d); })
    .finally(() => { if (!ignore) setLoading(false); });
  return () => { ignore = true; };  // runs before the next effect + on unmount
}, [url]);

L4 AbortController + refetch

Actually cancel the network call. An abort is not an error — swallow it.

const controller = new AbortController();
fetch(url, { signal: controller.signal })
  .catch(err => {
    if (err.name === 'AbortError') return; // we caused this. not a failure.
    setError(err);
  });
return () => controller.abort();
const refetch = useCallback(() => setTick(t => t + 1), []);
useEffect(() => { /* ... */ }, [url, tick]);

The whole thing

import { useState, useEffect, useCallback } from 'react';

export function useFetch(url) {
  const [data, setData] = useState(null);
  const [error, setError] = useState(null);
  const [isLoading, setLoading] = useState(true);
  const [tick, setTick] = useState(0);

  const refetch = useCallback(() => setTick(t => t + 1), []);

  useEffect(() => {
    let ignore = false;
    const controller = new AbortController();

    setData(null); setError(null); setLoading(true);

    fetch(url, { signal: controller.signal })
      .then(res => {
        if (!res.ok) throw new Error('HTTP ' + res.status);
        return res.json();
      })
      .then(json => { if (!ignore) setData(json); })
      .catch(err => {
        if (err.name === 'AbortError') return;   // expected, ignore
        if (!ignore) setError(err);
      })
      .finally(() => { if (!ignore) setLoading(false); });

    return () => { ignore = true; controller.abort(); };
  }, [url, tick]);

  return { data, error, isLoading, refetch };
}

// usage
const { data, error, isLoading, refetch } = useFetch('/api/users/' + id);

Gotchas

Passing an inline options object as a dependency. useFetch(url, { headers }) creates a new object every render → the effect re-runs → setState → render → new object → infinite loop. 
// ✗ new identity every render
useEffect(() => {...}, [url, options]);

// ✓ pick one
useEffect(() => {...}, [url, JSON.stringify(options)]);   // small & serialisable
const optsRef = useRef(options); optsRef.current = options; // don't want to refetch
const opts = useMemo(() => ({ headers }), [headers]);       // caller stabilises it
Treating an abort as a failure. Cleanup fires → catch runs → you render "Something went wrong" on a perfectly good page. Always if (err.name === 'AbortError') return; first.
Not resetting state on url change. Without the reset, user 2's loading spinner sits next to user 1's name. Blank it out, then load.
Only aborting, no ignore. Abort can lose to a response already in the microtask queue. The boolean is the cheap, always-correct guard; abort is the optimisation.
refetch defined without useCallback. A new function every render breaks any consumer that puts it in a dependency array or a memoised child.

If they push

"Add caching." A module-level Map keyed by url. Seed state from it, write to it on success. 
const cache = new Map();
const [data, setData] = useState(() => cache.get(url) ?? null);
// on success: cache.set(url, json);
Then you need invalidation — say that out loud; it's the hard part.
"Two components request the same url at once." Dedupe with an in-flight map: Map<url, Promise>. If a promise exists, await it instead of firing a second request.
"Why does it fetch twice in dev?" React 18 StrictMode mounts, unmounts, remounts every component to surface exactly this class of bug. Dev-only. If your cleanup is correct it's harmless — that's the point of the test.
"Cancel on a fast-typing search box." Same hook: debounce the url in the caller, and the abort handles the rest. Every keystroke's request dies with its effect.
"So why does everyone use React Query / SWR instead?" Because this hook is the easy 10%. A real app also needs a shared cache across components, request dedupe, retries with backoff, refetch on window focus and reconnect, pagination, optimistic updates, and cache invalidation after a mutation — plus the data surviving unmount so going back doesn't re-flash a spinner. useFetch stores data per component; React Query stores it per url, globally. That single difference is the whole library. Write useFetch to prove you understand effects; ship React Query.

Say this out loud

  • "I'll return data, error, isLoading and refetch — three things to render, one verb."
  • "The effect is keyed on the url, so changing the url is the refetch."
  • "This version has a race — a slow first request can land after a fast second one and overwrite it."
  • "So I set ignore = true in the cleanup, and abort the request too."
  • "An AbortError isn't a real error, I bail out before touching error state."
  • "I reset data to null when the url changes so we never show the previous resource."
  • "For anything real I'd reach for React Query — the caching and dedupe is where this gets hard."
