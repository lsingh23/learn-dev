Web Performance: Core Web Vitals & the Rendering Path

Why your page is slow, how the browser actually decides when to paint, and how to talk about all of it without hand-waving.

Here's a thing that happened to me. I once "optimised" a landing page by lazy-loading every image on it. Every single one. The page had fewer bytes on first load, the Network panel looked gorgeous… and the performance score went down. Not a little. A lot.

That result made no sense to me at the time, and if it makes no sense to you either, good — that's exactly the gap this guide fills. The reason it got worse is a small, specific fact about when the browser learns it needs to download a picture, and it only becomes obvious once you can picture what the browser is doing moment to moment.

So that's where we start. Not with metrics, not with acronyms — with the machinery. Once you can see the machine, every performance rule you've ever half-memorised turns into something you can derive on the spot. And deriving things on the spot is, more or less, the entire skill an interviewer is checking for.

Part 1The critical rendering path

You type a URL, you hit enter, and some milliseconds later there are pixels. In between, the browser runs a fixed sequence of steps. That sequence has a name — the critical rendering path — and essentially every performance technique in existence is "make one of these steps happen sooner, or happen less often."

Let's walk it, slowly, one step at a time. I promise this pays off.

Step 1: HTML arrives as bytes, and gets parsed into the DOM

The server doesn't hand you a document. It hands you a stream of bytes, in chunks, over the network. The browser doesn't wait for the last byte before starting work — that would be a waste of good waiting time. It parses incrementally: as each chunk lands, it turns characters into tokens (<div>, class="hero", text) and turns tokens into nodes, and links those nodes into a tree.

That tree is the DOM — the Document Object Model. It's the browser's in-memory representation of your markup. Not the markup itself; a live object graph you can poke at from JavaScript.

The important word there is incrementally. The browser is building the tree while the rest of the HTML is still in flight. Remember that — it's why a script in the middle of your document is such a problem, which we'll get to shortly.

Step 2: CSS arrives, and gets parsed into the CSSOM

While parsing the HTML, the browser hits something like this:

<link rel="stylesheet" href="/styles/main.css">

It fires off a request for that file and — this part matters — keeps parsing the HTML. A stylesheet doesn't stop the HTML parser. But when the CSS does arrive, it gets parsed into its own tree: the CSSOM, the CSS Object Model. Every rule, resolved into a tree that mirrors the document structure, so the browser can answer "what are the final computed styles for this node?"

Why a tree and not a flat list? Because CSS cascades and inherits. If body has font-size: 16px, every descendant that doesn't override it needs to know that. The only way to compute a node's real style is to know its ancestors' styles. Tree.

Step 3: DOM + CSSOM combine into the render tree

Now the browser walks the DOM, and for each node asks the CSSOM: what does this look like? The result is a third tree, the render tree — only the things that will actually be drawn, each one carrying its computed styles.

"Only the things that will actually be drawn" is doing real work in that sentence. Two categories get excluded:

  • Nodes that are never visual at all: <head>, <meta>, <script>.
  • Nodes with display: none.

And here's the contrast that shows up in interviews constantly:

display: nonevisibility: hidden
In the render tree?No — excluded entirelyYes — it's in there
Takes up space?NoYes, full box, just not painted
Toggling it causes…Layout (the box appears/disappears)Paint only (geometry never changed)

visibility: hidden is like an invisible person still standing in the queue: you can't see them, but you still can't take their spot. display: none is them leaving the building — everyone behind shuffles forward.

Step 4: Layout (a.k.a. reflow)

The render tree knows what to draw and how it should look, but not where. Layout is the pass that computes geometry: exact position and exact size of every box, in real pixels, given the viewport size.

This is where percentages become numbers. width: 50% means nothing until you know the parent is 800px wide. Layout resolves the whole cascade of dependencies, top to bottom, and it is expensive — it's the step most likely to show up as a red bar in a performance profile.

Step 5: Paint

Now the browser fills in pixels: text glyphs, colours, borders, shadows, gradients, images. It doesn't necessarily paint into one flat image — it paints into one or more layers, like sheets of transparent acetate stacked on top of each other.

Step 6: Composite

Finally those layers get stacked and drawn to the screen in the right order, respecting things like z-index, opacity and transform. This step can be handed to the GPU, which is extremely good at exactly one thing: taking existing bitmaps and moving, scaling, rotating and fading them. That fact becomes very important in a minute.

Under the hood

Real browser engines subdivide these steps further — style recalculation is technically separate from render-tree construction, and paint splits into "record display lists" and "raster." Chrome's Performance panel labels them Recalculate Style, Layout, Pre-Paint, Paint, Composite Layers. The six-step model is the one everyone reasons with, and it's the one to say out loud in an interview. Just don't be surprised when DevTools shows extra rows.

Part 2Render-blocking CSS, parser-blocking scripts

Why CSS is render-blocking

Look at that diagram again and ask a slightly nasty question: the DOM is being built incrementally, so the browser has partial content almost immediately. Why doesn't it just… paint it? Show something, then restyle when the CSS lands?

Because the result would be horrifying. Imagine the browser paints your unstyled HTML: Times New Roman, blue underlined links, everything stacked in one column, full-bleed images at natural size. Then 300ms later the CSS arrives and the whole page violently rearranges itself into your actual design. That's called a flash of unstyled content, and browsers decided decades ago they'd rather show you nothing than show you that.

So the rule is: the browser will not perform the first paint until the CSSOM is complete. CSS is render-blocking.

My analogy: CSS is the set-dressing crew for a stage play. The actors (your DOM nodes) can walk on stage and get in position while the crew is still working — but the curtain does not go up until the set is finished. You don't let the audience watch people hang the backdrop.

Wait — so does CSS block parsing too?

No, and this distinction is a great one to land in an interview. A stylesheet blocks rendering, not HTML parsing. The parser happily keeps building the DOM while CSS downloads.

There is one sneaky exception. If the parser hits an inline <script> while a stylesheet is still downloading, it must pause that script — because the script might call getComputedStyle() or read offsetHeight, and answering that needs the CSSOM. So the script waits for the CSS, and the parser waits for the script. CSS ends up blocking parsing transitively. That's a genuinely deep answer if you ever get pushed on it.

Why synchronous scripts are parser-blocking

Now the scripts. Here's a plain one:

<script src="/js/analytics.js"></script>

When the HTML parser hits this, it stops. Fully stops. It downloads the file, executes it top to bottom, and only then resumes building the DOM. Everything below that line in your HTML is, for that moment, not in the document at all.

Why so brutal? Because of one ancient API: document.write(). A script is allowed to inject raw HTML into the parse stream at the exact point it appears. The parser genuinely cannot know what the rest of the document looks like until the script has had its say. So it waits.

<p>One</p>
<script> document.write('<p>Surprise!</p>') </script> // 👈 parser must wait
<p>Two</p>
// → One / Surprise! / Two

Nobody writes document.write anymore, but the parser can't know that in advance, so the blocking behaviour stays. It's a compatibility scar.

The consequence: a synchronous script in your <head> delays the DOM, which delays the render tree, which delays your first paint. A 200KB analytics bundle at the top of the document can cost you a second of blank screen on a mediocre phone.

Under the hood: the preload scanner

Browsers aren't completely helpless here. While the main parser is blocked on a script, a secondary lightweight parser — the preload scanner — races ahead through the raw HTML looking for URLs (src, href) and starts downloading them early. It can't build DOM, it just prefetches.

This matters practically: resources the preload scanner can see in your HTML get discovered early. Resources hidden inside JavaScript or CSS (a background-image in a stylesheet, an image URL that only exists after React renders) are invisible to it and get discovered late. That's one of the deepest reasons client-side-rendered pages have bad LCP.

Part 3async vs defer vs type="module"

This is probably the single most-asked question on this entire topic, so let's make it airtight. There are three things that could vary, and understanding the attributes means knowing which of the three each one changes:

  1. Does downloading block the parser? (Never, actually — download is always parallel for these.)
  2. Does executing block the parser?
  3. Is execution order guaranteed?

In words:

  • Plain <script src> — parser stops, downloads, executes, resumes. Order guaranteed. Worst for perf.
  • async — downloads in parallel with parsing, then executes the instant it's ready, interrupting the parser wherever it happens to be. Order is not guaranteed: whichever downloads first runs first. Great for standalone things with no dependencies — analytics, error trackers.
  • defer — downloads in parallel, then waits until the HTML is fully parsed, then executes in document order, just before DOMContentLoaded. This is the sensible default for your app code.
The trap

The wrong answer that gets candidates dinged: "async loads asynchronously and defer defers loading." That's backwards-ish and says nothing. Both download asynchronously. The difference is entirely about when they execute and whether order is preserved. Say it that way and you sound like you've actually debugged this.

What type="module" changes

<script type="module" src="/app.js"></script>

A module script is deferred by default — you don't need to write defer, it already behaves that way. Beyond timing, it also brings:

  • Its own scope (no accidental globals) and strict mode always on.
  • Real import/export, so the browser recursively fetches the dependency graph before executing anything.
  • Each module URL executes once, even if imported by five files.
  • CORS applies — cross-origin modules need proper headers.
  • Adding async to a module overrides the deferred behaviour: it runs as soon as it and its imports are ready.
How this gets asked

"What's the difference between async and defer?" · "Where do you put your script tags and why?" · "What does type=module change about script loading?"

Say this out loud

"Both download in parallel with HTML parsing, so neither blocks the download. The difference is execution. async executes the moment the file lands, which can interrupt parsing at an arbitrary point, and execution order between multiple async scripts isn't guaranteed — so I use it for independent things like analytics. defer waits until the HTML is fully parsed and then runs scripts in document order, right before DOMContentLoaded, which is what I want for app code that touches the DOM or depends on other scripts. And type="module" is deferred by default, so I don't need to add anything."

Why it lands: you separated download from execute, mentioned ordering, and tied each to a real use case. That's three levels of depth in twenty seconds.

Part 4Reflow, repaint, composite

Everything so far was about the first render. But pages keep changing — you toggle a class, an animation runs, data arrives. Each change forces the browser to redo some suffix of the pipeline. How much of the pipeline is the whole game.

Think of it like a printed newspaper. Changing a headline's size means re-flowing every article on the page around it — that's layout. Changing the headline's ink colour means the layout is fine, you just reprint that patch — that's paint. Sliding a transparent sticker across the finished page changes neither — that's composite.

This is why the animation advice you've heard is what it is:

❌ Animating layout properties 
.card {
  transition: left 300ms;   /* every frame = full reflow */
}
.card:hover { left: 20px; }
✅ Animating composited properties 
.card {
  transition: transform 300ms; /* 👈 GPU just moves the bitmap */
}
.card:hover { transform: translateX(20px); }
Under the hood: layout thrashing

Here's a subtle killer. Browsers batch style changes and flush layout once, at the end of the frame — unless you ask for a value that requires up-to-date geometry. Reading offsetHeight, getBoundingClientRect(), scrollTop or getComputedStyle() forces a synchronous layout right now.

So a loop that writes then reads, writes then reads, forces a layout on every iteration:

// ❌ forced synchronous layout, N times
for (const row of rows) {
  row.style.height = row.offsetHeight + 10 + 'px';
}

// ✅ read everything first, then write everything
const heights = rows.map(r => r.offsetHeight);
rows.forEach((r, i) => { r.style.height = heights[i] + 10 + 'px'; });

Saying the phrase "layout thrashing" and describing the read/write batching fix is one of the highest-signal things you can do in a perf interview.

Part 5Core Web Vitals

Google needed a small set of numbers that correlate with "does this page feel good to use," that could be measured on real users' devices, and that map to three distinct kinds of pain. They landed on three questions:

  • Is it there yet? → LCP (loading)
  • Does it respond when I touch it? → INP (interactivity)
  • Does it stop jumping around? → CLS (visual stability)

A page "passes" when the 75th percentile of real users hits the good threshold. Not the average — the 75th percentile, so a quarter of your users can still be having a bad time and you pass. Mentioning p75 unprompted is a nice signal that you've looked at real dashboards.

LCP — Largest Contentful Paint (good: ≤ 2.5s)

What it measures: the moment the largest content element visible in the viewport finishes rendering. Usually a hero image, a video poster, or a big block of headline text. The browser keeps re-evaluating as things load — the "largest element" can change several times — and the final one wins.

It's a proxy for the human question "has the main thing loaded yet?" Which is exactly the right thing to measure, because a page that's technically interactive but still shows a grey box feels broken.

What typically causes a bad LCP:

  1. Slow server response (TTFB). If the HTML takes 1.2s to arrive, you've spent half your budget before the browser has done anything.
  2. Render-blocking resources. Big stylesheets and synchronous scripts in the head delay first paint, and LCP can't happen before first paint.
  3. Slow resource load time. The LCP image itself is 3MB, or unoptimised, or discovered late.
  4. Client-side rendering delay. The hero doesn't exist in the HTML at all; it appears only after a JS bundle downloads, parses, executes, fetches data, and renders. The preload scanner never had a chance.

How to fix it:

<!-- in <head>: tell the browser about the hero image immediately -->
<link rel="preload" as="image" href="/hero.avif" fetchpriority="high">

<!-- and on the element itself -->
<img src="/hero.avif" width="1200" height="600"
     fetchpriority="high"       <!-- 👈 jump the queue -->
     alt="...">       <!-- 👈 note: NO loading="lazy" -->
  • Preload the LCP image so it's discovered in the first few bytes of HTML rather than after CSS or JS runs.
  • fetchpriority="high" — by default browsers give images low priority until layout proves they're in the viewport. This overrides that guess.
  • Never lazy-load it (whole section on this below — it's a favourite trick question).
  • Server-render the hero so it's in the initial HTML.
  • CDN + caching + compression to attack TTFB.
  • Shrink the image — modern format, right dimensions. Often this alone fixes it.

INP — Interaction to Next Paint (good: ≤ 200ms)

INP replaced FID (First Input Delay) as a Core Web Vital in March 2024. Knowing that, and knowing why, is genuinely worth points — it shows you've read something written after 2022.

FID measured only the delay before the browser could start handling your first interaction. That's two enormous limitations. It ignored every interaction after the first, and it ignored the actual work — if your click handler took 900ms to run and re-render, FID cheerfully reported a great score, because it stopped counting the instant the handler began.

So basically every site passed FID while users sat there tapping a button that did nothing. Not a useful metric.

INP measures the full round trip, for interactions across the entire page visit: from the moment you tap, through input delay (waiting for the main thread to be free), through the event handlers running, through style and layout, all the way to the next frame actually painted showing the result. Then it reports roughly the worst interaction of the visit (technically it discards a small number of outliers on pages with many interactions).

What causes a bad INP: long tasks hogging the main thread (a task over 50ms blocks input), enormous synchronous re-renders (a React state change that re-renders 3,000 components), expensive event handlers, heavy work fired on every keystroke, and giant DOM trees that make every style recalculation slow.

How to fix it:

  • Break up long tasks and yield to the main thread between chunks, so pending input can be handled.
  • Debounce/throttle handlers that fire on input, scroll or resize.
  • Move heavy computation off the main thread into a Web Worker.
  • Show feedback in the next frame, do the work after. Paint the "loading" state first, then start the expensive job.
  • Reduce re-render scope — memoize, split state, virtualize big lists.
Wait — "yield to the main thread"? What does that mean?

JavaScript is single-threaded, and the same thread paints. While your function runs, nothing else can happen: no click can be processed, no pixel can be drawn. "Yielding" means deliberately stopping, handing control back to the browser so it can process input and paint, then resuming your work in a later task. We cover the actual APIs in Part 16.

CLS — Cumulative Layout Shift (good: ≤ 0.1)

You're reading an article. You go to tap a link. In that exact instant an ad loads above it, everything jumps down, and you tap "Delete account" instead. That feeling is what CLS measures.

It's a unitless score: for each unexpected shift, impact fraction (how much of the viewport moved) × distance fraction (how far it moved, as a share of viewport size). Those get summed into session windows, and the worst window is your score.

The key word is unexpected. Shifts within 500ms of a user interaction are excluded — if you click "show more" and content expands, that's expected, and it isn't penalised.

What causes it:

  • Images without dimensions. The browser reserves zero height, lays out the text, then the image arrives and shoves everything down.
  • Ads, embeds and iframes that inject themselves at unknown size.
  • Web fonts. The fallback font renders first, then your webfont swaps in with different metrics, and every line re-flows. That's FOUT — flash of unstyled text. The alternative, FOIT (flash of invisible text), hides the text entirely while the font loads, which avoids the shift but can nuke your LCP if the LCP element is text.
  • Content injected above existing content — a cookie banner, a "you have 3 new messages" bar, a late-arriving hero.
  • Animating layout properties like height or top instead of transform.

How to fix it:

❌ No reserved space 
<img src="/product.jpg" alt="Blue mug">
<!-- height 0 until it loads, then BOOM, everything moves -->
✅ Space reserved from the first paint 
<img src="/product.jpg" width="800" height="600" alt="Blue mug">

/* CSS keeps it responsive; the ratio comes from the attributes */
img { max-width: 100%; height: auto; }

/* or, when you don't know the file's real size */
.media { aspect-ratio: 16 / 9; }

Modern browsers turn width/height attributes into an implicit aspect-ratio, so they reserve correctly-shaped space before the file arrives, even in a fluid layout. This is the single highest-leverage CLS fix and it's free.

For the rest: give ad slots a fixed min-height container. For fonts, font-display: optional avoids the swap entirely (the font is used only if it arrives almost instantly, otherwise it's skipped for this page load), and size-adjust / ascent-override on a @font-face fallback lets you tune the fallback's metrics to match your webfont so the swap barely moves anything. And animate with transform, which as we established doesn't touch layout at all.

How this gets asked

"What are the Core Web Vitals?" · "What replaced FID and why?" · "A page has CLS of 0.4 — how do you find the cause?"

Say this out loud

"LCP, INP and CLS — loading, interactivity, visual stability, measured at the 75th percentile of real users. INP replaced FID in early 2024 because FID only measured the delay before the first interaction's handler started, so a page could score perfectly while every button took a second to respond. INP measures the full interaction-to-paint latency across the whole visit, so slow handlers and heavy re-renders finally count."

Part 6Diagnostic metrics, and lab vs field

The three Core Web Vitals tell you that something's wrong. These others tell you where.

  • TTFB — Time to First Byte. Request sent → first byte of the response. This is DNS + connection + TLS + server think-time + redirects. If TTFB is 1.5s, no amount of frontend work saves your LCP. Fix the backend, add a CDN, kill redirect chains, cache at the edge.
  • FCP — First Contentful Paint. When anything from the DOM first paints. Sits between TTFB and LCP. If FCP is bad, suspect render-blocking CSS/JS. If FCP is fine but LCP is bad, the page started drawing quickly and then the specific big element was slow — usually the hero image or client-side rendering.
  • TBT — Total Blocking Time. Sum of the "over 50ms" portion of every long task between FCP and interactive. It's the lab-measurable stand-in for INP, since a lab test has no real user clicking things. High TBT almost always means too much JavaScript executing.

Notice how neatly they decompose LCP: LCP ≈ TTFB + render-blocking delay + resource load time + element render delay. When someone hands you a bad LCP, that equation is your entire diagnostic strategy.

Lab data vs field data

This distinction separates people who have run Lighthouse from people who have shipped performance work.

Lab (synthetic)Field (real users / RUM)
ToolsLighthouse, WebPageTest, DevToolsCrUX, Search Console, your own web-vitals reporting
ConditionsOne simulated device, one throttled network, cold cache, no extensionsEvery device, every network, warm caches, ad blockers, everything
Reproducible?Yes — great for A/B-ing a fixNo — it's a distribution, reported at p75
Can measure INP?Not really (no real interactions) — uses TBT as a proxyYes, properly
Good forDebugging, catching regressions in CIKnowing whether users are actually suffering

The failure mode is optimising until Lighthouse says 100 and declaring victory, while real users on three-year-old Android phones over patchy 4G are still waiting six seconds. Lighthouse is a microscope, not a thermometer. Use field data to decide what to fix and whether you fixed it; use lab data to figure out why.

In an interview

Volunteering "…but I'd want to check field data too, because Lighthouse is one simulated device and CrUX is what our users actually experienced at p75" is one of the cheapest ways to sound senior in this entire topic. It signals that you know a score isn't the goal — the users are.

Part 7Lazy loading — and the hero image trap

The idea is simple: don't download things nobody is going to look at. A 40-image gallery where the user only ever sees the first three is 37 wasted downloads competing for the same bandwidth as the things that matter.

The browser gives you this for free:

<img src="/gallery/12.jpg" loading="lazy"
     width="600" height="400" alt="...">

<iframe src="https://example.com/map" loading="lazy"></iframe>

The browser defers the request until the element is near the viewport. Keep the width/height — lazy-loaded images cause layout shift precisely because they arrive late, so reserving space matters more here, not less.

For anything that isn't an image or iframe — a heavy chart component, an infinite-scroll trigger, a video that should only initialise when visible — use IntersectionObserver, which tells you asynchronously when an element enters the viewport, without you writing scroll handlers that run 60 times a second:

const observer = new IntersectionObserver((entries) => {
  for (const entry of entries) {
    if (!entry.isIntersecting) continue;
    loadChartFor(entry.target);
    observer.unobserve(entry.target); // 👈 don't load it twice
  }
}, { rootMargin: '200px' });      // 👈 start early, before it's visible

document.querySelectorAll('.chart').forEach(el => observer.observe(el));

That rootMargin is the difference between "lazy loading" and "user stares at a blank box." Start the load a few hundred pixels before the element is on screen, so it's ready by the time it's seen.

The third flavour is route-based code splitting: don't ship the JavaScript for the settings page to someone reading the homepage. More on that in the next section.

Why you must never lazy-load the LCP image

Back to my humiliating story from the opening. Here's what actually happens when you put loading="lazy" on your hero image.

Normally, the preload scanner spots <img src="/hero.jpg"> within milliseconds of the HTML arriving and starts downloading it immediately — in parallel with CSS, before layout even exists.

With loading="lazy", the browser deliberately does not do that. It has to wait until it knows where the image will be, which means waiting for CSS, waiting for layout, and only then discovering "oh, this one's in the viewport, better fetch it." That's a whole extra round trip, bolted onto the end of the critical path, for the exact element the LCP metric is timing.

So the decision line is above the fold vs below the fold. Anything in the initial viewport loads eagerly, ideally with fetchpriority="high" for the biggest one. Everything below the fold gets loading="lazy". That's the whole rule, and it's a rule you can now derive instead of memorise.

A common misconception

"Lazy loading is always a win because fewer bytes is always better." No — lazy loading trades total bytes for discovery latency. That's a great trade for things the user may never see, and a terrible one for things they're staring at right now.

Part 8Bundle size and code splitting

JavaScript is the most expensive kilobyte you can ship. A 200KB image and a 200KB JS bundle are not remotely equivalent: the image gets decoded off the main thread and painted; the JS must be downloaded, parsed, compiled and executed on the same thread that handles every tap. On a low-end phone that's the difference between "a bit slower" and "the page is frozen."

Strategies, roughly in the order I'd apply them:

1. Route-based splitting first. Biggest win for the least risk. Someone landing on /pricing should not download the checkout flow, the admin dashboard, or the rich text editor.

const Dashboard = lazy(() => import('./routes/Dashboard')); // 👈 own chunk

That import() — a dynamic import — is the signal your bundler uses to cut the graph into a separate file that's fetched on demand.

2. Component-level splitting for heavy widgets. A charting library, a video player, a WYSIWYG editor, a date picker with every locale. If it's below the fold or behind an interaction, split it and load it on intersection or on click.

3. Vendor chunking. Put stable third-party dependencies in their own chunk. Your app code changes every deploy; React doesn't. Separate chunks mean users only re-download the part that actually changed. (This pairs directly with the caching section — the two techniques only pay off together.)

4. Tree shaking. Bundlers statically analyse ES module import/export to drop code nothing references. It only works with ESM — CommonJS require() is dynamic, so it can't be analysed the same way — and it's defeated by side effects, which is what "sideEffects": false in package.json is for.

5. Audit with a bundle analyser. Every bundler has one, and they all draw the same treemap of "what is actually in here." Run it before guessing. Nine times out of ten there's one absurd rectangle — a date library with every locale, an icon set imported wholesale, two copies of the same package at different versions.

6. Replace heavy dependencies. The classics: moment (huge, all locales bundled) → date-fns, day.js, or the native Temporal API where available. Lodash imported as a whole → per-method imports, or just native array methods.

❌ Pulls in the whole library 
import _ from 'lodash';
_.debounce(save, 300);
✅ Pulls in one function 
import debounce from 'lodash-es/debounce';
debounce(save, 300);

7. Ship modern syntax to modern browsers. Transpiling to ES5 for browsers that died years ago inflates your bundle noticeably — every arrow function becomes a function expression, every async becomes a state machine, plus polyfills. Setting a realistic browserslist target, or shipping a modern build via type="module" with a legacy nomodule fallback, can cut 10–20% for free.

The how of configuring all this — splitChunks, manualChunks, module federation — belongs in the bundler guide; here, what matters is knowing which strategy solves which problem and in what order you'd reach for them.

Part 9Image optimisation

If you can only do one thing to a typical website, do this one. Images are usually the majority of page weight, and unlike JavaScript, fixing them requires no refactoring at all.

Pick the right format

  • AVIF — best compression by a wide margin, ~50% smaller than JPEG at similar quality. Slower to encode; use it as the first choice with fallbacks.
  • WebP — ~25–35% smaller than JPEG, universally supported now. Great middle ground, supports transparency and animation.
  • JPEG — the safe fallback for photos.
  • PNG — only for images that need lossless quality or crisp transparency. Never for photographs; a PNG photo is often 5× the size for no visible gain.
  • SVG — anything vector: logos, icons, illustrations. Scales infinitely, usually tiny, and you can style it with CSS.

Serve the right size, not just the right format

The most common waste in the wild isn't format, it's dimensions. A 4000px-wide photo downscaled by CSS to a 400px thumbnail still downloads all four thousand pixels — and the phone still decodes them, which costs memory and main-thread time. You're paying 100× for something invisible.

<img src="/photo-800.jpg"
     srcset="/photo-400.jpg 400w, /photo-800.jpg 800w, /photo-1600.jpg 1600w"
     sizes="(max-width: 700px) 100vw, 700px"
     width="800" height="600" alt="Harbour at dusk">

Two attributes, two different jobs, and interviewers love to check you know which is which:

  • srcset lists the files you have and how wide each one is.
  • sizes tells the browser how wide the image will be displayed at a given viewport width. Without it the browser assumes 100vw and over-downloads.

The browser then picks, factoring in device pixel ratio. It makes this choice from the preload scanner, before CSS — which is why sizes has to be your promise about the layout rather than something read from the stylesheet.

<picture> for format fallback and art direction

<picture>
  <source srcset="/hero.avif" type="image/avif">
  <source srcset="/hero.webp" type="image/webp">
  <img src="/hero.jpg" width="1200" height="600" alt="...">
</picture>

The browser takes the first <source> whose type it supports; the <img> is the required last-resort fallback (and it's the element that actually renders, so all your attributes go there).

Art direction is the other use: with a media attribute on each source you can serve a genuinely different crop on mobile — a tight portrait crop instead of a wide landscape shot squeezed to nothing. That's a job srcset can't do, because srcset assumes all the candidates are the same picture.

Finally: quality settings — 75–85 is usually indistinguishable from 100 at a fraction of the size; and a CDN with on-the-fly transformation (Cloudinary, imgix, Next/Image, Cloudflare Images) so you upload one original and it generates every format and size on demand, cached at the edge. That's the pragmatic answer to "how do you handle this at scale."

Part 10Eliminating render-blocking resources

We established that nothing paints until the CSSOM is ready. So the goal is: make the CSS needed for the top of the page arrive as fast as physically possible, and make everything else not block.

Inline the critical CSS. Extract the styles needed to render the above-the-fold content and put them directly in a <style> tag in the head. Zero extra requests — it arrives with the HTML. Then load the full stylesheet without blocking:

<style>/* ~10KB of above-the-fold styles, inlined */</style>

<link rel="stylesheet" href="/full.css"
      media="print" onload="this.media='all'"> <!-- 👈 the classic trick -->
<noscript><link rel="stylesheet" href="/full.css"></noscript>

Why does that work? Because a stylesheet only blocks rendering if it applies to the current medium. media="print" means "irrelevant to the screen," so the browser downloads it at low priority without blocking paint; the onload then flips it to all and it applies. Same reason you can legitimately split a genuine print stylesheet out — it'll never block.

Defer your scripts. Covered above, but it belongs on this checklist: defer (or type="module") on everything, async for independent third-party tags.

Handle fonts deliberately. Fonts are sneaky render-blockers because they're discovered late — the browser only knows it needs a font after parsing the CSS that references it, and only if a matching element exists.

@font-face {
  font-family: 'Inter';
  src: url('/fonts/inter.woff2') format('woff2');
  font-display: swap;   /* 👈 show fallback text immediately */
}

Self-host rather than using a third-party font host — that removes a whole DNS + TCP + TLS handshake to another origin from the critical path. Then <link rel="preload" as="font" type="font/woff2" crossorigin> the one or two faces you actually need above the fold. (Yes, crossorigin is required even same-origin — fonts are always fetched in CORS mode, and without it you'll download the file twice. That's a lovely detail to drop.)

font-display is a real trade-off, not a free win: swap protects LCP but risks CLS, optional protects CLS but may skip your font on slow connections. Say which one you'd pick and why, and you've turned a checklist item into a judgement call.

Remove unused CSS. Big component libraries and years of accumulated styles mean most pages ship far more CSS than they use. DevTools' Coverage panel shows you exactly how much, colour-coded, live. It's often 70%+ unused, and every unused byte is still render-blocking.

Part 11Debouncing, throttling, passive listeners

Some events fire absurdly often. scroll, resize, mousemove, and input on a fast typist can all produce dozens of events per second. If your handler does anything non-trivial, you've just guaranteed a bad INP.

Two shapes of fix, and the distinction matters:

  • Debounce — wait until the events stop, then run once. "Tell me when they've finished typing." Perfect for search-as-you-type, autosave, validation.
  • Throttle — run at most once every N ms while events continue. "Tell me every 100ms, no matter how much they scroll." Perfect for scroll position, progress indicators, anything that needs continuous-ish updates.

Debouncing a scroll handler that updates a sticky header would mean the header only moves after you stop scrolling — useless. Throttling a search request means firing a request every 200ms while someone types a ten-letter word — wasteful. Picking the wrong one is a classic interview trap; the giveaway is asking yourself whether you need updates during the activity or only after it.

The perf-specific companion is passive listeners:

window.addEventListener('scroll', onScroll, { passive: true }); // 👈

A touch or wheel listener is allowed to call preventDefault() to cancel scrolling. That means the browser can't start scrolling until your handler has run and it knows whether you cancelled — so a slow handler literally delays the scroll itself, producing that horrible sticky feeling. passive: true is a promise: "I will never call preventDefault." The browser can then scroll on the compositor immediately and run your handler whenever. (Browsers now default touchstart/touchmove/wheel on window and document to passive for this reason, but being explicit is still good practice — and knowing why is the interview answer.)

Part 12Caching strategies

The fastest request is the one that never happens. Caching is how you make the second visit — and often the second page — nearly instant.

Cache-Control, the one header that matters

Cache-Control: public, max-age=31536000, immutable

The pieces:

  • max-age=N — this response is fresh for N seconds. During that window the browser uses the cached copy with no network request at all. Not a fast request. Zero request.
  • no-cache — a famously misleading name. It does not mean "don't cache." It means "cache it, but revalidate with the server before every use." You still get the speed benefit when nothing changed (the server replies 304 Not Modified, no body), you just always pay one round trip.
  • no-store — this is "don't cache." Never write it to disk. For genuinely sensitive responses.
  • immutable — "this URL's content will never change; don't even revalidate on reload." Stops the browser from wasting round trips when a user hits refresh.
  • stale-while-revalidate=N — my favourite. After freshness expires, serve the stale copy instantly and refetch in the background for next time. The user gets zero latency; the cache self-heals. Ideal for content that's allowed to be a few minutes old.

ETag and conditional requests

An ETag is a fingerprint of the response body. When the cached copy goes stale, the browser asks again but includes If-None-Match: "abc123". If nothing changed, the server replies 304 Not Modified with an empty body. You still pay the round trip, but not the bytes. (Last-Modified + If-Modified-Since is the older, coarser, timestamp-based version of the same idea.)

The pattern that makes aggressive caching safe

Here's the tension. You want max-age=31536000 (a year!) so returning users download nothing. But if you cache app.js for a year and then deploy a fix, users are stuck on the broken version for a year. That's terrifying, so most people set a timid max-age=3600 and lose most of the benefit.

The resolution is beautifully simple: make the filename depend on the content.

// build output
app.8f3a2b1c.js
vendor.c4e91d07.css

// served with
Cache-Control: public, max-age=31536000, immutable

Change one character of source and the hash changes, so the URL changes, so it's a different resource the browser has never seen and must fetch. Nothing changes, the URL is identical and it's served from cache instantly. You never need to invalidate anything — you don't bust the cache, you sidestep it.

The one piece that must not be cached aggressively is the HTML, because that's what points at the hashed filenames. Give it no-cache (revalidate every time) so a deploy is picked up immediately, and let the HTML hand out the new URLs. This is exactly why vendor chunking pays off: your app hash changes every deploy, React's doesn't, so returning users re-download 30KB instead of 300KB.

How this gets asked

"How do you cache aggressively without shipping stale code?" — this is a favourite because the naive answer ("set a short max-age") shows you've never thought about it.

Say this out loud

"Content-hashed filenames plus a one-year immutable max-age on the assets, and no-cache on the HTML. The HTML is always revalidated, so a deploy is picked up straight away, and it references new hashed URLs for anything that changed. Since the URL changes whenever the content changes, there's nothing to invalidate — unchanged files keep their URL and stay cached. I'd also split vendor code into its own chunk so a normal deploy doesn't invalidate the framework."

CDN edge caching and service workers

A CDN caches your responses in data centres physically near your users. Two wins: fewer milliseconds of round-trip latency (physics — light in fibre isn't that fast), and your origin server never sees most of the traffic. For static assets this is nearly free; for HTML it's where stale-while-revalidate at the edge shines.

A service worker is a script that sits between your page and the network and can answer requests itself, from a cache it controls. That gives you offline support and instant repeat loads, with real strategies — cache-first for hashed static assets, network-first for API data, stale-while-revalidate for things in between. It's powerful and genuinely tricky (update lifecycles, users stuck on old service workers, scope rules), so in an interview: know what it is, know it's the layer below HTTP caching that you fully control, and don't pretend it's a casual afternoon's work.

Part 13Virtualization for long lists

You've got a table of 10,000 rows. Each row has a few divs, a bit of text, a button. You render them all. Now:

  • Building ~60,000 DOM nodes takes hundreds of milliseconds of main-thread time — a giant long task that tanks INP.
  • Layout has to compute geometry for all of them.
  • Memory balloons; on a mid-range phone the tab may just die.
  • Every subsequent style recalculation has to walk a monstrous tree, so everything gets slower, including things unrelated to the list.

And the user can see about 12 rows.

Virtualization (or windowing) is the fix: render only the rows in the viewport, plus a few extra above and below (the overscan, so fast scrolling doesn't reveal blank space). Then keep the scrollbar honest by putting a spacer element of the full theoretical height in the container, and translate the rendered window to the right offset.

Fixed height is the easy case: row 4,217's offset is just 4217 × rowHeight, so you can compute the visible window with arithmetic. Variable height is much harder — you don't know an item's height until you render it, so libraries estimate, render, measure, then correct, which can cause visible jitter or scroll jumps. If you can make your rows a fixed height, do; it's not a cop-out, it's a real engineering trade.

And the costs are real, which is the part candidates forget:

  • Accessibility. Screen readers may announce "row 3 of 15" instead of "of 10,000" unless you set aria-setsize/aria-posinset and use the right roles. Keyboard focus can land on an element that gets unmounted mid-scroll.
  • Ctrl+F doesn't work. Browser find can't find text that isn't in the DOM. If your users search the page, this is a genuine regression and you need your own search UI.
  • SEO. Content not in the DOM generally isn't indexed. Never virtualize a public content list you want in search results.
  • Scroll anchoring and restoration get fiddly — restoring the exact position after navigating back is real work.
  • Complexity. Sticky headers, expandable rows, and drag-to-reorder all get harder.

So when is it worth it? When the list is genuinely large (hundreds to thousands of complex rows), the content is app-like rather than content-like, and you've measured that the DOM size is the bottleneck. For 200 simple rows, don't — pagination or "load more" is simpler and keeps Ctrl+F working. Also check whether CSS content-visibility: auto gets you most of the win first: it lets the browser skip rendering work for off-screen subtrees while keeping the nodes in the DOM, so search and accessibility survive.

Part 14Walk me through debugging a slow page

This is asked constantly, and it's not really testing tool knowledge. It's testing whether you have a process or whether you just start changing things. Here's a narrative you can actually deliver.

0. Ask what "slow" means

Slow to load? Slow to respond after loading? Slow on one route or everywhere? Slow for everyone or only on mobile? Half the time this question alone reframes the problem. And it shows you don't optimise blind.

1. Get a baseline — field data first, then lab

Start with real-user data if it exists: CrUX, Search Console, or your RUM dashboard. Which vital is failing, at p75, on which device class? That tells me whether I'm hunting a loading problem, an interactivity problem, or a stability problem — three completely different investigations.

Then run Lighthouse on the specific page, mobile preset, throttled, to get a reproducible artefact I can re-run after each change. I write the numbers down. Optimising without a written-down baseline means you can never prove you helped.

2. Network panel — the waterfall

Disable cache, throttle to Slow 4G, reload, and read the waterfall top to bottom:

  • How long is the first bar? That's TTFB. If the HTML takes 1.5s, stop — this is a backend or CDN problem and no frontend change will save it.
  • What's blocking at the top? Render-blocking CSS and synchronous scripts show as a wall before anything else starts.
  • What's the biggest file? Sort by size. It's usually an unoptimised image or one enormous JS chunk.
  • When does the LCP image start downloading? If it starts late, it was discovered late — that's a preload or lazy-loading problem.
  • Are there redirect chains, or waterfalls of dependent requests? A request that can't start until another finishes is latency you can often parallelise away.

3. Performance panel — record and read the flame chart

Record a page load (or an interaction, if that's the complaint). Then:

  • Look for long tasks — the main-thread blocks with the little red triangle. Anything over 50ms blocks input. That's your INP/TBT culprit list, sorted by size.
  • Read the flame chart depth-first. Width = time. Find the widest bar, then look at what's underneath it — that's what it called. Keep descending until you hit something you recognise from your own code or a specific library.
  • Check the summary breakdown — Scripting vs Rendering vs Painting vs System. Mostly scripting? Too much JS: split it, defer it, or move it to a worker. Mostly rendering/layout? Layout thrashing or a huge DOM: look for forced synchronous layout warnings, which DevTools flags explicitly. Mostly painting? Large paint areas or expensive effects like big blurs and shadows.
  • Layout Shift markers on the timeline show exactly what moved and when — click one and it names the element.

4. Framework-level: the React Profiler (if it's re-render bound)

If the scripting time is inside the framework rather than in a library, switch to the React Profiler. Record the slow interaction and look at the commit chart: which components re-rendered, how many, and how long each took. The usual findings are a context value changing on every render, a new object or array literal passed as a prop breaking memoization, or an unvirtualized list re-rendering all its children. The Profiler even tells you why each component re-rendered if you turn that setting on.

5. Fix one thing. Measure. Confirm.

Change one thing at a time and re-run the same lab test. If the number didn't move, revert it — a "fix" that doesn't measurably help is just added complexity and future confusion. Then ship it and watch field data over the following week, because that's the only place you learn whether real users got faster.

The framing that makes you sound senior

Measure first, optimise second. Say it, and mean it. The most common junior answer is a shopping list — "I'd minify, lazy load images, use a CDN, tree shake…" — which sounds knowledgeable but reveals that you'd start changing things before knowing what's wrong. Every one of those might be irrelevant to this page.

The senior answer is: get a measurement, form a hypothesis, test the hypothesis, verify the fix moved the number, confirm in the field. Same knowledge, completely different signal.

Part 15Resource hints

Sometimes you know something the browser doesn't. Resource hints are how you tell it.

<!-- I need this NOW, and you'd discover it too late -->
<link rel="preload" as="image" href="/hero.avif" fetchpriority="high">

<!-- probably needed on the NEXT navigation, whenever you're idle -->
<link rel="prefetch" href="/checkout.js">

<!-- I'll be talking to this origin soon: do the handshakes now -->
<link rel="preconnect" href="https://api.example.com" crossorigin>
<link rel="dns-prefetch" href="https://api.example.com">

<!-- fetch + parse this ES module graph early -->
<link rel="modulepreload" href="/app.js">
  • preload — "fetch this at high priority, I need it for this page." The killer use case is a late-discovered critical resource: an LCP image referenced from CSS, or a font. The as attribute is mandatory — it sets the priority and the correct request headers, and without it the browser may fetch the file twice.
  • prefetch — "fetch this at the lowest priority, when you're idle, because the user will probably need it next." Prefetching the JS for the page behind your main CTA makes that navigation feel instant. It's low priority by design, so it won't compete with the current page.
  • preconnect — do DNS + TCP + TLS to an origin ahead of time, without fetching anything. Setting up a fresh HTTPS connection costs multiple round trips; on mobile that can easily be 300ms. Use it for origins you know you'll hit — your API, a font host, a payment provider. Add crossorigin when the eventual request is CORS (fonts always are), otherwise you warm the wrong kind of connection.
  • dns-prefetch — just the DNS lookup. Cheaper and more widely supported; a reasonable fallback alongside preconnect.
  • modulepreload — like preload but module-aware: it fetches, parses, and follows the import graph, so a deep dependency chain doesn't turn into a serialised waterfall of round trips.
A common misconception

"Preloading more things makes the page faster." It doesn't, and this is the follow-up an interviewer will hit you with. Bandwidth is finite. preload means high priority, and priority is relative — if you preload ten things, you've told the browser everything is urgent, which is identical information to telling it nothing is. Worse, those high-priority fetches now compete with your actual critical resources, and can make LCP worse than doing nothing.

Rule of thumb: preload should be a short list — typically the LCP image and one or two fonts. If you're preloading more than a handful, you're not prioritising, you're just shouting.

The other trap: preconnecting to a dozen origins. Each connection consumes resources and DNS/TLS capacity. Two to four preconnects for origins you'll definitely use, and no more.

Part 16Reducing main-thread work

One thread runs your JavaScript, computes styles, does layout, and paints. If JS occupies it for 300ms, nothing else happens for 300ms: no click is processed, no frame is drawn, no hover state updates. The page is, in every way the user can perceive, frozen.

A long task is any task over 50ms. Fifty milliseconds is the threshold because it leaves enough headroom to respond to an interaction within a comfortable budget even if input arrives at the worst possible moment.

Think of the main thread as a single checkout lane in a shop. If someone is paying for a full trolley, everyone behind them waits — even the person holding one banana. You can't add a lane (JS is single-threaded), but you can ask the big shopper to pack a few bags, step aside, and rejoin.

Yielding: breaking one long task into many short ones

❌ One 400ms task — page is frozen 
function processOrders(orders) {
  for (const order of orders) {   // 5,000 orders
    expensiveTransform(order);
  }
}
✅ Many short tasks — input can get through 
async function processOrders(orders) {
  let lastYield = performance.now();
  for (const order of orders) {
    expensiveTransform(order);
    if (performance.now() - lastYield > 50) {
      await scheduler.yield();   // 👈 let the browser breathe
      lastYield = performance.now();
    }
  }
}

The total work is identical. But now the browser gets gaps between chunks in which it can handle a click and paint a frame. Same CPU, dramatically better INP — because INP measures responsiveness, not throughput.

Your options for that yield point:

  • await scheduler.yield() — the modern, purpose-built one. Crucially it yields at high priority, so your continuation resumes ahead of other pending tasks rather than going to the back of the queue. (Newer API; feature-detect and fall back.)
  • await new Promise(r => setTimeout(r, 0)) — the universal fallback. Works everywhere, but your continuation queues behind everything else.
  • navigator.scheduling.isInputPending() — ask "is a user input waiting right now?" and only yield if so. Avoids yielding needlessly when nobody's interacting.
  • requestIdleCallback(fn) — "run this whenever there's spare time at the end of a frame." Right for genuinely optional background work: prefetching, analytics batching, warming caches. Wrong for anything the user is waiting on, since it might not run for a long time on a busy page.

Web Workers: actually leaving the main thread

Yielding shares one lane more politely. A Web Worker opens a second lane — a genuine background thread.

// main.js
const worker = new Worker('/parser.worker.js');
worker.postMessage({ csv: rawText });
worker.onmessage = (e) => renderTable(e.data.rows); // 👈 UI never froze

The catch: a worker has no DOM access. It can't read or touch elements — it only exchanges messages, and the data gets copied (structured clone) unless you use transferable objects like ArrayBuffers. So workers are for computation, not rendering: parsing a big CSV, image processing, crypto, diffing large datasets, running a search index.

Rule of thumb: if the work takes a meaningful chunk of time and doesn't need the DOM, it belongs in a worker. If it needs the DOM, break it into chunks and yield.

Part 17Interview follow-ups, answered

Click to reveal each answer — try answering out loud first. That's the whole point.

"async vs defer?"

Both download in parallel with HTML parsing, so download is never the difference. async executes as soon as the file arrives, interrupting parsing at whatever point it's reached, and multiple async scripts run in whatever order they finish — no guarantees. defer waits until parsing is complete, then runs scripts in document order right before DOMContentLoaded. So: async for independent third-party scripts, defer for app code with dependencies or DOM access. type="module" behaves like defer automatically.

"Why is CSS render-blocking?"

Because the render tree needs both the DOM and the CSSOM, and CSS cascades — a rule at the bottom of the last stylesheet can override everything above it, so no element's final style is known until all the CSS is parsed. If the browser painted early it would show unstyled content and then violently reflow into the real design. It chooses to show nothing rather than show that. Worth adding: CSS blocks rendering, not HTML parsing, though it blocks parsing indirectly when a synchronous script has to wait for the CSSOM.

"What replaced FID, and why?"

INP replaced FID as a Core Web Vital in March 2024. FID only measured the delay before the first interaction's handler started running — so a page where every button took 800ms of work could still score perfectly, because FID stopped counting the moment the handler began. INP measures the full interaction-to-next-paint latency, across all interactions in the visit, and reports roughly the worst one. That means long tasks, expensive handlers and heavy re-renders finally show up in the score.

"How would you improve LCP on a page you've never seen?"

I'd decompose it before touching anything, because LCP is roughly TTFB + render-blocking delay + resource load time + element render delay, and the fix is completely different for each. First: what is the LCP element? DevTools tells me. Then check TTFB — if that's 1.5s it's a server/CDN problem and nothing on the frontend helps. Then look for render-blocking CSS and sync scripts delaying first paint. Then check when the LCP resource starts downloading: late start means a discovery problem (preload it, remove loading="lazy", add fetchpriority="high"), slow transfer means it's too big (modern format, right dimensions, CDN). If the element only appears after JS runs, the real fix is server-rendering it. Then re-measure to confirm which one actually mattered.

"What causes layout shift, and how do you fix it?"

Anything that changes the size or position of already-painted content without the user asking for it. The big four: media without dimensions, late-injected content like ads and banners above existing content, web fonts swapping in with different metrics, and animating layout properties. Fixes map one to one: always set width/height or aspect-ratio on images, videos and iframes so space is reserved before the file lands; give ad and embed slots a fixed min-height; use font-display: optional or metric-matched fallbacks via size-adjust; and animate transform/opacity instead of top/height. Shifts within 500ms of a user interaction are excluded, so expanding an accordion on click is fine.

"Why shouldn't you lazy-load the hero image?"

Because you delay the very thing the metric measures. Normally the preload scanner finds the hero in the first few bytes of HTML and starts fetching it immediately. With loading="lazy" the browser has to wait for CSS and layout to determine whether the image is in the viewport before it will even request it — so you've added a full round trip to the end of the critical path, for the LCP element specifically. The rule is: above the fold loads eagerly, ideally with fetchpriority="high"; below the fold gets lazy loading.

"How do you cache aggressively without shipping stale code?"

Content-hashed filenames plus Cache-Control: max-age=31536000, immutable on assets, and no-cache on the HTML. The hash means the URL changes exactly when the content changes, so there's nothing to invalidate — unchanged files keep their URL and their cached copy, changed files are new URLs the browser has never seen. The HTML is revalidated every load, so a deploy is picked up immediately and hands out the new URLs. I'd also split vendor code into its own chunk so a normal app deploy doesn't invalidate the framework, and use stale-while-revalidate for content that's allowed to be slightly stale.

"Walk me through debugging a slow page."

First I'd ask what "slow" means and for whom, then get field data to see which vital is failing at p75 and on what devices — that decides whether it's a loading, interactivity or stability problem. Then a Lighthouse run on mobile throttling as a reproducible baseline I write down. Network panel next: TTFB, render-blocking resources at the top of the waterfall, biggest payloads, and when the LCP resource starts. If it's an interactivity problem, a Performance recording: find long tasks over 50ms, read the flame chart down to my own code, and check the scripting-vs-rendering-vs-painting split, because that points at completely different fixes. React Profiler if the time is inside the framework. Then fix one thing, re-run the same test to confirm the number moved, and watch field data after shipping. Measure first, optimise second.

"Reflow vs repaint?"

Reflow (layout) recomputes geometry — position and size of boxes — and is triggered by geometric changes like width, height, padding, font-size, or adding and removing DOM nodes. It's expensive because it can cascade to ancestors and siblings, and it's always followed by repaint and composite. Repaint only redraws pixels without recomputing geometry — triggered by things like colour, background, box-shadow, visibility. Cheaper, but still main-thread work. Below both is composite: changing only transform or opacity on a promoted layer skips layout and paint entirely and runs on the GPU, which is why that's what you animate. The related gotcha is layout thrashing — interleaving DOM writes and geometry reads forces a synchronous layout on every iteration, so you batch all reads and then all writes.

"When is virtualization worth it?"

When the list is genuinely large — hundreds to thousands of non-trivial rows — and I've measured that DOM size or initial render is the bottleneck, not something else. The wins are a much smaller DOM, faster initial render, and cheaper style recalculation everywhere. The costs are real: Ctrl+F stops finding off-screen content, screen readers need explicit aria-setsize/aria-posinset, off-screen content isn't indexed for SEO, and scroll restoration and variable row heights get genuinely fiddly. So I wouldn't virtualize a public content page or a 200-row table — pagination is simpler. I'd also try content-visibility: auto first, since it skips rendering work for off-screen subtrees while keeping the nodes in the DOM, so find-in-page and accessibility survive.

"Why not just put everything in one bundle? Fewer requests is faster, right?"

That was true under HTTP/1.1, where browsers capped parallel connections per origin, so concatenation was a real optimisation. Under HTTP/2 and HTTP/3, requests are multiplexed over one connection and the per-request cost is small, so the tradeoff flipped. One giant bundle means every user downloads, parses and executes code for pages they'll never visit, and one line changed invalidates the whole cached file. Splitting means smaller critical payloads, better caching granularity, and less main-thread parse and execute time. The counterweight is that too many tiny chunks add overhead and can create request waterfalls — so route-level splitting plus a vendor chunk, not a chunk per component.

"Why not just preload everything important?"

Because priority is relative. Preload doesn't create bandwidth; it reorders a queue. If everything is high priority, nothing is — and worse, all those high-priority fetches now compete with the resource that actually determines your LCP, so overusing preload measurably makes things slower. I keep it to a short list: the LCP image and maybe one or two fonts. For things needed on the next navigation I use prefetch, which is deliberately idle-priority so it can't steal bandwidth from the current page.

"Isn't a 100 Lighthouse score the goal?"

No — it's a proxy, and it's a lab measurement on one simulated device with a cold cache and no extensions. Real users have different devices, networks, warm caches and ad blockers, and the vitals that Google actually uses come from field data at p75. Lighthouse is excellent for debugging and for catching regressions in CI, because it's reproducible. But I'd decide what to work on from field data, and verify the fix in the field afterwards. It's also possible to game the score without helping anyone, which is a good sign the number isn't the objective.

"Debounce or throttle for a search input? What about a scroll handler?"

Debounce the search input — I only want to fire a request once the user has stopped typing, otherwise I'm sending a request per keystroke and racing the responses. Throttle the scroll handler — I need updates during the scroll, just not sixty times a second, so capping it at one call every 100ms or so is right. The general test is whether I need feedback while the activity is happening (throttle) or only once it's over (debounce). For scroll specifically I'd also add { passive: true }, so the browser doesn't have to wait for my handler to find out whether I'm cancelling the scroll.

No first paint until the CSSOM is complete, because the cascade means no final style is known until all CSS is parsed. Blocks rendering, not parsing.
Sync scripts are parser-blocking
The parser stops, downloads, executes, resumes — because document.write could change the rest of the document.
async vs defer
Both download in parallel. async = execute on arrival, order not guaranteed. defer = execute after parsing, in document order. Modules are deferred by default.
Reflow vs repaint vs composite
Geometry → layout (most expensive). Appearance only → paint. transform/opacity on a layer → composite only (GPU, cheapest).
Layout thrashing
Interleaving DOM writes and geometry reads forces synchronous layout each iteration. Batch reads, then writes.
LCP ≤ 2.5s
Render time of the largest viewport element. LCP ≈ TTFB + render-blocking delay + resource load + element render delay.
INP ≤ 200ms
Full interaction-to-next-paint, all interactions. Replaced FID in March 2024 because FID ignored the actual handler work and everything after the first input.
CLS ≤ 0.1
Unexpected movement. Fix by reserving space: width/height, aspect-ratio, min-height on ad slots, font metric matching.
Diagnostic metrics
TTFB = server; FCP = first anything painted; TBT = lab proxy for INP. All three are Core-Web-Vital diagnostics, not vitals.
Lab vs field
Lighthouse = reproducible microscope for debugging. CrUX/RUM at p75 = what users actually felt. Decide from field, debug in lab.
Lazy loading
loading="lazy" below the fold, IntersectionObserver with rootMargin for custom cases. Never the LCP image — you delay its discovery.
Code splitting
Route-level first, then heavy components, plus a vendor chunk. Tree shaking needs ESM. Audit with a bundle analyser before guessing.
Images
AVIF/WebP with JPEG fallback, SVG for vector. srcset = the files you have; sizes = how wide it'll be displayed. <picture> for format fallback and art direction.
Unblocking render
Inline critical CSS, load the rest with media="print" + onload, defer scripts, self-host and preload fonts with font-display, delete unused CSS.
Debounce vs throttle
Debounce = run after it stops (search, autosave). Throttle = run at most every N ms during (scroll, progress). Add {passive:true} to scroll/touch listeners.
Caching
Content-hashed filenames + max-age=31536000, immutable; no-cache on HTML. no-cache = revalidate; no-store = never store. stale-while-revalidate = instant + self-healing.
Virtualization
Render the visible window plus overscan, spacer keeps the scrollbar honest. Costs: Ctrl+F, a11y, SEO, scroll restoration. Try content-visibility: auto first.
Resource hints
preload = need now (keep it to 1–3). prefetch = next navigation, idle. preconnect/dns-prefetch = warm a third-party origin. modulepreload = follow the ESM graph.
Main-thread work
Long task = >50ms. Yield with scheduler.yield(), gate on isInputPending(), background work via requestIdleCallback, DOM-free computation into a Web Worker.
The framing
Measure first, optimise second. Baseline → hypothesis → one change → re-measure → confirm in the field.

That's the whole map. And here's the thing worth carrying into the room with you: almost none of this is memorisation. Every single rule in the cheat sheet falls out of the pipeline diagram at the top. Why is CSS render-blocking? Look at the diagram — the render tree needs both trees. Why is lazy-loading the hero bad? The image can't be discovered until layout runs. Why animate transform? It enters the pipeline at the last step.

When an interviewer asks something you haven't specifically prepared for — and they will — go back to the pipeline and reason forward out loud. Watching a candidate derive the right answer is far more convincing than hearing them recite one. 🚀
