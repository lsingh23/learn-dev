useState, useEffect & the Hooks Rules

Almost every confusing React bug you will ever hit comes from one of two misunderstandings: thinking state is a variable, and thinking effects are lifecycle callbacks. Let's fix both, properly, from the ground up.

Here's a component. It has a counter, and a button that's supposed to add three.

Take a guess before you read on. You click the button once. What does the count become?

Reveal the answer

It becomes 1. Not 3. And it will keep going up by 1 every click, forever, no matter how many setCount calls you stack in there.

If that surprised you — good. If it didn't surprise you but you can't explain why in a sentence, that's the more common situation, and it's the one this guide is really for. Because the explanation isn't a quirk or a gotcha. It's the single mental model that React is built on, and once you have it, about eight other mysteries dissolve at once: why your state "doesn't update immediately", why your effect runs twice, why your setInterval is stuck logging zero, why your dependency array won't stop looping.

I'm going to admit something up front: this stuff is genuinely brain-bending. I've watched people with two years of React on their CV get quietly tripped up by the counter above. Being confused here is not a sign that you're bad at this. It's a sign that your model of React is the intuitive one — and the intuitive one is wrong.

So let's build the right one.

Part 1A render is a snapshot

Before we can talk about useState, we need to be precise about a word that gets thrown around loosely: render.

When people say "the component renders", they often picture something happening on screen — pixels changing, the browser painting. That's not what it means in React. Let's separate three things that happen in sequence, because keeping them apart is going to matter a lot later:

  1. Render. React calls your component function. Literally: Counter(). Your function runs top to bottom and returns some JSX describing what the UI should look like. Nothing has touched the screen yet.
  2. Commit. React compares what you returned with what's currently on screen, works out the minimum set of DOM operations, and applies them. The DOM is now updated.
  3. Paint. The browser takes the updated DOM and draws actual pixels. The user finally sees something.

So "a render" is just "one call to your component function". And here's the thing that unlocks everything:

The one idea to hold onto

Every render is a separate call to your function, and each call gets its own props, its own state values, its own local variables, and its own event handlers. They're frozen in place for that render. They never change.

Let me make that concrete, because it sounds abstract until you see it.

Your component is a function, so it has a fresh scope every time

Forget React for one second. Here's plain JavaScript:

Nobody finds this confusing. Each call to greet creates a brand new scope, with its own name and its own message. The first call's message doesn't magically become "Hello, Grace" when we call it again. That call is over. Its variables are what they were.

React components are exactly the same. They're just functions React calls. So when Counter renders with a count of 0, the count variable inside that particular call is the number 0. Not "a reference to the count". Not "a live view of the state". The number 0. A constant, for the lifetime of that render.

When state changes, React doesn't reach into the old call and update the variable. It calls your function again, from scratch, and this time useState hands back 1. That's a completely separate scope with a completely separate count constant.

The analogy: frames of a film

A render is a photograph. When you take a photo of a room, the photo doesn't update when someone walks in. It's fixed. To show the new arrangement, you take another photo.

Your UI is a film strip of these photographs. React's job, when state changes, is to shoot a new frame. The old frames still exist in memory — event handlers from an old render can still be sitting in a timeout somewhere, holding onto that old frame's values, which is exactly how the stale-closure bugs we'll see later happen.

Where this analogy breaks down: photographs are passive, and your renders aren't quite — they contain live functions that can be called later. So a better image might be a flipbook where each page also has a little machine glued to it, and the machine only knows about the numbers printed on its own page. Clunkier, but more accurate. Hold onto that image; we'll come back to it.

Back to the counter

Now the original puzzle should almost solve itself. You click the button. React runs the addThree that belongs to render #1 — the one where count is the number 0.

Three instructions, all saying the same thing: make it 1. React processes them in order, the last one wins, and the next render has a count of 1. There's no bug in React here. Your code asked for 1, three times.

This also explains a related thing people hit constantly:

People describe this as "state updates are asynchronous". That's sort of true but it's the wrong mental model, because it makes you think if you just waited long enough — setTimeout, await, whatever — the variable would eventually change. It won't. count in this scope is a const holding the number 0. It is 0 now, it will be 0 in ten seconds, it will be 0 forever, because this render is a photograph and photographs don't update.

The state does update. It just updates for the next render, which will get its own fresh count.

A common misconception

"setCount is async, so I need to await it / put my code in a setTimeout to see the new value."

Neither works, and both make the code worse. There is nothing to await — setState returns undefined. And a setTimeout inside this handler still closes over this render's count, so it will happily log 0 a second later too. If you need to do something with the new value, compute it into a variable first (const next = count + 1) and use next. If you need to react to the value changing, that's a different tool, and we'll get there.

Batching: why you only get one re-render

There's a second thing happening in that click handler, and it's a good thing. React doesn't re-render after each setCount. If it did, clicking that button would trigger three full renders, three commits, possibly three paints — for a UI that only ends up in one final state. Wasteful, and visually janky.

Instead React batches. It collects every state update triggered during the handler, waits until your handler has finished running, then does a single re-render with the final result.

The analogy I like: a waiter taking an order. You say "I'll have the soup." Then "actually, the salad." Then "no, the soup." The waiter doesn't sprint to the kitchen after each sentence. They wait until you've stopped talking, then walk over once with your final order. That's batching — and it's why the intermediate values never reach the screen.

The updater form: setCount(c => c + 1)

Okay. So if setCount(count + 1) three times gives us 1, how do we actually add three?

We need a way to say something the snapshot can't say: not "set it to 1", but "whatever it ends up being, add one to that". React gives us exactly that. Instead of passing a value, pass a function:

That function is called an updater function. React puts it in a queue, and when it's time to render, it walks the queue in order, feeding each function the result of the previous one:

QueuedValue going inValue coming out
c => c + 10 (current state)1
c => c + 112
c => c + 123 ← final

Notice what changed conceptually. setCount(count + 1) is a value — computed now, from a stale snapshot. setCount(c => c + 1) is a recipe — evaluated later, against the freshest value React has. That distinction is the whole ballgame.

Wait — should I always use the updater form?

Not always, but here's a clean rule: if the new state is computed from the old state, use the updater form. setCount(c => c + 1), setItems(prev => [...prev, newItem]), setOpen(o => !o). If the new state has nothing to do with the old — setName(input.value), setUser(data) — just pass the value; the updater form would be noise.

The updater form also saves you inside async code and effects, where the captured snapshot may be very old. We'll see that in the stale closures section, where it's not a style preference but the actual fix.

Under the hood

Each piece of state on a fiber (React's internal object representing a component instance) has a queue of pending updates. Calling the setter pushes onto that queue and schedules work. During the next render, React starts from the last committed value and applies each queued update: if it's a function it calls it, if it's a plain value it just replaces. That's genuinely all "batching" is — a queue that gets drained once.

One consequence worth knowing: React runs updater functions during render, so they must be pure. No fetching, no mutating, no console.log-and-hope. In StrictMode React will call them twice on purpose to shake out impurity.

Bailing out: same value, no render

One small behaviour that occasionally confuses people. If you set state to the value it already has, React will usually skip the re-render:

React compares with Object.is, which is basically === with saner handling of NaN and -0. This is why mutating state is so catastrophic — which brings us neatly to the next thing.

Never mutate state

Here's a bug that looks completely reasonable:

The item genuinely does get added to the array. But setCart(cart) hands React the exact same array object it already had. React does its Object.is check, sees the same reference, shrugs, and bails out. No re-render. Your data changed and your screen didn't, which is the most demoralising class of bug there is.

Same for objects. Treat everything in state as if it were frozen:

The useful mental reframe: state is not a box you edit, it's a value you replace. Same as strings. You'd never expect "hello".toUpperCase() to change "hello" — it hands you a new string. Treat your arrays and objects with the same respect and a whole class of bugs evaporates.

Wait — isn't copying the whole array slow?

Almost never, at UI scale. A spread of a few hundred items is a fraction of a millisecond, and it's a shallow copy — the item objects themselves aren't duplicated, just the references to them. If you genuinely have huge deeply-nested state that's hot in a profiler, that's when you reach for Immer (which lets you write mutating-looking code and produces immutable results underneath). Reaching for it before you've measured is premature.

Lazy initial state

One more useState subtlety, and it's a real performance footgun because the code looks fine.

Remember: a render is a call to your function. Every line runs, every time. So parseHugeDocument() is called on every render — every keystroke, every state change, forever. React politely ignores the result after the first render (initial state is only used once) but it doesn't stop your function from running. You're paying full price for a value that gets thrown away.

The fix is to pass the function itself instead of calling it:

Now you're handing React a recipe rather than a result. React calls it exactly once, on the first render, and never again. Same pattern shows up with useState(() => JSON.parse(localStorage.getItem("draft"))) — reading localStorage on every render would be a real, measurable cost.

Wait — do I need this for useState(0) or useState([])?

No. Those are already values; there's nothing to compute. Lazy init is only worth it when producing the initial value costs something: parsing, reading storage, looping over data, generating an id. And notice the trap in the other direction — useState(() => 0) works but is pointless noise, while useState(someFunction) when you actually wanted to store a function will call it instead of storing it. To store a function in state you'd need useState(() => myFn).

The interview layer: useState

How this gets asked

"Why doesn't my state update immediately after I call setState?" · "If I call setCount(count + 1) three times in a row, what happens?" · "What's the difference between passing a value and passing a function to a setter?" · "Why do we never mutate state directly?" · "What's lazy initial state?"

These start as recall and turn into depth fast. The interviewer is listening for whether you say the word snapshot (or something equivalent), because that's the difference between someone who memorised a rule and someone who understands the model.

Say something like this

"State isn't a variable that mutates — each render is a snapshot, so count inside a given render is a constant for that render. When I call setCount, I'm not changing that constant, I'm asking React to re-render with a new value, and React batches those requests and re-renders once at the end of the event. So setCount(count + 1) three times is really 'set it to 1' three times. If the new state depends on the old, I use the updater form, setCount(c => c + 1), because React applies those in order against the latest value rather than against my stale snapshot."

Why it lands: you've explained the behaviour and the mechanism and given the fix, in the right order. Saying "React batches" alone is the memorised answer; connecting it to the snapshot is the understood one.

Traps

Trap: saying "setState is asynchronous". It gets you halfway and then invites the follow-up "so can I await it?" — and if you hesitate there, you've shown the model is shaky. Say "React re-renders with the new value; the variable in the current render never changes" instead.

Trap: saying you mutate state "because React does a shallow comparison and it's a performance thing". Closer, but incomplete — mention that the bail-out means the render never happens at all, and that concurrent features and things like StrictMode assume purity.

Follow-up: why not just make React deep-compare state so mutation works?

Because deep comparison is O(size of your data) on every update, for every component, and you'd pay it constantly. Reference comparison is a single pointer check. Immutability buys React (and memo, and useMemo, and every state library) an O(1) "did this change?" check. It also makes time-travel, undo stacks, and concurrent rendering possible, because old values remain valid rather than being clobbered in place.

Follow-up: is there ever a time you'd read state right after setting it?

You can't — but you rarely need to. Compute the next value into a local variable and use that: const next = count + 1; setCount(next); analytics.track(next);. If you need the value React actually settled on after a queue of updaters, you read it on the next render. And if you truly need the DOM to be updated synchronously before continuing (measuring, say), that's flushSync — a last resort we'll cover later.

Follow-up: what happens if you call a setter during render, not in a handler?

An unconditional setState during render is an infinite loop — render triggers state change triggers render. React will actually throw "Too many re-renders" to stop you. There is one legitimate pattern: a conditional set during render to adjust state when a prop changes, which React handles specially by re-running the render before committing. But it's niche; the usual answer is that you derive the value instead, which is the next section's whole theme.

Part 2useEffect is for synchronisation, not lifecycle

If you learned React from class components, or from most tutorials, you've probably absorbed a translation table like this:

Class lifecycle"Equivalent" hook
componentDidMountuseEffect(fn, [])
componentDidUpdateuseEffect(fn, [deps])
componentWillUnmountthe returned cleanup function

This table is a trap. It's not exactly wrong — the timings roughly line up — but it plants the wrong question in your head. It makes you ask "when do I want this code to run?", and that question leads directly to every dependency-array bug in existence.

The question React wants you to ask is completely different:

The reframe

An effect exists to keep something outside of React in sync with your React state. Not "run this at time T" — but "whenever this state says X, the outside world should be in configuration X."

"Something outside React" means: a network connection, a browser API, a setInterval, a subscription to a store, a third-party chart library that owns a DOM node, the document title, an event listener on window. React calls these external systems. They don't know your state exists, so somebody has to walk over and tell them. That somebody is an effect.

The analogy: a thermostat, not an alarm clock

An alarm clock fires at a time. You set it for 7am; at 7am it goes off. That's the lifecycle model, and it's how most people first read useEffect.

A thermostat doesn't work like that. You set it to 20°C, and its job is to keep the room at 20°C, continuously. It doesn't care what time it is. If you change the target to 22, it does whatever's necessary to make the room match. If you leave the house and turn the system off, it stops heating — that's cleanup.

Effects are thermostats. The dependency array is the target setting. When the target changes, the effect re-synchronises: it undoes what it did for the old target (cleanup), then does what's needed for the new one.

Where the analogy breaks down: a thermostat runs continuously, whereas your effect function runs at discrete moments after render. But the intent — "keep this thing matching that thing" — is exactly right, and it's the intent that fixes your dependency arrays.

A concrete effect

Here's the canonical example, a chat room that connects to a server:

Read that with the thermostat model, out loud: "While this component is on screen, there should be a live connection to roomId. If roomId changes, the connection should change to match."

Nothing in that sentence mentions mounting, updating, or unmounting. That's the point. The lifecycle stuff falls out automatically:

  • Component appears → nothing was synced, so connect.
  • roomId goes from "general" to "random" → we're synced to the wrong thing, so disconnect from general, connect to random.
  • Component disappears → nothing should be synced any more, so disconnect.

Cleanup: when it runs and why it exists

The function you return from an effect is the cleanup, and this is the bit people under-use. Here's the precise rule:

Cleanup timing

The cleanup from the previous effect run happens before the next effect run, and also when the component unmounts. Every effect run is paired with exactly one cleanup run.

That "before the next run" half is the part people forget, and forgetting it produces leaks. Without the disconnect above, switching rooms five times leaves you with five open connections, all pushing messages into your app. With the cleanup, you always have exactly one.

A checklist for whether you need cleanup: did the effect start something, subscribe to something, or claim something? Then it must stop, unsubscribe, or release it.

The dependency array: "re-synchronise when these change"

Now that the thermostat model is in place, let's be precise about the second argument. Most people read it as "run the effect when these values change". The more accurate reading is:

Read your dep array like this

"These are all the values from the render that my effect uses. If any of them differ from last time, my effect is out of sync with reality — clean up and re-synchronise."

Why does the distinction matter if the observable behaviour is similar? Because it changes what you do when the array misbehaves. Under the "run when" reading, the dependency array is a trigger list you control — so when your effect runs too often, the natural move is to remove an entry. Under the "re-synchronise" reading, the array isn't yours to choose. It's a derived fact: it's exactly the set of reactive values your effect body reads. Removing one doesn't make the effect need it less; it just makes you lie to React.

That reframe alone prevents the single most common React bug, and we'll take it apart properly in Part 4.

No array, empty array, or some deps?

This is a guaranteed interview question, so let's nail all three.

Read through the synchronisation lens:

  • No array at all. You've told React "I can't promise anything about what I depend on, so assume everything." It re-syncs after every render. Usually a mistake, and often an infinite loop: if the effect sets state, that render triggers the effect, which sets state, forever.
  • []. You've told React "my effect uses nothing from the render, so it never needs to re-sync." Setup once, cleanup on unmount. Legitimate for things genuinely independent of your data — a global listener, an analytics init. Illegitimate as a way of saying "only on mount please" when the effect actually does read props or state, because then you've just lied and earned yourself a stale closure.
  • [a, b]. The normal case. Re-sync whenever a or b changes, compared with Object.is — the same reference check as state. That reference detail is where the infinite loops come from.
A common misconception

"[] means run on mount."

It means "this effect never needs to re-synchronise". The on-mount-only behaviour is a consequence, not the definition. The reason to care: if you write [] because you want mount-only, but your effect reads userId, then when userId changes your effect keeps working with the original value and no one tells you. React's lint rule flags this — and if you find yourself disabling that rule, treat it as a design smell, not a formality.

Why does my effect run twice? (StrictMode)

You write a perfectly good effect, open the dev server, and your console log appears twice. Or your fetch fires twice. Or your chat connects, disconnects, and connects again.

Nothing is broken. If your app is wrapped in <React.StrictMode> (which create-react-app, Vite's React template, and Next.js all do by default), then in development only, React deliberately mounts each component, unmounts it, and mounts it again. So every effect runs setup → cleanup → setup.

Why on earth would React do that to you? Because it's a test you can't opt out of forgetting. React is checking that your effect is resilient to being run twice — that setup and cleanup are symmetrical.

Think of it like a fire drill. Nobody enjoys the alarm, but the whole point is to discover now, in a safe setting, that a fire door is jammed — rather than during an actual fire. StrictMode is React pulling the alarm on your effects in dev, so that you find your missing cleanup on your laptop and not in production.

And this isn't hypothetical paranoia. In React 18+ with features like Offscreen/Activity components and Fast Refresh, a component genuinely can be unmounted and remounted with its state preserved. Effects that only work the first time are a real bug class, not a theoretical one.

Notice that the fix for "my effect runs twice" is never "make it run once". It's make running twice harmless. That reframe is what interviewers are listening for.

Wait — so should I just turn StrictMode off?

Please don't. It only double-invokes in development; production runs each effect once, so you're not shipping double fetches either way. Turning it off doesn't fix a bug, it hides one — and the class of bug it hides (unsymmetrical setup/cleanup) is exactly the class that produces memory leaks and zombie subscriptions. If a double fetch in dev is genuinely painful, the honest fix is a data library with request deduplication, which you want anyway.

Under the hood

StrictMode's double-invocation isn't limited to effects. In dev it also calls your component function body twice, and calls useState updater functions, useMemo factories and reducers twice. All of these are supposed to be pure, so calling them twice should produce identical results. If your render function pushes into an array declared outside the component, or mutates a prop, or generates a random id and stores it, StrictMode will make that visible as doubled or inconsistent output. That's not React being flaky — it's React handing you a purity linter that runs at runtime.

Part 3When you do not need an effect

Here's a claim I want to be blunt about, because it's the highest-leverage thing in this whole guide: most effects in most codebases shouldn't exist.

Effects are an escape hatch — a door out of React into the messy outside world. Every time you use one you're adding a render pass, a bit of latency, and a dependency array to get wrong. If there's no external system involved, there's probably no effect needed. Let's go through the three big cases.

Case 1: derived state

Walk through what actually happens when items changes. React renders with the new items and the old total. It commits that to the DOM — so for one frame, the user can see the wrong total. Then the effect runs, sets state, and React renders a second time with the correct total. Two renders, a flash of wrong data, an extra piece of state that can fall out of sync, and a dependency array to maintain.

And for what? total isn't really state. It's a fact about state. It can always be computed from items.

One render. Impossible to desync. No dependency array. The test to apply: can I compute this from existing props and state? Then it isn't state.

Wait — isn't recalculating on every render wasteful?

Usually no. Summing a hundred numbers is nothing next to the DOM work React is already doing. If you have profiled it and the calculation is genuinely expensive — sorting ten thousand rows, say — wrap it in useMemo(() => ..., [items]), which caches the result between renders. But useMemo is a performance optimisation, not a correctness tool, and it's still one render rather than the effect's two.

Case 2: responding to an event

This one's subtler, and it's the one I see most in real code.

Ask the diagnostic question: why should this code run? The answer isn't "because submitted is true" — it's "because the user clicked Submit". The state is just a courier carrying the message from the click to the effect. Cut out the middleman:

Why does the first version actually break, not just look worse? Because effects fire on any reason the value became true. StrictMode remounts → the toast fires again. The component gets remounted by a route change while submitted is still true → toast again. You've made a one-off action into a standing rule.

The diagnostic that sorts every case

Ask: "is this code running because something happened, or because something is displayed?"

Happened (a click, a submit, a keypress) → event handler. Is displayed (this chat room is on screen, so a connection should exist) → effect.

Case 3: resetting state when a prop changes

Same problem as before: there's a render where the new user is shown with the old user's draft text in the box, before the effect wipes it. React has a much cleaner tool for "this is conceptually a different thing now" — the key prop.

When a key changes, React treats it as a different component instance: it unmounts the old one, throws away all its state, and mounts a fresh one. No intermediate bad frame, no effect, no partial resets where you forget one of the five state variables.

So when is an effect right?

When there's a real external system on the other side of the wire:

  • Opening/closing a WebSocket or subscription
  • Setting up and tearing down timers
  • Adding window / document event listeners
  • Driving a non-React library that owns a DOM node (a map, a chart, a video player)
  • Syncing to document.title, localStorage, the URL
  • Fetching data — if you're not using a library (see Part 11)
In an interview

"When do you not need useEffect?" is a seniority filter. A junior answers by listing lifecycle equivalences. A senior answers: "if there's no external system, I probably don't need one — derived values get computed during render, event-response logic goes in the handler, and resetting state on a prop change is usually a key." Being able to say why the effect version is worse — the extra render and the visible intermediate frame — is what turns a decent answer into a strong one.

Part 4The dependency array and its three failure modes

Nearly every dependency-array problem is one of three shapes. Once you can name which one you're looking at, the fix is mechanical.

Failure mode 1: the missing dependency (stale values)

This searches for whatever query was on the first render, and then never again, no matter how much the user types. The effect body reads query, so query belongs in the array. It's not a matter of taste — the array is supposed to be the complete list of reactive values the body uses.

The fix is to be honest: }, [query]);. That's it. Install eslint-plugin-react-hooks and it will tell you every time; it's one of the very few lint rules I'd argue is nearly always right.

Failure mode 2: the recreated object or function (infinite loop)

This is the one that hurts.

Trace it. Render 1 creates an object; the effect runs; it sets state; state change causes render 2; render 2 creates a brand new object with identical contents; React compares with Object.is, and two separate objects with the same contents are not the same reference, so it counts as changed; the effect runs again; sets state again; render 3... and your fan spins up.

The same thing happens with functions, arrays, and inline callbacks passed as props — anything created fresh during render. {} !== {}, [] !== [], (() => {}) !== (() => {}). Primitives are fine: "abc" === "abc" and 20 === 20, always.

Fix A — move it inside the effect (best when you can)

If the object is only used by the effect, it belongs inside the effect. Now the dependency list contains only userId, a string, compared by value. The loop is gone. This is the fix you should reach for first, and it solves the majority of real cases.

Fix B — stabilise it at the source

Sometimes the object or function is a prop, or is used elsewhere in the component too. Then you stabilise its identity where it's created, with useMemo (for values) or useCallback (for functions):

These two are the same tool wearing different hats: useMemo caches a value, useCallback caches a function. (useCallback(fn, deps) is literally useMemo(() => fn, deps).) Both give you a stable reference that only changes when the deps change — which is exactly what a dependency array needs.

Fix C — useReducer, so you don't depend on state at all

If the effect only needs state in order to compute the next state, a reducer removes the dependency entirely, because dispatch is guaranteed stable across renders:

Fix D — a ref, for values you want to read but not react to

Occasionally you genuinely have a value the effect should read but should not re-synchronise on — an onMessage callback that changes every render, say, where re-subscribing the socket each time would be absurd. Stash it in a ref:

Refs aren't reactive — changing .current doesn't trigger anything — which is precisely why they're allowed to be left out of dependency arrays. Use this sparingly and deliberately; it's a sharp tool. (This pattern is what React's experimental useEffectEvent is designed to replace one day.)

Failure mode 3: "I removed the dep to stop the loop"

Which brings us to the antipattern. You hit the infinite loop from failure mode 2. You notice that deleting options from the array makes the loop stop. Problem solved, right?

What you've actually done is trade a loud bug for a quiet one. The loop is gone because the effect now runs once — with the first render's options — and then ignores every subsequent change forever. Your dashboard silently shows the wrong user's widgets. Loops announce themselves in ten seconds; stale data gets discovered by a customer in three weeks.

The rule

The dependency array is not a control panel. It's a declaration of what your effect reads. If the effect runs too often, the answer is never to remove a dependency — it's to change what the effect depends on: move the value inside, memoise it at the source, use a reducer, or move it to a ref. Fix the cause, not the report.

Trap

An // eslint-disable-next-line react-hooks/exhaustive-deps in a code sample is a red flag in an interview, and mentioning that unprompted scores points. If you're ever asked to review code containing one, say what you'd do instead: "I'd rather restructure so the honest dependency list is small, than suppress the rule."

Part 5Stale closures

This is the one. If you understand stale closures, you can debug essentially any weird React behaviour, and you will be noticeably ahead of most candidates. It's also genuinely hard, so we're going to build it up slowly — starting with plain JavaScript, no React at all.

First: what a closure actually is

When you create a function in JavaScript, it doesn't just remember its own code. It also keeps a live link to the scope it was created in. That link is the closure.

makeGreeter finished running ages ago, but greetAda still has access to its name. Two calls to makeGreeter produced two separate scopes, and each returned function is permanently attached to its own.

The analogy: a function is a balloon, and the scope it was created in is the little bag of sand tied to its string. The balloon can drift anywhere in your program — into a timeout, into an event listener, into a promise callback three seconds from now — and it carries that same bag with it. It cannot swap the bag for a newer one.

Now: a React component is `makeGreeter`

Here's the connection, and it's the whole thing. Every render is a fresh call to your component function, creating a fresh scope. Every function you define inside — event handlers, effect bodies, timer callbacks — closes over that render's scope.

So a function created during render #1 is tied to render #1's bag of sand. It will see count === 0 for the rest of its life, no matter how many renders happen afterwards. That's a stale closure: a function that outlives the render it was born in, still reading that render's values.

Usually this is invisible, because React creates fresh handlers each render and the DOM gets the fresh ones. The problem appears when a function sticks around across renders. Which is exactly what an effect with [] deps does.

The classic broken counter

Take a guess. It's ticking once a second and calling setCount(count + 1) each time.

Reveal the answer

It logs 0. Then 0. Then 0. Forever. And the heading on screen goes to 1 and then stops dead.

Let's walk it, slowly, because every piece of this is now something we know.

  1. Render #1. count is 0. React creates the effect function; the arrow function passed to setInterval closes over render #1's scope, where count is the number 0.
  2. The effect runs. The interval is registered. It is now living in the browser, holding that render-#1 callback.
  3. One second later. The callback fires. It logs 0 — correct, that's what count is in its bag of sand. Then it calls setCount(0 + 1), so state becomes 1.
  4. Render #2. A new scope, where count is 1. React looks at the effect's deps — [] — sees nothing changed, and therefore does not re-run the effect. So the interval isn't cleared, isn't recreated, and keeps holding the render-#1 callback.
  5. Two seconds. The same old callback fires. It logs 0. It calls setCount(0 + 1) — which is setCount(1). State is already 1, so React bails out. No re-render. Nothing visibly happens.
  6. Repeat forever.

Sit with that for a second. Nothing here is mysterious once you accept the snapshot model — it's just a closure doing exactly what closures always do. The illusion that state is a "live" variable is what makes it feel supernatural.

Three fixes, and when to use each

Fix 1 — the updater form (usually the right answer)

Look at what changed: the callback no longer reads count. It sends React a recipe, and React evaluates it against the current value. Since the effect body doesn't use any reactive value, [] is now an honest dependency array, not a lie. The interval is created once and keeps working forever.

Use this whenever your callback only needs the old state to compute the new state. It's clean, it's cheap, and it's the answer to give first in an interview.

Fix 2 — declare the dependency and let it re-sync

Now every time count changes, React tears down the old interval and sets up a new one, closing over the new value. Correct — and notice it's only correct because the cleanup exists; without it you'd accumulate an interval per second.

The trade-off is that the timer restarts on every change, so your "one second" resets each tick. For a counter, harmless. For anything where the timer's phase matters (a debounce, a genuine clock), it's wrong, which is why fix 1 is usually preferred here.

Fix 3 — a ref, when you must read the latest value without re-syncing

Why does this dodge the problem? Because useRef returns the same object on every render. The closure captures that object, and the object's .current property is mutable — so while the box is frozen in the closure, what's inside the box isn't. It's a mailbox nailed to the wall: the closure knows where the mailbox is, and anyone can drop new mail in.

Use this when you need "the latest value" but re-synchronising would be wrong or expensive — logging, analytics, a socket handler, an animation loop. Don't reach for it first; it's an escape hatch, and it opts you out of React's tracking.

Wait — why don't my onClick handlers go stale?

Great question, and the answer confirms the model rather than contradicting it. On every render, React creates a new handler function closed over that render's values, and when it commits, it attaches the new one to the DOM node. So the handler on screen is always from the most recent render — its closure is fresh because it was just made. Staleness needs a function that survives across renders, and normal JSX handlers don't. That's why intervals, listeners registered in a [] effect, and long-lived promise callbacks are the usual suspects.

How this gets asked

"What's a stale closure?" · "Here's a component with a setInterval — what's wrong with it?" (live coding favourite) · "Why is my state always the initial value inside this callback?" · "How would you fix it without adding count to the deps?"

That last one is the depth probe: they want to hear the updater form or the ref pattern, not just "add the dependency".

Say something like this

"A stale closure is when a function outlives the render it was created in and keeps reading that render's values. Each render is a new function scope, so a callback defined in render one captures render one's count permanently. It bites you with things that persist across renders — intervals, event listeners registered with empty deps, or code after an await. Three fixes: use the updater form so the callback doesn't need to read state at all; or declare the real dependency so the effect tears down and re-subscribes with fresh values; or, if re-subscribing would be wasteful, keep the value in a ref, since a ref object is stable across renders and its .current is always current."

Why it lands: you named the mechanism (closures + snapshots), the symptom, and gave three fixes with the trade-off between them. That's a conversation, not a definition.
