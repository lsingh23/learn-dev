The empty <div>

Here's something you've maybe done without thinking much about it. You build a React app, deploy it, load it in the browser, and it works great. Then, out of curiosity, you right-click and hit View Page Source.

And this is the entire page:

index.html — the whole thing
<!DOCTYPE html>
<html>
  <head><title>My Store</title></head>
  <body>
    <div id="root"></div>   <!-- 👈 that's it. that's your app. -->
    <script src="/bundle.js"></script>
  </body>
</html>

Wait, what? Where's the product list? Where's the nav bar, the heading, the price, the "Add to cart" button? You can see them on the screen. But the document the server actually sent contains none of them.

That single observation — the gap between what the server sent and what you see — is the seed of this entire topic. Every rendering strategy in React is a different answer to one question: who fills in that div, and when?

We're going to build up from absolute basics. I'll assume you know what HTML, JavaScript and React components are, and nothing else. By the end you'll understand CSR, SSR, SSG, ISR, hydration, and React Server Components well enough to argue about them at a whiteboard.

Fair warning up front: this is genuinely confusing material. Not "you're not smart enough" confusing — "the industry gave four different things overlapping names" confusing. I've been writing React for years and I still occasionally have to stop and think about which piece runs where. If you feel lost at some point, that's the material, not you. Keep going.

What a browser actually does (the foundation)

Before we can talk about rendering strategies, we need to be crystal clear on the boring mechanics. Skipping this is why most people find SSR confusing.

When you type mystore.com and press Enter, roughly this happens:

  1. Your browser sends an HTTP request to a server — a computer somewhere else that's listening for requests.
  2. The server sends back a response. For a page load, that response body is a string of HTML text. Literally just characters.
  3. The browser reads that text and builds the DOM — an in-memory tree of objects representing the elements. <h1>Hello</h1> becomes an object with a tag name, attributes, and text.
  4. The browser paints that tree to the screen. Now the user sees pixels.
  5. If the HTML references CSS or JavaScript files, the browser fetches those too. When a <script> arrives, the browser runs it, and that script can change the DOM.

Two things to lock in, because everything else depends on them:

First: the browser can only paint what's in the DOM. If the HTML the server sent is an empty div, the first paint is a blank white screen. There's nothing else to draw. The browser is not being lazy; there is genuinely nothing there.

Second: "the server" is just a computer running a program. It doesn't have to send a file from disk. It can run code and build the HTML string on the fly. This is not a new idea — PHP and Rails did it for twenty years. It's going to become important in about five minutes.

Wait — what does "render" even mean here?

This word is doing double duty and it trips everyone up. When a browser person says "render," they mean paint pixels on screen. When a React person says "render," they mean call your component functions to produce a description of the UI. React's render doesn't touch the screen at all — it produces a JavaScript object tree, and then something else turns that into DOM.

Throughout this guide, "render" means the React sense: run the components. I'll say "paint" when I mean pixels.

What React actually produces

One more foundation piece. When React "renders" your component, what comes out?

What JSX compiles to
// You write:
function Greeting() {
  return <h1 className="title">Hello</h1>;
}

// The build tool turns that into roughly:
function Greeting() {
  return { type: 'h1', props: { className: 'title', children: 'Hello' } };
}
// → a plain JavaScript object. Not HTML. Not DOM. Just an object.

React components return plain JavaScript objects describing what the UI should look like. That object tree is the famous "virtual DOM." Something downstream then takes those objects and does something real with them.

And here's the key insight that unlocks server rendering: there is more than one thing you can do with that object tree.

  • In the browser, react-dom turns it into real DOM nodes and puts them on the page.
  • On a server, react-dom/server turns it into an HTML string — no DOM required, no browser required.

That second bullet is the entire basis of SSR. Same components, same render, different output format. Hold onto that.

Client-Side Rendering, and its waterfall

Client-Side Rendering (CSR) is the empty-div approach from the top of the page. The server sends a nearly-empty HTML shell plus a script tag. Everything you see is built by JavaScript in the browser, after the fact. "Client" here just means the user's browser — the thing on the other end of the connection from the server.

This is what you get from Create React App, or a default Vite React app. It's also what people mean by "SPA" (Single-Page Application).

Let's follow a real page — a product detail page — through a CSR load, second by second. Say the user is on a mid-range phone on a decent-but-not-amazing connection.

Look at that diagram and let it sink in for a second. For the first 1.8 seconds, the user is staring at a blank white rectangle. Not a slow page — an empty one. Then they get a spinner. Then, finally, at 2.5 seconds, they see a product.

Now here's the part that really matters, and it's the thing interviewers are probing when they ask about CSR. Look at why it took that long. Each step could not begin until the previous one finished:

This is called a network waterfall: a chain of requests where each one can only start after the previous one comes back. The browser can't fetch the product data early, because it doesn't know it needs product data until it has downloaded and executed your JavaScript and gotten as far as the useEffect.

Here's the component that causes it:

❌ The classic CSR data-fetching pattern
function ProductPage({ id }) {
  const [product, setProduct] = useState(null);

  useEffect(() => {
    fetch(`/api/products/${id}`)   // 👈 can't run until React is booted
      .then(res => res.json())
      .then(setProduct);
  }, [id]);

  if (!product) return <Spinner />;   // 👈 the user lives here for a while
  return <h1>{product.name} — ${product.price}</h1>;
}

Three separate costs are stacked in that diagram, and it's worth naming them separately because different solutions attack different ones:

  1. Blank screen cost. Nothing is visible until JS runs. Bad for perceived speed, bad for users on slow devices, and bad for search engines and link previews that may not run your JavaScript at all.
  2. Bundle cost. You shipped React itself, your router, your date library, your component code — all before anything appeared.
  3. Waterfall cost. The data request starts dead last, when it's arguably the most important thing on the page.

Under the hood: why is CSR so popular then?

Because it's operationally lovely. The output is a folder of static files. You can drop it on any CDN for pennies, there's no server process to keep alive, no server to crash at 3am, and local development is one command. For an internal dashboard behind a login — where SEO is irrelevant and the user is on a laptop on office wifi — CSR is often exactly the right call. Don't let anyone tell you SPAs are obsolete.

Server-Side Rendering & hydration

So how do we solve this? Let's go back to that foundational fact I asked you to hold onto: the server is just a computer running a program, and React can render to an HTML string instead of to DOM.

Put those together, and you get Server-Side Rendering (SSR). When a request comes in, the server runs your React components right there, produces a complete HTML string with real content in it, and sends that as the response.

Roughly what an SSR server does per request
app.get('/products/:id', async (req, res) => {
  const product = await db.products.find(req.params.id);  // fast: same datacenter

  const html = renderToString(<ProductPage product={product} />);
  //     👆 a real string: "<h1>Wool Socks — $12</h1>"

  res.send(`<div id="root">${html}</div><script src="/bundle.js"></script>`);
});

Now view-source shows the actual product. The browser receives HTML with content in it, builds the DOM, and paints something meaningful almost immediately. No blank screen. No waiting for JavaScript. Google's crawler sees your text. Slack's link preview works.

But hm — hold on. If the HTML is just a static string, how does the "Add to cart" button work? Strings don't have onClick handlers. The server produced markup, and markup is inert.

Hydration

This is where the single most important word in this guide shows up.

The JavaScript bundle still gets downloaded, and React still boots up in the browser. But instead of building the DOM from scratch, React does something different: it renders your components in memory, walks the HTML that's already on the page, and — assuming they match — adopts those existing DOM nodes as its own, attaching event listeners and wiring up state as it goes.

This process is called hydration.

The analogy

Dan Abramov (a longtime member of the React team) gave the metaphor the name comes from: the server-rendered HTML is dry — it has shape but no life. Hydration is watering the dry HTML with the water of interactivity. The markup was already there, in the right shape; what React adds is the ability to respond.

I find instant noodles the most useful version of this. The server ships you a brick of dried noodles: it already looks like noodles, it's already noodle-shaped, you can hold it. But you can't eat it. Pouring hot water over it doesn't change its shape — it makes it work.

Where the analogy breaks: real hydration isn't gentle. React genuinely re-renders your whole component tree in memory to figure out what handlers go where. It's a full render pass, just one that reuses the DOM nodes at the end instead of creating them. So it's less "sprinkle water on it" and more "rebuild the whole thing in your head, then confirm it matches the thing on the counter." Keep that in mind — it explains why hydration is expensive.

Here's the new timeline. Same app, same network, but server-rendered:

Compare the two diagrams side by side in your head. The win is enormous and it's specifically about content: 2.5s → 0.7s. The user is reading the product description while the JavaScript is still downloading.

But notice something honest in that second diagram: interactivity got slightly worse, 1.8s → 2.2s. We added hydration work that CSR didn't have to do. In exchange, we removed the blank screen and the data waterfall. For almost every public-facing site that's a fantastic trade — but it is a trade, and saying so out loud in an interview is a strong signal.

The uncanny valley

Between 0.7s and 2.2s, the page looks completely finished but isn't. If the user taps a button in that window, nothing happens. This is the classic SSR complaint — it can feel worse than a spinner, because a spinner at least tells the truth. Modern React softens this with streaming and selective hydration (hydrate the part the user clicked first), but the fundamental gap is real.

What SSR does not fix

SSR gets talked about like a performance cheat code, and it isn't. Let's be precise about what it leaves on the table, because this is exactly where good interview conversations go.

1. You still ship the same JavaScript

This is the big one. SSR renders your components on the server and sends every one of those components to the browser so they can be hydrated. Your bundle is not one byte smaller. If you imported a 60KB markdown parser to render a product description, that parser runs on the server and gets downloaded by every visitor — even though, after the initial render, it does nothing at all.

Think about it: React needs the component code in the browser to hydrate, and it needs it whether or not the component will ever re-render. That feels wasteful, and it is. File that away — it's the exact hole React Server Components were built to fill.

2. Hydration is a real cost

Hydration means running your entire component tree, on the user's device, on top of work the server already did. On a fast laptop it's a blink. On a three-year-old Android phone, hydrating a complex page can block the main thread for hundreds of milliseconds — during which taps, scroll and typing are all frozen.

There's a slightly uncomfortable framing worth internalising: with SSR you render everything twice. Once on the server to make HTML, once in the browser to make it interactive.

3. If you fetch on the client, the waterfall is back

SSR only removes the waterfall for data the server fetched during that render. Bolt SSR onto a codebase where components fetch in useEffect, and you get this:

❌ SSR that gains almost nothing
function Reviews({ productId }) {
  const [reviews, setReviews] = useState(null);

  useEffect(() => {
    fetch(`/api/reviews/${productId}`).then(r => r.json()).then(setReviews);
  }, [productId]);
  // 👆 useEffect NEVER runs on the server. So the server renders...

  if (!reviews) return <Spinner />;   // 👈 ...this. A spinner. In your HTML.
  return <ReviewList items={reviews} />;
}

The server dutifully renders a spinner into the HTML. The browser paints a spinner fast, hydrates, then starts the fetch. You've paid for a server and gained a faster spinner. This is such a common outcome that it's worth stating as a rule: SSR is only as good as the data you fetch during the server render.

Under the hood: why useEffect doesn't run on the server

useEffect is defined to run after the browser has painted. On the server there's no browser, no paint, no time passing — renderToString is a single synchronous pass that produces a string and stops. So effects are simply skipped. The same goes for useLayoutEffect (React will actually warn you about it). What does run on the server: the component function body itself, and useState's initial value.

Hydration mismatches

Hydration has a precondition that's easy to state and easy to violate: the HTML React produces in the browser must match the HTML the server sent. React isn't rebuilding the page, it's adopting it — and adoption only works if the thing it expected is the thing that's there.

When they differ, you get the dreaded "Hydration failed because the server rendered HTML didn't match the client" error. Here's the classic offender:

❌ Guaranteed mismatch
function Timestamp() {
  return <p>Rendered at {new Date().toLocaleTimeString()}</p>;
}
// Server (12:04:31) → "<p>Rendered at 12:04:31</p>"
// Client (12:04:33) → "<p>Rendered at 12:04:33</p>"
// 💥 React: these are not the same tree.

The three families of cause, and they're all the same idea — the server and the browser are different environments:

  • Time. Date.now(), new Date(), relative timestamps like "3 seconds ago." The server rendered at one moment, the browser hydrates at another. Also: server and user are usually in different time zones, so even formatting a fixed date can differ.
  • Randomness. Math.random(), shuffled lists, randomly-generated IDs. Two runs, two answers.
  • Browser-only state. Anything read from window, localStorage, navigator, cookies-via-document, or media queries. The server has no window, so you branch — and the two branches render differently. This is why "the theme flickers to light mode on reload" is such a common SSR bug.

The general fix is the same shape every time: render the server-safe version first, then update after hydration. An effect runs only in the browser, and only after hydration is done, so it's the safe place to introduce browser-only truth.

✅ Server and client agree on the first render
function Timestamp({ isoDate }) {
  const [mounted, setMounted] = useState(false);
  useEffect(() => setMounted(true), []);   // 👈 browser-only, post-hydration

  // Both server and first client render produce the exact same output:
  if (!mounted) return <p>Rendered at <time dateTime={isoDate} /></p>;

  return <p>Rendered at {new Date(isoDate).toLocaleTimeString()}</p>;
}

Yes, this causes a second render and a small visual shift. That's the actual cost of the fact that your app now runs in two places. There's no way to wish it away — you can only choose where to absorb it.

Trap: "just suppress the warning"

React offers suppressHydrationWarning on an element. It's a real, legitimate escape hatch for genuinely unavoidable cases (a timestamp element, mostly). But it silences the message, not the mismatch — React may still throw away the server HTML for that subtree and re-render it. Reaching for it reflexively is a red flag in an interview. Reaching for it deliberately, and being able to say why, is a green one.

"SSR" is an umbrella term: SSG, ISR, per-request

Here's a thing that quietly confuses a lot of people, including people who use these tools every day. When someone says "we use SSR," they might mean any of several different strategies. The precise distinction is simply: when does the HTML get generated?

There are three useful answers.

Static Site Generation (SSG) — at build time

You run your components once, on your machine or in CI, before anyone visits. The output is a folder of finished .html files. Deploy them to a CDN. Every visitor gets the same file, served from an edge server near them, in milliseconds.

The analogy I like: SSG is a printed newspaper. It was typeset once at 4am, and 200,000 identical copies went out on trucks. Handing someone a copy is nearly free. The catch is equally obvious — if news breaks at noon, every copy is stale until tomorrow's print run.

Fastest possible option, cheapest possible option. Only works when the content is the same for everybody and doesn't change often. Blog posts, docs, marketing pages, changelogs.

Incremental Static Regeneration (ISR) — at build time, then refreshed

ISR is SSG with an expiry date. You serve the pre-built page instantly, but you tell the framework "consider this stale after 60 seconds." The next visitor after that window still gets the cached page immediately (so nobody waits), and in the background the server re-renders the page and swaps in the fresh copy for everyone after.

Newspaper analogy again: it's a paper with hourly editions. You still grab a pre-printed copy off the stack — instant — but the stack gets replaced regularly without stopping the presses for a full re-run.

Where it breaks down: real ISR is per-page and cache-key-aware, not a global schedule, and different hosts implement it differently. But "static, with a refresh interval" is the right mental model.

This is the sweet spot for content that's shared across users but does change: an e-commerce category listing, a pricing page, a leaderboard.

Per-request SSR — at request time

The thing we described earlier: a server runs your components fresh for this request, for this user. Slower than serving a file (you're paying for the render plus your database calls on every hit) and you need a running server — but it's the only option when the page genuinely differs per user or must be up-to-the-second.

Logged-in dashboards, "recommended for you," anything reading cookies or auth headers, live inventory counts.

And the useful realisation: these aren't app-wide decisions any more. Modern frameworks let you choose per route. A single site can have a statically generated marketing page, an ISR product listing, and a per-request dashboard.

Wait — is SSG just... a static site? Like in 1998?

Yes! Genuinely. The output is HTML files on a disk. The difference is only in authoring: you write components and data-fetching in React and a build step produces the files, instead of hand-writing them. And unlike 1998, the page then hydrates and becomes a full React app for subsequent navigation. Sometimes the old idea was right and we just needed better tooling around it.

React Server Components

Alright. Deep breath. This is the part everybody finds hardest, so let's start by clearing the biggest misconception out of the way, because if you carry it in you will not be able to understand anything that follows.

A common misconception

"React Server Components are the new SSR." / "RSC replaces SSR."

No. RSC is not a faster SSR, not SSR 2.0, not a competitor to SSR. They're complementary, and in practice you use both at once. A typical Next.js App Router page uses Server Components and server-side rendering together on the same request. Turning on RSC does not turn off SSR.

They solve different problems entirely:

  • SSR answers: "how do I get meaningful HTML to the browser fast?" It's about the first paint.
  • RSC answers: "how do I stop shipping component code and data-fetching logic to the browser at all?" It's about the bundle and where the code lives.

If you only remember one sentence from this section, make it: SSR is about rendering components in two places; RSC is about some components only existing in one.

The actual new idea

Remember the SSR complaint from earlier — you still ship the same JavaScript? Server Components attack exactly that.

A Server Component is a component that runs only on the server, and whose code is never sent to the browser. It renders once, on the server, produces a description of UI, and its source code stays home. The browser receives the output — never the component.

Two consequences fall straight out of that, and they're both big.

Consequence one: those components cost zero bytes. Import a 200KB markdown-to-HTML library inside a Server Component and use it to render a blog post? The library runs on the server. The browser gets the finished HTML. Your bundle doesn't grow at all. This is the part that makes people sit up.

Consequence two: they can be async. This is the one that changes how code looks. Since the component only ever runs on the server, and the server can wait, React lets a Server Component be an async function that you await inside. You can talk to your database, read a file, call an internal service — directly, in the component body.

Here's the whole pitch in one image. Same feature, both ways:

❌ Client component + useEffect
'use client';
import { useState, useEffect } from 'react';

function Reviews({ productId }) {
  const [reviews, setReviews] = useState(null);
  const [error, setError] = useState(null);

  useEffect(() => {
    let cancelled = false;
    fetch(`/api/reviews/${productId}`)
      .then(r => r.json())
      .then(d => { if (!cancelled) setReviews(d); })
      .catch(e => { if (!cancelled) setError(e); });
    return () => { cancelled = true; };
  }, [productId]);

  if (error) return <p>Something broke.</p>;
  if (!reviews) return <Spinner />;

  return <ReviewList items={reviews} />;
}
// + you had to build /api/reviews
// + all of this ships to the browser
✅ Async Server Component
import { db } from '@/lib/db';

async function Reviews({ productId }) {
  const reviews = await db.reviews.findMany({
    where: { productId },
  });                        // 👈 straight to the DB

  return <ReviewList items={reviews} />;
}
// no API route needed
// no loading state
// no useEffect, no cleanup flag
// 0 bytes shipped to the browser

Sit with that for a second, because the reduction is the pitch. The left column has a race-condition guard, two pieces of state, an error path, a loading path, and a whole HTTP endpoint you had to write and deploy. The right column is a function that gets data and returns markup.

The API route disappeared because it existed only to move data across the client/server gap. When the component is already on the server, there's no gap to cross.

Wait — where did the loading state go?

Good catch, that's the right question. Fetching still takes time; someone still has to wait. The difference is who orchestrates it. You wrap the Server Component in React's <Suspense> and give it a fallback:

<Suspense fallback={<ReviewsSkeleton />}>
  <Reviews productId={id} />
</Suspense>

Now the rest of the page streams to the browser immediately, and the reviews section streams in when the query resolves. The loading state moved from inside the component (as state you manage) to outside it (as a boundary you declare). Same user experience, far less bookkeeping.

But we lost something, and it matters

Look again at that Server Component. It runs once, on the server, and then it's over. Its code isn't in the browser. So ask yourself:

What would useState even mean in there?

State is a value that changes over time and causes a re-render. But this component cannot re-render — it doesn't exist in the browser, there's no copy of it there to run again. Same for onClick: the browser would need the handler function, and functions can't be serialized into HTML. Same for useEffect: effects run after paint, and this component is long gone by paint time.

So Server Components have hard limits, and they are all the same limit wearing different hats:

Can't useBecause
useState, useReducerThere's nothing on the client to re-render when it changes.
useEffect, useLayoutEffectEffects run after browser paint. There's no browser.
onClick, onChange, any handlerHandlers are functions; functions can't cross to the browser as data.
window, localStorageDoesn't exist on a server.
Custom hooks that use any of the aboveSame reasons, one level up.

And symmetrically, Server Components can do things client code never could: read environment secrets, query a database directly, read the filesystem, call an internal service that isn't exposed to the internet. Your API key can sit in a Server Component and never leave the building.

So we need both kinds of component in one app. Which brings us to the hard part.

The server / client boundary

If some components run only on the server and others need to run in the browser, React needs to know which is which. The marker is a string at the very top of a file:

LikeButton.jsx
'use client';   // 👈 must be the first line in the file

import { useState } from 'react';

export function LikeButton({ initialCount }) {
  const [count, setCount] = useState(initialCount);
  return <button onClick={() => setCount(count + 1)}>❤️ {count}</button>;
}

In a framework with RSC enabled, every component is a Server Component by default. That's a real inversion — the thing you've done your whole React career is now the opt-in. 'use client' is how you opt back in.

It's a boundary, not a label

Here is the single most misunderstood thing about 'use client', and getting it right will separate you from most candidates.

'use client' does not mean "this one file is a client component." It marks a doorway into the client bundle. Everything you import from below that doorway — the whole subtree of imports — becomes client code too, whether or not those files have the directive themselves.

This is why a single carelessly-placed 'use client' near the root of your app can quietly drag your entire component tree into the browser bundle, undoing the whole benefit. The practical advice: push 'use client' as far down the tree as you can. Make the interactive leaf a client component, not its container.

The composition rules

Two rules, and the second one has an escape hatch that surprises everyone.

Rule 1: a Server Component can import and render a Client Component. Totally normal. The server renders the Client Component's initial output into the HTML, and includes a note in the payload saying "this bit needs to be hydrated by Tabs.jsx."

Rule 2: a Client Component cannot import a Server Component. Once you're inside client code, everything you import comes with you into the browser bundle — and a Server Component can't run there. It might query a database. That code cannot go to a browser. So the bundler refuses.

The escape hatch: pass it as children

But hold on — that sounds crippling. Does it mean once I have a client-side layout component, nothing inside it can ever be a Server Component again?

No, and the reason is subtle and lovely. Rule 2 forbids importing, not rendering. If a Server Component higher up renders the Server Component and hands the result to a Client Component as a prop, everything works:

❌ Client imports server
'use client';
import { useState } from 'react';
import { UserStats } from './UserStats';
//     👆 a Server Component. Bundler error.

export function Sidebar() {
  const [open, setOpen] = useState(true);
  return (
    <aside>
      <button onClick={() => setOpen(!open)}>Toggle</button>
      {open && <UserStats />}
    </aside>
  );
}
✅ Server passes it through as children
// Sidebar.jsx
'use client';
import { useState } from 'react';

export function Sidebar({ children }) {
  const [open, setOpen] = useState(true);
  return (
    <aside>
      <button onClick={() => setOpen(!open)}>Toggle</button>
      {open && children}   {/* 👈 just a hole */}
    </aside>
  );
}

// page.jsx  — a Server Component
<Sidebar>
  <UserStats />   {/* rendered on the server, slotted in */}
</Sidebar>

Why does this work? Because Sidebar never sees UserStats. It receives an already-rendered chunk of UI and drops it into a hole. It doesn't know or care where that chunk came from. It never imports it, so UserStats's code never enters the client bundle.

The analogy: think of the Client Component as a picture frame, and the Server Component's output as a photograph. The frame doesn't need a darkroom. It doesn't need to know how the photo was developed. It just needs something rectangular to hold. As long as you hand it a finished print, it does its job.

Where it breaks down: the frame can't change the photo. If the interactive component needs to alter what's inside based on state — re-fetch it, filter it — the picture-frame trick isn't enough, and you'll need to either lift the interactivity higher or make that part client-rendered.

Why props crossing the boundary must be serializable

When a Server Component renders a Client Component and passes props, those props have to physically travel from the server to the browser — as text, over the network. Anything that can't be written down as text can't make the trip.

That rules out:

  • Functions. A function is compiled code plus a closure over live variables. You can't write that down and rebuild it elsewhere. This is exactly why you can't pass onClick down from a Server Component — the handler must be defined in client code.
  • Class instances. Serializing a class instance gives you its fields, not its methods or its prototype chain. It arrives as a plain object with the behaviour stripped off, which is worse than an error.
  • Symbols, Dates-as-you-might-expect, and other exotica. React's serializer is more capable than JSON.stringify — it does handle Date, Map, Set, BigInt and Promises — but the safe habit is to send plain data (strings, numbers, booleans, null, arrays, plain objects) and construct the rich thing on the client. Assume less than the serializer supports and you'll never be surprised.
❌ Can't cross the boundary
// page.jsx — Server Component
export default function Page() {
  return <LikeButton onLike={() => console.log('liked')} />;
  //                 👆 Error: functions cannot be passed to client components
}
✅ Data crosses; behaviour stays put
// page.jsx — Server Component
export default function Page() {
  return <LikeButton postId={42} initialCount={17} />;
  //                 👆 plain numbers. easy to write down.
}
// LikeButton.jsx is 'use client' and defines its own onClick.

A good rule of thumb: data flows down across the boundary; behaviour stays on the side it belongs to. (One exception coming up shortly — Server Actions bend this, deliberately and carefully.)

The RSC Payload

So the server rendered some Server Components and marked some spots as "hydrate this with LikeButton." How does that information reach the browser?

Not as HTML. HTML can express "this is a button labelled ❤️ 17", but it can't express "and by the way, this button should be controlled by the module at chunk-abc123.js with these props." So React invented a second format.

The RSC Payload is a compact, streamable description of the rendered tree containing three kinds of thing:

  1. The rendered output of Server Components — plain elements, text, attributes.
  2. Placeholders where Client Components go, each pointing at the JS module that implements it.
  3. The serialized props being handed to each of those Client Components.

Conceptually, something in the spirit of:

RSC Payload (heavily simplified — the real format is terser)
["$", "article", null, { children: [
  ["$", "h1", null, { children: "Wool Socks" }],
  ["$", "p",  null, { children: "Warm. Very warm." }],
  ["$", "$L7", null, { postId: 42, initialCount: 17 }]
       // 👆 "render client module #7 here, with these props"
]}]

The analogy: the payload is a flat-pack furniture box. Most of it is finished parts you just place — that's the Server Component output. But a few spots have a slip of paper reading "insert hinge #7 here", and hinge #7 comes in a separate bag — that's the client JS chunk. The instructions say exactly which hinge and exactly where.

Where it breaks down: unlike flat-pack, you're not assembling from nothing. On a first page load React also sends real HTML (that's SSR doing its job) so the page paints before any of this is processed. The payload's job is to tell React how to hydrate that HTML and how to update it later.

And that "later" is the second reason the payload exists. When you navigate to a new page in an RSC app, the browser doesn't request a fresh HTML document — it requests the payload for the new route. React merges it into the existing tree. This is why client state (scroll position, an open modal, a video that's playing) can survive a navigation, while the new page's server work still happens on the server.

Under the hood: the full first-request pipeline

On an initial page load in a Next.js App Router app, all of this happens in one request:

  1. Server Components render on the server → produces the RSC Payload.
  2. React + the framework turn that payload (with Client Components rendered to their initial output) into an HTML string — this step is SSR, and it's why "Client Components run on the server too" is true.
  3. The HTML streams to the browser. The user sees content. 🎉
  4. The payload is streamed alongside it, embedded in the document.
  5. The client JS bundle — containing only Client Components — downloads and hydrates the interactive parts.

Notice that RSC and SSR both appear, at different steps, doing different jobs. That's the complementarity, made concrete.

Terminology cleanup

Let me say the quiet part loudly: the naming here is genuinely bad, and a lot of the confusion people feel is not conceptual confusion, it's vocabulary collision. Let's untangle it once, carefully.

TermWhat it actually means
Server-Side Rendering (SSR) A technique: run components on the server to produce an HTML string, so the browser paints content before JS loads. Predates RSC by years. Applies to Client Components too.
React Server Components (RSC) The overall paradigm / architecture: an app made of both server-only and client components, with a boundary and a payload format between them.
Server Component An individual component that runs only on the server. Its code is never sent to the browser. Can be async. No state, no effects, no handlers.
Client Component A component marked 'use client' (or imported by one). Its code is sent to the browser so it can be interactive. It still renders on the server during SSR — see below.

Now the two traps.

A common misconception

"'use client' means the component only runs on the client."

It does not. A Client Component runs in both places: once on the server during SSR to generate the initial HTML, and again in the browser during hydration and on every subsequent state change. The name describes where its code is allowed to live (it must be available on the client), not where it executes.

This has a very practical consequence people hit on day one: put window.localStorage.getItem('theme') in the body of a Client Component and it will crash with window is not defined — during the server render. The directive did not save you. That code still has to go in an effect.

A better mental name would have been 'use interactive' or 'needs hydration'. Too late now.

The second trap is the word "server" doing two jobs. A Server Component runs on the server. A Client Component also runs on the server (during SSR). So "does it run on the server?" is a useless question. The useful questions are:

  • Does its code get downloaded by the browser? Server Component: no. Client Component: yes.
  • Can it re-run after the page loads? Server Component: no. Client Component: yes, that's the whole point.

If you can hold those two questions in your head, the whole taxonomy collapses into something manageable.

Server Actions & where the ecosystem sits

One last piece, briefly, because it completes the picture. We covered reading data on the server. What about writing it?

Server Actions are functions marked 'use server' that live on the server but can be called from client code. React and the bundler conspire: the client gets a stub, and calling it fires an RPC to the real function on the server.

A Server Action
// actions.js
'use server';

export async function addToCart(formData) {
  const productId = formData.get('productId');
  await db.cart.add({ userId: await currentUser(), productId });
  revalidatePath('/cart');   // tell the framework this cached page is stale
}

// page.jsx — a Server Component, no 'use client' anywhere
<form action={addToCart}>
  <input type="hidden" name="productId" value={42} />
  <button>Add to cart</button>
</form>

This is the deliberate exception to "functions can't cross the boundary." A Server Action can be passed to a Client Component — but what crosses is not the function body, it's a reference to an endpoint the framework generated for you. The code stays on the server; only an ID travels.

The honest caveat: that's also a security surface. Every Server Action is a public HTTP endpoint, whether or not the UI that calls it is visible. Authorization must be checked inside the action itself — never assume "well, only admins can see the button."

Note the 'use server' / 'use client' naming is another sharp edge: 'use server' does not mark a Server Component (those are the default and need no directive). It marks a Server Action. Different thing entirely.

Where things actually stand

Be accurate about this in interviews — it's a maturity signal:

  • RSC is a React feature, but it needs deep bundler and router integration, so you don't use it directly — you use it through a framework.
  • Next.js App Router is the main production implementation and where the overwhelming majority of real RSC code lives today.
  • Other implementations exist and are maturing (React Router / Remix, Waku, Parcel's RSC support, RedwoodSDK), but Next is the default answer.
  • The Next.js Pages Router is the older, non-RSC model: getServerSideProps / getStaticProps and classic SSR/SSG. It's still widely deployed and still fine. Knowing both, and why the App Router changed things, is a good look.

The honest tradeoffs

I've spent a lot of words on the upside. A candidate who can only sell RSC sounds like a marketing page. Here's the other column.

Real complexity, not accidental complexity. There's now a boundary running through your app, and you have to hold it in your head at all times. "Can I use a hook here?" was never a question before; now it is. New engineers hit the boundary within their first hour and it's genuinely disorienting.

Framework coupling. An RSC app is a Next.js app (or equivalent) in a way that a CRA app never was. Ejecting is hard. You're taking a bet on a framework's roadmap, its hosting story, and its release cadence.

Debugging spans two runtimes. A console.log in a Server Component appears in your terminal, not the browser console — which trips up literally everyone at first. Stack traces cross the boundary. React DevTools understands the client tree well and the server tree less well.

The ecosystem is still catching up. A huge number of npm packages assume they run in a browser. Component libraries that use context or hooks internally need 'use client', and older versions don't have it — so you end up writing thin wrapper files just to add the directive. This is improving fast, but it's real friction today.

You need a server. An RSC app can't be a folder of static files on a CDN. That's cost, ops, and a cold-start story you didn't have before. (Some routes can still be statically generated — but the architecture assumes a server exists.)

And it isn't always worth it. For a heavily interactive app where nearly every component needs state anyway — a design tool, a spreadsheet, a game — most of your tree is going to be 'use client' regardless. The bundle savings evaporate and you've bought complexity for very little. Being able to say "we didn't adopt RSC because our app is 90% interactive canvas" is a stronger answer than reciting benefits.

The interview layer

How this gets asked

The literal phrasings you'll hear:

  • "Walk me through what happens when a user loads a React app."
  • "What's the difference between client-side and server-side rendering?"
  • "What is hydration?"
  • "When would you use static generation instead of SSR?"
  • "Have you used the Next.js App Router? What are Server Components?"
  • "What's the difference between SSR and React Server Components?" — the big one.
  • "You've got a page that's slow to load. How would you diagnose and fix it?" — the open-ended version, and the one where this knowledge really pays.

Notice which of these test recall ("what is hydration") and which test depth ("why is it expensive," "when would you not use RSC"). The recall questions are the setup. The depth questions are the actual interview, and they're almost always follow-ups.

Model answers

Say this — "CSR vs SSR"

"With client-side rendering, the server sends an almost-empty HTML file plus a JS bundle. The user stares at a blank screen until the bundle downloads and React boots — and only then does the data fetch even start, so you get a waterfall. With server-side rendering, the server runs the React components and sends back real HTML, so the browser can paint meaningful content almost immediately. The JS still downloads afterwards and hydrates that markup to make it interactive. So SSR mainly buys you a much faster first contentful paint and working SEO; it costs you a server, and time-to-interactive is actually slightly worse because hydration is extra work."

Why it lands: it's a narrative, not a definition, and it names a cost. Anyone can say "SSR is faster." Saying "faster to content, slightly slower to interactive, and here's why" tells the interviewer you've actually looked at a performance panel.

Say this — "What are Server Components?"

"Server Components run only on the server, and their code is never sent to the browser at all. Because they only run there, they can be async — you can await a database query directly inside the component instead of building an API route and fetching from a useEffect. The tradeoff is they can't have state, effects, or event handlers, since none of that means anything without a copy running in the browser. So you mark the genuinely interactive leaves with 'use client' and leave everything else on the server. The two big wins are less JavaScript shipped and no client-server data waterfall."

Why it lands: it leads with the mechanism ("code is never sent"), derives the constraints instead of memorising them, and ends with the two benefits. It's also short enough to say out loud without losing the room.

Follow-up questions

"So what's the difference between SSR and RSC?"

The one-liner: SSR is about when the HTML is produced; RSC is about which components exist in the browser at all.

SSR takes your components — all of them — runs them on the server to make an HTML string, then ships every one of those components to the browser so they can be hydrated. Bundle size unchanged. RSC changes what's in that bundle: Server Components render on the server and their code never travels, so they contribute zero bytes and can't be hydrated (there's nothing to hydrate them with).

The critical add-on, and the thing that separates a good answer from a great one: they aren't alternatives. A Next.js App Router request uses both — RSC decides which components run where and produces the payload, then SSR turns that into the HTML that paints first. If you say "we replaced SSR with RSC," you've said something false.

"What is hydration, and why is it expensive?"

Hydration is React booting up in the browser on top of server-rendered HTML: instead of creating DOM nodes, it renders your tree in memory, matches it against the existing markup, and attaches event listeners and state to those nodes. Dan Abramov's framing is watering dry HTML with the water of interactivity.

It's expensive for three compounding reasons. One: it's a full render pass — every component in the tree runs, on the user's device, mostly to recompute something the server already computed. Two: it's largely synchronous and blocks the main thread, so during hydration the page can't respond to taps or scroll — and it's happening exactly when the user is most likely to try. Three: it requires the whole JS bundle first, so it's gated behind your biggest download.

The practical consequence is the uncanny valley: the page looks ready but isn't. Mitigations: ship less JS (which is exactly RSC's pitch), stream with Suspense so hydration can be broken into chunks, and lean on selective hydration so React prioritises the part the user just interacted with.

"When would you choose SSG over SSR?"

When the page is the same for every visitor and doesn't need to be second-fresh. Then rendering it once at build time and serving a file from a CDN is strictly better: faster (no server work per request, edge-cached), cheaper, and it can't fall over under load because there's nothing to fall over.

You need per-request SSR the moment the output depends on who is asking — auth state, personalisation, cookies, a cart — or has to be genuinely live, like inventory at checkout.

And the answer that shows real experience: it's rarely all-or-nothing. You pick per route, and for the big middle ground — shared content that changes on a timescale of minutes — you use ISR: serve the static page instantly, revalidate in the background. Also worth naming the SSG failure mode: build time scales with page count, so a 500,000-SKU catalogue can't be fully pre-built, and you fall back to generating on first request and caching.

"Why can't I use useState in a Server Component?"

Because state is only meaningful if something can re-render when it changes — and a Server Component cannot re-render. It runs once on the server, produces output, and is finished. Its code was never sent to the browser, so there is literally no copy of that function available to run again. Calling setState would have nothing to call.

Same logic covers the whole family: useEffect runs after browser paint and there's no browser; onClick needs a live function in the browser and functions can't be serialized; window doesn't exist server-side. It's one restriction, not five.

Deriving it like this is much stronger than listing it. The interviewer is checking whether you memorised a table or understood a model.

"Why can't I pass a function as a prop across the boundary?"

Because props that cross from server to client have to be serialized — written down as text and sent over the network. A function isn't data; it's compiled code plus a closure over live variables in the server's memory. There's no honest way to write that down and reconstitute it in a different process on a different machine.

So event handlers have to be defined in client code. The pattern is: pass the data down (postId, initialCount), and let the Client Component own the behaviour.

The nuance worth adding: Server Actions are the deliberate exception. A 'use server' function can be passed to a Client Component — but what actually crosses is a reference to a framework-generated endpoint, not the function body. The code never leaves the server; calling it is an RPC.

"Does 'use client' mean the component only runs on the client?"

No — and this is the most common misunderstanding in the whole area. A Client Component still renders on the server during SSR to produce the initial HTML, then runs again in the browser to hydrate, then on every state change after that. The directive marks where the client bundle begins — it means "this code must be available in the browser," not "this code only executes in the browser."

Concrete proof: put window.matchMedia(...) in the body of a 'use client' component and it crashes with window is not defined during the server render. Browser-only code still belongs in an effect.

The other half of the answer is the boundary point: 'use client' isn't a per-file label. Everything imported below it joins the client bundle too, even files without the directive — which is why you push the directive as far down the tree as possible.

"What's the benefit if the user still downloads React anyway?"

Sharp question, and it deserves a precise answer rather than a defensive one. Yes — if any part of the page is interactive, the browser downloads the React runtime plus every Client Component. RSC doesn't get you to zero JS.

What it removes is your application code and its dependencies on the server side of the boundary. The React runtime is a fixed cost that doesn't grow with your app; a markdown parser, a syntax highlighter, a date library, an i18n bundle, your ORM types and data-fetching code — those grow with your app, and those are what vanish. In a content-heavy app that's often the majority of the bundle.

And bundle size isn't even the only win. You also delete the API layer that existed purely to move data across the network, you remove the client-side data waterfall, and you keep secrets and heavy queries on the server. Then the honest close: for a highly interactive app where most components need state anyway, the savings are small and the complexity might not pay for itself. That last sentence is what makes the answer credible.

"What causes a hydration mismatch?"

Anything that makes the browser's first render produce different markup from what the server sent — because hydration adopts existing DOM rather than rebuilding it, so it needs the shapes to match.

The three usual causes: time (Date.now(), "3 minutes ago", timezone differences between server and user), randomness (Math.random(), shuffled arrays, random IDs), and browser-only state (window, localStorage, media queries, document.cookie) where the server takes a different branch than the client. There's also plain invalid HTML nesting — a <div> inside a <p> gets silently restructured by the browser's parser, so the DOM no longer matches what React emitted. That one's sneaky.

The fix is always the same shape: render something server-safe first, then correct it in an effect after hydration. And name the cost honestly — that means a second render and possibly a flash. suppressHydrationWarning exists but it hides the symptom, not the mismatch.

"How does RSC affect bundle size?"

Server Components contribute zero bytes to the client bundle — neither the component nor anything it imports on the server side of the boundary. So a heavy dependency used only in a Server Component becomes effectively free to the user.

But the mechanism is import-graph-based, not per-file, and that's the part people get wrong. Everything reachable from a 'use client' file is in the bundle. Put 'use client' at the top of your root layout and you've shipped your whole app to the browser while thinking you're using RSC. So the discipline is: keep the directive on the interactive leaves, and use the children/props pattern to keep server-rendered content inside client containers.

Worth adding: it's not purely a win. The RSC Payload is extra bytes over the wire on top of the HTML, and it's re-fetched on navigation. You're trading a large one-time JS download for smaller repeated payload downloads. Usually a good trade; not a free one.

Traps

Trap 1 — "RSC replaced SSR"

This is the single most common wrong answer, and it reads as "I skimmed a blog post." They are complementary and used together. If you catch yourself about to say "instead of SSR," say "on top of SSR."

Trap 2 — "SSR makes your site faster"

Too vague, and half wrong. Faster to first contentful paint. Not faster to interactive. Always split the metric. If you say "faster" without qualification, expect "faster at what?" and you'll be on the back foot.

Trap 3 — "Server Components are faster than Client Components"

Category error. Speed isn't the axis — capability and location are. A Server Component avoids shipping code and can fetch data close to the database. A Client Component can respond to a click. Comparing them on speed suggests you don't have the model.

Trap 4 — "Hydration is just React attaching event listeners"

Half true, and the missing half is the expensive half. It's a full render pass of your whole tree on the user's device, which is why it blocks the main thread. If your answer implies it's a cheap decoration step, you can't then explain why anyone cares about it.

Trap 5 — Recommending SSR for everything

An internal dashboard behind a login gets no SEO benefit and its users are on decent hardware. A canvas-based editor has no meaningful HTML to pre-render. Saying "it depends on whether the page needs SEO, how shared the content is, and how interactive it is" is a much better answer than picking a favourite architecture.

One closing thought. If this felt like a lot, that's because it is — you just absorbed about a decade of architectural argument in one sitting. But notice that almost everything here falls out of a single question you can always re-derive from scratch:

Where does this code run, and what has to travel over the network?

Blank screen? Nothing meaningful travelled. Hydration cost? Code travelled and had to run again. Server Component? The code didn't travel. Can't pass a function? Functions can't travel. Hydration mismatch? Two runs of the same code, two different environments, two different answers.

Every rule in this guide is a consequence of that one question. If you can hold onto it, you can rebuild the rest at the whiteboard. Good luck. 🚀
