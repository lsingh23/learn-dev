1. The foundation: primitives and objects

Everything in JavaScript is one of two kinds of thing. Not "sort of two kinds" — genuinely two, and the line between them is the single most important line in the language.

On one side you have primitives. These are the simple, atomic values. There are seven of them:

TypeExampleWhat it's for
string'hello'Text
number42, 3.14, NaN, InfinityAll numbers — no separate int/float
booleantrue, falseYes/no
undefinedundefined"No value has been assigned here"
nullnull"Deliberately nothing"
symbolSymbol('id')Unique keys that can't collide
bigint9007199254740993nIntegers too big for number

You'll hear people say "seven-ish" because symbol and bigint are newer and rarely come up in day-to-day app code. For interviews, know that they exist and that they're primitives; nobody's going to grill you on bigint.

On the other side you have objects. And "object" here is a much bigger tent than you might expect. Plain objects are objects, obviously — but so are arrays, functions, dates, regular expressions, Map, Set, class instances, DOM nodes. If it isn't in that table of seven, it's an object.

typeof 'hello'        // → 'string'
typeof 42             // → 'number'
typeof true           // → 'boolean'
typeof undefined      // → 'undefined'

typeof { a: 1 }       // → 'object'
typeof [1, 2, 3]      // → 'object'   👈 arrays are objects
typeof new Date()     // → 'object'
typeof function () {} // → 'function' 👈 the one special case

Functions are objects — you can put properties on them, they're passed around by reference like objects — but typeof gives them their own label as a convenience, because "is this callable?" is a question people ask a lot.

And then there's the famous one:

typeof null           // → 'object'   👈 this is a bug. an old, permanent one.

We'll come back to why in section 7, because the reason is a genuinely fun piece of history and it comes up in interviews constantly. For now: null is a primitive, typeof lies about it, and that's that.

What actually separates the two groups?

Two things, and they're connected.

First: primitives are immutable. Not "you shouldn't change them" — you cannot. There is no operation in JavaScript that modifies the number 5 or the string 'hello'. String methods look like they mutate, but they don't:

const greeting = 'hello';
greeting.toUpperCase();   // → 'HELLO'  (a brand new string)
console.log(greeting);    // → 'hello'  (the original, untouched)

Objects, by contrast, are mutable. You can add, change, and delete their properties all day long, and it's still the same object.

Second — and this is the one that matters — is how they're stored and passed around. That deserves its own section.

2. Values vs. references

Here's the mental model. I want you to actually picture this, because everything downstream depends on it.

Imagine your program has two storage areas.

The first is a wall of labelled boxes — one box per variable. The box is small. It fits a number, a boolean, a short piece of text. When you write const age = 30, the value 30 is physically written inside the box labelled age.

The second area is a big warehouse floor where you keep things too big for a box: objects, arrays, functions. When you create an object, it gets put down somewhere on the warehouse floor and given an address — like #8891. And then what goes in the little labelled box isn't the object. It's a sticky note with the address written on it.

You'll hear these two areas called the stack and the heap. That's the real terminology, and it's roughly accurate — though real JS engines are cleverer than this (they do things like storing small integers inline and interning strings). The analogy breaks down if you push it into performance territory. But as a model of behaviour, it's exactly right, and behaviour is what we care about.

Assignment copies the box, not the warehouse

Here's the rule that falls out of the picture. When you write b = a, JavaScript copies what's in the box. Always. No exceptions.

For a primitive, what's in the box is the value itself, so you get a real, independent copy:

let score = 10;
let highScore = score;   // copies the value 10

score = 99;
console.log(highScore);  // → 10   ✅ unaffected

For an object, what's in the box is an address. So you copy the address. Both variables now hold sticky notes pointing at the same spot on the warehouse floor:

const user = { name: 'Ada', role: 'admin' };
const admin = user;      // copies the address, NOT the object

admin.role = 'superadmin';
console.log(user.role);  // → 'superadmin'  😬

Nothing was copied here except a scrap of paper with an address on it. There is still exactly one object in the whole program.

A common misconception

"JavaScript passes primitives by value and objects by reference."

This is the phrasing everyone uses, and it's close enough that you'll be understood — but the precise version is better and interviewers notice it: JavaScript is always pass-by-value. It's just that the value of an object variable is a reference.

Why does the distinction matter? Because true pass-by-reference would let a function reassign the caller's variable, and JS can't do that:

function replace(obj) {
  obj = { name: 'Grace' };   // reassigns the local sticky note only
}
const person = { name: 'Ada' };
replace(person);
console.log(person.name);    // → 'Ada'  (unchanged!)

function rename(obj) {
  obj.name = 'Grace';        // follows the address, edits the warehouse
}
rename(person);
console.log(person.name);    // → 'Grace'

Mutating through the reference reaches the caller. Reassigning the parameter doesn't. That's exactly what "pass-by-value, where the value is a reference" predicts. Some people call this call-by-sharing.

And now: [1,2,3] === [1,2,3]

We have everything we need. Let's go back to the very first line.

[1, 2, 3] === [1, 2, 3]   // → false

Two array literals appear in that line, which means JavaScript builds two separate arrays — two distinct places on the warehouse floor, at two distinct addresses. Say #4400 and #4401.

Then === compares them. And for objects, === doesn't look at the contents at all. It compares the addresses. #4400 is not #4401. Therefore: false.

The analogy I like: two identical twins. Same DNA, same haircut, same clothes. Ask "are these the same person?" and the answer is no — there are two of them. === on objects asks "same person?", never "same appearance?".

const a = [1, 2, 3];
const b = [1, 2, 3];
const c = a;

a === b   // → false   two arrays, two addresses
a === c   // → true    one array, one address, two labels

// contrast with primitives:
'abc' === 'abc'   // → true    the value IS the content
5 === 5           // → true

This is worth sitting with for a second, because it is the load-bearing fact for the rest of this guide. There is no such thing as "two objects that are equal" in JavaScript's built-in comparison. There's only "the same object" or "not the same object."

Wait, what about…

"So how do I check whether two objects have the same contents?" You write that yourself, or you use a library. We'll build it in section 12. The fact that JS gives you no built-in for it surprises everyone at first, and it's a great interview question.

3. What === actually does

=== is called strict equality, and its algorithm is refreshingly short. Two steps:

  1. If the two operands have different types → false. Done. No conversions, no negotiation.
  2. Same type? Compare them:
    • Objects: same address?
    • Primitives: same value?

That's it. Which is why '5' === 5 is false — string and number, different types, stop.

There is exactly one wrinkle, and it's NaN.

NaN === NaN   // → false
NaN !== NaN   // → true    the only value not equal to itself

NaN means "Not a Number" and it's what you get from a numeric operation that has no sensible numeric answer: 0/0, Math.sqrt(-1), parseInt('hello'), undefined + 1.

The reason it isn't equal to itself: NaN isn't a value so much as an error marker. Think of it like a "RETURNED TO SENDER" stamp on an envelope. Two envelopes both stamped "returned to sender" didn't fail for the same reason and aren't the same letter. Asking whether they're equal is asking a question that has no meaningful answer, so IEEE-754 (the floating point standard JS numbers follow, which predates JS by a decade) says: just answer false to everything.

Practically, this means you can never test for NaN with equality. Use Number.isNaN():

const price = Number('not a price');   // → NaN

price === NaN            // → false  ❌ always false, useless
Number.isNaN(price)      // → true   ✅
Object.is(price, NaN)    // → true   ✅ also works
Under the hood

Object.is() is "=== with the two historical warts fixed": it says NaN equals NaN, and it says 0 does not equal -0 (whereas 0 === -0 is true). You will almost never write it directly — but React uses it internally to decide whether state actually changed, which is why it's worth recognizing. And the old isNaN() global is a trap: it coerces first, so isNaN('hello') is true even though a string isn't NaN. Always the Number. one.

4. What == actually does

== is loose equality, or in the spec, abstract equality. And here's the thing people get wrong about it: == is not random. It's not "JavaScript guesses." It follows a completely deterministic procedure. It's just that the procedure was designed in 1995 in about ten days with the goal of being forgiving to beginners, and forgiving turned out to mean unpredictable.

The one-sentence version: == tries to make the two sides the same type, then compares.

The useful version — the one you can actually reason with — is five rules, applied in order. If the types already match, == behaves exactly like === and we're done. So all of these are about what happens when the types differ:

#SituationWhat happens
1null vs undefinedtrue. Special-cased. They equal each other and nothing else.
2number vs stringThe string becomes a number.
3boolean on either sideThe boolean becomes a number first (true→1, false→0), then start over.
4object vs primitiveThe object becomes a primitive (see next section), then start over.
5anything elsefalse.

Notice rules 3 and 4 say "then start over." == is a loop. It keeps simplifying until both sides are the same type, then does a direct comparison. Let's run the notorious cases through it.

Case 1: null == undefined is true, but null == 0 is false

This one trips people because they reason "both are falsy, so they should be loosely equal." But falsiness is a different system — it's about how values behave in an if. It has nothing to do with ==.

null == undefined hits rule 1. It's hardcoded. The language designers decided the two "absence" values should be interchangeable when you're loosely checking for absence, which — honestly — is the one genuinely good decision in the whole == design.

null == 0 also hits rule 1's clause, which says null is loosely equal to undefined and to nothing else. There is no rule that converts null to a number in the == algorithm. So we fall through to rule 5: false.

null == undefined   // → true   (rule 1)
null == 0           // → false  (no rule applies → false)
null == false       // → false  (nope)
null == ''          // → false  (nope)
undefined == 0      // → false  (same deal)

// but, infuriatingly:
null >= 0           // → true   👈 relational operators DO convert null to 0

That last line is the punchline that shows == isn't just "convert and compare" — it has its own special rules that >= doesn't share. Nobody expects you to know this in an interview; I include it because it's the cleanest proof that == is a hand-written list of cases rather than a principled system.

Case 2: '' == 0 is true

Rule 2: string vs number, so the string converts to a number. And the empty string converts to 0. (Why? Because Number('') is 0 — the spec says an empty or whitespace-only string numifies to zero.) So we end up with 0 == 0 → true.

'' == 0        // → true    Number('') is 0
'  ' == 0      // → true    whitespace-only also numifies to 0
'0' == 0       // → true
'1' == true    // → true    true→1, then '1'→1
'abc' == 0     // → false   Number('abc') is NaN, and NaN equals nothing

Case 3: [] == false is true

This is the famous one, and it's a three-step chain. Watch it unfold:

// start:       [] == false
// rule 3:      [] == 0          // boolean → number
// rule 4:      '' == 0          // object → primitive: [] stringifies to ''
// rule 2:       0 == 0          // string → number
// result:     true

Every individual step is defensible. The composition is madness. This is the single best argument against ever using ==: not that any one rule is crazy, but that they chain, and no human tracks three coercions in their head while reading a pull request.

The step that probably needs explaining is rule 4 — how does [] become ''? That's ToPrimitive, and it deserves its own section.

5. ToPrimitive: where the weirdness comes from

Objects can't be compared to numbers or strings directly, so whenever JavaScript needs a primitive and you've handed it an object, it runs an internal procedure called ToPrimitive. It's not magic — it's a phone call.

Picture it like this: JavaScript rings up the object and says "I need you as a simple value. What have you got?" The object has two people who can answer that phone: valueOf() and toString(). Every object inherits both.

Which one JS calls first depends on what it's hoping for — the spec calls this the hint:

  • Hint "number" (arithmetic, == against a number, <): try valueOf() first. If it returns a primitive, use it. Otherwise fall back to toString().
  • Hint "string" (template literals, using the object as a property key): try toString() first, then valueOf().
  • Hint "default" (the + operator, == generally): behaves like "number" for almost everything. Dates are the exception — they prefer string.

Now, the key fact: for plain objects and arrays, valueOf() just returns the object itself. Which isn't a primitive. Which means it's useless, and JS falls through to toString() every single time.

[].valueOf()          // → []          not a primitive, keep going
[].toString()         // → ''          👈 this is what gets used

[1, 2].toString()     // → '1,2'       arrays join with commas
[5].toString()        // → '5'

({}).valueOf()        // → {}          not a primitive
({}).toString()       // → '[object Object]'

Array's toString is just join(','). An empty array joins to an empty string. That's the whole trick behind [] == false — no mystery, just a method call you didn't know was happening.

Once you have that, a bunch of "cursed JavaScript" tweets decode instantly:

[] == ''         // → true    '' == ''
[5] == 5         // → true    '5' == 5 → 5 == 5
[1,2] == '1,2'   // → true    '1,2' == '1,2'

[] == []         // → false   👈 both objects! no coercion happens at all,
                 //            it's just an address comparison

{} + []          // → 0 in a REPL, '[object Object]' in an expression
                 //   (this one's about parsing, not coercion — ignore it)

That [] == [] line is my favourite, because it shows the rules are consistent. Coercion only kicks in when the types differ. Object vs object? Straight to address comparison, same as ===.

Under the hood

Some built-in objects override valueOf to return something genuinely useful, and that's when ToPrimitive stops looking silly:

const d = new Date('2026-01-01');
d.valueOf()      // → 1767225600000  (a real primitive: ms since epoch)
d - 0            // → 1767225600000  works! subtraction hints "number"
`${d}`           // → 'Thu Jan 01 2026...'  template literal hints "string"

You can define your own too, via valueOf, toString, or the modern Symbol.toPrimitive method which takes the hint as an argument and overrides both. This is how libraries make objects that behave like numbers.

So: the practical rule

Use === everywhere. Always. Full stop.

Not because == is evil, but because === has one rule and == has a decision tree with recursion in it. Code is read far more than it's written, and === means the reader never has to run an algorithm in their head. Every mainstream linter config (eqeqeq) enforces this by default.

But there is one place == is genuinely idiomatic, and knowing it is a small green flag in interviews:

if (user.middleName == null) {
  // runs for BOTH null and undefined, and nothing else
}

// exactly equivalent to:
if (user.middleName === null || user.middleName === undefined) { }

Because rule 1 says null is loosely equal to undefined and to nothing else, x == null is a precise, safe "is this nullish?" check. It will not fire for 0, '', false, or NaN. It's the one coercion in the language that's tight enough to trust, and you'll see it all over well-written libraries. Some style guides even carve out an exception for it (eqeqeq: ['error', 'always', { null: 'ignore' }]).

That said — if your codebase bans == outright, x === null || x === undefined is fine, and x ?? fallback often removes the need entirely. Don't die on this hill; just know the reasoning.

6. Truthiness and the falsy list

Separate system, easily confused with ==, so let's nail it down.

When a value lands somewhere that needs a boolean — an if, a while, a &&, a ! — JavaScript runs ToBoolean on it. That algorithm is beautifully simple: there is a short list of falsy values, and everything else is truthy.

The complete list. There are eight, and two are exotic:

false
0
-0
0n          // BigInt zero
''          // empty string (all quote styles)
null
undefined
NaN

That's the entire list. Memorizing it is genuinely worth it — it takes thirty seconds and it comes up constantly. Everything not on it is truthy, including several things people guess wrong:

Boolean([])          // → true   👈 empty array is TRUTHY
Boolean({})          // → true   👈 empty object is TRUTHY
Boolean('0')         // → true   non-empty string
Boolean('false')     // → true   non-empty string
Boolean(' ')         // → true   a space is a character
Boolean(-1)          // → true   only ZERO is falsy, not "negative"
Boolean(function(){})// → true
A common misconception

"[] is falsy — that's why [] == false is true."

Nope, and this is the mix-up I see most. [] is truthy. You can prove it in one line: if ([]) console.log('yep') logs. The reason [] == false is true is the coercion chain we traced earlier — it never asks whether [] is truthy. Two different algorithms, two different answers, and they happen to disagree. If you say this in an interview, correcting yourself with "actually, [] is truthy — the == result comes from toString" is a strong recovery.

The if (count) bug

Here's the falsy list ruining someone's afternoon. Realistic setup: a shopping cart badge.

❌ Buggy
function CartBadge({ itemCount }) {
  if (!itemCount) {
    return 'Your cart is empty';
  }
  return `${itemCount} items`;
}

Looks fine. Ships. Then a bug report: "the badge says 'Your cart is empty' when I have zero items." Well… yes? That's correct. Okay, different report: a dashboard.

❌ Buggy
function UnreadCount({ count }) {
  if (!count) return null;              // hide the badge
  return <span>{count}</span>;
}

// count = 5      → shows "5"        ✅
// count = 0      → hides           ✅ (intended!)
// count = undefined (still loading) → hides  ✅ (also intended!)

So far so good — this is actually one of the cases where truthiness does what you want. The bug appears the moment 0 is a meaningful value rather than an empty one:

❌ Buggy
function TempReading({ celsius }) {
  if (!celsius) return 'No reading available';
  return `${celsius}°C`;
}

// celsius = 0  →  "No reading available"   👈 WRONG. 0°C is a reading!
✅ Fixed
function TempReading({ celsius }) {
  if (celsius == null) return 'No reading available';   // null or undefined only
  return `${celsius}°C`;
}

// celsius = 0          →  "0°C"                    ✅
// celsius = undefined  →  "No reading available"   ✅

Same bug class, different disguise, in JSX:

❌ Buggy
{cart.items.length && <CartList items={cart.items} />}

// empty cart → length is 0 → the whole expression evaluates to 0
// → React renders a literal "0" on your page. 🎉
✅ Fixed
{cart.items.length > 0 && <CartList items={cart.items} />}

The rule to internalize: truthiness checks are fine when "empty" and "missing" should behave the same. The moment 0 or '' is a legitimate value in your domain, switch to an explicit check. Prices, counts, coordinates, temperatures, form inputs, ratings — all classic victims.

7. null vs undefined

Most languages get by with one "nothing" value. JavaScript has two, which sounds like a design flaw but there's actually a real distinction underneath — it just gets muddied in practice.

The intended semantics:

  • undefined = "nobody has put anything here." It's the absence of assignment. It's the language's default, produced automatically.
  • null = "I am deliberately telling you there's nothing here." It's an intentional empty. A human wrote it.

The analogy: undefined is an unlabelled, unopened box in the warehouse — nobody's touched it. null is a box with a note inside saying "intentionally left empty — signed, the developer." Both are empty. Only one is a decision.

You almost never write undefined yourself. JavaScript hands it to you in five situations:

let cachedUser;
cachedUser;                     // → undefined   1. declared, not assigned

const user = { name: 'Ada' };
user.email;                     // → undefined   2. missing property

const scores = [10, 20];
scores[7];                      // → undefined   3. out-of-range index

function greet(name) { }
greet();                        // name is undefined   4. missing argument

function noReturn() { }
noReturn();                     // → undefined   5. no return statement

null, by contrast, only ever exists because somebody put it there — you, an API response, or a DOM method telling you it found nothing (document.querySelector('.nope') → null).

Why typeof null === 'object'

This is pure history and it's a great story to have ready.

In the very first JavaScript engine (1995), values were stored as a chunk of memory where the low bits acted as a type tag. Tag 000 meant "this is an object — the rest of the bits are a pointer." Other tags marked integers, strings, booleans.

The null pointer was represented as all-zero bits. Which means its type tag was… 000. Object. So typeof, which just reads the tag, dutifully reported 'object'.

It was fixed in a proposal for ES6 — typeof null would return 'null' — and it was rejected, because too much code on the live web does typeof x === 'object' as a stand-in for "is this a reference type." Changing it would have broken real websites. So it's permanent. It's not a feature; it's a fossil.

Practically, this means typeof alone can't tell you if something is a real object:

❌ Buggy
function isObject(value) {
  return typeof value === 'object';
}
isObject(null);   // → true   😬
✅ Fixed
function isObject(value) {
  return typeof value === 'object' && value !== null;
}
// (add !Array.isArray(value) if you want to exclude arrays too)

Default parameters only fire on undefined

Here's a place the distinction has teeth. Default parameter values trigger when the argument is undefined — and only then. null is treated as a real value you chose to pass.

function createUser(name, role = 'member') {
  return { name, role };
}

createUser('Ada');              // → { name: 'Ada', role: 'member' }  ✅ default fires
createUser('Ada', undefined);   // → { name: 'Ada', role: 'member' }  ✅ default fires
createUser('Ada', null);        // → { name: 'Ada', role: null }      👈 no default!
createUser('Ada', '');          // → { name: 'Ada', role: '' }        no default (correctly)

This bites when data comes from a database. SQL's empty is NULL, which serializes to JSON null, which arrives in your JS as null — and blows straight past every default you wrote. Destructuring defaults have the identical rule:

const { theme = 'light' } = { theme: null };
theme;   // → null, not 'light'

JSON treats them completely differently

null is a real JSON type. undefined isn't in the JSON spec at all — so JSON.stringify has to do something, and what it does depends on where the undefined is:

JSON.stringify({ a: 1, b: undefined, c: null });
// → '{"a":1,"c":null}'      👈 the key `b` is GONE entirely

JSON.stringify([1, undefined, 3]);
// → '[1,null,3]'            👈 in an array it becomes null (positions must hold)

JSON.stringify(undefined);
// → undefined               👈 not a string! not '"undefined"'! just undefined

JSON.stringify({ save: function () {} });
// → '{}'                    functions vanish the same way

Silent key removal is a genuinely nasty source of bugs — you PATCH an object to your API expecting to clear a field, and the field just isn't in the payload, so the server leaves it alone. If you mean "clear this," send null.

8. ?? vs ||

You've probably written this to supply a fallback:

const pageSize = userPreference || 20;

|| returns the left side if it's truthy, otherwise the right side. Which means it doesn't fall back on "missing" — it falls back on the entire falsy list. And we just learned that list includes 0 and ''.

So the moment a user legitimately chooses zero, you silently overrule them:

❌ Buggy
const settings = { fontSize: 0, username: '', notifications: false };

const fontSize = settings.fontSize || 16;        // → 16     👈 user wanted 0
const username = settings.username || 'Anon';    // → 'Anon' 👈 user cleared it on purpose
const notify = settings.notifications || true;   // → true   👈 user opted OUT. we opted them in.

That third line is the scary one. It is impossible for that expression to ever return false. You've written a setting that can't be turned off.

?? — the nullish coalescing operator — fixes this by narrowing the trigger from "falsy" to "nullish", meaning null or undefined and nothing else:

✅ Fixed
const fontSize = settings.fontSize ?? 16;        // → 0
const username = settings.username ?? 'Anon';    // → ''
const notify = settings.notifications ?? true;   // → false

// and it still does the job it was hired for:
undefined ?? 'fallback'   // → 'fallback'
null ?? 'fallback'        // → 'fallback'

Think of it as: ?? asks "is this missing?" while || asks "is this empty-ish?" — and empty-ish is a much bigger, blurrier net than you usually want.

My rule: reach for ?? by default. Use || only when you genuinely want empty string and zero to trigger the fallback — for example const label = title.trim() || 'Untitled', where an all-whitespace title really should become "Untitled."

Wait, what about…

"Why does a ?? b || c throw a syntax error?" Because mixing ?? with || or && without parentheses is deliberately illegal. The precedence would be ambiguous to readers, so the spec authors made you disambiguate: (a ?? b) || c. It's a rare case of a language forcing clarity, and I love it.

Related: ??= exists too. options.retries ??= 3 assigns only if retries is null or undefined.

9. Copying: shallow vs. deep

Back to the warehouse. We established that = copies the sticky note, not the object. So how do we make an actual copy?

The standard tools are spread (...) and Object.assign:

const original = { name: 'Ada', role: 'admin' };

const copy = { ...original };                    // spread
const copy2 = Object.assign({}, original);       // same thing, older syntax

copy.role = 'guest';
console.log(original.role);   // → 'admin'  ✅ the original is safe
console.log(copy === original); // → false   ✅ genuinely a different object

For arrays it's the same idea: [...list], or list.slice(), or Array.from(list).

This works. It really did make a new object. But it made a shallow copy, and the word "shallow" is doing a lot of load-bearing work.

What "shallow" actually means

A shallow copy walks the object's own keys and copies each value into a new object. And remember what "the value" is for a nested object: an address. So nested objects aren't copied — their sticky notes are.

❌ Buggy
const user = {
  name: 'Ada',
  settings: { theme: 'dark', fontSize: 14 }   // 👈 a nested object
};

const copy = { ...user };
copy.settings.theme = 'light';                // reaching THROUGH the copy...

console.log(user.settings.theme);             // → 'light'  😱 the original changed
console.log(copy.settings === user.settings); // → true     same object!

The analogy I use: you photocopy a document, and the document has a URL on it. The photocopy has its own paper — you can scribble on it without marking the original. But the URL on the copy points at the same web page. Edit that page and both documents now "say" something different.

Shallow copies are not bad. They're the right tool most of the time, especially in React where you usually update one level at a time. The failure mode is specifically reaching through a copy to mutate something nested. If you never do that — if instead you copy each level you're changing — you're fine:

✅ Fixed
const copy = {
  ...user,
  settings: { ...user.settings, theme: 'light' }   // 👈 copy that level too
};

console.log(user.settings.theme);   // → 'dark'  ✅ safe

This nested-spread pattern is the bread and butter of React state updates. It's a bit ugly three levels deep, which is exactly why libraries like Immer exist — but you should be able to write it by hand.

Deep copy option 1: structuredClone (the modern answer)

Since roughly 2022, browsers and Node ship a built-in deep clone. It's global; you don't import anything.

const user = { name: 'Ada', settings: { theme: 'dark' }, tags: ['a', 'b'] };
const clone = structuredClone(user);

clone.settings.theme = 'light';
user.settings.theme;                    // → 'dark'  ✅ fully independent
clone.settings === user.settings;       // → false   ✅

It handles all the things the JSON trick can't: Date objects stay Dates, Map and Set survive, typed arrays survive, NaN and Infinity survive, and — the good one — circular references work.

const node = { id: 1 };
node.self = node;                   // 👈 points at itself

structuredClone(node);              // ✅ works fine
JSON.stringify(node);               // ❌ TypeError: Converting circular structure to JSON

Its limits, which you should be able to name: it throws on functions, on DOM nodes, and on class instances' prototypes — meaning a cloned class instance comes back as a plain object with the right data but no methods and no instanceof. It also drops getters/setters (it copies the resulting value) and ignores property descriptors like non-enumerability.

structuredClone({ save: () => {} });   // ❌ DataCloneError

class Cart { constructor() { this.items = []; } total() { return 0; } }
const cloned = structuredClone(new Cart());
cloned instanceof Cart;                // → false
cloned.total;                          // → undefined  (methods live on the prototype)

Notice that throwing is arguably a feature. It fails loudly rather than silently mangling your data — which is exactly what the next option does.

Deep copy option 2: JSON.parse(JSON.stringify(x)) — and its casualties

This is the trick everyone learns first. Serialize the object to a JSON string, parse it back into a fresh object. Since strings are primitives with no references in them, the round trip severs every connection to the original. It genuinely does deep-copy.

const deepCopy = JSON.parse(JSON.stringify(original));

It's also a shredder. JSON can only represent objects, arrays, strings, numbers, booleans, and null — so anything else is either destroyed or, worse, quietly transformed into something that looks fine until it doesn't.

❌ What it silently destroys
const state = {
  createdAt: new Date('2026-01-01'),
  onSave: () => {},
  middleName: undefined,
  tags: new Set(['a', 'b']),
  index: new Map([['a', 1]]),
  score: NaN,
  budget: Infinity,
};

JSON.parse(JSON.stringify(state));
// → {
//     createdAt: '2026-01-01T00:00:00.000Z',  👈 a STRING now. .getTime() explodes.
//     tags: {},                               👈 empty object. data gone.
//     index: {},                              👈 empty object. data gone.
//     score: null,                            👈 NaN became null
//     budget: null,                           👈 Infinity became null
//   }
//   onSave: key removed entirely
//   middleName: key removed entirely

// and two things don't degrade quietly — they throw:
JSON.stringify({ id: 123n });      // ❌ TypeError: BigInt not serializable
JSON.stringify(circularObject);    // ❌ TypeError: circular structure

Rank the damage by how long it takes to notice:

  1. Circular references throw immediately. Loud, instant, easy to fix. Fine.
  2. Functions and undefined disappear. You notice when something stops working.
  3. Map/Set become {}. Total silent data loss. Nasty.
  4. Date becomes a string. The absolute worst, because it keeps working. It prints correctly, it sorts correctly (ISO strings sort chronologically!), it survives your tests — and then three weeks later something calls .getFullYear() on it in production and you get is not a function.

Also worth knowing: it's slow. Serializing to a string and re-parsing burns CPU on large structures. And it respects toJSON() methods, which is exactly why Dates come back as strings — Date.prototype.toJSON exists and returns an ISO string.

So when is it acceptable? When your data is genuinely plain JSON — which, to be fair, describes most API responses. If you're cloning something that came straight from await res.json() and hasn't been touched, the round trip is lossless by definition. Just say that out loud in an interview rather than pretending the technique is fine in general.

Deep copy option 3: lodash.cloneDeep

The pre-structuredClone industry standard, still the most capable option:

import cloneDeep from 'lodash/cloneDeep';
const clone = cloneDeep(state);

It handles everything structuredClone does, plus it preserves prototypes (class instances stay instanceof) and copies functions by reference rather than throwing. The cost is a dependency and bundle weight (import the single module, not all of lodash). Reach for it when you're cloning class instances or objects with methods; otherwise structuredClone is free and built in.

10. Object.freeze and real immutability

If mutation is the problem, can't we just ban it? Object.freeze is JavaScript's attempt:

const config = Object.freeze({ apiUrl: '/api', retries: 3 });

config.retries = 5;        // silently does nothing (throws in strict mode / modules)
config.timeout = 1000;     // can't add either
delete config.apiUrl;      // can't delete either

console.log(config.retries);   // → 3
Object.isFrozen(config);       // → true

Two things to know, and both are interview bait.

First: it's shallow. Same word, same problem as copying. Freeze locks the top-level keys; nested objects are untouched.

❌ Buggy
const config = Object.freeze({
  api: { url: '/api', key: 'secret' }
});

config.api = {};                // ❌ blocked — good
config.api.url = '/hacked';     // ✅ allowed — the nested object isn't frozen!
console.log(config.api.url);    // → '/hacked'

The lock is on the front door, not on the individual rooms. To lock everything you recurse — a "deep freeze":

✅ Fixed
function deepFreeze(obj) {
  for (const value of Object.values(obj)) {
    if (value && typeof value === 'object') deepFreeze(value);
  }
  return Object.freeze(obj);
}

Second: const and freeze protect different things, and confusing them is extremely common. Go back to the boxes-and-warehouse picture:

  • const locks the box. You can't put a different sticky note in it — no reassignment.
  • Object.freeze locks the thing in the warehouse. You can't rearrange its contents.
const list = [1, 2, 3];
list.push(4);        // ✅ fine! we didn't reassign `list`, we mutated the array
list = [];           // ❌ TypeError: Assignment to constant variable

const frozen = Object.freeze([1, 2, 3]);
frozen.push(4);      // ❌ TypeError: Cannot add property 3

So: is Object.freeze "enough for immutability"? For a small config object at module level, sure. For application state, no — it's shallow, it fails silently in sloppy mode (making bugs hard to spot), it has a real performance cost if you freeze large structures on every update, and it doesn't stop anyone from swapping the whole reference. In practice teams get immutability from discipline plus tooling — always creating new objects, with Immer or a linter enforcing it — rather than from freezing.

11. Why React cares so much

Everything above converges here, so let's connect it explicitly. This is self-contained — you don't need to know React deeply to follow it.

React's core job is deciding when to re-render. Comparing two big state objects property-by-property, on every update, for every component, would be brutally slow. So React does the cheap thing instead: it compares references, using Object.is (essentially ===).

"Is the new state the same object as the old state? Yes → nothing changed, skip. No → something changed, re-render."

That's fast — comparing two addresses is a single machine instruction. But it comes with a contract: if you change data, you must also change the reference. Mutate in place and the address stays the same, so React looks, sees the same address, and concludes nothing happened.

❌ Buggy
const [todos, setTodos] = useState([]);

function addTodo(text) {
  todos.push({ text, done: false });   // mutates the existing array
  setTodos(todos);                     // same address as before...
}
// React: "todos === todos? Yep. Nothing to do." → UI never updates 😤
✅ Fixed
function addTodo(text) {
  setTodos([...todos, { text, done: false }]);   // brand new array, new address
}
// React: "different reference → re-render." ✅

The maddening part is that mutation sometimes appears to work, because an unrelated state update triggers a re-render and your mutated data shows up late. That's the worst kind of bug: intermittent, and it makes you doubt the framework instead of the code.

The same reference check drives three other things you'll be asked about:

// 1. useEffect dependencies — compared with Object.is
useEffect(() => {
  fetchResults(filters);
}, [filters]);
// if `filters` is an object rebuilt inline on every render, it's a new address
// every time → the effect fires every render → infinite loop territory.

// 2. React.memo — shallow-compares props by reference
<UserCard user={{ name: 'Ada' }} />
// new object literal each render → memo never helps.

// 3. useMemo / useCallback exist precisely to keep a reference STABLE
const filters = useMemo(() => ({ status, sort }), [status, sort]);

So the whole memoization story in React is: reference equality is cheap, references change whenever you build a new object, and useMemo/useCallback are tools for holding a reference still across renders. It's the same one idea from section 2, wearing a hat.

12. Comparing two objects

We keep hitting "but what if I want to compare contents?" Let's answer it properly. There are three levels.

Reference equality — a === b. Same object? Instant. This is what React uses.

Shallow equality — same keys, and each value passes ===. One level deep. This is what React.memo does to props.

function shallowEqual(a, b) {
  if (Object.is(a, b)) return true;
  if (typeof a !== 'object' || a === null) return false;
  if (typeof b !== 'object' || b === null) return false;

  const keysA = Object.keys(a);
  if (keysA.length !== Object.keys(b).length) return false;

  return keysA.every((key) => Object.is(a[key], b[key]));
}

shallowEqual({ a: 1 }, { a: 1 });          // → true
shallowEqual({ a: { b: 1 } }, { a: { b: 1 } });  // → false  👈 nested objects differ by ref

Deep equality — recurse all the way down. In production, use lodash.isEqual or fast-deep-equal. But be able to sketch one, because it's a classic whiteboard question:

function deepEqual(a, b) {
  if (Object.is(a, b)) return true;                      // primitives + same ref + NaN
  if (typeof a !== 'object' || a === null) return false;
  if (typeof b !== 'object' || b === null) return false;
  if (Array.isArray(a) !== Array.isArray(b)) return false;

  const keys = Object.keys(a);
  if (keys.length !== Object.keys(b).length) return false;

  return keys.every((key) =>
    Object.prototype.hasOwnProperty.call(b, key) && deepEqual(a[key], b[key])
  );
}

Mention the limitations before the interviewer does — it doesn't handle Date, Map, Set, or circular references (which would infinitely recurse; a real implementation keeps a WeakMap of visited pairs). Naming your own gaps reads as senior.

A common misconception

"You can compare objects with JSON.stringify(a) === JSON.stringify(b)."

Tempting, and it works for simple flat data — but it's key-order sensitive, which makes it wrong far more often than people realize:

JSON.stringify({ a: 1, b: 2 }) === JSON.stringify({ b: 2, a: 1 });
// → false  👈 same data, different insertion order

Plus it inherits every JSON casualty from section 9 (undefined keys vanish, Dates stringify, Maps empty out) and it throws on circular refs. Fine for a quick console.log comparison; never in shipped logic.

13. The interview layer

These topics are asked constantly — == vs === is probably the single most common JS interview question in existence, and the copying question is right behind it. The good news is that the bar for a great answer is low, because most candidates recite "== does type coercion" and stop. Going one level deeper is easy signal.

How this gets asked

The literal phrasings you'll hear:

  • "What's the difference between == and ===?"
  • "Explain type coercion in JavaScript."
  • "What are the falsy values?"
  • "What's the difference between null and undefined?"
  • "What's the difference between a shallow copy and a deep copy?"
  • "How would you deep clone an object?"
  • "Why does React tell you not to mutate state?"
  • Or, most often, they just write [] == false on the board and watch your face.

Recall vs. depth: the falsy list and "=== checks type too" are recall — answer fast and move on, lingering makes you look junior. Coercion chains, deep-clone tradeoffs, and the React connection are depth questions — that's where you slow down and show your reasoning.

Model answer: == vs ===

Say this out loud

"=== checks type and value with no conversion — if the types differ, it's immediately false. == tries to coerce the operands to a common type first, following a specific algorithm: booleans become numbers, strings compared to numbers become numbers, and objects get converted to primitives via valueOf then toString. That chaining is why you get things like [] == false being true — the array stringifies to empty string, which numifies to zero, and false is also zero. I use === everywhere because it has one rule instead of a decision tree. The one exception is x == null, which is a clean way to check for null or undefined in a single comparison."

Why it lands: you named the actual mechanism (ToPrimitive) rather than saying "it does weird stuff," you traced one notorious case, you gave a practical stance, and the == null exception shows you've formed an opinion rather than memorized a rule. That last bit is what separates a 3 from a 4.

Model answer: shallow vs. deep copy

Say this out loud

"Objects are held by reference, so assignment just copies the pointer — both variables point at the same object. Spread or Object.assign gives you a real new object, but only one level deep: nested objects are still shared by reference, so mutating copy.settings.theme also changes the original. For a genuine deep copy I'd reach for structuredClone — it's built in, handles Dates, Maps, Sets and circular references, and throws on functions instead of silently dropping them. I'd avoid JSON.parse(JSON.stringify()) for anything but plain JSON, because it turns Dates into strings and Maps into empty objects without telling you."

Why it lands: you started from the reference model instead of jumping to techniques, you gave a concrete failure case, and you named a specific silent-corruption example. Interviewers are listening for whether you understand why shallow is shallow, not whether you can list clone methods.

Follow-ups (this is the valuable part)

"When would you ever actually use ==?"

One place: x == null, to check for null-or-undefined in a single comparison. It's safe precisely because the loose-equality rules special-case null and undefined to equal each other and nothing else — it won't fire for 0, '', or false. Beyond that, no. If a codebase bans it entirely I'd use === null || === undefined, or restructure so ?? handles it.

"Why not just use == everywhere? It's more forgiving."

Forgiving is the problem. With ===, a reader knows the answer by looking. With ==, they have to mentally execute a multi-step conversion — and the steps compose, so [] == false takes three of them. Forgiving also hides real bugs: if you're comparing a string to a number, something upstream probably didn't parse correctly, and === surfaces that instead of papering over it.

"Why is typeof null 'object'?"

A bug from the original 1995 implementation. Values carried a type tag in their low bits, 000 meant "object pointer," and the null pointer was all zeros — so it read as an object tag. It was proposed for a fix in ES6 and rejected because too much existing code relies on the current behaviour. So it's permanent. Practically, an isObject check needs typeof x === 'object' && x !== null.

"How do you deep clone an object?"

structuredClone(obj) is the modern built-in answer — it handles nested structures, Dates, Maps, Sets, typed arrays, and circular references, and it's available in all current browsers and Node 17+. It throws on functions and loses class prototypes, so if I need those I'd use lodash's cloneDeep. If the data is guaranteed plain JSON, the JSON.parse(JSON.stringify()) round trip is lossless, but I wouldn't use it as a general tool. And often the honest answer is that I don't need a deep clone at all — I need to copy the one path I'm changing, with nested spreads.

"What's wrong with JSON.parse(JSON.stringify(x))?"

It only round-trips things JSON can represent. Functions and undefined properties get dropped, Map and Set become empty objects, NaN and Infinity become null, BigInt throws, and circular references throw. The most dangerous one is Date, which becomes an ISO string — it still prints and sorts correctly, so it passes review and tests, and then fails in production the first time something calls a Date method on it. It's also slow, since you're serializing and re-parsing.

"?? vs || — when does the difference actually bite?"

Whenever a falsy value is legitimate data. || falls back on the entire falsy list, so fontSize || 16 overrides a user's deliberate 0, name || 'Anon' overrides a deliberately cleared field, and enabled || true is an expression that can literally never return false — a setting nobody can switch off. ?? triggers only on null and undefined, which is almost always the intent. I default to ?? and use || only when I explicitly want empty-string-or-zero to fall through.

"Why does React need me to not mutate state?"

React decides whether to re-render by comparing the old and new state with Object.is — a reference comparison, because comparing deeply on every update would be too slow. If you mutate an object in place, the reference doesn't change, so React sees identical addresses and skips the render. The same reference check drives useEffect dependency arrays and React.memo, which is also why rebuilding an object inline on every render makes memoization useless and can make effects fire in a loop. It's one mechanism showing up in three places.

"How do you compare two objects for equality?"

=== only tells you if they're the same object, so you pick a level. Reference equality is what React uses. Shallow equality — same keys, values compared with === — is what React.memo does to props and it's usually enough. Deep equality means recursing, which I'd do with lodash.isEqual or fast-deep-equal rather than hand-rolling, though I can write a basic version. What I wouldn't do is compare JSON.stringify output, because it's sensitive to key order — {a:1,b:2} and {b:2,a:1} come out different.

"Is Object.freeze enough for immutability?"

Not on its own. It's shallow — it locks the top-level properties but nested objects stay mutable, so you'd need a recursive deep-freeze. It also fails silently outside strict mode, so a mutation just quietly does nothing rather than erroring. And freezing large structures on every state update costs real time. In practice I'd treat it as a guard rail for constants or something you turn on in development, and get actual immutability from always creating new objects — with Immer or a lint rule enforcing it if the codebase needs help.

"Is const the same as immutable?"

No, and they're the classic mix-up. const prevents reassigning the variable — you can't point it at a different object. It says nothing about the object itself, so const list = []; list.push(1) is completely legal. const locks the label; Object.freeze locks the contents.

"Why isn't NaN equal to itself?"

It comes from IEEE-754, the floating point standard, not from JavaScript. NaN represents "this computation had no meaningful numeric result," and two failed computations aren't meaningfully the same value, so the standard defines every comparison involving NaN as false. The practical consequence is you can't test for it with === — you use Number.isNaN(), not the old global isNaN(), which coerces its argument first and reports true for any non-numeric string.

"What does {...obj} not copy?"

Nested objects — those are shared by reference. It also only copies own, enumerable properties, so inherited prototype properties and non-enumerable ones don't come along, and getters are evaluated and copied as plain values rather than staying getters. For arrays, [...arr] has the same shallowness: the array is new, the objects inside it are the originals.
