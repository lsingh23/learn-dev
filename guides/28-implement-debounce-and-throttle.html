Implementing debounce and throttle

Two tiny functions that get asked constantly. Both are about six lines. The interview is really about whether you know why those six lines work.

The problem

You've got a search box that fetches on every keystroke:

input.addEventListener('input', (e) => {
  fetch('/api/search?q=' + e.target.value).then(showResults);
});

Type laptop and you fire six requests. Five are garbage, and they can come back out of order and overwrite the good one. What you actually want is: wait until the user stops typing, then fire once. That's debounce.

Different problem — a scroll progress bar. Scroll fires ~60 times a second. Waiting for the user to stop is useless here; the bar needs to move during the scroll. What you want is: run it, but at most once every 100ms. That's throttle.

  • Debounce — wait for quiet.
  • Throttle — enforce a rhythm.

Building debounce

The one thing you need to know: setTimeout returns an ID, and clearTimeout(id) cancels the pending timer before it fires. Debounce is just cancel-and-restart, over and over.

In words: every call cancels the previous timer and starts a fresh one. Only a full quiet period lets the timer survive to fire.

Step 1 — the shape
function debounce(callback, delay) {
  return function () {
    // ...
  };
}

A function that takes a function and returns a function. That gap between the two — the body of debounce — is where we stash the timer ID. It's private (nobody outside can touch it) and it persists between calls, because the returned function closes over it.

Step 2 — cancel and restart
function debounce(callback, delay) {
  let timerId;                       // 👈 survives between calls

  return function () {
    clearTimeout(timerId);           // kill whatever was pending
    timerId = setTimeout(callback, delay);
  };
}

That's a working debounce. Trace it at 300ms: keystroke at 0ms schedules a timer for 300ms. Keystroke at 90ms kills it and schedules 390ms. And so on. Stop typing at 500ms, nothing kills the timer, it fires at 800ms. One call.

Forwarding arguments and this

Attach that to the search box and it breaks: the callback gets no event. Our wrapper is a middleman, and right now it's swallowing the message. Forward it:

return function (...args) {                     // gather whatever we were called with
  clearTimeout(timerId);
  timerId = setTimeout(() => callback(...args), delay);   // hand it through
};

One more leak. If someone attaches the debounced function as an object method, this is lost by the time the timeout runs — callback(...) is a bare call. So capture and restore it:

✅ The version to write in an interview
function debounce(callback, delay) {
  let timerId;

  return function (...args) {
    const context = this;                        // 👈 whoever called us
    clearTimeout(timerId);
    timerId = setTimeout(() => {
      callback.apply(context, args);             // 👈 restore it
    }, delay);
  };
}

Two deliberate choices there. The outer function is a normal function, not an arrow — arrows have no this of their own, so there'd be nothing to capture. The inner one is an arrow, precisely because it inherits this from around it. And apply (rather than call) because we're already holding an array.

Wait — does the this part actually matter?

In modern arrow-heavy code, rarely. But the interviewer is asking a this question in disguise. Write it, and say so: "I'm forwarding this so it still works as an object method — rarely matters in practice, but a shared utility shouldn't assume."

Cancelling

A pending timer that fires after your component unmounts is a real bug. Hang a cancel on the returned function — it closes over the same timerId:

function debounce(callback, delay) {
  let timerId;

  function debounced(...args) {
    const context = this;
    clearTimeout(timerId);
    timerId = setTimeout(() => callback.apply(context, args), delay);
  }

  debounced.cancel = () => clearTimeout(timerId);   // 👈 functions are objects
  return debounced;
}

Building throttle

Run immediately, then ignore everything for the next interval ms. A turnstile: it lets one person through, then locks for a beat, regardless of how many are pushing.

✅ Throttle, simplest version
function throttle(callback, interval) {
  let cooling = false;

  return function (...args) {
    if (cooling) return;                // 👈 inside the window? drop it

    callback.apply(this, args);         // fire straight away
    cooling = true;
    setTimeout(() => { cooling = false; }, interval);
  };
}

At 100ms with scroll events every 16ms: fires at 0ms, drops the next six, opens again at 100ms. Sixty calls a second becomes ten.

There's a second common way to write it, with a timestamp instead of a timer. Same behaviour, nothing to leak — either is fine:

function throttle(callback, interval) {
  let lastRun = 0;

  return function (...args) {
    const now = Date.now();
    if (now - lastRun < interval) return;
    lastRun = now;
    callback.apply(this, args);
  };
}
A common misconception

"Throttle guarantees a call every interval ms." No — it only runs when an event actually arrives. If events stop mid-window, the last one is dropped entirely. For a progress bar that means it can settle slightly short. Fixing it means storing the last args and firing them when the window closes (a "trailing call") — worth mentioning, not worth writing unless asked.

Which one, when

Ask: do I care about the final value, or about a steady stream?

SituationPickWhy
Search-as-you-typeDebounceOnly the finished query matters.
Autosave a draftDebounceSave on pause, not mid-word.
Scroll / resize handlerThrottleMust update during the action.
Mousemove drag previewThrottleContinuous feedback, capped cost.
Double-click on SubmitThrottleFirst click counts, rest don't.

For scroll-linked animation specifically, requestAnimationFrame beats a time-based throttle — it runs once per frame, exactly when the browser is about to paint. Good thing to mention.

The interview layer

How it gets asked

  • "Implement debounce." / "Implement throttle."
  • "Difference between debounce and throttle? When would you use each?"
  • "Our search box fires a request per keystroke — how would you fix it?" (same question, in scenario form — the most common shape)
🗣 Model answer — "what's the difference?"

"Both limit how often a function runs, but they answer different questions. Debounce waits for a pause — every call resets a timer, so it fires once the events stop. That's search-as-you-type, where only the final query matters. Throttle enforces a rate — it runs immediately, then ignores calls for a fixed window. That's scroll or mousemove, where you need updates during the interaction, just not sixty a second. The code reflects that: debounce holds a timer ID it keeps clearing, throttle holds a flag or a timestamp."

That lands because you gave the mechanism and a concrete use case for each. "Debounce delays, throttle limits" sounds memorised.

Follow-ups

"Why not just setTimeout in the handler?"

A bare setTimeout only delays — six keystrokes still schedule six calls, just later. The cancellation is the whole idea.

"Why does the timer ID need to be in a closure?"

It has to survive between calls, so it can't be local to the returned function. A global would work for exactly one debounced function — the second would fight over the same slot. The closure gives each one its own private timer, which is what makes debounce reusable.

"Why apply instead of callback(...args)?"

Only to forward this. Arguments would forward fine either way.

"What does a debounced function return?"

Nothing useful — at call time the real function hasn't run yet. If you need the result, have the callback resolve a promise or set state. Good one to raise unprompted.

"How do you use debounce in React?"

The trap: const search = debounce(fn, 300) in the component body creates a brand new debouncer with a fresh empty timer on every render, so nothing is ever debounced. Create it once — useMemo(() => debounce(fn, 300), []) or a ref — and call .cancel() in the effect cleanup.

"Your throttle drops the last event — bug?"

A tradeoff. For a progress bar you want a trailing call so the UI settles correctly. For an analytics ping, dropping it is right. I'd default to the simple version and add trailing only when the UI visibly ends up wrong.

Traps

  • Not forwarding arguments. Works in a toy test, breaks on any real handler.
  • Returning an arrow from debounce. Kills this forwarding silently.
  • Calling debounce() inside the handler. New debouncer per event → every call fires. It must be called once, and the result is what you attach.
  • Saying "throttle delays the call." It doesn't — it fires immediately, then blocks. Saying otherwise reads as having them mixed up.

Cheat sheet

  • Debounce — every call resets the timer; only the last in a burst runs.
  • Throttle — run now, ignore calls for a fixed window.
  • Closure — private, persistent storage for the timer/flag, per instance.
  • ...args + apply — forward arguments and this; the wrapper is a middleman.
  • Cancel — debounced.cancel = () => clearTimeout(timerId); call it on unmount.
  • React — create the debounced fn once (useMemo/ref), never inline.
  • Scroll animation — prefer requestAnimationFrame.

  let timerId;
  return function (...args) {
    const ctx = this;
    clearTimeout(timerId);
    timerId = setTimeout(() => fn.apply(ctx, args), delay);
  };
}
