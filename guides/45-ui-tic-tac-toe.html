The state shape (and the flat-vs-nested decision)

Step 2 of the framework, as always. And here the very first decision is a real one: is the board a flat Array(9) or a 3×3 nested array?

Flat. Every time. Indices 0–8, one .map() to render, win-lines are just triples of numbers, and on the rare occasion you need geometry you get it for free with row = Math.floor(i / 3) and col = i % 3. Nested arrays buy you board[r][c] and charge you for it everywhere else: two loops to render, two loops to check, .map(row => [...row]) to copy without mutating. Say that in one breath and move on — it's a ten-second answer that reads as experience.

So, before any JSX, the comment block:

// state:
//   board → Array(9) of 'X' | 'O' | null      ← that's it. genuinely.
// derived:
//   xIsNext  → board.filter(Boolean).length % 2 === 0
//   result   → calculateWinner(board) → { player, line } | null
//   isDraw   → !result && board.every(Boolean)
//   isOver   → result || isDraw
//   status   → a string built from the three above

The reveal: you only need one piece of state

Quick question before you write a single useState: how many things does this game actually need to remember?

One. The board. That's the whole memory of the game.

Whose turn it is? Count the filled cells — if it's even, X plays. Who won? Run a function over the board. Is it a draw? Board full, nobody won. Is the game over? Winner or draw. The status message? A string assembled from those. Not one of them can disagree with the board, because not one of them exists independently of it.

Keeping xIsNext as state is defensible — but it's already a second source of truth, and it's the thing that breaks the moment you add undo. I'd derive it.

❌ The classic mistake
const [board, setBoard] = useState(Array(9).fill(null));
const [winner, setWinner] = useState(null);  // 👈 now two things can disagree
const [isOver, setIsOver] = useState(false); // 👈 and now three

Look at what you just signed up for. Every handler must update all three in the right order. Reset must clear all three. Undo must recompute all three. And if you ever forget one — and under interview pressure you will — you get a board showing a completed line with a status bar cheerfully saying "Next player: O". That bug is invisible in your head and extremely visible on the screen.

✅ One source of truth
const [board, setBoard] = useState(Array(9).fill(null));

const xIsNext = board.filter(Boolean).length % 2 === 0;
const result  = calculateWinner(board);              // { player, line } | null
const isDraw  = !result && board.every(Boolean);
const isOver  = Boolean(result) || isDraw;

This is the purest example of the derived-data rule in the whole series. Nine cells of state and a game that cannot enter an inconsistent state, because there's nothing to keep in sync. Say the sentence out loud while you type it: "if I can compute it, I won't store it."

Win detection as data, not logic

The instinct is to write the checks. Three ifs for rows, three for columns, two for diagonals, and a lot of &&. Don't. Encode the rules as data and write one loop over them.

const LINES = [
  [0,1,2], [3,4,5], [6,7,8],  // rows
  [0,3,6], [1,4,7], [2,5,8],  // columns
  [0,4,8], [2,4,6],           // diagonals
];

function calculateWinner(board) {
  for (const line of LINES) {
    const [a, b, c] = line;
    if (board[a] && board[a] === board[b] && board[a] === board[c]) {
      return { player: board[a], line };   // 👈 return the line too
    }
  }
  return null;
}

Returning the winning line alongside the symbol costs one word and buys you the highlight-the-winning-cells polish for free. Interviewers ask for it roughly always. And notice the function is pure: board in, result out, no React, no state. That means it's the bit you can reason about, test, and reuse when the grid grows.

The click handler, five lines

function handleClick(i) {
  if (board[i] || isOver) return;        // 👈 both guards
  const next = [...board];               // copy, never mutate
  next[i] = xIsNext ? 'X' : 'O';
  setBoard(next);
}

Two guards, and candidates reliably write only the first. Without isOver the game happily keeps accepting moves after someone has won — you fill in the remaining squares while the banner says X won. It's a one-word fix and a very cheap point.

The copy matters just as much: board[i] = ... mutates the array React is already holding, so Object.is sees the same reference and nothing re-renders. If your clicks "do nothing", this is why.

Rendering the grid

<div style={{ display:'grid', gridTemplateColumns:'repeat(3, 64px)', gap:4 }}>
  {board.map((cell, i) => (
    <button
      key={i}
      onClick={() => handleClick(i)}
      disabled={Boolean(cell) || isOver}
      className={result?.line.includes(i) ? 'cell win' : 'cell'}
    >{cell}</button>
  ))}
</div>
<p aria-live="polite">{status}</p>

Real <button> elements, not divs — free keyboard support and free screen-reader semantics, and disabled communicates "taken" without you writing anything. key={i} is genuinely fine here, the rare case where an index key is correct: the cells never reorder. And aria-live on the status line means the outcome is announced rather than silently appearing.

The four upgrades they'll ask for

Reset — one line

<button onClick={() => setBoard(Array(9).fill(null))}>New game</button>

It's one line precisely because everything else was derived. In the three-state version above, reset is three lines and one of them is easy to forget. This is the moment to point back at your state shape and say so.

N×N with K in a row — a parameter, not a rewrite

Because the board is flat and the lines are data, generating the rules for any size is a small function:

function buildLines(n) {
  const lines = [];
  for (let r = 0; r < n; r++) lines.push([...Array(n)].map((_, c) => r * n + c));
  for (let c = 0; c < n; c++) lines.push([...Array(n)].map((_, r) => r * n + c));
  lines.push([...Array(n)].map((_, i) => i * n + i));          // ↘ diagonal
  lines.push([...Array(n)].map((_, i) => i * n + (n - 1 - i))); // ↙ diagonal
  return lines;
}

Everything downstream is untouched: calculateWinner becomes line.every(i => board[i] === board[line[0]]) and works for any length. If they want K-in-a-row on a bigger board (Gomoku), you generate every K-length window in each direction instead — same idea, still data. That's a strong senior signal, and it only exists because of the flat choice you made in minute two.

Move history and time travel

The React-docs classic, and it's the pointer shape from guide 34 laid on top of what you already have. State becomes a list of boards plus an index into it; the current board stops being state entirely.

const [history, setHistory] = useState([Array(9).fill(null)]);
const [move, setMove] = useState(0);
const board = history[move];                     // 👈 derived again

function play(next) {
  const trimmed = [...history.slice(0, move + 1), next]; // drop redone futures
  setHistory(trimmed);
  setMove(trimmed.length - 1);
}

Undo is setMove(move - 1). Note the slice: jumping back and then playing must discard the abandoned future, or your history branches. And note that xIsNext and the winner still derive correctly at any point in history — because they derive from board, and board is just whatever the pointer points at. Had you stored the winner, time travel would have been a rewrite.

An AI opponent

The trivial version is one line — pick a random empty index in an effect after the human moves; the real version is minimax with alpha-beta pruning over the same pure calculateWinner. Mention both, and don't start here: an unfinished board with a half-written minimax scores far worse than a finished game you then describe upgrading.

The general grid-game recipe

Every grid game is the same three moves. (a) A flat array of cells, one entry per square, holding the smallest thing that describes that square. (b) Every rule expressed as a pure function of that array — winner, legal moves, score, game-over. (c) Configuration as data rather than branching logic: win lines for tic-tac-toe, the eight neighbour offsets [-n-1, -n, -n+1, -1, +1, n-1, n, n+1] for Minesweeper's mine counting and flood fill, the six column drop-points for Connect Four, the per-letter green/yellow/grey scoring pass for Wordle. Same skeleton, different data table.

What they're scoring

Not whether the game works — it will. It's whether you said "the board is the only state" before writing code, whether your rules live in a pure function they could unit-test, and whether the follow-up ("now make it 5×5") costs you a parameter or a rewrite.

Follow-ups, and what to say

"Why not store the winner in state?"

Because then the winner and the board can disagree, and keeping them in sync becomes my job in every handler. The winner is a pure function of the board, so I compute it during render — it's one pass over nine cells, and it can never be stale.

"How would you make it 5×5 with 4-in-a-row?"

The board is already flat, so it's Array(n * n) and a CSS repeat(n, 1fr). The only real work is generating the win lines — every 4-length window along each row, column and diagonal. calculateWinner doesn't change: it still just looks for a line where every cell equals the first and isn't null.

"How do you add undo?"

I'd move to a history array of boards plus a current-move pointer, and derive the board from history[move]. Undo is decrementing the pointer. Playing after an undo has to slice off the abandoned future first, otherwise history branches.

"Why a flat array rather than 3×3?"

Win lines become triples of indices instead of coordinate pairs, rendering is a single map, and copying immutably is one spread instead of a nested map. When I do need geometry it's Math.floor(i / 3) and i % 3. Nested arrays make every helper about twice as long and buy nothing here.

Cheat sheet

  • One piece of state: the board. Flat Array(9).fill(null).
  • Flat beats nested — index triples, one map, one spread to copy. row = Math.floor(i/3), col = i % 3 when needed.
  • Derive everything else: turn (parity of filled cells), winner, draw, game-over, status.
  • Never store the winner. Two sources of truth, one of them always stale.
  • Rules as data: a LINES table plus a four-line pure calculateWinner.
  • Return the winning line, not just the symbol — free highlighting.
  • Two guards in the handler: cell taken and game over.
  • Copy, don't mutate — const next = [...board], or nothing re-renders.
  • Real <button>s, disabled when filled; aria-live on the status.
  • Upgrades in order: reset (one line) → N×N (generate lines) → history + pointer for undo → AI last, if ever.
  • Any grid game: flat cells + pure rule functions + config data (win lines, neighbour offsets).
